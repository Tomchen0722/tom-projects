## 1. 文件目的

本文件用來統一團隊對「要做什麼、怎麼做、做到什麼程度才算完成」的理解，避免在開發期間出現下列情況：

- 同一個分數由不同成員用不同公式計算。
- 前端畫面顯示新版五科分數，但後端仍沿用舊生活機能百分比。
- 資料不足、套件失敗或語言不支援時，被錯誤當成 0 分或中立。
- UI 看起來完成，但排序、明細與推薦理由無法重現分數。
- 為趕進度而擅自修改已經由組長確認的評分規則。

本專案的核心目標是：

> 先排除不符合必要條件的房源，再用交通、生活、價格、口碑、設備五科成績單比較；每一分都能說明原因。

### 1.1 三份根目錄文件的分工

- `AGENTS.md`：供 AI 程式代理讀取的強制工作規則，內容應精簡、可執行並清楚界定修改範圍。
- `專案執行準則.md`：供全組共同確認的產品規格、協作流程、測試與驗收標準；本文件為正式基準。
- `AI_README.md`：記錄現行技術架構、目前開發進度及已做出的重要實作決定。

三份文件不得互相複製整段內容。`AGENTS.md` 應引用本文件；技術現況以 `AI_README.md` 與實際程式為證據，但現行程式若不符合已核准規格，應登記為待處理差異，不得反過來默默改寫規格。

本文件第 2.3～2.6 節的協作與邊界規則適用整個儲存庫；第 3 節以後的五科評分、租客端 NLP、UI 與驗收細節，主要適用於租客入口。房東入口與後台分析另有任務時，不要求套用租客頁資訊架構，但不得破壞共用契約。

### 2.1 本次要完成的內容

1. 將租客入口由舊版「生活機能百分比排序」改為新版「五科各 5 分、總分 25 分」。
2. 依使用者最在意的兩科進行第一層排序，再以總分等規則處理同分。
3. 將新版分數、分數拆解、推薦理由與注意事項呈現在租客入口。
4. 將房源詳細分析頁改為可理解的四個區塊：
   - 房源總覽

## 3. 專案核心原則

### 3.1 先篩選，再評分

下列屬於「必要條件」，不參加加減分：

- 行政區或地點
- 房型
- 預算範圍
- 可住人數
- 必備設備

不符合必要條件的房源直接排除，不允許靠其他科目高分補回來。

### 3.2 五科必須同一尺度

每一科均為 0～5 分，總分為 0～25 分：

```text
總分 S = 交通分 T + 生活分 L + 價格分 Pscore + 口碑分 R + 設備分 E
```

任何畫面、排序、圖表與匯出資料，都必須使用同一套分數。

### 3.3 每一分都要能解釋

系統不可只輸出「21.5 分」，必須能顯示：

- 每科得分
- 小指標得分
- 原始數據
- 得分原因
- 資料不足或限制提醒
- 評分規則版本

### 3.4 資料不足不等於 0 分

資料缺失時不得硬猜，也不得默認為低分：

- 缺少核心欄位：顯示「資料不足，暫不排名」。
- NLP 不支援：顯示「無法分析」，不算中立。
- 價格比較樣本不足：標示「比較樣本較少」。
- 設備欄位不完整：標示「設備資料不完整」。

### 3.5 總分不是品質或安全保證

畫面需保留適當提醒：

> 綜合分數僅協助使用者決定優先查看順序，不代表安全、品質、訂房成功或交易保證。

## 4. 新版評分規則（唯一正式基準）

> 本節未經組長書面確認，不得擅自修改門檻、配分或排序順序。

## 4.1 第一科：交通方便（0～5 分）

### 捷運方便度（0～3 分）

| 最近捷運出口直線距離 | 分數 |
|---|---:|
| 400 公尺以內 | 3 |
| 401～800 公尺 | 2 |
| 801～1,200 公尺 | 1 |
| 超過 1,200 公尺 | 0 |

### 公車方便度（0～2 分）

| 最近公車站牌直線距離 | 分數 |
|---|---:|
| 300 公尺以內 | 2 |
| 301～600 公尺 | 1 |
| 超過 600 公尺 | 0 |

```text
交通分 T = 捷運分 M + 公車分 B
```

實作限制：

- 使用最近一個有效 POI，不以出口或站牌數量累加。
- 距離可用 Haversine 計算。
- 前台必須標示「直線距離估計」，不可稱為步行距離。
- POI 缺失或房源無座標時，不可直接給 0 分。

## 4.2 第二科：生活便利（0～5 分）

| 項目 | 達成條件 | 分數 |
|---|---|---:|
| 超商或超市 | 500 公尺內至少 1 個不重複地點 | 2 |
| 餐飲 | 800 公尺內至少 5 個不重複地點 | 1 |
| 診所 | 1 公里內至少 1 個不重複地點 | 1 |
| 公園 | 1 公里內至少 1 個不重複地點 | 1 |

```text
生活分 L = 超商／超市分 C + 餐飲分 F + 診所分 H + 公園分 P
```

實作限制：

- 必須先去重再計數。
- 優先依資料 ID 去重；無 ID 時使用「標準化名稱 + 四捨五入座標」。
- 學校不計入固定生活分，可作資訊標籤或額外篩選。
- 設施數量可供使用者查看，但超過門檻後不再無限加分。

## 4.3 第三科：價格合理（1～5 分；資料不足時不計分）

### 比較組

優先使用：

```text
同一行政區 + 相同房型 + 可住人數相差不超過 1 人
```

比較組應至少有 10 間有效房源。少於 10 間時依序放寬：

1. 放寬可住人數條件。
2. 改用同一行政區 + 相同房型。
3. 仍不足時，標示資料不足或比較樣本較少。

### 價格差異率

```text
D = (本房源價格 - 比較組中位價格) ÷ 比較組中位價格 × 100%
```

| 價格差異率 D | 價格分 |
|---|---:|
| D ≤ -10% | 5 |
| -10% < D ≤ 0% | 4 |
| 0% < D ≤ 10% | 3 |
| 10% < D ≤ 25% | 2 |
| D > 25% | 1 |

實作限制：

- 使用中位數，不使用平均數作為主要比較基準。
- 極端價格、缺失價格及格式錯誤須先清理。
- 前台必須顯示比較組條件、中位價格、差異率與樣本數。
- 價格便宜不代表品質好，不可單獨產生「最佳房源」結論。

## 4.4 第四科：住客口碑（0～5 分）

口碑由三個角色組成：

1. Airbnb 整體評分：最高 3 分。
2. NLP 評論內容：最高 2 分。
3. 有效評論數：不加分，只控制口碑最高上限。

### Airbnb 整體評分 A

| Airbnb 平均評分 | A |
|---|---:|
| 4.8～5.0 | 3 |
| 4.5～4.79 | 2.5 |
| 4.2～4.49 | 2 |
| 4.0～4.19 | 1 |
| 低於 4.0 | 0 |
| 沒有評分 | 資料不足 |

### NLP 內容分 N

建議分析最近最多 20 則「語言可支援且內容有效」的評論：

```text
P+ = 正面評論數 ÷ 可分析評論總數
P- = 負面評論數 ÷ 可分析評論總數
N = clamp(1 + P+ - P-, 0, 2)
```

- 正面：加分。
- 負面：扣分。
- 中立：不加不扣，但算在可分析評論分母。
- 無法分析：不算中立，也不放入分母。

### 有效評論數上限 C

| 有效評論數 | 口碑最高分上限 C |
|---|---:|
| 0 | 不計分 |
| 1～4 | 3 |
| 5～19 | 4 |
| 20 以上 | 5 |

```text
原始口碑分 Rraw = A + N
最終口碑分 R = min(Rraw, C)
```

NLP 必守規則：

- 英文使用 VADER。
- 中文使用 jieba + 已核准中文情感詞典／規則。
- 成果展示版本可先限定中文、英文。
- 日文及其他不支援語言標記為無法分析，不硬套英文 VADER。
- 套件未啟用、空白、過短、欄位錯誤都必須提供明確狀態。
- 顯示「總評論數、選取數、有效分析數、無法分析數、分析涵蓋率」。
- 至少人工標註 30～50 則評論進行基本驗證。

### 住客常提到的優點（正面評論解釋圖）

#### 功能定位

本區塊用來回答：「住客在正面評論中，經常稱讚這間房源的哪些地方？」

- 建議 UI 標題使用「住客常提到的優點」，不使用容易誤導的「高頻率關鍵詞（正面）」。
- 本區塊屬於口碑解釋資訊，不是新的評分項目。
- 優點詞、提及數與涵蓋率不得再次加入 NLP 分、口碑分、五科總分或推薦排序，避免同一批評論被重複計分。
- UI 概念圖中的 `clean`、`convenient`、`comfortable`、`mrt` 等文字只是版面示意，不得寫死為固定輸出。

#### 資料來源

- 使用與房源口碑情緒分析相同的近期評論範圍，最多取最近 20 則。
- 優點擷取只能使用其中「語言可支援、內容有效、且情緒分類為正面」的評論。
- 中立、負面、無法分析、空白、重複或明顯無意義評論不得混入正面優點統計。
- 畫面須顯示本次優點整理使用的有效正面評論數。

#### 前處理規則

正式排行前至少完成：

1. 語言辨識與中英文分流。
2. 英文斷詞；中文使用 jieba 或已核准的中文斷詞流程。
3. 英文字母大小寫統一。
4. 移除中英文停用詞，例如 `and`、`the`、`to`、`is`、`very`、`was`、`的`、`了`、`是`、`很`。
5. 排除標點、網址、Email、純數字、單一字母、表情符號、空白與其他無意義雜訊。
6. 排除房源名稱、固定模板文字或其他會在每則評論重複出現、但不能代表房源優點的詞。
7. 使用經團隊確認且具版本紀錄的同義詞／主題映射，例如：
   - `clean`、`cleanliness`、`乾淨`、`整潔` → `環境乾淨`
   - `mrt`、`metro`、`subway`、`捷運站` → `鄰近捷運`
   - `friendly host`、`host`、`房東親切` → `房東友善`

成果展最低可接受版本為「完成停用詞與雜訊清理後的有意義詞語排行」；時間允許時，應進一步整合為中文優點主題。

#### 統計單位

- 圖表數值應代表「有幾則有效正面評論提到此優點」，不得直接使用原始單字總出現次數。
- 同一則評論中，同一優點即使重複出現多次，最多只計 1 則。
- 同一則評論可以同時提到多個不同優點。
- 可同時顯示涵蓋率：`提及該優點的正面評論數 ÷ 有效正面評論數`。

#### 顯示門檻與低樣本保護

| 有效正面評論數 | 呈現方式 |
|---:|---|
| 0 | 不繪圖，顯示「目前沒有足夠的正面評論可整理」。 |
| 1～2 | 不繪製排行，改顯示正面評論摘錄，避免單一住客意見被誤認為共同看法。 |
| 3～4 | 可繪製優點圖，但必須標示「樣本較少，結果僅供參考」。 |
| 5 以上 | 正常繪製優點統計圖。 |

「3 則」是成果展第一版的最低繪圖門檻，不代表統計結果已高度穩定；若日後調整門檻，必須留下版本、原因與測試紀錄。

#### UI 呈現

- 最多呈現 6～8 個有意義的優點。
- X 軸名稱使用「提及正面評論數」。
- hover 建議顯示：優點主題、提及則數、有效正面評論總數與涵蓋率。
- 圖下方應說明資料來源與統計口徑，例如：「根據最近 20 則評論中的 19 則有效正面評論整理；同一則評論對同一優點最多計算一次。」
- 切換房源後，優點圖、計數與支持評論必須依 `listing_id` 同步更新，不得殘留上一間房源結果。

## 4.5 第五科：房源設備（0～5 分）

設備分為兩類：

- 必備設備：缺少即排除。
- 希望設備：符合比例換算成 5 分。

使用者可選 1～5 項希望設備：

```text
E = 符合希望設備數 m ÷ 使用者選擇希望設備數 k × 5
```

限制：

- k 至少為 1；若使用者未選，UI 應要求完成選擇，不可除以 0，也不可私自給 0、3 或 5 分。
- 5 項是「希望設備合計總上限」，不是按下「更多設備」後可以額外再增加 5 項。
- 同一設備不得同時列為必備與希望設備。
- 建立設備同義詞表，例如 WiFi、Wi-Fi、Wireless Internet 視為同一設備。
- 缺少設備資料與明確未提供設備必須分開。

### 4.5.1「更多設備」操作契約

正式按鈕名稱建議使用：

```text
＋選擇其他希望設備
```

「更多設備」按鈕的功能只是在畫面中開啟、展開或顯示完整設備選擇介面；按下按鈕本身不代表設備已被選取，也不得直接改變任何房源分數、總分或排序。

#### 操作狀態

| 使用者動作 | 是否更新已套用偏好 | 是否重新評分 |
|---|---|---|
| 開啟／展開完整設備清單 | 否 | 否 |
| 在視窗中暫時勾選或取消，但尚未按「套用選擇」 | 否 | 否 |
| 按「取消」、關閉視窗或返回 | 否，恢復進入視窗前狀態 | 否 |
| 按「套用選擇」且通過驗證 | 是 | 是 |

實作時應區分：

- `applied_preferred_amenities`：目前已正式套用並參與評分的設備。
- `draft_preferred_amenities`：選擇視窗尚未確認的暫存內容。

不得把暫存勾選立即寫入正式評分狀態，避免使用者尚未確認時，推薦清單與地圖持續跳動。

#### 選擇數量與提示

- 希望設備合計必須為 1～5 個不同設備。
- 顯示 `已選擇 k／5 項`。
- 目前已選 3 項時，最多只能再選 2 項；不是再增加 5 項。
- 達 5／5 後，其他未選設備應停用或阻止選取，並顯示「已選滿 5 項；如需更換，請先移除一項」。
- 嘗試傳入第 6 項、重複設備或未知設備時，前端與後端都必須拒絕；不得靜默截取前 5 項。
- 再次開啟選擇介面時，應正確載入目前已套用的 1～5 項選擇。

限制 5 項的目的不是因為第 6 項無法計算，而是為了讓設備分維持「個人最在意設備的符合程度」，避免使用者勾選大量一般設備後，將真正重要的需求稀釋成設備清單完整度競賽。

#### 套用後的計算影響

按下「套用選擇」後，只重新計算受到設備偏好影響的項目：

- 每間候選房源的設備分 E。
- 五科總分 S。
- 推薦等級、房源卡片、雷達圖與推薦理由。
- 地圖在「房源設備」或「綜合總分」模式下的顏色與 hover。
- 若「房源設備」是最在意兩科之一，重新計算優先分 Q 與第一層排序。
- 若「房源設備」不是最在意兩科之一，Q 不變；但第二層總分排序仍可能改變。

不得因修改希望設備而重新執行交通距離、生活 POI、價格比較或 NLP 情緒分析；這些既有分數應直接重用。

#### 必備與希望設備互斥

- 已列為必備設備者，不得再次選為希望設備。
- UI 應將該設備隱藏、停用或標示「已列為必要條件」。
- 後端收到同一設備同時存在於兩組時，必須回傳驗證錯誤，不得重複篩選又加分。

#### 設備資料狀態

設備判斷應盡量區分：

```text
present：公開清單明確列出
absent：資料來源明確表示未提供
unknown：資料不完整或無法判斷
```

`unknown` 不得直接當作 `absent`。若任一已選希望設備為未知且無核准的缺失處理規則，應標示「設備資料不足」，不得產生看似精確但無法驗證的設備分。

允許 0 項、提高 5 項上限、改變公式或改成不同權重，均屬評分規則變更，必須先經組長確認、更新規則版本與測試。

## 5. 排序規則

使用者必須且只能選擇最在意的兩科：

```text
優先分 Q = 最在意科目 1 分數 + 最在意科目 2 分數
```

### 5.1「最在意的面向」選擇契約

正式規範：

> 「最在意的面向」必須且只能選擇 2 項。未選滿 2 項時，應提示使用者完成選擇；選滿後不得新增第 3 項。選擇結果只用於第一層排序，優先分為兩科分數合計，最高 10 分。其他三科仍納入 25 分總分及詳細展示。

操作狀態：

| 已選數量 | UI 行為 | 排序狀態 |
|---:|---|---|
| 0／2 | 顯示「請選擇最在意的兩個面向」 | 不產生正式個人化排序 |
| 1／2 | 顯示「請再選擇 1 個面向」 | 不產生正式優先分 Q |
| 2／2 | 顯示兩個已選面向，可移除或更換 | 啟用正式第一層排序 |
| 嘗試第 3 項 | 阻止選取並顯示「最多選擇 2 項」 | 不改變既有兩項與排序 |

UI 建議：

- 優先使用支援 `max_selections=2` 的多選元件，欄位名稱為「最在意的兩個面向」。
- 若保留概念圖中的「新增面向」按鈕，按鈕只能在目前少於 2 項時出現；達 2 項後必須隱藏、停用或改為「更換選擇」。
- 「新增面向」的語意只代表加入第 1 或第 2 個面向，不代表可無限制新增。
- 同一面向不得重複選取。
- 兩個面向為同等重要，選擇先後順序不得影響 Q 或排序；例如「交通＋價格」與「價格＋交通」必須得到完全相同結果。
- 使用者移除其中一項後，Q 立即失效並回到 1／2 提示狀態，直到重新選滿 2 項。
- 不得自動加入預設第 2 項而未告知使用者；如專案日後採預設值，必須明確顯示且可修改。

運算限制：

- Q 的範圍固定為 0～10 分。
- Q 只負責第一層排序，不加入 S，不改變任何單科分數。
- 未被選為最在意的其他三科仍完整計入 25 分總分、房源卡、雷達圖、地圖與詳細分析。
- 不得改成三科加總、平均、百分比、排名分或隱藏權重。
- 若需要支援第 3 個面向，視為重大評分規則變更，必須先經組長核准、升級規則版本並重新設計排序與測試。
- 儲存與快取偏好時，應將兩科視為「無順序集合」；可使用排序後 tuple 或等效方式作為穩定快取鍵。

### 5.2 正式排序順序

正式排序順序：

1. 優先分 Q 由高至低。
2. 五科總分 S 由高至低。
3. 有效評論數由高至低。
4. 每晚價格由低至高。
5. 房源 ID 作為穩定排序鍵，確保相同輸入每次結果一致。

注意：

- 優先分只影響排序，不另加進 25 分，避免重複計分。
- 排序必須可重現，不可加入未固定的隨機因素。
- 缺少核心資料、無法產生完整五科分數的房源不得混入正式排名。

## 6. UI 與資訊架構規範

UI 概念圖為主要視覺與資訊層級參考，不要求像素完全相同；若視覺與可用性衝突，以清楚、可操作、可解釋為優先。

## 6.1 推薦房源清單頁

### 左側篩選區

依序分為：

1. 必要條件
   - 行政區
   - 房型
   - 預算
   - 可住人數
   - 必備設備
2. 最在意的面向
   - 欄位名稱建議使用「最在意的兩個面向」
   - 五科中必須且只能選擇兩科
   - 顯示已選數量，例如 `1／2`、`2／2`
   - 未選滿時顯示提示；選滿後不得再新增第 3 項
   - 可移除或更換既有面向，但不得以選擇順序產生不同權重
3. 希望設備
   - 合計選擇 1～5 項，5 項為總上限
   - 按鈕建議命名為「＋選擇其他希望設備」
   - 按鈕只開啟完整選擇介面，不能直接加分或立即改變排名
   - 顯示 `已選擇 k／5 項`，達 5 項後須先移除才能更換
   - 只有按下「套用選擇」後才正式重新計算

### 頁首 KPI

建議顯示：

- 符合條件房源數
- 中位價格
- 平均綜合分數（／25）
- 優先查看房源數

若保留 Airbnb 平均評分，名稱必須明確寫成「Airbnb 平均評分」，不可與新版口碑分混淆。

### 房源卡片

每張卡片至少顯示：

- 房源照片、名稱、行政區、房型
- 每晚價格
- Airbnb 整體評分與評論數
- 綜合推薦分（／25）與等級
- 五科分數
- 推薦理由
- 注意事項或資料不足提醒
- 查看詳情
- 提出租房意願
- 加入收藏

不得繼續把舊「生活機能 95.3 分」當作新版總分。

### 房源分布地圖與「地圖著色依據」下拉式選單

#### 功能定位

地圖下拉式選單是**視覺分析工具**，不是篩選器，也不是排序器。它的用途是讓使用者在同一批已篩選房源中，切換觀察不同評分面向的空間分布。

畫面名稱應使用：

```text
地圖著色依據：綜合總分 ▼
ⓘ 只改變地圖顏色與提示內容，不影響篩選結果或推薦排序
```

三種控制必須明確分工：

| 控制項 | 負責內容 | 不得影響 |
|---|---|---|
| 必要條件 | 決定哪些房源留下 | 不負責加權排序 |
| 最在意的兩科 | 決定推薦清單排序 | 不改變房源是否符合必要條件 |
| 地圖著色依據 | 決定地圖圓點用哪個分數呈現 | 不改變房源集合與清單順序 |

#### 下拉式選項

固定提供：

1. 綜合總分
2. 交通方便
3. 生活便利
4. 價格合理
5. 住客口碑
6. 房源設備

預設值為「綜合總分」。除非專案負責人另行核准，不增加「舊生活機能百分比」或其他未納入五科制度的選項。

#### 切換時允許改變的內容

- 房源圓點顏色。
- 地圖圖例標題、刻度與分級文字。
- 圓點 hover 中最優先顯示的分數與計分證據。
- 地圖區塊的輔助說明文字。

#### 切換時不得改變的內容

- 必要條件篩選後的房源 ID 集合。
- 推薦清單排序與分頁順序。
- 五科原始分數與綜合總分。
- 房源座標與圓點位置。
- 使用者目前的地圖縮放與中心位置；只有必要條件改變或使用者主動重設地圖時，才重新調整視野。

若未來希望使用者能「依目前地圖科目重新排序」，必須設計另一個明確按鈕，例如「依此科排序」，不得讓下拉式選單暗中改變排序。

#### 地圖資料範圍

- 地圖應呈現「符合必要條件且具有有效座標」的同一批候選房源，不應只顯示目前分頁的 10 或 20 間房源。
- 若受效能限制而設候選上限，畫面必須標示：`地圖顯示 X／Y 間符合房源`，並說明截斷規則。
- 房源數量過多時，優先使用點位群聚（cluster）或合理抽稀，不可無提示地隱藏房源。
- 清單分頁切換不得改變地圖房源集合；必要條件改變時才重新產生候選集合。

#### 顏色、圖例與尺度

總分模式使用規劃書核准的正式區間：

| 綜合總分 | 圖例文字 |
|---|---|
| 20～25 | 優先查看 |
| 15～19.9 | 值得考慮 |
| 10～14.9 | 普通 |
| 0～9.9 | 建議多比較 |

單科模式固定使用 0～5 分尺度，可採下列分級：

| 單科分數 | 圖例文字 |
|---|---|
| 4～5 | 表現突出 |
| 3～未滿 4 | 表現不錯 |
| 2～未滿 3 | 普通 |
| 1～未滿 2 | 較弱 |
| 0～未滿 1 | 明顯不足 |

必守規則：

- 總分色階固定為 0～25，單科固定為 0～5。
- 不可依當頁最大值與最小值自動縮窄色階，避免放大 0.1 分等細微差異。
- 點大小原則上固定；不得同時用顏色與大小重複表達同一分數。
- 不可只依顏色傳達意義；圖例、hover 與文字標籤須同步呈現，以兼顧色覺差異與可讀性。
- 概念圖中的示意分級若與核准評分規劃書不同，以規劃書與本準則為準。

#### 資料不足與無法定位

- 有座標但所選科目無法計分：保留在地圖上，以灰色圓點表示「資料不足」，不得當成 0 分或紅色低分。
- 無有效座標：無法放在地圖上，地圖上方需顯示未呈現的房源數量與原因。
- 綜合總分不完整：在綜合總分模式以灰色呈現，hover 顯示缺少哪一科或哪個核心欄位。
- 灰色資料不足點不得被納入正常分數色階的高低比較。

#### Hover 顯示規範

所有模式至少顯示房源名稱、價格及目前選定指標。不同模式應補充對應證據：

- 綜合總分：總分、五科分數與推薦等級。
- 交通方便：最近捷運／公車距離及各自得分，並標示直線距離估計。
- 生活便利：超商／超市、餐飲、診所、公園的達標狀態與數量。
- 價格合理：本房源價格、同類中位價格、差異率、比較樣本數。
- 住客口碑：Airbnb 換算分、NLP 分、有效分析數與評論上限。
- 房源設備：希望設備命中數、選擇數與未符合項目。

Hover 中的證據必須與詳細分析頁及評分模組輸出完全一致，不可另外計算一套結果。

#### 點擊行為

- 點擊圓點可顯示房源簡要資訊及「查看詳細分析」。
- 選定房源可用外框、符號或標記強調；不得以大幅改變點大小造成分數誤讀。
- 不得點擊圓點後直接送出租房意願或交易操作，以避免誤觸。

#### 效能與狀態管理

- 下拉切換應讀取已計算完成的 `total_score` 或五科分數欄位，不應每次切換都重新執行距離、價格比較或 NLP 分析。
- 快取鍵需包含資料版本、評分規則版本與必要條件；「地圖著色依據」僅為呈現狀態。
- 在同一組必要條件下切換科目時，應保留地圖中心、縮放、選定房源與清單排序。
- 切換回原科目後，顏色、圖例與 hover 應可重現相同結果。

## 6.2 房源詳細分析頁

### 6.2.1 進入詳細頁、切換房源與返回狀態契約

#### 主要與輔助入口

「房源詳細分析」的主要入口為推薦房源卡片上的 `查看詳情` 按鈕。為符合一般使用者操作習慣，房源照片與房源標題可作為指向同一詳細頁的輔助入口。

三個入口必須傳遞同一個穩定且唯一的 `listing_id`：

```text
點擊房源照片 ─┐
點擊房源標題 ─┼→ 設定 selected_listing_id → 進入房源詳細分析
點擊查看詳情 ─┘
```

不得使用房源名稱、清單列號、目前分頁位置或 DataFrame index 作為唯一識別，因為房源名稱可能重複，排序與分頁位置也可能改變。

房源卡片中的其他操作必須維持獨立功能：

- `提出租房意願`：進入意願填寫或示範流程，不得誤導至詳細分析頁。
- `加入收藏`：只更新收藏狀態，原則上不離開推薦清單。
- 點擊卡片內的一般文字或空白處：不得因整張卡片皆可點而造成收藏、意願按鈕誤觸。

#### 地圖入口

地圖是第二入口，但採兩段式操作：

1. 點擊房源圓點，先顯示房源摘要與目前著色指標的證據。
2. 使用者再按摘要內的 `查看詳細分析`，才進入詳細頁。

不得因單次點擊地圖圓點就強制跳頁，也不得由地圖點擊直接觸發租房意願、收藏或交易操作。

#### 進入後的預設狀態

- 從推薦卡片或地圖摘要進入時，預設開啟 `📊 房源總覽`。
- 頁面必須先依 `listing_id` 載入該房源的基本資料、五科分數、證據、警告與規則版本，再繪製各區塊。
- 房源名稱、照片、價格、分數、雷達圖、地圖與 NLP 結果必須全部屬於同一個 `listing_id`，不得殘留上一間房源的快取或 session state。
- 成果展版原則上在同一瀏覽器分頁內切換頁面，不強制開啟新分頁。

#### 詳細頁上方的房源切換選單

詳細頁上方可提供 `選擇房源查看詳細分析` 下拉選單，但它是「進入詳細頁後的快速切換工具」，不是主要入口，也不是重新篩選器。

選單規則：

- 預設選中目前的 `selected_listing_id`。
- 原則上只列出目前必要條件篩選後的候選房源，並顯示足以辨識的名稱、行政區、價格與綜合分數。
- 選擇其他房源時，只切換 `selected_listing_id` 並更新詳細頁內容，不得改變必要條件、最在意兩科、希望設備或推薦清單排序。
- 切換後所有區塊必須同步更新，不得出現標題是房源 B、雷達圖或評論仍是房源 A 的混合狀態。
- 若介面可控制目前內層頁籤，切換房源時可保留相同分析頁籤以利比較；若技術上無法穩定控制，則一致重設為 `房源總覽`，並在實作說明中記錄。不得出現不確定或隨機切換。

#### 返回推薦清單與狀態保留

詳細頁必須提供明確的 `← 返回推薦清單`。返回後應保留使用者進入前的邏輯狀態：

- 行政區、房型、預算、入住人數及必備設備。
- 最在意的兩個面向。
- 已套用的希望設備。
- 候選房源排序與目前清單頁碼。
- 地圖著色依據、地圖中心、縮放與選定房源。
- 可行時保留原清單捲動位置；若框架無法可靠還原，至少回到原頁碼並將剛查看的房源醒目標示。

不得因查看一間房源後返回，就清空所有條件、回到第一頁或重新套用預設偏好。

#### 無效或失效房源處理

若 `listing_id` 不存在、格式錯誤、房源已移除或目前資料版本無法讀取：

- 不得讓頁面整體崩潰或顯示其他房源資料。
- 顯示 `找不到此房源，或房源目前已不在可用資料中`。
- 提供 `返回推薦清單`。
- 記錄錯誤原因供除錯，不得把無效 ID 默默改成第一間房源。

若只有單一科目資料不足，仍可進入詳細頁；該科顯示資料不足與原因，不應阻止其他可用資訊呈現。

建議使用四個內層頁籤：

1. `📊 房源總覽`
2. `🚇 交通與生活圈`
3. `💰 價格與設備`
4. `💬 口碑與評論`

### 房源總覽

- 房源核心資訊
- 綜合分數與推薦等級
- 五科雷達圖（固定 0～5）
- 五科數字卡
- 推薦理由與注意事項

雷達圖僅用於總覽，精確分數仍須以數字呈現。

### 交通與生活圈

- 最近捷運出口及得分
- 最近公車站及得分
- 超商／超市、餐飲、診所、公園是否達標
- 原始數量、最近距離與 POI 地圖
- 「直線距離估計」提醒

### 價格與設備

- 本房源價格
- 同類房源中位價格
- 價格差異率
- 比較樣本數與比較條件
- 必備設備確認
- 希望設備命中清單與設備分
- 完整設備清單可放入展開區塊

### 口碑與評論

- 最終口碑分
- Airbnb 分數 A
- NLP 分數 N
- 評論數上限 C
- 有效分析數與分析涵蓋率
- 正／中／負比例圓餅圖
- 無法分析數另行顯示
- 「住客常提到的優點」橫條圖，顯示提及該優點的正面評論則數
- 正面與負面評論摘錄

優點圖不得充斥 `the`、`and`、`to`、`is`、`very`、`was` 等無意義停用詞；不得把概念圖示意詞寫死，也不得將優點排行再次加入評分。

## 7. 推薦文字規範

推薦理由採規則式生成，不必依賴生成式 AI。文字應由分數與原始證據產生，例如：

> 交通與生活便利表現突出，捷運出口約 350 公尺，500 公尺內有超商；價格比同類中位數高約 8%，建議再比較設備與評論。

規則：

- 不使用「保證」、「絕對安全」、「一定值得租」等語句。
- 至少包含一項優點。
- 有明顯弱項、資料不足或樣本不足時必須提示。
- 推薦理由中的數字必須能追溯至實際計算結果。

## 10. 測試規範

## 10.1 單元測試邊界值

至少包含：

- 捷運 400、401、800、801、1,200、1,201 公尺。
- 公車 300、301、600、601 公尺。
- 餐飲 4、5 個地點。
- 價格差異率 -10%、0%、10%、25% 邊界。
- Airbnb 評分 4.0、4.2、4.5、4.8。
- 評論數 0、1、4、5、19、20。
- 設備命中 0／k、部分命中、全部命中。

## 10.2 資料品質測試

- 相同 POI ID 重複。
- 同名且座標極近的 POI。
- 房源缺座標、價格、行政區、房型。
- 價格含貨幣符號、逗號、空白或異常值。
- 設備同義詞與大小寫差異。
- 空白評論、短評論、不支援語言。

## 10.3 NLP 測試

至少準備：

```text
The room was clean and wonderful. → 正面
The room was dirty, noisy and terrible. → 負面
The room is on the third floor. → 中立或接近中立
房間很乾淨，交通也很方便。 → 正面
房間很髒，而且晚上非常吵。 → 負面
日文評論 → 無法分析／不納入，不可硬判成中立
```

## 10.4 「住客常提到的優點」測試

至少包含：

1. 英文正面評論含大量 `the`、`and`、`to`、`is`、`very`、`was`，正式圖表不得顯示這些停用詞。
2. 中文正面評論含大量 `的`、`了`、`是`、`很`，正式圖表不得顯示這些停用詞。
3. 一則評論重複出現 5 次 `clean`，同一優點仍只計 1 則評論提及。
4. 正面、中立、負面與無法分析評論混合時，優點只能從有效正面評論產生。
5. 中英文都提到乾淨時，已啟用主題映射的版本應合併為同一優點；未啟用時至少不得出現停用詞與雜訊。
6. 0 則有效正面評論時不繪圖；1～2 則時顯示摘錄而非排行；3～4 則時顯示低樣本警語；5 則以上正常呈現。
7. 圖表最多顯示 6～8 項，X 軸為「提及正面評論數」。
8. hover 的提及則數、有效正面評論總數及涵蓋率計算正確。
9. 切換 `listing_id` 後，優點圖、計數、來源評論與低樣本狀態全部同步更新，不得沿用上一間房源結果。
10. 修改停用詞、同義詞或優點圖內容後，NLP 分 N、口碑分 R、總分 S 與推薦排序不得因此再次增加或改變；除非情緒分類本身另有經核准的修改。
11. 概念圖中的 `clean`、`convenient`、`comfortable` 等示意詞不得在無對應評論證據時固定顯示。
12. 支持評論功能若有實作，點擊優點後顯示的評論必須真的包含該優點的來源證據。

## 10.5 UI 一致性測試

同一房源在下列位置顯示的分數必須一致：

- 推薦清單卡片
- 地圖 hover
- 詳細頁總覽
- 雷達圖
- 分數明細
- 推薦理由

### 地圖下拉式選單必測案例

1. 切換六個選項後，候選房源 ID 集合完全相同。
2. 切換六個選項後，推薦清單順序與分頁完全不變。
3. 只有圓點顏色、圖例、輔助說明與 hover 重點內容改變。
4. 總分色階固定 0～25，單科色階固定 0～5；更換行政區後仍不得自動縮窄。
5. 分數缺失顯示灰色「資料不足」，不可顯示為 0 分低分。
6. 無座標房源不出現在地圖，且畫面顯示未呈現數量。
7. hover 的分數、原始證據與詳細頁一致。
8. 清單換頁不改變地圖候選範圍；必要條件改變才更新地圖集合。
9. 切換科目時保留地圖中心、縮放與目前選定房源。
10. 切換科目不得重新執行 NLP、POI 距離或價格比較等高成本計算。

### 希望設備與「更多設備」必測案例

1. 只開啟或收起完整設備清單時，已套用設備、E、S、Q 與排序完全不變。
2. 暫時勾選設備後按「取消」或直接關閉，必須恢復原選擇，不能殘留草稿狀態。
3. 按下「套用選擇」後，才更新設備偏好並重新計算 E 與 S。
4. 選擇 1 項與 5 項時皆可正確套用；E 必須依 `m ÷ k × 5` 計算。
5. 已選 3 項後，只允許再選 2 項，UI 顯示 `3／5`、`4／5`、`5／5`。
6. 嘗試選擇第 6 項時，前端與後端均拒絕，不得截斷或默默忽略。
7. 同一設備不得重複選取，也不得同時出現在必備與希望設備。
8. 「更多設備」按鈕本身不得修改任何計分欄位、session state 正式值或排序。
9. 設備不是最在意兩科時，變更設備偏好不得改變 Q；但 S 與第二層排序可依新 E 更新。
10. 設備是最在意兩科之一時，套用後 E、Q、S 與第一層排序均須一致更新。
11. 套用設備偏好時，不得重跑交通、生活、價格或 NLP 計算。
12. 再次開啟完整設備清單時，正確載入目前已套用的選擇。
13. 設備資料為 `unknown` 時，不得當成確定沒有；依規則顯示資料不足。
14. WiFi／Wi-Fi／Wireless Internet 等同義詞需命中同一標準設備，不可重複計分。

### 最在意面向必測案例

1. 0 項時顯示「請選擇 2 項」，且不產生正式優先分 Q。
2. 1 項時顯示「請再選擇 1 項」，且不得以單科分數冒充 Q。
3. 2 項時啟用排序，Q 等於兩科分數合計且最高 10 分。
4. 嘗試選擇第 3 項時，UI 與後端都必須拒絕，既有兩項與排序不得改變。
5. 「交通＋價格」與「價格＋交通」產生相同 Q、相同候選排序與相同快取結果。
6. 移除其中一項後，立即回到未選滿狀態，Q 不得沿用舊值。
7. Q 不加入 S；切換最在意面向只能改變第一層排序，不得改變五科分數與 25 分總分。
8. 未選的其他三科仍須出現在房源卡、雷達圖、地圖單科選項與詳細分析。
9. 同一面向不得重複選取；前後端都要驗證。
10. 若採「新增面向」按鈕，少於 2 項時可用，達 2 項後須隱藏、停用或改為更換功能。

### 房源詳細分析導航必測案例

1. 點擊房源卡片的 `查看詳情`，載入與該卡片完全相同的 `listing_id`。
2. 點擊房源照片或標題，應與 `查看詳情` 進入同一房源；房源名稱重複時仍不得選錯。
3. `提出租房意願` 與 `加入收藏` 不得誤導至詳細分析頁。
4. 點擊地圖圓點只顯示摘要；只有再按 `查看詳細分析` 才進入詳細頁。
5. 從卡片或地圖進入時，預設顯示 `房源總覽`。
6. 詳細頁上方選單只列目前候選房源，且預設選中目前 `listing_id`。
7. 在詳細頁切換房源後，標題、價格、五科分數、雷達圖、POI、設備與 NLP 均更新為同一房源，不得混用舊快取。
8. 切換房源不得修改必要條件、最在意兩科、希望設備、推薦排序或地圖著色依據。
9. 返回推薦清單後，篩選條件、偏好、清單頁碼、排序與地圖狀態皆維持原狀。
10. 返回後至少能重新定位或醒目標示剛查看的房源；框架支援時應還原原捲動位置。
11. 使用無效、已移除或不存在的 `listing_id` 時，顯示友善錯誤與返回按鈕，不得崩潰或默認載入第一間房源。
12. 詳細頁切換原則採同一瀏覽器分頁，不得每次查看都強制開啟新分頁。
13. 若切換房源時無法可靠保留內層頁籤，必須一致重設為 `房源總覽`；不可出現隨機行為。

## 11. 驗收條件（Definition of Done）

一項功能只有同時符合下列條件才算完成：

- [ ] 依本文件規則完成。
- [ ] 有可重現測試案例。
- [ ] 通過相關單元測試與整合測試。
- [ ] 沒有偷偷回退到舊評分。
- [ ] UI 顯示與後端分數一致。
- [ ] 「最在意的面向」只能選擇 2 項；0／1／2／第 3 項嘗試的狀態與提示均通過驗收。
- [ ] 兩科選擇順序不影響 Q、排序或快取；Q 未被重複加入總分。
- [ ] 「更多設備」只開啟選擇介面；取消不改變正式狀態，套用後才更新評分。
- [ ] 希望設備合計限制 1～5 項；第 6 項、重複項及必備／希望重複均通過前後端驗證。

- [ ] 地圖著色切換不影響房源集合、清單排序或分頁。

### 12.4 重大變更

下列變更必須先經組長確認：

- 改變五科名稱或滿分。
- 改變 25 分總分架構。
- 改變任何配分或門檻。
- 改變排序邏輯。
- 將希望設備改為允許 0 項、超過 5 項、加入不同權重，或修改 `E = m ÷ k × 5`。
- 將「最在意的面向」改為少於或多於 2 項，或加入第 3 面向、順位權重與比例權重。
- 將不支援語言納入 NLP。
- 改變正面優點圖的資料來源、統計單位、最低繪圖門檻，或讓優點排行參與評分。
- 移除資料不足保護。
- 擅自改變詳細分析頁的主要入口、以房源名稱／索引取代唯一 `listing_id`，或取消返回狀態保留。
- 大幅偏離 UI 概念圖的資訊架構。

## 13. 發表與對外說法

完成實作且通過驗收後，才可說：

> 租客入口已採用五科房源評分，並以近期中英文評論的 NLP 結果參與口碑計分。

尚未完成時，應說：

> 這是已確認的新版評分與 UI 規劃，目前正在實作與驗證。

不得誇大：

- 不稱整套規則為黑箱 AI 模型。
- 不聲稱 Haversine 是實際步行距離。
- 不聲稱 NLP 能準確處理所有語言。
- 不聲稱高分代表絕對安全或一定適合租用。

## 14. 最後原則

> 功能可以分階段完成，但同一個版本中，計算、排序、畫面與說明必須使用同一套規則；資料不足時寧可誠實顯示，也不可製造看似完整但錯誤的分數。
