# LLM 生成原理說明 — 評論摘要與智慧建議

> Smart_accommodation_4 · 本文說明兩個「由 Gemini 自動生成」功能的完整運作原理。
> 核心問題:畫面上看不到 prompt,它到底怎麼生成的?

---

## 一句話總覽

**你看不到 prompt,是因為它由後端程式在記憶體裡組好,直接透過 API 送給 Gemini,不會顯示在畫面上。**

兩個功能都遵循同一套設計:

```
Python 算好數字  →  填進固定 prompt 模板  →  送 Gemini  →  顯示回傳文字
   (可追溯)          (藏在後端程式)         (只潤飾)      (標註來源)
```

**關鍵設計原則:LLM 只負責把數字寫成通順的句子,不負責產生數字。**
所有百分比、金額、面向名稱都由程式先算好,LLM 只能引用、不能瞎編。這樣每個數字都能追溯到原始資料。

---

## 功能一:評論自動摘要

**位置**:房東入口 → 房源詳情 / 口碑情報 → 「📝 評論自動摘要」
**程式**:`modules/review_summary.py`

### 六步流程

**第 1 步(離線,無 LLM):面向情感預計算**

`scripts/build_absa.py` 事先把 24 萬則評論處理完存成 CSV。每則評論做的事:

- 比對 14 個面向的中英關鍵詞(清潔、位置交通、隔音、WiFi、空調、床、衛浴、房東服務、性價比、空間大小、設備廚房、入住流程、早餐餐飲、停車)
- 取關鍵詞前後 30 字的「局部窗口」,用正負向詞計分(能拆解「早餐好吃**但**浴室很小」)

結果存進 `data/_absa_listing.csv`(每房源 × 每面向的正評數、負評數、負評率)。

> 這步是純詞典比對,可離線重現,與 LLM 無關。

**第 2 步:按下按鈕,撈出這間房的統計**

`collect_facts()` 從 CSV 撈出:
- `praise`:正評率 ≥55% 的前 3 個面向
- `complain`:負評率 ≥8% 的前 3 個面向
- 高頻正/負向詞

**第 3 步:填進 prompt 模板(這就是看不到的 prompt)**

`build_prompt()`(`review_summary.py` 第 104~118 行)把數字套進固定模板:

```
你是旅宿業評論分析師。請用繁體中文寫出一段 3~5 句的評論摘要,給房東閱讀。

房源:XXX(萬華區)
評論則數:6
面向情感分析結果:
- 住客稱讚的面向:清潔(正評率 88%)、位置交通(正評率 71%)、房東服務(正評率 56%)
- 住客抱怨的面向:空間大小(負評率 17%、6 則提及)
- 高頻正面詞:乾淨、方便、親切…
- 高頻負面詞:小、擠…

要求:
1. 第一句先總結整體口碑傾向。
2. 接著具體說明旅客最常稱讚什麼、最常抱怨什麼(引用上面的面向與比例)。
3. 最後一句給一個最優先的改善方向。
4. 直接輸出段落,不要標題、不要條列、不要開場白。
```

**第 4 步:送 Gemini**

`client.models.generate_content(model=m, contents=prompt).text`

**第 5 步:模型名稱容錯**

依序試 `gemini-2.5-flash → gemini-flash-latest → gemini-2.0-flash`,哪個先成功用哪個。畫面標「gemini(gemini-flash-latest)」代表第二個才成功。

**第 6 步:顯示**

Gemini 回的文字貼到畫面,標註來源。

## 功能二:智慧建議

**位置**:房東入口 → 風險診斷 → 「🧠 產生 LLM 智慧建議」(僅 🔴 紅色高風險出現)
**程式**:`modules/llm_advisor.py`

### 與評論摘要的差別:餵給 LLM 的材料來自四個來源

| 材料 | 來源 | 誰算的 |
|---|---|---|
| 模型預測(空屋率 83%、高風險機率、警報層級) | LightGBM 雙軌模型 | 離線訓練 |
| LIME 風險原因(如「500m公車站數 ≤20 → +1.0pp」) | LIME 局部線性近似 | 即時計算 |
| 跨平台競品概況(1km 內筆數、價格落點) | BallTree 競品索引 | 即時查詢 |
| 設施缺口(周邊過半競品有、你沒有) | 競品設施覆蓋率比對 | 即時計算 |

### prompt 模板(`llm_advisor.py` 第 50~66 行)

```
你是台北市短租市場的資深營運顧問。以下是一間 Airbnb 房源的
AI 風險評估結果,請用繁體中文為房東寫出具體可執行的改善建議。

房源資訊:XXX|大安區|整棟出租|每晚 NT$ 3,374
模型預測:未來一年空屋率 83%,高風險機率 82%(警報層級:🔴 高風險)
LIME 判定的主要風險原因:
- 500m公車站數 ≤20(影響 +1.0 個百分點)
- (其餘正向風險原因…)
1km 跨平台競品概況:1km 內 165 筆競品,同容量層貴於 58%
設施缺口(周邊過半競品有、本房源沒有):WiFi、洗衣機、電梯

要求:
1. output 3~4 條建議,每條含「做什麼、怎麼做、預期效果」,格式為 markdown 條列。
2. 建議必須對應上述風險原因與競品數據,給出具體數字(如目標價格區間)。
3. 語氣專業但親切,不用開場白與結尾,直接輸出條列。
```

### 兩個關鍵設計

1. **只有紅色高風險才觸發**:`build_prompt` 只在 `tier == "red"` 被呼叫;黃色、綠色用規則引擎,不打 API,控制成本。
2. **手動按鈕觸發**:調整房價或最低入住天數**不會**自動呼叫,避免每拖一次滑桿就打一次 API。

## 兩者對照表

| | 評論自動摘要 | 智慧建議 |
|---|---|---|
| 程式 | `modules/review_summary.py` | `modules/llm_advisor.py` |
| 餵給 LLM 的材料 | ABSA 面向統計(1 種) | 模型 + LIME + 競品 + 設施(4 種) |
| 觸發條件 | 手動按鈕(任何房源) | 手動按鈕(僅紅色高風險) |
| 輸出格式 | 一段 3~5 句摘要 | 3~4 條行動建議(做什麼/怎麼做/預期效果) |
| 底層流程 | **完全相同**:Python 算數字 → 填模板 → 送 LLM → 顯示 | 同左 |

---

## 為什麼這樣設計(三個理由)

1. **防止 LLM 亂編數字**
   若直接把評論原文或「請分析這間房」丟給 Gemini,它可能捏造「88%」這種數字。
   現在數字全由程式(ABSA 詞典、LIME、模型、競品索引)算好,LLM 只能引用,無法瞎編。
   你看到的每個百分比都能追溯到原始資料。

2. **省成本、省時間**
   24 萬則評論不可能每次按按鈕都送 LLM。離線算好、只送摘要,一次呼叫幾百 token。

3. **無金鑰也能用**
   沒設金鑰時,`_rule_summary()` / `_rule_advice()` 用同一批數字套規則模板組句
   (就是預設顯示的「規則版」),不會壞掉。

## 金鑰設定

兩個功能共用同一把金鑰。設定方式(擇一):

- **本機**:`.streamlit/secrets.toml` 加入
  ```toml
  GEMINI_API_KEY = "AIza..."
  # 或 ANTHROPIC_API_KEY = "sk-ant-..."(改用 Claude)
  ```
- **Streamlit Cloud**:App settings → Secrets 貼上同樣內容
- **環境變數**:`GEMINI_API_KEY` / `ANTHROPIC_API_KEY`

未設定金鑰時,兩個功能都自動退回規則引擎版本,功能不中斷。
