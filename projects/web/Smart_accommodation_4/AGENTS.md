## 4. 不可違反的評分不變條件

### 4.1 總體架構

```text
S = T + L + Pscore + R + E
```

- T：交通分，0～5。
- L：生活分，0～5。
- Pscore：價格分，1～5；資料不足時不計分。
- R：口碑分，0～5。
- E：設備分，0～5。
- S：總分，0～25。

不得把舊生活機能百分比混入 S。

### 4.2 必要條件

行政區、房型、預算、入住人數、必備設備屬篩選條件，不計分。缺少必備條件的房源必須排除。

### 4.3 交通分

```text
捷運：≤400m=3；401–800m=2；801–1200m=1；>1200m=0
公車：≤300m=2；301–600m=1；>600m=0
T = 捷運分 + 公車分
```

- 使用最近有效地點。
- 距離為 Haversine 直線距離估計。
- 無座標或 POI 資料缺失時，不得自動給 0。

### 4.4 生活分

```text
500m 內超商／超市 ≥1：2 分
800m 內不重複餐飲 ≥5：1 分
1km 內不重複診所 ≥1：1 分
1km 內不重複公園 ≥1：1 分
```

必須先去重，再判斷門檻。

### 4.5 價格分

比較組：同區 + 同房型 + 可住人數差不超過 1，優先至少 10 間。

```text
D = (price - median_price) / median_price * 100
D ≤ -10% → 5
-10% < D ≤ 0% → 4
0% < D ≤ 10% → 3
10% < D ≤ 25% → 2
D > 25% → 1
```

不得只用行政區中位數取代正式比較組，除非是經核准的不足樣本降級策略，且前台需標示。

### 4.6 口碑分

Airbnb 分 A：

```text
4.8–5.0 → 3
4.5–4.79 → 2.5
4.2–4.49 → 2
4.0–4.19 → 1
<4.0 → 0
```

NLP 分 N：

```text
P+ = positive / analyzable
P- = negative / analyzable
N = clamp(1 + P+ - P-, 0, 2)
```

評論上限 C：

```text
0 則 → 不計分
1–4 則 → 上限 3
5–19 則 → 上限 4
20+ 則 → 上限 5
R = min(A + N, C)
```

不可將評論數直接加分。

### 4.7 設備分

```text
E = matched_preferences / selected_preferences * 5
```

- 希望設備合計必須為 1～5 個不同設備；5 是總上限，不是「更多設備」按鈕可額外增加的數量。
- 選擇數 k 必須介於 1～5；不得私自把 0 項補成任意分數，也不得默默接受第 6 項。
- 必備設備與希望設備不可重複計分。
- 必須經設備同義詞標準化。
- 設備 `unknown` 不得直接當成 `absent`；無核准缺失規則時應回傳資料不足狀態。

### 4.7.1「更多設備」互動不變條件

代理必須遵守：

1. 「更多設備」或「＋選擇其他希望設備」只能開啟／展開完整設備選擇介面，不得直接新增設備、加分、更新總分或改變排序。
2. 必須區分已套用狀態與尚未確認的草稿狀態；建議使用 `applied_preferred_amenities` 與 `draft_preferred_amenities` 或等效結構。
3. 使用者暫時勾選、取消或瀏覽設備時，不得修改正式評分狀態。
4. 只有按下「套用選擇」並通過驗證後，才可更新正式希望設備。
5. 按下「取消」、關閉視窗或返回時，必須捨棄草稿並保留原已套用選擇。
6. UI 顯示 `已選擇 k／5 項`；達 5 項後，新增選項需停用或阻止，並提示先移除一項。
7. 前端與後端都必須驗證 1～5 個不同、合法且不與必備設備重複的標準設備 ID。
8. 收到第 6 項、重複項、未知項或必備／希望重疊時，必須回傳明確錯誤；不得靜默截斷前 5 項或自動刪除衝突項目。
9. 套用後只重新計算 E、S，以及設備為最在意科目時的 Q；不得重跑交通、生活、價格或 NLP。
10. 設備不在最在意兩科時，修改希望設備不得改變 Q；只允許透過 S 影響後續同分排序。
11. 再次開啟選擇介面時，必須正確載入目前正式套用的選擇。
12. 允許 0 項、提高 5 項上限、修改設備公式或加入設備權重，均屬重大評分規則變更，須停止並取得專案負責人確認。

### 4.8 排序

```text
Q = 使用者最在意科目 1 + 使用者最在意科目 2
```

排序依序：

1. Q 降冪。
2. S 降冪。
3. 有效評論數降冪。
4. 價格升冪。
5. 房源 ID 作穩定排序。

Q 不加入 S。

### 4.9「最在意的面向」選擇不變條件

正式限制：

> 「最在意的面向」必須且只能選擇 2 項。未選滿 2 項時，應提示使用者完成選擇；選滿後不得新增第 3 項。選擇結果只用於第一層排序，優先分為兩科分數合計，最高 10 分。其他三科仍納入 25 分總分及詳細展示。

代理必須遵守：

- 前端需限制最多 2 項；後端評分／排序函式亦須再次驗證恰好 2 個不同科目，不能只相信 UI。
- 0 項或 1 項時，不得產生正式 Q，不得默默補預設科目，也不得用單科或總分冒充個人化優先排序。
- 嘗試傳入第 3 項、重複項目或未知科目時，必須回傳明確驗證錯誤或不可排序狀態，不得截斷後悄悄繼續。
- 不得因 UI 概念圖出現「新增面向」按鈕而允許選擇超過 2 項。若採用新增按鈕，按鈕只能在目前選擇少於 2 項時出現；達 2 項後必須隱藏、停用或改為更換功能。
- 建議直接使用最多選 2 項的 multiselect；標籤使用「最在意的兩個面向」，並顯示 `已選 0／2`、`1／2` 或 `2／2`。
- 兩個科目同等重要；輸入順序不得形成權重。「交通、價格」與「價格、交通」必須得到相同 Q 與相同排序。
- 偏好狀態與快取鍵應正規化為無順序集合，例如 `tuple(sorted(selected_dimensions))`。
- 使用者移除一項後，舊 Q 必須失效，不得殘留在 session state、快取或已合併資料框。
- Q 的範圍固定 0～10；Q 不得加入 S，也不得改變五科原始分數。
- 未選的另外三科仍必須參與 S，並出現在卡片、雷達圖、地圖與詳細頁。
- 不得自行改成三科加總、三科平均、順位加權、百分比權重或全部五科優先分；任何此類需求均屬重大規則變更，須停止修改並請專案負責人確認。

## 5. NLP 專用規則

### 5.1 套件

實際程式若使用：

```python
from vaderSentiment.vaderSentiment import SentimentIntensityAnalyzer
```

則部署依賴必須包含：

```text
vaderSentiment>=3.3.2
jieba>=0.42.1
```

不要以安裝 `nltk` 取代目前的 `vaderSentiment` 匯入方式。

### 5.2 語言分流

- 英文：VADER。
- 中文：jieba + 核准詞典／規則。
- 中英混合：必須採明確、可測試的策略，不可默默忽略中文部分。
- 日文與其他未支援語言：`無法分析` 或 `unsupported`。

### 5.3 狀態欄位

單則分析結果應能區分：

```text
label: positive | neutral | negative | unanalyzable
valid: true | false
reason: analyzer_missing | unsupported_language | empty_text | too_short | no_supported_content | ...
analyzer: vader | zh_lexicon | none
```

不可把下列情況標為中立：

- VADER 未載入。
- jieba 未載入。
- 不支援語言。
- 空白評論。
- 資料欄位錯誤。

### 5.4 取樣

- 房源口碑優先取最近最多 20 則可支援評論。
- 若資料有日期，必須先按日期降冪排序。
- 隨機抽樣最多 200 則的舊邏輯不得用於新版口碑分。
- 全域後台分析可另有取樣規則，但不得與房源口碑分混用。

### 5.5 UI 顯示

至少顯示：

- 房源總評論數
- 本次選取數
- 有效分析數
- 無法分析數
- 分析涵蓋率
- 正／中／負比例
- NLP 分數 N
- 實際分析器啟用狀態

頁面不可固定宣稱 VADER／jieba 已啟用而不檢查實際狀態。

### 5.6 「住客常提到的優點」

代理實作正面優點圖時必須遵守：

1. 功能只用於解釋正面評論在稱讚什麼，不是新的評分項目。
2. 資料來源只能是目前房源最近最多 20 則評論中，語言可支援、內容有效且分類為正面的評論。
3. 不得混入中立、負面、無法分析、空白、重複或無意義評論。
4. 不得直接對未清理的原始評論做單字頻率排行。
5. 必須移除中英文停用詞、標點、網址、Email、數字、單一字母、表情符號與其他雜訊。
6. 不得讓 `and`、`the`、`to`、`is`、`very`、`was`、`的`、`了`、`是`、`很` 等停用詞進入正式圖表。
7. 同一則評論的同一優點最多計算一次；統計值必須是「提及該優點的正面評論則數」，不是原始單字出現總次數。
8. UI 概念圖中的 `clean`、`convenient`、`comfortable`、`mrt` 等只是示意，不得寫死為固定結果。
9. 成果展最低版本可先輸出清理後的有意義詞語；完整版本應使用具版本紀錄的中英文同義詞／優點主題映射，例如將 `clean`、`乾淨`、`整潔` 合併為 `環境乾淨`。
10. 顯示規則固定為：0 則不繪圖；1～2 則改顯示摘錄；3～4 則可繪圖但顯示低樣本警語；5 則以上正常繪圖。
11. 最多顯示 6～8 項，X 軸為「提及正面評論數」；hover 應顯示提及數、有效正面評論總數與涵蓋率。
12. 優點詞、提及數與涵蓋率不得修改 N、R、S、Q 或推薦排序。
13. 切換房源時，快取鍵及衍生結果至少包含 `listing_id`、評論資料版本與文字處理規則版本，不得沿用上一間房源結果。
14. 停用詞表、同義詞表、主題映射或最低門檻變更時，必須留下版本、原因與測試證據。

## 6. UI 不變條件

UI 概念圖是資訊架構參考。代理可依 Streamlit 限制調整間距與組件，但不得省略核心資訊。

### 6.1 推薦清單

必須包含：

- 必要條件、最在意兩科、希望設備三組輸入。
- 「最在意的兩個面向」必須顯示 0／2、1／2、2／2 狀態；達 2 項後不得出現可新增第 3 項的有效控制。
- 希望設備顯示 `已選擇 k／5 項`；「更多設備」只開啟選擇介面，必須有明確的套用／取消行為。
- 已列為必備的設備，不得在希望設備中成為可選且可加分的項目。
- KPI：符合房源、中位價格、平均綜合分、優先查看房源。
- 房源卡：綜合分、五科分、理由、注意事項。
- 地圖：預設依總分著色，可切換單科。
- 詳細頁口碑區使用「住客常提到的優點」，不得顯示未清理的停用詞排行；樣本門檻與提及評論數統計須符合第 5.6 節。
- 色階固定：總分 0～25，單科 0～5。

### 6.2 地圖著色下拉式選單互動契約

下拉選單名稱使用 `地圖著色依據`，固定選項：

```text
綜合總分
交通方便
生活便利
價格合理
住客口碑
房源設備
```

代理必須維持以下不變條件：

1. 選單只控制地圖圓點的顏色、圖例、輔助文字與 hover 重點。
2. 不得修改必要條件篩選後的候選房源 ID 集合。
3. 不得修改推薦清單排序、分頁順序、優先分 Q 或總分 S。
4. 不得因切換指標而改變地圖圓點位置、地圖中心或縮放。
5. 不得把下拉式選單實作成隱藏的重新排序器；需要排序功能時應另設明確控制項並先取得核准。

#### 地圖資料範圍

- 使用符合必要條件、可排名且有有效座標的候選集合；不得只跟隨目前清單分頁。
- 有候選數量上限時，UI 必須顯示 `地圖顯示 X／Y 間符合房源` 及截斷規則。
- 無座標房源不繪製，但必須顯示未呈現數量。
- 資料量大時可使用 cluster；不得無提示丟棄點位。

#### 色階與圖例

總分固定區間：

```text
20–25：優先查看
15–19.9：值得考慮
10–14.9：普通
0–9.9：建議多比較
```

單科固定 0～5，不得依當前資料 min/max 自動縮窄。可使用：

```text
4–5：表現突出
3–<4：表現不錯
2–<3：普通
1–<2：較弱
0–<1：明顯不足
```

- 點大小原則上固定，不得與顏色重複編碼同一分數。
- 不可只靠顏色傳遞資訊；必須有文字圖例與 hover 數值。
- 有座標但所選分數缺失時使用灰色 `資料不足`，不得轉成 0 分。
- 概念圖示意分級與正式規劃不同時，以評分規劃書及 `專案執行準則.md` 為準。

#### Hover 證據

使用同一份評分結果物件產生 hover，不得在 UI 重新計算另一套分數：

- 總分：S、五科分數、推薦等級。
- 交通：M、B、最近距離與直線距離提醒。
- 生活：C、F、H、P 的達標狀態與數量。
- 價格：價格、中位價、D、比較樣本數。
- 口碑：A、N、C、有效分析數。
- 設備：m、k、命中與未命中設備。

#### 點擊與狀態

- 點擊點位只開啟簡要資訊／查看詳細分析，不直接觸發租房意願或交易。
- 使用外框或符號標示選定房源，避免大幅改變點大小。
- 切換著色指標時保留目前 viewport、選定房源與清單順序。
- 選項切換只讀取既有分數欄位，不得重跑 NLP、距離與價格比較。
- 快取須包含資料版本、規則版本及必要條件；著色指標僅屬 UI state。

### 6.3 詳細分析

#### 6.3.1 導航與房源識別不變條件

代理必須遵守：

1. 推薦卡片的 `查看詳情` 是主要入口；房源照片與房源標題可作為指向同一詳細頁的輔助入口。
2. 所有入口必須傳遞穩定、唯一且經驗證的 `listing_id`；不得以房源名稱、DataFrame index、清單列號或分頁位置識別房源。
3. `提出租房意願` 與 `加入收藏` 必須維持獨立動作，不得誤導至詳細分析頁。
4. 點擊地圖點位只能先開啟摘要；使用者再按 `查看詳細分析` 才可導向詳細頁。不得單擊點位即強制跳頁。
5. 從推薦清單或地圖進入時，預設顯示 `房源總覽`，並將 `selected_listing_id` 設為來源房源。
6. 詳細頁上方房源選單只用來在目前候選集合中切換 `selected_listing_id`，不得修改篩選條件、偏好、Q、S、排序或地圖著色狀態。
7. 切換房源時，所有資料讀取、元件 key、快取 key 與衍生結果都必須包含 `listing_id`；不得出現房源 B 標題搭配房源 A 雷達圖、POI 或評論的 stale state。
8. 房源選單預設值必須與 `selected_listing_id` 一致；候選房源名稱重複時仍須以 ID 區分。
9. 進入詳細頁前應保存推薦清單的邏輯狀態：必要條件、最在意兩科、希望設備、排序、頁碼、地圖著色、viewport 與選定房源。
10. `返回推薦清單` 必須還原上述狀態，不得清空條件、跳回第一頁或重新套用預設值。捲動位置若無法可靠保存，至少返回原頁碼並標示剛查看房源。
11. 無效、已移除或不存在的 `listing_id` 必須回傳友善錯誤與返回路徑；不得默認載入第一間房源、其他房源或讓頁面崩潰。
12. 詳細頁原則上在同一瀏覽器分頁內切換，不得每次查看都強制開啟新分頁。
13. 切換房源時若能可靠控制內層頁籤，可保留目前分析區以利比較；否則必須一致重設為 `房源總覽`，不得出現隨機或不一致行為。
14. 單科資料不足不得阻止整頁載入；只將該科標為資料不足並保留其他可用內容。

建議四頁籤：

- 房源總覽
- 交通與生活圈
- 價格與設備
- 口碑與評論

五科雷達圖固定 0～5，並同時顯示精確數字。

### 6.4 用語

優先使用：

- `綜合推薦 21.5／25`
- `提出租房意願`
- `直線距離估計`
- `資料不足，暫不排名`
- `比較樣本較少`
- `無法分析`

避免：

- `立即租房`（若沒有真實交易流程）
- `AI 保證推薦`
- `步行距離`（只有 Haversine 時）
- `無評論 = 0 分`
- `無法分析 = 中立`

## 7. 程式修改原則

### 7.1 小步修改

- 優先抽離評分函式，再調整 UI。
- 不要在同一個變更中同時重構整個專案與修改所有規則。
- 保留既有可用功能，除非任務要求移除。
- 不得為了讓畫面先跑而加入未告知的假資料或硬編碼分數。

### 7.2 模組化

評分規則應位於獨立模組，不得只存在於 Streamlit 元件事件中。

每個評分函式建議回傳：

```python
{
    "score": 4.0,
    "max_score": 5.0,
    "status": "ok",
    "components": {...},
    "evidence": {...},
    "reasons": [...],
    "warnings": [...],
    "rule_version": "tenant-score-v1.0",
}
```

### 7.3 錯誤處理

- 不使用裸 `except Exception: pass` 隱藏評分錯誤。
- 可捕捉例外，但須記錄原因並回傳資料不足狀態。
- 錯誤不可悄悄轉成 0 分。

### 7.4 快取

Streamlit 快取鍵須包含會影響結果的規則版本、使用者偏好與資料版本，避免規則更新後仍顯示舊分數。

### 7.5 既有共用架構

- 色彩、字級、間距、圓角、陰影、斷點與分數帶以 `modules/design_tokens.py` 為唯一來源，不得在頁面新增字面色碼、字級或圓角。
- 共用 UI 優先使用 `modules/ui_kit.py`；`modules/ui_components.py` 是相容門面，不得無理由複製另一套元件。
- 房源詳情優先重用 `modules/listing_detail.py`；若租客入口需要專屬內容，應清楚區分專屬與共用層。
- 評分規則以 `modules/tenant_scoring.py` 為目前實作位置，不得把另一套分數重新寫回頁面事件中。
- 修改 `modules/*.py` 後，以重新啟動的 Streamlit 程序驗收，不能只依賴 Rerun 判定新程式已載入。

### 7.6 Git 協作

- 不使用 `git add .`；只加入本次任務相關檔案。
- 不擅自還原、刪除或覆蓋不屬於本次任務的變更。
- 未經使用者要求，不自行提交、推送、合併、重寫歷史或切換他人分支。
- 開始與完成工作時都檢查 `git status --short`，交接時列出實際修改檔案、測試結果與尚未提交事項。
- 發現遠端或其他組員同時修改相同檔案時，先理解差異並保留雙方有效內容，不以整檔覆蓋解決衝突。

## 9. 必須執行的測試

每次修改評分相關程式後，至少執行：

1. Python 語法／匯入檢查。
2. 五科單元測試。
3. 排序測試。
4. 資料不足測試。
5. NLP 正面、負面、中立、無法分析測試。
6. 一筆完整房源人工重算比對。
7. 地圖著色切換不變性測試：六個選項切換後，房源集合與清單排序不變。
8. 地圖固定尺度、灰色資料不足、hover 證據與 viewport 保留測試。
9. Streamlit 頁面啟動測試。
10. 最在意面向選擇測試：0／1／2／第 3 項嘗試、重複項目、未知項目。
11. 選擇順序不變性測試：相同兩科顛倒順序時，Q、排序與快取結果完全一致。
12. 狀態清除測試：由 2 項移除為 1 項後，舊 Q 與舊排序不得殘留。
13. 總分隔離測試：更換最在意兩科只改變第一層排序，S 與五科分數完全不變。
14. 更多設備開啟測試：只開啟／收起設備介面時，正式選擇、E、S、Q 與排序不變。
15. 草稿取消測試：勾選後取消或關閉，正式狀態與分數不變。
16. 套用測試：只有按「套用選擇」後，E、S 與必要時的 Q 才更新。
17. 設備數量測試：1 項、5 項可正常套用；第 6 項前後端都拒絕且不截斷。
18. 設備互斥測試：必備與希望設備不得重複，重複時回傳明確錯誤。
19. 設備重算隔離測試：修改希望設備不得重跑交通、生活、價格或 NLP。
20. 設備同義詞／未知狀態測試：同義詞只計一次；unknown 不得當成 absent。
21. 詳細頁入口測試：`查看詳情`、照片與標題均以正確 `listing_id` 載入同一房源。
22. 按鈕隔離測試：`提出租房意願`、`加入收藏` 不得進入詳細分析頁。
23. 地圖兩段式測試：點位先顯示摘要，再按 `查看詳細分析` 才導向。
24. 重複名稱測試：兩個同名房源仍依不同 `listing_id` 載入正確內容。
25. 詳細頁切換測試：切換房源後所有區塊、快取與元件狀態均屬同一 `listing_id`。
26. 返回狀態測試：返回推薦清單後，必要條件、偏好、排序、頁碼與地圖狀態均保留。
27. 無效 ID 測試：不存在或失效 `listing_id` 顯示友善錯誤，不崩潰也不載入第一間房源。
28. 預設頁籤測試：由清單或地圖進入時顯示 `房源總覽`；房源切換後的頁籤行為固定且可重現。
29. 同分頁測試：查看不同房源不得強制產生多個瀏覽器分頁。
30. 停用詞測試：中英文常用停用詞不得出現在正式優點圖。
31. 單則去重測試：一則評論重複同一優點多次，僅計 1 則提及。
32. 正面來源隔離測試：中立、負面與無法分析評論不得進入優點排行。
33. 樣本門檻測試：0、1、2、3、4、5 則有效正面評論對應正確呈現與警語。
34. 動態資料測試：概念圖示意詞不得在無評論證據時固定輸出。
35. 房源切換測試：優點圖、計數、支持評論與低樣本狀態依 `listing_id` 同步更新。
36. 評分隔離測試：修改優點清理與展示不得改變 N、R、S、Q 或推薦排序。
37. 同義詞測試：啟用主題映射時，中英文同義詞合併為同一優點且不重複計數。

必測邊界：

```text
捷運：400/401/800/801/1200/1201
公車：300/301/600/601
價格：-10/0/10/25%
評論數：0/1/4/5/19/20
Airbnb：4.0/4.2/4.5/4.8
```

若測試因環境限制未執行，必須明確說明「未執行」，不得聲稱通過。

## 10. 禁止事項

代理不得：

- 未經同意修改五科名稱、滿分、公式或門檻。
- 把舊 `conv_pct` 改名後當作新總分。
- 將缺失資料自動補為 0。

- 用全行政區中位價取代正式比較組且不告知。
- 將總分與最在意兩科重複加權。
- 允許「最在意的面向」少於 2 項時仍宣稱完成個人化排序，或允許新增第 3 項。
- 因概念圖的「新增面向」字樣而自行實作三科加總、平均、順位權重或比例權重。
- 將使用者選擇順序視為重要性順位，除非另有核准規格。
- 遇到超過 2 項時默默截斷、取前兩項或忽略多餘項目。
- 以房源名稱、DataFrame index、清單列號或頁碼位置取代唯一 `listing_id` 進行詳細頁導航。
- 點擊地圖圓點就強制跳頁，或讓 `提出租房意願`／`加入收藏` 誤導至詳細分析頁。
- 進入或返回詳細頁時清空既有篩選、偏好、分頁、排序或地圖狀態。
- 切換房源後混用上一間房源的雷達圖、POI、設備、評論或 NLP 快取。
- 遇到無效 `listing_id` 時默認載入第一間房源或其他房源。
- 將「更多設備」按鈕實作為直接加分、直接新增設備或立即更新推薦結果。
- 允許希望設備超過 5 項，或收到第 6 項時默默截斷為前 5 項。
- 使用者取消／關閉設備視窗後仍保留未套用的草稿，或讓草稿影響正式評分。
- 將同一設備同時作為必備篩選與希望設備加分。
- 把設備資料 unknown 直接當成 absent，或以未標準化字串造成重複／漏判。
- 修改希望設備時重跑交通、生活、價格或 NLP 等不相關計算。
- 讓地圖色階隨當頁資料自動縮窄，誇大細微差異。
- 讓「地圖著色依據」改變候選房源、推薦排序、分頁或最在意兩科。
- 讓地圖只顯示目前清單分頁，卻未在畫面清楚標示。
- 把資料不足點當作 0 分低分，或以紅色呈現。
- 每次切換地圖著色指標都重新執行 NLP、POI 距離或價格比較。
- 直接把未清理的原始單字頻率當作「住客常提到的優點」。
- 讓 `and`、`the`、`to`、`is`、`very`、`was`、`的`、`了`、`是`、`很` 等停用詞進入正式圖表。
- 將概念圖的示意詞寫死，或在正面評論不足時虛構、補值、沿用上一間房源的優點結果。
- 以同一則評論內的重複單字次數灌高優點排名。
- 將中立、負面或無法分析評論混入正面優點擷取。
- 讓優點關鍵詞、提及數或涵蓋率額外增加 NLP 分、口碑分、總分或影響排序。
- 修改房東風險模型、訓練資料或後台功能，除非任務明確要求。
- 宣稱未驗證的功能已完成或準確。
- 只修改畫面，不修改實際排序與計分。

- 暫時勾選新設備後按取消，確認原本設備、E、S 與排序不變。
- 套用 1～5 項希望設備，確認畫面顯示正確的 `k／5`，設備分依比例更新。
- 嘗試選第 6 項，確認 UI 阻止且後端不接受，也不會默默只取前 5 項。
- 確認已列為必備的設備無法再次列為希望設備。
- 記錄切換前的房源數量與清單前五名。
- 依序切換六個地圖選項。
- 確認房源數量與清單前五名不變。
- 確認圖例、圓點顏色與 hover 證據隨選項正確改變。
- 確認資料不足點為灰色，且不被說成低分。
- 選一間英文評論很多的房源，確認 `and`、`the`、`to` 等詞不出現在優點圖。
- 選一間只有 1～2 則有效正面評論的房源，確認不產生高頻排行；3～4 則時顯示低樣本警語。
- 切換兩間房源，確認優點圖、提及數與支持評論不會沿用上一間結果。
- 修改或切換優點圖後，確認口碑分與總分沒有被重複加分。

## 12. 最終判斷原則

遇到不確定情況時，依序選擇：

1. 保留可解釋性。
2. 保留資料真實性。
3. 清楚顯示限制。
4. 保持規則一致。
5. 再考慮視覺效果與效能。

> 寧可顯示「資料不足」，也不要產生看似完整、實際無法驗證的分數。
