# 2026-07-25 — 💰 營收與成長：敘事重構

**Goal:** 把「房型獲利排行 → 熱力圖 → 供需矩陣 → 長短租」四塊平行陳列，
改成三段有因果推進的敘事，主張定為：

> **「賣不掉的房源，不是比較差的房源。」**

## 為什麼是這個主張（2026-07-25 資料實測，scratchpad/vacancy_split*.py）

| 發現 | 數字 | 影響 |
|---|---|---|
| 沉睡房源（全年封鎖）太少 | 260 間(4.1%)，可算金額僅 69 間，喚醒增量 +0.8% | ❌ 砍掉此線 |
| 同格已訂率離散度極大 | 同行政區×房型 IQR 中位 **35.1pp** | ✅ 同儕比較有意義 |
| 落後房源（落差>20pp） | **1,162 間**（28.5%） | ✅ 主母體 |
| 落後組 vs 達標組可控因素 | 評分 4.86/4.84、超讚房東 **51.3%/41.1%**、設施 29/29、描述 492/485、最低入住 3/3、價格比 1.04/0.99 | ✅ **全部一樣 → 主張成立** |
| 保守抽成增量 | 落差只縮小 30% → **$21.1M（+7.5%）** | ✅ 可對外講 |
| 帕累托 | 增量前 **300 間 = 55% 機會**（占落後組 26%） | ✅ 投放名單 |
| 落後非區域現象 | 分布 24 格，各格落後占比 11~40%、中位 29% | ✅ 排除「只是某區爛」 |

**刻意不做**：任何「降價 X% → 空屋率降 Y%」的因果宣稱。橫斷面資料只能做
**同儕比較與排序**，頁面上一律以「落差」與「投報排序」表述。

## 母體與口徑（頁面須明示）

- 真實檔期口徑：`年營收估算 = price × booked_days`（沿用 `calendar_analytics.portfolio_summary`）
- 平台抽成 = 年營收估算 × 抽成率（預設 0.15）
- **已知資料坑**：calendar 6,419 / listings 5,511 / 交集 **4,406**（31% 對不起來）→ 頁面標註母體

## 三版：門檻改為使用者可調（使用者問「為什麼是 73 天」）

**73 天沒有資料依據**，是一版寫死的「落後同儕 20 個百分點」換算來的，20 只是
順手的整數。實測落差分布是平滑遞減、**沒有自然斷點**：

| 門檻 | 點名房子 | 占可比 | 平均少住 | 一年少賺合計 | 前 300 間占比 |
|---|---|---|---|---|---|
| 30 天 | 1,560 間 | 38% | 113 天 | $78,896,140 | 50% |
| 50 天 | 1,375 間 | 34% | 122 天 | $76,023,314 | 52% |
| **73 天（預設）** | **1,162 間** | **29%** | **134 天** | **$70,348,950** | **55%** |
| 100 天 | 871 間 | 21% | 149 天 | $59,343,114 | 62% |
| 120 天 | 705 間 | 17% | 159 天 | $50,919,633 | 69% |
| 150 天 | 436 間 | 11% | 173 天 | $33,113,026 | 88% |
| 180 天 | 130 間 | 3% | 194 天 | $10,958,221 | 100% |

既然資料沒有指出該切在哪，這條線就是**營運判斷而非資料事實**，不該由開發者
寫死。改為 ② 區塊內的滑桿 `pf_gap_days`（30–180 天，預設 73），
`peer_gap_table` / `uplift_ranking` 都在區塊內依當下門檻現算，
②③ 的房子數、金額、名單、圖表一起連動。

`render_gap_diagnosis()` 的簽章因此改為 `(d, cm, money) -> up`：門檻在它裡面，
所以名單也由它算好回傳給 ③，避免上游先用舊門檻算一份。

**對 Demo 的好處**：廠商問「為什麼是 73 天」時，「這是可調的營運決策，
你想拉多嚴都可以」比「我選的」好回答太多。

### 四版：滑桿改數字輸入框，③ 的 300 間也開放填寫

使用者要求兩個數字都改成「方框 + 上下增減鈕」。`st.slider` → `st.number_input`：
**這個數字要能精確指定並記錄成營運規則**（「我們的標準是 90 天」），滑桿拉不準
也講不清楚，number_input 才填得準。

| 控制項 | key | 預設 | 範圍 | step |
|---|---|---|---|---|
| 一年比鄰居少幾天有人住，才算「有問題」？ | `pf_gap_days` | 73 | 1–364 | 1 |
| 這一季有能力先處理幾間？ | `pf_topn` | 300 | 1–無上限 | 10 |

**`pf_topn` 刻意不設 `max_value`**：上限會隨 ② 的門檻變動，若使用者先填了大數字、
之後把門檻調嚴使名單變短，帶上限的 number_input 會因 session 值超出範圍而報錯。
改為不設上限、在程式裡 `min(want, len(up))` 夾住，並在夾住時明講「目前只找到 N 間，
想多找一些就把天數調小」。

連帶修正：`多花 3 倍力氣` 原本是寫死的字面值，改為 `len(up) / topn` 現算；
名單列數改為 `min(20, topn)`，避免使用者說只處理 5 間卻列出 20 間。

側欄既有的抽成率滑桿（`pf_commission`）不動，測試只斷言這兩個 key 不是滑桿。

## 六版：風險模型盲區的分流與建議作法

使用者點 ③名單第一名 #41487133 跳到風險管理，發現**風險模型說它「🟢 安全、28%」**，
但它正是名單裡損失最大的一間（一年只住 7 天、鄰居 174 天、少賺 $86 萬）。
LIME 歸因列出的還是「1km 內同房型密度 −13.85pp、床數 −10.45pp、臥室數 −9.16pp」
這類**優點**。此時按「產生此房源輔導通知」，寄出去的信等於告訴房東「你這間很棒」，
方向是反的。

### 根因：兩套系統量的東西不同

| | 風險模型（`_predictions.csv`） | ③名單（本頁） |
|---|---|---|
| 吃什麼 | **靜態結構特徵**：房型密度、床數、臥室數… | **真實訂房日曆** |

## 七版：「模型沒評估到」的原因註解（含一次自我更正）

使用者問「未評估到」是什麼原因，不能只丟一個數字。

### 第一次查證：結論錯了

只看了 id 格式與評論數就下結論：「id 都是 19 碼新格式、31.6% 從未有評論，
**推測**是資料不夠完整讓模型評估」。這個解釋很弱——因為 68% 其實有評論，
根本解釋不了為什麼它們也被排除。

### 第二次查證：找到乾淨的分界

追加比對 `host_since` 後，分界完全乾淨：

```
已納入模型的房源  host_since 最晚: 2024-09-30
未納入模型的房源  host_since 最早: 2024-10-11
重疊數: 0 / 392

未評估組     host_since 中位 2025-06-07，96% 在 2024-12 之後
模型有抓到組 host_since 中位 2017-06-20，  0% 在 2024-12 之後
```

**真正根因是訓練資料的時間切點**，不是資料品質。id 格式是「比較新」的
*結果*，不是獨立原因；評論少也是同一個原因的副產品。**第一版文案已更正**，
從「推測資料不足」改為明確的時間切點說明，並告訴使用者「重新訓練就會納入」。

### 實作

`platform_analytics.py` 新增兩個純函式：
- `model_coverage_cutoff(df, pred)` — 切點 = 模型母體內最晚的 `host_since`。
  **動態計算而非寫死日期**，模型重訓後自動更新；缺資料回 `None`（誠實地
  講不出原因，不硬掰日期）。
- `explain_unevaluated(df, cutoff)` — 逐筆產生短句原因。有 `host_since` 且
  晚於切點 → 「房東 2025-04 才加入，晚於模型訓練資料」；否則退回中性的
  「不在模型的訓練資料裡」。非「未評估」的列回空字串。

`portfolio_sections.py`：名單每一列的徽章下方加 `st.caption(原因)` ——
使用者要的是**那一列下面**就看得到，不是捲回上方彙總卡去猜是哪一間。
彙總卡的說明同步改為時間切點版本。

## 八版：常駐文字改成滑鼠移過去的小提示

使用者要求：七版每列常駐顯示的 `st.caption(原因)` 太占版面（20 列都撐高），
改成「滑鼠移到『沒評估到』才顯示小視窗」。

### 實作

純 CSS hover tooltip，不用 JS：`_TOOLTIP_CSS`（`.pf-tip` / `.pf-tip-bubble`，
`:hover` 切換 `visibility`/`opacity`）；徽章有原因時包一層
`<span class="pf-tip">徽章<span class="pf-tip-bubble">原因</span></span>`。
CSS 只在表頭有「風險模型怎麼看」欄位時注入一次（`st.markdown(_TOOLTIP_CSS,
unsafe_allow_html=True)`），沿用 `_BATCH_BAR_CSS`（risk_cockpit_sections.py）
已有的「表格專屬 CSS 注入」寫法。

### 驗證與已知限制

真人滑鼠 hover 需要瀏覽器辨識**真實游標位置**，JS 派發 `mouseover` 事件
**無法**觸發 `:hover` 偽類（已實測確認：派發後 `getComputedStyle` 仍是
`visibility:hidden`）。本環境的 `computer{action:"screenshot"}` 目前不可用，
連帶讓 `hover(coordinate)` 也用不了，所以無法用真實游標移動來驗證。

改用能證明機制本身正確的方式：

```
提示文字內容: "房東 2025-04 才加入，晚於模型訓練資料"          ✓ 正確
滑鼠移入前狀態: visibility:hidden, opacity:0                  ✓ 預設隱藏
CSSOM 內 .pf-tip:hover 規則: ".pf-tip:hover .pf-tip-bubble
  { visibility: visible; opacity: 1; }"                       ✓ 規則存在且未被跳脫/截斷
```

`:hover` + `visibility`/`opacity` 切換是無廠商前綴、所有現代瀏覽器都支援的
標準寫法,CSS 規則確認完整落地,可以合理判斷可以正常運作,但**沒有做到
逐項列出的「真人移動滑鼠」那種端對端驗證**——如實記錄此限制。
