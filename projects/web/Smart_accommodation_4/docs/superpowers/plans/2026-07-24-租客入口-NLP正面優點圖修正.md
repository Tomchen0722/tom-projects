# 租客入口 NLP「住客常提到的優點」修正實作計畫

> 狀態：已完成實作與驗證
> 日期：2026-07-24
> 負責範圍：租客入口
> 計分規則版本：`tenant-score-v1.0`（本案不升版）
> 優點整理規則版本：預定 `tenant-positive-aspects-v1.0`
> 討論依據：`doc/租客入口/租客入口_NLP正面關鍵詞圖表_問題說明與修改建議_組長討論版.pdf`

## 1. 目標

將租客入口房源詳情中的「高頻關鍵詞（正面）」改為「住客常提到的優點」，讓圖表回答：

> 近期有效正面評論中，住客具體稱讚這間房源哪些地方？

本案只修正正面優點的資料來源、文字處理、統計單位與 UI 呈現，不修改 NLP 內容分 N、口碑分 R、25 分綜合總分 S、個人化優先分 Q 或推薦排序。

## 2. 已確認的現況問題

### 2.1 同一區塊使用兩套評論範圍

- `modules/tenant_scoring.py::review_sentiment_breakdown()` 使用依日期降冪排序的近期最多 20 則評論。
- `modules/nlp_analysis.py::listing_review_summary()` 使用 `batch_sentiment(..., sample_n=200)`，超過 200 則時採固定亂數抽樣。
- 租客頁左側情感分佈來自近期 20 則，右側關鍵詞圖卻可能來自隨機 200 則。
- 因此畫面雖顯示 `有效分析 19/20`，關鍵詞次數仍可能超過 100，兩圖無法互相解釋。

### 2.2 使用整間房源的主要語言處理所有評論

- `listing_review_summary()` 先以整間房源的 `language_type.mode()` 選出一種主要語言。
- 截圖對應的房源依「269 則評論」推定為 `listing_id=14582309`；資料包含中文 127 則、英文 99 則、中英混合 35 則、其他 8 則。
- 該房源主要語言為中文，因此英文評論走中文分詞分支，只套用中文停用詞表。
- `and`、`the`、`to`、`is`、`very`、`was` 等英文停用詞因而進入排行。

### 2.3 現行統計是原始詞頻

- `extract_keywords()` 使用 `Counter.update(words)`。
- 同一則評論重複出現同一詞五次，就會累計五次。
- 正式需求的統計單位應為「提及該優點的正面評論則數」，同一則評論的同一優點最多計一次。

### 2.4 `cleaned_comments` 可能仍是原始文字

- 目前資料只有 `reviews_cleaned.csv.gz` 時，`modules/data_loader.py` 會以原始 `comments` 補上 `cleaned_comments`。
- 因此不可只依欄位名稱假設文字已完成網址、Email、數字、標點及其他雜訊清理。

### 2.5 缺少低樣本顯示保護

- 現行租客頁只要 `pos_keywords` 非空就畫圖。
- 尚未區分 0、1～2、3～4、5 則以上有效正面評論的呈現方式。

### 2.6 部署依賴未明確釘選

- `modules/nlp_analysis.py` 會匯入 `vaderSentiment` 與 `jieba`。
- 現行 `requirements.txt` 尚未列出這兩個套件。
- 正式實作需補上依賴並驗證部署環境實際啟用，不能只在本機可用。

## 3. 已確認的產品決策

1. 只使用目前房源依日期排序後的近期最多 20 則評論。
2. 只從語言可支援、內容有效且情緒分類為正面的評論整理優點。
3. 每則評論依自己的語言處理；中英混合評論同時處理中英文內容。
4. 移除中英文停用詞、標點、網址、Email、數字、單一字母、表情符號及其他雜訊。
5. 同一則評論的同一優點最多計一次。
6. 以「提及該優點的正面評論則數」排序。
7. 最多顯示 6～8 個優點。
8. 以小型、具版本的中英雙語主題映射輸出繁體中文優點名稱。
9. 0 則有效正面評論不畫圖。
10. 1～2 則有效正面評論不畫排行，改顯示正面評論摘錄。
11. 3～4 則可畫圖，但顯示「樣本較少，結果僅供參考」。
12. 5 則以上正常顯示。
13. 若正面評論達門檻但沒有任何可辨識優點，顯示資料不足，不虛構或補入示意詞。
14. 優點圖不增加任何分數，也不改變推薦排序。

## 4. 建議程式設計

### 4.1 建立共用的近期評論分析結果

在 `modules/nlp_analysis.py` 新增純函式，例如：

```python
analyze_recent_reviews(reviews_df, listing_id, window=20)
```

責任：

- 依 `listing_id` 篩選。
- 有日期時按日期降冪排序。
- 只取近期 `window=20` 則。
- 分別記錄原始取樣數、有效分析數及無法分析數。
- 每則保留 `listing_id`、評論 ID、日期、語言、文字、情緒標籤、有效狀態與原因。
- 套件未載入、不支援語言、空白、過短或無有效內容時，標為無法分析，不得當成中立。

`modules/tenant_scoring.py::review_sentiment_breakdown()` 應委派此函式取得統計，使口碑分與詳細頁使用同一批近期評論。重構前先建立特徵測試，確認在分析器正常可用時，既有 N、R 計算結果不變。

### 4.2 新增租客專用正面優點摘要

在 `modules/nlp_analysis.py` 新增：

```python
listing_positive_aspect_summary(
    reviews_df,
    listing_id,
    window=20,
    rule_version="tenant-positive-aspects-v1.0",
)
```

建議輸出：

```python
{
    "listing_id": 14582309,
    "status": "ok",
    "rule_version": "tenant-positive-aspects-v1.0",
    "window_size": 20,
    "sampled_count": 20,
    "analyzable_count": 19,
    "positive_count": 18,
    "matched_positive_count": 16,
    "items": [
        {
            "key": "cleanliness",
            "label": "環境乾淨",
            "mentions": 12,
            "coverage": 0.667,
        }
    ],
    "positive_snippets": [],
    "warnings": [],
}
```

狀態至少區分：

- `no_reviews`
- `no_analyzable_reviews`
- `no_positive_reviews`
- `positive_sample_too_small`
- `no_recognized_aspects`
- `low_sample`
- `ok`

租客頁改用新函式，不直接改變既有 `listing_review_summary()` 的公開欄位，避免影響 `modules/review_summary.py` 及其他入口。共用的底層清理函式可以重用，但輸出契約分開。

### 4.3 每則評論獨立處理語言

- `en`：英文斷詞後套用英文停用詞表。
- `zh`：jieba 分詞後套用中文停用詞表。
- `mixed_zh_en`：同一則評論分別處理中文與英文片段，再合併候選主題。
- `other`：標為不支援，不進入優點整理。
- 無論主要語言為何，英文 token 都必須套用英文停用詞；中文 token 都必須套用中文停用詞。

不得再以整間房源的 `mode()` 決定所有評論的關鍵詞處理方式。

### 4.4 小型中英雙語優點主題映射

第一版先聚焦租客可理解且可驗證的主題，例如：

| 主題 key | 顯示名稱 | 詞彙示例 |
|---|---|---|
| `cleanliness` | 環境乾淨 | clean、cleanliness、spotless、乾淨、整潔、清潔 |
| `location` | 地點便利 | convenient location、great location、地點方便、位置便利 |
| `mrt_access` | 鄰近捷運 | mrt、metro、station、捷運、地鐵 |
| `comfort` | 居住舒適 | comfortable、cozy、舒適、溫馨 |
| `host_service` | 房東友善 | friendly host、helpful host、房東友善、服務親切 |
| `quietness` | 環境安靜 | quiet、peaceful、安靜、寧靜 |
| `spaciousness` | 空間寬敞 | spacious、large room、寬敞、空間大 |
| `value` | 價格划算 | good value、worth、划算、超值 |

規則：

- 主題表需有 `POSITIVE_ASPECT_RULES_VERSION`。
- `great`、`nice`、`good` 等籠統正面詞不可單獨成為正式優點。
- `location`、`host` 等中性名詞不應在缺少正面語境時單獨判定為優點。
- 同義詞命中後先轉為主題 key，再以每則評論的主題集合計數。
- 概念圖中的示意詞不得寫死為輸出。

### 4.5 統計與涵蓋率

對每則有效正面評論建立 `set(aspect_keys)`，再計算：

```text
mentions(topic) = 提及該主題的有效正面評論則數
coverage(topic) = mentions(topic) / positive_count
```

必須成立：

```text
0 <= mentions(topic) <= positive_count
0 <= coverage(topic) <= 1
```

`matched_positive_count` 表示至少辨識到一個優點主題的正面評論數，用來呈現整理涵蓋率，但不參與評分。

### 4.6 快取策略

近期最多只處理 20 則，第一版可不新增快取，優先確保正確性並避免 stale state。

若效能實測後需要快取，快取鍵至少包含：

- `listing_id`
- 評論資料版本或內容指紋
- `window`
- 情緒分析規則版本
- `POSITIVE_ASPECT_RULES_VERSION`

只把 `listing_id` 當快取鍵不足以保證評論或規則更新後失效。

## 8. 必測案例

1. 評論大量包含 `the、and、to、is、very、was`，正式輸出不得出現這些詞。
2. 同一則評論重複 `clean` 五次，「環境乾淨」只計一則提及。
3. 同一則評論同時出現 `clean、乾淨、整潔`，同一主題仍只計一則。
4. 中文、英文及中英混合評論都能使用各自的停用詞與主題映射。
5. 中立、負面與無法分析評論不得進入正面優點整理。
6. 第 21 則及更舊評論不得影響近期 20 則結果。
7. 0 則有效正面評論不畫圖。
8. 1～2 則顯示摘錄，不畫排行。
9. 3～4 則畫圖並顯示低樣本警語。
10. 5 則以上正常顯示。
11. 正面評論足夠但無主題命中時顯示資料不足。
12. 每個 `mentions` 都小於或等於 `positive_count`。
13. 涵蓋率等於 `mentions / positive_count`。
14. 切換 `listing_id` 後不殘留前一間房源的圖表、數量或摘錄。
15. 變更優點整理規則後，N、R、S、Q 與排序完全不變。
16. `vaderSentiment` 或 `jieba` 未啟用時顯示無法分析，不得當成中立。
17. `modules/review_summary.py` 既有呼叫不因新函式而失敗。
