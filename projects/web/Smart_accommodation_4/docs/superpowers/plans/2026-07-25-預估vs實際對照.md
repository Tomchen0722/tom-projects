# 預估 vs 實際 對照（階段一：KPI 對照表）

日期：2026-07-25　依 2026-07-25 grilling 逐題定案實作。

## 背景（根因）

市場總覽的 KPI 卡（平均預估空屋率 50.7%、高風險占比 28.9%、平台年收入 $3.61 億）
全部是模型預估值，錨定在 2025-09-30 的資料快照，至今已近 10 個月，
但介面上沒有任何「實際發生了什麼」的對照。

追查 Y 定義後發現更根本的問題：

```
Y_vacancy = availability_365 ÷ 365
```

`availability_365` 是「日曆上顯示為可預訂的天數」，屬**供給面**（房東開放意願），
不是**需求面**（實際有人住）。日曆上「不可訂」混合三種原因：真被訂走／房東封鎖／
房東還沒開放遠期日曆。

實測證據（同一批房源、同一份檔案、同一時間窗口）：

| 檢驗 | 數值 |
|---|---|
| corr(日曆空屋率, 評論推算空屋率) | **0.122**（幾乎無關） |
| 日曆法均值 vs 評論法均值 | 50.4% vs 77.2%（差 26.5pp，純定義差異） |
| `availability_365=0` 的 357 間 | 模型判定空屋率 0%（最健康），但其中 **59.7% 過去一年零評論** |

即：已停業、沒生意的房源，在現行模型眼中是「零空屋率的模範生」。

## 計算口徑（已驗證）

**實際入住天數** —— Inside Airbnb 官方公式，已在本專案資料上 100% 精確重現
（6,241/6,241 筆零誤差，用 `number_of_reviews_ltm` 反推 `estimated_occupancy_l365d`）：

```
入住天數 = min(窗口內評論數 × 2 × max(minimum_nights, 3), 上限)
上限 = 窗口天數 × (255/365)     # 官方 70% 入住率上限，依窗口長度等比縮放
× 2 = 官方假設 50% 住客會留評論
```

**窗口**：2025-09-30（listings 快照日）→ 2026-06-30（reviews 最後一筆），共 273 天。

**排除規則（方案丁）**：`窗口內評論數 = 0` 且 `number_of_reviews_ltm = 0`
→ 標記 `is_dormant`（無經營跡象），不計入任何平均；1,380 間。

**兩邊同母體鐵律**：預估欄與實際欄都只算 4,469 間（排除 dormant 後）。
故對照表的預估值（49.7%/23.9%/$2.77億）**刻意不等於**市場總覽卡片
（50.7%/28.9%/$3.61億，5,849 間全母體），介面必須標明原因。

# 階段二：四象限進平台後台（風險管理分頁）

日期：2026-07-25（接續階段一，同日）

## 目標

平台後台目前只有單軸紅黃綠（模型 tier），會把「模型說安全、實際已停業」的房東
整批漏掉。階段二在風險管理分頁加入雙軸分類，讓平台方能分辨兩類房東並分流處理。

## 使用者定案

| 議題 | 定案 | 理由 |
|---|---|---|
| 第二軸（實際狀況） | **`real_vac`（已發生入住）** | 與階段一口徑一致；涵蓋 76.4% 高於日曆版 72.3% |
| 第一軸（模型體質） | **沿用 `tier`（模型機率）** | 與房東入口、風險管理現行一致；tier 才是真正的體質推估 |
| 放置分頁 | **風險管理** | 該頁本來就是「找房東 → 下鑽房源」的流程，四象限補上分流判斷 |

## 兩種第二軸的實測差異（決策依據）

| 候選 | 涵蓋 | 平均入住率 |
|---|---|---|
| A `real_vac`（已發生 273 天） | 4,469 間（76.4%） | 34.9% |
| B `booked_rate_d90`（未來 90 天日曆） | 4,227 間（72.3%） | 34.8% |

兩者平均值幾乎相同，但**個別房源相關係數僅 0.146** —— 總體量級一致、對「哪一間有問題」
的判斷經常不一致。選 A 是因為「過去 9 個月真的沒生意」比「未來 3 個月沒訂單」
更能證明房東已出問題，且遠期日曆有「房東尚未開放」的汙染。

## 門檻（沿用現行常數，實測分布健康無需重調）

以**實際入住率** = `1 - real_vac` 套用 `quadrant.BOOKED_FULL/BOOKED_EMPTY`：

| 條件 | 象限 |
|---|---|
| `is_dormant=1` | ❔ 無經營跡象（新增第 5 類，不混入其他格） |
| red/yellow + 入住率 < 20% | 🚨 高風險警訊 |
| red/yellow + 入住率 ≥ 20% | ⚠️ 靠降價撐住 |
| green + 入住率 ≥ 50% | ✅ 健康 |
| green + 入住率 < 50% | 👻 隱形危機 |

實測分布（5,849 間）：隱形危機 1,884 · 高風險警訊 1,035 · 無經營跡象 1,380 ·
健康 837 · 靠降價撐住 713。無任何一格塌陷。

## 設計決策（實作層）

- **不改動 `quadrant.classify_row` 既有行為** —— 房東入口依賴它，改了會連帶影響。
  改為在 `quadrant.py` 新增 `classify_actual()` 與 `ACTUAL_QUADRANTS`，
  共用同一組色票與優先序，但說明文案改寫為「已發生」語意
  （原文案寫「未來也幾乎沒人訂」，不適用於回顧視角）。
- **新增第 5 類「無經營跡象」** —— 階段一已確立此群體有獨立意義（1,380 間，
  前後兩期都零評論），平台行動與其他四類不同（先確認還想不想做，
  而非投入輔導資源），不可混入 alarm 或 unknown。

| ✅ 健康 | 837 | |
| ⚠️ 靠降價撐住 | 713 | |

隱形危機是最大一格，直接驗證了階段二的前提：單軸紅黃綠會把
「模型說安全、實際已在流血」的 1,884 間整批漏掉。

篩選連動驗證：大安區 1,123 間（191/387/103/150/292）、
北投區 62 間（19/14/4/3/22），加總無誤；北投區「高風險警訊+無經營跡象」占 66%，
與階段一算出的北投區高風險占比 62.9% 相互印證。

`T.LEGACY_P` 才是 quadrant color key（high/medium/accent/low/muted）對應色碼的表，
不是 `T.COLOR`——後者的鍵名是語意角色（danger/warning/secondary/success/muted）。
