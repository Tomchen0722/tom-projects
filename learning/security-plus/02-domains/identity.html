身分驗證與聯合登入

Kerberos、RADIUS、TACACS+、SAML、OAuth、OIDC——這些縮寫在考試裡幾乎每次都出現，而且常常互相當干擾選項。這一課把它們排進一張圖。

🎯 先分清楚三個常被混用的詞

這三個詞在中文裡都常被講成「驗證」，但考試會嚴格區分：

英文中文回答什麼問題例子
Authentication
(AuthN)		身分驗證你是誰？輸入帳號密碼、刷指紋
Authorization
(AuthZ)		授權你能做什麼？你是一般員工，看不到薪資系統
Accounting紀錄你做了什麼？稽核日誌記下你何時登入、改了什麼
💡 這三個合稱 AAA。考試看到 AAA 就是在講這三件事。
記憶順序：先證明你是誰 → 再決定你能做什麼 → 最後記錄你做了什麼。

🔑 驗證的三大要素（多因素的基礎）

要素英文例子弱點
你知道的Something you know密碼、PIN、安全問題會被猜、被偷、被釣魚
你擁有的Something you have手機、硬體金鑰、智慧卡會遺失、被偷
你本身的Something you are指紋、臉部、虹膜無法更換（外洩就永久失效）
你在哪裡Somewhere you areGPS、IP 位置可用 VPN 偽造
你怎麼做Something you do打字節奏、手寫簽名準確度較低
⚠️ 考試最愛的陷阱：什麼才算「多因素」？
密碼 + 安全問題 = 不是 MFA（兩個都是「你知道的」，屬於同一要素）
密碼 + 簡訊驗證碼 = 是 MFA（知道的 + 擁有的）
指紋 + 臉部 = 不是 MFA（兩個都是「你本身的」）

必須來自不同的要素類別，才叫多因素。
💡 各種 MFA 的強度排序（由弱到強）：
簡訊 OTP（可被 SIM 交換攻擊攔截）→ 電子郵件 OTP → 驗證器 App 的 TOTP → 推播確認 → FIDO2 / 硬體金鑰

FIDO2 / WebAuthn 之所以最強，是因為它會綁定網域——即使使用者被騙到釣魚網站，金鑰也不會對錯誤的網域回應。這是唯一能真正抵抗釣魚的方式。

🏢 企業內部的驗證協定

這一組是「公司內網」在用的，考試常拿它們互相當干擾選項。

Kerberos

項目說明
用在哪Windows 網域（Active Directory）的預設驗證協定
核心概念票證（Ticket）——驗證一次拿到票，之後用票去存取各種服務
關鍵角色KDC（金鑰發放中心）、TGT（票證授權票證）、TGS
好處密碼不會在網路上傳輸；實現單一登入（SSO）
弱點極度依賴時間同步——時鐘差超過 5 分鐘就驗證失敗
⚠️ 考試關鍵字：看到「時間同步」「時鐘偏移」「票證」就是 Kerberos。
這也是實務上 AD 環境最常見的故障——某台機器時間跑掉，就登不進網域。

相關攻擊也常考：Pass-the-Ticket（偷票證來用）、Golden Ticket（偽造 TGT，等於整個網域淪陷）。

LDAP

LDAP 是目錄服務的查詢協定，不是驗證協定本身——它是「公司的電話簿」，記錄有哪些使用者、群組、電腦。

💡 LDAP vs LDAPS：LDAP 走 389 埠明文傳輸；LDAPS 走 636 埠，用 TLS 加密。
考試常問「如何保護目錄查詢的機密性」→ 改用 LDAPS 或 STARTTLS。

Active Directory 就是微軟基於 LDAP + Kerberos 實作的目錄服務。

RADIUS vs TACACS+

比較RADIUSTACACS+
標準開放標準（IETF）Cisco 專有
傳輸協定UDP（1812/1813）TCP（49）
加密範圍只加密密碼，其餘明文加密整個封包
AAA 拆分驗證與授權綁在一起驗證、授權、紀錄各自獨立
典型用途使用者上網：Wi-Fi、VPN、802.1X管理設備：誰能登入路由器下哪些指令
⚠️ 這組是必考題，記法：
RADIUS = 給「使用者」用的（連 Wi-Fi、撥 VPN），UDP、只加密密碼。
TACACS+ = 給「管理員」用的（登入網路設備），TCP、全加密、可細到指令層級授權。

題目說「要控制哪個工程師能在路由器上下哪些指令」→ TACACS+（因為它的授權是獨立且細緻的）。

🌐 跨組織的聯合身分（Federation）

前面那組是公司內部。當你要「用 Google 帳號登入某個網站」或「員工用公司帳號登入 Salesforce」，就需要聯合身分協定。

💡 先建立最重要的一組區別，這題幾乎每次考：

SAML = 驗證（AuthN），回答「這個人是誰」
OAuth 2.0 = 授權（AuthZ），回答「這個 App 可以動我的哪些資料」
OIDC = 蓋在 OAuth 之上的驗證層，補上 OAuth 缺的「你是誰」

常見誤解：OAuth 不是用來登入的。它原本的設計是「授權第三方存取資源」，很多人拿它當登入用，才有了 OIDC 來把這件事做對。

SAML 2.0

項目說明
資料格式XML
三個角色使用者、IdP（身分提供者，如公司 AD FS）、SP（服務提供者，如 Salesforce）
傳遞什麼SAML Assertion——一份簽章過的 XML，聲明「這個人是誰、有哪些屬性」
典型場景企業 SSO：員工用公司帳號登入各種 SaaS

OAuth 2.0 與 OIDC

項目OAuth 2.0OIDC
目的授權（給 App 存取權）驗證（確認使用者身分）
資料格式JSONJSON
核心產物Access Token額外多一個 ID Token（JWT 格式）
典型場景「允許這個 App 讀取你的 Google 雲端硬碟」「用 Google 帳號登入」
⚠️ 三者的選擇題怎麼判斷：
• 題目出現 XML、Assertion、企業內部 SSO → SAML
• 題目出現 「授權第三方 App 存取資料」、API 存取 → OAuth 2.0
• 題目出現 「用某某帳號登入」、ID Token、行動 App 登入 → OIDC

另外：SAML 較多用於傳統企業與網頁 SSO；OIDC 較多用於行動 App 與現代 API。新專案通常選 OIDC。

🚪 存取控制模型

驗證完之後，要決定「你能碰什麼」。這幾個模型考試會直接問定義：

模型誰決定權限特徵典型場景
DAC
自主存取控制		資源擁有者你建的檔案你決定分享給誰Windows 檔案權限、Google Drive
MAC
強制存取控制		系統依標籤強制擁有者也不能自行放寬軍方、政府機密分級
RBAC
角色型		依職務角色權限給「角色」，人再綁角色企業最常用
ABAC
屬性型		依多重屬性動態判斷可考慮時間、地點、裝置狀態零信任架構
Rule-based依預設規則「上班時間才能存取」防火牆規則、時間限制
💡 DAC vs MAC 最好記的差別：DAC 的 D 是 Discretionary（自主）——擁有者有裁量權；MAC 的 M 是 Mandatory（強制）——系統說了算，誰都不能改。

RBAC vs ABAC：RBAC 看「你是什麼角色」；ABAC 看「你是什麼角色 而且 現在幾點、在哪裡、用什麼裝置」。ABAC 更彈性但也更複雜。

🔐 特權帳號管理（PAM）

一般使用者的帳號被盜，損失有限；管理員帳號被盜，整個組織淪陷。所以特權帳號要另外管。

機制解決什麼
最小權限原則只給完成工作所需的最低權限
職責分離（SoD）同一個人不能既申請又核准
Just-in-Time 權限需要時才提權，用完自動收回
密碼保管庫管理員不知道實際密碼，由系統代登入
工作階段錄影特權操作全程錄下來供稽核
定期權限審查檢查有沒有人權限累積過多（權限蔓延）
⚠️ 權限蔓延（Privilege Creep）是實務上最常見的問題：員工轉調部門時，新權限加上去了，舊權限卻沒有收回。做久了一個人身上累積十幾個部門的權限。

解法是定期的存取審查（Access Review），以及把「離職/轉調流程」與身分系統自動串接。

📝 隨堂練習

Q1. 公司要求員工登入時輸入密碼，再回答「你的第一隻寵物叫什麼」。這算多因素驗證嗎？

看答案
不算。密碼和安全問題都屬於「你知道的」，是同一個要素類別。

這叫「多步驟驗證」而不是「多因素驗證」。要成為 MFA，必須加入不同類別——例如手機驗證器（你擁有的）或指紋（你本身的）。

而且安全問題的安全性很低：寵物名字、母親的娘家姓這類資訊常常能從社群媒體查到，或用社交工程問出來。

Q2. 網路工程師需要限制「張三只能在路由器上執行 show 指令，不能執行 configure」。應該用 RADIUS 還是 TACACS+？

看答案
TACACS+。兩個理由：

① TACACS+ 把授權（Authorization）獨立出來，可以做到指令層級的授權控制。RADIUS 把驗證與授權綁在一起，粒度較粗。
② TACACS+ 的典型用途就是網路設備管理；RADIUS 的典型用途是使用者網路存取（Wi-Fi、VPN）。

額外加分：TACACS+ 用 TCP 且加密整個封包，管理流量的機密性也比較好。

Q3. 使用者抱怨「早上都好好的，下午突然登不進網域了」。查了發現該台電腦的時間比伺服器快了 8 分鐘。原因是什麼？

看答案
Kerberos 的時間偏移限制。Kerberos 的票證帶有時間戳記，用來防止重放攻擊（攻擊者錄下驗證封包再重送）。

預設容忍的時鐘偏移是 5 分鐘，超過就判定票證無效。

解法：把該台電腦的時間與網域控制站同步（通常設定 NTP 指向 DC）。
預防：全網統一 NTP 來源，並監控時間偏移。這是 AD 環境最經典的故障之一。

Q4. 某個手機 App 想讓使用者「用 Google 帳號登入」，並且之後要讀取使用者的 Google 行事曆。應該用哪些協定？

看答案
兩個都要，而且它們負責不同的事：

• OIDC 負責登入——確認「這個人是誰」，拿到 ID Token（JWT），裡面有使用者識別碼與 email。
• OAuth 2.0 負責授權——取得 Access Token，用來呼叫 Google Calendar API 讀行事曆。

因為 OIDC 本來就是建構在 OAuth 2.0 之上，實務上這是同一次授權流程就能一起完成：請求時同時要 openid（給 OIDC）和 calendar.readonly（給 OAuth）這兩個 scope。

為什麼不用 SAML？SAML 是 XML 格式、為瀏覽器場景設計，在行動 App 上笨重且不易處理。行動與 API 場景一律優先 OIDC。
