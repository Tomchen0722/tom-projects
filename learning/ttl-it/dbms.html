🗄️ 資料庫管理及應用 考題形態與滿分關鍵

SUBJECT FOCUS & STRATEGY

「資料庫管理及應用」占台灣菸酒第一試筆試總成績 45%，為全非選擇題型。 歷年命題重點非常鮮明：「ERD 實體關聯圖繪製與轉表」、「正規化推導（1NF 至 BCNF）」、「SQL 複雜子查詢與 JOIN 撰寫」以及「交易管理 ACID 與並行鎖定 2PL」四大台柱幾乎年年輪番上陣。

💡 資料庫高分三大心法

1. ERD 標記要規範： 實體（矩形）、屬性（橢圓）、關聯（菱形）、主鍵（底線）、外來鍵（虛線或 FK 標示），基數比（1:1, 1:N, M:N）務必清晰標明。

2. 正規化推導務必寫出「函數相依（FD）」： 證明為何違反 2NF（存在部分相依）或 3NF（存在遞移相依），列出候選鍵（Candidate Key），切忌直接寫答案。

3. SQL 關鍵字使用大寫標準規範： 寫作 SELECT, FROM, WHERE, GROUP BY, HAVING, ORDER BY，條件與別名（Alias）排版乾淨俐落。

🏛️ 第一單元：資料庫架構與資料獨立性

DATABASE SYSTEM ARCHITECTURE

由 ANSI/SPARC 提出的資料庫三層綱要架構（Three-Schema Architecture）旨在達成資料獨立性（Data Independence），降低應用程式與底層實體儲存之耦合度。

架構層級 英文術語與發音 對應視圖與職責 資料獨立性保證
外部層 (External Level) External Schema
User View 		各部門或特定使用者所見到的客製化局部資料視圖（View）。隱藏無權限之欄位，提供安全性。 邏輯資料獨立性（Logical Data Independence ）：
當概念層綱要變更（例如新增一個欄位或表格）時，現有外部層視圖或應用程式無需隨之改寫。
概念層 (Conceptual Level) Conceptual Schema
Community View 		整個資料庫的全局邏輯結構，描述所有實體、屬性、關聯、完整性限制條件（Integrity Constraints），不涉底層儲存硬體細節。
內部層 (Internal Level) Internal Schema
Physical Storage 		描述資料在硬碟或儲存媒體中的實體儲存結構、記錄格式、B+ Tree 索引排列、壓縮與加密方式。 實體資料獨立性（Physical Data Independence ）：
變更內部層儲存結構（如建立新索引或更換硬碟路徑）時，概念層綱要維持不變。

📐 第二單元：實體關聯模型 (ER Model) 與轉表規範

ERD MODELING & RELATIONAL MAPPING
關聯型態 英文術語與發音 轉為關聯綱要（Table Schema）的外來鍵規則 台酒產銷實務範例
一對一 (1:1) One-to-One 將任一方的主鍵（Primary Key, PK）放入另一方作為外來鍵（Foreign Key, FK），並加上唯一性限制（UNIQUE）。通常偏向放入完全參與（Total Participation）的一方。 酒廠（Brewery）與 廠長（Plant_Manager）：每一酒廠由一位廠長負責。
一對多 (1:N) One-to-Many 「多端擺外來鍵」原則： 將 1 端實體的主鍵，放入 N 端實體的關聯表中作為外來鍵（FK）。 門市（Store）與 訂單（Orders）：一間門市可接收多筆訂單，訂單表記錄 store_id (FK)。
多對多 (M:N) Many-to-Many 「必須新增獨立中介關聯表」： 該中介表的主鍵由兩端實體的主鍵組合而成（Composite PK），同時各自作為指向兩端的外來鍵。 訂單（Orders）與 產品（Products）：一筆訂單包含多項產品，一種產品在多筆訂單中出現；中介表 Order_Detail(order_id, product_id, quantity)。
多值屬性 Multivalued Attribute 必須獨立建表，以實體原主鍵加上該多值屬性作為複合主鍵。 門市聯絡電話（一間門市可能有多組電話）：Store_Phone(store_id, phone_number)。

🔍 第三單元：正規化理論 (Normalization 1NF ~ BCNF)

FUNCTIONAL DEPENDENCY & NORMAL FORMS

正規化之目的乃在消除資料重複（Data Redundancy），並根除新增異常（Insert Anomaly）、刪除異常（Delete Anomaly）與修改異常（Update Anomaly）。

正規形式 英文術語與發音 必須消除之相依性與條件 白話判定標準
第一正規化 (1NF) 1NF
Atomic Value 		每一個屬性的值域皆必須為原子值（Atomic / 單一不可再分），且不存在重複群（Repeating Groups）。 一個欄位格子不能塞入多筆資料（如多個電話或逗號分隔的商品）。
第二正規化 (2NF) 2NF
Partial Dependency 		符合 1NF，且消除所有「部分函數相依」（Partial FD）。即非主鍵屬性必須完全依賴整個複合主鍵，不能只依賴主鍵的一部分。 若主鍵是單一欄位，則自動滿足 2NF！只有複合主鍵時才需檢查是否部分依賴。
第三正規化 (3NF) 3NF
Transitive Dependency 		符合 2NF，且消除所有「遞移函數相依」（Transitive FD）。即非主鍵屬性不得依賴另一個非主鍵屬性（若 X ➔ Y 且 Y ➔ Z，則必須拆表消除 X ➔ Z）。 不能有「隔層依賴」現象（例如：員工號 ➔ 部門號 ➔ 部門名稱，需將部門拆為獨立表）。
BCNF (Boyce-Codd) BCNF
Superkey 		比 3NF 更嚴格：對於每個非平凡函數相依 X ➔ Y，其決定者 X 必須為超鍵（Superkey）。 消除主鍵屬性對非超鍵的依賴，徹底杜絕任何剩餘之冗餘。

💻 第四單元：SQL 實戰指令與高頻查詢模式

SQL DDL, DML, JOINS & WINDOW FUNCTIONS

在台酒從業職員試卷上，SQL 題目要求考生精確手寫 SQL 語句。請注意標準語法、彙總與巢狀查詢：

【實戰範例】：台酒各門市酒品銷售量統計與查詢

題目需求： 查詢 2025 年度總銷售金額超過 1,000,000 元之各門市名稱（store_name），及其銷售總額與平均訂單金額，並由高至低排序：

-- 台酒各門市年度營收統計與 HAVING 篩選實戰
SELECT 
    s.store_name,
    COUNT(o.order_id) AS total_orders,
    SUM(o.total_amount) AS total_revenue,
    ROUND(AVG(o.total_amount), 2) AS avg_order_value
FROM 
    Stores s
INNER JOIN 
    Orders o ON s.store_id = o.store_id
WHERE 
    o.order_date BETWEEN '2025-01-01' AND '2025-12-31'
GROUP BY 
    s.store_id, s.store_name
HAVING 
    SUM(o.total_amount) >= 1000000
ORDER BY 
    total_revenue DESC;
【SQL 執行順序口訣】：
FROM ➔ ON ➔ JOIN ➔ WHERE ➔ GROUP BY ➔ HAVING ➔ SELECT ➔ DISTINCT ➔ ORDER BY ➔ LIMIT。
重點提醒： WHERE 是在分組前過濾單筆資料，不能使用彙總函數（如 SUM）；HAVING 是在分組後過濾群組結果！

🔐 第五單元：交易管理 ACID 與並行控制 (2PL)

TRANSACTION MANAGEMENT & CONCURRENCY CONTROL
核心特徵 英文術語與發音 技術定義與達成機制 台酒常考考點
Atomicity (原子性) Atomicity 「All or Nothing」原則。交易內之所有操作要麼全部成功寫入，要麼任一失敗時全數回復（Rollback）至初始狀態。由復原管理員（Recovery Manager / WAL 日誌）確保。 轉帳交易中，扣款成功但入帳失敗時之回復機制。
Consistency (一致性) Consistency 交易執行前後，資料庫必須維持所有既定的完整性條件（如庫存不得為負數、外來鍵關聯存在）。 符合實體完整性與參照完整性限制。
Isolation (隔離性) Isolation 多個並行交易同時執行時，彼此互不干擾，其執行結果與按某種順序循序執行之結果完全相同。由並行控制（Concurrency Control / 鎖定機制）確保。 四大隔離等級（Isolation Levels）：
1. Read Uncommitted（可能髒讀）
2. Read Committed（防髒讀，不可重複讀仍可能）
3. Repeatable Read（防不可重複讀，幻讀仍可能）
4. Serializable（最嚴格，防範一切並行問題）
Durability (持久性) Durability 交易一旦確認提交（Commit），其所產生的變更即永久寫入資料庫儲存媒體中，即使隨後發生斷電或系統當機亦絕不遺失。由預寫式日誌（WAL）與檢查點（Checkpoint）確保。 REDO 與 UNDO 復原流程。
二階段鎖定協定 Two-Phase Locking (2PL) 1. 成長階段（Growing Phase）： 交易只能獲取鎖定（Lock），不可釋放任何鎖定。
2. 縮減階段（Shrinking Phase）： 交易一旦釋放任一鎖定，即進入此階段，只能釋放鎖定，絕不可再獲取任何新鎖定。
定理： 凡遵守 2PL 之排程，必保證為可循序化（Conflict Serializable）！ 		Strict 2PL（嚴格二階段鎖）： 所有排他鎖（X-Lock）必須維持至交易 Commit 或 Abort 時才一次性釋放。可徹底杜絕級聯回退（Cascading Rollback）！

PAST ESSAY QUESTIONS & BENCHMARK SOLUTIONS
📝 申論一：給定關聯綱要 R(A, B, C, D, E) 與函數相依集合 F = {A ➔ B, AB ➔ C, C ➔ D, D ➔ E}，試求 R 之候選鍵（Candidate Key），並依序推導其目前最高符合第幾正規化？若不符合 3NF，請進行無損分解。【台酒經典題】 ▼

【完整詳細推導過程】

步驟一：求屬性閉包（Attribute Closure）與候選鍵：
觀察相依集合 F：
• 屬性 A 只出現在左邊，必為候選鍵之一部分。
• 計算閉包 A+：
1. 初始：{A}
2. 依 A ➔ B，得 {A, B}
3. 依 AB ➔ C，得 {A, B, C}
4. 依 C ➔ D，得 {A, B, C, D}
5. 依 D ➔ E，得 {A, B, C, D, E} = R 全部屬性！
因此，唯一候選鍵（Candidate Key / 主鍵）為 A。主鍵屬性為 {A}，非主鍵屬性為 {B, C, D, E}。

步驟二：判斷最高符合第幾正規化：
1. 1NF： 屬性皆為原子值，符合 1NF。
2. 2NF 檢驗： 主鍵為單一屬性 A，不存在任何真子集，故不存在「部分函數相依」，滿足 2NF！
3. 3NF 檢驗： 觀察相依 C ➔ D 與 D ➔ E：
因 A ➔ C 且 C ➔ D，存在非主鍵屬性對非主鍵屬性之依賴，即存在「遞移函數相依（Transitive Dependency）」！
因此，R 目前最高僅符合第二正規化（2NF），不符合 3NF。

步驟三：無損且保持相依之 3NF 分解：
依據 3NF 分解演算法，將產生遞移相依之屬性獨立拆解：
1. 依 D ➔ E 拆出：R1(D, E)，主鍵為 D。
2. 依 C ➔ D 拆出：R2(C, D)，主鍵為 C。
3. 剩餘相依 A ➔ B, C 組成：R3(A, B, C)，主鍵為 A。
最終 3NF 分解結果為：R1(D, E), R2(C, D), R3(A, B, C)，具備無損連接與相依性保持。
