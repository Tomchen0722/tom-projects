A. 網路模型與設備（第 1～8 題）

1OSI
OSI 模型中，負責「邏輯定址與繞送」的是哪一層？
  • (A) 資料連結層　(B) 網路層　(C) 傳輸層　(D) 會議層
看詳解
答案：(B) 網路層（Network Layer，第 3 層）

層級速記：
‧ L2 資料連結層 → 實體定址（MAC）、訊框、交換器
‧ L3 網路層 → 邏輯定址（IP）、封包、路由器
‧ L4 傳輸層 → 端對端可靠傳輸、埠號、區段

「定址」有兩種要分清楚：MAC 是 L2、IP 是 L3。
2設備
一台 24 埠的交換器，所有埠均已連接電腦，且未設定 VLAN。此網路有幾個碰撞網域與幾個廣播網域？
  • (A) 1 個碰撞網域、1 個廣播網域
  • (B) 24 個碰撞網域、1 個廣播網域
  • (C) 1 個碰撞網域、24 個廣播網域
  • (D) 24 個碰撞網域、24 個廣播網域
看詳解
答案：(B) 24 個碰撞網域、1 個廣播網域

‧ 交換器的每一個埠就是一個獨立碰撞網域（各埠獨立頻寬、全雙工不碰撞）→ 24 個
‧ 交換器不會分割廣播網域（廣播訊框會洪泛到所有埠）→ 1 個

對照：
‧ 集線器（Hub）：24 埠 = 1 個碰撞網域（共享頻寬）
‧ 路由器：每個介面各為一個廣播網域
‧ 若切成 3 個 VLAN → 變成 24 個碰撞網域、3 個廣播網域
3OSI
資料在 OSI 各層的名稱，下列對應何者錯誤？
  • (A) 傳輸層 — Segment　(B) 網路層 — Packet　(C) 資料連結層 — Frame　(D) 實體層 — Datagram
看詳解
答案：(D)
實體層的資料單位是 Bit（位元）。

Datagram 通常指 UDP 的資料單位（User Datagram）或 IP Datagram，不是實體層。

由上而下記：Data → Segment → Packet → Frame → Bit
4設備
交換器收到一個訊框，但其 MAC 位址表中找不到目的 MAC，交換器會如何處理？
  • (A) 丟棄該訊框　(B) 洪泛（Flooding）到除來源埠外的所有埠　(C) 回送錯誤訊息　(D) 轉送給預設閘道
看詳解
答案：(B) 洪泛（Flooding）

交換器的三種行為：
‧ Forward：查表找到 → 只送該埠
‧ Flooding：查表找不到 → 送到所有其他埠（讓目標自己回應，順便學習）
‧ Filter：目的埠與來源埠相同 → 丟棄

資安延伸：MAC 洪泛攻擊（MAC Flooding）即利用此機制——大量偽造來源 MAC 塞爆位址表，使交換器對所有流量都洪泛，攻擊者便能竊聽。防護為 Port Security（限制每埠 MAC 數量）。
5VLAN
關於 VLAN，下列敘述何者錯誤？
  • (A) 可在同一台實體交換器上分割多個廣播網域
  • (B) 不同 VLAN 間的通訊必須經由 L3 設備繞送
  • (C) Trunk Port 使用 IEEE 802.1Q 標籤承載多個 VLAN
  • (D) 同一 VLAN 內的主機必須連接在同一台實體交換器上
看詳解
答案：(D)
VLAN 是邏輯分群，可以跨越多台交換器——這正是 Trunk Port 存在的目的：交換器之間以 Trunk 連接，透過 802.1Q 標籤讓同一 VLAN 的流量能跨設備傳遞。

VLAN 的核心價值就是「脫離實體位置的限制」：三樓的會計人員和一樓的會計人員可以在同一個 VLAN，人員換座位不用重拉線。
6實體層
下列關於光纖的敘述，何者錯誤？
  • (A) 不受電磁干擾影響　(B) 傳輸距離較雙絞線遠　(C) 單模光纖傳輸距離較多模短　(D) 竊聽難度較銅線高
看詳解
答案：(C)
單模（Single-mode）：蕊徑細、光走單一路徑、色散小 → 距離最遠（數十公里），成本較高。
多模（Multi-mode）：蕊徑粗、多路徑造成色散 → 距離較短（數百公尺至 2 公里），成本低。

記憶法：「單一路線跑得遠」。
7STP
交換器網路中使用 STP（生成樹協定）的主要目的為？
  • (A) 加密傳輸資料　(B) 防止網路迴圈造成廣播風暴　(C) 分配 IP 位址　(D) 提升傳輸速率
看詳解
答案：(B)
交換器之間若有迴圈，廣播訊框會無限循環放大 → 廣播風暴，並造成 MAC 表震盪與訊框重複。

關鍵理解：實體上要有備援線路（避免單點故障），但邏輯上只能啟用一條。STP 就是負責「平時阻斷備援路徑、故障時自動啟用」。

注意：IP 封包有 TTL 可防止無限迴圈，但L2 訊框沒有 TTL——這就是為什麼 L2 特別需要 STP。這是很好的深度考點。
8無線
無線網路使用 CSMA/CA 而非 CSMA/CD 的主要原因為？
  • (A) 無線速度較快　(B) 無線網卡無法同時收發，且存在隱藏節點問題　(C) 無線不需要碰撞處理　(D) CSMA/CD 已被淘汰
看詳解
答案：(B)
兩個原因：
1. 無線網卡是半雙工，無法一邊傳送一邊偵測碰撞（CD 的前提就是「邊說邊聽」）。
2. 隱藏節點問題：A 與 C 都在 B 的範圍內，但 A、C 彼此聽不到 → 兩者都以為通道空閒而同時傳送，在 B 處碰撞。

因此改採事前避免：以 RTS/CTS 交握取得傳送許可，並用 ACK 確認送達。

B. IP 位址與子網路（第 9～18 題，計算題重點）

9子網路
IP 位址 192.168.10.100/26，其網路位址與廣播位址分別為？
  • (A) 192.168.10.0 / 192.168.10.255
  • (B) 192.168.10.64 / 192.168.10.127
  • (C) 192.168.10.96 / 192.168.10.127
  • (D) 192.168.10.64 / 192.168.10.255
看詳解
答案：(B) 192.168.10.64 / 192.168.10.127

三步驟解法：
① /26 → 遮罩末組 = 192（26 − 24 = 2 個網路位元 → 11000000）
② 區塊大小 = 256 − 192 = 64
③ 網段邊界：.0、.64、.128、.192 → 100 落在 64～127

→ 網路位址 = .64、廣播位址 = .127（下一段起點 128 減 1）
→ 可用範圍 .65 ~ .126，共 2⁶ − 2 = 62 台
10子網路
子網路遮罩 255.255.255.240 對應的 CIDR 表示法與可用主機數為？
  • (A) /26，62 台　(B) /27，30 台　(C) /28，14 台　(D) /29，6 台
看詳解
答案：(C) /28，14 台

240 = 11110000（4 個 1）→ 24 + 4 = /28
主機位元 = 32 − 28 = 4 → 2⁴ − 2 = 14 台

必背的九個遮罩值：0、128、192、224、240、248、252、254、255
對應 1 的個數：0、1、2、3、4、5、6、7、8

考場上把這排數字先寫在草稿紙角落，所有子網路題都會變快。
11子網路
將 192.168.1.0/24 切割成 8 個大小相同的子網路，每個子網路的遮罩與可用主機數為？
  • (A) /27，30 台　(B) /26，62 台　(C) /28，14 台　(D) /29，6 台
看詳解
答案：(A) /27，30 台

切成 8 個子網路 → 需借 3 個位元（2³ = 8）
原本 /24 → 借 3 位元 → /27，遮罩 255.255.255.224
主機位元 = 32 − 27 = 5 → 2⁵ − 2 = 30 台

八個子網路（區塊大小 = 256 − 224 = 32）：
.0、.32、.64、.96、.128、.160、.192、.224

驗算：8 × 32 = 256 ✔
12子網路
某部門需要至少 100 台主機的 IP 位址，最節省位址的子網路遮罩為？
  • (A) /24　(B) /25　(C) /26　(D) /27
看詳解
答案：(B) /25

逐一測試（要找「剛好夠用」的最小區塊）：
‧ /26 → 2⁶ − 2 = 62 台 ✘ 不夠
‧ /25 → 2⁷ − 2 = 126 台 ✔ 夠且最省
‧ /24 → 254 台（夠，但浪費 128 個位址）

解題技巧：從「需求數 + 2」往上找最接近的 2 的次方。100 + 2 = 102 → 最接近且大於它的是 128 = 2⁷ → 主機位元 7 位 → /25。
13子網路
下列哪一個 IP 位址可以指派給主機使用？
  • (A) 192.168.5.63/26　(B) 192.168.5.64/26　(C) 192.168.5.100/26　(D) 192.168.5.127/26
看詳解
答案：(C) 192.168.5.100/26

/26 區塊大小 = 64，網段為 .0-.63、.64-.127、.128-.191、.192-.255

‧ (A) .63 → 第一段的廣播位址 ✘
‧ (B) .64 → 第二段的網路位址 ✘
‧ (C) .100 → 落在 .65~.126 的可用範圍 ✔
‧ (D) .127 → 第二段的廣播位址 ✘

口訣：每個網段的頭（網路位址）與尾（廣播位址）都不能給主機用。
14子網路
將 172.16.4.0/24、172.16.5.0/24、172.16.6.0/24、172.16.7.0/24 聚合成單一路由，結果為？
  • (A) 172.16.4.0/21　(B) 172.16.4.0/22　(C) 172.16.0.0/22　(D) 172.16.4.0/23
看詳解
答案：(B) 172.16.4.0/22

把第 3 組轉二進位找共同前綴：
4 = 00000100
5 = 00000101
6 = 00000110
7 = 00000111
    ↑↑↑↑↑↑ 前 6 位元相同
前兩組相同（16 位元）＋ 第 3 組相同 6 位元 = 22 位元 → 172.16.4.0/22

驗算：/22 在第 3 組的區塊大小 = 256 − 252 = 4 → 涵蓋 4、5、6、7 ✔

快速法：連續 4 個 /24 聚合 → 位元數減 2（因 2² = 4）→ 24 − 2 = 22。
15IP
某台電腦的 IP 位址顯示為 169.254.15.30，最可能的原因為？
  • (A) 已成功取得公有 IP　(B) DHCP 伺服器無回應，自動指派 APIPA 位址　(C) 該電腦設定為靜態 IP　(D) 網路卡故障
看詳解
答案：(B)
169.254.0.0/16 是 APIPA（自動私有 IP 定址），Windows 在 DHCP 取得失敗時自動指派。

實務判讀：看到這個 IP 就代表「DHCP 沒通」，應排查：
1. 網路線／交換器埠是否正常
2. DHCP 伺服器是否運作、位址池是否耗盡
3. 跨網段時 DHCP Relay 是否設定
4. 是否被 Port Security 或 802.1X 阻擋

這是網路疑難排解申論題的高頻素材。
16IP
下列何者不是 RFC 1918 定義的私有 IP 位址範圍？
  • (A) 10.0.0.0/8　(B) 172.16.0.0/12　(C) 192.168.0.0/16　(D) 127.0.0.0/8
看詳解
答案：(D)
127.0.0.0/8 是迴路位址（Loopback），用於測試本機 TCP/IP 堆疊（127.0.0.1 即 localhost），不是私有位址。

三個私有網段要背熟：
‧ 10.0.0.0/8（1 個 A 級）
‧ 172.16.0.0/12（172.16 ~ 172.31，共 16 個 B 級）
‧ 192.168.0.0/16（256 個 C 級）

注意 172 那個範圍是 /12 不是 /16，這是常見陷阱。
17路由
路由器繞送表中同時存在 10.0.0.0/8、10.1.0.0/16、10.1.1.0/24 三筆記錄，收到目的地為 10.1.1.5 的封包時會選擇？
  • (A) 10.0.0.0/8　(B) 10.1.0.0/16　(C) 10.1.1.0/24　(D) 隨機選擇
看詳解
答案：(C) 10.1.1.0/24
依最長前綴匹配（Longest Prefix Match）原則，前綴越長代表越精確，優先選用。

白話：「台北市大安區」比「台北市」更精確，當然聽前者。

延伸：預設路由 0.0.0.0/0 前綴長度為 0，所以永遠是最後的選擇——「都找不到才走這條」。
18IPv6
關於 IPv6，下列敘述何者錯誤？
  • (A) 位址長度為 128 位元
  • (B) 取消了廣播（Broadcast），改用多播與任播
  • (C) 標頭中保留了檢查碼（Checksum）欄位以提升可靠性
  • (D) 支援無狀態位址自動設定（SLAAC）
看詳解
答案：(C)
IPv6 移除了標頭檢查碼，理由是：
1. 資料連結層（如 Ethernet FCS）與傳輸層（TCP/UDP checksum）已有檢查機制，重複檢查是浪費
2. IPv4 每經一台路由器就要因 TTL 改變而重算檢查碼 → 移除後路由器處理速度更快

這正是 IPv6「簡化標頭以提升繞送效能」的設計精神，也是常考點。

C. 傳輸層與應用層（第 19～27 題）

19TCP
TCP 三向交握的正確順序為？
  • (A) SYN → ACK → SYN　(B) SYN → SYN+ACK → ACK　(C) ACK → SYN → SYN+ACK　(D) SYN → FIN → ACK
看詳解
答案：(B) SYN → SYN+ACK → ACK

① 用戶端送 SYN（seq=x）「我想連線」
② 伺服器回 SYN+ACK（seq=y, ack=x+1）「好，我也想跟你連，並確認收到你的」
③ 用戶端送 ACK（ack=y+1）「確認收到」

為什麼要三次：連線是雙向的，兩邊都要確認「對方收得到我」；第三次的 ACK 讓伺服器確知用戶端也收到了它的回應，同時完成雙方初始序號的同步。
20TCP
下列何者不是 TCP 的特性？
  • (A) 連線導向　(B) 保證資料順序　(C) 提供擁塞控制　(D) 標頭固定為 8 bytes
看詳解
答案：(D)
8 bytes 是 UDP 的標頭大小（來源埠、目的埠、長度、檢查碼，各 2 bytes）。
TCP 標頭至少 20 bytes（含選項可到 60 bytes），因為要放序號、確認號、視窗大小、旗標等。

這就是 UDP 快的原因之一：標頭小、無狀態、不需交握。
21TCP
TCP 的「流量控制」與「擁塞控制」，下列敘述何者正確？
  • (A) 兩者相同，都是防止網路壅塞
  • (B) 流量控制針對接收端處理能力，擁塞控制針對網路整體狀況
  • (C) 流量控制使用慢啟動，擁塞控制使用滑動視窗
  • (D) UDP 也具備這兩種機制
看詳解
答案：(B)

‧ 流量控制：解決「接收端來不及處理」→ 機制是滑動視窗（接收端以 rwnd 告知還能收多少）
‧ 擁塞控制：解決「網路壅塞」→ 機制是慢啟動、擁塞避免、快速重送、快速回復（cwnd）

(C) 剛好把兩者的機制對調了，是常見陷阱。
(D) 錯：UDP 兩者皆無，這也是它快但不可靠的原因。

白話：流量控制是「你講太快我聽不完」；擁塞控制是「馬路太塞大家慢一點」。
22TCP
TCP 擁塞控制中，當發生「逾時（Timeout）」時，擁塞視窗（cwnd）會如何變化？
  • (A) 維持不變　(B) 減半　(C) 設為 1，重新進入慢啟動　(D) 加倍
看詳解
答案：(C) cwnd 設為 1，重新慢啟動

兩種丟包情況的處理不同，這是關鍵考點：

‧ 收到 3 個重複 ACK（快速重送）→ 代表網路仍能傳遞封包，只是掉了一個 → 屬輕微壅塞 → ssthresh 減半、cwnd 設為新門檻，進入快速回復
‧ 逾時（Timeout）→ 代表連 ACK 都回不來 → 屬嚴重壅塞 → ssthresh 減半、cwnd 歸 1，從頭慢啟動

設計邏輯：情況越嚴重，退讓越多。
23埠號
下列協定與預設埠號的對應，何者錯誤？
  • (A) HTTPS — 443　(B) SSH — 22　(C) DNS — 53　(D) RDP — 3306
看詳解
答案：(D)
RDP（遠端桌面）是 3389；3306 是 MySQL。

資安提醒：這兩個埠都是絕對不該直接暴露在網際網路的高風險埠：
‧ 3389（RDP）是勒索軟體最常見的入侵管道之一（暴力破解帳密）
‧ 3306（MySQL）等資料庫埠對外開放等同把資料庫送人

遠端管理應改走 VPN ＋ MFA 或跳板機。
24DNS
DNS 中，將網域名稱指向另一個網域名稱的記錄類型為？
  • (A) A　(B) AAAA　(C) CNAME　(D) MX
看詳解
答案：(C) CNAME（別名記錄）

‧ A：名稱 → IPv4
‧ AAAA：名稱 → IPv6（四個 A，因為位址是 IPv4 的四倍長）
‧ CNAME：名稱 → 另一個名稱
‧ MX：郵件伺服器
‧ PTR：IP → 名稱（反向查詢）
‧ TXT：文字記錄（SPF、DKIM、網域所有權驗證）
25DNS
下列何種技術可用於驗證 DNS 回應的真實性，防止快取毒化攻擊？
  • (A) DNSSEC　(B) DHCP Snooping　(C) NAT　(D) VLAN
看詳解
答案：(A) DNSSEC
DNSSEC 以數位簽章為 DNS 記錄簽名，解析器可驗證回應確實來自權威伺服器且未被竄改。

注意：DNSSEC 提供的是完整性與來源鑑別，不提供機密性（查詢內容仍是明文）。要加密查詢內容需用 DoH（DNS over HTTPS）或 DoT（DNS over TLS）。這個區辨是加分考點。
26HTTP
HTTP 狀態碼 403 代表？
  • (A) 找不到資源　(B) 未經身分驗證　(C) 已驗證但無權限存取　(D) 伺服器內部錯誤
看詳解
答案：(C) Forbidden（禁止存取）

401 vs 403 的區別（常考）：
‧ 401 Unauthorized：還沒證明你是誰（未驗證）→ 請先登入
‧ 403 Forbidden：知道你是誰，但你沒資格（已驗證但無授權）

其他常見：404 找不到、429 請求過多、500 伺服器內部錯誤、502 閘道錯誤、503 服務不可用。

27診斷
traceroute（或 tracert）的運作原理為？
  • (A) 送出大量 ping 封包統計延遲
  • (B) 逐次遞增封包的 TTL 值，利用 TTL 歸零時路由器回送的 ICMP 逾時訊息
  • (C) 查詢 DNS 反向記錄
  • (D) 讀取路由器的繞送表
看詳解
答案：(B)
送出 TTL=1 的封包 → 第一台路由器把 TTL 減為 0 → 丟棄並回送 ICMP Time Exceeded → 因而得知第一台路由器的位址。
再送 TTL=2 → 得知第二台……以此類推，直到抵達目的地。

這是「把協定機制拿來當診斷工具」的漂亮設計，也是 TTL 欄位的經典應用。

補充：部分路由器設定為不回應 ICMP，此時 traceroute 會顯示 * * *，不代表網路不通。

D. 密碼學與身分驗證（第 28～36 題）

28密碼學
A 要傳送機密文件給 B，確保只有 B 能閱讀，A 應使用何者加密？
  • (A) A 的公鑰　(B) A 的私鑰　(C) B 的公鑰　(D) B 的私鑰
看詳解
答案：(C) B 的公鑰
因為只有 B 的私鑰能解開用 B 的公鑰加密的內容，而私鑰只有 B 持有。

口訣：
‧ 要保密 → 用「對方的公鑰」加密（機密性）
‧ 要簽名 → 用「自己的私鑰」簽章（鑑別性、不可否認性）

若同時需要保密與簽章：先用自己的私鑰簽章，再用對方的公鑰加密整包。
29密碼學
下列何者只有數位簽章能提供，而 HMAC 無法提供？
  • (A) 完整性　(B) 來源鑑別　(C) 不可否認性　(D) 機密性
看詳解
答案：(C) 不可否認性（Non-repudiation）

原因：HMAC 使用雙方共享的祕密金鑰，所以 A 能產生的訊息 B 也能產生 → 事後 A 可主張「那是 B 自己偽造的」，無法歸責。
數位簽章用的是只有簽署者持有的私鑰，因此無法抵賴。

(D) 兩者都不提供機密性——雜湊與簽章都不會把原文藏起來。

三層遞進要記牢：雜湊（完整性）→ HMAC（＋來源鑑別）→ 數位簽章（＋不可否認性）。
30密碼學
關於對稱式與非對稱式加密，下列敘述何者錯誤？
  • (A) 對稱式加解密速度較快，適合大量資料
  • (B) n 個人採對稱式互相通訊需 n(n−1)/2 把金鑰
  • (C) 非對稱式解決了金鑰配送問題
  • (D) HTTPS 全程只使用非對稱式加密以確保安全
看詳解
答案：(D)
HTTPS 採混合加密：
‧ 交握階段用非對稱式（驗證伺服器身分、安全協商出對稱金鑰）
‧ 資料傳輸階段用對稱式（如 AES-GCM），因為非對稱式慢 100～1000 倍，全程使用會慢到無法使用

設計精神：用慢但能解決信任問題的非對稱式處理「金鑰交換」，用快的對稱式處理「大量資料」。這是密碼學工程的經典組合。
31密碼學
下列雜湊演算法中，何者目前仍被視為安全？
  • (A) MD5　(B) SHA-1　(C) SHA-256　(D) CRC32
看詳解
答案：(C) SHA-256

‧ MD5：已可實際製造碰撞，不可用於安全用途
‧ SHA-1：已被證實可碰撞（SHAttered 攻擊），應停用
‧ CRC32：是錯誤偵測碼，不是密碼學雜湊，完全無抗碰撞性（設計目的只是偵測傳輸錯誤）
‧ SHA-256／SHA-3：現行標準

易錯點：CRC 與 checksum 是「防意外錯誤」，密碼學雜湊是「防惡意竄改」，兩者目的完全不同。
32密碼學
AES 加密採用 ECB 模式的主要問題為？
  • (A) 加密速度太慢　(B) 相同明文區塊產生相同密文，會洩漏資料樣式　(C) 無法解密　(D) 金鑰長度不足
看詳解
答案：(B)
ECB 各區塊獨立加密，相同明文 → 相同密文。加密一張圖片後，圖案輪廓仍清晰可辨。

核心啟示：用了強演算法不等於安全，作業模式與實作細節才是關鍵。

建議模式：GCM（同時提供機密性與完整性，屬 AEAD）為現行首選；CBC 需正確使用隨機 IV；CTR 可平行處理。
33PKI
數位憑證中，用來確保憑證本身未被竄改的是？
  • (A) 憑證持有人的公鑰　(B) 簽發 CA 的數位簽章　(C) 憑證序號　(D) 有效期間
看詳解
答案：(B) CA 的數位簽章
CA 用自己的私鑰對整份憑證內容簽章，驗證者以 CA 的公鑰驗證 → 只要內容被改動一個位元，驗證就會失敗。

信任鏈的起點：作業系統／瀏覽器預先內建的根憑證清單。
這也解釋了為什麼「安裝來路不明的根憑證」極度危險——等於授權對方可偽造任何網站的身分，中間人攻擊將完全無法察覺。
34PKI
下列何者可提供即時查詢憑證是否已被撤銷？
  • (A) CRL　(B) OCSP　(C) RA　(D) CSR
看詳解
答案：(B) OCSP（線上憑證狀態協定）

‧ CRL：撤銷清單，定期發布（如每天一次）→ 有時效落差，且清單可能很大
‧ OCSP：向 CA 即時查詢單一憑證狀態 → 較即時，但每次連線都要查詢（可能有隱私與效能問題，故有 OCSP Stapling 改良）
‧ RA：註冊機構，負責核驗申請人身分
‧ CSR：憑證簽署請求（申請憑證時產生的檔案）
35驗證
下列何者屬於真正的「多因子驗證（MFA）」？
  • (A) 密碼 ＋ 安全提示問題　(B) 密碼 ＋ 手機簡訊 OTP　(C) 密碼 ＋ PIN 碼　(D) 指紋 ＋ 臉部辨識
看詳解
答案：(B) 密碼（你知道的）＋ 手機 OTP（你擁有的）

MFA 必須是不同類別的因子：
‧ (A) 密碼與安全提問都是「你知道的」 ✘
‧ (C) 密碼與 PIN 都是「你知道的」 ✘
‧ (D) 指紋與臉部都是「你本身的」 ✘

三大類別：你知道的（Know）／你擁有的（Have）／你本身的（Are）。

補充：簡訊 OTP 雖合格，但有 SIM 卡挾持風險，安全性低於 FIDO2／實體金鑰或驗證器 App。
36存取控制
機關資訊系統依「職稱」授予權限，人員異動時只需變更其職稱指派即可。這屬於何種存取控制模型？
  • (A) DAC　(B) MAC　(C) RBAC　(D) ABAC
看詳解
答案：(C) RBAC（角色存取控制）
權限綁在角色而非個人，使用者被指派角色。

為什麼機關最適合 RBAC：公務機關人事異動頻繁（輪調、代理、升遷），若權限直接綁個人，異動時容易漏收回舊權限，長期累積成「權限膨脹」。RBAC 只要改角色指派，管理成本低且不易出錯。

搭配定期權限盤點（Access Review）效果更好——這是稽核常見的查核項目。

E. 攻擊、防禦與法規（第 37～45 題）

37攻擊
攻擊者大量送出 SYN 封包但不完成三向交握，導致伺服器連線資源耗盡。此為何種攻擊？
  • (A) SQL Injection　(B) SYN Flood　(C) ARP 欺騙　(D) XSS
看詳解
答案：(B) SYN Flood（屬 DoS/DDoS 的一種）
伺服器收到 SYN 後會配置資源並記入「半開連線表」等待第三次 ACK。攻擊者不回應（且常偽造來源 IP），使該表被塞滿，正常使用者無法連線。

防護：
‧ SYN Cookie：伺服器不預先配置資源，把狀態編碼在序號中，收到合法 ACK 才建立連線（最有效）
‧ 縮短半開連線逾時時間
‧ 限制單一來源的連線速率
‧ 部署流量清洗服務或 CDN
38攻擊
關於 XSS 與 CSRF 的區別，下列敘述何者正確？
  • (A) XSS 是誘使使用者的瀏覽器發出非預期請求；CSRF 是注入惡意腳本
  • (B) XSS 是注入惡意腳本在受害者瀏覽器執行；CSRF 是利用既有登入狀態發出非預期請求
  • (C) 兩者都需要攻擊者取得伺服器權限
  • (D) 兩者的防禦方式完全相同
看詳解
答案：(B)

一句話區分：XSS 是「偷你的身分」，CSRF 是「借你的手」。

XSSCSRF
本質注入並執行惡意腳本誘使瀏覽器自動帶憑證送出請求
根因輸出未編碼無法辨識請求是否為使用者本意
防禦輸出編碼、CSP、HttpOnly CookieCSRF Token、SameSite Cookie、重要操作重新驗證
注意：HttpOnly 可降低 XSS 竊取 Cookie 的危害，但對 CSRF 無效（CSRF 根本不需要讀取 Cookie，瀏覽器會自動帶上）。
39攻擊
下列何者不是防範 ARP 欺騙的有效措施？
  • (A) Dynamic ARP Inspection（DAI）　(B) DHCP Snooping　(C) 靜態 ARP 綁定　(D) 隱藏 SSID
看詳解
答案：(D) 隱藏 SSID
隱藏 SSID 是無線網路的「隱蔽」手段，與 ARP（L2 位址解析）完全無關，且本身也不是有效的安全措施（探測封包仍可發現 SSID）。

ARP 的根本弱點：ARP 協定沒有任何驗證機制，誰回答都算數。

有效防護：DHCP Snooping 建立可信的「IP-MAC-埠」對照表 → DAI 依此表檢查每個 ARP 封包 → 偽造的直接丟棄。這組合是實務主要手段。
40防禦
IDS 與 IPS 的主要差異為？
  • (A) IDS 偵測並告警，IPS 主動阻擋　(B) IDS 較 IPS 新　(C) IDS 只能用於無線網路　(D) 兩者完全相同
看詳解
答案：(A)

‧ IDS（偵測）：旁接部署，不在流量路徑上 → 不影響效能，但只能事後告警
‧ IPS（防禦）：串接部署，在流量路徑上 → 可即時阻擋，但誤判會直接中斷業務，且本身成為單點故障

實務做法：IPS 的新規則常先以「僅告警」模式觀察一段時間，確認誤報率可接受後才啟用阻擋。這個細節寫進申論很有實務感。
41防禦
防火牆規則設計時，最重要的原則為？
  • (A) 預設允許，逐條封鎖已知威脅
  • (B) 預設拒絕，僅開放必要的服務
  • (C) 只管制進入流量，出去的流量不需限制
  • (D) 規則越多越安全
看詳解
答案：(B) 預設拒絕（Default Deny）

(A) 錯：黑名單思維永遠追不上新威脅，且遺漏一項就是破口。
(C) 錯：出向流量同樣要管制——可阻斷惡意程式的 C2 連線與資料竊出，也是偵測入侵的重要訊號。
(D) 錯：規則過多會互相矛盾、難以維護，且常出現「早已無用卻忘了刪除」的過度開放規則。應定期檢視清理。
42架構
關於 DMZ（非軍事區）的設計，下列敘述何者錯誤？
  • (A) 用於放置需對外提供服務的主機，如網站、郵件伺服器
  • (B) 即使 DMZ 主機被攻陷，攻擊者仍無法直接存取內部網路
  • (C) 資料庫伺服器應放在 DMZ 以方便網站存取
  • (D) DMZ 與內部網路之間應有防火牆隔離
看詳解
答案：(C)
資料庫絕不可放在 DMZ。DMZ 是「預期可能被攻破」的區域，把最有價值的資料放在那裡等於自毀防線。

正確架構：網頁伺服器放 DMZ → 資料庫放在內部受保護網段 → 兩者之間以防火牆規則只允許特定 IP、特定埠的連線。

DMZ 的核心價值是限制橫向移動：即使對外服務被攻破，攻擊者仍被卡在中間地帶。
43雲端
依據雲端「責任共擔模式」，在 SaaS 模式下，客戶（機關）主要仍需負責什麼？
  • (A) 實體機房安全　(B) 作業系統修補　(C) 資料與使用者權限設定　(D) 虛擬化層維護
看詳解
答案：(C) 資料與使用者權限設定

核心原則：不論 IaaS、PaaS 或 SaaS，「資料」與「存取權限設定」永遠是客戶自己的責任。

實務印證：絕大多數雲端資料外洩事件不是雲端業者被駭，而是客戶自己把儲存空間設為公開（Misconfiguration）或權限給得太寬。

因應工具：CSPM（雲端安全態勢管理）持續掃描錯誤設定。
44法規
依《資通安全管理法》，公務機關的資安責任等級如何劃分？
  • (A) 分為高、中、低三級　(B) 分為 A 至 E 五級　(C) 分為 1 至 3 級　(D) 不分級，一體適用
看詳解
答案：(B) A、B、C、D、E 五級
依機關業務重要性與所保有資料之敏感程度核定，等級越高應辦事項越多（專責人力配置、防護措施、演練頻率、稽核要求等）。

注意區分：這是「機關的責任等級」（A~E 五級）；而「資安事件」另依影響程度分為 1~4 級，其中 3、4 級為重大事件，通報時限更短並須提出調查處理報告。

兩套分級容易搞混，是常見的陷阱題。
45應變
機關發現伺服器遭勒索軟體加密，下列處置何者最不適當？
  • (A) 立即將受害主機自網路隔離
  • (B) 立即重灌系統以盡快恢復服務
  • (C) 依規定向主管機關通報資安事件
  • (D) 保存記憶體與磁碟證據供後續調查
看詳解
答案：(B) 立即重灌系統

三個嚴重後果：
1. 證據全毀：記憶體中的惡意程式、攻擊者連線紀錄、加密金鑰痕跡全部消失，無法查明入侵管道
2. 無法防止再次發生：不知道怎麼進來的，重灌後可能立刻再被入侵
3. 可能仍有後門：攻擊者可能已在其他主機植入後門、竊得網域管理員帳密

正確順序：圍堵（隔離）→ 保存證據 → 通報 → 分析根因 → 根除（含重設所有可能外洩憑證）→ 由乾淨備份復原 → 事後檢討

另注意：原則上不支付贖金（付了不保證能解密、助長犯罪，且公務機關支付涉及預算與法律問題）。

📊 二、三向交握與四向斷線 
【建立連線：三向交握】
  用戶端                                    伺服器
    │──── SYN, seq=x ──────────────────────►│  「我要連線，我的序號是 x」
    │◄─── SYN+ACK, seq=y, ack=x+1 ─────────│  「好，我的序號 y，確認收到你的 x」
    │──── ACK, ack=y+1 ────────────────────►│  「確認收到你的 y」
    │◄═══════ 連線建立（ESTABLISHED）═══════►│

【中止連線：四向斷線】
  用戶端                                    伺服器
    │──── FIN ─────────────────────────────►│  「我沒資料要送了」
    │◄─── ACK ─────────────────────────────│  「知道了」（此時伺服器仍可送資料）
    │            ── 伺服器把剩餘資料送完 ──   │  ← 半關閉（Half-Close）狀態
    │◄─── FIN ─────────────────────────────│  「我也送完了」
    │──── ACK ─────────────────────────────►│  「知道了」
    │       （用戶端進入 TIME_WAIT 2MSL）     │
問題理由
為何建立需三次連線是雙向的，兩端都須確認「對方收得到我」並同步初始序號。
前兩次只確認了「用戶端→伺服器」這個方向；第三次 ACK 才讓伺服器確知用戶端也收到了它的回應。
若只有兩次，延遲抵達的舊 SYN 可能使伺服器建立無效連線並浪費資源。
為何斷線需四次TCP 為全雙工，兩個方向須各自關閉。
一方送 FIN 只表示「我沒資料要送了」，但對方可能還有資料尚未傳完。
因此 ACK 與 FIN 不能合併——先回 ACK 收下，把剩餘資料送完後再送自己的 FIN。
TIME_WAIT 的作用等待 2MSL：① 確保最後的 ACK 送達（若遺失可重送）② 讓網路中殘留的舊封包消散，避免影響新連線
⚠️ 補充：SYN Flood 攻擊 攻擊者大量送出 SYN 但不回第三次 ACK，使伺服器的半開連線佇列被塞滿而無法服務正常使用者。
防禦：SYN Cookie（不預先配置資源）、縮短逾時、增加佇列長度、部署防護設備。寫出這一段是明顯加分。
📊 三、流量控制 vs 擁塞控制
比較點流量控制（Flow Control）擁塞控制（Congestion Control）
解決的問題接收端來不及處理網路中間壅塞（路由器緩衝區滿）
對象端對端（兩端之間）對整個網路
機制滑動視窗——接收端在 ACK 中回報 rwnd（接收視窗大小），傳送端據以限速傳送端自行維護 cwnd（擁塞視窗），依據封包遺失與 RTT 動態調整
資訊來源接收端明確告知由封包遺失等現象推測（網路不會主動通知）
📐 實際傳送量 可傳送量 = min( rwnd , cwnd )　← 兩個限制取較嚴格者
擁塞控制的四個階段作法
① 慢啟動（Slow Start）cwnd 由 1 開始，每收到 ACK 就倍增（指數成長），直到門檻值 ssthresh
② 壅塞避免超過門檻後改為每個 RTT 加 1（線性成長），避免衝過頭
③ 快速重送收到 3 個重複 ACK → 不等逾時，立即重送該封包
④ 快速回復門檻減半、cwnd 減半後回到壅塞避免（而非退回 1）——TCP Reno 的改良

一句話總結：流量控制是「接收端喊停」；擁塞控制是「傳送端自己看路況踩煞車」。

📐 為何要混合？ 非對稱式解決「金鑰配送與信任」但太慢；對稱式夠快但無法安全交換金鑰。
→ 用非對稱式安全地交換一把對稱金鑰，之後全部改用對稱式。
這是「用慢的解決信任問題，用快的解決效能問題」的經典設計。
前向保密（Forward Secrecy）說明
定義即使伺服器的長期私鑰日後外洩，過去已錄下的加密通訊仍無法被解密
沒有 FS 的風險傳統 RSA 金鑰交換中，工作階段金鑰是以伺服器公鑰加密後傳送的。攻擊者若長期側錄流量，一旦取得私鑰，即可回頭解開所有歷史通訊
實作方式採 DHE／ECDHE（臨時 Diffie-Hellman）金鑰交換：
‧ 每次連線各自產生臨時金鑰對，協商出工作階段金鑰
‧ 臨時私鑰用完即丟，從不儲存也從不傳送
‧ 伺服器的長期私鑰只用來「簽章」證明身分，不用來加密金鑰
現況TLS 1.3 已移除不具前向保密的金鑰交換方式，強制使用 (EC)DHE

（跨站腳本）		其他使用者的瀏覽器其他使用者輸入被當成 HTML／JavaScript 執行，在受害者瀏覽器中執行攻擊者的腳本
CSRF
（跨站請求偽造）		使用者已登入的網站使用者的帳號權限盜用使用者已通過驗證的身分，誘使其瀏覽器發出非本意的請求

  → 未輸入密碼即可登入

  → 網站原樣存入資料庫並回顯
  → 其他使用者瀏覽該頁時，腳本在【他們的瀏覽器】執行 → Cookie 被竊

【CSRF】
  受害者已登入公文系統（瀏覽器持有有效的 Session Cookie）
  同時開啟攻擊者的網頁，其中藏有：
      
  → 瀏覽器【自動附上 Cookie】發出請求 → 伺服器誤認為本人操作

攻擊者能否看到回應可（除盲注外）可（透過腳本回傳）通常不能（僅能觸發動作）

📊 二、防範措施
攻擊根本防護輔助措施
SQL Injection參數化查詢／預備語句（Prepared Statement）——SQL 結構先編譯，參數永遠只當資料‧ ORM 或預存程序（但其內部不可再動態組字串）
‧ 輸入白名單驗證
‧ 資料庫帳號最小權限，不得用 sa／root
‧ 錯誤訊息不外洩
XSS輸出編碼（Output Encoding）——依輸出位置（HTML 內文／屬性／JS／URL）採對應的編碼方式‧ 輸入驗證與 HTML 淨化（Sanitize）
‧ CSP（內容安全政策）限制可執行的腳本來源
‧ Cookie 加 HttpOnly（使 JS 讀不到）、Secure
‧ 使用會自動跳脫的樣板引擎

‧ 驗證 Referer／Origin 標頭
‧ 敏感操作要求重新輸入密碼或二次驗證
‧ 變更狀態的操作一律用 POST，不可用 GET
三句話總結：
SQL Injection → 「參數化查詢」（別讓資料變成指令）
XSS → 「輸出編碼」（別讓資料變成畫面上的程式碼）
CSRF → 「Token 驗證」（確認請求真的是從我的網站發出的）
⚠️ 常見錯誤觀念 XSS 的防護重點在「輸出」不在「輸入」。同一份資料輸出到 HTML、屬性、JavaScript 需要不同的編碼方式；只在輸入時過濾，換個輸出位置就可能被繞過。

④ 持續評估信任不是一次性的——工作階段期間持續評估風險，異常即降權或中斷

📊 一、WEP → WPA → WPA2 → WPA3
協定年代加密完整性主要問題／改進現況
WEP1999RC4，40／104 位元金鑰CRC-32IV 僅 24 位元且明文傳送、會重複；金鑰靜態；CRC 可被竄改 → 數分鐘即可破解絕對禁用
WPA2003RC4 + TKIPMIC（Michael）過渡方案，可沿用舊硬體；每封包更換金鑰；但底層仍是 RC4，已被破解不建議使用
WPA22004AES-CCMPCCMP安全性大幅提升；但 2017 年發現 KRACK 攻擊（四向交握重放）；PSK 模式易遭離線字典攻擊可用（須更新韌體）
WPA32018AES-GCMP-256（企業版）GCMP‧ SAE 取代 PSK 交握 → 抵抗離線字典攻擊、具前向保密
‧ 強制管理框架保護（PMF）→ 防解除認證攻擊
‧ OWE：開放網路也能加密
‧ Easy Connect 簡化 IoT 設定		建議採用
📐 三個必記的 WPA3 關鍵字 SAE（Simultaneous Authentication of Equals）——即使密碼很弱，攻擊者也無法離線暴力破解，每次猜測都必須與 AP 互動。
PMF（Protected Management Frames）——管理框架也受保護，解除認證攻擊失效。
OWE（Opportunistic Wireless Encryption）——開放式網路（不需密碼）也能加密，解決了公共 Wi-Fi 全明文的老問題。

另須區分：Personal 模式（PSK／SAE，共用密碼）vs Enterprise 模式（802.1X + RADIUS，每人獨立帳號，可個別撤銷）。機關內部網路應採 Enterprise 模式。

📊 二、常見攻擊手法
攻擊手法危害
惡意熱點（Evil Twin／Rogue AP）架設與機關同名 SSID 且訊號更強的假 AP誘使連線後竊取帳密與資料，為公共場所最大威脅
解除認證攻擊（Deauth）偽造管理框架強制斷線造成阻斷服務；或迫使重連以捕捉交握封包供離線破解
離線字典／暴力破解捕捉四向交握後離線猜測 PSK弱密碼可在數小時內破出（WPA3-SAE 可防）
中間人攻擊（MITM）結合惡意熱點或 ARP 欺騙攔截與竄改流量
KRACK重放四向交握訊息，使金鑰重置可解密部分流量（更新韌體即可修補）
WPS PIN 攻擊WPS 的 8 位數 PIN 設計缺陷數小時內取得密碼 → 應停用 WPS
戰爭駕駛（War Driving）開車掃描標記無線網路建立攻擊目標清單
干擾（Jamming）發射同頻干擾訊號阻斷服務
⚠️ 兩個無效的「安全措施」 ① 隱藏 SSID——探測封包中仍會出現，用工具數秒即可發現。
② MAC 位址過濾——MAC 明文傳送且可輕易偽造。

兩者只能防止一般人誤連，不具實質安全效果，不可作為主要防護。寫出這一點是明顯的加分。

📊 一、《個人資料保護法》主要規範
面向規範重點
① 個資之定義自然人之姓名、身分證字號、聯絡方式、特徵、社會活動等得以直接或間接方式識別該個人之資料
② 特種個資病歷、醫療、基因、性生活、健康檢查、犯罪前科——原則不得蒐集處理利用，例外情形從嚴
③ 蒐集之要件公務機關須有執行法定職務必要範圍等法定事由，且與特定目的有相當關聯
④ 告知義務蒐集時應告知：機關名稱、蒐集目的、個資類別、利用之期間／地區／對象／方式、當事人權利、不提供之影響
⑤ 利用之限制原則應於蒐集之特定目的必要範圍內利用；目的外利用須符合法定例外事由
⑥ 當事人權利查詢、請求閱覽、製給複製本、補充或更正、停止蒐集處理利用、刪除——且不得預先拋棄或以特約限制
⑦ 安全維護義務公務機關應指定專人辦理安全維護事項，採行適當之技術與組織措施防止個資被竊取、竄改、毀損、滅失或洩漏
⑧ 外洩通知個資遭違反本法之情事時，應查明後以適當方式通知當事人
⑨ 責任公務機關違法致當事人受損害者負損害賠償責任；並有行政與刑事責任規定

作答提醒：條號不必強記，把「特定目的」「必要範圍」「告知義務」「安全維護措施」「通知當事人」這幾個關鍵詞寫對即可拿分。

📊 二、技術措施（主表）
類別措施說明
① 加密傳輸加密全站 TLS 1.2 以上；內部系統間傳輸亦應加密
儲存加密資料庫加密（TDE）或欄位層級加密；金鑰與資料分離保管，並建立金鑰輪替機制
② 密碼保護慢速雜湊＋隨機鹽bcrypt／Argon2；絕不可明文或可逆加密儲存；搭配 MFA
③ 去識別化最小化蒐集非必要不蒐集、不留存——這是成本最低、效果最好的一招
遮罩（Masking）畫面與報表顯示 A12****89、王○明；依角色決定可見程度
匿名化／假名化統計分析用途應移除或以代號取代識別欄位；假名化仍屬個資，匿名化才脫離個資法適用

異常偵測非上班時間查詢、短時間大量查詢、查詢非承辦案件 → 自動告警
⑥ 環境管理環境分離開發／測試／正式分離；測試環境不得使用真實個資（須以假資料或去識別化資料）
設備管控端點加密、USB 管控、DLP；設備報廢須資料徹底清除
⑦ 生命週期保存與銷毀訂定保存年限，屆期依規定銷毀；備份媒體同受管控（常被遺忘的漏洞）
📊 三、開放資料（Open Data）注意事項
風險層次問題對策
① 直接識別資料中含姓名、身分證字號、電話一律移除
② 小樣本揭露某里僅 1～2 筆低收入戶 → 鄰里間即可指認出當事人設定最小揭露門檻（如少於 N 筆即不揭露或合併分組）
③ 間接識別「出生年月日＋性別＋郵遞區號」組合起來即可能鎖定個人準識別欄位須泛化：年齡改年齡層、日期改月份、地址改至區級
④ 交叉比對重新識別與其他公開資料集比對後還原身分發布前進行重新識別風險評估；必要時採 k-匿名等技術
其他應注意事項說明
法規檢視確認無個資法、營業秘密、國家機密或其他法令限制公開之情形；符合《政府資訊公開法》
資料品質正確、完整、定期更新；標示資料時點與更新頻率——過期資料比沒有資料更糟
格式與可用性採機器可讀的開放格式（CSV、JSON、XML），避免只提供 PDF；提供資料字典說明欄位定義
授權條款明訂政府資料開放授權條款，說明可否商業利用與需否標示出處
持續管理建立下架與更正機制；設置意見回饋窗口；定期檢視是否仍適合開放
內部程序建立開放前審查機制（業務單位＋政風／法制＋資訊單位共同審查），並留存審查紀錄
✍️ 必寫拿分點 1. 個資法要寫出「特定目的」「必要範圍」「告知義務」「安全維護措施」「通知當事人」五個關鍵詞
2. 特種個資要列舉並說明原則禁止
3. 技術措施至少分五類，且要具體（不能只寫「加密」，要寫傳輸／儲存、金鑰分離保管）
4. 「非必要不蒐集」是最有效的個資保護——高分句
5. 「測試環境不得使用真實個資」與「日誌不可被查詢者自行刪改」是實務性加分
6. 開放資料務必寫「小樣本揭露」與「間接識別（準識別欄位組合）」——這兩點是本小題的核心鑑別點
7. 補上機器可讀格式、標示資料時點、開放前審查機制

📊 一、服務模式與部署模式
服務模式提供內容客戶管理範圍例子
IaaS
基礎設施即服務		虛擬機、儲存、網路作業系統以上全部虛擬主機、雲端儲存
PaaS
平台即服務		作業系統、執行環境、資料庫服務應用程式與資料應用服務平台、託管資料庫
SaaS
軟體即服務		完整應用軟體僅資料與使用者權限雲端郵件、線上文件、視訊會議
部署模式說明適用
公有雲由雲端業者提供，多租戶共用彈性大、成本低；資料主權與法遵須審慎評估
私有雲專供單一組織使用敏感業務；控制權高但成本與維運負擔大
社群雲由具共同需求之組織共享政府共構雲——多機關共用，兼顧成本與管控
混合雲公有＋私有結合，資料與應用可跨越機關最常見的務實選擇：敏感資料留內部，對外服務或尖峰運算放公有雲
📊 二、責任共擔模式
📐 核心觀念 「雲端業者負責『雲的安全』（Security OF the Cloud）；客戶負責『雲中的安全』（Security IN the Cloud）。」

最重要的一句：責任可以委外，但「責任歸屬」不能委外。
機關仍是個資的蒐集者與管理者，發生外洩時對民眾負責的仍是機關本身。
層次自建機房IaaSPaaSSaaS
資料與內容客戶客戶客戶客戶
身分與存取管理客戶客戶客戶客戶
應用程式客戶客戶客戶業者
作業系統與中介軟體客戶客戶業者業者
虛擬化層客戶業者業者業者
實體主機與網路客戶業者業者業者
機房實體安全客戶業者業者業者
⚠️ 客戶永遠要負責的三件事 無論哪種服務模式，「資料」「身分與存取權限」「組態設定」永遠是客戶的責任。

實務上絕大多數雲端資安事件都不是業者被駭，而是客戶的「組態設定錯誤」——例如儲存空間誤設為公開讀取、管理介面對外開放、未啟用 MFA 的管理帳號外洩。寫出這一點是本題最高分的關鍵。
📊 三、移轉公有雲之資安與法遵考量
面向應考量事項
法遵資料落地與主權——資料儲存位置是否在國內？是否受外國法律管轄？涉及國家機密或重要業務者應留在國內
個資法——委外處理個資須監督受託者；跨境傳輸須符合限制；契約明定個資保護義務
資通安全管理法——雲端服務納入資通安全維護計畫；系統分級後採對應防護基準；委外仍須監督受託者資安維護情形
採購法規與相關規範——應符合政府採購與雲端服務相關作業規定；優先評估已通過安全評鑑之服務
資安身分與存取——管理帳號一律 MFA；最小權限；避免使用最高權限帳號日常作業；定期輪替金鑰
組態管理——最常見的事故來源；應採組態基準檢核與自動化掃描，避免儲存空間或管理介面誤開放
資料保護——傳輸與靜態加密；金鑰管理權責釐清（是否由機關自行保管金鑰）；備份策略與離線副本
日誌與監控——啟用完整稽核日誌並另存一份於機關可控之處；異常告警
網路——虛擬網路隔離、安全群組、不對外開放管理埠；必要時以專線或 VPN 連接
營運可用性與 SLA——明定服務水準、故障賠償與通報義務；評估業者單一區域故障的影響
廠商鎖定（Vendor Lock-in）——盡量採標準化技術與開放格式；避免深度綁定專有服務
退場機制——契約應明定資料可攜、資料格式、移轉協助、終止後資料徹底刪除並提出證明
成本——雲端非必然較便宜；須估算流量費用與長期總持有成本，並建立用量監控避免超支
採購與管理契約條款——資安責任、事件通報時限、稽核權（機關得要求提供第三方稽核報告）、再委外之限制
業者評估——是否具備 ISO 27001／27017／27018 等認證；財務穩健度與服務延續性
人員能力——雲端管理需要新技能，應規劃教育訓練；機關人力有限時評估託管服務
建議結論：宜採混合雲策略——對外服務、非敏感業務與尖峰運算需求上公有雲；涉及個資、機密與核心業務之系統留在內部或政府共構雲。並宜擇一非關鍵系統先行試辦，累積經驗後再擴大。
✍️ 必寫拿分點 1. 三服務模式要寫出客戶管理範圍的差異；四部署模式要含社群雲（政府共構雲）
2. 責任共擔的定義句「業者負責雲的安全、客戶負責雲中的安全」必寫
3. 責任對照表要畫（層次 × 四種模式）——本題主要配分
4. 「資料、身分權限、組態設定永遠是客戶責任」＋「多數事故源於組態錯誤」——最高分的兩句
5. 強調「責任可以委外，責任歸屬不能委外」
6. 法遵務必寫資料落地與主權、個資法委外監督、資安法納入維護計畫
7. 結論建議混合雲＋先行試辦，並含退場機制與資料可攜

📊 一、生成式 AI 帶來的新型威脅
威脅說明對機關的具體影響
① 釣魚郵件品質大幅提升過去可靠「語句不通順」辨識，現在文法完美且能高度客製傳統的辨識教學失效；冒充上級或同仁的郵件極難分辨
② 深偽（Deepfake）可偽造語音與影像，門檻極低冒充長官來電要求緊急匯款或變更帳號（BEC 詐騙）；「聽到本人聲音」已不再是可靠的身分確認
③ 惡意程式撰寫門檻降低不具技術能力者也能產生可用的攻擊腳本攻擊者總數與攻擊頻率上升
④ 自動化攻擊可自動生成大量變體以規避特徵碼偵測；自動分析漏洞傳統特徵碼式防毒效果下降 → 須改用行為式偵測（EDR）
⑤ 假訊息與輿論操縱可大量產製看似真實的內容冒名發布不實政策訊息，損及機關公信力
⑥ 個資與機密外洩（內部風險）員工將公務資料貼入公開 AI 服務資料可能被業者留存或用於訓練 → 這是機關最真實、最常發生的風險
⑦ 社交工程精準化結合公開資訊自動產生高度個人化的話術針對特定承辦人的鎖定式攻擊增加
📊 二、AI 系統本身面臨的資安風險
風險原理後果
① 提示詞注入
（Prompt Injection）		在輸入或外部文件中夾帶指令，誘使模型忽略原有規則繞過限制、洩漏系統提示或機敏資訊；AI 讀取的網頁或文件都可能是攻擊面
② 資料投毒
（Data Poisoning）		在訓練資料中植入惡意樣本模型產生偏誤或被植入後門
③ 對抗性樣本對輸入做人眼難察的細微擾動使影像或語音辨識誤判（如門禁人臉辨識被繞過）
④ 模型竊取／萃取大量查詢後重建近似模型智慧財產損失
⑤ 訓練資料還原誘導模型輸出訓練時記憶的內容個資或機密外洩
⑥ 幻覺（Hallucination）模型會產生看似合理但錯誤的內容，且語氣同樣肯定公文或法規引用錯誤而未被察覺 → 對機關而言是最實際的風險
⑦ 供應鏈風險第三方模型、套件或外掛可能含惡意程式整體系統遭入侵
⑧ 過度依賴與可用性服務中斷或業者政策變更業務中斷；缺乏可解釋性導致決策無法說明
📊 三、機關導入之管理規範
面向應訂定之規範
① 使用範圍明定可使用與禁止使用的情形：公文初稿、翻譯、摘要可用；涉及個資、機密、尚未公開之政策不得使用
區分公開服務與機關自建／專屬環境之使用限制
指定允許使用的工具清單，避免各自使用來路不明的服務
② 資料管控（核心）嚴禁將個人資料、機密文件、系統帳密貼入公開 AI 服務——最重要的一條
必要時應先去識別化再使用
敏感業務應建置機關內部或封閉環境之 AI 服務，確保資料不外流
③ 輸出查核AI 產出一律視為「初稿」，必須經人工查核後始得使用
引用之法規、數據、案例必須逐一查證（防幻覺）
對外發布之內容依規定標示是否使用 AI 生成
④ 責任歸屬承辦人與核稿主管仍負完全責任——不得以「AI 產生的」作為卸責理由
行政決定不得完全交由 AI 作成；AI 僅為輔助，須保留人工判斷與說明理由之能力
⑤ 採購與委外契約明定資料不得用於模型訓練、資料留存與刪除、資料所在地
評估業者之資安認證、服務延續性與退場機制
⑥ 教育訓練說明 AI 的能力與限制（特別是幻覺）；深偽與新型社交工程之辨識
建立諮詢與通報窗口；定期更新規範
⑦ 配套控管關鍵作業（變更匯款帳號、人事異動）採雙人覆核與另一管道回撥確認——因應深偽
資安防護由特徵碼式轉向行為式偵測（EDR）；強化出向流量管控
結論句：機關對生成式 AI 宜採「明確規範、審慎試辦、逐步擴大」的策略——一味禁止會使同仁私下使用而更難管控；應提供合規的工具與清楚的界線，讓同仁知道「可以用什麼、不能放什麼」。
✍️ 必寫拿分點 1. 新型威脅要寫「深偽使『聽到本人聲音』不再可靠」與「員工把公務資料貼進公開 AI」——後者是機關最真實的風險
2. 指出「傳統以語句不通順辨識釣魚信的教學已失效」
3. AI 自身風險務必寫「提示詞注入」與「幻覺」；提示詞注入要說明外部文件也是攻擊面
4. 管理規範的核心是「嚴禁將個資與機密貼入公開服務」與「產出一律視為初稿，須人工查核」
5. 「承辦人仍負完全責任，不得以 AI 卸責」、「行政決定不得完全交由 AI 作成」——法制面加分句
6. 契約要寫「資料不得用於模型訓練」
7. 結論用「明確規範、審慎試辦、逐步擴大」並說明一味禁止反而更難管控——展現務實判斷

📊 一、BCP 與 DRP
比較點BCP（營運持續計畫）DRP（災害復原計畫）
全名Business Continuity PlanDisaster Recovery Plan
範圍整個機關的營運（人員、場所、流程、供應商、對外溝通）資訊系統與資料的復原
目的維持關鍵業務不中斷（可用替代方式）把系統救回來
時間軸涵蓋事發前、中、後全程著重事發後的復原
負責層級機關首長與各業務單位資訊單位為主
關係DRP 是 BCP 的一部分；BCP 涵蓋 DRP
例子系統全斷時改以紙本受理民眾申請；人員疏散與替代辦公場所由備份還原資料庫；切換至備援機房

前置作業：兩者皆應以業務衝擊分析（BIA）為基礎——先辨識關鍵業務與可容忍中斷時間，才能合理設定 RTO／RPO 並分配資源。

                        ← RPO →│← ─── RTO ─── →
   ────┬──────────┬───────────┼──────────────┬────► 時間
       │          │           │              │
   最後一次     資料仍       【故障】      服務恢復
   可用備份     持續產生      發生            正常

   RPO：可容忍的【資料遺失量】 ← 往回看，靠「備份／複寫頻率」決定
   RTO：可容忍的【停機時間】   ← 往前看，靠「備援架構」決定
指標定義白話由什麼決定
RTORecovery Time Objective——自故障發生至服務恢復可容忍之最長時間多久要修好備援架構、還原速度、演練熟練度
RPORecovery Point Objective——可容忍之最大資料遺失量（以時間表示）能掉多久的資料備份／日誌傳送頻率
📊 二、備份策略與 3-2-1 原則
類型備份內容備份時間空間還原步驟還原時間
完整備份全部資料最長最大1 份最短
差異備份自上次完整備份以來之異動中（逐日變長）中2 份（完整＋最近一次差異）中
增量備份自上次任何備份以來之異動最短最小完整＋全部增量最長（任一份損毀即斷鏈）
📐 3-2-1 原則 3 份副本（1 份正式 + 2 份備份）
2 種不同的儲存媒體（避免同一批媒體同時故障）
1 份存放於異地（因應火災、水災、機房整體毀損）

現代延伸：3-2-1-1-0
再加 1 份離線或不可變（Immutable）副本 ← 因應勒索軟體
0 個還原錯誤 ← 必須經過驗證
其他要點說明
多版本保留惡意程式可能潛伏數週，只留最近一版可能已被污染 → 須保留多個時間點（日／週／月）
備份加密備份媒體含個資，遺失即等同外洩 → 應加密並管控存取
定期還原演練「備份成功」不等於「還原成功」——須定期實際還原並計時，驗證是否符合 RTO
📊 三、本案架構建議（RTO ≤ 4 小時、RPO ≤ 30 分鐘、須防勒索）
要求推論對應作法
RPO ≤ 30 分鐘資料最多只能掉 30 分鐘 → 每日備份完全不夠交易日誌每 15～30 分鐘備份／傳送；或採非同步複寫至備援站
RTO ≤ 4 小時4 小時內須恢復服務 → 從備份完整還原大型系統可能來不及建置熱備援（Standby）系統可快速切換；預先撰寫並演練切換程序
防勒索軟體勒索軟體會主動搜尋並加密網路上的備份，取得網域管理員後甚至先刪除備份見下方專屬對策
層次建議架構
備份排程每週完整備份 ＋ 每日差異備份 ＋ 交易日誌每 30 分鐘
選差異而非增量，以縮短還原步驟數（顧 RTO）
高可用（顧 RTO）同機房叢集或同步複寫，單機故障可自動切換（分鐘級）
異地備援另一機房建置非同步複寫之待命系統，因應機房級災害
勒索軟體專屬對策① 離線備份（Air-gapped）——實體離線，勒索軟體構不到
② 不可變備份（Immutable／WORM）——保存期內連管理員也無法刪改
③ 備份系統帳號與網域分離——網域管理員遭竊也動不了備份
④ 多版本保留——因應潛伏期
⑤ 還原前先掃描，確認備份時點乾淨
⑥ 備份伺服器網段隔離，僅開放必要通訊
驗證機制每次備份後自動驗證完整性；每季實際還原演練並計時，確認符合 RTO/RPO；記錄演練結果與改善事項
制度面納入 BCP／DRP；明訂切換決策權責（誰有權宣告啟動）；對外公告替代作業方式；依《資通安全管理法》辦理演練與檢討
預防面備份是最後一道防線，前面仍須：修補管理、MFA、網段隔離、EDR、郵件防護、使用者非管理員權限
⚠️ 本題最關鍵的一句 「備份必須有離線或不可變副本，否則勒索軟體會連備份一起加密。」
這是實務上機關遭勒索後無法還原的最主要原因——備份一直掛在網路上。
✍️ 必寫拿分點 1. BCP／DRP 的核心差異：BCP 是「業務不中斷」、DRP 是「系統救回來」，DRP 屬於 BCP 的一部分
2. 舉出 BCP 的非資訊面例子（改以紙本受理）——顯示真的理解
3. RTO／RPO 最好畫時間軸圖，並寫「RPO 靠備份頻率、RTO 靠備援架構」
4. 備份比較表務必含「還原步驟數」——這才是選差異或增量的實務判準
5. 3-2-1 要展開解釋，並補3-2-1-1-0 的現代延伸
6. 第三小題必須逐一回應兩個數字，寫出「每日備份不夠 → 日誌 30 分鐘」「完整還原來不及 → 熱備援」
7. 勒索對策「離線／不可變備份」「備份帳號與網域分離」「還原前先掃描」三句必寫
8. 結尾補「備份是最後一道防線，前面的預防仍不可省」
