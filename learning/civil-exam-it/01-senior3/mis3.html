第 1 章　敏捷開發 (Agile)、DevOps 與專案排程推導

傳統的瀑布式開發在面對快速變動的需求時顯得笨重。敏捷宣言提倡「個人與互動勝過流程與工具」，而 DevOps 則將敏捷的精神延伸至系統的維運階段。

1-1　Scrum 框架的核心元素 (333)

分類元素說明
3 個角色產品負責人 (PO)決定「要做什麼 (What)」，維護 Product Backlog，最大化產品價值。
Scrum Master排除障礙的僕人式領導者，確保團隊遵循 Scrum 規則，但不干涉技術實作。
開發團隊跨職能、自我組織，決定「怎麼做 (How)」與「能做多少」。
3 個產出物產品待辦清單 (Product Backlog)PO 管理的所有需求清單，依商業價值排序。
衝刺待辦清單 (Sprint Backlog)團隊承諾在這個 Sprint 內要完成的工作項目。
潛在可交付產品增量每個 Sprint 結束時，必須產出一個經過測試、隨時可上線的軟體版本。
5 個事件Sprint 規劃會議團隊承諾本期要做的項目，估算故事點 (Story Points)。
每日立會 (Daily Scrum)每天 15 分鐘，報告「昨天做什麼、今天做什麼、遇到什麼障礙」。
Sprint 審查會議向利害關係人展示成果 Demo，蒐集回饋。
Sprint 回顧會議團隊內部自省「哪些做得好、哪些要改善 (KPT)」。
Sprint 本身通常為 2~4 週的固定時間箱 (Timebox)。
🎯 步驟化詳解：Scrum 衝刺速度 (Velocity) 與燃盡圖 (Burn-down Chart) 推導五部曲

【專案情境】某政府機關推動新版便民服務系統，整體 Product Backlog 初估總計 180 點故事點 (Story Points)。團隊採用 2 週為一個 Sprint，前三個 Sprint 團隊交付驗收之點數分別為：Sprint 1：26 點、Sprint 2：34 點、Sprint 3：30 點。

  • 步驟 1計算團隊歷史平均衝刺速度 (Average Velocity)
    $$\text{Average Velocity } (V) = \frac{26 + 34 + 30}{3} = \frac{90}{3} = \mathbf{30\text{ 點/Sprint}}$$
  • 步驟 2計算剩餘工作量與預估完工所需 Sprint 數
    ‧ 前三個 Sprint 累積完成：$26 + 34 + 30 = 90$ 點。
    ‧ 剩餘待辦點數：$180 - 90 = 90$ 點。
    ‧ 預估仍需 Sprint 數：$\frac{90\text{ 點}}{30\text{ 點/Sprint}} = \mathbf{3\text{ 個 Sprint}}$。
    ‧ 總專案預計需 $3 + 3 = 6$ 個 Sprint（共 12 週）完工。
  • 步驟 3建構衝刺燃盡圖 (Sprint Burn-down Chart) 追蹤每日進度
    在單一 Sprint (以 Sprint 4 承諾 30 點、10 個工作天為例)：
    ‧ 理想燃盡線 (Ideal Line)：從第 0 天的 30 點以每日 $-3$ 點之斜率線性下降至第 10 天的 0 點。
    ‧ 實際燃盡線 (Actual Line)：若實際折線位於理想線上方，代表專案進度落後；若位於理想線下方，代表專案進度超前。
  • 驗算範圍蔓延 (Scope Creep) 之調控策略
    若 PO 於 Sprint 3 額外追加了 20 點新需求，未完成總量增為 $90 + 20 = 110$ 點。在速度維持 30 點/Sprint 下，完工期自動延長為 $\lceil 110 / 30 \rceil = 4$ 個 Sprint，透明化呈現範圍與工期的權衡，杜絕傳統瀑布式無止盡加班。
🎯 步驟化詳解：專案要徑法 (CPM) 與總浮時 (Total Float) 逐步推導六部曲

【作業網絡】某軟體專案包含 5 項活動，作業相依性與工期如下：A (工期 4天，無先導)、B (工期 6天，先導 A)、C (工期 3天，先導 A)、D (工期 5天，先導 B)、E (工期 8天，先導 C)。

  • 步驟 1前推法 (Forward Pass) 計算最早開始 (ES) 與最早完成 (EF)
    ‧ $EF = ES + \text{Duration}$；多個先導活動時，$ES = \max(\text{先導之 } EF)$。
    ‧ 活動 A：$ES_A = 0,\; EF_A = 0 + 4 = \mathbf{4}$。
    ‧ 活動 B：$ES_B = 4,\; EF_B = 4 + 6 = \mathbf{10}$。
    ‧ 活動 C：$ES_C = 4,\; EF_C = 4 + 3 = \mathbf{7}$。
    ‧ 活動 D：$ES_D = 10,\; EF_D = 10 + 5 = \mathbf{15}$。
    ‧ 活動 E：$ES_E = 7,\; EF_E = 7 + 8 = \mathbf{15}$。
    👉 專案總工期 = $\max(EF_D, EF_E) = \mathbf{15\text{ 天}}$。
  • 步驟 2逆推法 (Backward Pass) 計算最晚完成 (LF) 與最晚開始 (LS)
    ‧ 終點活動：令 $LF_D = LF_E = 15$。
    ‧ $LS = LF - \text{Duration}$；多個後續活動時，$LF = \min(\text{後續之 } LS)$。
    ‧ 活動 D：$LF_D = 15,\; LS_D = 15 - 5 = \mathbf{10}$。
    ‧ 活動 E：$LF_E = 15,\; LS_E = 15 - 8 = \mathbf{7}$。
    ‧ 活動 B：$LF_B = LS_D = 10,\; LS_B = 10 - 6 = \mathbf{4}$。
    ‧ 活動 C：$LF_C = LS_E = 7,\; LS_C = 7 - 3 = \mathbf{4}$。
    ‧ 活動 A：$LF_A = \min(LS_B, LS_C) = \min(4, 4) = 4,\; LS_A = 4 - 4 = \mathbf{0}$。
  • 步驟 3計算總浮時 (Total Float = LS − ES = LF − EF)
    ‧ $TF_A = 0 - 0 = \mathbf{0}$；$TF_B = 4 - 4 = \mathbf{0}$；$TF_D = 10 - 10 = \mathbf{0}$。
    ‧ $TF_C = 4 - 4 = \mathbf{0}$；$TF_E = 7 - 7 = \mathbf{0}$。
    👉 要徑 (Critical Path) 為總浮時為 0 之路徑：本專案同時存在兩條要徑：A → B → D 與 A → C → E！
  • 驗算浮時意義總結
    總浮時為 0 的活動無任何緩衝時間，任何一天的延遲都將直接導致專案整體交付日延期。管理要徑活動是專案經理 (PMP) 的首要核心職責！
⚡ 考前 30 秒秒殺口訣卡：敏捷 333 與要徑法公式秒殺
【敏捷 333】角色 PO、SM 與團隊，清單產品衝刺與增量，立會規劃審查與回顧
【CPM 算式】前推取大算最早，逆推取小算最遲；浮時為零成要徑，工期掌控分秒清
  • 自由浮時 (Free Float)：在不影響任何後續活動最早開始 (ES) 前提下，該活動可延遲的時間（$\min(ES_{\text{next}}) - EF$）。
  • 總浮時 (Total Float)：在不影響專案總完工日 (Project Finish) 前提下，該活動可延遲的時間（$LS - ES$）。

第 2 章　企業架構 (Enterprise Architecture) 與 TOGAF

2-1　TOGAF 的四大架構領域 (BDAT)

架構領域探討問題內容範例
業務架構 (Business Architecture)「組織做什麼？流程為何？」組織圖、業務流程圖 (BPMN)、業務目標與策略。
資料架構 (Data Architecture)「組織擁有哪些資訊資產？」概念資料模型 (ERD)、資料字典、資料擁有權定義。
應用架構 (Application Architecture)「需要哪些系統來支援業務？」應用系統清單、系統間的介接關係與 API 定義。
技術架構 (Technology Architecture)「系統需要什麼軟硬體基礎建設？」伺服器、網路架構、雲端平台、中介軟體、資安設備。

2-2　架構開發方法論 (ADM)

TOGAF 的核心是 ADM (Architecture Development Method)，這是一個迭代的循環流程。它強調從現行架構 (As-Is) 出發，定義目標架構 (To-Be)，然後找出兩者之間的差距 (Gap Analysis)，最後規劃出實作的過渡計畫。

🎯 步驟化詳解：TOGAF ADM 架構開發循環八階段推導步驟
  • 預備階段確定架構原則與範疇 (Preliminary Phase)
    確認組織治理框架、自訂 TOGAF 工具與方法論，並獲得高層主管的架構承諾。
  • 階段 A架構願景 (Architecture Vision)
    界定利害關係人、定義專案範圍與商業價值目標，產出《架構工作陳述書 (Statement of Architecture Work)》。
  • 階段 BCD核心架構設計 (BDAT 交付物推導)
    ‧ 階段 B（業務架構）：梳理業務流程現狀與目標，執行差距分析。
    ‧ 階段 C（資訊系統架構）：涵蓋資料架構（概念 ERD/主檔治理）與應用架構（服務邊界與 API 拓撲）。
    ‧ 階段 D（技術架構）：設計底層運算、儲存、網路、虛擬化與雲端基礎設施。
  • 階段 EFG實施與過渡計畫 (Opportunities to Governance)
    ‧ 階段 E（機會與解決方案）：評估打包各過渡架構 (Transition Architectures)。
    ‧ 階段 F（遷移規劃）：排定優先順序、依成本效益建立詳細路線圖。
    ‧ 階段 G（實施治理）：確保專案建置完全符合架構契約 (Architecture Contract)。
  • 階段 H架構變更管理 (Architecture Change Management)
    持續監控新興技術、業務模式變更與法規要求，啟動新一輪 ADM 迭代循環。

第 3 章　資料治理 (Data Governance) 與 IT 投資評估

在 AI 與大數據時代，「資料是新的石油」。但未經提煉與管理的石油只是污染，資料治理就是組織內的煉油廠管理制度。

3-1　資料治理的核心要素

要素說明
資料擁有者 (Data Owner)對特定資料集負責的高階業務主管。決定誰可以存取、資料的分類分級。
資料管家 (Data Steward)負責日常維護資料品質與詮釋資料 (Metadata) 的業務人員。
資料字典與 Metadata描述資料的資料。確保跨部門對同一個名詞（如「營業額」）有完全一致的定義與計算公式。
資料品質管理 (Data Quality)確保資料的準確性、完整性、一致性、及時性與有效性。建立資料清洗與異常監控機制。
資料血緣 (Data Lineage)追蹤資料的生命週期。從資料來源、經過哪些 ETL 轉換，到最終呈現在哪個報表上。發生錯誤時能快速追溯根因。
🎯 步驟化詳解：IT 投資專案淨現值 (NPV) 與投資報酬率 (ROI) 折現現金流計算四部曲

【決策案例】某公營行庫規劃汰換舊核心系統，初期建置成本（$C_0$）為 1,000 萬元。預期未來三年每年因節省人工作業與減少出錯所帶來之淨現金流入分別為：第 1 年 440 萬元、第 2 年 484 萬元、第 3 年 532.4 萬元。若組織設定之資金折現率（$r$）為 10%，請計算其淨現值 (NPV) 並做成採購建議。

  • 步驟 1列出淨現值 (NPV) 通用公式
    $$\text{NPV} = \sum_{t=1}^{n} \frac{CF_t}{(1 + r)^t} - C_0$$
  • 步驟 2計算各年度淨現金流之現值 (Present Value, PV)
    ‧ 第 1 年現值：$PV_1 = \frac{440}{1 + 0.10} = \frac{440}{1.1} = \mathbf{400\text{ 萬元}}$。
    ‧ 第 2 年現值：$PV_2 = \frac{484}{(1.1)^2} = \frac{484}{1.21} = \mathbf{400\text{ 萬元}}$。
    ‧ 第 3 年現值：$PV_3 = \frac{532.4}{(1.1)^3} = \frac{532.4}{1.331} = \mathbf{400\text{ 萬元}}$。
  • 步驟 3加總折現現金流並扣除初期投資計算 NPV
    $$\text{總未來現金流現值} = 400 + 400 + 400 = 1,200\text{ 萬元}$$ $$\text{NPV} = 1,200\text{ 萬元} - 1,000\text{ 萬元} = \mathbf{+200\text{ 萬元}}$$
  • 驗算投資決策準則判定
    ‧ NPV 準則：$\text{NPV} = +200\text{ 萬元} > 0$，代表本投資專案能為組織帶來超越 10% 資金成本之超額淨效益，決策：應予核准投資！
    ‧ 未折現回本期 (Payback Period)：第 1 年 (440) + 第 2 年 (484) = 924 萬；剩餘 76 萬於第 3 年約 0.14 年回收，約 2.14 年回本。
⚡ 考前 30 秒秒殺口訣卡：IT 投資效益四大評估指標
【口訣】NPV 大於零可行，IRR 高於折現金；回本愈快風險小，ROI 利潤比成本
  • NPV (淨現值)：首選指標，考量貨幣時間價值，NPV > 0 即具經濟效益。
  • IRR (內部報酬率)：使 NPV 剛好等於 0 之折現率，IRR > 資金成本即值得投資。
  • TCO (整體擁有成本)：包含採購、導入、維運、教育訓練至報廢的全生命週期總成本。

第 4 章　IT 委外進階與軟體供應鏈安全 (SBOM)

現代政府機關極度依賴委外，如何管理廠商與第三方軟體套件的風險，是高階資訊人員的必修課。

4-1　軟體供應鏈安全與 SBOM

駭客發現與其直接攻擊防禦嚴密的機關，不如攻擊機關的軟體供應商，或在常見的開源套件中植入後門（如 Log4j 事件）。

🎯 步驟化詳解：軟體物料清單 (SBOM) 生成、弱點關聯與修補驗收標準作業流程
  • 步驟 1CI/CD 構建階段自動化產出標準 SBOM
    委外廠商在編譯交付軟體時，透過自動化工具（如 Syft、Trivy）產出符合國際標準格式（CycloneDX 或 SPDX）之機器可讀清單，詳列所有開源相依套件、版本號及雜湊簽章（Hash SHA-256）。
  • 步驟 2與國家弱點資料庫 (NVD / CVE) 自動化關聯
    機關資安監控平台載入該 SBOM，自動與 MITRE CVE 及美國 NVD 進行即時弱點串接比對。
  • 步驟 3CVSS 漏洞嚴重度分級與履約驗收
    ‧ 若發現 CVSS 評分 $\ge 7.0$ 之高危弱點（High / Critical）：系統自動阻擋發布，列為驗收不通過項目。
    ‧ 要求廠商在契約明訂之 SLA 期限內（如重大弱點 48 小時內）交付修補版本（Patch）與重簽之 SBOM。
  • 驗算防範次日零時差威脅 (Day-0 Tracking)
    當未來的某一天（如一年後）國際突然爆發某底層套件（如 Apache Commons）新弱點時，機關無需逐一發函詢問廠商，直接在內部 SBOM 資料庫執行一鍵檢索，數秒內即可精確定位受影響之主機清單！

4-2　供應商鎖定 (Vendor Lock-in) 的防範策略

鎖定類型防範策略 (機關應採取的對策)
資料鎖定契約明訂機關擁有資料所有權，且廠商必須提供開放格式 (如 CSV, JSON, XML) 的資料匯出功能。
原始碼與架構鎖定契約明定機關擁有原始碼或至少有修改權。要求廠商採用開放標準與主流框架，避免使用廠商獨家專有的開發工具。
基礎設施鎖定 (雲端)採用容器化技術 (Docker, Kubernetes)，使應用程式可以在 AWS, Azure 甚至地端機房之間平滑轉移 (Multi-Cloud 策略)。

第 5 章　ESG、綠色 IT 與新興資料治理 (Data Mesh)

現代資訊主管 (CIO) 不只要懂技術，還要懂如何讓 IT 幫助企業達成永續經營與法規遵循，這是近年國考申論題的新寵兒。

5-1　綠色 IT 與 ESG

  • 綠色資料中心 (Green Data Center)：透過冷熱通道隔離、虛擬化技術降低實體伺服器數量，來降低 PUE (能源使用效率 = 總用電量 / IT 設備用電量)。PUE 越接近 1 越好（標準機房約 1.5~2.0，頂級綠色機房可達 1.15）。
  • 無紙化與數位轉型：導入電子簽核系統、雲端協作，減少碳足跡。
  • IT 資產處置 (ITAD)：報廢電腦前必須澈底銷毀硬碟資料（Governance），並妥善回收電子廢棄物（Environmental）。

5-2　資料網格 (Data Mesh) 的四大核心原則

四大原則說明帶來的變革
領域導向去中心化所有權將資料擁有權與管理責任交還給最懂業務的各業務部門 (Domain)。打破中央資料團隊的單點溝通瓶頸。
資料即產品 (Data as a Product)各領域團隊必須像打造商業產品一樣維護資料，提供 SLA 與乾淨 API。資料使用者有明確的服務水準保證。
自助式資料基礎設施平台中央 IT 轉型為平台工程團隊，提供一鍵開通儲存、運算與管道的工具。降低各業務部門建置資料流水線的門檻。
聯邦式計算治理 (Federated Governance)由各領域代表共同制定統一的資料標準、合規與隱私政策，並由程式碼自動化落實。兼顧去中心化的敏捷與全組織的資安合規。
