深化 1　函數相依：Armstrong 公理與屬性閉包

1-1　Armstrong 公理系統（三條基本 + 三條推論）

類別規則敘述
基本公理反身律（Reflexivity）若 Y ⊆ X，則 X → Y
增廣律（Augmentation）若 X → Y，則 XZ → YZ
遞移律（Transitivity）若 X → Y 且 Y → Z，則 X → Z
推論規則合併律（Union）若 X → Y 且 X → Z，則 X → YZ
分解律（Decomposition）若 X → YZ，則 X → Y 且 X → Z
擬遞移律（Pseudotransitivity）若 X → Y 且 WY → Z，則 WX → Z
⚠️ 最常考錯的一點：左邊可以合併，右邊可以分解，反之不然
✔ 由 A → B 和 A → C，可推出 A → BC（合併律）
✔ 由 A → BC，可推出 A → B（分解律）
✘ 由 AB → C，不能推出 A → C 或 B → C

記法：「右分解可以，左分解不行」——因為 AB → C 表示「要 A 和 B 兩者一起」才能決定 C。

1-2　屬性閉包 X⁺：所有計算題的基礎

定義：X⁺ = 由 X 依函數相依集合 F 能推出的所有屬性。

演算法：
① 令 X⁺ = X
② 反覆掃描 F：若某個 Y → Z 滿足 Y ⊆ X⁺，則把 Z 加入 X⁺
③ 直到 X⁺ 不再改變為止
例題：R(A,B,C,D,E)，F = { A→BC, CD→E, B→D, E→A }。求 A⁺。

A⁺ = {A}
A→BC 成立（A ⊆ A⁺）→ A⁺ = {A,B,C}
B→D 成立（B ⊆ A⁺）→ A⁺ = {A,B,C,D}
CD→E 成立（C,D ⊆ A⁺）→ A⁺ = {A,B,C,D,E}
E→A 成立但 A 已在

A⁺ = {A,B,C,D,E} = R 的全部屬性 → A 是超鍵
💡 屬性閉包一次解決三種考題
① X 是不是超鍵？ → 看 X⁺ 是否等於全部屬性
② X → Y 是否成立？ → 看 Y 是否 ⊆ X⁺
③ 求候選鍵 → 見深化 2
✅ 深化 1 必背結論 ① Armstrong 三基本公理：反身、增廣、遞移；三推論：合併、分解、擬遞移。
② 右邊可分解，左邊不可分解（AB→C 推不出 A→C）。
③ 屬性閉包 X⁺ 是所有正規化計算題的共同工具。

深化 2　候選鍵求法與最小覆蓋

2-1　候選鍵的系統性求法（考場可用的機械流程）

步驟一：把屬性分成四類
類別判別結論
L 類只出現在相依式左邊必屬於每個候選鍵
R 類只出現在右邊必不屬於任何候選鍵
LR 類左右都出現可能屬於，須測試
N 類都沒出現必屬於每個候選鍵
步驟二：令 K = L 類 ∪ N 類，計算 K⁺。若 K⁺ = R 的全部屬性 → K 是唯一候選鍵。
步驟三：否則，逐一把 LR 類的屬性加入 K 測試，找出所有最小的超鍵。
例題：R(A,B,C,D)，F = { A→B, B→C, C→D }。求候選鍵。

左邊出現：A, B, C　右邊出現：B, C, D
L 類（只在左）= {A}　R 類（只在右）= {D}　LR 類 = {B,C}　N 類 = {}

K = {A}，A⁺ = {A,B,C,D} = 全部屬性
→ 候選鍵唯一，為 A
例題二（有多個候選鍵）：R(A,B,C)，F = { AB→C, C→A }。

左邊：A,B,C　右邊：C,A
L 類 = {B}（B 只在左邊）
B⁺ = {B} ≠ 全部 → 須加入 LR 類測試

{B,A}⁺ = {A,B,C} ✔ → AB 是候選鍵
{B,C}⁺ = {B,C,A} ✔ → BC 是候選鍵

候選鍵為 {AB, BC}——注意 B 出現在兩者中（因為它是 L 類）。

2-2　最小覆蓋（正則覆蓋）三步驟

① 右邊單一化：把 X → YZ 拆成 X → Y、X → Z
② 去除左邊多餘屬性：對 XA → B，若 X⁺ 已含 B，則 A 多餘
③ 去除多餘的相依式：移除某式後，若仍能推出它，則該式多餘
⚠️ 步驟順序不可調換
必須先做右邊單一化，再處理左邊，最後才刪整條——順序錯會得到不同（甚至錯誤）的結果。
而且最小覆蓋可能不唯一（視刪除順序而定），但每個都是合法答案。
💡 最小覆蓋的用途：3NF 分解演算法的輸入
3NF 合成法：對最小覆蓋中的每一條 X → Y，建一個關聯 R(X ∪ Y)；若沒有任何關聯包含候選鍵，再加一個由候選鍵組成的關聯。
這個分解保證：無損 ＋ 保持相依 ＋ 達到 3NF。
✅ 深化 2 必背結論 ① 只在左邊出現的屬性（L 類）與都沒出現的（N 類）必在每個候選鍵中。
② 求候選鍵：K = L∪N，算 K⁺；不足則逐步加入 LR 類測試。
③ 最小覆蓋三步驟：右邊單一化 → 去左邊多餘屬性 → 去多餘相依式，順序不可換。

深化 3　分解的兩個判定：無損 與 保持相依

3-1　無損分解（lossless join）的判定

二元分解的簡易判準（考試最常用）：
把 R 分解為 R₁ 與 R₂ 是無損的，若且唯若下列至少一個成立：

(R₁ ∩ R₂) → (R₁ − R₂)　或　(R₁ ∩ R₂) → (R₂ − R₁)

白話：兩個表的「共同欄位」必須是其中一邊的鍵。
例題：R(學號, 課號, 教師)，F = { 學號課號→教師, 教師→課號 }
分解為 R₁(學號, 課號) 與 R₂(教師, 課號)，是否無損？

R₁ ∩ R₂ = {課號}
R₁ − R₂ = {學號}，R₂ − R₁ = {教師}

課號 → 學號？不成立
課號 → 教師？不成立（一門課可能多位教師）

→ 此分解有損（做 JOIN 會產生原本不存在的假資料列）
⚠️ 「有損」的真正意義：不是資料變少，而是「多出假資料」
分解後再 JOIN 回去，會得到比原表更多的列——那些多出來的列是「虛假的組合」。
在公務系統中，這代表：把兩張表接起來查詢時，會查出「不存在的申請人與案件的配對」——而承辦人可能據此作成處分。

3-2　保持相依（dependency preservation）的判定

令分解後各關聯上的相依集合為 F₁, F₂, …，若 (F₁ ∪ F₂ ∪ …)⁺ = F⁺，則保持相依。

白話：原本的每一條規則，都還能「在單一張表上」檢查得出來。
💡 為什麼「保持相依」在實務上這麼重要
若某條業務規則必須把兩張表 JOIN 起來才能驗證——
① 資料庫的約束無法直接表達它
② 每次寫入都要做 JOIN 檢查，成本高
③ 併發時難以保證

結果：這條規則實際上就沒有被強制執行——而在公務系統中，那可能是一條法規要件。

3-3　各正規化層級的保證

目標無損分解保持相依
3NF一定可達成一定可達成
BCNF一定可達成不一定！
✅ 深化 3 必背結論 ① 二元分解無損的判準：共同欄位必須是其中一邊的鍵。
② 有損分解的後果是「JOIN 後多出虛假的列」，不是資料遺失。
③ 3NF 可同時保證無損與保持相依；BCNF 只保證無損。

深化 4　3NF 與 BCNF 的取捨：為什麼實務停在 3NF

4-1　兩者定義的精確差異

3NFBCNF
條件對每個非平凡相依 X → A：X 是超鍵，或 A 是主要屬性（屬於某候選鍵）對每個非平凡相依 X → A：X 必須是超鍵
差別3NF 多給了一個「或」——這個「或」正是它能保持相依的原因

4-2　經典反例：達 3NF 但未達 BCNF

R(學生, 課程, 教師)，語意：每位教師只教一門課；一門課可由多位教師教；學生修某課由某位教師授課。

F = { (學生, 課程) → 教師，教師 → 課程 }
候選鍵 = {(學生,課程), (學生,教師)}
主要屬性 = {學生, 課程, 教師}——全部都是

檢查 3NF：「教師 → 課程」中，教師不是超鍵，但課程是主要屬性 → 符合 3NF ✔
檢查 BCNF：「教師 → 課程」中，教師不是超鍵 → 違反 BCNF ✘
⚠️ 若強行分解為 BCNF 會發生什麼
分解為 R₁(教師, 課程) 與 R₂(學生, 教師)：
→ 無損 ✔
→ 但「(學生,課程) → 教師」這條相依，在任何單一表上都檢查不到了 ✘

後果：「同一個學生、同一門課，只能有一位教師」這條規則，資料庫再也無法自動強制——只能靠應用程式，而應用程式可以被繞過。
💡 申論的完整寫法
「本案分解至 BCNF 雖可消除所有非鍵決定因素之異常，惟將導致函數相依『(學生,課程)→教師』無法於單一關聯上檢查，該業務規則即失去資料庫層之強制力。
考量該規則屬法規要件、須確保不可被繞過，建議停留於 3NF，並以唯一約束輔助之。」

——這段話同時展現了「會算正規化」與「知道正規化的界線」。

4-3　4NF 與 5NF：知道存在即可

層級消除什麼實務
4NF多值相依（MVD）——兩組互相獨立的多值屬性放在同一表偶爾遇到
5NF連接相依幾乎只在理論上討論
4NF 的直觀例子：R(員工, 技能, 語言)——技能與語言彼此獨立。
一位懂 2 種技能、3 種語言的員工，會產生 2×3 = 6 列（笛卡兒積式的冗餘）。
分解為 R₁(員工,技能) 與 R₂(員工,語言) → 2+3 = 5 列。
✅ 深化 4 必背結論 ① 3NF 允許「A 是主要屬性」的例外，BCNF 不允許——差別就在這個「或」。
② 分解至 BCNF 可能喪失保持相依，使業務規則失去資料庫層的強制力。
③ 公務系統若該規則是法規要件，宜停留在 3NF 並輔以約束。

⚠️ 兩個高頻陷阱

① 投影 π 會去重，但 SQL 的 SELECT 預設「不」去重
關聯代數是集合語意（無重複），SQL 是多重集語意（允許重複）。
所以 π 對應的是 SELECT DISTINCT，不是 SELECT。

② 「除法」對應的是「對所有…都成立」的查詢
例：「找出修過所有必修課的學生」——這是典型的除法。

5-1　除法的 SQL 寫法（雙重否定）

-- 找出「修過所有必修課」的學生
SELECT s.學號 FROM 學生 s
WHERE NOT EXISTS (
    -- 不存在這樣一門必修課…
    SELECT 1 FROM 必修課 c
    WHERE NOT EXISTS (
        -- …是這位學生沒修過的
        SELECT 1 FROM 修課 e
        WHERE e.學號 = s.學號 AND e.課號 = c.課號
    )
);
💡 記法：「對所有 X 都 Y」＝「不存在 X 是不 Y 的」
公務應用：「找出已完成所有應辦事項的案件」、「找出所有承辦人都已簽核的公文」——都是除法。
另一種寫法：用 GROUP BY + HAVING COUNT(DISTINCT …) = (必修課總數)，較直觀但需注意重複修課的情形。
✅ 深化 5 必背結論 ① 投影 π 對應 SELECT DISTINCT（集合語意 vs 多重集語意的差別）。
② 除法對應「對所有…都…」，SQL 用雙重 NOT EXISTS 實作。
③ 五個基本運算：選擇、投影、聯集、差集、笛卡兒積——其餘皆可導出。

深化 6　交易：隔離級別、異常與 MVCC 原理

6-1　四種異常與四種隔離級別的完整對應

隔離級別髒讀不可重複讀幻讀更新遺失
Read Uncommitted可能可能可能可能
Read Committed不會可能可能可能
Repeatable Read不會不會標準允許；MySQL InnoDB 以間隙鎖避免可能
Serializable不會不會不會不會
⚠️ 「更新遺失（lost update）」不在標準的三種異常裡，但它最危險
甲改欄位 A、乙改欄位 B，乙後存 → 甲的修改消失，而且沒有任何錯誤訊息。
防護：樂觀鎖（版本號）或 SELECT … FOR UPDATE——單靠提高隔離級別在多數實作下並不保證。

6-2　三種異常的精確區分

異常發生在看到什麼
髒讀讀到尚未提交的資料對方可能回滾 → 你讀到根本不存在的值
不可重複讀同一列讀兩次值變了（別人 UPDATE 並提交）
幻讀同一個範圍查兩次列數變了（別人 INSERT 並提交）
💡 記法：不可重複讀看「同一列的值」，幻讀看「範圍內的列數」
公務例：產製報表時在同一交易中查了兩次——
不可重複讀 → 同一件案子的金額前後不同
幻讀 → 第二次查多出了幾件新收的案子，導致報表內部數字對不起來

6-3　MVCC：讀不擋寫、寫不擋讀

原理：更新時不覆蓋舊值，而是產生新版本並標記交易編號；
讀取者依自己交易開始的時點，看到當時的快照。
優點代價
讀不擋寫、寫不擋讀 → 併發度大增舊版本要保存，佔用空間
讀取到一致的快照需要定期清理（vacuum / undo 空間回收）
大幅減少鎖競爭長交易會阻止舊版本被清理 → 空間膨脹
⚠️ MVCC 系統最經典的運維事故：長交易
某支報表程式開了交易卻跑了六小時（或忘記結束）——這段期間所有舊版本都不能被清理。
結果：資料表膨脹數倍、查詢變慢、磁碟告急。
對策：監控「目前最久的交易執行時間」，超過門檻即告警。
✅ 深化 6 必背結論 ① 髒讀（未提交）／不可重複讀（同列值變）／幻讀（範圍列數變）——三者的區分是必考。
② 更新遺失須靠樂觀鎖或悲觀鎖，不能單靠提高隔離級別。
③ MVCC 以多版本換併發度，代價是空間與清理；長交易是其最大運維風險。

深化 7　兩階段鎖定與可序列化的關係

7-1　2PL（Two-Phase Locking）

成長階段（growing）：只能取得鎖，不能釋放
收縮階段（shrinking）：只能釋放鎖，不能取得

定理：遵守 2PL 的排程，必為衝突可序列化（conflict serializable）。
變體規則解決什麼
基本 2PL如上保證可序列化
嚴格 2PL寫鎖保留到交易結束避免串聯回滾（cascading rollback）
嚴謹 2PL所有鎖都保留到交易結束最容易實作，多數資料庫採用
⚠️ 2PL 保證可序列化，但「不」保證無死結
兩個交易各自持有對方要的鎖，都在等 → 死結。
2PL 只解決「正確性」，死結要另外處理（偵測後回滾其一，或統一取鎖順序預防）。

7-2　衝突可序列化的判定：優先圖（precedence graph）

① 每個交易畫成一個節點
② 若 Ti 的某操作與 Tj 的某操作衝突（至少一個是寫、且針對同一資料項）且 Ti 在前 → 畫一條 Ti → Tj
③ 若圖中無環 → 衝突可序列化；有環 → 不可
④ 無環時，拓樸排序即為等價的序列化順序
💡 這題是「圖的迴路偵測」的直接應用
與資料結構科的拓樸排序與環偵測是同一件事——申論時可以互相引用，展現整體觀。

7-3　死結的四個必要條件與對策

條件能否破壞實務對策
互斥不能（鎖的本質）—
佔有並等待可一次取得所有鎖（實務困難）
不可搶奪可逾時後回滾（wait-die / wound-wait）
循環等待可——最實用所有交易依相同順序取鎖
⚠️ 應用程式必須能處理「死結導致的回滾」
被選為犧牲者的交易會收到錯誤——程式應該重試，而不是把錯誤丟給使用者。
但重試須有次數上限，且該操作必須具備冪等性（否則重試會重複處理）。
✅ 深化 7 必背結論 ① 2PL 保證衝突可序列化，但不保證無死結。
② 嚴格 2PL（寫鎖保留至結束）避免串聯回滾；嚴謹 2PL 保留全部鎖。
③ 可序列化判定用優先圖：無環即可序列化，拓樸排序即等價順序。

深化 8　索引的成本模型：什麼時候優化器會放棄索引

8-1　成本估算的實際計算

情境：表有 500 萬列、5 萬個資料頁。查詢命中 10 萬列。
隨機 I/O 約 0.1 ms／次；循序 I/O 約 0.01 ms／頁。

方式計算時間
索引 ＋ 回表100,000 × 0.1 ms10,000 ms = 10 秒
全表掃描50,000 頁 × 0.01 ms500 ms = 0.5 秒
→ 全表掃描快 20 倍，優化器放棄索引是「對的」。
💡 經驗門檻：命中率超過約 10～20% 時，全表掃描通常較快
因為隨機 I/O 比循序 I/O 慢一個數量級——即使在 SSD 上這個差距仍然存在，只是縮小。
所以「加了索引卻沒有變快」不一定是索引的問題，可能是命中率太高。

8-2　涵蓋索引：消除回表的成本

若查詢所需的欄位全部都在索引中，就不需要回表 → 隨機 I/O 完全消失。

例：常查 SELECT 案號, 狀態 FROM 案件 WHERE 承辦人 = ?
→ 建索引 (承辦人, 案號, 狀態)
代價說明
索引變大欄位越多佔用越多空間
寫入成本增加索引中任一欄位被更新，索引就要維護

8-3　最左前綴原則的完整判定

複合索引 (A,B,C) 下的查詢能用到
WHERE A=1✔ A
WHERE A=1 AND B=2✔ A,B
WHERE A=1 AND B=2 AND C=3✔ 全部
WHERE A=1 AND C=3△ 只用到 A（B 斷了）
WHERE B=2 AND C=3✘ 完全用不到
WHERE A>1 AND B=2△ 範圍條件之後的欄位用不到
ORDER BY A, B✔ 可免排序
ORDER BY B, A✘ 順序不符
💡 複合索引的欄位順序設計原則
① 等值條件的欄位放前面，範圍條件放後面
② 選擇性高的放前面（能更快縮小範圍）
③ 若已有 (A,B,C)，就不需要再建 (A) 或 (A,B)——前綴已被涵蓋

8-4　讓索引失效的六種寫法

寫法問題改法
WHERE YEAR(日期)=2026欄位被函數包住改為半開區間範圍
WHERE 金額+0 = 100欄位參與運算WHERE 金額 = 100
LIKE '%後綴'前置萬用字元全文索引或反轉索引
隱含型別轉換字串欄位用數字比對——最容易被忽略統一型別並加引號
OR 串接不同欄位優化器可能放棄改用 UNION
統計資訊過期優化器估錯列數而選錯計畫更新統計資訊
✅ 深化 8 必背結論 ① 命中率超過約 10～20% 時全表掃描較快，因隨機 I/O 比循序慢一個數量級。
② 涵蓋索引可完全消除回表；代價是索引變大與寫入成本上升。
③ 最左前綴：範圍條件之後的欄位用不到；隱含型別轉換是最隱蔽的索引失效原因。

深化 9　查詢優化器：連接演算法的成本比較

9-1　三種連接演算法

演算法原理成本（概念）最適用
Nested Loop外表每一列，去內表查一次|R| × 內表查詢成本外表小 ＋ 內表連接欄有索引
Hash Join小表建雜湊表，再掃大表比對|R| + |S|大表對大表、等值連接
Merge Join兩邊排序後同時走訪排序成本 + |R| + |S|兩邊已排序或有排序索引
⚠️ Hash Join 只能用於「等值連接」
因為雜湊只能判斷「相等」，無法處理 >、<、BETWEEN。
不等值連接只能用 Nested Loop 或 Merge Join。

9-2　執行計畫的判讀重點

看什麼異常訊號
預估列數 vs 實際列數差距數十倍以上 → 統計資訊過期
存取方式應該用索引卻是全表掃描
連接方式大表對大表卻用 Nested Loop
是否有排序或暫存大量排序可能溢出到磁碟
回表次數過多 → 考慮涵蓋索引

9-3　同一支 SQL 為何時快時慢

原因說明對策
參數探測（parameter sniffing）用「台北市」編譯的計畫，套到「連江縣」就不合適重新編譯或分開寫
鎖等待被長交易卡住縮短交易
快取未命中資料不在緩衝區需讀硬碟增加緩衝區
大型查詢沖走快取報表掃了整張大表，把熱資料擠出緩衝區報表走唯讀副本
💡 「參數探測」的公務實例
查詢「某縣市的案件」——台北市有 50 萬筆（該用全表掃描），連江縣只有 200 筆（該用索引）。
資料庫只為第一次執行的參數編譯一套計畫並重複使用 → 另一種情況就會很慢。
診斷方法：記錄慢查詢日誌時，一併記下當時的參數值——只看 SQL 文字看不出問題。
✅ 深化 9 必背結論 ① Nested Loop（外表小＋內表有索引）／Hash Join（大對大、等值）／Merge Join（已排序）。
② Hash Join 只能用於等值連接。
③ 執行計畫先看「預估 vs 實際列數」——差距大即統計資訊過期。

深化 10　分散式：CAP、BASE、2PC 與 Saga

10-1　CAP 的正確理解

⚠️ CAP 不是「三選二」
網路分區（P）是必然會發生的，不是可以放棄的選項。
CAP 真正的意思是：當分區發生時，你要選擇 C 還是 A。
選擇分區時的行為公務適用
CP寧可拒絕服務，也不回傳可能過期的資料金額、核定、名額扣減
AP先回應，之後再同步（最終一致）公告瀏覽、統計查詢、案件進度顯示
💡 公務系統的判準只有一個問題
「如果這個數字是錯的或過期的，會不會導致一個違法的決定？」
會 → 選 CP，不惜代價；不會 → 可用快取、副本、最終一致。

10-2　ACID vs BASE

ACIDBASE
全名原子、一致、隔離、持久Basically Available、Soft state、Eventually consistent
一致性強一致最終一致
適用交易型（公務核心業務）大規模讀取、可容忍延遲

10-3　2PC 的阻塞問題與 Saga 的替代

兩階段提交（2PC）：
① 準備階段：協調者問所有參與者「可以提交嗎」；參與者鎖定資源並回覆
② 提交階段：全部同意 → 通知提交；有人拒絕 → 通知全部回滾
⚠️ 致命弱點：協調者在階段②之前故障
參與者已鎖定資源、已回答「可以」，但不知道最終結果——只能一直等，資源持續被鎖。
這就是「阻塞問題」，是 2PC 無法根治的缺陷。
2PCSaga
做法集中協調、同步提交拆成一連串本地交易，每步有補償動作
一致性強一致最終一致
中間狀態不可見對外可見
可用性低（阻塞）高
跨機關可行性幾乎不可行（沒有機關會讓外部協調者鎖住自己的資料庫）可行
💡 公務跨機關介接的實務解法
交易發件匣模式：本地交易只寫入「待送出」紀錄 → 另一支程序讀取並發送 → 附冪等性金鑰 → 失敗告警 → 每日對帳。
「對帳」是最終防線：因為分散式系統中總有些狀況是當下無法確定的（逾時、網路分區）。
✅ 深化 10 必背結論 ① CAP 不是三選二；P 必然發生，真正的選擇是分區時要 C 還是 A。
② 2PC 的致命弱點是協調者故障導致參與者阻塞。
③ 跨機關一致性實務上採「發件匣 ＋ 冪等性金鑰 ＋ 對帳」，而非 2PC。

深化 11　公務資料庫的時態設計（雙時態）

11-1　兩種「時間」必須分開

時間軸意義公務例
有效時間
（valid time）		事實在現實世界中成立的期間某人自 113/5/1 起設籍本市
交易時間
（transaction time）		資料在系統中被記錄的期間該筆設籍資料於 113/6/15 才被登錄進系統
💡 為什麼公務系統一定要分開這兩者
因為它們回答兩個不同的問題：
「這個人在 113 年 5 月時是否設籍本市？」→ 查有效時間
「我們在 113 年 6 月核定時，系統裡看到的資料是什麼？」→ 查交易時間

第二個問題在爭訟時至關重要——它決定了「機關當時的判斷是否有過失」。
⚠️ 只有一個時間軸會發生的事
民眾主張「我 5 月就設籍了，你們 6 月核定時為什麼說我不符合？」
若系統只記錄「現在的狀態」——機關無法證明「6 月當時系統裡確實沒有這筆資料」。

而如果資料是後來才補登的（追溯生效），機關的原處分在當時其實是正確的——但沒有雙時態設計就說不清楚。

11-2　實作方式

-- 雙時態表的欄位設計
CREATE TABLE 設籍紀錄 (
    id            BIGINT PRIMARY KEY,
    身分識別碼     VARCHAR(32) NOT NULL,
    設籍地        VARCHAR(64) NOT NULL,
    有效起日      DATE NOT NULL,      -- valid time 起
    有效訖日      DATE,               -- valid time 迄（NULL = 迄今）
    登錄時間      TIMESTAMP NOT NULL, -- transaction time 起
    失效時間      TIMESTAMP,          -- transaction time 迄（NULL = 現行有效）
    登錄人        VARCHAR(32) NOT NULL,
    依據          VARCHAR(128)        -- 公文字號或法規條次
);
兩種查詢：
① 現在系統認為，113/5/1 的事實是什麼？
　WHERE 有效起日 <= '113-05-01' AND (有效訖日 IS NULL OR 有效訖日 >= '113-05-01') AND 失效時間 IS NULL

② 在 113/6/15 那天，系統裡記載的 113/5/1 事實是什麼？
　WHERE 有效起日 <= '113-05-01' AND (有效訖日 IS NULL OR 有效訖日 >= '113-05-01')
　　AND 登錄時間 <= '113-06-15' AND (失效時間 IS NULL OR 失效時間 > '113-06-15')

11-3　需要時間維度的資料一覽

資料為何需要不做的後果
法規參數新舊法適用、程序重開舊案重算會套到新規則 → 錯誤
代碼表行政區改制、機關改隸舊資料無法解讀
組織架構單位改隸歷年統計錯亂、與已公告數字不符
人員任職職務調動責任歸屬混亂
權限設定職務變動權限悄悄擴大而無人察覺
補助標準標準調整金額計算違法
案件狀態流程追溯期限與爭訟無法舉證
✅ 深化 11 必背結論 ① 有效時間＝事實成立的期間；交易時間＝系統記錄的期間，兩者必須分開。
② 交易時間決定「機關當時的判斷是否有過失」，是爭訟舉證的關鍵。
③ 公務資料庫幾乎沒有一張核心表是不需要時間維度的。

金額核算、對帳Repeatable Read 以上同一交易內讀到的值必須一致
名額分配、抽籤Serializable 或明確加鎖不能有幻讀，否則會超額核給
統計快照快照隔離／另建彙總表避免長交易鎖住整張表
⚠️ 最容易被忽略的一點 提高隔離等級不能解決「遺失更新」——那是應用層的問題，要靠樂觀鎖（版本號）或 SELECT ... FOR UPDATE 解決。
申論若寫「用 Serializable 解決公文同時編輯」是錯的（也不可行，會鎖住半小時）。
✅ 深化 13 必背結論 ① 異常三種：髒讀（未提交）、不可重複讀（值變）、幻讀（列數變）
② 等級四階，Read Committed 是多數資料庫預設
③ 名額分配須防幻讀；遺失更新要用樂觀鎖，不是提高隔離等級

深化 14　MVCC：為什麼讀不會擋寫、寫不會擋讀

14-1　傳統鎖的困境

純鎖式的資料庫：有人在寫，讀的人就要等；有人在讀，寫的人也要等。
在「報表查詢跑十分鐘」的公務系統裡，這代表整張表被鎖十分鐘。

14-2　MVCC 的核心想法

📐 多版本並行控制 每次更新不覆蓋舊值，而是產生一個新版本並標記交易編號。
每個交易依自己的「快照時間點」，去讀當時應該看到的那個版本。

結果：讀取者不需要鎖，寫入者也不會被讀取者擋住。
時間交易 A（查詢）交易 B（更新）A 看到的值
T1開始，取得快照—100
T2—把值改為 200 並提交仍是 100
T3再讀一次—仍是 100（同一快照）
T4結束；新交易開始—200

14-3　MVCC 的代價

代價說明維運要點
舊版本堆積被取代的版本仍占空間須定期清理（如 VACUUM）
長交易的傷害一個開了三小時沒結束的交易，會讓這三小時的所有舊版本都不能清設定交易逾時；報表改讀副本
寫入放大更新一列可能觸發索引多處更新控制索引數量
⚠️ 公務系統的實際事故樣態 「資料庫空間暴增、效能崩潰」的常見原因不是資料變多，而是某個程式開了交易卻忘了提交或回滾（例如連線洩漏），
導致舊版本永遠無法清理。監控「最長執行中交易時間」是必要指標。
✅ 深化 14 必背結論 ① MVCC 讓讀不擋寫、寫不擋讀，靠的是保留多版本 ＋ 快照
② 代價是舊版本要清理；長交易會讓清理失效
③ 必監控指標：最長執行中交易、未提交交易數

深化 15　查詢執行計畫：看懂資料庫在想什麼

15-1　三種聯結演算法

演算法做法適合複雜度
巢狀迴圈對外表每一列去內表找外表很小、內表有索引O(n × log m)
雜湊聯結小表建雜湊表，大表掃過去查等值聯結、兩表都大O(n + m)
合併聯結兩表都排序後雙指標掃兩表已依聯結鍵排序（或有索引）O(n log n + m log m)

非等值聯結（如 ON a.金額 > b.門檻）不能用雜湊聯結——雜湊只能做等值比對。這是常考的判斷點。

15-2　執行計畫要看的五件事

📐 診斷順序 ①掃描方式：看到 Full Table Scan 且表很大 → 檢查索引與條件寫法
②預估 vs 實際列數：差距超過十倍 → 統計資訊過期，須更新
③聯結演算法：大表對大表卻用巢狀迴圈 → 通常是估算錯誤
④排序與暫存：出現「使用暫存檔」表示記憶體不夠，會落到磁碟
⑤成本最高的節點：從最貴的那一步開始改，不要亂調

15-3　統計資訊為什麼關鍵

資料庫是靠統計資訊（每個欄位有幾個相異值、資料分布如何）來估算「這個條件會篩出幾列」，
再據以決定要不要用索引、用哪種聯結。

統計過期的典型場景：年初剛匯入 500 萬筆資料，但統計還停在去年的 10 萬筆 →
資料庫以為只有 10 萬筆，選了巢狀迴圈 → 查詢從 2 秒變成 40 分鐘。

維運作為：大量匯入或刪除後主動更新統計資訊；並排定定期維護作業。

15-4　公務系統的效能調校順序

順序做什麼效益／成本
1改寫查詢（消除函數包欄位、消除 N+1）最高／零成本
2建立或調整索引高／低
3更新統計資訊、調整參數中／低
4加彙總表或快取高／中（要處理一致性）
5升級硬體最低／最高

申論結論句：「效能問題應先從查詢與索引著手，硬體升級是最後手段——因為前者常有數十倍改善，後者通常只有數倍。」

✅ 深化 15 必背結論 ① 三種聯結：巢狀迴圈（小外表）、雜湊（等值大表）、合併（已排序）
② 非等值聯結不能用雜湊聯結
③ 預估與實際列數差十倍以上 → 統計資訊過期
④ 調校順序：查詢 → 索引 → 統計 → 快取 → 硬體

深化 16　分割與分片：資料太大時的兩條路

16-1　分割（Partitioning）：同一台機器內切

方式依據公務適用
範圍分割依日期或編號區間最常用：依年度分割案件表
雜湊分割依鍵值雜湊平均分配資料量平均、無明顯時間性
清單分割依明確值列舉依行政區分割
📐 分割的三大效益 ①分割裁剪：查 115 年的案件時，資料庫只掃 115 年那一塊，其他年度完全不碰
②維護獨立：可單獨對某一年做重建索引、備份或壓縮
③快速歸檔：要把 100 年以前的資料下線，直接卸載該分割即可，不需 DELETE 500 萬筆

第三點在公務系統特別重要：大量 DELETE 會產生巨量交易紀錄、鎖表、且空間不會馬上釋放；卸載分割是瞬間完成的。

16-2　分片（Sharding）：拆到不同機器

分割分片
範圍單一資料庫內多台資料庫伺服器
目的查詢效率與維護突破單機容量與吞吐上限
跨界查詢資料庫自動處理需應用層彙整，交易一致性困難
複雜度低高
⚠️ 縣市政府該不該分片 絕大多數縣市政府的資料量（千萬級）用不到分片——單機加上適當索引與分割就綽綽有餘。
分片會帶來跨片交易、跨片統計、資料重新平衡三個難題，維運能量負擔不起。

申論寫法：「技術選擇須與機關維運能量相稱；本案資料量級以分割即可滿足，暫無分片必要。」

16-3　讀寫分離：更常用的擴充方式

主庫負責寫入，副本負責查詢與報表。

優點：報表跑再久也不影響核心作業。
必須注意的一件事：副本有複寫延遲——剛寫入的資料可能在副本上查不到。
故「寫入後立即查詢」的流程必須讀主庫，否則民眾送件後查不到自己的案件。
✅ 深化 16 必背結論 ① 分割三效益：分割裁剪、維護獨立、卸載分割取代大量 DELETE
② 分片是跨機器，代價是跨片交易與統計；縣市政府層級通常不需要
③ 讀寫分離要注意複寫延遲——寫後立即查須讀主庫

深化 17　資料庫加密：三層防護與各自擋得住什麼

17-1　三個層次

層次加密對象擋得住擋不住
傳輸中
（TLS）		連線網路竊聽、中間人資料庫內部的一切
靜態
（TDE 透明加密）		整個資料檔硬碟或備份檔被偷走合法登入的人照樣看得到明文
欄位級特定敏感欄位內部人員不當查詢、DBA 越權應用程式本身被入侵
📐 一句話判準 TDE 防的是「硬碟被搬走」，欄位加密防的是「人把資料查出來」。
兩者防的威脅完全不同，不能互相取代——這是申論最容易寫錯的地方。

17-2　欄位加密的三個實務難題

難題說明解法
無法查詢加密後的值無法做範圍查詢或排序另存一個加鹽雜湊欄位供等值比對
索引失效加密欄位建索引沒有意義改以其他欄位為查詢入口
金鑰管理金鑰跟資料放在一起 = 沒有加密獨立的金鑰管理系統，並規劃輪替

17-3　遮罩（Masking）：更常被需要的功能

動態資料遮罩：一般承辦查詢時看到 A12****789，具特定權限者才看到完整值。

這比全欄位加密更符合公務實務——大多數作業其實不需要完整的身分證字號，只需要確認是同一個人。
手段可否還原用途
加密可（有金鑰）需要原值的作業
雜湊 ＋ 鹽不可只需比對是否相同
遮罩顯示層處理，原值仍在畫面顯示、報表輸出
代碼化需查對照表資料交換時以代碼取代真值

17-4　備份也要加密（最常漏掉的一項）

⚠️ 備份是個資外洩的常見來源 正式環境防護嚴密，但備份檔可能：存在防護較弱的儲存裝置、送到異地、由廠商保管、放在測試環境還原。

要求：備份檔應加密、金鑰與備份分開保管、還原演練時使用去識別化資料。
✅ 深化 17 必背結論 ① TDE 防硬碟被偷，欄位加密防人越權查詢——不可互相取代
② 欄位加密會讓查詢與索引失效；需要比對時用加鹽雜湊
③ 金鑰不可與資料同放
④ 實務上遮罩比全加密更實用；備份也必須加密

深化 18　資料倉儲深入：ETL、ELT 與資料血緣

18-1　ETL vs ELT

ETLELT
順序抽取 → 先轉換 → 載入抽取 → 載入 → 在目標端轉換
轉換在哪獨立的 ETL 伺服器資料倉儲本身（算力強）
原始資料通常不保留保留原始副本
適合轉換複雜、目標端算力有限雲端資料倉儲、需要回溯原始值
公務建議：優先 ELT 並保留原始層——因為「當初到底進來的是什麼」在稽核與爭議時是關鍵。
只存轉換後的結果，等於把證據丟掉。

18-2　分層架構

📐 三層（或四層） 原始層（Raw／Bronze）：原封不動的來源副本，不做任何修改
↓
整理層（Cleansed／Silver）：清洗、統一代碼、去識別化、補齊
↓
應用層（Mart／Gold）：依主題彙總，供報表與儀表板直接使用

為什麼要分層：出現數字爭議時，可以逐層往回追——是來源錯、清洗規則錯，還是彙總邏輯錯。沒有分層就只能重跑一次並祈禱。

18-3　資料血緣（Data Lineage）

要回答的問題沒有血緣時的下場
這個數字是從哪裡來的？無法向議會說明
經過哪些加工？爭議時無法自證
如果來源系統要改欄位，會影響哪些報表？改了才發現三個儀表板壞掉
這份報表多久沒更新了？用了過期資料做決策

18-4　ETL 的品質檢核點

📐 每一批次都應自動檢查 ①筆數勾稽：來源筆數 = 載入筆數 ＋ 拒絕筆數
②金額合計勾稽：來源合計 = 目標合計（差一元都要查）
③值域檢查：日期是否合理、金額是否為負、代碼是否在對照表內
④重複檢查：主鍵是否重複
⑤異常告警：批次失敗或筆數異常變動，必須主動通知
⚠️ 最危險的失敗模式 批次沒跑成功，但儀表板照樣顯示舊資料——沒有人發現。
解法：畫面永遠顯示「資料更新時間」，並對超過預期未更新者發出告警。
✅ 深化 18 必背結論 ① 公務優先 ELT 並保留原始層——原始資料是稽核證據
② 三層架構：原始 → 整理 → 應用，出錯時可逐層追
③ 資料血緣回答「數字從哪來、改了會影響誰」
④ 每批次做筆數與金額勾稽；畫面顯示資料更新時間

深化 19　時態資料：公務系統的預設需求

19-1　兩種時間軸

時間意義公務例
有效時間
Valid Time		這筆事實在真實世界何時開始生效低收入戶資格自 115/1/1 起生效
交易時間
Transaction Time		這筆紀錄何時被寫進系統承辦於 115/2/10 才完成建檔
📐 為什麼兩個都要記 要回答兩種不同的問題：
①「這個人在 115 年 1 月是不是低收入戶？」→ 用有效時間
②「我們在 115 年 1 月當時知道他是低收入戶嗎？」→ 用交易時間

第二個問題在爭訟時是關鍵——承辦當時依據的資訊是什麼，決定了處分是否合法。

19-2　雙時態表的設計

欄位用途
業務主鍵識別是誰
有效起日／有效迄日真實世界的生效期間
建檔時間／失效時間系統中的版本期間
異動人、異動原因稽核必要
資料來源血緣追蹤

鐵則：這種表只能 INSERT，不能 UPDATE 或 DELETE。更正是「新增一筆更正紀錄並將舊版標記失效」，不是改掉舊值。

19-3　追溯生效的處理

情境：115 年 3 月才發現某人的資格應自 115 年 1 月起生效。

正確處理：新增一筆有效起日 = 115/1/1、建檔時間 = 115/3/x 的紀錄。

連帶效果：1、2 月已核算的補助可能需要補發——系統必須能重算過去期間，
而重算的前提就是資料模型保留了時間軸。
⚠️ 覆蓋式設計的災難 如果當初是直接 UPDATE 覆蓋：
①不知道原本是什麼 ②不知道何時改的 ③不知道誰改的 ④無法重算過去期間 ⑤爭訟時無法自證合法。

這五點就是申論的完整失分分析。

19-4　法規參數也要版本化

補助金額、級距、費率會隨法規修正而改變。系統必須依「案件發生當時的法規版本」計算，而非現行版本。
做法：把法規參數存成有生效期間的參數表，計算時依案件基準日取用對應版本。

✅ 深化 19 必背結論 ① 有效時間（真實世界何時生效）與交易時間（何時被記錄）都要保留
② 時態表只增不改；更正用新增紀錄的方式
③ 追溯生效需能重算過去期間，前提是保留了時間軸
④ 法規參數也要版本化，依案件基準日取用

深化 20　主從式複寫與高可用：RPO/RTO 怎麼落地

20-1　同步 vs 非同步複寫

同步複寫非同步複寫
提交條件備援也寫入成功才回應主庫寫入即回應
RPO0（不遺失）可能遺失最後幾秒
寫入延遲受兩地距離影響（光速限制）不受影響
適合同城短距離異地遠距離
📐 物理限制（申論可寫的硬事實） 光在光纖中約每公里 5 微秒，來回即 10 微秒。
台北到高雄約 350 公里 → 單次來回至少 3.5 毫秒。

若每筆交易都要等這 3.5 毫秒，寫入吞吐量會受嚴重限制。
這就是「異地備援通常採非同步」的物理原因——不是技術做不到，是物理限制。

20-2　架構選擇對照

業務RPORTO架構
災害應變、1190分鐘級同城同步 ＋ 自動切換
戶政、稅務數分鐘數小時異地非同步 ＋ 手動切換
內部行政系統1 日1～3 日每日備份 ＋ 還原
歷史查詢系統1 週1 週定期備份即可

20-3　切換的三個現實問題

⚠️ 有備援不代表切得過去 ①誰有權決定切換？——沒有明定，事故當下沒人敢做決定
②切換要多久？——包含 DNS 生效時間、應用程式連線字串更新、快取清除
③切回來怎麼辦？——備援期間產生的資料要如何同步回主庫，這一步最常被忽略

腦裂（Split-Brain）：主備因網路中斷而互相認為對方掛了，兩邊同時接受寫入 → 資料衝突且難以合併。
防範：仲裁節點（Quorum）或明確的人工決策程序。

20-4　演練才是重點

「沒有演練過的備援，等同沒有備援。」

年度演練應涵蓋：①實際切換 ②實際還原一份備份 ③驗證資料完整性 ④記錄實際花費時間並與 RTO 比對 ⑤切回主庫。

演練紀錄要留存——這既是資安法的要求，也是爭取預算的依據。
✅ 深化 20 必背結論 ① 同步複寫 RPO=0 但受距離限制；異地通常只能非同步
② 台北到高雄光速來回約 3.5 毫秒——這是物理限制
③ 切換要先定義：誰決定、多久、怎麼切回
④ 腦裂要靠仲裁機制防範；演練紀錄必須留存

深化 21　NoSQL 選型：四種類型與公務混合架構

21-1　四種類型的判準

類型資料模型強項公務適用
鍵值Key → Value極快的等值查詢Session、快取、驗證碼
文件JSON 文件結構彈性、巢狀陳情內容、表單、話務摘要
欄位家族寬表大量寫入、時序感測器數據、日誌
圖形節點與邊多層關係查詢人際關聯、金流追查、地籍相鄰
📐 圖形資料庫的關鍵優勢 「找出與某人有三層以內關聯的所有人」——
關聯式資料庫要做三次自我聯結，資料量大時效能極差；
圖形資料庫是沿著邊走，複雜度只與結果規模有關，與總資料量無關。

21-2　混合架構（公務的實際答案）

資料放哪裡理由
案件主檔、核定、金額關聯式資料庫要交易一致性、要稽核、要法遵
陳情內容、附件描述文件資料庫欄位常變、結構彈性
Session、驗證碼鍵值儲存短期、高頻
操作日誌、感測數據欄位家族／時序資料庫寫入極重
全文檢索搜尋引擎（倒排索引）關鍵字與相關性排序
⚠️ 混合架構的代價 多一套系統就多一套：備份、監控、權限、版本升級、人員技能。

公務判準：「除非現有關聯式資料庫確實無法滿足，否則不引入新的資料庫類型——
因為資訊室要養得起它。」

21-3　最終一致性可以接受嗎

資料可接受最終一致？理由
公告、法規查詢可以晚幾秒看到沒有影響
案件進度查詢視情況須顯示資料基準時間
繳費、核定、餘額不可以涉及金錢與權益，必須強一致
名額分配不可以會超額核給
✅ 深化 21 必背結論 ① 四型：鍵值（快取）、文件（彈性）、欄位家族（重寫入）、圖形（多層關係）
② 核心交易資料一律留在關聯式資料庫，其餘才考慮混合
③ 混合的代價是維運負擔加倍——要與機關能量相稱
④ 涉及金錢與名額者不可接受最終一致性

深化 22　資料品質的量化：從「感覺不準」到「準確率 97.3%」

22-1　六個構面與可計算的指標

構面指標算法目標值範例
完整性非空值筆數 ÷ 應有筆數必填欄位 100%
正確性抽樣比對權威來源的相符率≥ 99%
一致性跨系統勾稽相符筆數 ÷ 總筆數≥ 99.5%
時效性資料更新時間與現在的落差≤ 1 日
唯一性1 − 重複筆數 ÷ 總筆數≥ 99.9%
有效性符合格式與值域的比率≥ 99%

為什麼要量化：「資料很亂」無法編預算；「地址一致性僅 82%，導致跨局處統計誤差達 15%」才能說服長官。

22-2　資料品質的三道防線

📐 由前往後，成本由低到高 ①源頭控制（最便宜）：輸入即驗證、下拉選單取代自由輸入、必填欄位、格式檢查
②流程檢核（中）：ETL 批次的勾稽、跨系統定期比對、異常告警
③事後修補（最貴）：人工清洗、委外清理——而且不解決根因，明年還要再做一次

「進來時擋，比出去時補便宜十倍。」

22-3　資料品質報告的呈現方式

資料集完整性一致性時效性綜合趨勢
案件主檔99.8%98.2%即時A持平
地址資料97.1%82.4%1 日C改善中
聯絡電話88.5%95.0%1 日B下降

加上「趨勢」欄是關鍵——長官要看的不只是現況，而是「有沒有在改善」。

22-4　資料品質與行政責任的連結

⚠️ 申論的加分連結 資料品質不只是技術議題，它直接影響：
① 統計數字錯誤 → 政策決策失誤、對議會與民眾說明不實
② 名冊遺漏 → 應通知而未通知，屬行政疏失
③ 資料錯誤導致處分違法 → 撤銷、返還，甚至國家賠償

把技術指標連到法律後果，是高考三級與普考的分水嶺。
✅ 深化 22 必背結論 ① 六構面都可以算成數字：完整、正確、一致、時效、唯一、有效
② 三道防線：源頭 → 流程 → 事後，成本逐級上升十倍
③ 報告要有趨勢欄，不能只有現況
④ 品質問題要連到行政責任與法律後果

深化 23　資料庫維運的可觀測性：該監控哪些指標

23-1　四大類必監控指標

類別指標異常代表什麼
效能慢查詢數量與清單需要調校的目標
快取命中率偏低表示記憶體不足或查詢樣態改變
平均回應時間（P50／P95／P99）P99 惡化代表有少數人體驗極差
併發連線數與連線池使用率接近上限即將拒絕服務
最長執行中交易時間連線洩漏、忘了提交；會拖垮 MVCC 清理
鎖等待與死結次數設計或交易範圍有問題
容量表空間與成長率要能預測「幾個月後會滿」
交易紀錄檔大小暴增通常是長交易或備份失敗
可靠性備份成功率與最後成功時間最重要卻最常沒人看
複寫延遲副本落後多久
還原演練結果備份是否真的可用

23-2　為什麼要看 P95 / P99 而不是平均

📐 平均值會騙人 100 個查詢中，95 個 0.1 秒、5 個 20 秒 → 平均 1.1 秒，看起來還好。
但那 5 個人等了 20 秒，他們就是會打 1999 抱怨的人。

P95 = 1.9 秒、P99 = 20 秒 → 一眼就看出問題。

服務水準應以 P95 或 P99 訂定，不要用平均值。

23-3　告警設計的三個原則

原則說明
可行動每個告警都要對應一個「收到後該做什麼」——否則只是噪音
分級緊急（立即處理）／警告（上班處理）／資訊（不通知，只記錄）
抑制重複同一問題不要連發 200 封信——會導致真正重要的告警被忽略
⚠️ 告警疲勞 每天收到 50 封告警信，第三天起就沒有人在看了。
「告警太多」等於「沒有告警」——寧可少而準。

23-4　容量規劃：用成長率預測

目前 800 GB、每月成長 25 GB、磁碟 1 TB。
剩餘 = 1024 − 800 = 224 GB → 224 ÷ 25 ≈ 9 個月後滿。

公務意義：採購程序至少要 3～6 個月，所以現在就要開始編列預算，不能等到剩一個月才提。
把這個計算寫在簽呈裡，比寫「空間快不夠了」有效十倍。
✅ 深化 23 必背結論 ① 四類指標：效能、併發、容量、可靠性
② 最長執行中交易與備份成功率是最常被漏掉的兩個
③ 服務水準用 P95／P99，不要用平均值
④ 告警要可行動、分級、抑制重複；容量規劃要回推採購前置期

深化 24　資料庫申論的完整答題模板

24-1　「請設計某系統資料庫」的六段結構

🎯 六段模板（含配分建議） 【一】需求與限制（10%）
資料量級、讀寫比、查詢型態、保存年限（檔案法）、個資敏感度、可用性要求

【二】概念與邏輯設計（25%）—— 一定要畫圖或表
實體、關係、基數；主鍵選擇（不用身分證字號當主鍵）；正規化到 3NF 並說明刻意的反正規化

【三】實體設計（20%）
索引策略（含選擇率理由）、分割方式、資料型別（金額不用浮點數）

【四】完整性與交易（15%）
約束條件、外鍵、唯一性約束防重複核給、隔離等級、樂觀鎖

【五】安全與法遵（20%）—— 最能拉開差距
最小權限、稽核軌跡、去識別化、加密與遮罩、時態設計保留歷程、保存與銷毀

【六】維運與風險（10%）
備份與 RPO/RTO、監控指標、容量規劃、退場與資料可攜

24-2　萬用加分句（每題挑三句用）

面向句子
歷程「本表採只增不改設計，更正以新增更正紀錄方式處理，以保留完整稽核軌跡。」
法規版本「補助金額等法規參數採版本化參數表，計算時依案件基準日取用當時版本。」
個資「依最小必要原則，分析用資料表僅保留去識別化欄位，並設最小統計單位門檻。」
重複核給「以資料庫唯一性約束（申請人＋補助年度＋項目）確保不重複核給，不僅依賴程式檢查。」
金額「金額欄位採十進位型別，四捨五入時機依作業要點明定，並建立自動化測試。」
可攜「契約載明資料須可以標準格式完整匯出，避免供應商鎖定。」
備援「依營運衝擊分析訂定 RPO／RTO，並每年辦理還原與切換演練並留存紀錄。」

24-4　本科的一句話總結

🎯 資料庫應用這一科真正在考什麼 不是「你會不會寫 SQL」，而是——
「你能不能設計一個十年後還說得清楚、查得回來、經得起爭訟的資料模型。」

公務資料庫與商業資料庫最大的差別：商業系統可以忘記過去，公務系統不行。
