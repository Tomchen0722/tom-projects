第 1 章　資料庫基本概念與架構

1-1　為什麼需要資料庫

在資料庫出現之前，資料都存在各自的檔案裡（檔案系統 File System），造成五個問題：

檔案系統的問題說明資料庫的解法
資料重複 Redundancy人事室與會計室各存一份員工資料集中儲存、正規化
資料不一致 Inconsistency員工改地址只改了一邊單一資料來源
資料孤立 Isolation格式不同的檔案難以整合查詢統一的資料模型與 SQL
完整性難維護每支程式都要自己檢查由 DBMS 統一以限制條件把關
並行與安全問題多人同時改會出錯、權限難控管交易管理、並行控制、權限機制

1-2　DBMS 的三層綱要架構（ANSI/SPARC）

層級又稱內容使用者
外部層 External檢視層 View Level各使用者看到的資料子集（View）一般使用者、應用程式
概念層 Conceptual邏輯層 Logical Level整個資料庫的邏輯結構（有哪些表、欄位、關係）資料庫管理師 DBA
內部層 Internal實體層 Physical Level資料實際如何儲存（檔案格式、索引結構）DBMS 系統
📐 兩種資料獨立性（必考名詞） 邏輯資料獨立性（Logical Data Independence）
　＝ 改變概念層（例如新增一個欄位）時，外部層（既有的 View 與應用程式）不受影響。
　→ 較難達成

實體資料獨立性（Physical Data Independence）
　＝ 改變內部層（例如換儲存裝置、加索引）時，概念層不受影響。
　→ 較易達成
🧒 白話版：資料獨立性在講什麼

想像一家餐廳。

  • 內部層＝廚房怎麼運作（用瓦斯還是電磁爐、食材放哪個冰箱）
  • 概念層＝完整菜單（餐廳總共供應哪些菜）
  • 外部層＝你手上那份菜單（兒童菜單只印 5 道菜、素食菜單只印素菜）

實體獨立性：廚房換了新爐子，菜單完全不用改 → 容易做到。

邏輯獨立性：菜單新增了 10 道菜，但拿兒童菜單的客人完全無感 → 也做得到，但如果是「把牛肉麵這道菜拆成兩道」，兒童菜單就得跟著改 → 所以比較難。

這個架構的價值是：把改變的影響範圍限制在一層裡面，不會牽一髮動全身。

1-3　DBMS 的功能與人員角色

  • DDL（Data Definition Language）：定義結構 — CREATE、ALTER、DROP、TRUNCATE
  • DML（Data Manipulation Language）：操作資料 — SELECT、INSERT、UPDATE、DELETE
  • DCL（Data Control Language）：權限控制 — GRANT、REVOKE
  • TCL（Transaction Control Language）：交易控制 — COMMIT、ROLLBACK、SAVEPOINT
角色職責
DBA（資料庫管理師）設計綱要、效能調校、備份復原、權限管理、容量規劃
資料庫設計師需求分析、概念設計（ER 圖）、邏輯設計（正規化）
應用程式設計師撰寫存取資料庫的程式
終端使用者透過應用程式或查詢工具使用資料
💡 資料字典（Data Dictionary / 系統目錄） 儲存「關於資料的資料」（Metadata）：有哪些表、欄位型別、索引、限制、權限、統計資訊。
查詢最佳化器就是靠這裡的統計資訊決定執行計畫。常考名詞解釋。

第 2 章　關聯式模型與關聯代數

2-1　基本術語對照（一定要背中英對照）

正式術語俗稱說明
關聯 Relation資料表 Table二維表格
值組 Tuple列 Row / Record一筆資料
屬性 Attribute欄 Column / Field一個欄位
基數 Cardinality—列數（值組個數）
元數 Degree / Arity—欄位個數
值域 Domain—某屬性可取值的範圍

2-2　鍵值（Key）— 必考名詞

鍵值定義例子（學生表）
超鍵 Super Key能唯一識別一筆資料的屬性集合（可含多餘屬性）{學號}、{學號, 姓名}、{身分證字號, 姓名}
候選鍵 Candidate Key最小的超鍵（拿掉任一屬性就不唯一）{學號}、{身分證字號}
主鍵 Primary Key從候選鍵中選定一個；不可為 NULL、不可重複{學號}
替代鍵 Alternate Key沒被選為主鍵的候選鍵{身分證字號}
外鍵 Foreign Key指向另一表主鍵的屬性，用於建立關聯選課表的「學號」
複合鍵 Composite Key由兩個以上屬性組成的鍵選課表的 {學號, 課號}
🧒 超鍵 vs 候選鍵，一句話分清楚

超鍵＝「夠用就行，可以帶多餘的東西」。
{身分證字號, 姓名, 生日} 當然能唯一識別一個人，所以它是超鍵——但姓名和生日是多餘的。

候選鍵＝「剛剛好，一個都不能少」。
{身分證字號} 就夠了，再拿掉就沒東西了 → 這是候選鍵。

所以：候選鍵是「極小的超鍵」，每個候選鍵都是超鍵，但超鍵不一定是候選鍵。

2-3　完整性限制（Integrity Constraints）— 常考

完整性規則SQL 實作
實體完整性
Entity Integrity		主鍵不可為 NULL、不可重複PRIMARY KEY
參考完整性
Referential Integrity		外鍵的值必須存在於被參考表的主鍵中，或為 NULLFOREIGN KEY ... REFERENCES
值域完整性
Domain Integrity		欄位值須符合定義的型別與範圍CHECK、NOT NULL、資料型別
使用者定義完整性依業務規則自訂CHECK、TRIGGER、預存程序

參考完整性的處理動作（刪除／更新父表資料時）

動作行為使用時機
CASCADE連帶刪除／更新子表資料子資料無獨立意義（如訂單明細隨訂單刪除）
SET NULL子表外鍵設為 NULL子資料仍有意義（如員工的部門被裁撤）
SET DEFAULT設為預設值有合理的預設歸屬
RESTRICT / NO ACTION拒絕該操作預設行為，最安全

2-4　關聯代數（Relational Algebra）

SQL 的理論基礎。分為一元運算與二元運算。

運算符號意義對應 SQL
選擇 Selectionσ（sigma）依條件挑出符合的列（橫向切）WHERE
投影 Projectionπ（pi）挑出指定的欄（縱向切），會自動去除重複SELECT DISTINCT
更名 Renameρ（rho）改變關聯或屬性名稱AS
聯集 Union∪兩表相加去重（需相容）UNION
差集 Difference−在 A 不在 BEXCEPT / MINUS
交集 Intersection∩同時在 A 與 BINTERSECT
笛卡兒積 Cartesian Product×每一列都與另一表每一列配對CROSS JOIN
join Join⋈依條件結合兩表JOIN ... ON
除法 Division÷「對所有的…」查詢需用 NOT EXISTS 兩層改寫
💡 五個基本運算（Primitive Operations） σ、π、∪、−、× 是基本運算，其餘（∩、⋈、÷）都可以由這五個推導出來。
例：A ∩ B = A − (A − B)；A ⋈ B = σ條件(A × B)
這是常見的名詞題與觀念題。
⚠️ 除法（Division）— 最難也最常考 「找出選修了所有課程的學生」這類「對所有…」的查詢，就是除法。

SQL 改寫模板（雙重否定）：
「選修了所有課的學生」＝「不存在一門課，該學生沒有選」
SELECT S.學號 FROM 學生 S
WHERE NOT EXISTS (
    SELECT * FROM 課程 C
    WHERE NOT EXISTS (
        SELECT * FROM 選課 E
        WHERE E.學號 = S.學號 AND E.課號 = C.課號
    )
);
這個模板背下來，考到直接套。

第 3 章　ER 模型與轉換

3-1　ER 圖的組成元素

元素符號說明
實體 Entity矩形可獨立識別的事物（學生、課程）
弱實體 Weak Entity雙線矩形無法獨立存在，需依附強實體（如「眷屬」依附「員工」）
屬性 Attribute橢圓實體的特性
鍵屬性底線主鍵
複合屬性橢圓下再接橢圓地址 → 縣市 + 路名 + 號碼
多值屬性雙線橢圓一個人有多支電話
衍生屬性虛線橢圓年齡（由生日算出）
關係 Relationship菱形實體之間的關聯（學生「選修」課程）

3-2　基數（Cardinality）與參與限制

關係型態例子轉換為關聯表的做法
1 : 1員工 ↔ 停車位把任一方的主鍵放進另一方當外鍵（建議放在參與度高的那一方，減少 NULL）
1 : N部門 ↔ 員工把「1」那方的主鍵，放到「N」那方當外鍵
M : N學生 ↔ 課程必須另建一張關聯表，主鍵為兩方主鍵組成的複合鍵
🧒 為什麼 M:N 一定要多一張表

一個學生修很多課，一門課也有很多學生。如果硬要把課號塞進學生表：

學號 | 姓名 | 課號 → 一個學生修 5 門課，就要重複 5 列，姓名重複 5 次（資料重複）。

如果塞成 學號 | 姓名 | 課號1 | 課號2 | 課號3 → 更糟：欄位數固定，修第 4 門課就爆了，而且違反第一正規化。

唯一正確解法：拆出「選課」表，每一列代表「某學生修某課」這一件事：

學生(學號, 姓名, 系所)
課程(課號, 課名, 學分)
選課(學號, 課號, 成績)   ← 複合主鍵

注意「成績」這個欄位——它既不屬於學生也不屬於課程，而是屬於「這段關係」。這種欄位叫關係屬性，是 M:N 必須拆表的另一個理由。

參與限制（Participation Constraint）

  • 全部參與（Total）：雙線連接，該實體的每一筆都必須參與此關係（如：每個員工都必須屬於某個部門）。
  • 部分參與（Partial）：單線連接，可以不參與（如：不是每個員工都是主管）。

3-3　EER（延伸 ER）概念

概念說明
特化 Specialization由上而下：從「員工」細分出「教師」「行政人員」
一般化 Generalization由下而上：把「汽車」「機車」歸納成「車輛」
互斥 Disjoint (d)一個實體只能屬於一個子類
重疊 Overlapping (o)可同時屬於多個子類
聚合 Aggregation把一個「關係」當成實體，再與其他實體建立關係

3-4　ER 圖轉關聯表的完整步驟（申論常考）

📐 七個步驟 1. 每個強實體 → 一張表，選定主鍵
2. 每個弱實體 → 一張表，主鍵 = 強實體主鍵 + 部分鍵（Partial Key）
3. 1:1 關係 → 把一方主鍵當外鍵放到另一方（選參與度高者）
4. 1:N 關係 → 「1」方主鍵放到「N」方當外鍵
5. M:N 關係 → 建新表，主鍵 = 兩方主鍵之複合鍵，並加入關係屬性
6. 多值屬性 → 另建一張表（原表主鍵 + 該屬性，兩者組成複合主鍵）
7. 三元以上關係 → 建新表，主鍵 = 三方主鍵之複合鍵
申論題若給你一段業務描述要你「畫 ER 圖並轉換為關聯表」，務必兩者都畫／都寫，並在每張表底下標明主鍵（底線）與外鍵（標註 FK）。
這種題目的分數大多給在「M:N 有沒有正確拆表」與「外鍵方向對不對」。

第 4 章　函數相依與正規化（年年考）

4-1　函數相依（Functional Dependency, FD）

定義：X → Y 表示「知道 X 就能唯一決定 Y」。
X 稱為決定因素（Determinant）。

例：學號 → 姓名（知道學號就知道姓名）
　　姓名 → 學號（同名同姓的人可能不只一個）

三種特殊的函數相依（正規化的判斷關鍵）

類型定義例子違反哪個正規化
部分相依
Partial Dependency		 非鍵屬性只相依於複合主鍵的一部分 (學號, 課號) → 學生姓名，但其實 學號 → 學生姓名 就夠了 2NF
遞移相依
Transitive Dependency		 X → Y、Y → Z，導致 X → Z（Y 非鍵） 學號 → 系所代碼 → 系所名稱 3NF
非鍵決定因素 決定因素不是超鍵 教師 → 課程（教師不是候選鍵） BCNF

Armstrong 公理（推導 FD 的規則）

公理規則
反身律 Reflexivity若 Y ⊆ X，則 X → Y
擴充律 Augmentation若 X → Y，則 XZ → YZ
遞移律 Transitivity若 X → Y 且 Y → Z，則 X → Z
聯合律 Union若 X → Y 且 X → Z，則 X → YZ
分解律 Decomposition若 X → YZ，則 X → Y 且 X → Z
假遞移律 Pseudotransitivity若 X → Y 且 WY → Z，則 WX → Z

前三個是基本公理，後三個可由前三個推導。

屬性閉包（Attribute Closure）— 找候選鍵的工具

📐 求 X⁺ 的步驟 1. 令 X⁺ = X
2. 反覆檢查所有 FD：若某個 FD 的左邊 ⊆ X⁺，就把右邊加進 X⁺
3. 直到 X⁺ 不再變化

判斷候選鍵：若 X⁺ = 所有屬性，且 X 的任何真子集閉包都不等於所有屬性 → X 是候選鍵

範例：R(A, B, C, D)，FD = { A→B, B→C, C→D }

求 A⁺：
  A⁺ = {A}
  A→B  → A⁺ = {A, B}
  B→C  → A⁺ = {A, B, C}
  C→D  → A⁺ = {A, B, C, D}  ← 包含全部屬性
→ A 是候選鍵

求 B⁺ = {B, C, D}  ← 缺 A，不是候選鍵
求 C⁺ = {C, D}
求 D⁺ = {D}
結論：唯一候選鍵為 {A}
💡 快速找候選鍵的技巧 1. 只出現在 FD 左邊（從不出現在右邊）的屬性，一定要在候選鍵裡
2. 兩邊都沒出現的屬性，也一定要在候選鍵裡
3. 先把這些必要屬性湊起來求閉包，若已涵蓋全部屬性 → 就是唯一候選鍵
4. 若還不夠，再逐一加入其他屬性測試

這個技巧能省下大量時間，考場上非常好用。

4-2　正規化各階段（核心考點）

正規化要求消除的問題
1NF所有屬性值皆為單元值（Atomic），無重複群組多值欄位、重複欄位
2NF符合 1NF，且無部分相依（非鍵屬性須完全相依於主鍵）部分相依
3NF符合 2NF，且無遞移相依遞移相依
BCNF每個 FD 的決定因素都必須是超鍵非鍵決定因素造成的異常
4NF符合 BCNF，且無多值相依（MVD）多值相依
5NF（PJNF）無「連接相依（Join Dependency）」需三張以上表才能無損分解的情形
💡 口訣 1NF 去重複群、2NF 去部分依、3NF 去遞移依、BCNF 決定因素皆為超鍵。
考試時只要記住「2NF 只跟複合主鍵有關」——若主鍵是單一屬性，必定已符合 2NF（因為不可能部分相依）。這是超好用的判斷捷徑。

4-3　正規化實作範例（一定要會的題型）

假設有一張未正規化的「選課成績表」：

學號姓名系代碼系名稱課號課名學分成績
S01王小明D01資訊管理系C01資料庫385
S01王小明D01資訊管理系C02演算法378
S02李小華D01資訊管理系C01資料庫390

步驟 0：找出函數相依與主鍵

FD1: 學號 → 姓名, 系代碼
FD2: 系代碼 → 系名稱
FD3: 課號 → 課名, 學分
FD4: (學號, 課號) → 成績

主鍵 = (學號, 課號)

步驟 1：檢查 1NF

所有欄位都是單元值，已符合 1NF。（若原表有「電話：0912-xxx / 0922-xxx」這種欄位就違反 1NF。）

步驟 2：消除部分相依 → 2NF

主鍵是複合鍵 (學號, 課號)，檢查每個非鍵屬性：

  • 姓名、系代碼、系名稱 → 只依賴學號（部分相依 ❌）
  • 課名、學分 → 只依賴課號（部分相依 ❌）
  • 成績 → 依賴完整的 (學號, 課號) ✅
分解為三張表：
學生(學號, 姓名, 系代碼, 系名稱)
課程(課號, 課名, 學分)
選課(學號, 課號, 成績)

步驟 3：消除遞移相依 → 3NF

學生表中：學號 → 系代碼 → 系名稱，系名稱遞移相依於學號 ❌

最終 3NF 結果（四張表）：
學生(學號, 姓名, 系代碼)      系代碼為 FK
系所(系代碼, 系名稱)
課程(課號, 課名, 學分)
選課(學號, 課號, 成績)        學號、課號皆為 FK

步驟 4：檢查 BCNF

逐一檢查每張表的所有 FD，決定因素是否都是超鍵：

  • 學生表：學號 → 姓名, 系代碼。學號是主鍵 ✅
  • 系所表：系代碼 → 系名稱。系代碼是主鍵 ✅
  • 課程表：課號 → 課名, 學分。課號是主鍵 ✅
  • 選課表：(學號, 課號) → 成績。是主鍵 ✅

四張表皆符合 BCNF。

4-4　正規化解決的三種異常（申論必寫）

異常問題原表的例子
新增異常
Insertion Anomaly		想新增某資料卻被迫要有其他不相關資料新開一門「機器學習」課，但還沒人選 → 無法新增（因為主鍵含學號，不能為 NULL）
刪除異常
Deletion Anomaly		刪除某筆資料會連帶失去其他資訊李小華退選 C01，若他只修這一門 → 刪掉後連他是資管系的資訊都消失了
修改異常
Update Anomaly		同一資訊存多份，改一處其他沒改到就不一致系名稱從「資訊管理系」改為「資訊管理學系」→ 要改所有列，漏改就資料不一致

4-5　BCNF 與 3NF 的差異（進階考點）

🧒 什麼情況 3NF 不等於 BCNF

假設「教室排課表」：(課程, 時段, 教室)

  • FD1：(課程, 時段) → 教室（一門課在某時段固定在一間教室）
  • FD2：教室 → 課程（假設每間教室是專科教室，只上一種課）

候選鍵有兩個：{課程, 時段} 和 {教室, 時段}。

符合 3NF 嗎？符合。因為所有屬性都是鍵屬性（都在某個候選鍵裡），沒有「非鍵屬性的遞移相依」。

符合 BCNF 嗎？不符合。因為 FD2 的決定因素「教室」不是超鍵（單看教室無法決定時段）。

所以：BCNF 比 3NF 嚴格。差別只出現在「有多個重疊的複合候選鍵」的情況——這也是為什麼實務上 3NF 通常就夠用，因為那種情況不常見。

⚠️ BCNF 的代價：可能失去相依保存性 分解關聯表時有兩個理想性質：
(1) 無損分解（Lossless Join）：分解後再 JOIN 回去，資料不會多也不會少。
　判斷法：分解成 R1、R2 時，若 (R1 ∩ R2) → R1 或 (R1 ∩ R2) → R2 成立，即為無損分解。
(2) 相依保存（Dependency Preservation）：原本的所有 FD 在分解後的各表中仍能各自檢查。

關鍵結論：
‧ 3NF 一定能同時做到「無損分解」與「相依保存」
‧ BCNF 一定能做到無損分解，但可能無法保存相依

這是申論題「請說明為何實務上常以 3NF 為目標而非 BCNF」的標準答案。

4-6　反正規化（Denormalization）

正規化不是越高越好。分得太細會造成大量 JOIN，查詢變慢。

手法說明代價
合併表格把常一起查詢的兩張表合併資料重複
加入衍生欄位如訂單表直接存「總金額」而非每次算需維護一致性
重複欄位訂單明細直接存商品名稱（避免 JOIN 商品表）商品改名時不一致
預先彙總表建立月報表統計表需定期更新
💡 申論寫法 「正規化以消除資料異常、確保一致性為目標，適用於交易處理（OLTP）系統；
反正規化則以提升查詢效能為目標，常用於報表與分析（OLAP）系統。
實務上多以 3NF 為基準，再依效能瓶頸有選擇性地反正規化，並須建立同步機制與定期稽核以維持資料一致性。」
