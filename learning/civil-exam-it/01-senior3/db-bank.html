✅ 第一部分：觀念選擇題（45 題）

A. 基本概念與關聯模型（第 1～9 題）

1架構
下列關於「實體資料獨立性」之敘述，何者正確？
  • (A) 改變概念層時，外部層不受影響
  • (B) 改變內部層（如新增索引、更換儲存裝置）時，概念層不受影響
  • (C) 改變外部層時，概念層不受影響
  • (D) 資料庫與應用程式必須同時修改
看詳解
答案：(B)
實體資料獨立性 = 內部層改變不影響概念層（較易達成）。
邏輯資料獨立性 = 概念層改變不影響外部層（較難達成，即選項 A）。

記憶法：「實體」對應最底層（內部層），「邏輯」對應中間層（概念層）。由下往上不影響。
2鍵值
關聯 R(A, B, C, D) 中，{A, B} 可唯一識別每一筆資料，且 {A} 亦可唯一識別。下列敘述何者錯誤？
  • (A) {A, B} 是超鍵　(B) {A} 是候選鍵　(C) {A, B} 是候選鍵　(D) {A, B, C} 是超鍵
看詳解
答案：(C)
候選鍵必須是最小的超鍵。既然 {A} 單獨就能識別，{A, B} 就含有多餘屬性 B，因此它是超鍵但不是候選鍵。

(A)(D) 正確：任何包含候選鍵的屬性集合都是超鍵。
3完整性
「外鍵的值必須存在於被參考表的主鍵中，或為 NULL」是何種完整性？
  • (A) 實體完整性　(B) 參考完整性　(C) 值域完整性　(D) 使用者定義完整性
看詳解
答案：(B) 參考完整性（Referential Integrity）

對照記憶：
‧ 實體完整性 → 主鍵不可 NULL、不可重複
‧ 參考完整性 → 外鍵須存在於被參考主鍵中
‧ 值域完整性 → 欄位值須符合型別與 CHECK 條件
4關聯代數
關聯代數中，下列何者不屬於五個基本運算（Primitive Operations）？
  • (A) 選擇 σ　(B) 投影 π　(C) 交集 ∩　(D) 差集 −
看詳解
答案：(C) 交集
五個基本運算為 σ（選擇）、π（投影）、∪（聯集）、−（差集）、×（笛卡兒積）。

交集可由差集推導：A ∩ B = A − (A − B)
join 可由笛卡兒積 + 選擇推導：A ⋈ B = σ條件(A × B)
5關聯代數
關聯代數運算 π姓名(σ薪資>50000(員工)) 對應的 SQL 為？
  • (A) SELECT DISTINCT 姓名 FROM 員工 WHERE 薪資 > 50000
  • (B) SELECT 薪資 FROM 員工 WHERE 姓名 > 50000
  • (C) SELECT 姓名, 薪資 FROM 員工
  • (D) SELECT COUNT(姓名) FROM 員工 WHERE 薪資 > 50000
看詳解
答案：(A)
σ（選擇）→ WHERE；π（投影）→ SELECT 欄位。

關鍵細節：關聯代數的投影運算會自動去除重複值（因為關聯是「集合」），所以嚴格對應的 SQL 需加 DISTINCT。
SQL 的 SELECT 預設不去重（SQL 處理的是「多重集合 Bag」），這是理論與實作的著名差異，也是常考點。
6ER
將 M:N 關係轉換為關聯表時，正確做法為？
  • (A) 把一方主鍵放入另一方當外鍵
  • (B) 建立新表，主鍵為雙方主鍵組成之複合鍵
  • (C) 合併為一張表
  • (D) 各自獨立，無須處理
看詳解
答案：(B)
M:N 必須另建關聯表（又稱 Bridge Table / Junction Table）。

理由有兩個：
1. 若把課號塞進學生表，一個學生修 5 門課就要重複 5 列 → 資料重複
2. 關係本身可能有屬性（如選課的「成績」），這種屬性既不屬於學生也不屬於課程，只能放在關聯表

(A) 是 1:1 與 1:N 的做法（1:N 時放在「N」那一方）。
7ER
ER 圖中以雙線橢圓表示的元素為？
  • (A) 弱實體　(B) 多值屬性　(C) 衍生屬性　(D) 複合屬性
看詳解
答案：(B) 多值屬性（Multivalued Attribute）

符號速記：
‧ 矩形 = 實體；雙線矩形 = 弱實體
‧ 橢圓 = 屬性；雙線橢圓 = 多值屬性；虛線橢圓 = 衍生屬性
‧ 菱形 = 關係；雙線菱形 = 識別關係（連接弱實體）
‧ 底線 = 主鍵；虛線底線 = 部分鍵（弱實體用）
8參考完整性
部門表被刪除一筆資料時，希望員工表中對應的「部門代碼」自動設為 NULL，應使用何種設定？
  • (A) ON DELETE CASCADE　(B) ON DELETE SET NULL　(C) ON DELETE RESTRICT　(D) ON DELETE NO ACTION
看詳解
答案：(B) ON DELETE SET NULL

四種行為的選用時機：
‧ CASCADE：子資料無獨立意義（訂單刪除 → 訂單明細一起刪）
‧ SET NULL：子資料仍有意義（部門裁撤 → 員工還在，只是暫無部門）
‧ RESTRICT / NO ACTION：拒絕該操作（預設值，最安全）

實務提醒：CASCADE 很危險，一個 DELETE 可能連鎖刪掉大量資料。公部門系統多採 RESTRICT，改以「邏輯刪除」（設定失效日期）處理。
9概念
儲存「有哪些表、欄位型別、索引、權限與統計資訊」的是？
  • (A) 資料倉儲　(B) 資料字典（系統目錄）　(C) 交易日誌　(D) 檢視表
看詳解
答案：(B) 資料字典 / 系統目錄（Data Dictionary / System Catalog）
存放的是Metadata（描述資料的資料）。

重要延伸：成本式最佳化器（CBO）就是靠這裡的統計資訊決定執行計畫。統計資訊過期會導致最佳化器誤判，是實務上效能突然變差的常見原因。

B. 正規化（第 10～19 題）

10正規化
關聯 R(學號, 課號, 學生姓名, 成績)，主鍵為 (學號, 課號)，且 學號 → 學生姓名。此關聯符合哪一階正規化？
  • (A) 僅 1NF　(B) 2NF 但非 3NF　(C) 3NF 但非 BCNF　(D) BCNF
看詳解
答案：(A) 僅符合 1NF
「學生姓名」只相依於主鍵的一部分（學號），屬於部分相依 → 違反 2NF。

分解方式：
學生(學號, 學生姓名)
選課(學號, 課號, 成績)

判斷捷徑：只要主鍵是複合鍵，第一件事就是檢查每個非鍵屬性「是否依賴完整的主鍵」。
11正規化
關聯 R(員工編號, 姓名, 部門代碼, 部門名稱)，主鍵為員工編號，且 部門代碼 → 部門名稱。此關聯違反哪一階正規化？
  • (A) 1NF　(B) 2NF　(C) 3NF　(D) 未違反任何正規化
看詳解
答案：(C) 違反 3NF
存在遞移相依：員工編號 → 部門代碼 → 部門名稱。

為什麼不是違反 2NF？因為主鍵是單一屬性（員工編號），不可能有部分相依 → 單一屬性主鍵必定符合 2NF。這是超好用的判斷捷徑。

分解：
員工(員工編號, 姓名, 部門代碼)
部門(部門代碼, 部門名稱)
12正規化
關於 3NF 與 BCNF，下列敘述何者正確？
  • (A) BCNF 一定符合 3NF，反之不然
  • (B) 3NF 一定符合 BCNF
  • (C) 兩者完全等價
  • (D) BCNF 可保證相依保存，3NF 不行
看詳解
答案：(A)
BCNF 比 3NF 嚴格：BCNF ⊂ 3NF ⊂ 2NF ⊂ 1NF。

(D) 剛好講反了，這是高頻陷阱：
‧ 3NF：一定能達成「無損分解 + 相依保存」
‧ BCNF：一定能無損分解，但可能無法保存相依

這正是實務上常以 3NF 為目標的原因。
13正規化
R(A, B, C, D)，FD = { A→B, B→C, C→D }。R 的候選鍵為？
  • (A) {A}　(B) {A, B}　(C) {D}　(D) {A, B, C, D}
看詳解
答案：(A) {A}

求屬性閉包：
A⁺ = {A} → 用 A→B → {A,B} → 用 B→C → {A,B,C} → 用 C→D → {A,B,C,D} ✅ 涵蓋全部
B⁺ = {B,C,D}（缺 A）❌
C⁺ = {C,D} ❌　D⁺ = {D} ❌

快速判斷技巧：只出現在 FD 左邊、從不出現在右邊的屬性，一定要在候選鍵裡。此處 A 從未出現在任何 FD 的右邊 → A 必在候選鍵中。先算 A⁺ 發現已涵蓋全部 → {A} 就是唯一候選鍵。
14正規化
將 R(A,B,C) 分解為 R1(A,B) 與 R2(B,C)，若欲確保為無損分解，下列何者為充分條件？
  • (A) A → C 成立　(B) B → A 或 B → C 成立　(C) C → A 成立　(D) 無論如何都是無損分解
看詳解
答案：(B)
無損分解判斷法：分解為 R1、R2 時，若 (R1 ∩ R2) → R1 或 (R1 ∩ R2) → R2 成立，即為無損分解。

此處 R1 ∩ R2 = {B}，故需 B → A（決定 R1 其餘屬性）或 B → C（決定 R2 其餘屬性）。

(D) 錯：若共同屬性無法決定任一方，JOIN 回去會產生虛假值組（Spurious Tuples），資料變多了。
15正規化
下列何者不是正規化所要消除的資料異常？
  • (A) 新增異常　(B) 刪除異常　(C) 修改異常　(D) 死結
看詳解
答案：(D) 死結
死結是並行控制的問題，與正規化（結構設計）無關。

正規化消除的是三種異常：
‧ 新增異常：想新增某資料卻因主鍵不完整而無法新增
‧ 刪除異常：刪掉一筆連帶失去其他不相關的資訊
‧ 修改異常：同一資訊存多份，改一處造成不一致
16正規化
關聯 R(學生, 社團, 電話)，其中一個學生可參加多個社團、也可有多支電話，社團與電話彼此獨立。此關聯應正規化至第幾階才能消除異常？
  • (A) 2NF　(B) 3NF　(C) BCNF　(D) 4NF
看詳解
答案：(D) 4NF
這是典型的多值相依（Multivalued Dependency, MVD）問題。

因為社團與電話彼此無關，若放在同一張表，一個學生參加 3 個社團、有 2 支電話，就必須存 3×2 = 6 列（笛卡兒積式的重複）。

主鍵是 (學生, 社團, 電話) 三者全部，所以沒有非鍵屬性 → 已符合 BCNF，但異常仍在。

4NF 分解：
學生社團(學生, 社團)
學生電話(學生, 電話)
17正規化
下列何者不是反正規化（Denormalization）的目的？
  • (A) 減少 JOIN 次數　(B) 提升查詢效能　(C) 消除資料重複　(D) 加速報表產出
看詳解
答案：(C)
「消除資料重複」是正規化的目的，反正規化刻意接受資料重複來換取查詢效能。

取捨關係：
‧ 正規化 → 一致性好、寫入快、查詢需大量 JOIN（適合 OLTP）
‧ 反正規化 → 查詢快、需維護一致性（適合 OLAP／報表）
18正規化
關於 Armstrong 公理，下列何者為基本公理（其餘可由此推導）？
  • (A) 聯合律、分解律、假遞移律
  • (B) 反身律、擴充律、遞移律
  • (C) 反身律、聯合律、分解律
  • (D) 擴充律、遞移律、假遞移律
看詳解
答案：(B) 反身律、擴充律、遞移律

‧ 反身律（Reflexivity）：Y ⊆ X → X → Y
‧ 擴充律（Augmentation）：X → Y → XZ → YZ
‧ 遞移律（Transitivity）：X → Y、Y → Z → X → Z

聯合律、分解律、假遞移律皆可由上述三者推導，屬衍生規則。
19正規化
某關聯所有屬性都是候選鍵的成員（即無非鍵屬性），下列敘述何者正確？
  • (A) 一定符合 BCNF
  • (B) 一定符合 3NF，但不一定符合 BCNF
  • (C) 一定違反 2NF
  • (D) 一定符合 4NF
看詳解
答案：(B)
3NF 的定義只管「非鍵屬性不可遞移相依」。若沒有非鍵屬性，3NF 自動成立。

但 BCNF 要求所有 FD 的決定因素都是超鍵，這與屬性是否為鍵成員無關。

經典反例：R(課程, 時段, 教室)，FD：(課程,時段)→教室、教室→課程。
候選鍵為 {課程,時段} 與 {教室,時段}，三個屬性都是鍵成員 → 符合 3NF；
但「教室」不是超鍵 → 違反 BCNF。

(D) 錯：第 16 題的例子（學生、社團、電話）就是全屬性為鍵但違反 4NF。

21SQL
下列 SQL 為何會發生錯誤？
SELECT 部門, COUNT(*) FROM 員工 WHERE COUNT(*) > 5 GROUP BY 部門;
  • (A) GROUP BY 位置錯誤
  • (B) WHERE 在 GROUP BY 之前執行，此時聚合函數尚未計算
  • (C) COUNT(*) 語法錯誤
  • (D) 缺少 ORDER BY
看詳解
答案：(B)
SQL 執行順序：FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY。
WHERE 在 GROUP BY 之前，那時還沒分組，聚合函數不存在。

正確寫法：
SELECT 部門, COUNT(*) FROM 員工 GROUP BY 部門 HAVING COUNT(*) > 5;

一句話：WHERE 過濾「列」、HAVING 過濾「組」。
22SQL
員工表有 10 筆資料，其中「獎金」欄位有 4 筆為 NULL。SELECT COUNT(*), COUNT(獎金) FROM 員工; 的結果為？
  • (A) 10, 10　(B) 10, 6　(C) 6, 6　(D) 6, 10
看詳解
答案：(B) 10, 6
COUNT(*) 數列數，不管內容有無 NULL → 10。
COUNT(欄位) 只數該欄非 NULL 的個數 → 10 − 4 = 6。

延伸陷阱：AVG(獎金) 的分母是 6 而非 10。若業務上 NULL 應視為 0，必須寫 AVG(COALESCE(獎金, 0))。
23SQL
若子查詢 SELECT 部門代碼 FROM 部門 的結果中含有 NULL，則 SELECT * FROM 員工 WHERE 部門代碼 NOT IN (子查詢) 的結果為？
  • (A) 正常回傳不符合的員工
  • (B) 回傳空集合
  • (C) 回傳全部員工
  • (D) 語法錯誤
看詳解
答案：(B) 回傳空集合

x NOT IN (1, 2, NULL) 等價於 x <> 1 AND x <> 2 AND x <> NULL。
而 x <> NULL 的結果是 UNKNOWN（三值邏輯），TRUE AND UNKNOWN = UNKNOWN，永遠不會是 TRUE → 沒有任何列符合。

對策：
1. 改用 NOT EXISTS（不受 NULL 影響）
2. 子查詢加 WHERE 部門代碼 IS NOT NULL

這是 SQL 三值邏輯最著名的陷阱，也是很好的申論素材。
24SQL
要找出「有部門資料但沒有任何員工」的部門，下列寫法何者錯誤？
  • (A) SELECT d.* FROM 部門 d LEFT JOIN 員工 e ON d.代碼=e.部門代碼 WHERE e.員工編號 IS NULL
  • (B) SELECT * FROM 部門 d WHERE NOT EXISTS (SELECT 1 FROM 員工 e WHERE e.部門代碼=d.代碼)
  • (C) SELECT d.* FROM 部門 d INNER JOIN 員工 e ON d.代碼=e.部門代碼 WHERE e.員工編號 IS NULL
  • (D) SELECT * FROM 部門 WHERE 代碼 NOT IN (SELECT 部門代碼 FROM 員工 WHERE 部門代碼 IS NOT NULL)
看詳解
答案：(C)
INNER JOIN 只會回傳「兩邊都有對應」的列。既然有對應，員工編號就不可能是 NULL（除非該欄位本身允許 NULL，但它是主鍵）→ 結果永遠為空。

關鍵觀念：「找出沒有對應資料的列」必須用 OUTER JOIN（讓沒對應的也留下來，再用 IS NULL 篩出），或用 NOT EXISTS。
LEFT JOIN + IS NULL 是找差集的經典技巧。
25SQL
A 表有 5 列、B 表有 3 列，SELECT * FROM A CROSS JOIN B; 回傳幾列？
  • (A) 3　(B) 5　(C) 8　(D) 15
看詳解
答案：(D) 15
CROSS JOIN 是笛卡兒積，5 × 3 = 15。

要查詢「每個部門薪資最高的員工」，下列哪種寫法最不易出錯？

  • (B) 使用窗函數 ROW_NUMBER() OVER (PARTITION BY 部門 ORDER BY 薪資 DESC) 再取 = 1
  • (C) SELECT 部門, 姓名, 薪資 FROM 員工 WHERE 薪資 = MAX(薪資)
  • (D) SELECT DISTINCT 部門, MAX(薪資) FROM 員工
看詳解
答案：(B)

(A) 是經典錯誤：「姓名」既不在 GROUP BY 也沒被聚合 → 標準 SQL 報錯；MySQL 舊版會回傳不確定的姓名（可能不是最高薪那個人），是很難發現的 bug。
(C) 錯：WHERE 不能用聚合函數。
(D) 錯：DISTINCT 不能解決 GROUP BY 的問題，且沒有分組依據。

正確寫法： 
SELECT 部門, 姓名, 薪資 FROM (
  SELECT 部門, 姓名, 薪資,
         ROW_NUMBER() OVER (PARTITION BY 部門
                            ORDER BY 薪資 DESC) AS rn
  FROM 員工
) t WHERE rn = 1;
若要「並列最高薪都列出」，把 ROW_NUMBER() 換成 RANK()。

34交易
「T1 修改 X 但尚未 COMMIT，T2 讀取到該值，隨後 T1 ROLLBACK」屬於何種並行問題？
  • (A) 遺失更新　(B) 髒讀　(C) 不可重複讀　(D) 幻讀
看詳解
答案：(B) 髒讀（Dirty Read）
T2 讀到了「從未真正存在過」的資料（因為 T1 回復了）。

四種問題的一句話區辨：
‧ 遺失更新：我的修改被覆蓋
‧ 髒讀：讀到未提交的資料
‧ 不可重複讀：同一列讀兩次，值不同（UPDATE 造成）
‧ 幻讀：同一查詢讀兩次，列數不同（INSERT/DELETE 造成）
35交易

  • (A) Read Uncommitted　(B) Read Committed　(C) Repeatable Read　(D) Serializable
看詳解
答案：(C) Repeatable Read

隔離等級髒讀不可重複讀幻讀

Read Committed✅❌❌
Repeatable Read✅✅❌

原因：Repeatable Read 鎖住了「已讀取的列」，但無法阻止別人新增符合條件的新列。要防幻讀需範圍鎖（Range Lock），即 Serializable。
36交易
關於兩階段鎖定協定（2PL），下列敘述何者正確？
  • (A) 可保證可序列化，且可避免死結
  • (B) 可保證可序列化，但無法避免死結
  • (C) 無法保證可序列化
  • (D) 成長階段可同時加鎖與解鎖
看詳解
答案：(B)
2PL 分為成長階段（只加鎖）與收縮階段（只解鎖），可保證可序列化，但不保證無死結。

反例：T1 鎖 A 後要鎖 B；T2 鎖 B 後要鎖 A → 兩者都符合 2PL，但互相等待形成死結。

補充：嚴格 2PL（Strict 2PL）把所有 X 鎖保留到交易結束才釋放，可避免連鎖回復（Cascading Rollback），是實務常用做法。
37交易
下列何者不是死結成立的必要條件？
  • (A) 互斥　(B) 持有並等待　(C) 可搶奪　(D) 循環等待
看詳解
答案：(C)
死結四條件是「互斥、持有並等待、不可搶奪、循環等待」。
如果資源可以被搶奪，死結就不會形成（可以強行拿走化解僵局）。

破壞任一條件即可避免死結：
‧ 破壞「持有並等待」→ 要求一次取得所有資源
‧ 破壞「不可搶奪」→ 允許回復某交易
‧ 破壞「循環等待」→ 規定所有交易依相同順序取鎖（實務最常用）
38交易
保障交易「持久性（Durability）」的主要機制為？
  • (A) Undo Log　(B) Redo Log 與預寫式日誌（WAL）　(C) 共享鎖　(D) 兩階段鎖定
看詳解
答案：(B)

對應關係要記牢：
‧ 原子性（A） ← Undo Log（回復未完成的交易）
‧ 持久性（D） ← Redo Log + WAL（重做已提交的交易）
‧ 隔離性（I） ← 鎖定機制、MVCC

下列關於叢集索引（Clustered Index）之敘述，何者正確？
  • (A) 一張表可建立多個叢集索引
  • (B) 索引順序即為資料實體排列順序，一張表只能有一個
  • (C) 只能建立在文字型別欄位上
  • (D) 不支援範圍查詢
看詳解
答案：(B)
因為資料只能有一種實體排列順序，所以叢集索引一張表最多一個（通常就是主鍵）。

(D) 恰好相反：叢集索引的範圍查詢效能最好，因為符合條件的資料在磁碟上是相鄰的，可以循序讀取。
40索引
已建立索引 INDEX(部門代碼, 職稱, 到職日)，下列哪個查詢無法有效使用該索引？
  • (A) WHERE 部門代碼 = 'D01'
  • (B) WHERE 部門代碼 = 'D01' AND 職稱 = '科員'
  • (C) WHERE 職稱 = '科員'
  • (D) WHERE 部門代碼 = 'D01' AND 職稱 = '科員' AND 到職日 > '2020-01-01'
看詳解
答案：(C)
最左前綴原則（Leftmost Prefix）：複合索引必須從最左邊的欄位開始用，中間不能跳過。

(C) 跳過了「部門代碼」直接用「職稱」→ 無法定位起點 → 索引失效（部分 DBMS 可能做索引掃描，但效益大減）。

比喻：電話簿按「姓 → 名」排序。知道姓「陳」可快速定位；只知道名叫「小明」，還是得整本翻。
41索引
下列哪個 WHERE 條件會導致「到職日」欄位上的索引失效？
  • (A) WHERE 到職日 >= '2024-01-01'
  • (B) WHERE YEAR(到職日) = 2024
  • (C) WHERE 到職日 BETWEEN '2024-01-01' AND '2024-12-31'
  • (D) WHERE 到職日 IS NULL
看詳解
答案：(B)
欄位被函數包住，DBMS 無法直接比對索引中的原始值 → 只能全表掃描後逐列計算 YEAR()。

改寫方式：WHERE 到職日 >= '2024-01-01' AND 到職日 < '2025-01-01'

核心原則一句話：「索引欄位左邊不要動它」——不包函數、不做運算、不讓型別被隱含轉換。

補充：部分 DBMS 支援函數式索引（Function-based Index），可對 YEAR(到職日) 直接建索引，但需事先建立。

  • (A) 索引被刪除了
  • (B) 資料字典中的統計資訊過期，導致成本式最佳化器誤判

  • (B) 實務上因網路分割必然可能發生，故 P 為必選，取捨在 C 與 A 之間
  • (C) NoSQL 資料庫一定選擇 CP

看詳解
答案：(B)

45安全
機關系統儲存使用者密碼，下列做法何者最為適當？
  • (A) 以 AES 加密後儲存
  • (B) 以 MD5 雜湊後儲存
  • (C) 以 bcrypt／Argon2 等慢速雜湊搭配隨機鹽（Salt）儲存
  • (D) 明文儲存但限制資料庫存取權限
看詳解
答案：(C)

(A) 加密是可還原的，金鑰若洩漏所有密碼一次曝光。而系統本來就不需要「知道」使用者的原始密碼，只需驗證 → 應用單向雜湊。
(B) MD5 已被證明可碰撞，且運算太快（可每秒嘗試數十億次），加上彩虹表查表即可破解。
(D) 明文儲存是最嚴重的錯誤，一旦資料庫外洩即全部曝光，且違反《個人資料保護法》之安全維護義務。

正解的兩個關鍵：
1. 慢速雜湊（bcrypt/scrypt/Argon2/PBKDF2）—— 刻意設計得慢，讓暴力破解不可行
2. 每帳號不同的隨機鹽 —— 使彩虹表失效，且相同密碼的兩個人雜湊值也不同

特性意義保障機制白話
A 不可分割性
（Atomicity）		交易全做或全不做Undo Log（失敗時回復原值）轉帳不會只扣款不入帳
C 一致性
（Consistency）		交易前後皆滿足所有完整性限制限制條件（PK、FK、CHECK）＋觸發器＋A/I/D 三者共同達成總金額不會憑空增減

📊 一、索引原理與 B+ 樹
項目內容
原理另建一組依鍵值排序的結構，存放「鍵值 → 資料列位置」，查詢時先查索引再取資料，避免全表掃描
效益800 萬筆全表掃描 O(n)；B+ 樹索引僅需 3～4 次磁碟 I/O
成本主體磁碟 I/O，不是 CPU 比較次數（磁碟比記憶體慢千倍以上）→ 索引設計的目標是把樹壓矮
為何用 B+ 樹說明
① 高分支度、樹極矮一個節點對齊一個磁碟區塊（4～16 KB）可放數百個鍵 → 800 萬筆僅 3～4 層；AVL 樹需約 23 層
② 只有葉節點存資料內部節點只放索引鍵 → 同樣大小可放更多鍵 → 樹更矮
③ 葉節點串接且有序範圍查詢（日期區間、BETWEEN、ORDER BY）可沿葉節點連續掃描
④ 效能穩定所有查詢皆走到葉節點，時間可預測，利於查詢最佳化器估算成本
⑤ 自平衡不會因公文字號遞增插入而退化（BST 會退化為串列）

📊 三、索引的代價與建立原則
代價說明
拖慢寫入每次 INSERT／UPDATE／DELETE 都須同步維護所有相關索引；索引越多，寫入越慢
占用空間索引本身需要磁碟與記憶體（緩衝區）
維護成本長期異動後產生碎片，須定期重建或重組；統計資訊過期會使最佳化器誤判
建立原則說明
① 以實際查詢頻率為依據從慢查詢日誌找出最耗時、最頻繁的查詢，針對它建索引
② 建在WHERE / JOIN / ORDER BY / GROUP BY 的欄位而非「看起來重要」的欄位
③ 選高選擇性欄位不同值越多越適合（如公文字號）；性別、狀態等低基數欄位單獨建索引效益低

📊 一、SQL Injection 原理
項目內容
定義攻擊者於輸入欄位夾帶 SQL 語法片段，使其被資料庫當作指令執行而非資料
根本原因以字串串接組成 SQL，導致「資料」與「指令」的界線消失
危害繞過驗證登入、竊取全表資料、竄改或刪除資料、提權執行系統指令
【錯誤寫法：字串串接】
sql = "SELECT * FROM 使用者 WHERE 帳號='" + id + "' AND 密碼='" + pw + "'";

攻擊者在帳號欄輸入：   ' OR '1'='1' --

組成的 SQL 變成：
SELECT * FROM 使用者 WHERE 帳號='' OR '1'='1' --' AND 密碼=''
                                  └─ 恆真 ─┘ └ 後面被註解掉 ┘
→ 條件恆為真，未輸入密碼即可登入
攻擊型態手法
驗證繞過' OR '1'='1' --
聯集注入' UNION SELECT 帳號, 密碼 FROM 使用者 -- → 竊取其他表資料
破壞性注入'; DROP TABLE 公文; --
盲注（Blind）頁面無錯誤訊息時，以真假回應差異或時間延遲（SLEEP）逐字元推測資料
📊 二、四層防護（主表）
層次措施說明
程式層
（根本解）		① 參數化查詢／預備語句最有效、唯一的根本解——SQL 結構先編譯，參數只當資料傳入，永遠不會被當指令
② 使用 ORM 或預存程序但預存程序內部若仍動態組字串，一樣會被注入
③ 輸入驗證（白名單）型別、長度、格式檢核；僅為輔助，不可作為唯一防線
④ 錯誤訊息不外洩不得回傳資料庫錯誤原文（會洩漏表名、欄位名）；記錄於伺服器日誌即可

⑥ 敏感資料加密即使被取出也無法直接使用
⑦ 稽核與監控開啟稽核日誌，監控異常查詢量與異常語法
網路層⑧ WAF（Web 應用防火牆）攔截常見注入樣式；屬縱深防禦，可被繞過

管理層⑩ 安全程式設計規範明訂禁止字串串接組 SQL，納入程式碼審查

（Time-Variant）		保存長期歷史，每筆皆有時間維度可比較歷年同期案件量
④ 非揮發性

E 萃取

📊 一、五個基本運算
運算符號作用對應 SQL
選擇（Selection）σ挑列（水平切）WHERE
投影（Projection）π挑欄（垂直切），並自動去除重複SELECT DISTINCT

其餘運算（交集、各種 join、除法、更名）皆為衍生運算，可由這五個組合而成。
📊 二、衍生運算之推導
📐 Theta Join（θ-Join） R ⋈θ S = σθ( R × S )
→ 先做笛卡兒乘積產生所有組合，再用選擇留下符合條件者。

📐 自然連結（Natural Join） R ⋈ S = π去除重複欄( σR.A = S.A( R × S ) )
→ 在 θ-Join 的基礎上，條件為同名欄位相等，並以投影去除重複欄位。

📐 交集（Intersection） R ∩ S = R − ( R − S )
→ 用兩次差集即可。（也可寫成 S − (S − R)）

驗證交集公式：R = {1,2,3}、S = {2,3,4}
R − S = {1}；R − (R−S) = {1,2,3} − {1} = {2,3} ✔ 正是交集。

📊 三、除法運算（Division）
項目內容
符號R ÷ S
語意找出 R 中與 S 的「每一個」值都配對過的那些項目
對應的中文問法「找出符合所有條件的…」「…全部都…的…」
形式定義R(A, B) ÷ S(B) = { a | ∀ b ∈ S，(a, b) ∈ R }
可由基本運算推導R ÷ S = πA(R) − πA( ( πA(R) × S ) − R )
意思是：從所有 a 中，扣掉「有某個 b 沒配到」的 a
📐 實例：找出「報名了全部研習課程」的員工
報名 R員工課程
張三C1
張三C2
張三C3
李四C1
李四C3
王五C2
課程 S = {C1, C2, C3}

R ÷ S = { 張三 }（只有張三三門全報）
為何 SQL 沒有除法運算子說明
SQL 缺乏全稱量詞（∀）SQL 只有 EXISTS（存在量詞 ∃），沒有 FOR ALL
邏輯轉換「對所有 x 皆成立」 ⟺ 「不存在 x 使其不成立」
∀x P(x) ⟺ ¬∃x ¬P(x)
實作因此以 雙重 NOT EXISTS 改寫
-- 解法 1：雙重 NOT EXISTS（標準答案）
SELECT DISTINCT e.員工編號, e.姓名
FROM   員工 e
WHERE  NOT EXISTS (                       -- 不存在這樣一門課
         SELECT 1 FROM 課程 c
         WHERE NOT EXISTS (               -- 是他沒報名的
                 SELECT 1 FROM 報名 r
                 WHERE r.員工編號 = e.員工編號
                   AND r.課程代碼 = c.課程代碼 ) );
-- 白話：「不存在一門課，是他沒報名的」＝「所有課他都報了」

-- 解法 2：計數比對（較直觀，實務常用）
SELECT r.員工編號
FROM   報名 r
WHERE  r.課程代碼 IN (SELECT 課程代碼 FROM 課程)
GROUP BY r.員工編號
HAVING COUNT(DISTINCT r.課程代碼) = (SELECT COUNT(*) FROM 課程);
⚠️ 解法 2 的兩個必要細節 ① 必須用 COUNT(DISTINCT ...)——若同一人可重複報名同一課，不加 DISTINCT 會誤判
② 若報名表可能含已停開課程，須加 WHERE ... IN (SELECT 課程代碼 FROM 課程) 限定範圍

時間軸 ──────────────────────────────────────────►
                    ↑Checkpoint                    ↑當機

  T1  ├────COMMIT──┤                    ← 檢查點前已提交 → 不必處理
  T2  ├──────────────────COMMIT──┤      ← 檢查點後提交   → REDO
  T3  ├──────────────────────────────►  ← 尚未提交       → UNDO
  T4              ├────COMMIT──┤        ← 檢查點後提交   → REDO
  T5                      ├──────────►  ← 尚未提交       → UNDO
階段作為
① 分析（Analysis）由最後一個 Checkpoint 開始掃描日誌，建立兩份清單：
Redo List（已 COMMIT）／Undo List（未 COMMIT）
② 重做（Redo）由檢查點往後（前向）掃描，將 Redo List 中交易的新值重新套用
→ 確保已回覆使用者「成功」的交易確實生效
③ 回復（Undo）由日誌末端往前（反向）掃描，將 Undo List 中交易的舊值寫回
→ 確保未完成的交易不留下半套結果
④ 開放服務復原完成後恢復對外服務；記錄事件並檢討

📊 三、三種備份與 RTO／RPO
類型備份內容備份時間占用空間還原步驟還原時間
完整備份全部資料最長最大1 份最短
差異備份自上次完整備份以來的異動中（逐日變長）中2 份（完整 + 最近一次差異）中
增量備份自上次任何備份以來的異動最短最小完整 + 全部增量最長（且任一份損毀即斷鏈）
指標全名意義白話由什麼決定

RPORecovery Point Objective可容忍的資料遺失量上限能掉多久的資料備份／日誌傳送頻率
📐 兩者的關鍵區別 RPO 看的是「往回看，最後一個可用的還原點在多久以前」；
RTO 看的是「往前看，從故障到恢復服務要多久」。

RPO 靠備份頻率，RTO 靠備援架構。兩者要求越嚴格，成本越高——須依業務衝擊分析（BIA）合理設定。

📊 一、檢視表（View）
項目內容
定義以 SQL 查詢定義的虛擬表；只儲存查詢定義，不儲存資料，查詢時才動態執行
對應三層架構屬 外部層（External Level），提供各使用者不同的資料視角
功能說明
① 安全性（最主要）只開放必要的欄位與列，隱藏敏感資料
② 簡化複雜查詢將多表 JOIN 封裝為單一「表」，使用者不需理解底層結構
③ 邏輯資料獨立性底層表結構調整時，修改 View 定義即可，應用程式不必改
④ 一致的計算邏輯常用的計算（如年資、逾期天數）集中定義，避免各程式算法不一
限制說明
① 效能不會變好View 只是查詢的代名詞；不會預先計算，也不會加速；巢狀多層的 View 可能使最佳化器難以產生好的執行計畫
② 不一定可更新含 DISTINCT、GROUP BY、聚合函數、UNION、多表 JOIN 的 View 通常不可直接 INSERT／UPDATE——因為無法對應回底層的唯一一列
③ 相依性底層表刪除或改名會使 View 失效
④ 不能建索引一般 View 無法建立索引（物化檢視表則可以）
📝 二、用於權限控管的實例 
-- 情境：人事資料含薪資與身分證字號，一般單位僅可查基本資料

-- ① 建立僅含必要欄位的檢視表（欄位層級控管）
CREATE VIEW v_員工通訊錄 AS
SELECT 員工編號, 姓名, 部門代碼, 職稱, 分機
FROM   員工;                          -- 不含薪資、身分證字號、到職日

-- ② 建立僅含本單位資料的檢視表（列層級控管）
CREATE VIEW v_本單位員工 AS
SELECT 員工編號, 姓名, 職稱, 分機
FROM   員工
WHERE  部門代碼 = ( SELECT 部門代碼 FROM 使用者對照
                    WHERE 帳號 = CURRENT_USER );

-- ③ 遮罩顯示（去識別化）
CREATE VIEW v_案件查詢 AS
SELECT 案件編號,
       CONCAT(SUBSTRING(申請人姓名,1,1), '○') AS 申請人,   -- 王○
       CONCAT(SUBSTRING(身分證字號,1,3), '****',
              SUBSTRING(身分證字號,8,3))       AS 身分證,   -- A12****89
       申請日期, 處理狀態
FROM   案件;

-- ④ 只授權 View，不授權底層表 ← 關鍵步驟
REVOKE ALL ON 員工   FROM 一般使用者;
GRANT  SELECT ON v_員工通訊錄 TO 一般使用者;

📊 三、預存程序 vs 觸發器
比較點預存程序（Stored Procedure）觸發器（Trigger）
啟動方式明確呼叫（CALL／EXEC）自動觸發（INSERT／UPDATE／DELETE 事件）
參數可傳入參數、可回傳值不可傳參數、不可回傳值
可見性高（程式碼中看得到呼叫）低——「看不見的執行」，最大缺點
交易可自行控制（COMMIT／ROLLBACK）屬於觸發它的交易；失敗會使原交易一併回復
除錯較容易困難（可能連鎖觸發其他觸發器）
效能風險可控每筆異動都執行，批次大量更新時可能嚴重拖慢
適用時機預存程序觸發器
典型用途‧ 複雜業務邏輯封裝（如批次結算）
‧ 減少網路往返（多道 SQL 一次執行）
‧ 安全控管（只授權執行程序，不授權表）		‧ 稽核軌跡（自動記錄誰改了什麼）
‧ 強制完整性（超出 CHECK 能力的規則）
‧ 自動維護彙總欄位
不宜用於過度使用會使業務邏輯分散於資料庫，不利版本控管與移植複雜業務邏輯——難以追蹤與維護；寧可寫在應用層或預存程序
選擇原則：需要「一定會執行、不可被繞過」的，用觸發器（如稽核）；需要「看得見、好維護」的，用預存程序。
📊 四、物化檢視表（Materialized View）
項目一般 View物化檢視表
是否儲存資料否（每次查詢重算）是（實際存放結果）
查詢效能與原查詢相同大幅提升
資料即時性永遠最新可能過期
可否建索引否可以
額外成本無占用空間 ＋ 更新維護成本
用途說明
報表與統計耗時的彙總查詢預先算好（如「各區各月案件統計」），報表秒開
資料倉儲彙總作為預先彙總層，減少對明細表的重複掃描
跨系統資料快取減少對來源系統的查詢壓力
注意事項說明
① 更新策略完全重建（簡單但慢）／增量更新（快但需異動紀錄）／即時同步（最新但拖慢寫入）
② 資料非即時使用者可能看到舊資料 → 必須在報表上標示「資料更新時間」，避免誤解與爭議
③ 適用判準適合「讀多寫少、可容忍延遲」的分析場景；不適用於須即時正確的交易查詢
④ 更新時機宜排於離峰時段（如每日凌晨），避免影響線上作業
✍️ 必寫拿分點 1. View 「只存定義不存資料」、「不會提升效能」——最常被誤解的兩點
2. 限制要寫「含 GROUP BY／聚合的 View 不可更新」及其原因
3. 權限控管實例要寫 SQL，且必須包含「收回底層表權限」——本題關鍵句
4. 觸發器的最大缺點是「看不見的執行」，且每筆異動都執行
5. 選擇原則要有一句明確的判準（稽核用觸發器、業務邏輯用預存程序）
6. 物化檢視表要指出「資料可能過期，須標示更新時間」

📊 一、分散式資料庫
項目內容
定義資料分散儲存於多個節點（可跨地理位置），但對使用者呈現為單一邏輯資料庫
理想目標分散透明性——使用者不需知道資料實際存在哪個節點
優點缺點
① 可擴展性（水平擴展，加機器即可）① 設計與維運複雜度高
② 高可用（單一節點故障不中斷）② 分散式交易困難（跨節點難維持 ACID）
③ 地理就近存取（降低延遲）③ 網路成為瓶頸與故障點
④ 反映組織分權結構（各機關管自己的資料）④ 一致性難以保證（受 CAP 限制）
⑤ 容災能力（異地備援）⑤ 除錯與問題追蹤困難；人力技術門檻高
📊 二、資料分割 vs 資料複寫 
資料分割（Sharding）─ 把資料「切開」放不同節點
   節點A: 台北市案件    節點B: 台中市案件    節點C: 高雄市案件
   （每個節點資料【不同】，合起來才是全部）

資料複寫（Replication）─ 把資料「複製」到不同節點
   主節點: 全部資料 ──► 副本1: 全部資料 ──► 副本2: 全部資料
   （每個節點資料【相同】，任一個就是全部）
比較點資料分割（Partitioning／Sharding）資料複寫（Replication）
作法把資料切成不重疊的片段放到不同節點把相同資料複製到多個節點
主要目的解決「資料量太大」與「寫入吞吐不足」解決「讀取量太大」與「可用性／容災」
擴展方向寫入與儲存皆可擴展只擴展讀取（寫仍集中於主節點）
容錯本身不提供（該片段的節點掛了，那部分資料就不可用）提供（可切換到副本）
一致性議題跨分片查詢與交易困難複寫延遲→ 副本可能讀到舊資料
常見策略範圍分割（依年度）／雜湊分割（依 ID 取模）／清單分割（依縣市）主從式（一寫多讀）／多主式（多點可寫，須解衝突）
兩者是互補而非二選一。實務常同時使用：先分割解決容量與寫入，每個分片再各自複寫以取得容錯與讀取擴展。
選擇要點說明
分割鍵的選擇最關鍵選不好會造成資料傾斜（某節點特別滿）或熱點（查詢集中一節點）；且應盡量讓常一起查詢的資料落在同一分片，避免跨分片 JOIN
再平衡成本分片數變動時需搬移資料 → 可採一致性雜湊降低搬移量
複寫模式同步複寫：不掉資料但寫入慢；非同步複寫：寫入快但可能掉最近幾筆（影響 RPO）
📊 三、兩階段提交協定（2PC） 
          協調者（Coordinator）              參與者（Participants）

  階段一   ──── PREPARE（可以提交嗎？）────►  各自寫日誌、鎖定資源
  【準備】  ◄─── YES / NO ─────────────────  回報是否就緒

  階段二   全部 YES → ──── COMMIT ────────►  正式提交、釋放鎖
  【提交】  有任一 NO → ──── ABORT ────────►  回復、釋放鎖
           ◄─── ACK ──────────────────────
階段協調者參與者
① 準備階段
（Prepare / Voting）		發送 PREPARE 詢問是否可提交執行交易但不提交；寫入日誌、鎖定資源；回覆 YES（已就緒）或 NO
② 提交階段
（Commit）		全部 YES → 送 COMMIT
任一 NO 或逾時 → 送 ABORT		依指令提交或回復，釋放鎖，回覆 ACK
問題說明緩解
① 阻塞協定（最大問題）參與者回覆 YES 後、收到指令前，資源持續鎖定。若協調者當機，參與者無限期等待，資源無法釋放，服務停擺3PC（加入預提交階段）；或以 Paxos／Raft 選出新協調者
② 單點故障協調者是單一失效點協調者本身高可用化
③ 效能差需多輪網路往返且長時間持鎖 → 並行度大幅下降減少跨節點交易；設計時讓相關資料落在同一節點
④ 資料不一致風險提交階段部分參與者當機，可能造成短暫不一致，需人工介入完整日誌與復原程序
替代方案說明
Saga 模式將長交易拆成一系列本地交易，失敗時執行補償交易（如「取消訂單」抵銷「建立訂單」）→ 犧牲隔離性換取可用性
最終一致性以訊息佇列非同步傳遞，容許短暫不一致
最務實的作法從設計上避免分散式交易——把需要同時異動的資料放在同一個節點（同一分片）
✍️ 必寫拿分點 1. 優缺點各至少四項，缺點要有「分散式交易困難」與「維運複雜度高」
2. 分割 vs 複寫最好畫圖；核心對比是「分割解決寫入與容量、複寫解決讀取與容錯」
3. 明確指出兩者互補、實務常併用
4. 提到分割鍵選擇不當造成資料傾斜與熱點是加分
5. 2PC 必須畫出兩階段的訊息流程
6. 「2PC 是阻塞協定，協調者當機會使參與者無限期持鎖」——本題最關鍵的一句
7. 補充 Saga 與「從設計上避免分散式交易」展現實務判斷

申論 14正規化進階 · 25 分
關聯 R(A, B, C, D, E)，函數相依集合 F = { AB → C, C → D, D → E, AB → E }。

(一) 求出 R 的所有候選鍵，並說明推導過程。（8 分）
(二) 判斷 R 符合第幾階正規化，並說明理由。（7 分）
(三) 將 R 分解至 3NF，並驗證是否為無損分解與相依保存。（10 分）
看答題架構
📋 答題骨架 一、屬性分類 → 候選鍵推導（屬性封閉集計算）→ 二、正規化階數判定（表）→ 三、分解結果 → 四、無損與相依保存驗證
📊 一、求候選鍵
步驟作法本題
① 分類屬性看每個屬性出現在函數相依的左邊、右邊、或都不出現只在左邊：A, B
兩邊都有：C, D
只在右邊：E
② 關鍵推論「只出現在左邊」的屬性，必定屬於每一個候選鍵（因為沒有任何相依能推導出它）A、B 必在候選鍵中
③ 先試 {A, B}計算屬性封閉集 (AB)⁺見下方計算
📐 屬性封閉集計算 (AB)⁺ 起始：(AB)⁺ = {A, B}
套用 AB → C：AB ⊆ {A,B} ✔ → 加入 C → {A, B, C}
套用 C → D：C ⊆ {A,B,C} ✔ → 加入 D → {A, B, C, D}
套用 D → E：D ⊆ {A,B,C,D} ✔ → 加入 E → {A, B, C, D, E}

(AB)⁺ = {A, B, C, D, E} = R → AB 是超鍵
最小性檢查封閉集結論
(A)⁺{A}不足以推導全部 → 不是超鍵
(B)⁺{B}不足 → 不是超鍵
移除 A 或 B 皆不再是超鍵 → 滿足最小性
又因 A、B 必屬於每個候選鍵，故不存在其他候選鍵。

結論：R 的候選鍵只有一個 —— {A, B}
主要屬性：A, B　｜　非主要屬性：C, D, E
📊 二、正規化階數判定
階要求本題檢查結果
1NF所有欄位為單一值題目未提及多值屬性✔ 符合
2NF無部分相依（非主要屬性不可只依賴候選鍵的一部分）檢查 (A)⁺ = {A}、(B)⁺ = {B}，單獨的 A 或 B 都推不出 C、D、E → 無部分相依✔ 符合
3NF無遞移相依（非主要屬性不可透過另一非主要屬性依賴候選鍵）AB → C → D：C 是非主要屬性，D 也是 → 遞移相依
AB → C → D → E：同樣是遞移相依		✘ 違反
結論：R 符合 2NF，但不符合 3NF（存在遞移相依 AB → C → D → E）。

3NF 的正式定義：對每一個非平凡函數相依 X → Y，必須 X 是超鍵 或 Y 的每個屬性都是主要屬性。
本題 C → D：C 不是超鍵（(C)⁺ = {C,D,E} ≠ R），且 D 不是主要屬性 → 違反。

順帶一提 BCNF：BCNF 要求每個非平凡相依的左邊都必須是超鍵。本題 C → D、D → E 的左邊都不是超鍵 → 更不符合 BCNF。

📊 三、分解至 3NF
步驟作法
① 求最小覆蓋 Fmin檢查 AB → E：由 AB → C、C → D、D → E 已可推得 E → AB → E 是多餘相依，可刪除
Fmin = { AB → C, C → D, D → E }
② 每個相依成一個表R1(A, B, C)、R2(C, D)、R3(D, E)
③ 確認含候選鍵R1 的鍵即為 {A, B} = 候選鍵 ✔（若無任何分解表含候選鍵，須另加一個）
📐 分解結果 R1(A, B, C)　主鍵 (A,B)
R2(C, D)　主鍵 C，C 為 R1 的外鍵參照
R3(D, E)　主鍵 D，D 為 R2 的外鍵參照
📊 四、驗證
驗證項目判準本題
無損分解
（Lossless Join）		二元分解 R = R1 ∪ R2 為無損，若共同屬性是其中一方的超鍵：
(R1 ∩ R2) → R1　或　(R1 ∩ R2) → R2		—
R1 與 R2 的共同屬性 = {C}；C → D，即 C 是 R2(C, D) 的鍵✔ 無損
(R1⋈R2) 與 R3 的共同屬性 = {D}；D → E，即 D 是 R3(D, E) 的鍵✔ 無損
相依保存
（Dependency Preserving）		原相依集的每個相依，是否都能在單一分解表內檢查—
AB → C 在 R1 ✔｜C → D 在 R2 ✔｜D → E 在 R3 ✔
（AB → E 為多餘相依，可由上述三者推導）		✔ 保存
結論：本分解同時滿足「無損分解」與「相依保存」，且各表皆符合 3NF。

重要理論：
‧ 分解至 3NF：一定可以同時達成無損且相依保存
‧ 分解至 BCNF：一定可以無損，但不保證相依保存
→ 這正是實務上多數系統止於 3NF 的原因。
✍️ 必寫拿分點 1. 候選鍵推導必須寫出屬性封閉集的逐步計算，不能只給答案
2. 明確寫出「只出現在左邊的屬性必屬於每個候選鍵」這個推論法則
3. 要做最小性檢查（(A)⁺、(B)⁺）才算完整
4. 判定 3NF 要引用正式定義（X 是超鍵 或 Y 為主要屬性），並指明是 C → D 違反
5. 分解前要先求最小覆蓋，並指出 AB → E 是多餘相依
6. 無損驗證要寫出「共同屬性是其中一方的鍵」並逐步套用
7. 結論補上「3NF 保證無損＋相依保存；BCNF 不保證相依保存」——本題最高分的一句
