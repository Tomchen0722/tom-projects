第 5 章　SQL 完整教學

這一章一定要動手寫。SQL 是「看得懂但寫不出來」的典型科目。
建議裝一個 SQLite（單一檔案、免安裝）或用線上的 SQL Fiddle 練習。

5-1　DDL：定義結構

-- 建立資料表
CREATE TABLE 員工 (
    員工編號  CHAR(6)      PRIMARY KEY,
    姓名      VARCHAR(50)  NOT NULL,
    性別      CHAR(1)      CHECK (性別 IN ('M', 'F')),
    到職日    DATE         DEFAULT CURRENT_DATE,
    薪資      DECIMAL(10,2) CHECK (薪資 >= 0),
    部門代碼  CHAR(3),
    主管編號  CHAR(6),
    FOREIGN KEY (部門代碼) REFERENCES 部門(部門代碼)
        ON DELETE SET NULL ON UPDATE CASCADE,
    FOREIGN KEY (主管編號) REFERENCES 員工(員工編號)   -- 自我參考
);

-- 修改結構
ALTER TABLE 員工 ADD 電子郵件 VARCHAR(100);
ALTER TABLE 員工 MODIFY 姓名 VARCHAR(80);        -- Oracle/MySQL
ALTER TABLE 員工 ALTER COLUMN 姓名 VARCHAR(80);  -- SQL Server
ALTER TABLE 員工 DROP COLUMN 電子郵件;
ALTER TABLE 員工 ADD CONSTRAINT chk_sal CHECK (薪資 <= 500000);

-- 刪除
DROP TABLE 員工;         -- 整張表（含結構）消失
TRUNCATE TABLE 員工;     -- 只清空資料，保留結構
指令類別刪除範圍可否 ROLLBACK速度
DELETEDML可用 WHERE 選擇性刪列可以慢（逐列記錄 log）
TRUNCATEDDL清空全表資料通常不可（自動 commit）快
DROPDDL連表結構一起刪通常不可快
⚠️ 這張表是超高頻考點 「DELETE、TRUNCATE、DROP 有何差異」幾乎年年出現在選擇題或申論子題。
記憶重點：DELETE 是 DML 可回復、TRUNCATE 與 DROP 是 DDL 不可回復；DROP 連結構都沒了。

5-2　DML 基礎

INSERT INTO 員工 (員工編號, 姓名, 薪資, 部門代碼)
VALUES ('E00001', '王小明', 45000, 'D01');

-- 從查詢結果批次插入
INSERT INTO 員工備份 SELECT * FROM 員工 WHERE 到職日 < '2020-01-01';

UPDATE 員工 SET 薪資 = 薪資 * 1.03
WHERE 部門代碼 = 'D01' AND 到職日 < '2020-01-01';

DELETE FROM 員工 WHERE 員工編號 = 'E00001';
⚠️ 最恐怖的 SQL 錯誤 UPDATE 員工 SET 薪資 = 0; — 忘了寫 WHERE，全公司薪水歸零。
實務習慣：先用 SELECT 把 WHERE 條件驗證過，再改成 UPDATE／DELETE。申論題談「資料庫維運」時，這點可作為作業程序控管的例子。

5-3　SELECT 的執行順序（理解這個就不會寫錯）

📐 撰寫順序 vs 執行順序 撰寫順序：SELECT → FROM → WHERE → GROUP BY → HAVING → ORDER BY → LIMIT

實際執行順序：
① FROM / JOIN　（先決定資料從哪來）
② WHERE　（對個別列過濾）
③ GROUP BY　（分組）
④ HAVING　（對群組過濾）
⑤ SELECT　（挑欄位、算聚合函數）
⑥ DISTINCT
⑦ ORDER BY　（排序）
⑧ LIMIT / TOP　（取前幾筆）
🧒 為什麼要知道執行順序

因為它解釋了三個最常見的錯誤：

①「為什麼 WHERE 裡不能用 COUNT()？」
因為 WHERE 在 GROUP BY 之前執行，那時還沒分組，COUNT 還不存在。要過濾聚合結果請用 HAVING。

②「為什麼 WHERE 裡不能用 SELECT 定義的別名？」
因為 WHERE（②）比 SELECT（⑤）早執行，別名還沒誕生。但 ORDER BY（⑦）在 SELECT 之後，所以 ORDER BY 可以用別名。

③「WHERE 和 HAVING 到底差在哪？」
WHERE 過濾「列」、HAVING 過濾「組」。而且因為 WHERE 先執行，把條件寫在 WHERE 效能較好（先篩掉再分組，資料量小）。

5-4　JOIN 完整說明（必考）

JOIN 類型回傳內容語法
INNER JOIN只有兩邊都符合條件的列A INNER JOIN B ON A.k = B.k
LEFT (OUTER) JOIN左表全部 + 右表符合者（無對應則右表欄位為 NULL）A LEFT JOIN B ON ...
RIGHT (OUTER) JOIN右表全部 + 左表符合者A RIGHT JOIN B ON ...
FULL (OUTER) JOIN兩邊全部，無對應處填 NULLA FULL JOIN B ON ...
CROSS JOIN笛卡兒積（m × n 列）A CROSS JOIN B
SELF JOIN同一張表自己接自己（需取別名）員工 e1 JOIN 員工 e2 ON e1.主管編號 = e2.員工編號
NATURAL JOIN自動用同名欄位做等值結合A NATURAL JOIN B（實務上不建議用，太隱晦）
-- 查詢每位員工及其部門名稱（沒有部門的員工也要列出）
SELECT e.姓名, e.薪資, COALESCE(d.部門名稱, '（未分派）') AS 部門
FROM 員工 e
LEFT JOIN 部門 d ON e.部門代碼 = d.部門代碼;

-- SELF JOIN：查詢每位員工及其主管姓名
SELECT e.姓名 AS 員工, m.姓名 AS 主管
FROM 員工 e
LEFT JOIN 員工 m ON e.主管編號 = m.員工編號;

-- 找出「沒有任何員工」的部門（LEFT JOIN + IS NULL 技巧）
SELECT d.部門名稱
FROM 部門 d
LEFT JOIN 員工 e ON d.部門代碼 = e.部門代碼
WHERE e.員工編號 IS NULL;
💡 「LEFT JOIN + IS NULL」是找差集的經典技巧 「找出 A 有但 B 沒有的資料」有三種寫法：
1. LEFT JOIN ... WHERE B.key IS NULL（效能通常最好）
2. WHERE key NOT IN (SELECT key FROM B)（注意 NULL 陷阱）
3. WHERE NOT EXISTS (SELECT 1 FROM B WHERE ...)（最安全）
⚠️ NOT IN 的 NULL 陷阱（高階考點） 若子查詢結果中含有 NULL，NOT IN 會回傳空結果！

原因：x NOT IN (1, 2, NULL) 等價於 x <> 1 AND x <> 2 AND x <> NULL。
而 x <> NULL 的結果是 UNKNOWN（不是 TRUE 也不是 FALSE），整個 AND 運算就永遠不會是 TRUE。

對策：改用 NOT EXISTS，或在子查詢加 WHERE key IS NOT NULL。
這是申論題「請說明 SQL 中 NULL 之三值邏輯」的最佳實例。

5-5　聚合函數與 GROUP BY

函數說明NULL 處理
COUNT(*)計算列數包含 NULL 的列
COUNT(欄位)計算該欄非 NULL 的個數忽略 NULL
COUNT(DISTINCT 欄位)計算不重複值個數忽略 NULL
SUM / AVG總和／平均忽略 NULL（AVG 的分母不含 NULL）
MAX / MIN最大／最小忽略 NULL
⚠️ AVG 與 NULL 的經典陷阱 5 筆資料的薪資為 100, 200, NULL, NULL, 300。
AVG(薪資) = (100+200+300) / 3 = 200（不是 600/5 = 120）。

若業務上 NULL 應視為 0，必須寫 AVG(COALESCE(薪資, 0))。這種細節就是申論題的得分點。 
-- 查詢各部門平均薪資，只列出人數 >= 5 且平均薪資 > 50000 的部門
SELECT d.部門名稱,
       COUNT(*) AS 人數,
       ROUND(AVG(e.薪資), 0) AS 平均薪資,
       MAX(e.薪資) AS 最高薪
FROM 員工 e
JOIN 部門 d ON e.部門代碼 = d.部門代碼
WHERE e.到職日 <= '2024-12-31'      -- ② 先過濾「列」
GROUP BY d.部門代碼, d.部門名稱     -- ③ 分組
HAVING COUNT(*) >= 5                 -- ④ 再過濾「組」
   AND AVG(e.薪資) > 50000
ORDER BY 平均薪資 DESC;             -- ⑦ 可用別名
💡 GROUP BY 的鐵則 SELECT 裡出現的欄位，要嘛在 GROUP BY 裡、要嘛被聚合函數包住，不可以有第三種。
違反這條規則在標準 SQL 與大多數 DBMS 會直接報錯（MySQL 舊版寬鬆，會回傳不確定的值——這是常見的 bug 來源）。

5-6　子查詢（Subquery）

類型說明範例
純量子查詢回傳單一值，可放在任何值的位置WHERE 薪資 > (SELECT AVG(薪資) FROM 員工)
單欄多列配合 IN、ANY、ALLWHERE 部門代碼 IN (SELECT ... )
相關子查詢
Correlated		內層引用外層的欄位，每一列都要執行一次（效能較差）WHERE EXISTS (SELECT 1 FROM B WHERE B.k = A.k)
衍生表
Derived Table		放在 FROM 裡當一張臨時表FROM (SELECT ...) AS t
CTE
共用資料表運算式		用 WITH 定義，可讀性最好，可遞迴WITH t AS (SELECT ...) SELECT * FROM t
-- ANY / ALL 的差異
WHERE 薪資 > ANY (SELECT 薪資 FROM 員工 WHERE 部門代碼='D01')
-- 只要比 D01 中「任一人」高就算 → 等於比「最低薪」高

WHERE 薪資 > ALL (SELECT 薪資 FROM 員工 WHERE 部門代碼='D01')
-- 要比 D01 中「所有人」都高 → 等於比「最高薪」高

-- CTE：查詢薪資高於本部門平均的員工
WITH 部門平均 AS (
    SELECT 部門代碼, AVG(薪資) AS 平均薪
    FROM 員工 GROUP BY 部門代碼
)
SELECT e.姓名, e.薪資, a.平均薪
FROM 員工 e
JOIN 部門平均 a ON e.部門代碼 = a.部門代碼
WHERE e.薪資 > a.平均薪;

-- 遞迴 CTE：查詢某主管底下所有層級的部屬（組織圖展開）
WITH RECURSIVE 部屬 AS (
    SELECT 員工編號, 姓名, 主管編號, 1 AS 層級
    FROM 員工 WHERE 員工編號 = 'E00001'      -- 起始點
    UNION ALL
    SELECT e.員工編號, e.姓名, e.主管編號, p.層級 + 1
    FROM 員工 e JOIN 部屬 p ON e.主管編號 = p.員工編號
)
SELECT * FROM 部屬;

5-7　窗函數（Window Function）— 近年新考點

-- 各部門薪資排名（不影響列數，這是與 GROUP BY 最大的差別）
SELECT 姓名, 部門代碼, 薪資,
   RANK()       OVER (PARTITION BY 部門代碼 ORDER BY 薪資 DESC) AS 排名,
   DENSE_RANK() OVER (PARTITION BY 部門代碼 ORDER BY 薪資 DESC) AS 密集排名,
   ROW_NUMBER() OVER (PARTITION BY 部門代碼 ORDER BY 薪資 DESC) AS 序號,
   AVG(薪資)     OVER (PARTITION BY 部門代碼) AS 部門平均
FROM 員工;
函數並列時的行為（薪資 100, 100, 90）
RANK()1, 1, 3（跳號）
DENSE_RANK()1, 1, 2（不跳號）
ROW_NUMBER()1, 2, 3（強制不重複）
GROUP BY vs 窗函數：GROUP BY 會把多列壓成一列；窗函數保留每一列，只是額外算出一個群組統計值。
「查出每位員工的薪資，以及他所屬部門的平均薪資」這種需求，用窗函數一行搞定，用 GROUP BY 則需 JOIN 子查詢。

5-8　檢視表、預存程序、觸發器

物件定義優點限制／風險
檢視表 View儲存的查詢，虛擬表簡化複雜查詢、權限控管（只開放部分欄位）、邏輯獨立性含聚合／DISTINCT／GROUP BY 的 View 通常不可更新
物化檢視表
Materialized View		把 View 結果實際存下來查詢極快需定期刷新，資料非即時
預存程序
Stored Procedure		預先編譯的 SQL 程式，可帶參數減少網路往返、防 SQL Injection、集中商業邏輯、可授權執行邏輯散落資料庫、跨 DBMS 不可攜、版控困難
觸發器
Trigger		事件（INSERT/UPDATE/DELETE）發生時自動執行強制完整性、自動寫稽核軌跡難以除錯（隱藏的副作用）、可能連鎖觸發、影響效能
-- View：只開放非敏感欄位給一般使用者
CREATE VIEW 員工公開資料 AS
SELECT 員工編號, 姓名, 部門代碼 FROM 員工;   -- 刻意不含薪資
GRANT SELECT ON 員工公開資料 TO 一般使用者;

-- Trigger：自動記錄薪資變更軌跡（稽核用）
CREATE TRIGGER trg_薪資稽核
AFTER UPDATE OF 薪資 ON 員工
FOR EACH ROW
BEGIN
    INSERT INTO 薪資異動紀錄(員工編號, 原薪資, 新薪資, 異動時間, 異動者)
    VALUES (:OLD.員工編號, :OLD.薪資, :NEW.薪資, CURRENT_TIMESTAMP, USER);
END;
✅ 公部門申論加分角度 談 View 時可寫：「機關可藉檢視表實現最小權限原則，例如人事系統僅開放不含薪資與身分證字號之 View 給一般單位，符合《個人資料保護法》必要範圍之要求。」
談 Trigger 時可寫：「可用於自動產生稽核軌跡（Audit Trail），符合《資通安全管理法》對存取紀錄保存之要求。」

第 6 章　交易管理與並行控制

6-1　交易（Transaction）與 ACID

特性英文意義由誰保障
原子性Atomicity全部成功或全部失敗，不容許做一半復原機制（Undo Log）
一致性Consistency交易前後資料庫都須滿足所有完整性限制限制條件 + 應用程式邏輯
隔離性Isolation並行執行的交易互不干擾，結果如同循序執行並行控制（鎖定、MVCC）
持久性Durability一旦 COMMIT，即使系統當機也不會遺失Redo Log + 寫入非揮發性儲存
🧒 用轉帳理解 ACID

A 帳戶轉 1000 元給 B。這件事包含兩個動作：A 減 1000、B 加 1000。

  • 原子性：不可以只做「A 減 1000」就當機——錢會人間蒸發。要嘛兩個都做，要嘛都不做。
  • 一致性：轉完後「A + B 的總額」必須跟轉之前一樣。
  • 隔離性：如果同時有另一筆交易在查 A 的餘額，它不該看到「已扣款但還沒入帳」的中間狀態。
  • 持久性：銀行螢幕顯示「轉帳成功」之後拔插頭，重開機錢還是要在 B 那裡。

6-2　並行問題（四種，必考）

問題情境白話
遺失更新
Lost Update		 T1 讀 X=100，T2 讀 X=100，T1 寫 X=110，T2 寫 X=120 T1 的修改被覆蓋掉了，像沒發生過
髒讀
Dirty Read		 T1 改 X 但未 COMMIT，T2 讀到新值，之後 T1 ROLLBACK T2 讀到從未真正存在的資料
不可重複讀
Non-repeatable Read		 T1 讀 X=100 → T2 改 X=200 並 COMMIT → T1 再讀 X=200 同一筆資料，讀兩次值不同
幻讀
Phantom Read		 T1 查「薪資>5萬」得 10 筆 → T2 新增一筆符合條件並 COMMIT → T1 再查得 11 筆 同一查詢，列數變多（憑空出現）
💡 不可重複讀 vs 幻讀，一句話分清 不可重複讀是「同一列的值變了」（UPDATE 造成）；
幻讀是「列的數量變了」（INSERT / DELETE 造成）。
這兩者的區別是高頻考點，一定要能講清楚。

6-3　隔離等級（Isolation Level）

隔離等級髒讀不可重複讀幻讀效能
Read Uncommitted❌ 可能❌ 可能❌ 可能最好
Read Committed✅ 防止❌ 可能❌ 可能好（多數 DBMS 預設）
Repeatable Read✅✅ 防止❌ 可能中（MySQL 預設）
Serializable✅✅✅ 防止最差
⚠️ 這是典型的取捨（Trade-off）題 隔離等級越高 → 一致性越好，但並行度越低、效能越差。

申論寫法：「機關系統應依業務性質選擇隔離等級。涉及金流、選課額度等不容錯誤之交易，宜採 Serializable 或搭配悲觀鎖定；一般查詢報表類作業採 Read Committed 即可，以兼顧效能。」

6-4　鎖定機制（Locking）

鎖類型又稱可否共存
共享鎖 S（Shared）讀鎖S 與 S 可以共存（多人同時讀沒問題）
互斥鎖 X（Exclusive）寫鎖X 與任何鎖都不能共存
📐 兩階段鎖定協定（2PL, Two-Phase Locking） 成長階段（Growing Phase）：只能加鎖，不可解鎖
收縮階段（Shrinking Phase）：只能解鎖，不可加鎖

→ 可保證可序列化（Serializability），但不保證不會死結

嚴格 2PL（Strict 2PL）：所有 X 鎖都保留到交易結束（COMMIT/ROLLBACK）才釋放 → 可避免連鎖回復（Cascading Rollback），實務常用。

鎖定粒度（Granularity）

粒度並行度管理成本
資料庫層級最低最低
資料表層級低低
頁層級（Page）中中
列層級（Row）最高最高

粒度越細，並行度越高，但要管理的鎖數量暴增（記憶體與 CPU 成本）。實務上 DBMS 會用鎖升級（Lock Escalation）：當某表的列鎖數量過多時，自動升級為表鎖。

6-5　死結（Deadlock）

📐 死結四條件（Coffman 條件，必須同時成立） 1. 互斥（Mutual Exclusion）：資源不可共享
2. 持有並等待（Hold and Wait）：持有資源的同時等待其他資源
3. 不可搶奪（No Preemption）：不能強行拿走別人的資源
4. 循環等待（Circular Wait）：形成等待環

破壞任一條件即可避免死結。
策略做法優缺點
預防 Prevention破壞四條件之一，如規定所有交易依相同順序取得鎖（破壞循環等待）有效但限制大
避免 Avoidance時間戳記法（Wait-Die / Wound-Wait）、銀行家演算法需事先知道資源需求
偵測與復原 Detection建立等待圖（Wait-for Graph），找到環就挑一個犧牲者（Victim）回復實務最常用；犧牲者選擇需考量成本
忽略設定逾時（Timeout），等太久就放棄最簡單，但可能誤殺正常交易
💡 實務上如何降低死結 1. 統一存取順序（例如所有交易都先鎖「帳戶表」再鎖「交易紀錄表」）
2. 縮短交易長度（別在交易中間等使用者輸入、別在交易裡呼叫外部 API）
3. 降低隔離等級（在業務允許範圍內）
4. 使用適當索引（避免全表掃描造成大量鎖定）
第 4 點最常被忽略，但實務上效果最大——沒有索引的 UPDATE 會鎖很多列。

6-6　MVCC（多版本並行控制）

現代主流 DBMS（PostgreSQL、Oracle、MySQL InnoDB）採用的機制：寫入時建立新版本，讀取時看舊版本快照。

✅ 核心優點：讀不阻塞寫，寫不阻塞讀 傳統鎖定機制下，有人在寫就不能讀。MVCC 讓讀取者去看「交易開始那一刻的快照」，因此完全不需要等待。
代價：需要額外空間存放多版本，並需定期清理舊版本（PostgreSQL 的 VACUUM）。

6-7　復原機制（Recovery）

機制用途
Undo Log記錄「舊值」，用於回復未完成的交易（保障原子性）
Redo Log記錄「新值」，用於重做已 COMMIT 但還沒寫入磁碟的交易（保障持久性）
WAL（Write-Ahead Logging）先寫日誌再改資料。這是持久性的實作基礎
檢查點 Checkpoint定期把記憶體中的變更寫入磁碟並記錄位置，縮短復原時間
📐 當機後的復原流程 1. 從最近的 Checkpoint 開始讀取日誌
2. Redo：所有已 COMMIT 的交易 → 重做（確保持久性）
3. Undo：所有未 COMMIT 的交易 → 回復（確保原子性）

備份策略（申論常結合 BCP 考）

類型內容備份時間復原時間
完整備份 Full全部資料最長最短
差異備份 Differential自上次完整備份後的變更中中（完整 + 最後一次差異）
增量備份 Incremental自上次任何備份後的變更最短最長（完整 + 所有增量）
RTO（復原時間目標）：可容忍多久救回來 → 決定備援架構（熱備援／冷備援）
RPO（復原點目標）：可容忍遺失多少資料 → 決定備份頻率與日誌傳送方式

公部門常見要求：關鍵系統 RTO ≤ 4 小時、RPO ≤ 15 分鐘。申論題談備份一定要提這兩個指標。

第 7 章　索引與查詢最佳化

7-1　索引的原理與代價

🧒 索引就是書後面的索引頁

一本 500 頁的書，你想找「正規化」這個詞。

  • 沒有索引：從第 1 頁翻到第 500 頁（全表掃描 Full Table Scan）
  • 有索引：翻到書末索引頁，看到「正規化 …… p.213」，直接跳過去

但索引有代價：索引頁本身占空間（儲存成本），而且如果書要改版新增內容，索引頁也得跟著重編（寫入成本）。

所以結論很清楚：查詢多的欄位建索引；寫入多、查詢少的表少建索引。

索引的效益索引的代價
‧ 加速 WHERE 條件過濾
‧ 加速 JOIN（結合欄位）
‧ 加速 ORDER BY / GROUP BY（B+ 樹本身有序）
‧ 唯一索引可強制唯一性
‧ 覆蓋索引可完全避免回表 		‧ 額外儲存空間
‧ INSERT／UPDATE／DELETE 變慢（每個索引都要維護）
‧ 索引過多會讓最佳化器選錯執行計畫
‧ 需定期重建以消除碎片

7-2　索引種類

種類說明
叢集索引
Clustered Index		索引順序即為資料的實體排列順序；一張表只能有一個。範圍查詢極快
非叢集索引
Non-clustered		索引與資料分開存放，索引葉節點指向資料位置；可建多個
唯一索引 Unique強制欄位值不重複（主鍵自動建立）
複合索引 Composite多欄位組成，欄位順序極重要（最左前綴原則）
覆蓋索引
Covering Index		查詢所需的全部欄位都在索引中 → 不必回表讀資料，效能最佳
部分／過濾索引只對符合條件的列建索引（如只對「未結案」的公文建）
雜湊索引 Hash等值查詢 O(1)，不支援範圍查詢與排序
點陣圖索引 Bitmap適合低基數欄位（如性別、狀態），資料倉儲常用
全文索引 Full-text支援文字內容搜尋（需分詞）
📐 複合索引的最左前綴原則（Leftmost Prefix） 建立索引 INDEX(部門代碼, 職稱, 到職日) 後：

✅ 可用到索引：
　WHERE 部門代碼 = 'D01'
　WHERE 部門代碼 = 'D01' AND 職稱 = '科員'
　WHERE 部門代碼 = 'D01' AND 職稱 = '科員' AND 到職日 > '2020-01-01'

❌ 用不到（或只能部分用到）：
　WHERE 職稱 = '科員'　（跳過了最左的部門代碼）
　WHERE 到職日 > '2020-01-01'

比喻：就像電話簿按「姓 → 名」排序。你知道姓就能快速找到；但只知道名字叫「小明」，還是得整本翻。

7-3　索引失效的常見情形（實務必考）

寫法問題改善
WHERE YEAR(到職日) = 2024欄位被函數包住，索引失效WHERE 到職日 >= '2024-01-01' AND 到職日 < '2025-01-01'
WHERE 薪資 * 12 > 600000欄位參與運算WHERE 薪資 > 50000
WHERE 姓名 LIKE '%明'前置通用字元，無法用 B+ 樹改為 LIKE '明%'，或建全文索引／反轉索引
WHERE 員工編號 = 123（欄位是字串）隱含型別轉換WHERE 員工編號 = '123'
WHERE A = 1 OR B = 2OR 兩側各有索引時可能不走索引改用 UNION，或建複合索引
SELECT *無法使用覆蓋索引，必須回表只選需要的欄位
欄位選擇性太低如「性別」只有兩個值，走索引反而慢不建索引，或改用點陣圖索引
💡 一句話總結 「索引欄位左邊不要動它」——不要包函數、不要做運算、不要讓型別被隱含轉換。這一句可以解釋上表七成的情形。

7-4　查詢最佳化

階段工作
1. 語法解析（Parse）檢查語法、語意、權限
2. 查詢改寫（Rewrite）展開 View、簡化條件、子查詢轉 JOIN
3. 產生執行計畫列舉可能的存取路徑與 JOIN 順序，估算成本
4. 執行依選定計畫取得結果

兩種最佳化方式

  • 規則式最佳化（RBO）：依固定規則（如「有索引就用索引」）。已較少使用。
  • 成本式最佳化（CBO）：依資料字典中的統計資訊（列數、值分布、索引選擇性）估算各方案成本，選最低者。現代 DBMS 的主流。
⚠️ 統計資訊過期是實務上最常見的效能問題 CBO 依賴統計資訊。若一張表從 1 千筆長到 1 千萬筆但統計資訊沒更新，最佳化器會誤判資料量很小而選擇全表掃描 → 效能突然崩掉。
對策：定期執行統計資訊更新（ANALYZE TABLE / UPDATE STATISTICS）。這是 DBA 的例行工作，也是很好的申論實務細節。

三種 JOIN 演算法

演算法作法適用
Nested Loop Join對外表每一列，掃內表一次外表小、內表結合欄位有索引
Sort-Merge Join兩表各自排序後合併兩表都大、已有排序或索引
Hash Join小表建雜湊表，大表逐列探測兩表都大、等值結合、記憶體足夠

SQL 調校檢查清單

  1. 用 EXPLAIN / EXPLAIN PLAN 看執行計畫，找出全表掃描
  2. 避免 SELECT *
  3. 把過濾條件盡早放（能寫 WHERE 就不要寫 HAVING）
  4. 用 EXISTS 取代 IN（子查詢資料量大時）
  5. 用 UNION ALL 取代 UNION（若確定無重複，可省去排序去重）
  6. 避免在索引欄位上使用函數
  7. 大量資料處理改用批次分段，避免長交易鎖住整表
  8. 定期更新統計資訊、重建碎片化索引

8-3　NoSQL 與 CAP 定理

類型資料模型代表產品適用情境
鍵值 Key-Valuekey → valueRedis、DynamoDB快取、Session、計數器
文件 DocumentJSON / BSONMongoDB、CouchDB結構多變的資料、內容管理
欄族 Column-Family依欄族存放Cassandra、HBase大量寫入、時序資料、日誌
圖形 Graph節點 + 邊Neo4j社群關係、關係鏈追查（如金流圖）
📐 CAP 定理 分散式系統無法同時滿足三者，最多只能滿足兩個：
C（Consistency）一致性：所有節點看到相同資料
A（Availability）可用性：每個請求都能得到回應
P（Partition Tolerance）分區容錯：網路分割時系統仍能運作

關鍵理解：在真實的分散式系統中，網路分割一定會發生，所以 P 是必選的。
實際的取捨是 CP（一致性優先，如 HBase、傳統 RDBMS 叢集）還是 AP（可用性優先，如 Cassandra、DynamoDB）。
🧒 CAP 用生活例子講

你和朋友各有一本共用的記帳簿（兩個節點）。突然你們失聯了（網路分割）。這時朋友要記一筆帳：

  • 選 CP（一致性優先）：「不行，我沒辦法跟你確認，先不要記。」→ 資料絕對不會不一致，但服務停擺。
  • 選 AP（可用性優先）：「先記著，等聯絡上再合帳。」→ 服務不中斷，但那段期間兩本帳不一致（最終一致性）。

哪個對？看業務。銀行轉帳選 CP（寧可不能用，也不能算錯錢）；社群按讚數選 AP（少算幾個讚沒關係，網站不能掛）。

項目ACID（RDBMS）BASE（NoSQL）
全稱Atomicity, Consistency, Isolation, DurabilityBasically Available, Soft state, Eventually consistent
一致性強一致性（立即）最終一致性（允許暫時不一致）
優先目標正確性可用性與擴充性

RDBMS vs NoSQL 的選擇

需求建議
需要複雜 JOIN 與交易一致性（財務、戶政、稅務）RDBMS
資料結構固定且需嚴格驗證RDBMS
需要水平擴充到極大規模NoSQL
資料結構多變、半結構化（IoT、日誌、感測器）NoSQL
高速讀寫、可容忍短暫不一致NoSQL
✅ 申論標準結論 「RDBMS 與 NoSQL 並非取代關係，而是互補。實務上常採混合持久化（Polyglot Persistence）：核心交易資料以 RDBMS 保障 ACID，快取與日誌以 NoSQL 提升效能與擴充性。機關導入時應依資料特性與一致性要求分別選擇，並考量現有人力之維運能力。」

第 9 章　資料庫安全與個資保護

9-1　存取控制

模型說明
DAC（自主存取控制）資料擁有者自行授權；SQL 的 GRANT／REVOKE 即屬此類
MAC（強制存取控制）由系統依安全等級（如機密／密／一般）強制決定，使用者不可自行授權
RBAC（角色存取控制）權限給角色，使用者被指派角色。實務最常用，便於人員異動管理
ABAC（屬性存取控制）依使用者、資源、環境屬性動態判斷（如「只有本轄區人員在上班時間可查」）
GRANT SELECT, INSERT ON 員工 TO 人事助理;
GRANT SELECT ON 員工公開資料 TO PUBLIC;
REVOKE INSERT ON 員工 FROM 人事助理;

-- 角色式管理（RBAC）
CREATE ROLE 人事管理者;
GRANT SELECT, INSERT, UPDATE ON 員工 TO 人事管理者;
GRANT 人事管理者 TO 王小明;   -- 人員異動只需改角色指派

9-2　資料庫常見威脅與防護

威脅說明防護
SQL Injection將惡意 SQL 混入輸入欄位參數化查詢（Prepared Statement）、ORM、輸入驗證、最小權限、錯誤訊息不外露、WAF
權限過大應用程式使用 DBA 帳號連線最小權限原則，應用程式專用帳號僅授予必要權限
資料外洩備份檔案、匯出檔未加密靜態加密（TDE）、備份加密、傳輸加密（TLS）
內部人員濫用有權限者查詢無關資料稽核軌跡、異常查詢偵測、職務分工（SoD）
特權帳號濫用DBA 可看所有資料特權帳號管理（PAM）、雙人共管、操作錄影
📐 SQL Injection 防範核心：資料與指令分離 ❌ 錯誤（字串串接）：
sql = "SELECT * FROM 使用者 WHERE 帳號='" + input + "'"
輸入 ' OR '1'='1 → 條件恆真，登入繞過

✅ 正確（參數化查詢）：
sql = "SELECT * FROM 使用者 WHERE 帳號 = ?"
stmt.setString(1, input)
→ 輸入值永遠被當成「資料」，不會被解讀為 SQL 語法

9-3　個資保護技術（公部門必考）

技術說明可否還原
加密 Encryption以金鑰轉換為密文✅ 有金鑰可還原
雜湊 Hashing單向轉換（密碼儲存必用，需加鹽 Salt）❌ 不可還原
遮罩 Masking部分隱藏（A12345****）❌
代碼化 Tokenization以無意義代碼取代，對照表另行保管✅ 有對照表可還原
去識別化移除或轉換可識別特定個人之資訊視方法而定
假名化 Pseudonymization以假名取代，保留可連結性✅ 有對應表
k-匿名 k-Anonymity確保每筆資料至少與 k−1 筆無法區分❌
差分隱私 Differential Privacy加入統計雜訊，保護個體但保留整體統計特性❌
✅ 法規連結（申論務必寫） 《個人資料保護法》：蒐集、處理、利用須有特定目的且在必要範圍內；應採行適當之安全維護措施；外洩時應查明並通知當事人。
《資通安全管理法》：公務機關應依資安責任等級辦理防護、資安事件通報應變（依等級於一定時限內通報）、定期資安稽核與演練。
資料開放：釋出前應完成去識別化，並評估重新識別風險（多個資料集交叉比對可能重新識別）。
💡 密碼儲存的正確做法（常考） ❌ 明文儲存 → 最嚴重的錯誤
❌ 只用 MD5／SHA-1 → 已可被破解，且可用彩虹表查表
✅ 使用專為密碼設計的慢速雜湊：bcrypt、scrypt、Argon2、PBKDF2
✅ 每個帳號使用不同的隨機鹽（Salt），防止彩虹表與相同密碼被看出
關鍵觀念：密碼雜湊要「刻意設計得慢」，才能抵抗暴力破解。

第 10 章　考前速記表

正規化速查

階段一句話判斷捷徑
1NF有沒有多值或重複群組欄位？看到「電話：A/B/C」就違反
2NF非鍵屬性有沒有只依賴複合主鍵的一部分？主鍵是單一欄位 → 自動符合 2NF
3NF有沒有「非鍵 → 非鍵」的遞移相依？找 X→Y→Z 的鏈

SQL 執行順序

FROM → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT
推論：WHERE 不能用聚合函數、不能用 SELECT 的別名；ORDER BY 兩者都可以用。

交易與並行速查

概念重點
ACID原子性靠 Undo、持久性靠 Redo + WAL、隔離性靠鎖／MVCC
四種並行問題遺失更新、髒讀、不可重複讀（值變）、幻讀（列數變）
四種隔離等級越高越安全越慢；Serializable 才防幻讀
2PL先只加鎖、後只解鎖 → 保證可序列化，但不防死結
死結四條件互斥、持有並等待、不可搶奪、循環等待
實務死結處理偵測（等待圖）+ 選犧牲者回復

最容易被考倒的 12 個觀念

  1. DELETE 可 ROLLBACK，TRUNCATE／DROP 不可（前者 DML、後者 DDL）。
  2. WHERE 不能用聚合函數，要用 HAVING（因為執行順序）。
  3. COUNT(*) 含 NULL，COUNT(欄位) 不含 NULL。
  4. AVG 的分母不含 NULL。
  5. NOT IN 遇到子查詢含 NULL 會回傳空集合 → 改用 NOT EXISTS。
  6. 主鍵是單一欄位就一定符合 2NF。
  7. 3NF 保證無損分解＋相依保存；BCNF 只保證無損分解。
  8. B+ 樹只有葉節點存資料且葉節點相連，故範圍查詢快。
  9. 叢集索引一張表只能有一個。
  10. 索引欄位被函數包住就失效。
  11. CAP 中 P 是必選，實際取捨是 CP 或 AP。
  12. OLTP 要高度正規化，OLAP 刻意反正規化（星狀綱要）。

申論萬用結論句

「資料庫設計須在資料一致性與查詢效能之間取得平衡；機關實務上宜以 3NF 為基準，並依實際查詢瓶頸選擇性反正規化。
此外，涉及個人資料者應依《個人資料保護法》採行適當安全維護措施，並依《資通安全管理法》建立存取稽核與備份復原機制（訂定 RTO／RPO），使技術設計與法規遵循並行。」
