第 1 章　零信任架構 (Zero Trust Architecture, ZTA)

傳統的網路安全建立在「邊界防禦（如防火牆）」上，預設「內部網路是安全的」。但隨著遠距辦公與雲端服務普及，邊界已變得模糊。零信任架構打破了這個迷思。

1-1　零信任的核心精神

📐 「Never Trust, Always Verify」 不論存取要求來自外網或內網，預設皆不信任。必須對「每一次」的存取請求進行嚴格的身分驗證與授權。

1-2　零信任三大支柱 (NIST SP 800-207)

支柱說明關鍵技術
身分 (Identity)確保是合法的人員或設備。多因子驗證 (MFA)、單一簽入 (SSO)、FIDO2
設備 (Device)檢查設備的健康狀態與合規性。端點偵測與回應 (EDR)、行動裝置管理 (MDM)
網路 (Network) / 環境限縮橫向移動的範圍。微切分 (Micro-segmentation)、軟體定義邊界 (SDP)
🎯 步驟化詳解：NIST SP 800-207 零信任控制平面 PDP 與資料平面 PEP 存取判定五部曲
  • 步驟 1使用者或設備端點發起存取請求
    主體（Subject）透過 Untrusted Network 向企業內部資源發出請求，封包直接被邊界的策略強制執行點 (Policy Enforcement Point, PEP) 攔截並暫停連線。
  • 步驟 2PEP 向上轉呈控制平面 (Control Plane)
    PEP 將請求上下文資訊（使用者憑證、設備健康度、來源 IP、時間）轉發至策略決策點 (Policy Decision Point, PDP)。
  • 步驟 3策略引擎 (Policy Engine, PE) 進行動態風險評估
    PE 比對企業安全策略，並整合外部威脅情資（Threat Intelligence）、CDM 連續診斷與緩解系統、PKI 憑證中心，綜合計算信任分數（Trust Score）。
  • 步驟 4策略管理器 (Policy Administrator, PA) 核發動態憑證
    若 PE 判定通過，PA 發送控制指令給 PEP，指示 PEP 為該主體建立僅限於本次連線、最短有效期限的即時加密通道 (mTLS)。
  • 驗算連線期間之連續性驗證 (Continuous Evaluation)
    零信任絕非「登入一次即保證安全」。連線期間若端點 EDR 偵測到惡意程式植入，PE 立即通知 PA 下達撤銷指令，PEP 瞬間中斷資料傳輸通道。
⚡ 考前 30 秒秒殺口訣卡：零信任架構核心口訣
【口訣】從不信任持續驗，控制資料兩端分；PE 決策 PA 派，PEP 邊界閘門守
  • PDP (Policy Decision Point)：由 PE（大腦，負責決策）與 PA（手腳，下達指令）組成。
  • PEP (Policy Enforcement Point)：資料平面閘道，負責實際攔截與放行封包。
  • 三大支柱：身分鑑別 (MFA/FIDO)、設備健康 (EDR/合規)、網路微切分 (限制橫向移動)。

第 2 章　軟體定義網路 (SDN) 與 NFV

2-1　SDN 的核心概念

傳統網路設備（路由器、交換器）將「大腦」與「雙手」綁在一起：

  • 控制平面 (Control Plane)：決定封包「該往哪裡走」（路由演算法、OSPF、BGP）。
  • 資料平面 (Data Plane / Forwarding Plane)：真正執行「搬運封包」的工作（硬體 ASIC 轉發）。
SDN 的精髓：將控制平面集中抽離至軟體控制器 (SDN Controller)，底層交換器退化為純粹聽令轉發的資料平面。
🎯 步驟化詳解：SDN OpenFlow 多級 Flow Table 流水線比對與動作執行推導
  • 步驟 1封包進入 Table 0（最高優先階層比對）
    封包到達 OpenFlow 交換器，首先進入 Flow Table 0。由硬體 TCAM 提取標頭欄位（進埠、來源/目的 MAC、VLAN ID、來源/目的 IP、L4 埠號）與表項之 Match Fields 進行比對。
  • 步驟 2命中 Flow Entry (Match) 累加計數器並執行指令
    若比對成功：對應的 Counters 遞增（計數封包數與位元組數）。接著執行 Instructions，包含：
    ‧ 修改封包（如重寫 VLAN 標籤或改寫 TTL）。
    ‧ 呼叫 GoTo-Table n 指令，將封包帶往下一級 Flow Table 繼續比對（流水線架構，避免單表過度龐大）。
  • 步驟 3若完全未命中 (Table-Miss) 轉送控制器
    若所有表項皆無法匹配，觸發預設的 Table-Miss 動作：包裝成 Packet-In 訊息，透過 OpenFlow 南向介面 (Southbound API) 送往集中式 SDN 控制器。
  • 驗算控制器運算與下發 Flow-Mod
    控制器依全局拓撲計算最佳路徑後，回傳 Flow-Mod 指令將新的流表項寫入交換器硬體中，並以 Packet-Out 轉發該封包，完成首封包學習！
⚡ 考前 30 秒秒殺口訣卡：SDN 三大平面與介面對照
【口訣】應用在上北向下，控制中央管全網；南向下達 OpenFlow，資料平面純轉發
  • 北向介面 (Northbound API)：應用程式（如負載平衡、QoS 策略）與控制器通訊（通常為 RESTful API）。
  • 南向介面 (Southbound API)：控制器與底層硬體交換器通訊（如 OpenFlow, NETCONF）。
  • NFV (網路功能虛擬化)：將專用硬體（如防火牆、負載平衡器）軟體化執行於通用伺服器 VM/Container 上。

第 3 章　現代網頁協定 (HTTP/2, HTTP/3, QUIC)

3-1　HTTP/2 的改良

  • 多工處理 (Multiplexing)：在單一 TCP 連線上，可以交錯傳送多個請求與回應，解決了 HTTP 層的隊頭阻塞。
  • 標頭壓縮 (HPACK)：壓縮重複的 Header，減少頻寬浪費。
  • 二進位分框 (Binary Framing)：不再使用純文字傳輸，改用電腦更容易解析的二進位格式。
  • 伺服器推送 (Server Push)：伺服器可主動將 CSS/JS 推送給客戶端，不需等客戶端解析 HTML 後才來要。

3-2　HTTP/3 與 QUIC

HTTP/2 雖然解決了 HTTP 應用層的隊頭阻塞，但底層仍然使用 TCP。只要 TCP 掉了一個封包，整個連線的滑動視窗都會卡住等待重傳（TCP 層的隊頭阻塞）。

特性說明
基於 UDP 的 QUIC 協定HTTP/3 捨棄了 TCP，改用基於 UDP 開發的 QUIC 協定。由 QUIC 在應用層實作可靠傳輸與壅塞控制。
徹底解決 TCP 隊頭阻塞因為多個串流在 QUIC 中是獨立的，掉了一個封包只會影響該串流，其他串流可繼續傳輸。
連線遷移 (Connection Migration)連線不綁定 IP:Port 四元組，而是依據 64-bit 的 Connection ID。手機從 Wi-Fi 切換到 5G 行動網路時，連線完全不會中斷。
零往返時間 (0-RTT) 交握結合了傳輸層與加密層 (TLS 1.3) 的交握，以前連線過的伺服器可以直接傳送資料，連線速度極快。
🎯 步驟化詳解：HTTP/2 多工串流隊頭阻塞 vs HTTP/3 QUIC 連線遷移解構
  • 步驟 1解析 HTTP/2 之單一 TCP 虛擬串流機制
    HTTP/2 將連線劃分為多個帶有 Stream ID 的二進位 Frame。雖然應用層可交錯發送 Stream 1 (網頁) 與 Stream 2 (圖片)，但所有 Stream 最終打包在同一個 TCP 連線的 Byte Stream 中。
  • 步驟 2追蹤 TCP 封包遺失時的隊頭阻塞 (HOL Blocking)
    當 Stream 1 的 TCP 封包在網路中遺失時，受限於 TCP 的按序交付（In-order Delivery）保證，接收端作業系統核心的 TCP 滑動視窗停止前進，即使 Stream 2 的資料封包完好到達，也必須滯留在緩衝區內無法上交應用層！
  • 步驟 3HTTP/3 QUIC 如何徹底杜絕 HOL Blocking
    QUIC 直接建立在 UDP 之上，將可靠性保證提升至各別串流層面：
    ‧ Stream 1 遺失封包，只有 Stream 1 進行 ACK 偵測與重傳。
    ‧ Stream 2 不受任何牽連，核心立即將 Stream 2 資料交付應用程式渲染，串流之間完全相互獨立！
  • 驗算連線遷移 (Connection Migration) 流程
    傳統 TCP 依賴 {SrcIP, SrcPort, DstIP, DstPort} 四元組。使用者走出門外從 Wi-Fi 跳至 4G 時，SrcIP 改變，TCP 連線必定斷線重連。QUIC 使用 Connection ID (CID) 標識連線，IP 變更時只需發送一個更新 Probe 封包，下載作業零中斷！

第 4 章　IPv6 深度解析與過渡機制

4-1　IPv6 封包標頭簡化

IPv6 標頭大小固定為 40 Bytes（IPv4 為 20~60 Bytes）。為了加速硬體路由，IPv6 移除了 IPv4 標頭中一些不必要的欄位：

  • 移除 Checksum：因為第二層 (Ethernet) 與第四層 (TCP/UDP) 都有 Checksum，網路層不再重複檢查。
  • 移除 Fragmentation (分段) 欄位：IPv6 路由器不負責分段，若封包過大直接丟棄並回傳 ICMPv6 "Packet Too Big"。分段只能由來源端主機執行。

4-2　IPv4 到 IPv6 的過渡機制

技術說明
雙堆疊 (Dual Stack)設備同時跑 IPv4 與 IPv6 兩個協定。最直接，但仍需消耗 IPv4 位址。
穿隧技術 (Tunneling)把 IPv6 封包「包在」IPv4 封包裡面（如 6to4, Teredo），藉此通過不支援 IPv6 的 IPv4 網路。
位址轉換 (NAT64 / DNS64)將 IPv6 標頭轉換為 IPv4 標頭，讓純 IPv6 主機可暢通存取純 IPv4 網頁。
🎯 步驟化詳解：DNS64 與 NAT64 協同運作之封包位址合成與轉譯四部曲

【轉換情境】純 IPv6 客戶端 (2001:db8:1::10) 欲存取僅具備 IPv4 之伺服器 (192.0.2.1)。

  • 步驟 1DNS 查詢與 AAAA 合成 (DNS64)
    客戶端發出 AAAA 記錄查詢。DNS64 伺服器向上游查無 AAAA 紀錄，僅查到 IPv4 A 紀錄 192.0.2.1。DNS64 取出該 IPv4 位址並加上知名前綴（Well-Known Prefix 64:ff9b::/96），合成出虛擬 IPv6 位址：64:ff9b::192.0.2.1（即 64:ff9b::c000:0201）回傳給客戶端。
  • 步驟 2客戶端向合成位址發送 IPv6 封包
    客戶端發送來源為 2001:db8:1::10、目的為 64:ff9b::c000:0201 之 IPv6 封包。路由表將此前綴指引至 NAT64 閘道器。
  • 步驟 3NAT64 執行協定轉譯與狀態表記錄
    NAT64 閘道器剝除 IPv6 標頭：
    ‧ 將目的 IPv6 位址還原為 IPv4：192.0.2.1。
    ‧ 將來源 IPv6 位址透過 NAT 轉換為閘道自身之公開 IPv4 位址及動態連接埠。
    ‧ 重算 IPv4 Checksum 與 TCP Checksum，將 IPv4 封包轉發至網際網路。
  • 驗算反向回應封包重組
    IPv4 伺服器回傳回應封包，NAT64 閘道查表比對 Session，將 IPv4 標頭封裝回原本客戶端的 IPv6 標頭送回。整個過程對純 IPv6 客戶端與純 IPv4 伺服器完全透明！

第 5 章　進階 VPN 與 IPsec 實作

5-1　IPsec 協定套件

IPsec 運作於網路層 (Layer 3)，可保護 IP 封包的機密性與完整性。

核心協定功能說明
AH (Authentication Header)提供完整性與資料來源驗證。不提供機密性 (無加密)。
ESP (Encapsulating Security Payload)提供機密性 (加密)、完整性與身分驗證。實務上最常使用。
IKE (Internet Key Exchange)用來在通訊雙方之間建立安全關聯 (SA) 並自動交換金鑰。

5-2　IPsec 的兩種運作模式

模式保護範圍應用場景
傳輸模式 (Transport Mode)只加密/驗證 IP 封包的 Payload (資料部分)。原本的 IP 標頭保留不變。Host-to-Host (主機到主機的端點連線)
通道模式 (Tunnel Mode)加密/驗證 整個原始 IP 封包，並在外面加上一個新的 IP 標頭（通常是 VPN 閘道器的 IP）。Site-to-Site (分公司到總公司的 VPN)
🎯 步驟化詳解：IPsec 通道模式 (Tunnel Mode) ESP 封裝結構位元組拆解五步驟
  • 步驟 1保留原始 IP 封包作為資料載體
    原始封包結構：[Original IP Header] [TCP Header] [Data]。原始 IP 標頭含有內部私有 IP 位址（如 10.0.1.5）。
  • 步驟 2附加 ESP Trailer (尾端)
    在資料尾端加入 Padding（填充以符合區塊加密區塊倍數）、Pad Length、以及 Next Header（標註內部被包住的是 IP 協定，值為 4）。
  • 步驟 3執行加密 (Encryption)
    使用協商好的對稱式演算法（如 AES-GCM 或 AES-CBC），對 [Original IP Header] [TCP Header] [Data] [ESP Trailer] 進行整體加密！原始標頭被徹底加密隱蔽。
  • 步驟 4附加 ESP Header (開頭) 與 ESP Auth (認證尾端)
    ‧ 前端加入 ESP Header：包含 32 位元 SPI（安全關聯索引）與 Sequence Number（防重送攻擊）。
    ‧ 尾端加入 ESP Auth (ICV， integrity Check Value)：利用 HMAC 演算法對 ESP Header 及其加密載荷進行數位簽章。
  • 驗算附加外部全新 IP 標頭 (New Outer IP Header)
    最外層加上公網 VPN 閘道器的實體 IP 標頭。最終封包在公開網際網路傳輸時，任何中間路由器僅能看見外部閘道 IP，內部原始來源、目的與傳輸內容全部受到極致加密保護！
⚡ 考前 30 秒秒殺口訣卡：IPsec 封裝與協定秒殺口訣
【口訣】AH 認證不加密，ESP 全包最安心；傳輸模式保載荷，通道外掛新標頭
  • AH 與 NAT 不相容：因為 AH 驗證包含外部 IP 標頭，經 NAT 修改 IP 後 Checksum 必定損壞！
  • ESP 通道模式：企業 Site-to-Site VPN 標準首選，具備防重送、防竄改與強加密三合一保護。

第 6 章　次世代網路與物聯網 (5G/6G, 衛星, IoT)

隨著無線通訊與衛星技術的突破，網路的範圍已經從地表延伸到太空，連線的對象也從「人」變成了「萬物」。

6-1　5G 與網路切片技術 (Network Slicing)

5G 的三大特性是：大頻寬 (eMBB)、低延遲 (URLLC)、大連結 (mMTC)。為了一次滿足這三個截然不同的需求，5G 引入了「網路切片」技術。

📐 網路切片 (Network Slicing) 是什麼？ 想像一條實體的高速公路（實體 5G 網路），我們可以把它「虛擬切分」成好幾條專用車道（切片）：
- 車道 A（大頻寬 eMBB）：專門給看 4K/8K 影片的人走，路很寬，但不用太管煞車反應時間。
- 車道 B（低延遲 URLLC）：專門給「自駕車」與「遠距醫療」走，這條路保證絕對不塞車、反應極快，確保開刀不會卡頓。
- 車道 C（大連結 mMTC）：專門給幾百萬個路燈、水表（物聯網）走，這些設備傳送的資料很小，但數量極多。
結論：同一組實體設備，透過軟體定義網路 (SDN)，切出多個各自獨立的虛擬網路，互不干擾。

6-2　低軌衛星通訊 (LEO, 如 Starlink)

衛星種類特色與優缺點
同步衛星 (GEO)高度約 36,000 公里，和地球自轉速度一樣（看起來永遠停在天空同一個點）。涵蓋範圍大（三顆就能覆蓋全球），但延遲極高 (約 250ms 以上)，打遊戲會非常卡。
低軌衛星 (LEO)高度僅 500~2,000 公里。延遲超低 (約 20~40ms)，媲美光纖！缺點是因為飛太低，轉得很快，需要發射成千上萬顆衛星（衛星星系）才能確保地面永遠收得到訊號。

6-3　物聯網通訊協定 (MQTT)

物聯網 (IoT) 設備通常電池很小、網路很爛（例如裝在深山裡的溫濕度計）。如果用傳統網頁的 HTTP 來傳資料，標頭 (Header) 太肥大，會耗光電池。因此出現了 MQTT。

🎯 步驟化詳解：MQTT 協定 QoS 2 (Exactly Once) 四向交握保證不重複機制
  • 步驟 1發布者送出 PUBLISH (QoS 2)
    Publisher 送出帶有 Message ID 的 PUBLISH 封包，並將訊息存放在本地端 Outbox 佇列中。
  • 步驟 2Broker 確認收件並回傳 PUBREC (Publish Received)
    Broker 收到訊息，儲存 Message ID 防止重複處理，並回傳 PUBREC 告知「已收到第一段確認」。
  • 步驟 3發布者釋放狀態並送出 PUBREL (Publish Release)
    Publisher 收到 PUBREC 後，確認訊息已安全送達，將本機 Outbox 狀態清空，發送 PUBREL 封包給 Broker，通知 Broker 可以正式向訂閱者分發。
  • 驗算Broker 結束事務回傳 PUBCOMP (Publish Complete)
    Broker 收到 PUBREL 後，徹底刪除暫存狀態並回傳 PUBCOMP。四向交握確保在任何網路閃斷重傳情境下，訊息絕對不會遺失且嚴格只被處理一次（Exactly Once）！
