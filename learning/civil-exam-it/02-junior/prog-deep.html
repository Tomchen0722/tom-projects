🧒 白話說明

程式設計的考題有兩種：「這段程式的輸出是什麼」與「請寫一段程式」。

第一種靠追蹤表（trace table）——一格一格填，不用聰明，只要不急。

第二種靠固定的解題模板——排序、搜尋、遞迴、字串處理，各有標準寫法。

而公務程式最容易出錯的地方：差一錯誤、邊界條件、期限計算、金額型別——這一頁全部處理。

深化 1　追蹤表：把「看不懂」變成「填格子」

1-1　標準做法

① 把所有變數列成表格的欄
② 每執行一行就填一列
③ 迴圈每一輪都要填
④ 特別標記「條件判斷的結果」
例題： 
int n = 5, sum = 0, i = 1;
while (i <= n) {
    if (i % 2 == 1) sum = sum + i;
    i = i + 1;
}
// sum = ?
輪次ii ≤ 5 ?i%2==1 ?sum
進入前1——0
11是是1
22是否1
33是是4
44是否4
55是是9
66否 → 結束—9
答案：sum = 9（1+3+5）
💡 追蹤表的三個關鍵習慣
① 「進入前」那一列一定要寫——初始值錯了全盤皆錯
② 迴圈條件不成立的那一輪也要寫——那決定了迴圈跑幾次
③ i++ 與 ++i 在條件式中的差別要特別小心

1-2　巢狀迴圈的追蹤

for (i = 1; i <= 3; i++)
    for (j = 1; j <= i; j++)
        printf("%d%d ", i, j);
ij 的範圍輸出
1111
21, 221 22
31, 2, 331 32 33
總輸出：11 21 22 31 32 33（共 6 次 = 1+2+3）
💡 巢狀迴圈的執行次數速算
內層跑 i 次，外層 i 從 1 到 n → 總次數 = 1+2+…+n = n(n+1)/2
這也是「為什麼氣泡排序是 O(n²)」的來源。
✅ 深化 1 必背結論 ① 追蹤表要寫「進入前」與「條件不成立」的那一列。
② 巢狀迴圈 j 到 i 的總次數 = n(n+1)/2。
③ 追程式不需要聰明，只需要不急、一格一格填。

深化 2　迴圈的邊界：差一錯誤的系統性防範

2-1　四種迴圈寫法的執行次數

寫法執行次數i 的最後值
for (i=0; i<n; i++)n 次n
for (i=0; i<=n; i++)n+1 次n+1
for (i=1; i<=n; i++)n 次n+1
for (i=1; i<n; i++)n−1 次n
⚠️ 陣列索引的邊界（最常見的執行期錯誤）
大小為 n 的陣列，合法索引是 0 ～ n−1。
寫成 for (i=0; i<=n; i++) a[i]=… → 存取 a[n] 越界。

C 語言不會報錯，而是「悄悄改寫了旁邊的記憶體」——這是緩衝區溢位的來源。

2-2　差一錯誤的系統性防範

每次寫完迴圈，用三個具體值驗證：
① n = 0（空的情形）——會不會執行到不該執行的？
② n = 1（只有一個）——邊界是否正確？
③ n = 2（最小的「多個」）——迴圈與交換是否正確？
💡 半開區間的好處
用 [起, 迄)（包含起、不含迄）而非 [起, 迄]：
① 長度 = 迄 − 起（不用 +1）
② 空區間自然表示為 [x, x)
③ 相鄰區間可以無縫接合：[0,5) 與 [5,10)

這與資料庫查詢用「日期半開區間」是同一個道理。

2-3　公務系統最常見的邊界錯誤

法規文字正確條件寫錯的後果
「未滿 65 歲」age < 65邊界案例被系統性錯誤處理——每一件都是違法處分
「年滿 65 歲」age >= 65
「5,000 元以下」amount <= 5000
「超過 5,000 元」amount > 5000
⚠️ 每個門檻值都要測三個點：門檻−1、門檻、門檻+1
「年滿 65 歲」→ 測 64 歲 364 天、65 歲當天、65 歲又 1 天
「5,000 元以上」→ 測 4,999、5,000、5,001

這是防止「系統性違法」最直接的方法。
✅ 深化 2 必背結論 ① for(i=0;i<n;i++) 跑 n 次；<= 會多跑一次並可能越界。
② 用 n=0、1、2 三個值驗證每一個迴圈。
③ 每個門檻值測三個點：門檻−1、門檻、門檻+1。

深化 3　遞迴的三要素與展開技巧

3-1　遞迴的三個必要元素

元素說明缺少的後果
基底條件何時停止遞迴無限遞迴 → 堆疊溢位
遞迴呼叫呼叫自己不是遞迴
朝基底收斂每次呼叫都要更接近基底條件永遠到不了基底

3-2　展開技巧：由小到大，不要往下追

int f(int n) {
    if (n <= 1) return 1;
    return n * f(n - 1);
}
錯誤的做法：從 f(5) 往下追 → f(4) → f(3)… 很容易亂掉

正確的做法：由小到大列表
nf(n)計算
11基底
222 × f(1) = 2 × 1
363 × f(2) = 3 × 2
4244 × f(3) = 4 × 6
51205 × f(4) = 5 × 24

3-3　常考的遞迴函數

函數定義前幾項
階乘n × f(n−1)，f(1)=11, 2, 6, 24, 120
費氏數列f(n−1) + f(n−2)，f(1)=f(2)=11, 1, 2, 3, 5, 8, 13, 21
河內塔2·f(n−1) + 11, 3, 7, 15, 31 = 2ⁿ − 1
Ackermann成長極快不會考計算
💡 河內塔的公式推導
移動 n 個盤子 = 先移上面 n−1 個到中間 + 移最大的 1 個 + 再移 n−1 個過去
f(n) = 2·f(n−1) + 1，f(1) = 1
展開：1, 3, 7, 15, 31, 63… → f(n) = 2ⁿ − 1
⚠️ 遞迴費氏數列的效能陷阱
樸素遞迴的 fib(n) 時間複雜度是 O(2ⁿ)——因為 同一個子問題被重複計算無數次。
fib(40) 用遞迴要跑很久，用迴圈或記憶化只要瞬間。

這正是動態規劃存在的理由（重疊子問題）。

3-4　遞迴 vs 迴圈

遞迴迴圈
可讀性樹、圖等結構較直觀簡單重複較清楚
記憶體每層都佔用堆疊 → 深度過大會溢位固定
效能有函數呼叫成本較快
適用樹走訪、分治、回溯已知次數的重複
✅ 深化 3 必背結論 ① 遞迴三要素：基底條件、遞迴呼叫、朝基底收斂。
② 展開時「由小到大列表」，不要往下追。
③ 河內塔 = 2ⁿ − 1；樸素遞迴費氏是 O(2ⁿ)，須用記憶化或迴圈。

深化 4　陣列與字串處理的標準模板

4-1　五個必背模板

① 找最大值 
max = a[0];                     // 注意：不要初始化為 0
for (i = 1; i < n; i++)
    if (a[i] > max) max = a[i];
② 反轉陣列 
for (i = 0; i < n/2; i++) {       // 注意：只跑一半
    tmp = a[i]; a[i] = a[n-1-i]; a[n-1-i] = tmp;
}
③ 線性搜尋 
found = -1;
for (i = 0; i < n; i++)
    if (a[i] == target) { found = i; break; }
④ 二分搜尋（陣列須先排序） 
lo = 0; hi = n - 1;
while (lo <= hi) {                // 注意是 <=
    mid = lo + (hi - lo) / 2;     // 避免 (lo+hi) 溢位
    if (a[mid] == target) return mid;
    else if (a[mid] < target) lo = mid + 1;
    else hi = mid - 1;
}
return -1;
⑤ 氣泡排序 
for (i = 0; i < n-1; i++)
    for (j = 0; j < n-1-i; j++)   // 每輪後面已排好，可少比一個
        if (a[j] > a[j+1]) swap(a[j], a[j+1]);
⚠️ 三個常見的模板錯誤
① 找最大值時把 max 初始化為 0 → 若陣列全為負數就會錯
② 反轉陣列跑滿 n 次 → 換兩次等於沒換
③ 二分搜尋用 (lo+hi)/2 → 大數時可能溢位；應用 lo + (hi-lo)/2

4-2　字串處理的三個要點

要點說明
C 字串以 '\0' 結尾「abc」實際佔 4 個位元組
strlen 不含 '\0'strlen("abc") = 3；但 sizeof 陣列 = 4
中文的長度UTF-8 中一個中文字通常是 3 個位元組——用位元組計算長度會出錯
💡 公務系統的字串陷阱
「姓名最多 10 個字」——是 10 個「字元」還是 10 個「位元組」？
若用位元組計算，中文姓名只能填 3 個字。

而地址、案由等欄位若長度限制設計錯誤，會導致資料被截斷——這在公文上就是「記載不完整」。
✅ 深化 4 必背結論 ① 找最大值初始化為 a[0]，不是 0；反轉陣列只跑 n/2 次。
② 二分搜尋用 lo + (hi−lo)/2 避免溢位；條件是 lo <= hi。
③ 中文在 UTF-8 通常佔 3 位元組——長度限制須以字元數而非位元組數計。

深化 5　參數傳遞：傳值、傳址與傳參考

方式傳遞的是能否改變原變數語言例
傳值（by value）值的複本不能C 的一般參數
傳址（by address）位址的複本能（透過解參考）C 的指標參數
傳參考（by reference）變數本身的別名能C++ 的 & 參數
經典考題：交換兩個變數 
// ✘ 錯誤：傳值，改不到原變數
void swap(int a, int b) { int t=a; a=b; b=t; }

// ✔ 正確：傳址
void swap(int *a, int *b) { int t=*a; *a=*b; *b=t; }
// 呼叫：swap(&x, &y);
⚠️ 陣列名稱本身就是位址
所以把陣列傳進函數，函數內的修改會影響原陣列——即使看起來像傳值。

這是考題常設的陷阱：「傳陣列進去修改後，主程式的陣列變了嗎？」答案是「變了」。
💡 物件在多數語言中是「傳參考的值」
Java、Python、JavaScript 傳物件時，傳的是參考的複本：
✔ 修改物件的內容 → 原物件會變
✘ 把參數整個指向新物件 → 原物件不會變
✅ 深化 5 必背結論 ① 傳值改不到原變數；傳址與傳參考可以。
② 陣列名稱即位址，傳陣列等同傳址。
③ 多數語言傳物件是「傳參考的值」：可改內容，不可重新指向。

深化 6　變數範圍、生命週期與靜態變數

類型範圍生命週期存放位置
區域變數所在區塊離開區塊即消失堆疊 stack
全域變數整個程式程式執行期間資料區
靜態區域變數所在區塊（範圍不變）整個程式（值會保留）資料區
動態配置依指標而定直到 free/delete堆積 heap
經典考題： 
void f() {
    static int count = 0;   // 只初始化一次
    count++;
    printf("%d ", count);
}
// 呼叫 f() 三次的輸出？
答案：1 2 3——因為 static 變數只在第一次初始化，之後保留上次的值。
若沒有 static，輸出會是 1 1 1。
💡 static 的兩個不同意義（考題常混）
① 用在區域變數：延長生命週期（值保留）
② 用在全域變數或函數：限制範圍在本檔案內（不對外公開）
⚠️ 全域變數在公務系統中的風險
①任何地方都能改，出問題難以追查 ②多執行緒下的競爭條件 ③難以測試。

而在 Web 系統中，若把「目前使用者」存在全域變數——多人同時操作時，可能出現「甲看到乙的資料」的嚴重個資問題。
✅ 深化 6 必背結論 ① 區域變數在堆疊、動態配置在堆積；static 區域變數在資料區且值保留。
② static 用於區域變數是「延長生命」，用於全域是「限制範圍」。
③ Web 系統中用全域變數存使用者狀態，可能造成跨使用者的資料外洩。

深化 7　指標與記憶體：常考的四種錯誤

錯誤成因後果
空指標解參考指標為 NULL 卻去存取程式崩潰
懸空指標指向已被釋放的記憶體行為不可預測；可能被利用為漏洞
記憶體洩漏配置了卻沒釋放長時間執行後記憶體耗盡
緩衝區溢位寫入超過配置的範圍覆蓋相鄰記憶體；經典的安全漏洞
各自的防範：
① 使用前檢查是否為 NULL
② 釋放後立即設為 NULL
③ 配置與釋放成對出現；現代語言用自動記憶體管理或 RAII
④ 使用有邊界檢查的函數（如 strncpy 而非 strcpy）並驗證輸入長度
⚠️ 緩衝區溢位為何是嚴重的安全漏洞
因為它可能覆蓋堆疊上的「返回位址」——攻擊者可藉此讓程式跳到他指定的位置執行程式碼。

這是「輸入驗證」為何如此重要的根本原因：不驗證長度，就等於讓外部輸入決定程式的執行流程。
💡 現代語言的解法
Java、Python、C# 等有自動記憶體管理與陣列邊界檢查，大幅減少這四類錯誤。
但代價是效能開銷與 GC 停頓——而且邏輯錯誤（如差一錯誤）仍然存在。
✅ 深化 7 必背結論 ① 四種記憶體錯誤：空指標、懸空指標、記憶體洩漏、緩衝區溢位。
② 釋放後立即設 NULL；配置與釋放成對。
③ 緩衝區溢位可覆蓋返回位址，是經典的安全漏洞——輸入驗證是根本防線。

深化 8　物件導向的四大特性與實際差別

特性意義公務系統的應用
封裝隱藏內部實作，只開放介面金額欄位設為私有，只能透過檢查過的方法修改
繼承子類別取得父類別的特性各類申請案共用「案件」的基本屬性
多型同一個呼叫，依實際型別執行不同行為不同補助類別有各自的資格判定，但呼叫方式相同
抽象只定義「該有什麼」，不定義「怎麼做」定義審查流程的介面

8-1　多型的兩種形式（考題常混）

形式又稱決定時機做法
覆寫 Override執行期多型執行期子類別重新定義父類別的方法（簽章相同）
多載 Overload編譯期多型編譯期同名但參數不同的多個方法
💡 記法
Override（覆蓋）：ride = 騎上去，把父類別的蓋掉 → 簽章必須相同
Overload（多載）：load = 裝載，裝很多個同名的 → 參數必須不同

8-2　繼承 vs 組合

繼承組合
關係is-a（是一種）has-a（有一個）
耦合緊（父類別改變影響所有子類別）鬆
彈性編譯期決定執行期可換
⚠️ 「優先使用組合而非繼承」是現代設計的共識
因為繼承層級過深時：①改父類別會影響所有子類別 ②難以理解某個方法到底在哪裡定義 ③無法在執行期改變行為。

公務系統的例子：「補助案」不應繼承出十幾種子類別；
而應以「案件 ＋ 可替換的資格判定策略」組合——這樣新增一種補助只要加一個策略，不用改既有程式。
✅ 深化 8 必背結論 ① 四大特性：封裝、繼承、多型、抽象。
② Override 是執行期多型（簽章相同）；Overload 是編譯期多型（參數不同）。
③ 優先使用組合而非繼承——耦合較鬆且執行期可替換。

深化 9　例外處理與防禦性程式設計

9-1　例外處理的三個原則

原則說明
只捕捉能處理的例外捕捉了卻什麼都不做（吞掉例外）比不捕捉更糟
資源一定要釋放用 finally 或自動資源管理
錯誤訊息分兩套使用者看簡短的，日誌記詳細的
⚠️ 「吞掉例外」是最糟的做法
try { doSomething(); }
catch (Exception e) { }   // ✘ 什麼都不做
結果：程式看起來正常，但實際上什麼都沒做——而且沒有任何線索。

在公務系統中，這可能表現為「民眾以為送出成功，但案件根本沒有建立」。

錯誤做法正確做法

輸入錯誤「格式錯誤」「身分證號應為 1 個英文字母加 9 個數字」
💡 「服務代碼」是關鍵設計
畫面上不洩漏任何內部資訊，但客服能據此在日誌中精確找到那一次錯誤——兼顧資安與服務。

10-1　期限計算的正確實作

規則依據
始日不計算在內（原則）行政程序法第 48 條
公布日算第 1 日（例外！）中央法規標準法第 13 條
末日為休息日則順延行程法第 48 條
「14 個工作日」與「14 日」完全不同視法規用語
寄存送達經 10 日生效影響救濟期間的起算
⚠️ 這是資訊系統最容易造成「系統性違法」的一類錯誤
算錯一天 → 可能把「未逾期」誤判為「逾期」而駁回 → 每一件都是違法處分。

對策：①期限規則寫成參數而非寫死 ②建立假日表並每年維護 ③以法規條文逐項設計測試案例 ④上線後抽樣人工驗算。

10-2　條件判斷的順序陷阱

// ✘ 錯誤：第二個條件永遠到不了
if (income < 800000) rate = 0.1;
else if (income < 500000) rate = 0.2;   // 永遠不會執行！

// ✔ 正確：由小到大或由嚴到寬
if (income < 500000) rate = 0.2;
else if (income < 800000) rate = 0.1;
💡 這種錯誤的可怕之處：不會報錯
程式跑得好好的，只是某個級距的人永遠被套用錯誤的規則——而且可能好幾年都沒有人發現。

防範：用決策表列出所有級距，並為每一個級距至少設計一個測試案例。

原則：內部一律以標準日期型別（西元）儲存，僅在顯示與輸入時轉換。

民國年 = 西元年 − 1911

深化 13　遞迴的完整思考法：從展開到轉迴圈

13-1　寫遞迴的三個必要問題

📐 三問 ①終止條件是什麼？（什麼情況直接回答，不再遞迴）
②如何縮小問題？（每次呼叫必須更接近終止條件）
③如何用子問題的答案組出答案？

三問缺一：缺①或②會無窮遞迴 → 堆疊溢位；缺③會算錯。

13-2　追蹤遞迴的正確方法

從終止條件往回算，不要從最外層往下想。

例：f(n) = n × f(n-1)，f(1) = 1，求 f(5)

f(1) = 1 → f(2) = 2×1 = 2 → f(3) = 3×2 = 6 → f(4) = 4×6 = 24 → f(5) = 5×24 = 120

考場技巧：在題目旁邊由小到大列出 f(1)、f(2)、f(3)…，五秒鐘就能算出來，比展開遞迴樹快得多。

13-3　遞迴的效能陷阱

寫法複雜度f(40) 大約要
單純遞迴費氏數列O(2ⁿ)數秒到數十秒
記憶化遞迴O(n)瞬間
迴圈O(n)瞬間
📐 為什麼單純遞迴這麼慢 算 f(5) 時，f(3) 被算了 2 次、f(2) 被算了 3 次、f(1) 被算了 5 次——
大量重複計算。n 越大重複越誇張。

解法：把算過的存起來（記憶化），這就是動態規劃的核心思想。

13-4　遞迴改迴圈

遞迴類型能否輕易改迴圈說明
尾遞迴可以遞迴呼叫是最後一個動作，直接改成迴圈
線性遞迴（費氏）可以用兩個變數往前推
樹狀遞迴（走訪）較難需自行用堆疊模擬

什麼時候該用遞迴：問題本身有遞迴結構（樹走訪、目錄搜尋、分治法）時，遞迴寫起來清楚很多。
什麼時候不該：深度可能很大（堆疊溢位風險）、或有大量重複子問題（改用 DP）。

✅ 深化 13 必背結論 ① 三問：終止條件、縮小問題、組合子答案
② 追蹤遞迴要從終止條件往回算，考場最快
③ 單純遞迴費氏是 O(2ⁿ)——重複計算是元凶
④ 尾遞迴易改迴圈；樹狀遞迴需用堆疊模擬

深化 14　迴圈與邊界：差一錯誤的完整防範

14-1　迴圈次數的計算公式

迴圈次數備註
for(i=0; i<n; i++)n最標準的寫法
for(i=0; i<=n; i++)n+1陣列會越界
for(i=1; i<=n; i++)n從 1 開始的寫法
for(i=a; i<b; i+=d)⌈(b−a)/d⌉步進不為 1 時
for(i=n; i>0; i/=2)約 log₂n對數次

14-2　邊界檢查清單

📐 每個迴圈都要問的五個問題 ① 第一次的值是什麼？會不會少做一次？
② 最後一次的值是什麼？會不會越界？
③ n = 0 時會發生什麼？（空陣列、沒有資料）
④ n = 1 時會發生什麼？（只有一筆）
⑤ 條件會不會永遠成立？（無窮迴圈）
💡 考場技巧
看到迴圈題，先代 n = 1 或 n = 2 手算一次——
小數字五秒就算完，而且最容易看出差一錯誤。不要用眼睛看程式碼推理。

14-3　陣列越界的後果

語言越界時危險程度
C／C++不檢查，讀到隨機記憶體或崩潰（未定義行為）最高
Java／C#拋出陣列越界例外中
Python拋出索引錯誤；負索引另有意義中

資安關聯：C 語言的越界寫入就是緩衝區溢位——經典的漏洞類型，可導致任意程式碼執行。

14-4　公務程式的邊界值

情境要測的邊界
級距判定剛好等於門檻的那一元（是 > 還是 ≥ 依法規認定）
期間計算月底、跨年、2 月 29 日、末日為假日
金額0 元、負數、超過上限
資料筆數0 筆、1 筆、剛好等於分頁大小
字串空字串、只有空白、超長、含特殊字元
年齡／年資生日當天、閏年出生（2/29）
⚠️ 為什麼公務程式的邊界特別重要 級距邊界差一元，可能就是核准與駁回的差別；
期間差一天，可能就是受理與逾期的差別。

這些不是「小 bug」，是會影響民眾權益與處分合法性的錯誤。
✅ 深化 14 必背結論 ① i<n 是 n 次、i<=n 是 n+1 次；步進不為 1 用 ⌈(b−a)/d⌉
② 五個邊界問題，特別是 n=0 與 n=1
③ 考場先代 n=1 或 2 手算，不要用看的
④ 公務邊界：級距門檻、月底跨年、閏年、末日假日

深化 15　資料型別的陷阱：整數、浮點與字串

15-1　整數溢位

📐 溢位的危險在於「不會報錯」 8 位元無號整數上限 255；250 + 10 = 260 → 260 − 256 = 4（回繞）

程式繼續跑，但數字已經錯了，而且沒有任何錯誤訊息。
這比當機更危險——當機至少會被發現。
型別範圍公務適用
8 位元有號−128 ～ 127幾乎不用
16 位元有號−32768 ～ 32767件數可能不夠
32 位元有號約 ±21 億金額以「分」計時可能不夠
64 位元有號約 ±9.2×10¹⁸安全的預設選擇

15-2　浮點數不可用於金額

⚠️ 0.1 + 0.2 ≠ 0.3 因為 0.1 在二進位是無限循環小數，無法精確表示。
只有分母是 2 的次方的小數（0.5、0.25、0.125）能精確表示。

正確做法：
① 以整數儲存（單位取「分」）
② 或用十進位型別（decimal／numeric）
③ 四捨五入的時機依法規或作業要點認定，不由程式設計者決定

浮點數該用在哪：科學運算、統計、繪圖——這些場合本來就是近似值。

陷阱說明公務影響

實務建議：輸入時統一正規化（去頭尾空白、全形轉半形、英文轉大寫），再儲存與比對。

15-4　型別轉換的陷阱

轉換問題
浮點轉整數是截斷還是四捨五入？不同語言不同
大型別轉小型別可能溢位且不報錯

✅ 深化 15 必背結論 ① 整數溢位不會報錯——公務系統預設用 64 位元
② 金額用整數或十進位型別，絕不用浮點數
③ 字串三陷阱：編碼、中文字長度、罕用字造字區

深化 16　函式設計：參數、回傳與副作用

16-1　傳值與傳址的實際差異

16-2　副作用（Side Effect）

類型例問題
純函式同樣輸入永遠同樣輸出，不改變外部狀態好測試、好推理
有副作用改全域變數、寫檔案、改資料庫、發郵件難測試、難預測
💡 設計原則
把「計算」與「副作用」分開。

不好：一個函式同時算補助金額 ＋ 寫入資料庫 ＋ 發簡訊
較好：算金額（純函式，可單獨測試） → 寫入 → 發簡訊，各自獨立

好處：金額計算邏輯可以寫自動化測試，不需要真的連資料庫或發簡訊。

16-3　函式的三個設計原則

📐 三原則 ①單一職責：一個函式只做一件事；名字說不清楚在做什麼，通常就是做了太多事
②參數不要太多：超過四五個就該考慮包成一個結構
③明確的錯誤處理：失敗時要讓呼叫者知道——回傳錯誤或拋出例外，不要默默回傳 0 或 null

16-4　變數作用範圍

區域變數全域變數
作用範圍所屬區塊整個程式
生命週期離開區塊即消失程式結束才消失
維護性好（影響範圍小）差（任何地方都可能改到）

原則：變數的作用範圍應盡可能小。需要共用時，優先以「參數傳入、回傳值傳出」，而非全域變數。
全域變數在多執行緒環境下更是競爭條件的主要來源。

✅ 深化 16 必背結論 ① 傳址風險較高（可能改到原值），不是比較安全
② 把計算與副作用分開——計算部分才好寫測試
③ 三原則：單一職責、參數不多、明確錯誤處理
④ 變數作用範圍越小越好

深化 17　例外處理：讓錯誤被看見而不是被吞掉

17-1　三種錯誤處理策略

策略做法問題
回傳錯誤碼函式回傳成功或失敗呼叫者容易忘記檢查
拋出例外錯誤時中斷正常流程需要在適當層級接住
忽略錯誤捕捉例外但什麼都不做最危險——資料壞了卻沒人知道
⚠️ 最糟的寫法 「捕捉所有例外，然後什麼都不做」——這叫吞掉例外。

後果：程式看起來正常運作，但每一筆處理失敗的資料都消失了，
而且事後完全查不出來發生過什麼事。

寧可讓程式明顯地失敗，也不要讓它靜靜地錯下去。

17-2　例外處理的三個層次

📐 分層處理 ①能處理的就處理：如網路逾時 → 重試三次
②不能處理的往上拋：加上情境資訊再拋，不要把原始錯誤丟掉
③最外層統一處理：記錄詳細錯誤到日誌 ＋ 對使用者顯示友善訊息
對象應該看到什麼
使用者「系統忙碌，請稍後再試」＋錯誤代碼供查詢
維護人員完整的錯誤訊息、堆疊追蹤、當時的輸入值

為什麼不能對使用者顯示詳細錯誤：會洩漏資料庫結構、檔案路徑、程式框架版本——
這些都是攻擊者的情報。

17-3　防禦性程式設計

原則做法
不信任外部輸入一律驗證格式、範圍、長度；驗證要在伺服器端做
預期會失敗外部呼叫一定要設逾時；檔案可能不存在；網路可能斷
安全地失敗失敗時往安全的方向倒（驗證服務掛掉 → 拒絕存取）
前置條件檢查函式開頭先檢查參數是否合理

17-4　公務系統的錯誤處理要求

📐 四個必要條件 ①民眾的事要辦得成：系統故障時要有人工替代程序
②錯誤要被記錄：時間、使用者、輸入、錯誤內容——否則無法追查
③資料不能半調子：交易要嘛全成功，要嘛全失敗，不可以扣了款沒銷帳
④要能重試：冪等設計——同一筆重送不會重複處理
✅ 深化 17 必背結論 ① 吞掉例外是最危險的寫法——資料壞了沒人知道
② 使用者看友善訊息，維護人員看詳細日誌——詳細錯誤不可對外顯示
③ 防禦四原則：不信任輸入、預期失敗、安全失效、前置檢查
④ 公務四要求：人工替代、錯誤記錄、交易完整、冪等可重試

深化 18　物件導向：從封裝到設計原則

18-1　三大特性的實際價值

特性做什麼實際好處
封裝隱藏內部實作，只露出介面改內部時外面不用跟著改
繼承子類別沿用父類別共同行為只寫一次
多型同一個呼叫，不同物件不同行為新增類型時不必改既有程式
📐 多型的實際用途 假設有五種補助，每種計算方式不同。

沒有多型：一大串 if-else 判斷是哪一種補助 → 新增第六種要回去改這串判斷
有多型：每種補助是一個類別，都有 計算金額() 方法 → 新增第六種只要加一個新類別

18-2　繼承的陷阱

⚠️ 繼承被過度使用 繼承代表「是一種」（is-a）關係，不是「有一個」（has-a）。

錯誤：「案件」繼承「使用者」——因為案件不是一種使用者
正確：「案件」擁有一個「承辦人」（組合）

設計原則：優先使用組合而非繼承——繼承的耦合太緊，父類別一改全部子類別受影響。

18-3　類別設計的五個原則（SOLID 簡版）

原則一句話公務例
單一職責一個類別只有一個改變的理由「案件」不該同時管計算與寄信
開放封閉對擴充開放、對修改封閉新增補助類型不必改既有程式
里氏替換子類別要能替換父類別而不出錯不要在子類別違反父類別的約定
介面隔離不要強迫實作用不到的方法介面切小一點
依賴反轉依賴抽象而非具體實作換簡訊供應商不必改業務邏輯

對公務系統最實用的兩條：單一職責（好維護）與依賴反轉（換廠商或換服務時不必大改）。

18-4　什麼時候不需要物件導向

簡單的批次程式、一次性的資料轉換腳本、單純的計算——
硬套物件導向反而讓程式變複雜。

判準：如果這段程式會長期維護、會有多種類型、會被多處使用，物件導向有價值；
如果是寫一次跑一次就丟，寫得清楚簡單就好。

技術要與問題規模相稱——這在公務環境特別重要。
✅ 深化 18 必背結論 ① 封裝讓內部可改、繼承讓程式碼共用、多型讓新增類型不必改舊程式
② 繼承是 is-a，不是 has-a；優先使用組合
③ 最實用兩原則：單一職責與依賴反轉
④ 一次性腳本不需要物件導向——技術要與規模相稱

深化 19　資料庫存取程式的三個必修

19-1　參數化查詢（不只是為了安全）

好處說明
防 SQL 注入資料永遠是資料，不會被當成程式碼
效能較好資料庫可以重用執行計畫（同一句 SQL 只是參數不同）
不必處理跳脫姓名含單引號也不會出錯
型別正確日期、數字不必轉成字串

常見誤解：「我有過濾特殊字元所以安全」——黑名單永遠有繞過方法，
而且會擋掉正常的姓名（如帶單引號的外國名字）。

19-2　連線管理

⚠️ 連線洩漏是公務系統最常見的效能事故 症狀：CPU 不高、記憶體正常，但連線數滿了、新請求全部失敗。

原因：程式在發生例外時沒有關閉連線——正常流程有關，例外流程忘了關。

解法：①使用語言提供的自動釋放語法 ②使用連線池並設定逾時 ③監控「最長執行中交易」

19-3　N+1 查詢問題

📐 症狀與診斷 查 100 列資料（1 次查詢），再為每列各查一次關聯資料（100 次）＝ 101 次往返。

診斷方法：看資料庫慢查詢日誌，若發現同一句 SQL 只有參數不同、被執行數百次，就是 N+1。

解法：①用 JOIN 一次取回 ②或把小型代碼表整份快取在程式內

19-4　批次處理的正確寫法

做法10 萬筆的相對速度說明
逐筆寫入且逐筆提交最慢每筆都有交易與往返成本
批次寫入（每 500～1000 筆一批）快數十倍平衡效能與交易大小
全部放在一個交易快但危險鎖住太久、交易紀錄檔暴增
大量匯入工具最快適合初次資料轉換
💡 批次程式的三個必要設計
①可中斷可續跑：記錄處理到哪一筆，中斷後從那裡繼續
②冪等：重跑一次不會產生重複資料
③失敗告警：沒跑成功卻沒人知道，比跑得慢更危險
✅ 深化 19 必背結論 ① 參數化查詢不只防注入，還能重用執行計畫
② 連線洩漏：CPU 不高但連線滿——例外流程忘了關
③ N+1 的診斷：同一句 SQL 被執行數百次
④ 批次三設計：可續跑、冪等、失敗告警

深化 20　網頁程式的安全撰寫

20-1　輸入驗證的正確位置

⚠️ 前端驗證不是安全機制 前端驗證是使用者體驗（讓使用者早點知道打錯了），
不是安全機制——攻擊者可以直接送出請求，完全繞過前端。

所有驗證都必須在伺服器端再做一次。
驗證項目檢查什麼
格式身分證字號、日期、電話的格式
範圍金額不可為負、日期不可為未來、數量有上限
長度防止超長輸入耗盡資源
業務規則這個人有沒有資格、這個時段還開不開放
授權這個使用者有沒有權限操作這一筆

20-2　三大網頁攻擊的防禦寫法

攻擊根本防禦額外防護
SQL 注入參數化查詢資料庫最小權限、WAF
XSS輸出時依情境編碼CSP、HttpOnly Cookie
CSRFCSRF Token 並在伺服器端驗證SameSite Cookie、重要操作再驗證
📐 XSS 為什麼是「輸出編碼」而不是「輸入過濾」 同一段文字放在不同位置要用不同的編碼方式：
放在 HTML 內文、放在標籤屬性、放在 JavaScript 裡、放在網址裡——四種編碼都不一樣。

輸入時不知道這段文字未來會被放到哪裡，所以只能在輸出時依當下情境編碼。

20-3　權限控制失效（公務系統最常見）

典型情境：網址是 /case?id=12345，改成 12346 就看到別人的案件。

根本錯誤：把「畫面上沒有連結」誤當成「沒有權限」。

正確寫法：每一次資料存取，都在伺服器端檢查「這個登入者是否有權讀取這一筆」——
不能只靠前端隱藏，也不能只靠「參數不外洩」。

後果：一旦有此弱點，等同全體申辦民眾的個資可被逐號下載，屬重大個資事故。

20-4　檔案上傳的五道防護

📐 缺一不可 ①白名單：只允許必要的類型，並檢查實際內容而非只看副檔名
②大小限制：防止耗盡磁碟
③重新命名：避免原檔名含路徑符號造成目錄遍歷，或覆蓋既有檔案
④存放位置：放在網站根目錄之外，或設定該目錄不得執行程式
⑤掃毒：以防毒或沙箱檢查

最嚴重的後果：攻擊者上傳一個可執行的網頁程式並直接呼叫它 → 取得伺服器控制權。
✅ 深化 20 必背結論 ① 前端驗證是體驗，伺服器端驗證才是安全
② XSS 靠輸出編碼（因為輸入時不知道會被放到哪裡）
③ 每次存取都要在伺服器端驗證授權，不是靠隱藏
④ 上傳五道防護，關鍵是重新命名 ＋ 放在不可執行的目錄

深化 21　測試：從單元測試到驗收

21-1　四個測試層次

層次測什麼誰做頻率
單元測試單一函式或模組開發人員每次改動
整合測試模組之間的介接開發人員每次建置
系統測試整體功能與非功能需求測試人員版本發布前
使用者驗收（UAT）實際業務情境是否可行業務單位驗收前

各層不可互相取代。單元測試全過不代表整合沒問題；系統測試通過不代表業務單位覺得可用。

21-2　最該優先寫測試的三類邏輯

📐 公務系統的優先順序 ①金額計算：級距、比例、四捨五入、加總
②日期與期間：始日不計入、末日假日順延、閏年、跨年
③資格判定：各種條件組合，特別是邊界值

理由：這三類算錯的後果不是畫面醜，是民眾權益受損與處分違法。

21-3　測試案例的設計方法

方法做法例（補助金額 5 萬以下補 30%）
等價分割把輸入分成幾類，每類測一個低於 5 萬、等於 5 萬、高於 5 萬
邊界值測邊界及其前後一個單位49999、50000、50001
錯誤猜測憑經驗猜哪裡容易錯0 元、負數、超大金額
決策表多條件組合時列出所有組合低收入戶 × 有無身障 × 年齡層

邊界值是投報率最高的方法——大部分 bug 都在邊界。

21-4　測試資料的紅線

⚠️ 不可使用正式個資測試 測試環境的防護通常較弱（沒有完整的防火牆規則、沒有稽核、廠商人員可自由存取），
把正式個資搬進去，等於把個資放在最不安全的地方。

正確做法：
① 使用去識別化資料（姓名、身分證字號、地址全部代換）
② 或產生合成測試資料
③ 若因特殊需要必須使用，須經核准、限期、限範圍並留存紀錄
✅ 深化 21 必背結論 ① 四層測試不可互相取代；UAT 由業務單位做
② 優先測：金額、日期期間、資格判定
③ 邊界值是投報率最高的測試設計方法
④ 測試環境不可使用正式個資

深化 22　可維護的程式：命名、註解與重構

22-1　命名的價值

不好好差別
ddaysSinceReceived不必猜
flagisEligibleForSubsidy布林值用 is/has 開頭
process()calculateSubsidyAmount()知道回傳什麼
dataapplicantList知道是什麼與是複數
📐 一個判準 好的命名讓程式不需要註解就看得懂「在做什麼」。
註解應該用來說明「為什麼」，而不是重複程式碼在做什麼。

22-2　公務程式最需要的註解

沒用的註解有價值的註解
「i 加 1」「依 OO 作業要點第 3 點，末日為假日應順延」
「呼叫函式」「此處不用批次，因介接對象僅提供單筆查詢」
「宣告變數」「金額以分為單位儲存，避免浮點誤差」
「迴圈」「115 年起法規修正為三級距，舊案仍依原規則計算」

「法規依據」是公務程式最重要的註解——三年後承辦換人，沒有這行註解，沒人敢改這段邏輯，也不知道能不能改。

22-3　技術債的償還

步驟做法為什麼是這個順序
①先補測試為要重構的部分寫自動化測試改壞了會知道
②小步重構一次改一小塊，每次都跑測試出錯時容易定位
③持續進行每次改功能時順手改善周邊不需要專案就能慢慢還債
不要一次重寫—整批重寫的失敗率極高
💡 公務環境的技術債特別重
承辦輪調、需求臨時、沒有預算做重構。

務實建議：將重構納入年度維護契約的工作項目——
而不是等系統完全不能動才整批重置（那時的成本是十倍）。

22-4　版本控制的公務價值

能回答的問題沒有版本控制時
這段是誰在什麼時候為什麼改的？完全查不到
可以退回上一版嗎？只能靠備份或重寫
兩個人同時改會怎樣？後存檔的覆蓋前者
驗收時交付的是最新版嗎？無法確認

契約要點：應要求廠商將程式碼提交至機關的版本控制系統，
而非只在結案時交一份壓縮檔——後者無法看出開發過程，也無法確認是最新版。

✅ 深化 22 必背結論 ① 好命名讓程式不需註解就看得懂「做什麼」
② 註解寫「為什麼」；公務最重要的是法規依據
③ 還技術債：先補測試 → 小步重構，不要一次重寫
④ 版本控制應納入契約，由機關保管

深化 23　效能問題的診斷與改善順序

23-1　先量測，不要猜

⚠️ 過早最佳化 「我覺得這裡很慢」——通常是猜錯的。

正確做法：先量測找出真正的瓶頸，再針對瓶頸改善。
改善一個只佔總時間 3% 的環節，就算變快十倍，整體也只快 2.7%。
📐 阿姆達爾定律的實務版 整體改善幅度受限於「那個環節佔總時間的比例」。

所以要先問：時間都花在哪裡？
——資料庫查詢？網路往返？計算？渲染？

23-2　常見瓶頸與改善方式

瓶頸症狀改善
資料庫查詢多數時間在等資料庫索引、改寫查詢、消除 N+1
N+1 查詢同一句 SQL 執行數百次JOIN 或預先載入
外部呼叫等外部 API 回應快取、非同步、設逾時
大量資料載入記憶體記憶體用量暴增分批處理或串流
重複計算CPU 高記憶化、快取結果
連線洩漏CPU 不高但連線滿檢查例外流程是否關閉連線

23-3　改善的成本效益排序

順序做什麼效益／成本
1改寫查詢（消除函數包欄位、消除 N+1）最高／零
2建立或調整索引高／低
3加入快取高／中（要處理一致性）
4改為非同步或批次中／中
5升級硬體最低／最高

申論結論句：「效能問題應先從程式與資料庫層面著手，硬體升級為最後手段——
因為前者常有數十倍改善，後者通常只有數倍。」

23-4　快取的正確使用

📐 什麼該快取、什麼不該 適合快取：公告、法規、代碼表、統計結果——變動少、讀取多
不適合快取：案件狀態、餘額、名額——涉及民眾權益的即時資訊

兩種失效策略：
時間失效（TTL）：簡單，但會有陳舊期
事件失效：資料異動時主動清除快取，即時但實作較複雜

公務鐵則：涉及民眾權益的時效資訊不得依賴快取，
且畫面應顯示資料更新時間。

✅ 深化 23 必背結論 ① 先量測再改善——猜的瓶頸通常是錯的
② 最常見瓶頸：資料庫查詢與 N+1
③ 改善順序：查詢 → 索引 → 快取 → 非同步 → 硬體（最後）
④ 涉及權益的即時資訊不可依賴快取

深化 24　程式設計概要的滿分策略

24-1　選擇題的四大題型

題型解法年約題數
程式追蹤畫追蹤表，一行一行寫變數值4～6
複雜度判斷看迴圈層數與成長方式2～3
觀念區辨整理成比較表3～4
資料結構操作堆疊、佇列、樹的走訪2～3
📐 程式追蹤題的鐵律 畫表，不要用眼睛看。

表格欄位：第幾次迴圈 ｜ 各變數的值 ｜ 條件判斷結果

三十秒畫完表，答案就浮出來了——比盯著程式碼想五分鐘準確得多。

24-2　追蹤題的五個檢查點

檢查點常見陷阱
整數除法5/2 = 2 不是 2.5
迴圈條件< 還是 <=
前置與後置遞增++i 與 i++ 在運算式中的差別
break 與 continuebreak 跳出整個迴圈；continue 只跳過本次
陣列索引由 0 起算還是由 1 起算

24-3　申論題的四段結構

🎯 時間不夠時，四段各寫一點也比第一段寫死好 【一】解題思路（用文字說明，約 25%）
「本題可用 XX 方法，步驟為：先…，再…，最後…」
就算後面程式寫不完，這段也有分。

【二】流程或虛擬碼（約 25%）
條列步驟，不必寫成可編譯的程式

【三】關鍵程式片段（約 30%）
核心邏輯寫清楚，週邊（宣告、輸入輸出）可省略

【四】複雜度與邊界情況（約 20%）
「時間複雜度為 O(n)；須處理空輸入、資料量過大與例外情形」——這段最容易被忽略，也最容易補分

24-4　公務程式的加分句

面向句子
金額「金額採整數或十進位型別，避免浮點誤差；四捨五入時機依作業要點明定。」
期間「期間計算依行政程序法始日不計入，末日為假日順延，並每年更新行事曆。」
安全「資料庫存取採參數化查詢；所有驗證於伺服器端執行。」
權限「每次資料存取均於伺服器端驗證該使用者是否有權讀取該筆資料。」
錯誤「對使用者顯示友善訊息，詳細錯誤寫入日誌，避免洩漏系統資訊。」
測試「就金額、期間、資格判定三類邏輯建立自動化測試，含邊界值案例。」
批次「批次程式須可中斷續跑、具冪等性，並設失敗告警。」
