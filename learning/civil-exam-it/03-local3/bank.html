A. 觀念選擇題（第 1～30 題）

1資料結構
某縣市規劃垃圾車收運路線，欲以最短總里程連接所有里辦公處且不重複繞行，此問題最接近下列何者？
詳解
答案：(A) 最小生成樹（MST）
「以最小總成本連接所有節點且無迴圈」＝ MST（Kruskal 或 Prim）。

區辨：最短路徑是「兩點之間」最短（Dijkstra）；MST 是「連接所有點」總成本最小。

地特加分角度：實務上垃圾車路線還須考量單行道、載重限制、時段管制、清運時間窗，MST 僅為理論參考。
2資料結構
戶政事務所叫號系統需支援「一般號」與「敬老號」，敬老號優先叫號。最適合的資料結構為？
詳解
答案：(C) 優先佇列（Priority Queue），通常以 Heap 實作（插入與取出皆 O(log n)）。

地特加分角度：須提出老化（Aging）機制——若敬老號持續進來，一般號可能長期等待（飢餓）。
可設定「等待超過 N 分鐘則提升優先權」，兼顧優待與公平。
3資料結構
行政區資料為「縣市 → 鄉鎮市區 → 村里」的三層結構，最適合的表示方式為？
詳解
答案：(A) 樹狀結構
階層關係天生適合以樹表示；資料庫中可用自我參考的外鍵（上級代碼指向同表主鍵）實作。

實務補充：查詢「某縣市底下所有村里」屬階層查詢，SQL 可用遞迴 CTE（WITH RECURSIVE）展開。
4資料結構
公文管理系統需依「收文日期範圍」查詢 500 萬筆公文，最適合的索引結構為？
詳解
答案：(B) B+ 樹索引
B+ 樹只有葉節點存資料且葉節點以鏈結串列相連，定位起點後可循序走訪 → 範圍查詢極快。

(A) 雜湊索引等值查詢 O(1)，但完全不支援範圍查詢（雜湊破壞順序性）。
(C) 點陣圖索引適合低基數欄位（如公文狀態），不適合日期。
5資料結構
將人員名冊「先依所屬區排序、再依到職日排序」，第二次排序必須使用何種排序才不會破壞第一次的結果？
詳解
答案：(D) 合併排序（穩定排序）
穩定排序＝鍵值相同的元素，排序後相對順序不變。

多欄位排序的正確做法：先依次要鍵（到職日）排，再用穩定排序依主要鍵（區）排 → 同一區內的到職日順序會被保留。

穩定：泡插合、計基桶｜不穩定：選快堆謝（快速、選擇、堆積皆不穩定）。
6資料庫
關聯 R(案件編號, 承辦人編號, 承辦人姓名, 所屬科室, 科室主管)，主鍵為案件編號，且承辦人編號→承辦人姓名、所屬科室；所屬科室→科室主管。此關聯違反？
詳解
答案：(C) 違反 3NF（存在遞移相依）
案件編號 → 承辦人編號 → 所屬科室 → 科室主管，形成兩層遞移相依。

為何不是 2NF？主鍵為單一屬性（案件編號），不可能有部分相依 → 單一屬性主鍵必定符合 2NF。

分解：案件(案件編號, 承辦人編號FK)、人員(承辦人編號, 姓名, 所屬科室FK)、科室(科室代碼, 科室主管)
7資料庫
要查出「本府所有科室的案件數，包含零件數的科室」，SQL 應使用？
詳解
答案：(B) LEFT JOIN（以科室表為左表）
INNER JOIN 只會回傳「兩邊都有對應」的列 → 零件數的科室會消失。

SELECT d.科室名稱, COUNT(c.案件編號) AS 件數
FROM 科室 d
LEFT JOIN 案件 c ON d.科室代碼 = c.科室代碼
GROUP BY d.科室代碼, d.科室名稱;
注意：要用 COUNT(c.案件編號) 而非 COUNT(*)——後者會把 NULL 的那一列也算成 1。這是很細但常考的陷阱。
8資料庫
活動線上報名系統發生「名額 50 人卻收了 53 人」的情形，最可能的原因為？
詳解
答案：(B) 遺失更新（Lost Update）
多筆交易同時讀到「剩餘名額 1」，各自判斷可報名並各自寫回 0 → 實際收了多人。

錯誤做法：在應用程式層「先 SELECT 判斷、再 INSERT」——兩步驟之間存在競態條件。

正解：原子更新＋資料庫限制
UPDATE 活動 SET 餘額 = 餘額 - 1 WHERE id = ? AND 餘額 > 0;
並加 CHECK (餘額 >= 0) 作為最後防線——即使程式有 bug 也不會超收。
9資料庫
社政系統開放給一般業務單位查詢時，為避免其看到身分證字號與病歷註記，最適當的做法為？
詳解
答案：(B) 建立檢視表（View）並授權
View 可只開放必要欄位（甚至可加列層過濾，如「僅本區個案」），落實最小權限原則，符合《個人資料保護法》必要範圍之要求。

實作： 
CREATE VIEW 個案公開資料 AS
SELECT 個案編號, 姓名, 行政區, 案件狀態 FROM 個案;
GRANT SELECT ON 個案公開資料 TO 業務單位;
REVOKE ALL ON 個案 FROM 業務單位;
補充：病歷屬特種個資，限制更嚴；並應建立稽核軌跡記錄誰查了誰的資料。
10資料庫
市政儀表板需分析近五年各區各類案件趨勢，最適合的資料架構為？
詳解
答案：(B) 資料倉儲＋星狀綱要
事實表：案件事實（件數、處理天數、滿意度）
維度表：時間、行政區、承辦局處、案件類別、陳情管道

為何不用 (A)：大型分析查詢會耗盡資源、鎖住資料表，影響線上作業（OLTP 與 OLAP 不宜共用資料庫）。

成敗關鍵：底層資料品質與指標定義一致性——若各局處對「案件」定義不同，儀表板會淪為「美觀但不可信」。
11網路
某區公所網路規劃中，IP 監視系統應如何配置？
詳解
答案：(B) 獨立 VLAN 並限制對外連線
IP 監視器等 IoT 設備的三大風險：
① 預設密碼未更改　② 韌體長期不更新　③ 運算資源少難以加密

→ 常被組成殭屍網路（如 Mirai）發動 DDoS，或成為入侵內網的跳板。

正確做法：獨立網段、僅允許連至錄影主機、強制變更預設憑證、納入資產清冊、建立韌體更新機制。
(C) 直接用公有 IP 是極危險的做法——網路上有專門搜尋暴露攝影機的搜尋引擎。
12網路
IP 位址 192.168.50.140，遮罩 255.255.255.240，其可用主機範圍為？
詳解
答案：(A) 192.168.50.129 – .142
① 遮罩 240 → 區塊大小 = 256 − 240 = 16
② 段界：.0、.16、.32 …、.128、.144
③ 140 落在 128～143 → 網路位址 .128、廣播位址 .143
④ 可用範圍 = .129 ~ .142（14 台，2⁴−2）

(B) 的錯誤是把網路位址與廣播位址也算進去。
13網路
市民廣場提供免費 Wi-Fi，下列何者最為必要？
詳解
答案：(B)
公共 Wi-Fi 的第一原則就是隔離：獨立 VLAN + 防火牆隔離內網；並啟用用戶端隔離（Client Isolation）禁止訪客彼此連線（防止民眾之間互相攻擊）。

‧ (A) 隱藏 SSID 不是有效安全措施（探測封包仍可發現）
‧ (C) WEP 已被破解，絕不可用
‧ (D) 開放內部伺服器等於自毀防線；表單應放對外網站或 DMZ

另須依規定保存連線紀錄，蒐集手機號碼認證時須符合個資法特定目的告知義務。
14資安
某公所遭勒索軟體攻擊，發現連備份檔案也一併被加密，最可能的原因為？
詳解
答案：(B)
勒索軟體會主動搜尋網路上的共享磁碟與備份目標並一併加密；若取得網域管理員權限，甚至會先刪除備份再加密。

正確做法：
① 離線備份（Air-gapped）——磁帶或定期離線的儲存設備
② 不可變備份（Immutable／WORM）——保留期間內不可刪改
③ 備份系統帳號與網域分離、獨立網段
④ 多版本保留（惡意程式可能潛伏數週）

提醒：RAID 不是備份，它防硬碟故障但防不了加密與誤刪。
15資安
承辦人接到自稱局長的電話，語音與局長極為相似，要求緊急變更廠商匯款帳號。最適當的處理為？
詳解
答案：(B) 以另一既有管道回撥確認
生成式 AI 使深偽（Deepfake）語音門檻大幅降低——「聽到本人聲音」已不再是可靠的身分確認方式。

這也是典型的 BEC 商業郵件／電話詐騙手法，運用了權威與急迫兩種心理槓桿。

機關應訂定的控管：
‧ 變更匯款帳號等關鍵作業採雙人覆核
‧ 重要指示須以另一管道回撥（打通訊錄上的分機，而非對方給的號碼）確認
‧ 納入資安教育訓練與演練情境
16資安
依《資通安全管理法》，機關知悉資安事件後應如何處理？
詳解
答案：(B) 於規定時限內通報主管機關
依《資通安全管理法》及《資通安全事件通報及應變辦法》，知悉後即應於規定時限內通報，不得先處理完再通報。

事件依影響程度分 1～4 級；3、4 級為重大事件，通報時限更短且須提出調查、處理及改善報告。

作答提醒：不必背精確時數（依子法且可能修正），寫「規定時限內」最安全；硬背錯誤反而扣分。

另注意：機關的資安責任等級是 A～E 五級，與事件的 1～4 級是兩套不同的分級。
17資安
下列何者不是有效的無線網路安全措施？
詳解
答案：(C)
隱藏 SSID——探測封包仍可發現；MAC 過濾——MAC 可輕易偽造。
兩者屬「以隱蔽代替安全（Security through Obscurity）」，只能輔助，不能作為主要防護。

真正有效的是：強加密（WPA2-AES／WPA3）＋ 802.1X 企業級驗證（每人獨立帳號，離職只需停用該帳號）＋ 網段隔離。
18資安
機關網站遭 SQL Injection 攻擊，最根本的防範方式為？
詳解
答案：(B) 參數化查詢（Prepared Statement）
根本成因是「資料與指令未分離」；參數化查詢使輸入永遠被當成「值」而非 SQL 語法。

(A)(C)(D) 屬縱深防禦但無法根治：黑名單過濾可被編碼繞過，WAF 可能被規避。

地特加分角度：機關網站多為委外開發，故應於需求規格書明定安全開發規範，並於驗收時委由第三方執行滲透測試、缺失複測通過才驗收，契約並應載明保固期漏洞修補義務。
19資訊管理
本府委外開發之系統驗收後，發現僅原廠商能維護且維護費逐年上漲。此問題的根本原因最可能為？
詳解
答案：(B)——這是供應商鎖定（Vendor Lock-in）的典型成因。

契約應載明的五件事：
① 智慧財產權歸屬（原始碼著作權歸機關或取得可再授權之使用權）
② 原始碼與完整文件交付（含資料庫綱要、部署程序、第三方元件清單 SBOM）
③ 機關得自行或另委他人修改維護之權利
④ 退場條款：資料可攜（標準格式匯出）與系統移轉配合義務
⑤ 維護費計價方式與上限

長期策略：機關須保留規格制定能力與驗收判斷能力——可以不會寫程式，但必須看得懂架構、問得出關鍵問題。
20資訊管理
某市推動線上申辦後，年長里民反映不會使用而無法辦理。下列處理何者最適當？
詳解
答案：(B)
企業可以放棄不會用 App 的客戶，政府不行。數位化不得成為取得公共服務的門檻，否則違反平等原則。

因應數位落差的四項措施：
① 保留傳統管道（臨櫃、電話、紙本）
② 無障礙網頁（符合網頁無障礙規範，支援螢幕閱讀器）
③ 介面簡化與多語化（含新住民、原住民語）
④ 數位輔導（志工協助、社區教學推廣）

(A) 直接剝奪服務；(C) 涉及個資代辦之授權問題；(D) 差別待遇須審慎評估。
21資訊管理
民眾辦理出生登記後，系統主動通知可申請育兒津貼並提供線上辦理。此屬電子化政府的哪一階段？
詳解
答案：(D) 主動與智慧服務（第五階段）

五階段：① 資訊公布 → ② 互動溝通 → ③ 線上交易 → ④ 跨機關整合（免書證免謄本） → ⑤ 主動與智慧服務

關鍵差異：民眾不需要知道有這項福利，政府主動找上門。

這體現「生活事件導向」的服務設計——不以機關組織架構分類服務，而以民眾的人生事件（出生、就學、結婚、購屋、退休、死亡）組織。
22資訊管理
本府擬將某系統移至公有雲，下列何者仍為機關自身的責任？
詳解
答案：(C) 資料與存取權限設定
依責任共擔模式，不論 IaaS／PaaS／SaaS，「資料」與「存取權限設定」永遠是客戶的責任。

實務印證：絕大多數雲端外洩事件並非業者被駭，而是客戶自己把儲存空間設成公開或權限給得太寬。

機關上雲另須注意：資料主權與存放地點、退場機制與資料可攜、年度預算制與按量計費的扞格、維運人力技能轉型。
23資訊管理
本府各局處對「案件」定義不一致，導致統計無法勾稽。此問題的本質為？
詳解
答案：(B) 業務問題
「什麼算一件案子」必須由業務單位共同認定，資訊室只能提供工具與平台。

許多機關的資料整合失敗，正是因為誤以為這是資訊室的工作。

正確做法：
① 成立跨局處資料治理小組，由副首長層級主持（層級不夠協調不動）
② 建立共同資料標準與資料字典（定義、計算方式、例外處理）
③ 建立共用代碼表並指定資料管理者（Data Steward）
④ 建立定期勾稽機制（各局處加總須等於全府總計）
24資訊管理
某專案活動 A（工期 5 天）浮時為 0，活動 B（工期 3 天）浮時為 4 天。若欲縮短專案總工期，應優先對何者投入資源？
詳解
答案：(A) 活動 A
浮時為 0 表示 A 在要徑（Critical Path）上——只有壓縮要徑上的活動才能縮短總工期。

對浮時 4 天的 B 投入再多資源，專案一天也不會提早。

兩個延伸重點：
① 要徑會變動——壓縮後須重新計算，原本有浮時的路徑可能變成新要徑
② 趕工（增加資源，成本↑）vs 快速跟進（改平行，風險↑）——兩者代價不同
25資訊管理
本府擬開放「各區低收入戶補助統計」資料，下列何者為最需注意的風險？
詳解
答案：(B) 小樣本揭露風險

61SQL
欲查出「本年度未曾申請任何補助之低收入戶」，下列 SQL 寫法何者最不易出錯？
看詳解
答案：(B) NOT EXISTS
致命陷阱：若子查詢結果含 NULL，NOT IN 會回傳空集合（因為與 NULL 比較的結果是 UNKNOWN）。

NOT EXISTS 對 NULL 免疫，語意也最貼近「不存在符合條件之列」。

地特加分角度：這種錯誤在補助清查時會造成「應通知而未通知」，屬行政疏失，不只是技術問題。
62SQL
欲統計「各區補助件數，含件數為 0 之區」，應使用何種聯結？
看詳解
答案：(A)
「要保留全部的那一邊放左邊」——欲列出所有區，區就是左表。

另需以申請表的主鍵計數，而非 COUNT(*)：COUNT(*) 會把 LEFT JOIN 補出的 NULL 列也算成 1，造成無申請之區顯示為 1 件。

這是實務上最常見的統計錯誤之一。
63SQL
下列敘述何者正確描述 HAVING 與 WHERE 之差別？
看詳解
答案：(B)
執行順序：FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY。

能寫在 WHERE 的條件就不要寫在 HAVING——先把列過濾掉，分組的資料量才會小。

例：「2025 年各區件數超過 100 者」→ 年度條件放 WHERE，件數條件放 HAVING。

看詳解

看詳解

應變順序：①通報 ②遏止（隔離受害主機） ③保全證據 ④根除 ⑤復原 ⑥檢討改善。

93資安事件

看詳解

地特加分角度：地方政府易在選舉、重大政策、災害期間成為目標，應於這些時點前提高戒備等級。

110營運持續

答案：(B)

地特加分角度：可與鄰近縣市或中央機關洽談互為備援，是預算有限下的務實解——並須簽訂協議明定責任與資料保護。
111雲端
本府擬將部分系統移至公有雲，下列考量何者最優先？
看詳解
答案：(B)

112雲端
關於雲端服務之「責任共擔模型」，下列敘述何者正確？

「Security OF the cloud vs. Security IN the cloud」

模式客戶責任

114網路協定
下列何者最能說明 DNS 在資安上的重要性？
看詳解
答案：(B)
DNS 是信任鏈的起點——名稱解析被騙，後面所有防護都在保護錯誤的目的地。

防護：①DNSSEC（來源驗證） ②使用可信任的遞迴伺服器 ③DNS 查詢日誌監控（可及早發現受害主機連往惡意中繼站）。

地特加分角度：機關網域應啟用 DNSSEC 並防範網域被搶註或到期未續——網域過期被他人買走，是政府機關發生過的真實事故。
115應用安全
本府網站表單遭插入惡意腳本，致其他使用者瀏覽時被竊取 Session。此攻擊與防護為？
看詳解
答案：(B) XSS
核心觀念：輸入驗證擋不完，關鍵在「輸出時依情境編碼」——放進 HTML、屬性、JavaScript、URL 的編碼方式各不相同。

縱深防禦：①輸出編碼 ②CSP 限制可執行的腳本來源 ③Cookie 加上 HttpOnly 與 Secure ④SameSite 屬性。

地特加分角度：民眾陳情、留言板、線上報名等「會把民眾輸入顯示給別人看」的功能，就是 XSS 的高風險區。
116應用安全
本府線上申辦系統，使用者可藉修改網址中的案件編號查看他人案件。此屬何種弱點？
看詳解
答案：(B)
根本錯誤：「畫面上沒有連結」被誤當成「沒有權限」。

正確作法：每一次存取都在伺服器端驗證「這個使用者是否有權讀取這筆資料」，不能只靠前端隱藏。

⚠️ 地方政府的高風險場景 線上申辦、案件進度查詢、繳費紀錄——一旦有此弱點，等同全體申辦民眾的個資可被逐號下載，屬重大個資事故。
117日誌管理
關於資安日誌之保存，下列作法何者最適當？
看詳解
答案：(B)
三要件：①集中（攻擊者刪不到） ②完整（雜湊或唯寫媒體，防事後竄改） ③時間同步（NTP 校時，否則跨系統事件無法勾稽）。

地特加分角度：日誌本身可能含個資（IP、身分證字號、查詢內容），其存取權限與保存期限亦須依個資法規範管理——這是常被忽略的一層。

121行動應用
本府開發市民服務 App，關於資安設計下列何者正確？
看詳解
答案：(B)
App 是在「敵人的裝置」上執行的——反編譯即可看到所有寫死的內容。

要點：①金鑰不寫死 ②驗證與授權一律伺服器端判斷 ③憑證存於系統安全儲存區（Keychain／Keystore） ④偵測 Root／越獄 ⑤憑證綁定（Certificate Pinning）。

地特加分角度：App 不得成為唯一申辦管道（數位落差），且應提供無障礙支援——這是地方政府必寫的兩點。

看詳解

風險控制
預設密碼布建時強制變更並造冊
無法更新採購時即要求韌體更新機制與支援年限

地特加分角度：採購規範是最有效的關卡——設備買進來之後才想管理，通常已無法可管。

126需求管理
本府委外開發系統，上線後業務單位表示「跟當初講的不一樣」。最根本之預防作為為何？
看詳解

有效手段：①雛形（Prototype）或畫面稿先確認 ②驗收條件寫進規格書 ③需求變更走書面程序並評估工期與費用。

地特加分角度：務必寫「業務單位須指派專責對應窗口並全程參與，不得僅於驗收時才出現」。

看詳解

類型問的是例

128政府採購
依政府採購法，資訊系統委外採購欲同時衡量價格與技術，最適當之決標方式為？
看詳解
答案：(B) 最有利標
資訊服務屬異質性採購，價格最低往往品質最差，最低標會產生「劣幣驅逐良幣」。

要件：①訂定評選項目與權重（技術、管理、價格） ②組成評選委員會（含外聘專家） ③敘明評選過程與理由。

⚠️ 承辦要留意 最有利標的裁量空間大，程序更須嚴謹——評選紀錄、利益迴避聲明、序位計算方式都要留存，這是日後被檢調或審計調查時保護自己的依據。
129政府採購
下列何種情形，機關得依政府採購法辦理限制性招標？
看詳解
答案：(B)
限制性招標是例外，須有法定事由並敘明理由簽准，不是「比較快」的選項。

資訊採購常見適用：原系統之擴充、專屬軟體之續約授權、原著作權人之客製。

地特加分角度：「因為只有原廠商會維護」而年年限制性招標，正是供應商鎖定的結果——答題時應連結到本題庫第 119 題的知識移轉與原始碼交付要求。
130專案管理
專案進行中業務單位不斷追加功能，導致期程延宕。此現象稱為？
看詳解
答案：(A) 範疇潛變（Scope Creep）
特徵是「每次都只是小改一下」，單看沒問題，累積起來工期爆炸。

控制方法：①明確的範疇基準線 ②變更管制委員會 ③每次變更都同步評估「工期＋費用＋風險」並書面核定。

💡 一句話：「可以改，但要說清楚代價。」——拒絕變更不切實際，把代價攤開才是專業。
131專案管理

SPI = EV/PV = 0.8　　CPI = EV/AC = 0.67（小於 1 都是壞消息）

158資料應用

F. 地方演算法與系統設計（第 166～205 題）

同樣的演算法，地特會包成「垃圾車路線」「巡查排班」「避難疏散」來問。先辨認題型，再套模型。

166圖論
本府欲規劃道路巡查路線，要求「每條道路都走過一次且不重複」。此問題最接近下列何者？
看詳解
答案：(A) 尤拉路徑（Eulerian Path）
問題走過的對象複雜度
尤拉每條「邊」一次（道路巡查、清掃、抄表）可在多項式時間判定
漢米爾頓每個「點」一次（拜訪每個里辦公處）NP-完全
判定條件：無向連通圖中，奇數度頂點數為 0 → 存在尤拉迴路；為 2 → 存在尤拉路徑（須從其中一個奇點出發）；其他 → 不存在。

地特加分角度：實務上是中國郵差問題（CPP）——不存在尤拉迴路時，允許重複走部分路段但求總重複里程最小。
167圖論
本府欲以最低總成本鋪設光纖連接 12 個區公所（不需最短路徑，只求全部連通）。應採何演算法？
看詳解
答案：(B)（最小生成樹）
關鍵字辨識：「連接所有點」＋「總成本最小」＋「不需迴路」＝ MST。

演算法做法適合
Kruskal邊由小到大加入，用併查集避免成環稀疏圖
Prim從一點長出去，每次挑最近的點稠密圖
地特加分角度：實務上還要考慮可靠性——MST 是樹，斷一條線就有區公所失聯。應在關鍵節點加環狀備援，這已超出 MST，屬可靠性網路設計。這一句是拉開分數的地方。
168圖論
災害時本府需計算「從各里到最近避難所」的最短時間，且部分路段因災阻斷。最適合之處理為？
看詳解
答案：(A)
反向思考：要算「每個里到最近的避難所」，不必從每個里各跑一次；把所有避難所同時當起點（多來源 Dijkstra）跑一次即可。

實作：建一個虛擬起點連向所有避難所（權重 0），跑一次 Dijkstra，複雜度 O((V+E) log V)；(B) 的做法是 O(V(V+E) log V)。

地特加分角度：另須考量避難所收容上限——這時就不只是最短路徑，而是最小成本流／分配問題。
169圖論
本府某工程有多項作業具先後順序，欲安排可行的執行順序。應採何演算法？
看詳解
答案：(A) 拓樸排序
前提：必須是有向無環圖（DAG）；若有環，代表作業互相等待，無可行順序（這正好可用來偵測流程設計上的循環依賴）。

兩種作法：Kahn 演算法（反覆取出入度為 0 的節點）、DFS 後序反轉。

地特加分角度：延伸到關鍵路徑法（CPM）——在 DAG 上求最長路徑，即為工程最短可能工期；關鍵路徑上的作業一延誤，全案就延誤。
170排程
本府 1999 話務中心需依「案件急迫程度」派工，且須避免一般案件長期等待。最適合之設計為？
看詳解
答案：(B)
純優先佇列的問題是飢餓（Starvation）——低優先案件永遠排不到。

老化（Aging）：等待時間每增加 N 分鐘，優先權提升一級；使長期等待者終將被處理。

實作以 Heap，插入與取出皆 O(log n)。

地特加分角度：老化的參數（多久升一級）應依服務承諾（如「一般案件 3 日內處理」）回推設定，而非工程師隨意決定。
171排程
本府稽查人力有限，欲在有限工時內稽查「風險值最高」的場所組合。此問題最接近下列何者？
看詳解
答案：(A) 背包問題（Knapsack）
對應關係：背包容量＝可用工時；物品重量＝稽查耗時；物品價值＝風險值。

類型解法
0/1 背包（去或不去）動態規劃，O(nW)；屬 NP-完全，W 大時不可行
分數背包（可部分執行）貪心（按價值密度排序）即為最佳
地特加分角度：實務上會加入法定稽查頻率、地理鄰近性、陳情案件優先等約束，變成整數規劃；可用求解器或啟發式演算法求近似解，並保留人工調整空間。
172排程
本府欲安排值班表，須滿足「每日至少 2 人、每人每週至多 5 班、不可連續大夜」。此類問題最適合之解法為？
看詳解
答案：(B)
特徵是「有很多硬性規則要同時滿足」——這就是約束滿足問題（CSP）。

約束類型處理
硬約束必須滿足（法定工時、人數下限）
軟約束盡量滿足，違反則計罰分（個人偏好、假日公平）
地特加分角度：排班系統的成敗不在演算法，在「規則有沒有問清楚」——實務上一定要保留人工微調與換班申請功能，全自動排出來的班表沒人服氣。

174資料結構
本府叫號系統以陣列實作環狀佇列，大小 8，front = 6、rear = 2。目前元素個數為？
看詳解
答案：(B) 4
📐 公式 個數 = (rear − front + 容量) mod 容量 = (2 − 6 + 8) mod 8 = 4
驗證（採「front 指向第一個元素的前一格、rear 指向最後一個元素」的常見約定）：占用 7、0、1、2 共 4 格。

⚠️ 考試陷阱 環狀佇列的「滿」與「空」都會使 front = rear，故通常刻意浪費一格（最多存容量−1 個）或另設 count 變數。看到題目問「最多可存幾個」，要先確認採哪種約定。
175複雜度
本府某報表程式對 N 個里各自掃過全部 M 筆案件。其時間複雜度為？
看詳解
答案：(B) O(N × M)
N = 300 個里、M = 50 萬筆案件 → 1.5 億次比對，這就是報表跑一小時的原因。

改善方法：改成「掃一次案件，用雜湊表依里別累加」 → O(M)；或直接交給資料庫 GROUP BY 里別 並建索引。

💡 實務原則：「能在資料庫算的，不要撈到程式裡算。」——把 50 萬筆讀進記憶體再迴圈，是效能問題的頭號來源。
176複雜度
下列演算法之最壞情況時間複雜度，何者為 O(n²)？
看詳解
答案：(C) 快速排序
快速排序平均 O(n log n)，但最壞 O(n²)——發生在每次都選到極端的樞紐值（如對已排序資料選首元素為樞紐）。

演算法平均最壞穩定額外空間
合併排序n log nn log n是O(n)
堆積排序n log nn log n否O(1)
快速排序n log nn²否O(log n)

177搜尋

看詳解
答案：(B) 二分搜尋
「已排序」＋「找落在哪個區間」＝ 二分搜尋的變形（找上界／下界）。

複雜度 O(log n)；級距只有十幾筆時線性搜尋也夠快，但級距表若動態產生（如逐年累積）就有差別。

⚠️ 稅務程式的邊界陷阱 級距的邊界值屬於哪一級（是 > 還是 ≥），必須依法規條文認定，不能由程式設計者自行決定——差一元就可能差一個級距，這是會被訴願的。
178雜湊
本府以身分證字號為鍵建立雜湊表，發生大量碰撞。最可能之原因為？

180動態規劃
本府補助方案欲從多個可執行的計畫中，在預算限制下使受益人數最大，且各計畫不可分割。最適合之解法為？
看詳解
答案：(B) 動態規劃
「不可分割」＝ 0/1 背包，貪心法不保證最佳解。

反例：預算 10；計畫 A 花 6 益 7、B 花 5 益 5、C 花 5 益 5。
貪心（按益／費比）先選 A（1.17）→ 剩 4，什麼都做不了，總益 7；
最佳解選 B + C → 總益 10。這個反例可以直接寫在申論上。

地特加分角度：實務上受益人數不是唯一目標，還須考量弱勢優先、地區均衡、法定義務——應以多目標決策處理，並將權重提請權責會議核定。
181動態規劃
動態規劃適用之兩個必要性質為？
看詳解
答案：(A)
性質意思
最佳子結構整體最佳解由子問題最佳解組成
重疊子問題同一個子問題被反覆計算 → 存起來就省下重複
只有最佳子結構、沒有重疊 → 用分治法（如合併排序）；
只有重疊、沒有最佳子結構 → DP 會算錯。

區辨貪心法：貪心也要最佳子結構，但額外要求貪心選擇性質（每步的局部最佳不會妨礙全局最佳）——這正是 0/1 背包不能用貪心的原因。

195程式品質
本府某程式計算補助金額時偶有一元誤差。最可能之原因為？
看詳解
答案：(B)
金額絕不可用浮點數（float／double）——二進位無法精確表示 0.1，累加後必然出現誤差。應用整數（以分為單位）或十進位型別（decimal）。

另一半原因是四捨五入時機：「先分項進位再加總」與「先加總再進位」結果可能差一元——這必須依法規或作業規定認定，不是工程判斷。

⚠️ 為什麼一元很重要 公款的一元差額在會計上就是錯帳，須查明原因並更正；累積到千筆就是可被審計糾正的事項。

239綜合情境
本府資訊人員面對業務單位提出的不合理需求（如要求存取非其權責之個資），最適當之處理為？
看詳解
答案：(B)
⚠️ 這是保護自己的關鍵題 依公務員服務法，長官所發命令如認為違法，應負報告義務；且個資法之違法利用有刑事責任——「聽命行事」不當然免責。
正確三步：①說明法規限制 ②提出可合法達成目的的替代方案（如去識別化統計、限縮欄位） ③簽陳核示並留存書面。

地特加分角度：(D) 私下開通不留紀錄是最危險的——出事時你是唯一有紀錄的執行者。
240綜合情境
本府某項服務同時可線上與臨櫃辦理，兩者資料未即時同步致民眾重複申請。最適當之改善為？
看詳解
答案：(B)
多管道服務的鐵則：「前台可以多個，後台必須只有一個。」

常見錯誤設計：線上申辦另建一套資料庫，每晚才與臨櫃系統同步——白天這段時間就是漏洞。

地特加分角度：這同時解決另一個問題——民眾線上申請後臨櫃詢問，櫃檯查不到；或反之。單一資料來源是「服務一致性」的技術前提。
241綜合情境
本府欲提升資訊業務之持續改善能力，最根本之機制為？
看詳解
答案：(B)
區辨兩個概念：事件管理是「趕快恢復服務」；問題管理是「找出根因，讓它不要再發生」。

層次問的問題
事件怎麼快點恢復？
問題為什麼會發生？（連問五次「為什麼」）
改善要改什麼制度或設計才不會再犯？
地特加分角度：只有事件管理沒有問題管理的機關，會一直在救同一種火——而且會誤以為自己「應變能力很強」。
242綜合情境
本府擬訂定資訊業務相關自治法規。下列何者最適合以自治規則（非自治條例）訂定？
看詳解
答案：(B)
地方制度法的分工：涉及人民權利義務或設有罰則者，須以「自治條例」（經議會通過）；機關內部作業事項得以「自治規則」（行政機關訂定）。

事項法規形式
罰鍰、限制權利、創設義務自治條例
內部作業程序、資安管理規範自治規則
地特加分角度：這題是地方制度法與資訊業務的交會處，正是地特三等偏好的出題角度。

延伸：法學題庫地方制度法專章。
243綜合情境
本府欲爭取中央補助辦理數位建設，提案時最應強調何者？
看詳解
答案：(B)
審查委員在意的三件事：①符不符合政策方向 ②做完有什麼具體效益 ③補助結束後你養不養得起。

⚠️ 第三點最常被扣分 只寫建置經費、沒寫後續每年的維運經費從哪來，會被質疑「補助一結束就變蚊子建設」。應明確說明將於年度預算編列維運費用。
地特加分角度：可強調「本案成果可供其他縣市複製」——中央樂見補助產生外溢效益。
244綜合情境
本府資訊單位人力有限，面對各局處大量需求，最適當之處理機制為？
看詳解
答案：(B)
「先來先做」的問題：會吵的先做，重要的排在後面；而且資訊單位變成得罪人的那一方。

機制設計：①統一的需求申請單（含效益說明與業務依據） ②評估工時與風險 ③由跨局處會議（或府級主管）核定排序 ④公開排程與進度。

地特加分角度：關鍵在「把排序的決定權往上移」——資訊單位負責提供資訊（要多久、有什麼風險），由權責層級決定先後，這樣才有正當性也才做得下去。
245綜合情境
綜合全題庫，地方特考三等資訊處理人員最核心的職能為何？
看詳解
答案：(B)
📐 地特三等的三個核心能力（也是申論的評分軸） ①翻譯能力：把業務單位的話翻成技術需求，把技術限制翻成業務單位聽得懂的話
②法遵意識：每個技術方案都先問「法律上做得到嗎」
③排序能力：資源永遠不夠，能說出「為什麼先做這個」才是專業
寫申論時，這三件事各占一段，配上一張表與一句「分期試辦、逐步推廣」的結論，就是穩定的高分結構。

T. 資訊治理與管理實務進階（第 246～295 題）

對應地特三等深化教材第 13～24 章：資訊治理、專案管理、資安治理、資料治理、雲端與新興科技的機關應用。

246資訊治理
機關資訊治理架構中，「資訊長（CIO）」的核心職責應著重於？
看詳解
答案：(B)
📐 CIO 的定位 CIO 是橋接「業務需求」與「技術能力」的角色，不是最資深的工程師。
其價值在於：判斷哪些資訊投資能支撐施政目標，並在資安與成本之間做出治理層級的決策。
資訊治理三層次：策略層（CIO，對齊施政目標）、管理層（資訊主管，執行與控管）、操作層（工程師，實作）——
三層各司其職，混淆層級是治理失靈的常見原因。
247資訊治理
機關辦理「資訊業務委外評估」時，下列何者不應作為主要考量？
看詳解
答案：(B)
委外評估必須以「業務性質」與「風險可控性」為準，人際關係與政府採購的公平公正原則相牴觸。

評估面向應考量
業務性質是否涉及機敏政策、核心決策邏輯
資安風險個資、機敏資料的存取與外流風險
長期成本是否造成技術鎖定（原始碼、文件是否可取得）
公務提醒：委外評估報告應留存書面紀錄，作為未來稽核與課責的依據。
248資訊治理
機關導入 ISO 27001 資訊安全管理系統（ISMS），其核心精神為？
看詳解
答案：(B)
📐 PDCA 循環 P（規劃）：風險評估、訂定政策
D（執行）：落實管控措施
C（檢查）：內部稽核、監控成效
A（改善）：修正缺失、持續優化 → 回到 P，循環不止
⚠️ 常見誤區 「通過驗證」不等於「安全」——驗證只是證明制度存在，實際落實才是關鍵。
許多機關取得證書後便鬆懈，反而增加風險。
249資安治理
機關依「資通安全責任等級分級辦法」，其資安防護等級應如何決定？
看詳解
答案：(B)
資安分級是「風險基礎」的治理精神：業務性質涉及國安、金融、關鍵基礎設施者，責任等級較高；
一般行政機關則依業務衝擊程度分級，非一律齊頭式管理。

💡 考點延伸
不同責任等級對應不同的資安治理、防護、檢測及應變基準要求——
等級越高，稽核頻率與滲透測試要求也越高。
250資安治理
機關發生資安事件後，依規定應於知悉時起多久內完成通報？
看詳解
答案：(B)
⚠️ 涉及法規時限，務必以法規原文為準 資安事件通報依資通安全管理法及其子法規定，依事件等級有明確的通報時限，
逾期未通報或匿報，機關與相關人員可能面臨行政責任。
事件應變原則：①先止血再究責（優先復原服務、保全跡證） ②誠實通報（匿報的法律與信譽代價遠高於誠實通報） ③留存完整處理紀錄供事後檢討
251資安治理
機關辦理「弱點掃描」與「滲透測試」的差異為？
看詳解
答案：(B)
項目弱點掃描滲透測試
方式自動化工具比對已知漏洞資料庫人工模擬攻擊者實際嘗試入侵
頻率可較頻繁（月／季）通常年度或重大改版後
深度廣度優先深度優先，可發現邏輯性弱點
務必事先取得書面授權：滲透測試在未授權情況下執行，本身即構成違法入侵行為。
252資料治理
機關建立「資料字典」（Data Dictionary）的主要目的為？
看詳解
答案：(B)
沒有資料字典的機關常見亂象：A 系統的「案件狀態＝3」代表「已結案」，
B 系統的「狀態＝3」卻代表「退回補正」——跨系統對接時資料被誤判。

📐 資料字典應記載 欄位名稱、中文定義、資料型別、允許值域、負責維護單位、更新歷程
延伸應用：機關間資料介接（如政府資料交換平台）高度依賴一致的資料定義。
253資料治理
「資料生命週期管理」中，資料的「保存期限」應如何訂定？
看詳解
答案：(B)
階段要點
建立依業務規則產生
使用存取控制、稽核紀錄
保存依檔案法、個資法及業務法規訂定期限，非工程判斷
銷毀逾期個資應依法刪除或去識別化，並留存銷毀紀錄
常見錯誤：以「怕以後要用」為由無限期保留個資——
這違反個資法「特定目的消失應即刪除」的原則，屬法遵風險。
254資料治理
機關開放資料（Open Data）釋出前，最重要的檢核步驟為？
看詳解
答案：(B)
⚠️ 去識別化不是「刪掉姓名」就夠 單筆資料看似無法識別個人，但與其他公開資料集交叉比對後，可能被重新識別——
例如「出生年月＋郵遞區號＋性別」組合，往往能唯一鎖定特定個人。
開放資料檢核清單：①去識別化並評估重新識別風險 ②格式應為機器可讀（如 CSV、JSON） ③標示資料來源、更新頻率與授權方式 ④建立更新維護機制，避免資料過時誤導
255資料治理
機關「主檔資料管理」（Master Data Management）的核心價值為？
看詳解
答案：(B)
症狀：同一位民眾在戶政系統地址是「A」，在稅務系統地址卻是「B」——
各系統各自維護同一份資料，久了必然分歧。

📐 解法 指定單一權威來源（如戶政系統為地址的權威來源），
其他系統透過介接取得，而非各自輸入維護。
公務意義：這正是「單一申辦窗口」與「資料共享」政策能落地的技術基礎。
256系統整合
機關系統間介接時，採用「共用元件」（如自然人憑證、行動身分識別）而非各自開發驗證機制的主要理由為？
看詳解
答案：(B)
各自開發共用元件
每個系統各有一套弱點——攻擊面隨系統數線性增加集中維護，統一修補
驗證強度不一致強度統一，符合國家標準
重複開發成本高邊際成本遞減
反面代價：共用元件一旦出問題，影響範圍是全國性的——
因此共用元件的可用性與資安等級要求遠高於一般系統。
257系統整合
機關系統改版時，採「藍綠部署」（Blue-Green Deployment）策略的主要效益為？
看詳解
答案：(B)
📐 運作方式 藍（舊版）持續服務，綠（新版）同時部署並測試；
確認無誤後，將流量切換至綠版；
若發現問題，立即切回藍版，幾乎零停機。
對照傳統作法：直接於同一環境更新，若出錯只能緊急搶修或漫長回滾，
民眾申辦服務可能因此中斷數小時。

公務適用時機：報稅、報名等有法定期限、不容中斷的系統改版。
258系統整合
機關導入 API 閘道（API Gateway）管理跨系統介接，其主要功能不包括？
看詳解
答案：(B)
API 閘道是「管理層」，不是「業務邏輯層」——它不會、也不應該替代後端系統的商業邏輯。

API 閘道做什麼說明
統一驗證各系統不必各自實作身分驗證
流量控管速率限制，防止單一來源打爆後端
集中日誌誰、何時呼叫了哪個 API——稽核與追查的基礎
版本管理新舊版本並存，逐步汰換
259專案管理
機關資訊專案採「瀑布式開發」而非「敏捷開發」時，較適合的情境為？
看詳解
答案：(B)
瀑布式敏捷式
需求特性明確、少變動不確定、常調整
文件要求完整、階段性驗收精簡、持續交付
政府採購適配易對應驗收付款節點需搭配敏捷採購條款，較少見
實務折衷：許多機關採「混合式」——整體以瀑布式分階段驗收，內部開發用敏捷迭代。
260專案管理
機關資訊專案管理中，「範疇潛變」（Scope Creep）是指？
看詳解
答案：(B)
⚠️ 公務常見場景 「順便加一個功能」「這個應該不難吧」——
每次都是小需求，累積起來卻讓專案時程與預算完全失控。
防範機制：①建立正式的變更管理程序（新增需求須經評估與核准） ②任何範疇變更都應同步評估對時程、預算的影響 ③需求源頭應留存書面紀錄，避免各說各話

根本原因：初期需求訪談不夠完整，導致執行中不斷「發現」遺漏的需求。
261專案管理
機關辦理資訊專案的「風險管理」，下列敘述何者正確？
看詳解
答案：(B)
📐 風險管理四步驟（持續循環） ①識別：可能發生什麼問題（如廠商人力異動、關鍵人員離職）
②評估：發生機率 × 影響程度
③因應：避免、降低、轉移（如保險或合約條款）、接受
④監控：定期檢視，風險狀態會隨專案進行而改變
常見高風險項目：單一廠商依賴、關鍵技術人員異動、法規於專案期間修正。
262預算編列
機關資訊系統採「總持有成本」（TCO）評估而非僅比較採購價格，其理由為？
看詳解
答案：(B)
成本類型常見項目
初期採購、建置、教育訓練
長期維運年度授權費、維護費、資安更新、人力成本
汰換硬體生命週期到期、系統遷移成本
陷阱：低價標到的系統，若後續授權費逐年高漲或維運複雜，
五年總成本可能遠高於當初評估較貴的方案——這是採購評選時常被忽略的盲點。
263預算編列
機關年度資訊預算編列時，「維運費用」通常應如何估算較為合理？
看詳解
答案：(B)
「出問題再追加」的風險：政府預算編列有年度週期與程序時間，
臨時追加往往緩不濟急，甚至可能無法及時通過。

💡 業界經驗法則
系統維運成本常態約為建置成本的 15～20%／年，
並應隨使用量成長（如資料量、使用人數）動態檢討，而非一成不變。
連結前題：這正是TCO 評估的實務應用——編預算時要看長期，不能只看當年。
264法規遵循
機關辦理電子化服務時，依「行政程序法」與「電子簽章法」，下列敘述何者正確？
看詳解
答案：(B)
⚠️ 涉及法律效力，實際適用應以法規原文與主管機關解釋為準 電子簽章法承認電子文件與簽章在特定條件下可代替書面與簽名，
但並非所有法律行為都適用——部分事項（如涉及重大身分或財產處分）仍可能有特別規定。
公務系統設計要點：導入電子化流程前，應確認該業務的法定形式要求，
並會商法制單位，而非僅由資訊人員自行判斷。
265法規遵循
機關委託民間廠商處理個人資料（如民眾申辦資料）時，依個人資料保護法，機關的責任為？
看詳解
答案：(B)
「委外」不等於「免責」——這是機關辦理委外業務時最常見的誤解。

📐 委外個資管理應辦事項 ①於契約明定受託者之保護義務與範圍
②對受託者進行適當之監督（稽核、查核）
