1. 為什麼要自動化

手動作業的問題實際會發生什麼
慢50 台交換器改一條 ACL，SSH 進去一台台改，要一整天
會出錯複製貼上時漏了一行、貼到錯的機器、VLAN 號打錯一位數
不一致同型號的交換器，設定卻各不相同，因為每次都是「手動微調」
沒有稽核軌跡「這條規則是誰加的、什麼時候加的、為什麼？」沒人知道
無法測試改設定前無法驗證，只能上線後祈禱
比喻：手動設定像每次都手寫一份合約——寫 50 份會有 50 種細微差異，而且沒人記得改過哪些條款。自動化像用 Word 範本 + 版本控制——範本改一次，50 份全部一致，而且每次修改都有紀錄可以回溯。
自動化真正的價值不是「快」，是「一致和可回溯」。
  • 設定存在 Git 裡 → 誰在什麼時候改了什麼，一目瞭然
  • 設定即程式碼（Infrastructure as Code）→ 可以先在測試環境驗證
  • 出事可以 git revert → 幾秒鐘回到已知的良好狀態
  • 新人接手看 Git 就知道現況，不用逐台 show run 拼湊

2. 命令式 vs 宣告式

命令式（Imperative）

告訴系統「怎麼做」——一步一步的指令。

# 傳統 CLI / Netmiko
conf t
vlan 10
 name SALES
interface fa0/1
 switchport mode access
 switchport access vlan 10
end

問題：重複執行可能出錯；不知道目前狀態就不知道該下什麼指令。

宣告式（Declarative）

告訴系統「我要什麼結果」——它自己想辦法達成。

# Ansible / RESTCONF
vlans:
  - id: 10
    name: SALES
interfaces:
  - name: FastEthernet0/1
    mode: access
    access_vlan: 10

優點：冪等性——跑一次和跑一百次結果相同。

冪等性（Idempotency）是自動化最重要的概念。
執行 1 次的結果 = 執行 N 次的結果
有冪等性，你可以放心地重複執行——已經符合期望狀態的設備會被跳過（Ansible 顯示 ok），只有不符合的才會被修改（顯示 changed）。

沒有冪等性的腳本，第二次執行可能會重複加規則、或因為「VLAN 已存在」而報錯中斷。
Netmiko 本身沒有冪等性。它只是幫你自動打字。要有冪等性，你得自己寫「先檢查現況、不符合才改」的邏輯，或改用 NAPALM／Ansible 這類本身就處理好的工具。

3. 三種資料格式：JSON、XML、YAML

JSONXMLYAML
主要用在REST APINETCONFAnsible、設定檔
人類可讀性中低高
結構表示{ } 物件、[ ] 陣列成對標籤縮排
支援註解不支援支援支援（#）
檔案大小小大最小

同一份資料的三種寫法

// ── JSON ──
{
  "device": {
    "hostname": "SW1",
    "vlans": [
      { "id": 10, "name": "SALES" },
      { "id": 20, "name": "ENG" }
    ],
    "enabled": true,
    "uptime": 84200
  }
}
<!-- ── XML ── -->
<device>
  <hostname>SW1</hostname>
  <vlans>
    <vlan><id>10</id><name>SALES</name></vlan>
    <vlan><id>20</id><name>ENG</name></vlan>
  </vlans>
  <enabled>true</enabled>
  <uptime>84200</uptime>
</device>
# ── YAML ──
device:
  hostname: SW1
  vlans:
    - id: 10
      name: SALES
    - id: 20
      name: ENG
  enabled: true
  uptime: 84200
JSON 的四個常見錯誤（考試會考）：
  • 最後一個元素後面不能有逗號（trailing comma）
  • key 一定要用雙引號，不能用單引號，也不能不加
  • 不支援註解——加了 // 就會解析失敗
  • 布林值是小寫 true / false，不是 True/False
YAML 的三個地雷：
  • 絕對不能用 Tab 縮排，只能用空格。這是最常見的錯誤
  • 冒號後面要有空格：key: value，不是 key:value
  • yes、no、on、off 會被當成布林值。VLAN 名稱叫 NO 要加引號
# Python 裡的轉換
import json, yaml

data = json.loads(json_string)          # JSON 字串 → Python dict
json_string = json.dumps(data, indent=2) # dict → JSON 字串

data = yaml.safe_load(yaml_string)      # YAML → dict（用 safe_load，不要用 load）
yaml_string = yaml.dump(data)           # dict → YAML

4. REST API 與 HTTP

REST API 是用 HTTP 來操作資源的一種風格。網路設備把每個設定項目當成一個「資源」，用不同的 HTTP 動詞去操作它。

GET讀取資源
安全、冪等
POST新增資源
非冪等
PUT整個取代
冪等
PATCH局部修改
冪等
DELETE刪除資源
冪等
PUT 和 PATCH 的差別會害你刪掉設定。
  • PUT = 整個取代。送出的內容裡沒有的欄位，會被清空
  • PATCH = 只改送出的欄位，其他保持不變
實例：介面目前有 IP、description、ACL。你用 PUT 只送了 IP → description 和 ACL 會消失。要改單一項目永遠用 PATCH。

HTTP 狀態碼

碼意義網路自動化情境
200 OK成功GET 成功拿到資料
201 Created建立成功POST 成功建立新設定
204 No Content成功但無回應內容PUT/PATCH/DELETE 成功
400 Bad Request請求格式錯JSON 語法錯或欄位不合法
401 Unauthorized沒有認證帳密錯或 token 過期
403 Forbidden認證了但沒權限帳號權限等級不足
404 Not Found資源不存在URL 路徑打錯，最常見
409 Conflict衝突POST 建立已存在的資源
500 Internal Server Error伺服器出錯設備端的問題
速記：2xx 成功、3xx 重導向、4xx 是你的錯、5xx 是對方的錯。看到 4xx 先檢查自己的 URL、JSON 格式、帳密權限。

5. NETCONF / RESTCONF / gNMI

NETCONFRESTCONFgNMI
傳輸SSH（830）HTTPS（443）gRPC / HTTP2
資料格式XMLJSON 或 XMLProtobuf
資料模型YANGYANGYANG
交易（Transaction）支援不支援部分
設定回滾支援不支援不支援
串流遙測有限不支援強項
學習難度高低中
怎麼選？
  • 剛開始學／簡單任務 → RESTCONF，就是一般的 HTTP + JSON，用 requests 就能操作
  • 需要「全部成功或全部回滾」 → NETCONF，它有 candidate config 和 commit/rollback
  • 要即時監控大量設備 → gNMI，串流遙測效能遠勝輪詢 SNMP

NETCONF 的三種資料儲存區

Datastore意義
running目前生效的設定（等同 running-config）
candidate草稿區——改完之後 commit 才生效，可以先 validate
startup開機時載入的設定（等同 startup-config）
candidate + commit 是 NETCONF 最大的優勢。你可以一次改十個項目、驗證過再一起套用。中間出錯就整批放棄，不會留下改了一半的殘破設定。傳統 CLI 是打一行生效一行，改到一半斷線就慘了。
! ── 設備端啟用（IOS-XE）──
R1(config)# netconf-yang
R1(config)# restconf
R1(config)# ip http secure-server
R1(config)# username api-user privilege 15 secret ApiP@ss123
R1(config)# aaa new-model
R1(config)# aaa authentication login default local
R1(config)# aaa authorization exec default local

! ── 驗證 ──
R1# show netconf-yang sessions
R1# show platform software yang-management process
aaa authorization exec default local 這行不能少。沒有它，RESTCONF 會回 401 或 403，而且錯誤訊息不會告訴你原因。這是 IOS-XE 上最常見的 RESTCONF 卡關點。

6. YANG 資料模型

YANG 是一種「描述設定長什麼樣子」的語言。它定義了資料的階層、型別、限制——像是資料庫的 schema。

比喻：YANG 是表格的欄位定義，NETCONF/RESTCONF 是填表和送件的方式。有了統一的表格定義，不同廠牌的設備才能用同一套程式操作。
模型類型誰定義跨廠牌範例
IETF 標準模型IETF可以ietf-interfaces
OpenConfig 模型Google 等業者聯盟可以openconfig-interfaces
廠商原生模型Cisco / Juniper 等不行Cisco-IOS-XE-native
取捨很明確：標準模型可以跨廠牌但功能有限；原生模型能碰到每一個設定項目但綁死廠商。實務建議：能用標準模型就用，需要特殊功能才用原生。
# 查設備支援哪些 YANG 模型
R1# show netconf-yang datastores

# 用 pyang 檢視模型結構（先 pip install pyang）
$ pyang -f tree ietf-interfaces.yang

module: ietf-interfaces
  +--rw interfaces
     +--rw interface* [name]
        +--rw name           string
        +--rw description?   string
        +--rw type           identityref
        +--rw enabled?       boolean

# rw = 可讀可寫    ro = 唯讀
# *  = list（可以有多筆）    ? = optional
Cisco 的 YANG 模型全部公開在 GitHub（YangModels/yang）。實務上找路徑最快的方法是：先用 GET 撈整份設定下來，看 JSON 的 key 長什麼樣，再照著寫 PATCH。不需要背模型。

7. 實作一：用 RESTCONF 讀寫設定

URL 結構

https://<設備IP>/restconf/data/<YANG模型>:<容器>/<節點>
# ── 讀取所有介面 ──
GET https://192.168.1.1/restconf/data/ietf-interfaces:interfaces

# ── 讀取單一介面（注意 %2F 是斜線的編碼）──
GET https://192.168.1.1/restconf/data/ietf-interfaces:interfaces/interface=GigabitEthernet1

# ── Cisco 原生模型：讀取所有 VLAN ──
GET https://192.168.1.1/restconf/data/Cisco-IOS-XE-native:native/vlan

用 curl 快速測試

$ curl -k -u api-user:ApiP@ss123 \
    -H "Accept: application/yang-data+json" \
    https://192.168.1.1/restconf/data/ietf-interfaces:interfaces

Python 完整範例

import requests
import json
import urllib3
urllib3.disable_warnings()   # 實驗室用自簽憑證才關，正式環境要驗證

HOST = "192.168.1.1"
AUTH = ("api-user", "ApiP@ss123")
HEADERS = {
    "Accept": "application/yang-data+json",
    "Content-Type": "application/yang-data+json",
}
BASE = f"https://{HOST}/restconf/data"


def get_interfaces():
    """讀取所有介面"""
    r = requests.get(f"{BASE}/ietf-interfaces:interfaces",
                     auth=AUTH, headers=HEADERS, verify=False, timeout=10)
    r.raise_for_status()
    return r.json()


def set_description(ifname, desc):
    """改介面描述 —— 用 PATCH，不會動到其他欄位"""
    url = f"{BASE}/ietf-interfaces:interfaces/interface={ifname}"
    payload = {
        "ietf-interfaces:interface": {
            "name": ifname,
            "description": desc,
        }
    }
    r = requests.patch(url, auth=AUTH, headers=HEADERS,
                       data=json.dumps(payload), verify=False, timeout=10)
    # 204 = 成功且沒有回應內容
    if r.status_code == 204:
        print(f"  ✅ {ifname} 描述已更新")
    else:
        print(f"  ❌ {ifname} 失敗 {r.status_code}: {r.text}")


def create_vlan(vid, name):
    """建立 VLAN（Cisco 原生模型）"""
    url = f"{BASE}/Cisco-IOS-XE-native:native/vlan"
    payload = {
        "Cisco-IOS-XE-vlan:vlan-list": [
            {"id": vid, "name": name}
        ]
    }
    r = requests.patch(url, auth=AUTH, headers=HEADERS,
                       data=json.dumps(payload), verify=False, timeout=10)
    print(f"  VLAN {vid} → {r.status_code}")


if __name__ == "__main__":
    data = get_interfaces()
    for intf in data["ietf-interfaces:interfaces"]["interface"]:
        print(f"  {intf['name']:<28} enabled={intf.get('enabled')}")

    set_description("GigabitEthernet2", "== MANAGED BY PYTHON ==")
    create_vlan(110, "AUTOMATION-TEST")
verify=False 只能用在實驗室。它關掉 TLS 憑證驗證，等於接受任何中間人。正式環境要在設備上裝正式憑證，並用 verify="/path/to/ca.pem" 指定 CA。

同理，帳密不要寫死在程式裡。用環境變數或 python-dotenv，並確保 .env 有寫進 .gitignore——把設備密碼推上 GitHub 是真實發生過的事故。

8. 實作二：Python + Netmiko

不是所有設備都支援 RESTCONF——舊的 IOS 交換器只有 CLI。Netmiko 是幫你自動 SSH 進去打指令的函式庫，是網路工程師最實用的入門工具。

$ pip install netmiko

單台設備

from netmiko import ConnectHandler

device = {
    "device_type": "cisco_ios",
    "host": "192.168.1.1",
    "username": "admin",
    "password": "P@ssw0rd",
    "secret": "EnableP@ss",     # enable 密碼
    "fast_cli": False,
}

with ConnectHandler(**device) as conn:
    conn.enable()

    # 查詢類指令
    print(conn.send_command("show ip interface brief"))

    # 自動解析成 Python 結構（需 pip install ntc-templates）
    intfs = conn.send_command("show ip interface brief", use_textfsm=True)
    for i in intfs:
        if i["status"] != "up":
            print(f"  ⚠ {i['interface']} 是 {i['status']}")

    # 設定類指令
    cmds = [
        "vlan 110",
        " name AUTOMATION-TEST",
        "interface range fa0/10 - 12",
        " switchport mode access",
        " switchport access vlan 110",
        " spanning-tree portfast",
    ]
    print(conn.send_config_set(cmds))
    print(conn.save_config())          # 等同 write memory
use_textfsm=True 是 Netmiko 最有用的功能。它把 show 指令的文字輸出自動解析成 list of dict，你就不用自己寫正規表示式去切字串。支援上百個常用指令。

批次處理 50 台設備（含平行執行）

from netmiko import ConnectHandler
from netmiko.exceptions import NetmikoTimeoutException, NetmikoAuthenticationException
from concurrent.futures import ThreadPoolExecutor, as_completed
import csv, os, datetime

USER = os.environ["NET_USER"]      # 從環境變數讀，不寫死
PASS = os.environ["NET_PASS"]


def load_inventory(path="devices.csv"):
    """devices.csv: hostname,ip,device_type"""
    with open(path, newline="", encoding="utf-8") as f:
        return list(csv.DictReader(f))


def backup_one(row):
    """備份單台設備的設定，回傳 (hostname, 成功與否, 訊息)"""
    dev = {
        "device_type": row["device_type"],
        "host": row["ip"],
        "username": USER,
        "password": PASS,
        "conn_timeout": 15,
    }
    try:
        with ConnectHandler(**dev) as conn:
            cfg = conn.send_command("show running-config")
        stamp = datetime.date.today().isoformat()
        os.makedirs(f"backups/{stamp}", exist_ok=True)
        with open(f"backups/{stamp}/{row['hostname']}.cfg", "w", encoding="utf-8") as f:
            f.write(cfg)
        return (row["hostname"], True, f"{len(cfg)} bytes")

    except NetmikoAuthenticationException:
        return (row["hostname"], False, "帳號密碼錯誤")
    except NetmikoTimeoutException:
        return (row["hostname"], False, "連線逾時")
    except Exception as e:
        return (row["hostname"], False, str(e))


if __name__ == "__main__":
    devices = load_inventory()
    ok = fail = 0

    # 平行 10 條連線，50 台從 10 分鐘變 1 分鐘
    with ThreadPoolExecutor(max_workers=10) as pool:
        futures = {pool.submit(backup_one, d): d for d in devices}
        for fut in as_completed(futures):
            host, success, msg = fut.result()
            if success:
                ok += 1
                print(f"  ✅ {host:<20} {msg}")
            else:
                fail += 1
                print(f"  ❌ {host:<20} {msg}")

    print(f"\n  完成：成功 {ok} 台，失敗 {fail} 台")
平行數不要開太大。max_workers 設 50 同時連 50 台，可能觸發設備的 VTY 上限（預設只有 16 條）或 TACACS 伺服器的速率限制。10–20 是安全值。
寫入類的腳本一定要有「先看再做」模式。加一個 --dry-run 參數，先印出「我打算對哪幾台下哪些指令」，人工確認後才真的執行。一個沒測試過的迴圈可以在三十秒內毀掉整個網路。

9. 實作三：NAPALM 跨廠牌

NAPALM（Network Automation and Programmability Abstraction Layer with Multivendor support）在各廠牌之上包了一層統一介面——同一段程式碼可以操作 Cisco、Juniper、Arista。

$ pip install napalm
import napalm

driver = napalm.get_network_driver("ios")    # 或 "junos" / "eos" / "nxos"
device = driver(hostname="192.168.1.1",
                username="admin",
                password="P@ssw0rd",
                optional_args={"secret": "EnableP@ss"})

device.open()

# ── 統一格式的查詢（不管什麼廠牌，回傳結構都一樣）──
print(device.get_facts())          # 型號、序號、版本、uptime
print(device.get_interfaces())     # 介面狀態
print(device.get_arp_table())
print(device.get_bgp_neighbors())
print(device.get_lldp_neighbors())

device.close()

NAPALM 最強的功能：設定差異比對與回滾

import napalm

driver = napalm.get_network_driver("ios")
device = driver("192.168.1.1", "admin", "P@ssw0rd")
device.open()

# 1. 載入候選設定（此時還沒生效）
device.load_merge_candidate(filename="new_vlans.cfg")

# 2. 看看到底會改什麼 —— 這一步是關鍵
diff = device.compare_config()
print("預計變更：\n", diff)

# 3. 人工確認後才套用
if diff and input("確認套用？(yes/no) ") == "yes":
    device.commit_config()
    print("  ✅ 已套用")
else:
    device.discard_config()
    print("  已放棄變更")

# 4. 事後發現有問題 → 一行回滾
# device.rollback()

device.close()
compare_config() 是 NAPALM 存在的理由。它讓你在套用之前就看到完整的差異，像 git diff 一樣。這是 Netmiko 完全做不到的——Netmiko 只會照你的指令打字，打完你才知道結果。
NetmikoNAPALMAnsible
抽象層級低（就是自動打字）中高
跨廠牌需自己處理統一介面模組化支援
冪等性沒有部分有
差異比對沒有有有
回滾沒有有有（透過 NAPALM）
彈性最高（任何指令都能打）中中
適合臨時任務、特殊指令跨廠牌查詢與設定大規模、常態部署

10. 實作四：Ansible Playbook

Ansible 是宣告式的組態管理工具，無代理程式（agentless）——不用在設備上裝任何東西，靠 SSH 或 API 就能操作。

$ pip install ansible ansible-pylibssh
$ ansible-galaxy collection install cisco.ios

清單檔 inventory.yml

all:
  children:
    access_switches:
      hosts:
        SW1: { ansible_host: 192.168.1.11 }
        SW2: { ansible_host: 192.168.1.12 }
        SW3: { ansible_host: 192.168.1.13 }

Playbook：一次部署 VLAN 到所有接入層交換器

---
- name: 部署標準 VLAN 與埠設定
  hosts: access_switches
  gather_facts: no

  vars:
    standard_vlans:
      - { id: 10, name: SALES }
      - { id: 20, name: ENGINEERING }
      - { id: 30, name: FINANCE }
      - { id: 50, name: VOICE }
      - { id: 99, name: MGMT }
      - { id: 999, name: BLACKHOLE }

  tasks:
    - name: 備份目前設定
      cisco.ios.ios_config:
        backup: yes
        backup_options:
          dir_path: ./backups
          filename: "{{ inventory_hostname }}.cfg"

    - name: 建立 VLAN
      cisco.ios.ios_vlans:
        config: "{{ standard_vlans | map('combine', {}) | list }}"
        state: merged

    - name: 設定使用者埠
      cisco.ios.ios_config:
        lines:
          - switchport mode access
          - switchport access vlan 10
          - switchport nonegotiate
          - spanning-tree portfast
          - spanning-tree bpduguard enable
        parents: "interface {{ item }}"
      loop:
        - FastEthernet0/1
        - FastEthernet0/2
        - FastEthernet0/3

    - name: 關閉未使用的埠並隔離
      cisco.ios.ios_config:
        lines:
          - switchport access vlan 999
          - shutdown
          - description == UNUSED ==
        parents: "interface {{ item }}"
      loop: "{{ range(13, 25) | map('regex_replace', '^', 'FastEthernet0/') | list }}"

    - name: 存檔
      cisco.ios.ios_config:
        save_when: modified
# ── 先看會改什麼，不真的執行（最重要的習慣）──
$ ansible-playbook -i inventory.yml deploy_vlans.yml --check --diff

# ── 只對一台測試 ──
$ ansible-playbook -i inventory.yml deploy_vlans.yml --limit SW1

# ── 確認沒問題後全部執行 ──
$ ansible-playbook -i inventory.yml deploy_vlans.yml
--check --diff 是 Ansible 的救命符。它模擬執行並印出差異，完全不碰設備。任何正式環境的變更都應該先跑這個。搭配 --limit 先對一台試，確認無誤再全推。

執行結果怎麼讀

PLAY RECAP
SW1  : ok=5  changed=3  unreachable=0  failed=0
SW2  : ok=5  changed=0  unreachable=0  failed=0    ← 已經符合期望，沒改（冪等性）
SW3  : ok=2  changed=0  unreachable=1  failed=0    ← 連不上
第二次執行時 changed 應該全部是 0。如果重複執行還是一直 changed，代表某個 task 沒有冪等性（通常是用了 ios_config 的 lines 但比對邏輯不對）。這是檢查 playbook 品質的最快方法。

絕對不要把設備密碼 commit 進 Git。
  • .gitignore 要包含 *.env、secrets.yml、*.key、*.pem
  • 密碼用 Ansible Vault（ansible-vault encrypt secrets.yml）或環境變數
  • 備份的 running-config 裡面有加密後的密碼雜湊——推到公開 repo 等於送人破解材料。備份 repo 一定要設為 private
  • 已經推上去了？改密碼比清歷史更實際——git 歷史很難完全清乾淨

CI/CD：自動檢查與部署

# .github/workflows/network-ci.yml
name: Network Config CI

on: [pull_request]

jobs:
  validate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: 檢查 YAML 語法
        run: yamllint inventory/ playbooks/

      - name: Ansible 語法檢查
        run: ansible-playbook --syntax-check playbooks/*.yml

      - name: 對測試環境做 dry-run
        run: ansible-playbook -i inventory/lab.yml playbooks/deploy_vlans.yml --check --diff
這樣一來，任何人送 Pull Request，CI 就自動檢查語法並在實驗室環境跑 dry-run。錯誤在 merge 之前就被攔下來，而不是上線後才發現。這是軟體工程的標準做法，網路領域正在快速跟上。

12. 模型驅動遙測

SNMP（傳統輪詢）Model-Driven Telemetry
模式Pull——監控系統定時去問Push——設備主動送
頻率通常 5 分鐘可到秒級
設備負擔高（每次都要處理查詢）低（只在變化或排程時送）
資料格式MIB / OID（難懂）YANG（結構化）
擴展性設備多了輪詢就來不及好
比喻：SNMP 像每五分鐘打電話問「你還好嗎」——問的時候正常，掛掉電話後出事你完全不知道。Telemetry 像設備主動回報——「我的 CPU 剛剛跳到 90%」，即時而且不用你問。

更新模式行為適合
periodic固定間隔送一次介面流量、CPU、記憶體

典型的現代監控堆疊：設備 → Telegraf（收集）→ InfluxDB / Prometheus（時序資料庫）→ Grafana（視覺化）。全部開源，是目前業界最常見的組合。

13. 控制器：DNA Center 與 SDN

介面方向誰跟誰溝通用什麼
Northbound API控制器 → 上層應用你的程式 / 監控系統 ↔ 控制器REST API（JSON）
Southbound API控制器 → 設備控制器 ↔ 交換器 / 路由器NETCONF、OpenFlow、CLI、SNMP
方向記法：把控制器畫在中間，應用程式在上面（North）、設備在下面（South）。你寫的自動化腳本呼叫的是 Northbound API。

Cisco DNA Center 的能力

能力做什麼
Design定義站點階層、IP 位址池、設備設定範本
Policy用「群組」而非 IP 定義存取政策（SGT / TrustSec）
ProvisionPlug-and-Play：新設備上電自動取得設定
Assurance健康度評分、自動根因分析、「為什麼這位使用者連不上」
# DNA Center Northbound API 範例
import requests, urllib3
urllib3.disable_warnings()

DNAC = "https://sandboxdnac.cisco.com"     # Cisco DevNet 公開沙箱

# 1. 取得 token（有效期通常 1 小時）
r = requests.post(f"{DNAC}/dna/system/api/v1/auth/token",
                  auth=("devnetuser", "Cisco123!"), verify=False)
token = r.json()["Token"]

# 2. 列出所有網路設備
r = requests.get(f"{DNAC}/dna/intent/api/v1/network-device",
                 headers=headers, verify=False)

for d in r.json()["response"]:
    print(f"  {d['hostname']:<24} {d['platformId']:<18} {d['softwareVersion']}")
Cisco DevNet Sandbox 是免費的。提供 Always-On 的 DNA Center、IOS-XE（含 RESTCONF/NETCONF）、Meraki、ACI 等環境，不用自己買設備就能練 API。準備 CCNA 的自動化考題，這是最實際的練習場——網址搜尋「Cisco DevNet Sandbox」即可。

14. 導入的實務建議

1
先做「唯讀」的自動化設定備份、狀態盤點、合規稽核。零風險，而且立刻能證明價值。這一步就能省掉大量人工。
2
建立設備清單的單一真實來源CSV 或 YAML 都好，重點是只有一份。清單不準確，後面全部白搭。
3
所有東西進 Git包含腳本、範本、清單、備份。從第一天就養成 commit 訊息寫清楚的習慣。
4
才開始做「寫入」，而且從最無害的開始先自動化 description、NTP、syslog 這種改壞了也不會斷網的項目。
5
永遠先 dry-run，先 limit 一台--check --diff 加 --limit。這兩個參數會救你很多次。
6
寫回滾腳本，而且測試過它「出事怎麼回去」要在動手前就想好，不是出事才想。沒測試過的回滾等於沒有回滾。
7
建立實驗室環境GNS3、CML、EVE-NG 或 Containerlab。所有腳本先在這裡跑過。
自動化最大的風險：錯誤也會被自動化。手動改設定，改壞一台你就會發現。自動化改設定，30 秒改壞 200 台。

三個必要的保險：
  • 先備份，每次執行前自動存一份現況
  • 分批執行，Ansible 的 serial: 5 一次只做 5 台，出錯就停
  • 設定 fail-fast，第一台失敗就中止整個 playbook（any_errors_fatal: true）
學習路徑建議：
  1. Python 基礎（變數、迴圈、函式、dict/list）
  2. JSON / YAML 讀寫
  3. Netmiko 做備份與盤點 ← 最快看到成果
  4. Jinja2 產生設定
  5. Ansible 做部署
  6. RESTCONF / NETCONF 操作現代設備
  7. Git + CI/CD 建立流程
每一步都能獨立產生價值，不用全部學完才開始用。

完整實作 Lab：從備份到自動部署

需要 Python 3.10+ 與至少 2 台可 SSH 的設備（GNS3／CML／DevNet Sandbox 都可以）。約 120 分鐘。

階段一：唯讀（零風險）

  1. 建立 devices.csv（hostname, ip, device_type）
  2. 用 Netmiko + ThreadPoolExecutor 寫備份腳本，存成 backups/YYYY-MM-DD/hostname.cfg
  3. 加上完整的例外處理：認證失敗、逾時、其他錯誤要分開回報
  4. 用 use_textfsm=True 撈 show ip interface brief，列出所有非 up 的介面
  5. 寫合規稽核：檢查每台是否有 service password-encryption、ip ssh version 2、no ip http server

階段二：範本與版本控制

  1. 寫 Jinja2 範本 access_switch.j2
  2. 寫 switches.yml 存各台的變數（hostname、mgmt_ip、user_vlan）
  3. 用 Python 產生所有設定檔到 generated/
  4. git init，寫好 .gitignore（排除 .env、secrets、backups），commit 全部

階段三：寫入（有風險，先在實驗室）

  1. 安裝 Ansible 與 cisco.ios collection
  2. 寫 inventory.yml，帳密用 lookup('env', ...)
  3. 寫 playbook：備份 → 建 VLAN → 設埠 → 存檔
  4. 用 --check --diff --limit SW1 驗證
  5. 正式執行，然後再執行一次，確認 changed=0（冪等性）

階段四：API

  1. 在一台 IOS-XE 上啟用 restconf + netconf-yang（別忘了 aaa authorization）
  2. 用 curl 測試 GET ietf-interfaces:interfaces
  3. 用 Python requests 寫 GET + PATCH，修改介面描述
  4. 登入 Cisco DevNet Sandbox，取得 DNA Center token 並列出設備

驗收清單

  • 備份腳本對 3 台以上設備平行執行，總時間 < 30 秒
  • 故意把一台的密碼改錯，腳本能正確報出「帳號密碼錯誤」而不是崩潰
  • Jinja2 產生的設定檔跟手寫的一字不差
  • git log 至少有 5 個有意義的 commit
  • git status 看不到任何含密碼的檔案
  • Ansible playbook 第二次執行 changed=0
  • RESTCONF PATCH 回傳 204，且 show run 看得到變更

加碼挑戰

  1. 幫備份腳本加 --dry-run 參數，只印出會連哪些設備而不真的連。
  2. 用 NAPALM 的 compare_config() 在套用前印出差異，做出「人工確認才 commit」的流程。
  3. 寫一個腳本比對今天和昨天的備份，用 difflib 印出哪些設備的設定被改過——這是很實用的變更偵測。
  4. 設定 GitHub Actions，PR 時自動跑 yamllint 和 --syntax-check。
  5. 在 playbook 加上 serial: 1 和 any_errors_fatal: true，故意讓第二台失敗，觀察它是否正確中止。
  6. 用 Containerlab 或 CML 建一個 5 台設備的拓樸，把整套流程跑一遍。

本章重點回顧

  • 自動化的價值是一致性和可回溯，不只是快
  • 冪等性：執行 1 次和 N 次結果相同。Netmiko 沒有，Ansible / NAPALM 有
  • JSON 用在 REST、XML 用在 NETCONF、YAML 用在 Ansible
  • JSON 不能有尾逗號、不能有註解、key 要雙引號；YAML 不能用 Tab
  • PUT 整個取代（會清掉沒送的欄位）、PATCH 只改送的——改單項一律用 PATCH
  • 狀態碼：2xx 成功、204 是 PATCH/DELETE 成功、4xx 是你的錯、5xx 是對方的錯
  • NETCONF 走 SSH 830 + XML，有 candidate/commit/rollback；RESTCONF 走 HTTPS + JSON，最好上手
  • IOS-XE 開 RESTCONF 別忘了 aaa authorization exec default local
  • YANG 是資料模型；標準模型跨廠牌、原生模型功能全
  • Netmiko 彈性最高、NAPALM 能 diff 與 rollback、Ansible 適合大規模
  • Ansible --check --diff --limit 是正式環境的必要習慣
  • Git 管設定，密碼絕不 commit，備份 repo 一定要 private
  • Telemetry 是 push、SNMP 是 pull；Northbound 給應用、Southbound 給設備
  • 導入順序：唯讀 → 版本控制 → 低風險寫入 → 全面部署
