1. 排錯方法論：先有流程再動手

沒有方法的排錯像亂槍打鳥——這裡改一下、那裡重開一次，運氣好會通，但你不知道為什麼通，下次還會再發生。
有方法的排錯像醫生看診：問症狀 → 排除可能 → 驗證假設 → 確認治好了 → 記錄病歷。
1
定義問題（Define）「網路很慢」不是問題定義。要問到：誰受影響（一個人還是全部）？什麼時候開始？做什麼會發生？之前正常嗎？最重要的一句話：「這件事什麼時候是好的？那時到現在改了什麼？」
2
蒐集資訊（Gather）看拓撲圖、看設定、看日誌、看介面計數器。不要憑印象——實際的設定跟你記得的常常不一樣。
3
分析並縮小範圍（Analyze）用對分法：從中間切一刀，判斷問題在左邊還是右邊。八個節點的路徑，三次就能定位。
4
提出假設（Hypothesize）「我認為是 X 造成的，因為 Y」。一次只提一個假設。
5
驗證（Test）一次只改一件事，改完就測。同時改三個地方然後通了，你永遠不知道是哪一個有效。
6
記錄與回饋（Document）把根因、解法、預防措施寫下來。沒寫下來的排錯經驗，半年後等於沒發生過。
新手最常犯的三個錯：
① 先動手改再想——改了一堆之後，原本的問題還在，又多了三個新問題。
② 一次改多個地方——通了也不知道原因，下次還是不會處理。
③ 不留退路——改設定前沒有備份。正式環境動手前先 show run 存一份，遠端操作時先設 reload in 10（十分鐘後自動重開），改壞了設備會自己回到原設定救你。
遠端操作的保命符：reload in 10
在改動可能斷線的設定（ACL、路由、介面）之前先下這個指令。如果改完你還連得上，就下 reload cancel 取消；如果改壞了斷線，設備會在十分鐘後自動重開並載入未存檔的原設定。
這一招在遠端管理海外機房時救過無數人，比任何技術都值得先學會。

2. 分層排錯：由下而上的檢查清單

OSI 七層不只是考試用的，它是最有效的排錯順序。由下而上檢查，因為下層壞了上層一定不會好。

層檢查什麼指令
L1 實體線插好了嗎？介面 up 嗎？光衰？介面錯誤計數器有在跳嗎？show interface
show interface status
L2 資料連結VLAN 對嗎？Trunk 通嗎？STP 有沒有把埠擋掉？MAC 學到了嗎？show vlan brief
show interface trunk
show spanning-tree
show mac address-table
L3 網路IP 設對嗎？路由表有嗎？ARP 學到了嗎？ACL 擋掉了嗎？show ip interface brief
show ip route
show ip arp
show access-lists
L4 傳輸埠號通嗎？NAT 轉對嗎？防火牆放行嗎？show ip nat translations
telnet x.x.x.x 443
L7 應用DNS 解得出來嗎？服務起來了嗎？憑證過期了嗎？nslookup
curl -v
介面計數器怎麼看（這張表能解決一半的實體層問題） CRC errors 線材品質差、接頭鬆、電磁干擾、光衰 Input errors 泛指所有輸入錯誤,先看細項 Collisions 全雙工不該有碰撞 → 雙工不匹配 Late collisions 線太長,或雙工不匹配（經典症狀） Runts / Giants 封包太小 / 太大,常見於 MTU 或 VLAN 標籤問題 Output drops 介面壅塞,佇列滿了 → 頻寬不足或需要 QoS Input queue drops CPU 處理不過來 排錯口訣：先 clear counters,等幾分鐘再看,才知道是「現在還在發生」 還是「一年前留下的舊帳」。
雙工不匹配是最經典的「時好時壞」故障。
一端固定 full duplex、另一端 auto 協商成 half duplex，結果是：ping 通、小流量正常，但只要流量一大就掉封包、速度慢得離譜。
判斷方式：全雙工的介面上出現 collisions 或 late collisions 就一定是雙工不匹配（全雙工在物理上不可能有碰撞）。
解法：兩端都設 auto，或兩端都手動固定成一樣的設定。最忌諱一端 auto、一端手動。

3. 最常用的十個排錯指令

! ── 1. 一眼看完所有介面狀態（最常用）──
show ip interface brief
show interface status              ! 交換器上更好用,有 VLAN 與速度雙工

! ── 2. 看單一介面的完整健康狀況 ──
show interface gigabitEthernet 0/1
      ! 重點看：line protocol、duplex/speed、input/output errors、drops

! ── 3. 路由查得到嗎（用最長匹配的方式問）──
show ip route 10.2.2.10            ! 直接問「去這個 IP 會走哪」,比看整張表快

! ── 4. 二層通不通 ──
show mac address-table | include 001a
show interface trunk                ! 確認 allowed vlan 與 native vlan

! ── 5. 鄰居是誰（沒有拓撲圖時的救星）──
show cdp neighbors detail
show lldp neighbors detail          ! 非 Cisco 設備用這個

! ── 6. 路由協定鄰居 ──
show ip ospf neighbor
show ip eigrp neighbors
show ip bgp summary

! ── 7. ACL 有沒有在擋（看命中次數）──
show access-lists                   ! 每條規則後面的 (N matches) 是關鍵

! ── 8. 日誌（八成的線索都在這）──
show logging | include %LINK|%LINEPROTO
show logging | last 50

! ── 9. 誰在吃 CPU / 記憶體 ──
show processes cpu sorted | exclude 0.00
show processes memory sorted

! ── 10. 設定到底是什麼（不要憑印象）──
show running-config interface gigabitEthernet 0/1
show archive config differences     ! 比對改了什麼（要先設定 archive）
兩個省時間的小技巧：
① 管線過濾：| include（包含）、| exclude（排除）、| begin（從這裡開始顯示）、| section（顯示整個區段）。
show run | section router ospf 只印 OSPF 那一段，比翻兩百行設定快得多。
② clear counters 再觀察：介面計數器是累積值，可能是三年前留下的。清掉之後等五分鐘再看，跳的才是現在的問題。
debug 在正式環境是危險指令。
debug 是程序層級處理，流量大時可能把 CPU 吃到 100% 而讓設備失去回應。
安全用法：① 先 show processes cpu 確認 CPU 有餘裕；② 用 ACL 限制範圍（debug ip packet 101）；③ 設好 terminal monitor 才看得到輸出；④ 看完立刻 undebug all。
能用 show 解決就不要用 debug。

4. NetFlow：誰在用頻寬

介面計數器告訴你「這條線有多滿」，NetFlow 告訴你「是誰把它塞滿的」。

一個 Flow 的定義（傳統五元組） 來源 IP + 目的 IP + 來源埠 + 目的埠 + 協定 （新版的 Flexible NetFlow 可以自訂,還能加入 TOS、介面等） 路由器記錄每個 Flow 的： • 封包數、位元組數 • 開始與結束時間 • 進出介面 • TCP 旗標 然後把這些紀錄「匯出」給收集器（Collector）分析 路由器 ──UDP 匯出──▶ Collector ──▶ 報表：Top Talkers、應用分布
! ── Flexible NetFlow 三步驟設定 ──

! 1. 定義要記錄什麼（Flow Record）
R1(config)# flow record RECORD-1
R1(config-flow-record)# match ipv4 source address
R1(config-flow-record)# match ipv4 destination address
R1(config-flow-record)# match transport source-port
R1(config-flow-record)# match transport destination-port
R1(config-flow-record)# match ipv4 protocol
R1(config-flow-record)# collect counter bytes
R1(config-flow-record)# collect counter packets

! 2. 定義送去哪（Exporter）
R1(config)# flow exporter EXPORTER-1
R1(config-flow-exporter)# destination 10.1.1.100
R1(config-flow-exporter)# transport udp 2055

! 3. 綁在一起並套到介面
R1(config)# flow monitor MONITOR-1
R1(config-flow-monitor)# record RECORD-1
R1(config-flow-monitor)# exporter EXPORTER-1

R1(config)# interface gigabitEthernet 0/0
R1(config-if)# ip flow monitor MONITOR-1 input

! ── 直接在設備上看（沒有 Collector 也能用）──
R1# show flow monitor MONITOR-1 cache
R1# show flow monitor MONITOR-1 cache sort counter bytes top 10
                                        ! ← 這行就是「誰在吃頻寬」的答案
NetFlow vs SNMP vs SPAN，三個常被混淆：
SNMP＝統計數字（這條線用了多少頻寬、CPU 多少）。輪詢式、資料量小、看趨勢。
NetFlow＝誰跟誰在通訊（流量的組成）。不含封包內容，資料量中等。
SPAN＝完整封包複本（每一個位元組）。資料量最大，用於深入分析。
對應到問題：「線滿了嗎」→ SNMP；「誰把線塞滿的」→ NetFlow；「這個封包裡面是什麼」→ SPAN。
企業實例｜某企業的頻寬失竊案
對外 200M 線路每天下午三點準時滿載，客訴不斷。SNMP 只能看到「滿了」，看不出原因。IT 一度以為是有人在看影音，準備買頻寬。
開了 NetFlow 之後，Top Talkers 第一名是一台沒人認得的伺服器 IP，持續往境外某個位址上傳，每天下午固定啟動。
追查後發現是一台被遺忘的測試主機，三年前架設後沒人管，已經被入侵當成跳板。
結果：不用買頻寬，關掉那台機器就解決了，同時揭露一個潛伏三年的資安事件。
這個案例的意義：沒有 NetFlow 之前，這個問題的「解法」會是花錢升級頻寬——而且升級完問題還在。

5. SPAN / RSPAN：把封包複製一份出來

要用 Wireshark 分析封包，前提是封包要送得到你的電腦。但交換器只會把封包送給目的地，不會送給旁邊的你——SPAN 就是解決這件事的。

類型來源與目的用途
SPAN
（本地）		來源與目的在同一台交換器最常見。分析主機接在同一台交換器上時
RSPAN
（遠端）		來源與目的在不同交換器，中間用一個專用 VLAN 承載分析主機在機房、來源埠在辦公室
ERSPAN
（封裝遠端）		用 GRE 封裝跨三層網路傳送跨機房、跨網段的抓包
 
! ── 本地 SPAN：把 g0/1 的雙向流量複製到 g0/24 ──
SW1(config)# monitor session 1 source interface gigabitEthernet 0/1 both
SW1(config)# monitor session 1 destination interface gigabitEthernet 0/24

! ── 也可以監控整個 VLAN ──
SW1(config)# monitor session 2 source vlan 10 rx
SW1(config)# monitor session 2 destination interface gigabitEthernet 0/23

! ── 驗證 ──
SW1# show monitor session 1
SW1# show monitor
SPAN 的四個必知限制：
① 目的埠會失去正常功能——它變成純輸出，接在上面的電腦無法用那個埠上網（要另外接一張網卡）。
② 會話數量有限——多數交換器只支援 2 個 SPAN 會話，用完就要先關掉舊的。
③ 超訂會丟封包——把兩個滿載的 1G 埠複製到一個 1G 目的埠，一定會丟。抓包時看到「怪怪的遺漏」要先想到這點。
④ 會增加交換器負擔——正式環境長期開著不是好主意，用完就關。
什麼時候真的需要 SPAN？當你需要看到封包內容而不只是統計時：
• 應用程式說「網路把我的連線切斷了」，你要證明是誰送的 RST
• TLS 交握失敗，要看是哪一步
• 判斷延遲是網路造成還是伺服器回應慢（看 TCP 的時間戳）
• 抓廣播風暴的來源
反過來說，如果問題用 show 指令與 NetFlow 就能定位，就不要動用 SPAN。

6. IP SLA 與 EEM：讓設備自己反應

IP SLA：主動探測

不要等使用者抱怨才知道線路壞了。IP SLA 讓路由器自己定期去 ping 或測延遲，並把結果交給其他機制使用。

! ── 定義一個每 5 秒 ping 一次的探測 ──
R1(config)# ip sla 1
R1(config-ip-sla)# icmp-echo 8.8.8.8 source-interface gigabitEthernet 0/0
R1(config-ip-sla-echo)# frequency 5
R1(config-ip-sla-echo)# threshold 200            ! 延遲門檻(ms)
R1(config)# ip sla schedule 1 life forever start-time now

! ── 用 track 物件把探測結果變成「可以被引用的狀態」──
R1(config)# track 1 ip sla 1 reachability

! ── 應用一：浮動靜態路由自動切換 ──
R1(config)# ip route 0.0.0.0 0.0.0.0 203.0.113.1 track 1   ! 主線,探測失敗就撤掉
R1(config)# ip route 0.0.0.0 0.0.0.0 198.51.100.1 200       ! 備線,AD 較差

! ── 應用二：HSRP 介面追蹤 ──
R1(config-if)# standby 1 track 1 decrement 30

! ── 驗證 ──
R1# show ip sla statistics
R1# show track
沒有 track 的浮動靜態路由是假備援。
只寫 ip route 0.0.0.0 0.0.0.0 203.0.113.1（不加 track）時，只有介面斷掉才會撤掉這條路由。
但真實世界最常見的故障是「介面還亮著，但對面的網路壞了」——中華電信的機房出問題、上游路由器掛掉、光纖在某處斷掉但你這端的光還在。這時介面 up、路由還在、封包全部進黑洞。
加上 IP SLA + track，探測失敗就撤路由，備線才會真的接手。

EEM：設備的自動化腳本

Embedded Event Manager 讓設備在特定事件發生時自動執行動作。
典型用途：介面 down 時自動收集診斷資訊並寄信、CPU 超過 90% 時自動記錄 show processes cpu、有人下 write erase 時發出警告。
! ── 介面 down 時自動記錄現場並發 syslog ──
R1(config)# event manager applet IF-DOWN-CAPTURE
R1(config-applet)# event syslog pattern "Interface GigabitEthernet0/1, changed state to down"
R1(config-applet)# action 1.0 cli command "enable"
R1(config-applet)# action 2.0 cli command "show interface gigabitEthernet 0/1"
R1(config-applet)# action 3.0 cli command "show logging | last 20"
R1(config-applet)# action 4.0 syslog msg "EEM: g0/1 掉線,已擷取診斷資訊"
EEM 解決的是「間歇性故障」這個排錯惡夢。
某條線每週斷一次、每次三十秒，等你收到通知登入設備時現場已經恢復了，什麼都查不到。
EEM 讓設備在事發當下自動拍照存證，你隔天上班就有完整的現場資料。這是抓間歇性問題最有效的手段。

7. 基準線：沒有基準就沒有異常

「這台設備 CPU 60%，正不正常？」——沒有基準線就無法回答。
如果它平常就是 55–65%，那 60% 完全正常；如果它平常是 10%，那 60% 就是重大異常。
沒有基準線，所有監控數字都只是數字。

該建立基準的五項

介面使用率各時段的頻寬曲線。知道正常尖峰在哪，才知道什麼叫異常。
CPU / 記憶體設備的正常負載範圍。
延遲與丟包關鍵路徑的基準 RTT。用 IP SLA 長期記錄。
錯誤計數器正常情況下應該接近零且不增長。
設定基準標準設定樣板。用 archive 或 Git 保存，改了什麼一目了然。
! ── 設定變更歸檔（強烈建議每台都開）──
R1(config)# archive
R1(config-archive)# path flash:/config-backup
R1(config-archive)# maximum 10
R1(config-archive)# write-memory              ! 每次存檔就自動備份一份
R1(config-archive)# log config
R1(config-archive-log-cfg)# logging enable
R1(config-archive-log-cfg)# logging size 200
R1(config-archive-log-cfg)# notify syslog       ! 誰改了什麼指令都送 syslog

! ── 排錯神器：比對現在跟上次的差異 ──
R1# show archive config differences
R1# show archive log config all          ! 誰、什麼時候、下了什麼指令
show archive log config all 可以直接回答排錯的第一個問題：「最近改了什麼？」
在多人管理的環境中，這個指令解決過無數「不是我改的」爭議——它會列出誰、在什麼時間、從哪個 IP 登入、下了哪一行指令。
這是新設備上線時就該設好的東西，不是出事後才想到。

8. 八個真實故障案例

每個案例先看症狀，自己判斷可能原因，再看解析。這些都是實務上高頻出現的樣態。

案例 1｜新裝的無線 AP 拿不到 IP

症狀：接上新 AP，指示燈正常，但 AP 一直拿不到 IP。同一台交換器上其他埠都正常。

檢查：show interface status 顯示該埠 err-disabled。

根因：Port Security。該埠原本接的是一台 PC（maximum 1），換成 AP 之後，AP 會轉送多個無線用戶端的 MAC，超過上限就被 shutdown。

解法：調整 switchport port-security maximum 或改用 sticky 並放寬數量。同類問題：虛擬化主機、IP 電話後面接 PC、小型交換器接在辦公室——都會超過 maximum 1。

案例 2｜跨網段 ping 通但網頁開不了

症狀：從分公司 ping 總部伺服器完全正常，SSH 也能連，但網頁只載入一半就停住，大檔案下載會斷。

檢查：用 ping 10.2.2.10 size 1500 df-bit 測試，失敗。

根因：MTU。這條路徑上有 GRE over IPsec 隧道，封包加上封裝後超過鏈路 MTU，而設了 DF 位元的大封包被直接丟棄。

解法：隧道介面設 ip mtu 1400 與 ip tcp adjust-mss 1360。記住這個判斷法：小封包通、大封包不通 = MTU。

案例 3｜整個網段每天固定時間變慢

症狀：某個 VLAN 每天上午九點到九點半特別慢，其他時間正常。

檢查：show interface 看到上行埠的 output drops 在那個時段暴增；NetFlow 顯示大量流量來自同一批主機到同一個目的地。

根因：防毒軟體的集中更新排在九點，整個網段同時下載更新檔，把上行頻寬打滿。

解法：把更新時間錯開（分批），或在防毒伺服器端限速，或對更新流量套 QoS 降低優先級。這類「每天固定時間」的問題，答案幾乎都是排程任務。

案例 4｜換了一台交換器之後全網不通

症狀：把一台舊交換器換成新的（設定已經複製過去），插上線之後整個機房的網路都斷了。

檢查：show spanning-tree 顯示 Root Bridge 換成了新交換器。

根因：新交換器的 Bridge Priority 是預設值 32768，但 MAC 位址比原本的 Root 小，於是搶走了 Root 角色，整棵生成樹重新計算，流量路徑全部改變（可能走到低速線路上）。

解法：上線前先設定好 Bridge Priority，並在核心交換器上設 spanning-tree guard root（Root Guard）防止接入層搶 Root。這是「新設備上線前必做的檢查」第一名。

案例 5｜備援線路沒有接手

症狀：主線的 ISP 出問題，但公司完全連不上外網——備援線路沒有自動接手。

檢查：主線的實體介面仍然是 up，浮動靜態路由因此沒有被撤掉。

根因：ISP 的上游壞了，但「路由器到 ISP 的第一跳」還通，所以介面不會 down。沒有 IP SLA 探測，路由器不知道再往上走不通。

解法：加上 ip sla 探測一個遠端目標（例如 8.8.8.8，不要只探 ISP 的閘道），並用 track 綁定主線路由。「介面 up 但路不通」是雙線架構最常見的失敗模式。

案例 6｜某台伺服器間歇性斷線

症狀：一台伺服器每隔幾天就短暫失聯幾十秒，然後自己恢復。查的時候永遠是正常的。

檢查：設定 EEM 在介面 down 時自動擷取資訊。三天後抓到現場：show logging 有 MAC flapping 訊息，同一個 MAC 在兩個埠之間跳動。

根因：伺服器做了網卡 teaming，但交換器端沒有設成對應的 EtherChannel 模式，導致 MAC 在兩個埠之間漂移。

解法：依伺服器的 teaming 模式，在交換器上設定對應的 EtherChannel（LACP 或 static）。間歇性故障一定要用 EEM 或持續記錄，靠「等它發生時剛好在線上」是不可能的。

案例 7｜新增網段之後部分主機不通

症狀：新增了 10.1.50.0/24 網段，同網段內互通正常，但去總部只有部分伺服器通得到。

檢查：總部路由器 show ip route 10.1.50.0 查不到；但 10.1.0.0/16 這條在。

根因：路由是靠重分配從 EIGRP 進 OSPF 的，而重分配時套用的 prefix-list 只允許到 10.1.49.x，新網段不在允許範圍。

解法：更新 prefix-list。這正是「用過濾清單防迴圈」的副作用——每次新增網段都要記得改。所以第 19 章建議優先用 tag 防迴圈，因為 tag 不需要隨網段變動而修改。

案例 8｜VoIP 通話單向有聲音

症狀：內線互打，A 聽得到 B，但 B 聽不到 A。

檢查：單向語音幾乎必定是單向的封包路徑問題。檢查 ACL、NAT 與路由的回程。

根因：某段路徑上的 ACL 只放行了單一方向的 RTP 埠範圍；另一種常見原因是 NAT 只轉換了一個方向，或防火牆對 UDP 的 session 判定過期太快。

解法：檢查雙向路徑。排錯通則：任何「單向通」的問題，都要把去程與回程分開檢查——ping 通不代表回程正常，因為 ICMP 與實際應用走的埠不同，ACL 可能只擋了其中一種。

八個案例的共同心法
① 「什麼時候是好的？那時到現在改了什麼？」——案例 4、7 靠這句話就能定位。
② 症狀的形狀就是線索——小封包通大封包不通是 MTU（案例 2）；每天固定時間是排程（案例 3）；單向通是回程問題（案例 8）。
③ 間歇性故障必須自動存證——案例 6 沒有 EEM 就永遠查不到。
④ 「介面 up」不等於「路通」——案例 5 是雙線架構最常見的失敗。
⑤ 新設備上線前先想它會不會搶角色——案例 4 的 STP Root 是經典。
⑥ 安全機制也會造成故障——案例 1 的 Port Security、案例 7 的過濾清單，都是「做對了資安卻擋到自己」。

實作 Lab：建立一套排錯工具鏈

約 50 分鐘。這個 Lab 不練「怎麼設定」，練的是「出事時你手上有什麼」。

階段一：把地基打好（每台設備都該有）

  1. 設定 NTP——沒有正確時間，多台設備的日誌無法對照，排錯等於瞎子摸象
  2. 設定 Syslog 送到集中伺服器，等級設 informational（6）
  3. 開啟 archive + log config，讓每次設定變更都被記錄
  4. 設定 CDP/LLDP，確保拓撲可以自動探索
  5. 驗證：show clock、show logging、show archive log config all
NTP 是所有排錯的前提。當你要比對「交換器說 10:23:15 埠斷了」與「伺服器說 10:19:02 連線失敗」時，如果兩邊時間差了四分鐘，你會得出完全錯誤的因果關係。新設備上線的第一件事就是對時。

階段二：主動探測

  1. 設定 IP SLA 探測一個遠端目標，頻率 5 秒
  2. 建立 track 物件
  3. 設定主備兩條靜態路由，主線綁 track
  4. 把主線的下一跳「弄壞」（在中間設備上擋掉探測目標），觀察路由自動切換
  5. 用 show track 與 show ip route 驗證

階段三：看得見流量

  1. 設定 NetFlow（Flexible NetFlow 三步驟）
  2. 產生一些流量（大檔傳輸、多台主機同時上網）
  3. 用 show flow monitor X cache sort counter bytes top 10 找出 Top Talkers
  4. 設定一個 SPAN 會話，用 Wireshark 抓包驗證
  5. 觀察 SPAN 目的埠無法正常上網這件事

階段四：自動存證

  1. 設定一個 EEM applet：偵測到介面 down 時自動執行 show interface 與 show logging
  2. 手動 shutdown 該介面觸發它
  3. 確認 syslog 中有 EEM 產生的訊息與擷取的資訊

階段五：模擬故障（找同學互相出題）

  1. 請對方在你不知情的情況下製造一個故障（改 VLAN、加 ACL、改 native VLAN、關掉某個 OSPF network 語句）
  2. 你用分層排錯的順序找出來，全程只用 show 指令
  3. 找到後寫下：症狀、檢查步驟、根因、解法
  4. 交換角色再做一次
階段五是整個 Lab 最有價值的部分。設定會了不代表排錯會了——排錯是逆向工程，要從症狀推回原因。這個能力只能靠反覆練習養成，而且是面試時最能拉開差距的一項。

10. 考試陷阱整理

陷阱 1：全雙工介面出現 collisions
全雙工在物理上不可能有碰撞。看到 collisions 或 late collisions 就是雙工不匹配。
陷阱 2：介面計數器沒 clear 就下判斷
計數器是累積值，可能是三年前的舊帳。clear counters 後再觀察才有意義。
陷阱 3：以為介面 up 就代表路通
上游故障時介面仍是 up，浮動靜態路由不會撤。必須配 IP SLA + track。
陷阱 4：NetFlow 與 SPAN 搞混
NetFlow = 誰跟誰在通訊（不含封包內容）；SPAN = 完整封包複本；SNMP = 統計數字。
陷阱 5：SPAN 目的埠還想拿來上網
目的埠變成純輸出，接在上面的電腦無法正常通訊。而且 SPAN 會話數量有限、超訂會丟封包。
陷阱 6：在正式環境隨便下 debug
debug 是程序層級處理，可能把 CPU 吃滿導致設備失去回應。能用 show 就不要用 debug，用了要立刻 undebug all。
陷阱 7：忘記設 NTP
多台設備的日誌無法對照，排錯時會推出錯誤的因果關係。NTP 是排錯的前提，不是可有可無的功能。
陷阱 8：新交換器上線搶走 STP Root
預設 priority 相同時比 MAC，新設備 MAC 較小就會搶 Root。上線前先設 priority，核心開 Root Guard。
陷阱 9：遠端改設定不設 reload in
改壞了就斷線，只能請人到現場。遠端動高風險設定前一定要先設自動重開。
💡一句話記憶：
排錯先問「什麼時候是好的、改了什麼」，然後由下而上分層查；
小封包通大封包不通是 MTU、全雙工有碰撞是雙工不匹配、每天固定時間是排程；
看趨勢用 SNMP、看是誰用 NetFlow、看內容用 SPAN；
介面 up 不等於路通，備援一定要配 IP SLA。
