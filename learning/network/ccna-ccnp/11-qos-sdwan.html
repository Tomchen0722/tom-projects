QoS 與 SD-WAN

頻寬永遠會有不夠用的時候，QoS 決定「不夠用時誰先走」。SD-WAN 則是用軟體重新定義企業廣域網路的建置與管理方式。這章講原理，也講怎麼實際設定。

1. 為什麼需要 QoS

先講清楚一件事：QoS 不會增加頻寬。它做的是「決定在壅塞時誰被優先處理、誰被丟棄」。如果你的線路長期 100% 滿載，QoS 只能讓重要的服務活下來，正確的解法還是加頻寬。
比喻：QoS 像醫院急診室的檢傷分類。病人多的時候，不是先到先看，而是心肌梗塞優先於扭傷。急診室不會因為分類而變大，但至少不會有人在等待中死掉。

沒有 QoS 的網路就是「先到先看」——結果一個人下載大檔案，就把整間急診室塞住，心肌梗塞的病人（VoIP 通話）只能排隊。

沒有 QoS 會發生什麼

症狀使用者的說法技術原因
語音斷續、機器人聲「電話一直斷」抖動（jitter）過大，緩衝區來不及補償
視訊會議畫面馬賽克「畫面糊掉」封包遺失，畫格無法還原
ERP 系統很慢「系統當掉」TCP 重傳，延遲累積
只有某些時段會這樣「下午特別慢」備份或大量下載佔滿線路
企業導入 QoS 的三個典型觸發點：導入 VoIP 電話系統、開始大量使用視訊會議、WAN 頻寬有限但要跑關鍵業務系統。三個都沒有的話，其實可以先不做 QoS。

2. 四個品質指標與應用需求

指標意義成因
頻寬（Bandwidth）每秒能傳多少資料實體線路能力
延遲（Delay / Latency）封包從 A 到 B 花多久傳播 + 序列化 + 佇列 + 處理
抖動（Jitter）延遲的變化量佇列深度不斷變化
遺失（Loss）封包被丟掉的比例佇列滿了、線路錯誤
對即時應用來說，抖動比延遲更致命。穩定的 150 ms 延遲，VoIP 完全沒問題（緩衝區能補償）。但延遲在 20 ms 和 200 ms 之間跳來跳去，通話就會斷斷續續——因為緩衝區不知道該等多久。

應用單向延遲抖動封包遺失頻寬需求
語音 VoIP< 150 ms< 30 ms< 1%21–320 kbps／通
視訊會議< 200 ms< 30 ms< 1%384 kbps – 20 Mbps
串流影片（單向）< 4–5 秒不敏感< 2%視解析度
交易型應用< 400 ms不敏感0%（TCP 重傳）低
檔案傳輸 / 備份不敏感不敏感0%愈多愈好

延遲的四個組成

類型成因能不能靠 QoS 改善
傳播延遲光在纖維裡跑的物理時間（約 5 μs/km）不能（物理限制）
序列化延遲把封包一個位元一個位元推上線路的時間部分（加大頻寬、封包分片）
佇列延遲在路由器緩衝區排隊等待可以，這是 QoS 的主戰場
處理延遲路由器查表、封裝的時間部分（硬體轉發／CEF）
序列化延遲 = 封包大小(bits) ÷ 線路速率(bps)

1500 bytes 在 64 kbps 線路上 = 12000 ÷ 64000 = 187 ms（災難）
1500 bytes 在 1 Gbps 線路上 = 12000 ÷ 10⁹ = 0.012 ms（可忽略）
這解釋了為什麼慢速 WAN 線路需要 LFI（Link Fragmentation and Interleaving）——把大封包切小，讓語音封包能插隊。現代線路速度夠快，這個技術已經很少用了。

3. 三種 QoS 模型

模型做法擴展性實務地位
Best Effort什麼都不做，先到先服務無限預設值
IntServ
（整合服務）		用 RSVP 事先為每個流量預約頻寬差（每條流都要記狀態）幾乎沒人用
DiffServ
（差異化服務）		標記封包分類，每台路由器依標記自行處理好業界標準
DiffServ 的核心思想：不記狀態。路由器不需要知道「這是誰的第幾條連線」，只要看封包上的標記就決定怎麼處理。這就是它能擴展到全球網路的原因。本章後面講的所有技術都屬於 DiffServ。

4. 標記：CoS、DSCP、PHB

兩個層級的標記欄位

CoS（Class of Service）DSCP
在哪一層第二層（802.1Q 標籤裡的 PCP）第三層（IP 表頭的 ToS 位元組）
幾個位元3 bits → 0–76 bits → 0–63
限制只在 Trunk 上存在，Access 埠或跨路由器就消失端到端保留
用途交換器內部、接入層企業標準

IP 表頭的 ToS 位元組

DSCP6 bits · 0–63
ECN2 bits

舊的定義叫 IP Precedence，只用前 3 個位元（0–7）。DSCP 向下相容——DSCP 的前 3 位元就是 IP Precedence，所以 DSCP 的 CS 類別（Class Selector）剛好對應舊的 0–7。

PHB：每一跳的處理行為

PHB（Per-Hop Behavior）定義「看到這個標記時該怎麼處理」。四種標準 PHB：

EF · 46Expedited Forwarding
最低延遲，給語音
AF41 · 34互動視訊
AF31 · 26訊令 / 關鍵應用
AF21 · 18交易型資料
AF11 · 10大量資料傳輸
CS1 · 8Scavenger（次要）
BE · 0Best Effort（預設）

AF31 → 8×3 + 2×1 = 26　　AF43 → 8×4 + 2×3 = 38

不要忘記 CS6（網路控制）。OSPF、BGP、STP 的封包如果在壅塞時被丟掉，整個網路會開始震盪——比使用者的影片卡頓嚴重一百倍。任何 QoS 政策都必須為路由協定保留頻寬。

5. 信任邊界（Trust Boundary）

核心問題：使用者的電腦可以自己在封包上標 EF（最高優先權）。只要裝個工具，任何人都能把自己的 BT 下載標成語音等級，優先於所有人。所以不能信任端點的標記。
信任邊界的原則：在愈靠近使用者的地方決定要不要信任。
  • IP 電話 → 可以信任（它是公司的設備，且會標 EF）
  • 電腦 → 不信任，一律重新標記成 BE 或依 ACL 分類
  • 接電話再接電腦的埠 → 信任電話的標記，但把電腦那條的標記清掉
! ═══ 情境 1：埠上只接電腦 → 完全不信任 ═══
SW1(config)# interface fastEthernet 0/1
SW1(config-if)# mls qos trust none          ← 所有進來的標記都清成 0

! ═══ 情境 2：接 IP 電話 → 信任電話，但要求它重寫電腦的標記 ═══
SW1(config)# interface fastEthernet 0/5
SW1(config-if)# switchport access vlan 10
SW1(config-if)# switchport voice vlan 50
SW1(config-if)# mls qos trust device cisco-phone   ← 用 CDP 確認真的是電話
SW1(config-if)# mls qos trust cos
SW1(config-if)# switchport priority extend cos 0    ← 電話把 PC 的標記改成 0

! ═══ 情境 3：接另一台交換器（Trunk）→ 信任 DSCP ═══
SW1(config)# interface gigabitEthernet 0/1
SW1(config-if)# mls qos trust dscp

! ═══ 全域啟用 QoS（很多人忘記這行，不下的話上面全部無效）═══
SW1(config)# mls qos
mls qos 沒開，所有 QoS 設定都不生效。而且開啟之後，預設所有埠變成不信任（DSCP 全部重寫成 0）——如果你先開了全域 QoS 卻還沒設好各埠的信任，語音品質會立刻變差。先設好埠，再開全域。用 show mls qos 確認狀態。
新款 IOS-XE 交換器的指令不同：不再需要 mls qos 全域開關，改用 qos trust dscp 之類的介面指令，並全面改用 MQC（第 9 節）。設定前先 show version 確認平台。

6. 佇列機制：FIFO 到 LLQ

機制做法缺點用在
FIFO先進先出，一條佇列大流量會餓死小流量高速介面預設
WFQ依「流」自動分類，小流量優先不能手動指定政策低速介面預設
CBWFQ自訂類別，各保證最低頻寬沒有嚴格優先權，延遲不保證資料類流量
LLQCBWFQ + 嚴格優先佇列優先佇列會被限速（policed）企業標準
LLQ = Low Latency Queuing = CBWFQ 加上一個「插隊佇列」。放進優先佇列的流量（通常是語音）永遠先被送出，其他佇列只能等它清空。這保證了語音的延遲和抖動。
優先佇列有防餓死機制：它會被限速。你設 priority 1000（1 Mbps），語音超過 1 Mbps 的部分會被直接丟棄，而不是佔用其他人的頻寬。

這是刻意的設計——否則一個失控的語音流量會把整條線路吃光，連路由協定都送不出去。

所以優先佇列的頻寬要算準：
G.711 每通約 80 kbps（含表頭）
G.729 每通約 26 kbps（含表頭）

50 人同時通話（G.711）= 50 × 80k = 4 Mbps
優先佇列總量不要超過線路的 33%。這是 Cisco 的建議值。超過的話，其他類別（包含路由協定）會嚴重挨餓，網路穩定性下降。如果算出來需要超過 33%，代表你該加頻寬了。

7. 整形 vs 監管

Shaping（整形）Policing（監管）
超過速率時緩衝起來，慢慢送直接丟棄或重新標記
需要緩衝區要不要
會增加延遲會不會
會造成 TCP 重傳不會會
方向只能 outbound兩個方向都可以
流量曲線平滑鋸齒狀
典型用途配合 ISP 的頻寬合約、避免下游被淹沒限制某類流量的上限（例如訪客 Wi-Fi）
比喻：Shaping 像高速公路的匝道儀控——車太多時讓你在匝道等一下再放行，總量控制住，但你會多花時間。Policing 像超速照相——超過就開罰單（丟棄），不會讓你等。
經典情境：ISP 給你 100 Mbps 的實體介面，但合約只有 20 Mbps

問題：你的路由器以 100 Mbps 全速送出去，ISP 那端會把超過 20 Mbps 的部分直接丟棄（他們用 policing）。TCP 偵測到遺失就重傳，然後又被丟，形成惡性循環，實際吞吐量可能只剩 12 Mbps。

解法：在自己這端做 shaping 到 20 Mbps。主動控制輸出速率，讓 ISP 那端不需要丟包。而且緩衝在自己這裡，可以配合 QoS 決定「緩衝時誰先出去」。

! ── Shaping：整形到 20 Mbps ──
R1(config)# policy-map WAN-SHAPE
R1(config-pmap)# class class-default
R1(config-pmap-c)# shape average 20000000          ← 20 Mbps
R1(config-pmap-c)# service-policy WAN-QOS            ← 巢狀：在整形後的頻寬裡再分配

! ── Policing：訪客 Wi-Fi 限速 5 Mbps ──
R1(config)# policy-map GUEST-LIMIT
R1(config-pmap)# class GUEST-TRAFFIC
R1(config-pmap-c)# police 5000000 conform-action transmit exceed-action drop
「巢狀 policy-map」是 WAN 的標準寫法。外層 shape 到合約速率，內層再做 LLQ／CBWFQ 分配。因為 QoS 的佇列只有在「介面覺得壅塞」時才會啟動——實體介面是 100 Mbps，永遠不覺得壅塞，內層政策就永遠不會生效。先 shape 製造出人為的壅塞點，佇列才有意義。

8. 壅塞避免：WRED 與 TCP 全域同步

Tail Drop 的問題：TCP 全域同步。
  1. 佇列滿了 → 所有新來的封包一起被丟
  2. 所有 TCP 連線同時偵測到遺失 → 同時把傳送速率砍半
  3. 線路瞬間變得很空 → 所有連線又同時加速
  4. 再度塞爆 → 回到第 1 步
結果：頻寬使用率呈現鋸齒狀，平均利用率可能只有 50%，而且延遲不斷震盪。
WRED（Weighted Random Early Detection）的做法：在佇列滿之前就開始隨機丟。
  • 佇列深度低於最小門檻 → 完全不丟
  • 在最小和最大門檻之間 → 隨機丟少量封包，機率隨深度上升
  • 超過最大門檻 → 全部丟（退化成 tail drop）
隨機丟的效果是：只有少數幾條 TCP 連線降速，其他繼續全速，避免了同步震盪。

Weighted 的意思是可以依 DSCP 給不同門檻——AF13 比 AF11 更早開始被丟。 
R1(config)# policy-map WAN-QOS
R1(config-pmap)# class BULK-DATA
R1(config-pmap-c)# bandwidth percent 20
R1(config-pmap-c)# random-detect dscp-based
R1(config-pmap-c)# random-detect dscp af11 32 40 10
R1(config-pmap-c)# random-detect dscp af12 28 40 10
R1(config-pmap-c)# random-detect dscp af13 24 40 10
!                                    ↑最小 ↑最大 ↑丟棄分母(1/10)
WRED 只對 TCP 有效，不要用在語音或視訊上。UDP 不會因為丟包而降速——你丟它的封包，它照樣送，只是通話品質變差。語音類別要用 LLQ 保護，不是用 WRED。

9. 實作一：MQC 完整設定

MQC（Modular QoS CLI）是 Cisco 的統一 QoS 設定框架，三個步驟：

1
class-map — 分類「什麼樣的流量算是這一類」
2
policy-map — 定政策「這一類要怎麼處理」
3
service-policy — 套用「這個政策放在哪個介面的哪個方向」

步驟 1：分類

! ── 依 DSCP 分類（信任邊界之後的做法）──
R1(config)# class-map match-all VOICE
R1(config-cmap)# match dscp ef
R1(config-cmap)# exit

R1(config)# class-map match-any VIDEO
R1(config-cmap)# match dscp af41
R1(config-cmap)# match dscp af42
R1(config-cmap)# match dscp cs4
R1(config-cmap)# exit

R1(config)# class-map match-all SIGNALING
R1(config-cmap)# match dscp cs3
R1(config-cmap)# exit

R1(config)# class-map match-all NET-CONTROL
R1(config-cmap)# match dscp cs6
R1(config-cmap)# exit

! ── 依 ACL 分類（信任邊界上的做法）──
R1(config)# ip access-list extended ERP-TRAFFIC
R1(config-ext-nacl)# permit tcp any host 192.168.30.10 eq 1433
R1(config-ext-nacl)# exit

R1(config)# class-map match-all CRITICAL-APP
R1(config-cmap)# match access-group name ERP-TRAFFIC
R1(config-cmap)# exit

! ── 依應用分類（NBAR2，能認出上千種應用）──
R1(config)# class-map match-any SCAVENGER
R1(config-cmap)# match protocol bittorrent
R1(config-cmap)# match protocol netflix
R1(config-cmap)# match protocol youtube
match-all 和 match-any 差很多。match-all = 所有條件都要成立（AND），match-any = 任一條件成立即可（OR）。預設是 match-all。寫了三個 match dscp 又用 match-all，那條規則永遠不會匹配——一個封包不可能同時是 af41 和 af42。

步驟 2：定政策

R1(config)# policy-map WAN-QOS

! ── 語音：嚴格優先，限 10% ──
R1(config-pmap)# class VOICE
R1(config-pmap-c)# priority percent 10
R1(config-pmap-c)# set dscp ef

! ── 視訊：保證頻寬 + WRED ──
R1(config-pmap)# class VIDEO
R1(config-pmap-c)# bandwidth percent 25
R1(config-pmap-c)# random-detect dscp-based

! ── 路由協定：一定要保留 ──
R1(config-pmap)# class NET-CONTROL
R1(config-pmap-c)# bandwidth percent 5

! ── 訊令 ──
R1(config-pmap)# class SIGNALING
R1(config-pmap-c)# bandwidth percent 2

! ── 關鍵應用 ──
R1(config-pmap)# class CRITICAL-APP
R1(config-pmap-c)# bandwidth percent 20
R1(config-pmap-c)# set dscp af21
R1(config-pmap-c)# random-detect dscp-based

! ── 垃圾流量：能用多少算多少，且標記成 CS1 ──
R1(config-pmap)# class SCAVENGER
R1(config-pmap-c)# bandwidth percent 1
R1(config-pmap-c)# set dscp cs1

! ── 其他所有流量 ──
R1(config-pmap)# class class-default
R1(config-pmap-c)# bandwidth percent 25
R1(config-pmap-c)# fair-queue
R1(config-pmap-c)# random-detect

步驟 3：巢狀整形 + 套用

R1(config)# policy-map WAN-PARENT
R1(config-pmap)# class class-default
R1(config-pmap-c)# shape average 20000000
R1(config-pmap-c)# service-policy WAN-QOS
R1(config-pmap-c)# exit

R1(config)# interface gigabitEthernet 0/1
R1(config-if)# service-policy output WAN-PARENT
各類別的 bandwidth percent 總和不能超過 75%（預設）。剩下的 25% 保留給路由協定、二層控制流量等系統開銷。要用更多必須明確調整：max-reserved-bandwidth 90，但不建議。

        Class-map: VOICE (match-all)
          482910 packets, 38632800 bytes
          Match: dscp ef (46)
          Priority: 10% (2000 kbps), burst bytes 50000
          Priority Rate Limited: 0 packets, 0 bytes     ← 不是 0 就代表語音被限速丟了

        Class-map: VIDEO (match-any)
          Queueing
          queue limit 64 packets
          (queue depth/total drops/no-buffer drops) 0/12/0
          bandwidth 25% (5000 kbps)

R1# show policy-map interface gi0/1 output class VOICE
R1# show mls qos interface fa0/5 statistics       ! 交換器端
三個關鍵數字要盯：
  • Priority Rate Limited 不是 0 → 語音超量被丟，要加大 priority 或減少通話數
  • total drops 持續增加 → 那個類別頻寬不夠
  • queue depth 一直很高 → 延遲會很大，考慮調整分配

10. 實作二：AutoQoS 快速上手

手寫完整的 12 類 MQC 政策要好幾百行。AutoQoS 一行指令就自動產生一整套符合 Cisco 最佳實務的設定。

! ── 交換器：接 IP 電話的埠 ──
SW1(config)# mls qos
SW1(config)# interface fastEthernet 0/5
SW1(config-if)# auto qos voip cisco-phone

! ── 交換器：接另一台交換器（信任上游）──
SW1(config)# interface gigabitEthernet 0/1
SW1(config-if)# auto qos voip trust

! ── 路由器 WAN 介面（新版，會自動偵測應用）──
R1(config)# interface gigabitEthernet 0/1
R1(config-if)# auto qos

! ── 看它到底幫你產生了什麼（強烈建議做這一步）──
SW1# show auto qos
SW1# show running-config | begin class-map
AutoQoS 的正確用法：把它當成「範本產生器」。先用它產生一整套設定，再 show running-config 把產生的 class-map／policy-map 讀一遍，看懂之後依自己的需求微調。直接用預設值通常也堪用，但頻寬比例不見得符合你的環境。
AutoQoS 會直接修改 running-config，而且產生的設定量很大。在正式環境套用前：先備份設定（copy running-config flash:backup.cfg），並在維護時段做。移除要用 no auto qos voip，但殘留的 class-map 可能要手動清。

11. SD-WAN 是什麼

傳統 WAN 的四個痛點

痛點具體情況
MPLS 很貴專線月租是同頻寬網際網路的 5–20 倍
開通很慢新分公司拉專線要 4–12 週
備援線路閒置買了第二條線，平常完全不用，等於白花錢
設定要一台台改50 家分公司改一條政策，要 SSH 進 50 台機器
SD-WAN 的核心概念：把控制平面和資料平面分開。
控制平面「決定流量該怎麼走」。集中到控制器，一個地方設定，推送到所有站點。
資料平面「實際轉送封包」。留在各站點的邊緣設備上，就近處理。
管理平面「看狀態、設政策」。統一的圖形介面，不用 CLI。

SD-WAN 帶來什麼

能力實際意義
Transport IndependenceMPLS、光纖、4G/5G 全部可以混用，上面跑加密 overlay 隧道
Application-Aware Routing「語音走延遲最低的線，備份走最便宜的線」——依應用而非目的 IP 決定路徑
即時路徑切換持續量測每條線的延遲／抖動／遺失，品質變差幾百毫秒內自動換線
Zero-Touch Provisioning新設備寄到分公司，插上電和網路線自己從雲端下載設定
集中政策一個地方改，推送到全部站點
Direct Internet Access雲端服務（M365、Salesforce）直接從分公司出去，不用繞回總部
SD-WAN 不是萬靈丹，導入前要評估（涉及合約與費用，先算清楚）：
  • 授權費用通常是按站點按年計費，站點少的話可能比省下的 MPLS 費用還貴
  • 網際網路線路的品質不保證——SD-WAN 能選較好的線，但沒辦法讓爛線變好
  • 控制器是單點（雖然可以做高可用），控制器失聯時既有隧道仍運作，但無法變更政策
  • 團隊需要重新學習，傳統 CLI 技能不完全適用

12. Cisco SD-WAN 四個元件

元件平面職責類比
vManage管理圖形化管理介面、範本、監控、升級公司的總管理處
vSmart控制用 OMP 協定散布路由與政策路由的大腦（類似 BGP RR）
vBond協調新設備的第一個聯絡點，做認證與 NAT 穿透櫃檯接待
vEdge / cEdge資料放在各站點，實際轉送封包、建立隧道各分店員工

新站點上線流程（ZTP）

1
設備開箱插電接上任何一條能上網的線（光纖、4G 都可以）。
2
連上 vBond用出廠內建的憑證做雙向認證，確認彼此身分。
3
vBond 介紹 vManage 和 vSmart並協助處理 NAT 後方的連線建立。
4
從 vManage 下載設定範本整台設備的設定自動套用，不需要人工 CLI。
5
跟 vSmart 建立 OMP 連線取得路由資訊與政策。
6
與其他站點建立 IPsec 資料隧道開始承載業務流量。整個過程不需要工程師到現場。

三種 SD-WAN 政策

政策類型在哪裡執行做什麼
Centralized Control PolicyvSmart控制路由怎麼散布（哪些站點看得到哪些路由）
Centralized Data PolicyEdge（由 vSmart 下發）依應用選路徑、服務串接、QoS
Localized PolicyEdge 本地ACL、QoS 佇列、路由過濾
Application-Aware Routing 的實際設定邏輯
SLA 類別「VOICE-SLA」：
    延遲 < 150 ms
    抖動 < 30 ms
    遺失 < 1%

規則：
    符合「語音」應用的流量
    → 優先使用 MPLS
    → 若 MPLS 不符合 VOICE-SLA，改用 Internet
    → 若兩條都不符合，選相對較好的那條

    符合「備份 / 檔案同步」的流量
    → 只使用 Internet（永遠不佔用昂貴的 MPLS）

Edge 設備每隔數百毫秒用 BFD 量測每條隧道的實際品質，決策是持續即時的，不是設定一次就固定。

CCNA 只要求知道概念（控制平面／資料平面分離、四個元件的名字和角色）。CCNP ENCOR 會考得更細，包含 OMP、TLOC、政策架構。實際操作需要 vManage 環境，Cisco DevNet 有免費的 Always-On Sandbox 可以登入練習。

13. Overlay：VXLAN 與 EVPN

CH 2-2 提過 802.1Q 的 VLAN ID 只有 12 bits，上限 4094 個。雲端資料中心動輒上萬個租戶，完全不夠用。

VLAN (802.1Q)VXLAN
識別碼長度12 bits24 bits（VNI）
數量上限409416,777,216
封裝方式插入 4 bytes 標籤整個 L2 訊框包進 UDP（port 4789）
能跨越單一 L2 網域任何 L3 網路
額外開銷4 bytes50 bytes
原始 L2 訊框 → 外層 MAC + 外層 IP + UDP(4789) + VXLAN(VNI) + 原始訊框

「把二層網路裝進三層封包裡運送」
VXLAN 的 50 bytes 開銷會造成 MTU 問題。底層網路（underlay）的 MTU 必須至少 1550，否則 1500 bytes 的原始封包封裝後就超過了。資料中心通常直接把 underlay 設成 9000（Jumbo Frame）。忘記調的症狀又是那個經典的「小封包通、大封包不通」。

VTEP 與 EVPN

名詞意義
VTEPVXLAN Tunnel Endpoint。做封裝／解封裝的設備（通常是 ToR 交換器）
VNIVXLAN Network Identifier，24 bits 的「虛擬網段編號」
Underlay底層的三層網路，通常跑 OSPF 或 IS-IS，只負責讓 VTEP 之間互通
Overlay建在 underlay 之上的虛擬二層網路
EVPN用 MP-BGP 當 VXLAN 的控制平面，散布 MAC 與 IP 資訊
為什麼需要 EVPN？純 VXLAN 靠「flood and learn」——不知道目的 MAC 在哪就對所有 VTEP 群播氾濫，很浪費。EVPN 用 BGP 主動宣告「我這裡有這些 MAC 和 IP」，其他 VTEP 直接查表，不用氾濫。

這就是為什麼 CH 3-3 的 BGP 知識在資料中心也用得上——EVPN 本質上就是 BGP 的一個新位址族群（AFI/SAFI）。
! NX-OS 上的 VXLAN EVPN 片段（概念示意）
switch(config)# feature nv overlay
switch(config)# feature bgp
switch(config)# nv overlay evpn

switch(config)# interface nve1
switch(config-if)# source-interface loopback0
switch(config-if)# host-reachability protocol bgp
switch(config-if)# member vni 10010
switch(config-if-nve-vni)# suppress-arp

switch(config)# router bgp 65001
switch(config-router)# address-family l2vpn evpn
VXLAN／EVPN 是 CCNP Data Center 和 ENCOR 的內容，CCNA 只要知道「VLAN 不夠用時用 VXLAN，24 bits，1600 萬個」即可。但理解 overlay 的概念對看懂 SD-WAN 很有幫助——SD-WAN 本質上也是一種 overlay。

完整實作 Lab：WAN QoS 政策

Packet Tracer 的 QoS 支援有限，建議用 GNS3 或 Cisco CML。約 70 分鐘。

情境

總部 ── 20 Mbps 專線（實體介面 1 Gbps）── 分公司

需求：
  · 30 通 G.711 語音（每通 80 kbps → 2.4 Mbps）
  · 視訊會議尖峰 5 Mbps
  · ERP 系統（tcp/1433）必須保證
  · 夜間備份不能影響白天業務
  · 路由協定（OSPF）不能被餓死

步驟

  1. 交換器端：mls qos，接電話的埠設 trust device cisco-phone 並 extend cos 0，接 PC 的埠設 trust none
  2. 建立 class-map：VOICE(dscp ef)、VIDEO(af41/cs4)、SIGNALING(cs3)、NET-CONTROL(cs6)、ERP(ACL tcp/1433)、BACKUP(NBAR 或 ACL)
  3. 建立 policy-map WAN-QOS：VOICE 用 priority（自己算需要幾 %）、其他用 bandwidth percent
  4. ERP 和 BACKUP 類別加上 random-detect dscp-based
  5. 建立巢狀 policy-map WAN-PARENT，shape average 20000000 並嵌入 WAN-QOS
  6. 套用到 WAN 介面的 output 方向
  7. 驗證各類別的 bandwidth percent 總和不超過 75%

驗收清單

  • show policy-map interface 每個 class 都有非零的封包計數
  • Priority Rate Limited 是 0（語音沒有超量被丟）
  • Shaping 的 Target Rate 顯示 20000000
  • 用 iperf 或 ping 灌滿線路，同時 ping 語音目標，延遲和抖動仍在門檻內
  • show mls qos interface fa0/5 statistics 看得到 dscp 46 的封包
  • 從 PC 手動標一個 EF 封包，確認交換器把它重寫成 0（信任邊界生效）

加碼挑戰

  1. 把 VOICE 的 priority percent 故意設成 2%，用 iperf 灌 UDP 模擬語音，觀察 Priority Rate Limited 開始累加。
  2. 拿掉巢狀的 shape，直接把 WAN-QOS 套在 1 Gbps 介面上，觀察為什麼佇列統計永遠是 0（介面不覺得壅塞）。
  3. 把 NET-CONTROL 類別移除，灌滿線路後觀察 OSPF 鄰居是否開始 flap。
  4. 對比 police 和 shape：分別限速 5 Mbps，用 iperf TCP 測試實際吞吐量差多少。
  5. 用 auto qos 產生一套設定，跟你手寫的比較，看 Cisco 的預設比例跟你的判斷差在哪。

本章重點回顧

  • QoS 不增加頻寬，只決定壅塞時誰優先；長期滿載的解法是加頻寬
  • 四指標中抖動對即時應用最致命；語音門檻是 延遲 150ms / 抖動 30ms / 遺失 1%
  • 業界標準是 DiffServ（標記 + 各跳自行處理，不記狀態）
  • CoS 3 bits 只在 Trunk 上；DSCP 6 bits 端到端。AF 十進位 = 8x + 2y
  • 語音 EF(46)、路由協定 CS6(48)——後者絕不能忘
  • 不要信任端點的標記；電話可信任，電腦一律重寫
  • mls qos 沒開，所有 QoS 設定不生效
  • LLQ = CBWFQ + 嚴格優先佇列，優先佇列會被限速，總量不超過 33%
  • Shaping 緩衝、Policing 丟棄；配合 ISP 合約速率要用 shaping
  • WAN 要用巢狀 policy-map：外層 shape 製造壅塞點，內層才有意義
  • WRED 只對 TCP 有效，不要用在語音視訊上
  • SD-WAN 的核心是控制平面與資料平面分離；四元件 vManage / vSmart / vBond / vEdge
  • VXLAN 24 bits VNI，1600 萬個；EVPN 用 MP-BGP 當控制平面
去 模擬試題 選「自動化與架構」主題。QoS 在 CCNA 佔比不高但一定會考 DSCP 值和 LLQ 概念，CCNP ENCOR 則考得很細。
