1. 資料中心自動化的三個層次

從手動到自動的階梯 L1 腳本化 ── 把重複的 CLI 包成腳本 Bash / Python + SSH 問題:還是命令式,而且沒有狀態管理 L2 設定管理 ── 宣告「應該長什麼樣」 Ansible / Puppet 好處:冪等（跑幾次結果都一樣）、可版控 L3 事件驅動 ── 系統自己反應 EEM / POAP / Intersight 好處:不用人介入 實務建議:不要跳級 先把設定寫成程式碼並版控（L2） 再考慮讓它自己動（L3） 直接做 L3 但沒有 L2 的基礎,出事時你不知道現在的狀態該是什麼

2. NX-OS 的可程式化介面

介面說明適合
NX-API RESTHTTP + JSON/XML 操作物件模型與現有系統整合
NX-API CLI把 CLI 指令包進 HTTP 送出，回傳結構化結果從既有腳本遷移最快
NETCONF / RESTCONF標準協定 + YANG 資料模型跨廠牌自動化
Guest Shell交換器內建的 Linux 容器，可直接跑 Python在設備上就地執行腳本
Bash Shell直接進 NX-OS 底層 Linux進階排錯
# 啟用 NX-API N9K(config)# feature nxapi N9K(config)# nxapi https port 443 # 從外部呼叫（NX-API CLI 模式） curl -k -u admin:pass https://10.1.1.1/ins \ -H "Content-Type: application/json" \ -d '{"ins_api":{"version":"1.0","type":"cli_show", "chunk":"0","sid":"1","input":"show interface brief", "output_format":"json"}}' # Guest Shell:在交換器上直接跑 Python N9K# guestshell [guestshell@N9K ~]$ python3 my_script.py
✅ YANG 是什麼：一種描述設定與狀態資料結構的模型語言。它定義「一個介面有哪些欄位、型別是什麼、必填還是選填」。
NETCONF/RESTCONF 是傳輸方式，YANG 是資料的規格——兩者搭配才能做到跨廠牌的自動化。

3. EEM 與 POAP：讓設備自己動

EEM（Embedded Event Manager）

在設備內部設定「發生什麼事，就做什麼反應」，不需要外部系統介入。

# 例：偵測到某介面斷線就自動記錄診斷資訊並通知 N9K(config)# event manager applet LINK-DOWN-CAPTURE N9K(config-applet)# event syslog pattern "Interface Ethernet1/1.*down" N9K(config-applet)# action 1.0 cli command "show interface Ethernet1/1" N9K(config-applet)# action 2.0 cli command "show logging last 50" N9K(config-applet)# action 3.0 syslog priority critical msg "Eth1/1 斷線，已擷取診斷" N9K# show event manager policy internal
✅ EEM 最實用的場景是「偶發性故障」。問題只在半夜出現、你到現場時已經恢復——用 EEM 在事件發生的當下自動擷取現場資訊，隔天就有資料可以分析。

POAP（Power On Auto Provisioning）

開箱即用的自動佈建 新交換器出廠設定開機 ↓ 沒有 startup-config → 自動進入 POAP 模式 ↓ DHCP 取得 IP + Option 67 指向腳本位置 ↓ 下載並執行佈建腳本 ↓ 自動下載指定韌體 + 套用設定 + 重開 ↓ 上線,完全沒有人碰過 console 價值:上架 50 台交換器不用逐台設定 而且每一台的設定都保證一致（來自同一個範本）
陷阱：POAP 只在「沒有 startup-config」時觸發
如果設備曾經被設定過，開機不會進 POAP。要重新觸發必須先 write erase 並重開。
這也是保護機制——避免正式環境的設備意外被重新佈建。

4. Ansible、Puppet 與 Terraform

AnsiblePuppetTerraform
模式Push（從控制端推）Pull（代理定期拉）Push
需要代理程式不用（走 SSH/API）要裝 agent不用
語言YAMLPuppet DSLHCL
強項網路設備最常用大量伺服器的持續合規基礎設施佈建（含雲端）
狀態管理無狀態檔持續收斂有 state 檔
# Ansible 設定 Nexus VLAN 的 playbook - name: 設定資料中心 VLAN hosts: nexus_switches connection: network_cli tasks: - name: 確保 VLAN 存在 cisco.nxos.nxos_vlans: config: - vlan_id: 100 name: WEB-TIER - vlan_id: 200 name: DB-TIER state: merged - name: 設定介面 cisco.nxos.nxos_l2_interfaces: config: - name: Ethernet1/5 access: vlan: 100 state: merged
✅ 為什麼網路自動化多半選 Ansible：不需要在設備上裝代理程式——網路設備通常不允許裝第三方軟體。Ansible 走 SSH 或 API，設備端什麼都不用改。

Puppet 在 DC 的位置：比較常用在伺服器（尤其大量 Linux 主機的持續合規），網路設備上較少見但 NX-OS 有支援。
冪等（Idempotent）是自動化的核心要求
意思是：同一份設定跑一次和跑十次，結果完全相同。
Ansible 的模組會先檢查現況，只在需要時才做變更。如果你只是把 CLI 指令用腳本連續送出去，那不是冪等的——重跑可能產生重複設定或錯誤。

這是 L1 腳本化與 L2 設定管理的關鍵差別。

5. Streaming Telemetry：取代 SNMP 輪詢

SNMP 輪詢的問題 網管系統每 5 分鐘問一次:「介面流量多少?」 → 5 分鐘內的突波完全看不到 → 設備要花 CPU 回應大量查詢 → 設備越多,輪詢越慢 Streaming Telemetry 設備主動、持續把資料推出去（秒級甚至次秒級） → 用 gRPC / gNMI 傳輸,YANG 定義結構 → 推到 Kafka / 時序資料庫 / Grafana 差別像什麼 SNMP = 每 5 分鐘拍一張照片 Telemetry = 連續錄影
✅ Network Assurance 的概念：從「出事後去查」變成「持續確認網路是否符合預期」。
有了高解析度的遙測資料，可以做到：偵測微突發（microburst）、在效能劣化到影響使用者之前就發現、以及用歷史基準判斷「現在這個數字正不正常」。

技術用途關鍵記憶點
