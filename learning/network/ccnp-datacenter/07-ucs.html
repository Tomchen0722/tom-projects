Cisco UCS 統一運算

UCS 的核心不是硬體比較快，而是把伺服器的身分（MAC、WWN、BIOS）抽離硬體變成一份設定檔——換機器像換電池一樣簡單。

1. UCS 想解決的問題

傳統上換一台故障的伺服器：拆下舊的、裝上新的、重設 BIOS、重設網卡 MAC、重設 HBA 的 WWN、重做 Zoning、重裝作業系統——半天到一天跑不掉。
UCS 的目標是把這件事變成：新機器插上去，套用同一份「服務設定檔」，開機就是原本那台。
UCS 的核心概念:身分與硬體分離 傳統伺服器 身分（MAC、WWN、UUID、BIOS 設定、韌體版本） 全部燒在那台實體機器上 → 換機器 = 換身分 = 上下游全部要重設 UCS 身分抽出來變成 Service Profile（服務設定檔） 實體伺服器只是一個沒有個性的算力容器 Service Profile 內容: • MAC 位址（從 MAC Pool 取） • WWNN / WWPN（從 WWN Pool 取） • UUID（從 UUID Pool 取） • BIOS 政策、開機順序、韌體版本 • 網路與儲存的連接設定 把 Profile 從故障機器「解除關聯」再「關聯」到新機器 → 新機器完全繼承身分,上游的 Zoning 與 LUN 遮罩都不用改
✅ 這就是 UCS 最重要的價值主張。不是硬體比較快，而是把伺服器變成可替換的、由軟體定義的資源。考試很愛問這個核心概念。

2. 架構元件

UCS 的組成 Fabric Interconnect（FI） ── 大腦 + 統一出口 • UCS Manager 就跑在 FI 上（不是獨立伺服器） • 一定成對部署（A / B），叢集運作 • 所有網路與儲存流量都經過它 │ ┌────┴────┐ │ │ Chassis C-Series （刀鋒機箱） （機架伺服器） │ IOM / FEX（機箱內的 I/O 模組） • 不是交換器,只是「延伸線」 • 把刀鋒的流量集中送到 FI │ B-Series 刀鋒伺服器 └── VIC（Virtual Interface Card） 可虛擬出多張 vNIC 與 vHBA 兩種伺服器形式 B-Series（刀鋒）── 密度高、共用電源與散熱、適合大規模 C-Series（機架）── 彈性高、可裝更多本機碟與 GPU
必考：IOM 不是交換器
機箱裡的 IOM（也叫 FEX）不做本地交換——即使同一個機箱裡的兩台刀鋒要互通，流量也要先上到 FI 再繞回來。

為什麼這樣設計：所有流量都經過 FI，代表所有政策與監控都集中在一個地方，不會有「機箱內部的流量看不到」的死角。
代價是機箱內通訊多繞一段，但在 10G 以上的環境影響很小。

3. Pool、Policy 與 Template

元件作用例子
Pool身分資源池，自動配發MAC Pool、WWNN/WWPN Pool、UUID Pool、Server Pool
Policy可重複套用的設定BIOS 政策、開機順序、韌體套件、QoS
TemplateProfile 的模子vNIC/vHBA 範本、Service Profile 範本
Initial vs Updating Template（必考）
• Initial Template——用它產生 Profile 之後，兩者就脫鉤。改範本不影響已建立的 Profile。
• Updating Template——保持連結。改範本會自動套用到所有由它產生的 Profile。

威力與風險並存：Updating 讓你改一次就更新 200 台伺服器的設定；但改錯也會一次影響 200 台，而且某些變更會觸發重開機。
實務：正式環境用 Updating 但變更前務必先在測試 Profile 驗證。
✅ 手動指定 vs Pool 配發：絕對要用 Pool。手動打 MAC 與 WWN 一定會有人打錯或重複，而 SAN 環境裡兩個相同的 WWPN 會造成極難排查的故障。Pool 保證唯一性。

4. UCS 的儲存連接

FC / FCoE 開機Profile 裡指定 boot LUN 的目標 WWPN 與 LUN ID，伺服器本身可以完全沒有硬碟。
iSCSI 開機用 IQN 而非 WWPN，走一般 IP 網路。成本低。
FI 的兩種模式End-Host Mode（預設，不參與 STP，像一台大主機）／Switch Mode（當交換器用，會跑 STP）。
無狀態運算從 SAN 開機 + Service Profile = 伺服器完全無狀態，這是 UCS 的理想型態。
End-Host Mode 是預設也是建議
在 End-Host Mode 下，FI 對上游交換器來說就像一台伺服器——不跑 STP、不轉發上游之間的流量。
好處是：不會意外造成迴圈、不會捲進上游的 STP 拓撲、上游看到的 MAC 數量可控。
只有在特殊需求（例如要讓 FI 直接接儲存陣列）才切到 Switch Mode。

5. HyperFlex 與 Intersight

超融合（HCI）

三種架構的演進 傳統三層 伺服器 ── SAN 交換器 ── 儲存陣列 三種設備、三組管理介面、三批專業人員 融合式（Converged） 同樣的元件,但廠商預先整合驗證過並當成一套賣 例:FlexPod（Cisco UCS + NetApp） 超融合（Hyperconverged）= HyperFlex 把儲存陣列拿掉 → 用伺服器內建的硬碟組成分散式儲存 → 軟體定義,擴充就是加一台節點 → 一套介面管運算與儲存
優點限制
超融合部署快、管理單純、線性擴充運算與儲存綁在一起擴充——只缺儲存也要買整台節點
傳統三層運算與儲存可各自獨立擴充複雜、要多種專業
✅ 選型判斷：工作負載的運算與儲存需求比例穩定 → 超融合很適合（VDI 是典型）。
如果是資料成長遠快於運算需求（例如影音歸檔），傳統三層的獨立擴充比較划算。

Cisco Intersight

Intersight 是 Cisco 的雲端維運平台，把原本要逐一登入各套 UCS Manager 的工作集中起來。

跨站集中管理不論設備在哪個機房，都在同一個雲端介面管理。
主動式支援自動比對已知問題與韌體建議，出事前先提醒。
韌體協調檢查各元件版本相容性，這在 UCS 是很痛的維運工作。
API 優先所有功能都有 REST API，可接進既有的自動化流程。
