ACI 進階：Multi-Pod、微分段與服務插入

第 05 章講了 ACI 的政策模型與 Contract。這一章處理實際落地時真正會被問的三件事——多機房怎麼擴展、同一個 EPG 裡的機器怎麼互相隔離、防火牆怎麼插進 fabric。

1. 四種擴展架構怎麼選

把 ACI fabric 想成一家公司：
Multi-Pod = 同一家公司開了第二個辦公室，還是同一套人事制度、同一個總經理；
Multi-Site = 開了子公司，各有各的總經理，只有集團層級的政策要對齊；
Remote Leaf = 派了幾個人去客戶端駐點，還是總部管；
Multi-Tier = 同一個辦公室多加一層樓。
Multi-PodMulti-SiteRemote Leaf
APIC 叢集一個（跨 Pod 分散）各自獨立，上面加 Nexus Dashboard Orchestrator屬於原本的 fabric
故障域共用（同一個控制平面）完全隔離共用
延遲要求嚴格（IPN 之間需低延遲）寬鬆相對寬鬆
中間網路IPN（Inter-Pod Network），需支援 OSPF、多播、大 MTUISN（Inter-Site Network），只需 IP 可達與大 MTUIP 網路
典型用途同園區或近距離的兩棟樓跨城市、跨國的資料中心小型分點、邊緣站點不值得放整套 fabric
✅ 選型的判斷點只有一個：你要不要故障域隔離。
要一致的政策與單一管理介面、機房距離近 → Multi-Pod。
要各機房獨立存活、一邊出事另一邊不受影響 → Multi-Site。
只是幾個機櫃的小站點、不想在那裡放 Spine 與 APIC → Remote Leaf。

2. Multi-Pod：一個 fabric、多個機房

Multi-Pod 架構 Pod 1 Pod 2 Spine ── Leaf Leaf ── Spine │ │ └────────── IPN（Inter-Pod Network）──────────┘ 需求：OSPF、PIM Bidir 多播、DHCP relay、MTU ≥ 9150 APIC 叢集橫跨兩個 Pod（例如 3 台在 Pod1、2 台在 Pod2） → 只有一個管理介面、一套政策 → 但也是同一個控制平面故障域

IPN 的四個硬性要求

OSPFIPN 與 Spine 之間跑 OSPF 交換底層路由。
多播（PIM Bidir）承載 BUM 流量。這是 IPN 最容易卡關的一項——很多既有的骨幹網路不支援。
DHCP Relay讓遠端 Pod 的設備能向 APIC 取得位址完成自動佈建。
大 MTU（≥ 9150）VXLAN 封裝後封包會變大，MTU 不夠就會分片或丟棄。
Multi-Pod 部署失敗最常見的原因就是 IPN 沒配合。
企業的既有骨幹通常不跑多播、MTU 是預設 1500，而網路團隊往往低估了「要請骨幹團隊改設定」這件事的難度。
症狀：Pod 之間單播通、但跨 Pod 的廣播與 ARP 不通（多播沒開）；或大封包不通（MTU 不足）。
建議：專案啟動時就把 IPN 需求文件交給骨幹團隊確認，不要等到設備都到貨才發現骨幹不支援。
APIC 叢集的分散有講究。APIC 需要多數決（quorum）才能寫入設定。三台 APIC 分成 2+1 時，如果放兩台的那個 Pod 整個掛掉，剩下一台無法形成多數，fabric 會進入唯讀狀態（既有轉送仍正常，但無法變更設定）。
大型部署常用五台並搭配 standby APIC，或直接改用 Multi-Site 讓兩邊各有完整叢集。

3. Multi-Site：多個獨立 fabric

Multi-Site 架構 Nexus Dashboard Orchestrator（NDO） ↑ 集中定義跨站政策,再推送到各站 ┌──────────────┴──────────────┐ Site-A Site-B APIC 叢集 A APIC 叢集 B Spine ── Leaf Leaf ── Spine └────────── ISN ──────────────┘ 只需 IP 可達 + 大 MTU （不需要多播,BUM 用 Ingress Replication）
各站獨立 APIC一邊的控制平面出問題，另一邊完全不受影響。這是與 Multi-Pod 最大的差別。
NDO 集中編排跨站的 Tenant、VRF、EPG、Contract 在 NDO 上定義一次，推送到各站。各站仍可有自己的本地政策。
ISN 要求低只要 IP 可達與大 MTU，不需要多播——這讓它比 Multi-Pod 好落地很多。
可選擇性延伸哪些 EPG／橋接網域要跨站延伸是逐一決定的，不是全部一起。
✅ Multi-Pod vs Multi-Site 的一句話判斷：
問「Site-A 的 APIC 全部掛掉時，Site-B 還能不能正常運作與變更設定」——
要「能」→ Multi-Site；可以接受「不能」而想換取單一管理介面 → Multi-Pod。
企業實例｜某集團的架構選型轉折
集團原本規劃台北與桃園兩個機房走 Multi-Pod（距離近、延遲低，看起來很合適）。專案進行到一半，骨幹團隊回報：兩機房之間的租用線路無法支援 PIM Bidir 多播，電信商也不願意為此調整。
評估後改為 Multi-Site：ISN 只需要 IP 可達與大 MTU，租用線路直接就能用。
額外的收穫是當初沒想到的：改成 Multi-Site 之後，兩個機房的維護窗口可以完全分開——升級 Site-A 的 APIC 時 Site-B 完全不受影響。原本 Multi-Pod 的設計中，APIC 叢集升級是要整個 fabric 一起做的。
教訓：架構選型不能只看技術規格表，要先確認中間網路做不做得到。

4. Remote Leaf 與 vPod

Remote Leaf 讓你在小型站點只放一對 Leaf，不需要 Spine 也不需要本地 APIC——控制平面仍由主資料中心的 APIC 管理，透過 IP 網路（IPN）連回來。
典型場景：分公司機房只有幾個機櫃、零售門市的邊緣運算節點、共置機房（colo）的小規模部署。
好處政策與主 fabric 完全一致、單一管理介面、不必為小站點買整套設備。
限制依賴回主站的 IP 連線；WAN 斷線時本地流量仍可轉送（有本地存活能力），但無法變更設定。
延遲要求比 Multi-Pod 寬鬆，適合跨城市。
常見誤解：以為 Remote Leaf 斷線就會停擺。
現代版本的 Remote Leaf 具備本地存活（local switching）能力——WAN 斷掉時，站點內部的流量仍能正常轉送，只是無法與主站通訊、也無法推送新政策。
這跟「完全依賴總部」是不一樣的，設計時要講清楚，否則業務單位會誤以為風險太高而反對。

5. 微分段：同 EPG 內也能隔離

第 05 章講過：同一個 EPG 內的端點預設可以自由通訊，不需要 Contract。這在多數情況下很方便，但有時候正是問題所在。

問題情境 EPG: Web-Servers（十台網頁伺服器） Web1 Web2 Web3 ... Web10 ↕ 彼此可以完全自由通訊 攻擊者攻下 Web3 之後,可以直接橫向移動到其他九台。 但實際上這十台伺服器根本不需要互相通訊—— 它們只需要跟前面的 LB 和後面的 DB 講話。 微分段（uSeg EPG）：把 EPG 再切細 依 VM 名稱、IP、MAC、VM 標籤、作業系統等屬性 動態把端點分到不同的 uSeg EPG,彼此之間就需要 Contract 才能通
分類屬性用途範例
IP 位址 / 網段把特定網段的機器獨立出來
MAC 位址實體伺服器的精確指定
VM 名稱命名規則含 -prod- 的自動歸到正式環境 uSeg
VM 標籤 / 自訂屬性最實用：在 vCenter 上打標籤，ACI 自動套用政策
作業系統把還沒修補的舊版 OS 自動隔離
VM 識別碼精確指定單一 VM
✅ 微分段最強大的地方是「動態」。你定義的是規則而不是清單——「所有名稱含 quarantine 的 VM 歸到隔離 EPG」。
當資安團隊發現一台機器可疑時，只要在 vCenter 上改個標籤，網路政策就自動生效，不需要網路團隊介入、不需要改 IP、不需要移動 VLAN。
這是 ACI 相對於傳統 VLAN + ACL 最有說服力的一個功能。
企業實例｜某電商的資安事件應變
資安團隊在監控中發現一台應用伺服器有異常的對外連線。傳統做法是：通知網路團隊 → 找出那台機器接在哪個埠 → 改 VLAN 或加 ACL → 可能要重開機或改 IP，整個流程要 30 分鐘以上，而且改動有風險。
導入微分段後：資安人員直接在 vCenter 上把該 VM 加上 quarantine 標籤。ACI 的 uSeg 規則立刻把它移到隔離 EPG，該 EPG 只有一條 Contract——只允許存取資安鑑識主機。
整個過程約 30 秒，而且不需要網路團隊介入，VM 也不用重開。
鑑識完成後把標籤拿掉，機器就自動回到原本的 EPG。
微分段的實務限制要說清楚：
① 依 VM 屬性分類需要 VMM 整合（ACI 與 vCenter 或 Kubernetes 對接）；純實體伺服器只能用 IP/MAC 分類。
② uSeg EPG 與原 EPG 必須在同一個橋接網域。
③ 規則數量會增加政策複雜度，要有命名規範與文件，否則半年後沒有人說得清楚為什麼某台機器歸在某個 uSeg。

6. 服務插入與 PBR

Contract 決定「能不能通」，但很多時候需求是「可以通，但要先經過防火牆」。這就是服務插入（Service Insertion）。

傳統做法：靠網路設計逼流量繞過去 Web EPG ──▶ 改 VLAN、改預設閘道、改路由 ──▶ 防火牆 ──▶ DB EPG ↑ 防火牆變成網路拓撲的一部分,牽一髮動全身 ACI 的做法：Service Graph + PBR Web EPG ──── Contract（附帶 Service Graph） ────▶ DB EPG │ ▼ 防火牆（單臂,不改拓撲） 流量依「政策」被導向防火牆,而不是依「路由」。 防火牆可以單臂接在 fabric 上,不需要當閘道、不需要在路徑中間。
Service Graph定義流量要依序經過哪些服務裝置（防火牆 → IPS → 負載平衡器）。
PBR（政策式重導向）實際把流量導過去的機制。不改變 IP、不改變路由，純粹依 Contract 重導向。
Managed vs UnmanagedManaged 模式由 APIC 直接設定防火牆（需裝置套件）；Unmanaged 模式只做導流，防火牆自己管——現在多數採用後者。
✅ PBR 的最大價值是「防火牆不再是拓撲的一部分」。
傳統設計中，要讓流量經過防火牆就得把它放在路徑中間，於是防火牆變成單點故障、擴充要停機、而且「哪些流量會經過它」取決於路由設計，很難說得清楚。
ACI PBR 讓防火牆單臂掛在 fabric 上，要讓哪些流量經過它是Contract 決定的——一目了然，而且改動不影響拓撲。
設計時要注意的三件事：
① 對稱性——去程與回程必須經過同一台防火牆，否則具狀態防火牆會因為只看到單向流量而丟包。多台防火牆做負載分擔時要特別設計雜湊。
② 健康檢查——PBR 可設定追蹤（tracking），防火牆掛掉時決定要「直接放行（bypass）」還是「全部丟棄」。這是資安與可用性的取捨，要事先跟資安團隊講好。
③ 不對稱路由的排錯——服務插入的問題常表現為「TCP 連線建立不起來但 ping 得通」，因為 ICMP 無狀態而 TCP 有狀態。

7. L3Out 的常見設計

第 05 章介紹了 L3Out 的概念。實務上有幾個設計決策幾乎每個案子都會遇到。

決策選項與考量
路由協定OSPF（企業內常見）、BGP（對 ISP 或需要政策控制時）、靜態（最單純的小型部署）
External EPG 怎麼切用 0.0.0.0/0 一網打盡最簡單，但等於「外面全部是同一類」——無法對不同外部來源套不同 Contract。建議依實際需求切成幾個 External EPG
放在哪一層Border Leaf 專用（推薦，職責清楚）或與運算 Leaf 共用（省設備但故障影響面大）
Transit Routing讓 ACI 成為兩個外部網路之間的轉送路徑。要小心不要變成非預期的中轉站
External EPG 用 0.0.0.0/0 是最常見的偷懶做法，也是最常見的資安缺口。
這代表「所有外部來源都是同一類」，於是給內部 EPG 開的任何一條對外 Contract，都等於對整個外部世界開放。
比較好的做法：把外部切成幾個 External EPG（例如「總部網段」「分公司網段」「網際網路」「合作夥伴」），各自套不同的 Contract。
這跟第 04 章的 RBAC 是同一個精神——不要每個工程師都給 admin，也不要每個外部來源都給同一組權限。
企業實例｜一次因為 0.0.0.0/0 造成的意外
某公司的 ACI 部署中，L3Out 的 External EPG 用了 0.0.0.0/0，並給資料庫 EPG 開了一條 Contract 允許從外部存取 1433 埠（原意是「讓總部的管理主機能連進來管理」）。
半年後資安掃描發現：這個資料庫從網際網路可以直接連到——因為 0.0.0.0/0 涵蓋了所有來源，而 L3Out 同時也承載對外連線。
修正：把 External EPG 拆成「管理網段」與「其他」，1433 的 Contract 只掛在管理網段那個 EPG 上。
教訓：ACI 的政策模型很強大，但強大的前提是你把分類做細。全部歸成一類就退化成傳統的「有防火牆但規則寫成 any-any」。

8. 本章重點整理

陷阱 1：Multi-Pod 與 Multi-Site 搞混
Multi-Pod = 一個 APIC 叢集（共用故障域，IPN 需要多播）；Multi-Site = 各站獨立 APIC（故障域隔離，ISN 不需多播，用 NDO 編排）。
陷阱 2：低估 IPN 的需求
Multi-Pod 的 IPN 要 OSPF + PIM Bidir 多播 + DHCP Relay + MTU ≥ 9150。既有骨幹常常做不到，專案一開始就要確認。
陷阱 3：以為同 EPG 內就一定不能隔離
用 uSeg EPG（微分段）可以依 VM 屬性再細分。依 VM 標籤分類需要 VMM 整合。
陷阱 4：服務插入沒考慮對稱性
去程與回程必須經過同一台具狀態防火牆。症狀是「ping 通但 TCP 建不起來」。
陷阱 5：External EPG 全用 0.0.0.0/0
等於「外面全部是同一類」，任何一條對外 Contract 都變成對全世界開放。要依來源切成多個 External EPG。
陷阱 6：以為 Remote Leaf 斷線就停擺
具備本地存活能力，WAN 斷時站內流量仍可轉送，只是無法變更政策。
陷阱 7：APIC 叢集分散沒考慮多數決
三台分成 2+1 時，放兩台的 Pod 整個掛掉會讓 fabric 進入唯讀狀態（轉送正常但無法改設定）。
✅ 一句話：要單一管理選 Multi-Pod、要故障隔離選 Multi-Site、小站點用 Remote Leaf；EPG 內要再隔離用微分段、要強制過防火牆用 Service Graph + PBR；而這一切的效果好不好，取決於你把分類做得多細。
