1. vPC 進階：四個一定要開的功能

第 01 章講了 vPC 的組成與三種故障情境。實務部署時還有四個功能幾乎一定要開，不開會踩到各種難查的問題。

功能不開會怎樣開了之後
peer-gateway某些伺服器（NAS、負載平衡器）會把封包送到對方 vPC peer 的 MAC，導致封包必須繞 peer-link，甚至被丟棄每台 Nexus 都願意代替對方回應，封包直接在本地處理
peer-switch兩台 Nexus 在 STP 中是不同的 Bridge ID，切換時下游會經歷 STP 收斂兩台對外呈現同一個 Bridge ID，STP 收斂時間大幅縮短
auto-recovery兩台同時斷電後一起開機，因為互相看不到對方而都不敢啟用 vPC 埠，網路整個起不來等待一段時間後，其中一台自行成為 Primary 並啟用埠
ip arp synchronize切換後對端要重新學 ARP，造成短暫流量中斷兩台同步 ARP 表，切換更平順
! ── vPC domain 的建議設定 ──
N9K(config)# vpc domain 10
N9K(config-vpc-domain)# peer-switch
N9K(config-vpc-domain)# peer-gateway
N9K(config-vpc-domain)# auto-recovery
N9K(config-vpc-domain)# ip arp synchronize
N9K(config-vpc-domain)# role priority 100          ! 數字小的當 Primary
N9K(config-vpc-domain)# peer-keepalive destination 192.168.1.2 source 192.168.1.1 vrf management
N9K(config-vpc-domain)# delay restore 150           ! 重開後等路由收斂再啟用 vPC 埠

! ── 驗證 ──
N9K# show vpc
N9K# show vpc brief
N9K# show vpc consistency-parameters global
N9K# show vpc role
delay restore 是很多人漏掉但很重要的一項。
Nexus 重開機後，vPC 埠會很快 up，但路由協定還沒收斂完——結果流量進來了卻不知道往哪送，形成短暫黑洞。
delay restore 讓 vPC 埠等一段時間再啟用，給路由協定時間收斂。症狀是「重開機後有幾十秒的封包遺失」，很多人以為是正常現象，其實是可以避免的。

2. 一致性檢查與 Orphan Port

Type-1 與 Type-2 的差別

Type-1 不一致會停用 vPC。屬於「不一致就會造成轉送錯誤」的參數：STP 模式、MTU、VLAN 的允許清單、Port Channel 模式。
Type-2 不一致只警告，vPC 繼續運作。屬於「不一致但不至於出錯」的參數：ACL、QoS 設定、部分介面參數。
Type-1 不一致的症狀非常明確：vPC 突然掉了，而且是「兩邊都好好的但 vPC 就是起不來」。
最常見的原因是有人只在一台上改了設定——加了一個 VLAN 到 trunk allowed list、改了 MTU、調了 STP 參數。
排錯第一招：show vpc consistency-parameters global 與 show vpc consistency-parameters interface port-channel X，它會直接列出兩邊哪個參數不一樣。
預防：vPC 兩台的設定變更要成對進行，最好用自動化工具同時推送。

Orphan Port：vPC 架構裡的孤兒

什麼是 Orphan Port N9K-1 ══ peer-link ══ N9K-2 │ │ │ │ └────vPC──────────┘ ← 雙歸屬伺服器（正常） │ └─── 單歸屬伺服器 ← Orphan Port（只接一台） 問題：當 peer-link 斷掉時,Secondary 會關閉所有 vPC 成員埠, 但 Orphan Port 「不是」vPC 成員埠,所以它不會被關掉—— 結果那台單歸屬伺服器仍然 up,卻已經與網路其他部分隔離,形成黑洞。
! ── 解法：把 Orphan Port 也納入 peer-link 失效時的關閉範圍 ──
N9K(config)# interface ethernet 1/10
N9K(config-if)# vpc orphan-port suspend

! ── 找出目前有哪些 Orphan Port ──
N9K# show vpc orphan-ports
✅ 實務建議：資料中心的伺服器盡量都做雙歸屬。但現實中總會有一些設備只有一張網卡（老舊設備、管理主機、測試機），這些就是 Orphan Port。
把 vpc orphan-port suspend 設上去，讓它在 peer-link 失效時一起被關掉——與其讓它半死不活地送封包進黑洞，不如明確地讓它斷線，這樣監控系統才會告警、應用層的健康檢查才會切換。

3. 不停機升級：ISSU 與滾動升級

方式怎麼做適用
ISSU
（In-Service Software Upgrade）		單台設備不中斷轉送的情況下升級軟體有雙管理引擎的機箱式設備；固定式機型的支援版本有限制
vPC 滾動升級一次升一台，靠 vPC 的另一台維持服務最常用。兩台 Nexus 輪流升
ACI fabric 升級APIC 先升，再依維護群組分批升 Spine 與 LeafACI 環境。Leaf 要分成兩組交錯升級
vPC 滾動升級的標準流程 1. 確認健康 show vpc / show interface status / 確認沒有 Orphan Port 問題 2. 備份設定 copy running-config startup-config + 匯出到外部 3. 確認相容性 兩台在升級過程中會短暫跑不同版本 → 查相容矩陣 4. 升級 Secondary 重開,等它完全回來並確認 vPC 恢復 5. 驗證 show vpc / 確認流量分佈正常 / 觀察一段時間 6. 升級 Primary 重複步驟 4-5 7. 最終驗證 兩台版本一致、vPC 正常、所有 VLAN 通 ⚠ 步驟 4 與 6 之間務必留觀察時間,不要連續升兩台。
升級最大的風險不是升級本身，是「兩台版本不同期間的相容性」。
vPC 對兩端的軟體版本有相容性要求，跨大版本升級時可能不允許長時間混版運作。
務必先查該型號該版本的相容矩陣，某些跨版本必須經過中間版本，不能一次跳。
另一個常被忽略的：升級後某些預設值可能改變（例如新版預設啟用某個功能），升級後要用 show run diff 或與備份比對，確認設定沒有被意外改動。
企業實例｜一次沒有觀察期的升級事故
某資料中心排定週末升級一對 Nexus。工程師為了縮短維護窗口，升完 Secondary 看到 show vpc 顯示正常，就立刻開始升 Primary。
問題是：Secondary 雖然 vPC 起來了，但底層的 BGP 還在收斂中，此時把 Primary 也重開，等於兩台同時處於不完整狀態——整個機櫃列失聯約六分鐘。
事後檢討的結論：升完一台之後的「觀察期」不是形式，要驗證的不只是 vPC 狀態，還包括路由協定鄰居數量、路由表條目數、實際流量是否恢復到原本水準。
後來的做法：制定升級檢核表，每一台升完都要確認五項指標回到基準值才能繼續，最短觀察期 15 分鐘。

4. Breakout 埠與線材選擇

資料中心的機櫃佈線是一門實務學問，也是新手最常搞錯的地方。

Breakout（拆分）把一個 40G 埠拆成 4 個 10G，或 100G 拆成 4 個 25G。用一條線接到扇出線材（breakout cable）接四台伺服器。
DAC 銅纜短距離（機櫃內、相鄰機櫃）最便宜，不需光模組。缺點是粗、重、彎折半徑大。
AOC 主動光纜兩端固定光模組的成品線。比 DAC 細長、可拉更遠，但長度固定不可改。
光模組 + 光纖最有彈性，距離最遠。成本最高，但更換與擴充最方便。
! ── 設定 Breakout（設定後需要重載該模組）──
N9K(config)# interface breakout module 1 port 49 map 10g-4x

! 之後原本的 Ethernet1/49 會變成：
!   Ethernet1/49/1、1/49/2、1/49/3、1/49/4

! ── 查看目前的埠速率與模組 ──
N9K# show interface transceiver       ! 看光模組型號與光衰
N9K# show interface transceiver details
N9K# show running-config | include breakout
三個實務上常踩的坑：
① Breakout 設定會讓埠編號改變，原本掛在 Ethernet1/49 上的所有設定全部消失。要先規劃好再做，不要在正式環境臨時改。
② 不是每個埠都支援 Breakout——依機型不同，通常只有特定範圍的埠可以拆，查資料表。
③ 光模組要看 show interface transceiver details 的光衰值。介面 up 不代表光品質好——接收功率接近臨界值時會出現間歇性 CRC 錯誤，這是資料中心最難查的實體層問題之一。
✅ 排錯技巧：懷疑實體層時，先看 show interface transceiver details 的 Rx Power。
如果數值接近或低於 Warning / Alarm 門檻，就是光衰問題——可能是光纖髒了、彎折過度、接頭沒插好、或線太長。
清潔光纖接頭是最便宜也最常有效的第一步，很多「換了模組還是不好」的案子最後是接頭有灰塵。

5. 管理平台：NDFC 與 Nexus Dashboard

平台做什麼什麼時候需要
Nexus Dashboard承載各種服務的平台底座要跑下面那些服務時的前提
NDFC
（Fabric Controller，前身 DCNM）		NX-OS fabric 的自動化與管理：VXLAN EVPN fabric 的建置、拓撲視覺化、設定合規檢查、SAN 管理用 NX-OS 建 VXLAN fabric 時，手工設定幾十台 Leaf 不實際
NDO
（Orchestrator）		跨站編排——ACI Multi-Site 或多 fabric 的政策集中定義ACI Multi-Site 的必要元件
NDI
（Insights）		主動分析：異常偵測、設定合規、韌體建議、變更前的影響分析大型 fabric 的維運可視性
IntersightUCS 與 HyperFlex 的雲端管理（見第 07 章）運算層的管理
NDFC 對 NX-OS fabric 的價值，等於 APIC 對 ACI 的價值。
純用 CLI 建 VXLAN EVPN fabric，每台 Leaf 都要打幾十行設定，五十台就是幾千行，而且一個打錯就是難查的故障。
NDFC 用樣板驅動：定義 fabric 的參數（AS 號、底層 IP 池、VNI 範圍），它自動產生並推送每台設備的設定，還會持續檢查有沒有人手動改壞（設定飄移偵測）。
這也回答了「NX-OS VXLAN 與 ACI 怎麼選」這個問題的一部分——ACI 是買整套方案，NX-OS + NDFC 是保留 CLI 彈性但加上自動化。
企業實例｜五十台 Leaf 的設定飄移
某公司用 NX-OS 手工建了 VXLAN EVPN fabric，五十台 Leaf。運作一年後開始出現零星的「某個 VLAN 在某些機櫃不通」。
查了很久才發現：這一年間陸續有五位工程師上去改過設定，有人為了排錯臨時關掉某個 VNI 忘了開回來、有人新增 VLAN 時漏掉兩台 Leaf、有人改了 MTU。五十台的設定已經沒有兩台完全一樣。
導入 NDFC 之後：先做一次設定合規掃描，列出每台與樣板的差異（總共 137 處），逐一確認後統一收斂。之後所有變更都經由 NDFC 推送。
最大的收穫不是自動化，是「有一個唯一的真實來源」——現在問「VLAN 100 應該在哪些 Leaf 上」有明確答案，而不是要去五十台上各查一次。

6. Telemetry 取代 SNMP 輪詢

SNMP 輪詢 vs Streaming Telemetry SNMP（拉） 監控系統 ──每 5 分鐘問一次──▶ 設備 ✘ 兩次輪詢之間發生的事看不到 ✘ 設備要花 CPU 回應大量查詢 ✘ 幾百台設備 × 幾百個 OID = 輪詢風暴 Telemetry（推） 設備 ──主動推送(gRPC/gNMI)──▶ 收集器 ✔ 秒級甚至次秒級的資料 ✔ 設備只做一次序列化,不必回應每個查詢 ✔ 可訂閱「有變化才送」(on-change)
訂閱模式Periodic（固定間隔送）與 On-change（狀態改變才送）。介面計數器用前者、鄰居狀態用後者。
編碼與傳輸常見是 gRPC + protobuf 或 gNMI，資料模型用 YANG（見第 08 章）。
典型後端收集器（Telegraf 等）→ 時序資料庫（InfluxDB/Prometheus）→ 視覺化（Grafana）。也可直接送 NDI。
✅ Telemetry 解決的核心問題是「解析度」。
SNMP 五分鐘一次的介面統計，看不出「某個 30 秒的微爆發（microburst）把緩衝區塞爆導致丟包」——而這正是資料中心最常見的效能問題之一。
秒級的 telemetry 才看得到微爆發。這是為什麼高效能運算與金融交易環境一定要用 telemetry 而不是 SNMP。

7. 八個真實故障案例

每個案例先看症狀自己判斷，再看解析。這些都是資料中心環境的高頻樣態。

案例 1｜新增 VLAN 之後 vPC 掉了

症狀：工程師在其中一台 Nexus 上把 VLAN 200 加進 vPC trunk 的允許清單，幾秒後 show vpc 顯示大量 vPC 進入 suspended。

檢查：show vpc consistency-parameters interface port-channel 10 顯示兩邊的 allowed VLAN 不一致。

根因：Type-1 一致性檢查失敗。Trunk 的 allowed VLAN 清單屬於 Type-1 參數，兩邊不一致就會停用 vPC。

解法：在另一台上做同樣的變更。預防：vPC 兩台的設定變更必須成對進行，最好用自動化工具同時推送，或至少建立「改一台就立刻改另一台」的作業紀律。

案例 2｜peer-link 斷掉後某台伺服器完全失聯

症狀：peer-link 光纖被誤拔，多數服務正常（Secondary 關閉 vPC 埠，流量集中到 Primary），但有一台備份伺服器完全連不上。

檢查：該伺服器只有一張網卡，接在 Secondary 上。show vpc orphan-ports 顯示它是 Orphan Port。

根因：Orphan Port 不是 vPC 成員埠，peer-link 斷時不會被關閉，但它所在的 Secondary 已經被隔離，於是形成黑洞——埠是 up 的，伺服器以為自己在線上，實際上封包送不出去。

解法：在該埠設 vpc orphan-port suspend。與其半死不活，不如明確斷線讓監控與應用層的健康檢查能反應。更根本的解法是把它改成雙歸屬。

案例 3｜兩台 Nexus 同時斷電復電後網路起不來

症狀：機房跳電，兩台 Nexus 同時重開。電力恢復後，兩台都開機正常，但所有 vPC 埠都沒有啟用，整個機櫃列不通。

根因：兩台同時開機時互相看不到對方（peer-link 與 keepalive 都還沒建立），基於防止 split-brain 的保護機制，兩台都不敢啟用 vPC 埠。

解法：開啟 auto-recovery——等待一段時間後其中一台自行成為 Primary 並啟用埠。這是資料中心「跳電之後才發現沒設定」的經典項目，應該在部署時就開好。

案例 4｜跨 Leaf 的同網段 VM 不通

症狀：VXLAN EVPN 環境中，同一個 VLAN 的兩台 VM，在同一台 Leaf 下互通正常，跨到另一台 Leaf 就不通。

檢查順序：① VTEP loopback 互 ping — 通；② show bgp l2vpn evpn summary — 鄰居正常；③ show nve peers — 對端 VTEP 沒出現；④ show nve vni — 該 VNI 在其中一台是 Down。

根因：其中一台 Leaf 的 VLAN 沒有對應到 VNI（漏了 vn-segment），或 NVE 介面沒有加入該 member vni。

解法：補上設定。這個案例的價值在排錯順序——由下而上一層層確認，五個指令就定位了。如果一開始就去看 MAC 表，會浪費很多時間。

案例 5｜升級後某些流量突然不通

症狀：NX-OS 升級完成，vPC 與路由都正常，但某些應用的連線失敗。

檢查：與升級前的設定備份比對，發現某個功能的預設值在新版改變了——舊版預設關閉的一個安全檢查，新版預設開啟，擋掉了某類流量。

根因：升級不只是換軟體，預設值可能改變。而 show running-config 不會顯示「維持預設值」的項目，所以看設定看不出差異。

解法：升級後用 show running-config all（顯示含預設值的完整設定）與升級前的版本比對。升級前先讀 Release Notes 的「Changed Behavior」章節是最有效的預防。

案例 6｜FC 儲存間歇性 I/O 逾時

症狀：某台伺服器對 SAN 的存取偶爾逾時，重試後成功。同一個 VSAN 的其他伺服器正常。

檢查：show interface transceiver details 顯示該埠的 Rx Power 接近 Alarm 門檻；show interface 有零星的 CRC 錯誤。

根因：光衰。可能是光纖接頭有灰塵、彎折過度，或線材老化。

解法：清潔光纖接頭與模組（最便宜的第一步），無效再換線材或模組。儲存流量對丟包極度敏感——一般資料流量丟一兩個封包靠 TCP 重傳就沒事，FC 環境的丟包會直接變成 I/O 錯誤。「介面 up」在 SAN 環境完全不代表健康。

案例 7｜微爆發造成的間歇性丟包

症狀：應用團隊反映偶爾有延遲尖峰，但網路監控（SNMP，五分鐘一次）顯示介面使用率只有 40%，看起來很健康。

檢查：改用 秒級 telemetry 之後，發現該介面每隔一段時間有持續數百毫秒的 100% 滿載，伴隨 output drops 增加。

根因：微爆發（microburst）。分散式運算或備份任務在極短時間內送出大量資料，把介面緩衝區塞爆。五分鐘平均值把它完全平滑掉了。

解法：調整緩衝區配置、對該類流量套用 QoS、或從應用端錯開時間。這個案例說明了 telemetry 相對於 SNMP 的核心價值：解析度。

案例 8｜ACI 中兩個 EPG 明明有 Contract 卻不通

症狀：Web EPG 與 DB EPG 之間建了 Contract 允許 1433 埠，但連不上。

檢查：① Contract 的 provider 與 consumer 方向設反了；② 或 Filter 只寫了單向（只允許目的埠 1433，沒有處理回程）；③ 或兩個 EPG 在不同 VRF 而沒設定 VRF 間的路由洩漏。

根因（最常見）：方向設反。提供服務的那一端是 provider（DB 是 provider，Web 是 consumer），設反了就等於允許了相反方向的連線。

解法：確認方向；ACI 的 Contract 對於 TCP 通常會自動處理回程（若 Filter 有設 established 相關選項），但仍要確認 Filter 定義。排錯工具：APIC 上的 Contract 命中計數與 Endpoint Tracker，可直接看到封包有沒有命中規則。

八個案例的共同心法
① 「介面 up」在資料中心特別不可信——案例 2 的 Orphan Port、案例 6 的光衰，都是 up 但不健康。
② 成對的設備要成對變更——案例 1 的 vPC 一致性，是最常見的自己造成的故障。
③ 由下而上排錯——案例 4 用五個指令定位，是因為順序對。
④ 升級要比對「含預設值」的設定——案例 5 的陷阱是 show run 看不到。
⑤ 監控的解析度決定你看得到什麼——案例 7 的微爆發在五分鐘平均值裡完全隱形。
⑥ 保護機制也會造成「故障」——案例 3 的兩台都不敢啟用埠，其實是設計如此，缺的是 auto-recovery。

8. 本章重點整理

陷阱 1：vPC 只做基本設定
peer-switch、peer-gateway、auto-recovery、ip arp synchronize、delay restore 這五項幾乎都該開，不開會遇到各種難查的問題。
陷阱 2：只在一台上改設定
Trunk allowed VLAN、MTU、STP 模式都是 Type-1 參數，不一致會直接停用 vPC。用 show vpc consistency-parameters 查。
陷阱 3：忽略 Orphan Port
peer-link 斷時它不會被關，形成黑洞。設 vpc orphan-port suspend，或改成雙歸屬。
陷阱 4：升級不留觀察期
vPC 狀態正常不代表路由收斂完成。每台升完要驗證五項指標回到基準值才能繼續下一台。
陷阱 5：升級後只比對 show run
預設值改變不會顯示在 running-config 裡。要用 show running-config all 比對，並先讀 Release Notes 的行為變更章節。
陷阱 6：Breakout 設定在正式環境臨時改
會讓埠編號改變、原有設定全部消失。而且不是每個埠都支援。
陷阱 7：實體層只看介面 up/down
要看 show interface transceiver details 的 Rx Power。光衰造成的間歇性 CRC 是最難查的問題之一，清潔接頭是最便宜有效的第一步。
陷阱 8：用 SNMP 五分鐘平均值判斷有沒有壅塞
看不到微爆發。需要秒級 telemetry 才能發現。
✅ 一句話：vPC 的五個進階功能與一致性是穩定的地基；升級要有觀察期與含預設值的比對；實體層要看光衰不是只看 up/down；而監控的解析度決定你看不看得到真正的問題。
