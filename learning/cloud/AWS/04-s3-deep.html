1. 基本概念與命名規則

概念說明
Bucket最上層容器。名稱全球唯一（不只你的帳號，是全世界）
Object一個檔案 + 中繼資料。單一物件最大 5 TB
Key物件的完整路徑，例如 reports/2026/q1.pdf
PrefixKey 的前段。S3 沒有真正的資料夾，「資料夾」只是 UI 依 / 做的視覺分組
Bucket 名稱的硬規則（考試會考）：
  • 全球唯一——別人用過的名字你不能用
  • 3–63 個字元，只能小寫字母、數字、連字號、句點
  • 不能用底線、不能大寫、不能以連字號開頭或結尾
  • 不能長得像 IP 位址（192.168.1.1 這種）
  • 名稱建立後不能改，要改只能建新的搬過去
實務建議加上帳號 ID 或公司前綴避免撞名：mycompany-prod-reports-123456789012
S3 是 region 級服務，但名稱是全球唯一。資料實際存在你建立時選的 region，不會自己跑到別的地方。名稱全球唯一是因為 S3 支援用網域名稱存取（bucket.s3.amazonaws.com）。
# 建立 bucket（東京區要指定 LocationConstraint）
$ aws s3api create-bucket \
    --bucket mycompany-reports-123456789012 \
    --region ap-northeast-1 \
    --create-bucket-configuration LocationConstraint=ap-northeast-1

# 高階指令（s3 vs s3api 的差別見下方）
$ aws s3 mb s3://mycompany-reports-123456789012 --region ap-northeast-1

# 上傳、下載、同步
$ aws s3 cp report.pdf s3://mycompany-reports/2026/q1/
$ aws s3 sync ./local-dir s3://mycompany-reports/backup/ --delete
$ aws s3 ls s3://mycompany-reports/2026/ --recursive --human-readable --summarize
aws s3 和 aws s3api 差在哪？
s3 是高階指令（cp、sync、mv、rm），像 Linux 檔案操作，會自動處理分段上傳與平行處理。
s3api 是低階 API 對應，一個指令對一個 API 呼叫，能做細部設定（版本控制、政策、生命週期）。
日常搬檔案用 s3，設定用 s3api。
sync --delete 會刪掉目的地多出來的檔案。方向寫反（把空目錄同步到 bucket）就等於清空整個 bucket。

執行前務必先加 --dryrun 看它打算做什麼： 
$ aws s3 sync ./local s3://bucket/ --delete --dryrun

2. 八種儲存類別與選型

類別可用性最短計費取回費取回時間價格/GB/月
Standard99.99%—無即時US$0.025
Intelligent-Tiering99.9%—無即時0.025 起 + 監控費
Standard-IA99.9%30 天US$0.01/GB即時US$0.0138
One Zone-IA99.5%30 天US$0.01/GB即時US$0.011
Glacier Instant99.9%90 天US$0.03/GB即時US$0.005
Glacier Flexible99.99%90 天依速度1 分鐘–12 小時US$0.0045
Glacier Deep Archive99.99%180 天較高12–48 小時US$0.002
Express One Zone99.95%1 小時無個位數毫秒US$0.16
三個最容易在考試和帳單上踩雷的點：
  1. 耐久性全部都是 99.999999999%（11 個 9），差別在可用性不是耐久性。考題問「哪個類別耐久性最高」是陷阱——都一樣。
  2. One Zone-IA 只存在一個 AZ。那個 AZ 毀了資料就沒了。只放「可以重新產生」的資料（縮圖、轉檔快取）。
  3. 最短計費天數是真的會收費。放進 Standard-IA 第 3 天就刪，還是要付 30 天的錢。頻繁變動的檔案不要放 IA。
選型三個問題：

多久存取一次？ 每天 → Standard｜每月 → IA｜每年 → Glacier
需要多快拿到？ 即時 → Instant 以上｜可等幾小時 → Flexible/Deep
不知道存取模式？ → Intelligent-Tiering
Intelligent-Tiering 是最省心的選擇。AWS 自動依存取頻率搬層：30 天沒動 → IA、90 天 → Archive Instant、180 天 → Deep Archive。沒有取回費、沒有最短計費天數，只多一筆監控費（每 1000 個物件 US$0.0025）。

但小檔案不划算——128 KB 以下的物件不會被搬層，卻照樣收監控費。大量小檔案用 Standard 就好。
# 上傳時直接指定類別
$ aws s3 cp big.zip s3://my-bucket/ --storage-class GLACIER_IR

# 改變既有物件的類別（用 copy 覆蓋自己）
$ aws s3 cp s3://my-bucket/old.zip s3://my-bucket/old.zip \
    --storage-class DEEP_ARCHIVE --metadata-directive COPY

# 看目前各類別各佔多少（用 S3 Storage Lens 或 CloudWatch）
$ aws s3api list-objects-v2 --bucket my-bucket \
    --query 'Contents[].[Key,StorageClass,Size]' --output table
Glacier 類別要「還原」才能讀。Glacier Flexible 和 Deep Archive 的物件不能直接下載，要先發還原請求，等它變成暫時可讀： 
$ aws s3api restore-object --bucket my-bucket --key old.zip \
    --restore-request '{"Days":3,"GlacierJobParameters":{"Tier":"Standard"}}'

# 查還原進度
$ aws s3api head-object --bucket my-bucket --key old.zip --query Restore
Tier 有三種：Expedited（1–5 分鐘，貴）、Standard（3–5 小時）、Bulk（5–12 小時，最便宜）。Deep Archive 只有 Standard（12 小時）和 Bulk（48 小時）。

3. 生命週期：自動省錢

手動搬層不可能維護。生命週期規則讓 S3 自動依「物件建立幾天後」搬層或刪除。

$ cat > lifecycle.json <<'EOF'
{
  "Rules": [
    {
      "ID": "logs-tiering",
      "Status": "Enabled",
      "Filter": { "Prefix": "logs/" },
      "Transitions": [
        { "Days": 30,  "StorageClass": "STANDARD_IA" },
        { "Days": 90,  "StorageClass": "GLACIER_IR" },
        { "Days": 365, "StorageClass": "DEEP_ARCHIVE" }
      ],
      "Expiration": { "Days": 2555 }
    },
    {
      "ID": "cleanup-old-versions",
      "Status": "Enabled",
      "Filter": { "Prefix": "" },
      "NoncurrentVersionTransitions": [
        { "NoncurrentDays": 30, "StorageClass": "GLACIER_IR" }
      ],
      "NoncurrentVersionExpiration": { "NoncurrentDays": 90 }
    },
    {
      "ID": "abort-failed-uploads",
      "Status": "Enabled",
      "Filter": { "Prefix": "" },
      "AbortIncompleteMultipartUpload": { "DaysAfterInitiation": 7 }
    }
  ]
}
EOF

$ aws s3api put-bucket-lifecycle-configuration \
    --bucket my-bucket --lifecycle-configuration file://lifecycle.json

$ aws s3api get-bucket-lifecycle-configuration --bucket my-bucket
第三條規則（AbortIncompleteMultipartUpload）幾乎所有人都漏掉，而且它在偷你的錢。

分段上傳失敗時，已經傳上去的片段會一直留在 S3 並持續計費，但 aws s3 ls 完全看不到它們。有些帳號累積了幾 TB 的殭屍片段，付了好幾年的錢卻不知道。 
# 查有沒有殭屍片段（現在就去查一下）
$ aws s3api list-multipart-uploads --bucket my-bucket
每個 bucket 都應該加這條規則。
搬層本身要收費（每 1000 個物件的請求費）。
  • 轉到 IA / Glacier：每 1000 個物件約 US$0.01–0.05
  • 大量小檔案搬層可能比省下的錢還貴
經驗法則：物件小於 128 KB 不要設搬層規則。S3 也會自動忽略小於 128 KB 的物件不轉到 IA。

搬層方向的限制

Standard → IA → Glacier IR → Glacier Flexible → Deep Archive

只能往「更冷」的方向自動搬，不能反向。
要回到 Standard 只能手動 restore 或 copy。
實際效果算一次給你看：1 TB 的日誌資料
策略每月費用
全部放 Standard1024 × 0.025 = US$25.6
30 天後轉 IA、90 天後 Glacier IR、1 年後 Deep Archive
（假設穩定後 90% 在 Deep Archive）		約 US$3.5
省 86%，而且完全自動。設定一次，之後不用管。

4. 版本控制與 MFA Delete

版本控制讓每次覆蓋或刪除都保留舊版本。它是防止「誤刪」和「勒索病毒」最有效的機制。

$ aws s3api put-bucket-versioning \
    --bucket my-bucket --versioning-configuration Status=Enabled

$ aws s3api list-object-versions --bucket my-bucket --prefix reports/
版本控制有三個重要特性：
  1. 開啟後不能關閉，只能「暫停」（Suspended）。暫停後新物件不再產生版本，但舊版本仍然存在並持續計費
  2. 刪除不是真的刪除——會放一個 Delete Marker 在最上層，舊版本還在。刪掉 Delete Marker 檔案就「復活」了
  3. 每個版本都獨立計費。改一個 100 MB 的檔案 10 次 = 存了 1 GB
# 誤刪了？把 Delete Marker 刪掉就復原
$ aws s3api list-object-versions --bucket my-bucket --prefix important.xlsx \
    --query 'DeleteMarkers[?IsLatest==`true`].[Key,VersionId]' --output text

$ aws s3api delete-object --bucket my-bucket \
    --key important.xlsx --version-id 3HL4kqCxf3vjVBH40Nrjfkd

# 還原成某個舊版本（把它複製成最新版）
$ aws s3api copy-object --bucket my-bucket --key important.xlsx \
    --copy-source "my-bucket/important.xlsx?versionId=OLD_VERSION_ID"
版本控制 + 生命週期是標準組合。光開版本控制會讓費用不斷成長，一定要搭配 NoncurrentVersionExpiration 自動清掉舊版本（例如保留 90 天）。上一節的第二條規則就是做這件事。

MFA Delete：最高等級的保護

# 注意：只能用 root 帳號設定，而且必須用長期憑證（不能用 AssumeRole）
$ aws s3api put-bucket-versioning --bucket my-bucket \
    --versioning-configuration Status=Enabled,MFADelete=Enabled \
    --mfa "arn:aws:iam::123456789012:mfa/root-account-mfa-device 123456"
MFA Delete 的限制很嚴格：
  • 只有 root 帳號能開啟或關閉
  • 必須用 CLI（主控台做不到）
  • 之後每次刪除版本或關閉版本控制都要提供 MFA 碼
  • 不能用臨時憑證（AssumeRole 出來的）
因為太麻煩，實務上多數公司改用 Object Lock（第 10 節）或 SCP 禁止刪除來達到類似效果。

5. 安全：四道鎖

S3 資料外洩是雲端最常見的事故類型。Capital One、Verizon、Accenture、多家醫療機構都發生過。原因幾乎都一樣：bucket 被設成公開，或 bucket policy 寫錯。
層級機制作用
1Block Public Access總開關，蓋過所有其他設定
2Bucket Policy資源型政策，可跨帳號
3IAM Policy身分型政策
4ACL舊機制，AWS 現在建議停用

第一道：Block Public Access（一定要開）

# 帳號層級一次擋掉全部（最強的保護）
$ aws s3control put-public-access-block \
    --account-id 123456789012 \
    --public-access-block-configuration \
      BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true

# 單一 bucket
$ aws s3api put-public-access-block --bucket my-bucket \
    --public-access-block-configuration \
      BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true
設定擋什麼
BlockPublicAcls禁止新增公開的 ACL
IgnorePublicAcls忽略既有的公開 ACL
BlockPublicPolicy禁止新增公開的 bucket policy
RestrictPublicBuckets既有公開政策只對本帳號和 AWS 服務生效
2023 年起 AWS 新建的 bucket 預設就開啟全部四項，而且預設停用 ACL。但舊 bucket 不受影響——去把每個舊 bucket 都檢查一遍。 
# 找出沒有完整封鎖公開存取的 bucket
$ for b in $(aws s3api list-buckets --query 'Buckets[].Name' --output text); do
    cfg=$(aws s3api get-public-access-block --bucket "$b" \
          --query 'PublicAccessBlockConfiguration' --output json 2>/dev/null || echo "NONE")
    echo "$b : $cfg"
  done

第二道：Bucket Policy 常用範本

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyInsecureTransport",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:*",
      "Resource": ["arn:aws:s3:::my-bucket", "arn:aws:s3:::my-bucket/*"],
      "Condition": { "Bool": { "aws:SecureTransport": "false" } }
    },
    {
      "Sid": "DenyUnencryptedUpload",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:PutObject",
      "Resource": "arn:aws:s3:::my-bucket/*",
      "Condition": {
        "StringNotEquals": { "s3:x-amz-server-side-encryption": "aws:kms" }
      }
    },
    {
      "Sid": "OnlyFromOurVpcEndpoint",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::my-bucket/*",
      "Condition": {
        "StringNotEquals": { "aws:SourceVpce": "vpce-0abc123def456" }
      }
    }
  ]
}
寫 "Principal": "*" 加 "Effect": "Deny" 是安全的；寫 "Effect": "Allow" 就是把 bucket 公開給全世界。一個字之差，結果天差地遠。

套用政策前一定要用 Access Analyzer 檢查： 
$ aws accessanalyzer validate-policy \
    --policy-document file://bucket-policy.json --policy-type RESOURCE_POLICY
要對外提供檔案，不要把 bucket 公開——用這三種方式：
  1. CloudFront + OAC（Origin Access Control）——bucket 保持私有，只有 CloudFront 讀得到。對外網站的標準做法
  2. Presigned URL——產生一個有時效的連結，給特定的人下載
  3. S3 Access Points——為不同用途建立不同的存取端點與政策
# Presigned URL：15 分鐘後失效
$ aws s3 presign s3://my-bucket/report.pdf --expires-in 900
https://my-bucket.s3.ap-northeast-1.amazonaws.com/report.pdf?X-Amz-Algorithm=...

# 上傳用的 presigned URL（讓外部使用者直接傳到 S3，不經過你的伺服器）
$ aws s3 presign s3://my-bucket/uploads/file.zip --expires-in 3600
Presigned URL 的權限來自「產生它的那個身分」。如果用 root 或 admin 產生，那個連結就有 admin 的權限範圍。而且URL 的有效期不能超過產生它的憑證有效期——用臨時憑證產生的 presigned URL，憑證過期它也跟著失效。

6. 加密的四種方式

方式金鑰誰管加解密誰做費用適合
SSE-S3AWSAWS免費預設，多數情況夠用
SSE-KMS你（在 KMS）AWSKMS 金鑰 US$1/月 + 請求費需要稽核與權限控制
DSSE-KMS你AWS（加密兩層）較貴極高合規要求
SSE-C你自己AWS免費金鑰絕不能給 AWS
2023 年起 S3 對所有新物件預設啟用 SSE-S3。也就是說「有沒有加密」已經不是問題，問題變成「要不要用自己管的金鑰」。
# 設定 bucket 預設加密為 KMS
$ aws s3api put-bucket-encryption --bucket my-bucket \
    --server-side-encryption-configuration '{
  "Rules": [{
    "ApplyServerSideEncryptionByDefault": {
      "SSEAlgorithm": "aws:kms",
      "KMSMasterKeyID": "arn:aws:kms:ap-northeast-1:123456789012:key/xxx"
    },
    "BucketKeyEnabled": true
  }]
}'
BucketKeyEnabled: true 一定要開，它能省 99% 的 KMS 費用。

沒開的話，每一個物件的每一次讀寫都要呼叫一次 KMS（每萬次 US$0.03）。一天讀 1000 萬次 = 每天 US$30 = 每月 US$900。

開啟 Bucket Key 之後，S3 在 bucket 層級快取一把金鑰，KMS 呼叫次數降到原本的 1%。這是純粹的省錢，沒有任何安全性損失。
用 SSE-KMS 時，光有 S3 權限不夠。使用者還必須有 KMS key 的 kms:Decrypt 權限，否則會拿到 AccessDenied 而且錯誤訊息不會說是 KMS 的問題。

「IAM 明明給了 s3:GetObject 卻讀不到」→ 十之八九是 KMS key policy 沒給權限。這也是第 01 章「有 Admin 卻做不到」的其中一種情況。 
# 檢查某個 bucket 的加密設定
$ aws s3api get-bucket-encryption --bucket my-bucket

# 找出未加密的物件（用 S3 Inventory 或逐一檢查）
$ aws s3api head-object --bucket my-bucket --key file.pdf \
    --query '[ServerSideEncryption,SSEKMSKeyId]'

7. 效能優化與大檔上傳

指標數值
每個 prefix 每秒 寫入3,500 次 PUT/COPY/POST/DELETE
每個 prefix 每秒 讀取5,500 次 GET/HEAD
prefix 數量無上限
要更高吞吐量就「分散 prefix」。
❌ logs/2026-08-05-001.log　（全部同一個 prefix）
✅ logs/a1/2026-08-05-001.log
✅ logs/b7/2026-08-05-002.log

10 個 prefix → 每秒 35,000 次寫入
注意：2018 年後 S3 已經自動處理大部分的分區，一般用途不需要刻意做。只有在單一 prefix 真的撞到 3500/5500 上限（會收到 503 SlowDown）時才需要。

分段上傳（Multipart Upload）

檔案大小做法
< 100 MB單次 PUT 就好
100 MB – 5 GB建議用分段上傳
> 5 GB必須用分段上傳（單次 PUT 上限就是 5 GB）
# CLI 會自動分段，但可以調參數加速
$ aws configure set default.s3.multipart_threshold 64MB
$ aws configure set default.s3.multipart_chunksize 16MB
$ aws configure set default.s3.max_concurrent_requests 20
$ aws configure set default.s3.max_bandwidth 100MB/s

# 大量小檔案：用 sync 而不是逐個 cp
$ aws s3 sync ./thousands-of-files s3://my-bucket/data/
分段上傳的三個好處：
  1. 平行傳輸——多個片段同時傳，速度快很多
  2. 可續傳——某個片段失敗只要重傳那一段，不用整個重來
  3. 邊產生邊上傳——不需要先知道檔案總大小
但記得設 AbortIncompleteMultipartUpload 生命週期規則（第 3 節），否則失敗的片段會一直計費。

Transfer Acceleration：跨洲上傳加速

$ aws s3api put-bucket-accelerate-configuration \
    --bucket my-bucket --accelerate-configuration Status=Enabled

# 用加速端點上傳
$ aws s3 cp big.zip s3://my-bucket/ --endpoint-url https://s3-accelerate.amazonaws.com
Transfer Acceleration 每 GB 加收 US$0.04–0.08。它走 CloudFront 的邊緣節點進 AWS 骨幹網路，只有跨洲時才有明顯效果（台灣傳東京幾乎沒差，台灣傳美東才有感）。
AWS 有個線上測速工具可以先測「你的位置到各 region 加速多少」，划算再開。

8. 跨區複製與災難復原

CRR（跨區複製）SRR（同區複製）
目的災難復原、降低跨洲延遲、合規日誌集中、正式/測試環境同步、跨帳號備份
目標 region不同相同
# 前提：來源和目標 bucket 都必須開啟版本控制
$ aws s3api put-bucket-versioning --bucket src-bucket \
    --versioning-configuration Status=Enabled
$ aws s3api put-bucket-versioning --bucket dst-bucket-osaka \
    --versioning-configuration Status=Enabled

$ cat > replication.json <<'EOF'
{
  "Role": "arn:aws:iam::123456789012:role/s3-replication-role",
  "Rules": [{
    "ID": "dr-to-osaka",
    "Status": "Enabled",
    "Priority": 1,
    "Filter": { "Prefix": "critical/" },

    "Destination": {
      "Bucket": "arn:aws:s3:::dst-bucket-osaka",

$ aws s3api put-bucket-replication \
    --bucket src-bucket --replication-configuration file://replication.json
複製的六個限制（考試常考）：
  1. 兩邊都必須開版本控制
  2. 只複製「設定規則之後」的新物件。既有物件要另外用 S3 Batch Replication 補
  3. 不會鏈式複製——A→B、B→C，A 的物件不會到 C
  4. 預設不複製刪除動作，要明確開 DeleteMarkerReplication
  5. 永遠不複製「指定版本 ID 的刪除」——這是防止惡意刪除擴散的設計
  6. 需要一個有適當權限的 IAM Role
跨區複製要付：目標 bucket 的儲存費 + 跨區傳輸費（每 GB 約 US$0.09） + 複製請求費。
開 RTC（Replication Time Control，15 分鐘 SLA）還要額外每 GB US$0.015。

1 TB 的資料複製到大阪：一次性傳輸約 US$92，之後每月多付約 US$14 的儲存費。只複製真正關鍵的 prefix，不要整個 bucket 複製。
複製也能用來做「跨帳號防勒索備份」。把資料 SRR 或 CRR 到另一個帳號的 bucket，並在那個帳號啟用 Object Lock。就算主帳號被完全接管，攻擊者也刪不掉備份帳號的資料。這是目前對抗勒索軟體最有效的雲端架構。

9. 靜態網站 + CloudFront

不要用 S3 的「靜態網站託管」直接對外。它只支援 HTTP 不支援 HTTPS，而且需要把 bucket 設成公開。

正確做法：bucket 保持完全私有，前面掛 CloudFront + OAC。 
# ═══ 步驟 1：bucket 保持私有，開啟全部 Block Public Access ═══
$ aws s3api put-public-access-block --bucket my-site \
    --public-access-block-configuration \
      BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true

# ═══ 步驟 2：建立 Origin Access Control ═══
$ OAC_ID=$(aws cloudfront create-origin-access-control \
    --origin-access-control-config '{
      "Name": "my-site-oac",
      "OriginAccessControlOriginType": "s3",
      "SigningBehavior": "always",
      "SigningProtocol": "sigv4"
    }' --query 'OriginAccessControl.Id' --output text)

# ═══ 步驟 3：建立 CloudFront distribution（略，用 JSON 設定檔）═══

# ═══ 步驟 4：bucket policy 只允許這個 distribution ═══
$ cat > oac-policy.json <<'EOF'
{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "AllowCloudFrontOAC",
    "Effect": "Allow",
    "Principal": { "Service": "cloudfront.amazonaws.com" },
    "Action": "s3:GetObject",
    "Resource": "arn:aws:s3:::my-site/*",
    "Condition": {
      "StringEquals": {
        "AWS:SourceArn": "arn:aws:cloudfront::123456789012:distribution/E1ABCDEF"
      }
    }
  }]
}
EOF
$ aws s3api put-bucket-policy --bucket my-site --policy file://oac-policy.json
CloudFront + OAC 的好處：
  • 免費的 HTTPS（ACM 憑證在 CloudFront 用是免費的）
  • 全球 CDN 快取——使用者從最近的節點拿檔案
  • bucket 完全私有，不可能被直接存取
  • 可以掛 WAF 擋攻擊
  • 對外流量費比 S3 直出便宜（CloudFront US$0.114/GB vs S3 US$0.114/GB，但 CloudFront 有免費額度且快取命中不算源站流量）
OAC 取代了舊的 OAI（Origin Access Identity）。新專案一律用 OAC——它支援 SSE-KMS 加密的 bucket、支援所有 HTTP 方法、支援所有 region。OAI 已經是舊技術，考試可能兩個都問，但實務上用 OAC。
# 更新內容後要讓 CloudFront 快取失效
$ aws cloudfront create-invalidation \
    --distribution-id E1ABCDEF --paths "/*"
CloudFront 失效每月前 1000 個路徑免費，之後每個 US$0.005。
用 "/*" 只算 一個路徑，所以整站失效很便宜。
但更好的做法是檔名帶版本雜湊（app.a3f9b2.js），這樣根本不需要失效，也能設很長的快取時間。

10. Object Lock 與合規

Object Lock 提供 WORM（Write Once Read Many）——寫進去之後在期限內任何人都刪不掉，包含 root 帳號。

模式誰能提前解除用途
Governance有 s3:BypassGovernanceRetention 權限的人內部保護，防誤刪
Compliance沒有人，連 root 都不行法規要求（金融、醫療）
Legal Hold有權限的人可隨時移除訴訟期間凍結證據，無到期日
Compliance 模式是不可逆的。設定 7 年保留期之後，那筆資料就是會佔用 7 年的儲存空間並收費，AWS 支援也無法幫你刪除。

這牽涉到實際的長期費用承諾——導入前務必確認法規要求的年限，並且先在測試 bucket 用短期限（例如 1 天）試過。設錯年限沒有後悔藥。 
# Object Lock 只能在「建立 bucket 時」啟用，之後不能加
$ aws s3api create-bucket --bucket compliance-archive \
    --region ap-northeast-1 \
    --create-bucket-configuration LocationConstraint=ap-northeast-1 \
    --object-lock-enabled-for-bucket

# 設定預設保留規則
$ aws s3api put-object-lock-configuration --bucket compliance-archive \
    --object-lock-configuration '{
      "ObjectLockEnabled": "Enabled",
      "Rule": { "DefaultRetention": { "Mode": "GOVERNANCE", "Days": 2555 } }
    }'

# 對單一物件加 Legal Hold
$ aws s3api put-object-legal-hold --bucket compliance-archive \
    --key evidence.zip --legal-hold Status=ON
防勒索軟體的完整架構：
  1. 備份資料複製到另一個 AWS 帳號（CRR 跨帳號）
  2. 那個帳號的 bucket 啟用 Object Lock（Compliance 模式）
  3. 備份帳號用 SCP 禁止關閉 Object Lock 和版本控制
  4. 主帳號沒有備份帳號的任何寫入權限
這樣就算攻擊者拿到主帳號的 root 權限，也無法碰到備份。

11. 費用結構與省錢清單

費用項目東京區價格備註
儲存US$0.025/GB/月（Standard）依類別不同
PUT/POST/LIST 請求US$0.0047 / 1000 次寫入比讀取貴 10 倍
GET 請求US$0.00037 / 1000 次
對外傳輸US$0.114/GB通常是最大宗，前 100 GB/月免費
同 region 傳到 EC2免費前提是走 VPC Endpoint 或同 region
跨 region 傳輸US$0.09/GB
生命週期搬層US$0.01–0.05 / 1000 物件小檔案要注意
最常見的 S3 帳單意外，按發生頻率排序：
  1. 對外流量——網站圖片直接從 S3 出去，沒放 CloudFront
  2. 殭屍分段上傳——看不見但一直收費
  3. 版本控制沒配生命週期——舊版本無限累積
  4. 大量小檔案的請求費——存 1 億個 1 KB 的檔案，請求費遠超儲存費
  5. IA 類別放了頻繁存取的資料——取回費把省下的儲存費吃光
  6. SSE-KMS 沒開 Bucket Key——KMS 請求費暴增

盤點腳本

#!/bin/bash
echo "=== ① 沒有生命週期規則的 bucket ==="
for b in $(aws s3api list-buckets --query 'Buckets[].Name' --output text); do
  if ! aws s3api get-bucket-lifecycle-configuration --bucket "$b" >/dev/null 2>&1; then
    echo "  $b"
  fi
done

echo "=== ② 有殭屍分段上傳的 bucket ==="
for b in $(aws s3api list-buckets --query 'Buckets[].Name' --output text); do
  n=$(aws s3api list-multipart-uploads --bucket "$b" \
      --query 'length(Uploads)' --output text 2>/dev/null)
  [ "$n" != "None" ] && [ "$n" != "0" ] && echo "  $b : $n 個未完成上傳"
done

echo "=== ③ 開了版本控制但沒有 NoncurrentVersionExpiration ==="
for b in $(aws s3api list-buckets --query 'Buckets[].Name' --output text); do
  v=$(aws s3api get-bucket-versioning --bucket "$b" --query Status --output text 2>/dev/null)
  if [ "$v" == "Enabled" ]; then
    lc=$(aws s3api get-bucket-lifecycle-configuration --bucket "$b" 2>/dev/null)
    echo "$lc" | grep -q NoncurrentVersionExpiration || echo "  $b"
  fi
done

echo "=== ④ 用 KMS 但沒開 Bucket Key ==="
for b in $(aws s3api list-buckets --query 'Buckets[].Name' --output text); do
  enc=$(aws s3api get-bucket-encryption --bucket "$b" 2>/dev/null)
  echo "$enc" | grep -q '"aws:kms"' && ! echo "$enc" | grep -q '"BucketKeyEnabled": true' \
    && echo "  $b"
done

12. S3 進階功能（存取點與 Select）

前面十一節講的是「怎麼把東西放進 S3、放得安全又便宜」。這一節補上四個考試會考、但很多人沒用過的功能。

S3 Select：把過濾工作丟給 S3 做

傳統做法像把整箱資料搬回家再挑；S3 Select 像請倉庫幫你挑好再寄出來——傳輸量與運算量都少很多。
不用 S3 Select：下載 5 GB CSV → 在 EC2 上過濾 → 只需要其中 50 MB
傳輸 5 GB + EC2 運算時間

用 S3 Select：送一句 SQL 過去 → S3 只回傳符合的 50 MB
傳輸 50 MB，速度可快數倍
# 直接對 S3 上的 CSV 下 SQL，只取需要的欄位與列
$ aws s3api select-object-content     --bucket my-data --key sales/2026.csv     --expression "SELECT s.region, s.amount FROM S3Object s WHERE s.amount > 10000"     --expression-type SQL     --input-serialization '{"CSV":{"FileHeaderInfo":"USE"},"CompressionType":"GZIP"}'     --output-serialization '{"CSV":{}}'     result.csv
S3 Select 與 Athena 的分界（考題會這樣問）：
S3 Select＝單一物件的簡單過濾，程式碼裡呼叫，沒有資料表概念。
Athena＝跨大量物件的完整 SQL 分析，有資料表、可 JOIN、可搭 Glue Catalog。
題目說「應用程式只需要大檔案裡的一小部分欄位、想減少傳輸量」→ S3 Select；說「對整個資料湖下 SQL 分析」→ Athena。

Access Point：一個用途一個門

一個 bucket 被十個團隊共用時，bucket policy 會長到沒有人看得懂，而且改一次影響所有人。Access Point 讓每個用途有自己的端點與自己的政策。

一般 Access Point每個存取點有獨立的 DNS 名稱與政策，可限定只能存取某個前綴。bucket policy 只要授權給存取點即可。
VPC-only Access Point建立時指定 VPC，該存取點只能從那個 VPC 使用——比在 bucket policy 裡寫一堆條件乾淨得多。
Multi-Region Access Point一個全球端點對應多個區域的 bucket，自動導向延遲最低的那個，並走 AWS 全球網路加速。
Object Lambda Access Point讀取時即時轉換物件內容（去識別化、加浮水印、格式轉換），原始物件不動。
Object Lambda 的經典考題

「同一份客戶資料，分析團隊要看去識別化版本，稽核團隊要看完整版本，但不想儲存兩份。」
→ S3 Object Lambda Access Point：分析團隊走 Lambda 存取點（讀取時遮蔽個資），稽核團隊走一般存取點。
錯誤選項通常是「複製一份遮蔽過的資料到另一個 bucket」——那會有兩份資料要同步、要管理、要付錢。

Requester Pays：讓下載方付錢

開啟後，下載方要用自己的 AWS 帳號並在請求中帶上 x-amz-request-payer，請求費與傳出費就算在他們頭上，你只付儲存費。
考題關鍵字：「公開／共享大型資料集」＋「不想負擔龐大的資料傳出費用」。
限制：請求者必須是已驗證的 AWS 身分，所以匿名存取不能用。
$ aws s3api put-bucket-request-payment --bucket public-dataset     --request-payment-configuration Payer=Requester

# 下載方要明確表示「我付錢」，否則會被拒絕
$ aws s3 cp s3://public-dataset/big.parquet . --request-payer requester

Batch Operations：對幾百萬個物件做同一件事

「要把 5,000 萬個既有物件全部加上標籤／改儲存類別／套用 Object Lock／呼叫 Lambda 處理」——寫腳本一個一個 API 呼叫會跑到天荒地老。
正解是 S3 Batch Operations：吃一份 S3 Inventory 清單當輸入，由 AWS 平行執行，並產生完成報告。
注意跟生命週期規則的分界：生命週期是「以後符合條件的自動處理」，Batch Operations 是「現在把既有的一次處理完」。

13. CloudFront 內容保護與邊緣運算

第 9 節用 OAC 把 bucket 鎖起來了，但 CloudFront 的網址本身還是公開的。付費影片、私人相簿這類內容還需要下一層保護。

Signed URL vs Signed Cookie

Signed URL（簽章網址）Signed Cookie（簽章 Cookie）
保護範圍單一檔案多個檔案（整個路徑）
典型情境單支影片下載連結、一次性檔案整套線上課程、會員專區所有內容
要改用戶端嗎要改網址網址不用改，瀏覽器自動帶 Cookie
可設定到期時間、可用 IP 範圍、生效時間
一句話判斷：要保護「一個」檔案 → Signed URL；要保護「一整個目錄／一系列」檔案而且不想改每個網址 → Signed Cookie。
這組二選一在 SAA 出現頻率很高，判斷點就是檔案數量。
S3 預簽章網址（Presigned URL）不一樣。它是直接對 S3 產生的臨時網址，繞過 CloudFront。
要走 CDN 快取就用 CloudFront Signed URL／Cookie；只是讓某人臨時上傳或下載一個物件（例如使用者上傳頭像）就用 S3 預簽章網址。題目提到「使用者直接上傳到 S3、不經過我的伺服器」→ S3 預簽章網址。

地理限制（Geo Restriction）

CloudFront 內建依國家的允許／封鎖清單，適合版權授權區域限制。
需要更細的規則（依國家 + 路徑 + 速率）就用 WAF 的地理比對規則。考題問「僅限特定國家觀看」→ CloudFront Geo Restriction 就夠了。

邊緣運算：CloudFront Functions vs Lambda@Edge

CloudFront FunctionsLambda@Edge
執行位置邊緣站點（數量最多，離使用者最近）區域邊緣快取
執行時間次毫秒級可達數秒
語言JavaScript（受限子集）Node.js / Python（完整）
能不能連網路不能可以（可呼叫其他服務、讀 S3）
能不能讀請求主體不能可以
觸發時機Viewer Request / ResponseViewer 與 Origin Request / Response 四種
成本明顯較便宜較貴
典型用途標頭改寫、URL 重寫、快取鍵正規化、簡單的重新導向依裝置回傳不同影像、A/B 測試、呼叫 API 做驗證
判斷順序：先問「需要網路存取或讀請求主體嗎？」
需要 → Lambda@Edge（只有它做得到）。
不需要，只是改標頭或網址 → CloudFront Functions（更快、更便宜）。
題目強調「極高 QPS」「最低延遲」「最低成本」而動作又很簡單 → 一定是 CloudFront Functions。
Lambda@Edge 有幾個實務限制要記：函式必須建在 us-east-1（維吉尼亞北部）才能關聯到 CloudFront，而且不支援環境變數——組態要寫在程式碼裡或去 Parameter Store 抓。這兩點常出現在「為什麼部署失敗」的題目裡。

完整實作 Lab：安全的資料湖 + 靜態網站

約 90 分鐘。

S3 免費方案每月有 5 GB 標準儲存、20,000 次 GET、2,000 次 PUT。
這個 Lab 用到的資料量很小，費用接近 0。CloudFront 免費方案每月有 1 TB 傳輸。
唯一要注意：不要啟用 Object Lock Compliance 模式做實驗——那會鎖住資料無法刪除。要試就用 Governance 模式 + 1 天。

階段一：建立與加固

  1. 建立 bucket 你的名字-lab-YYYYMMDD，確認四項 Block Public Access 全開
  2. 開啟版本控制
  3. 設定預設加密為 SSE-KMS，並開啟 BucketKeyEnabled
  4. 套用 bucket policy：拒絕非 HTTPS、拒絕未加密上傳
  5. 用 accessanalyzer validate-policy 檢查政策沒有問題
  6. 用 HTTP 嘗試存取 → 應該被拒絕

階段二：生命週期與版本

  1. 設定三條生命週期規則：搬層、清理舊版本、中止未完成分段上傳
  2. 上傳一個檔案，修改後再上傳三次，用 list-object-versions 看到 4 個版本
  3. 刪除該檔案，確認出現 Delete Marker 且舊版本仍在
  4. 刪掉 Delete Marker，確認檔案復活
  5. 把某個舊版本 copy 成最新版，完成「還原到指定版本」

階段三：儲存類別與還原

  1. 上傳一個檔案指定 GLACIER 類別
  2. 嘗試直接 aws s3 cp 下載 → 應該失敗
  3. 發 restore-object 請求（Bulk tier），用 head-object 觀察 Restore 狀態
  4. 上傳一個檔案到 Intelligent-Tiering，比較兩者的差異

階段四：靜態網站 + CloudFront

  1. 建立第二個 bucket 放靜態網站檔案（保持私有）
  2. 建立 Origin Access Control
  3. 建立 CloudFront distribution，origin 指向該 bucket
  4. 套用只允許該 distribution 的 bucket policy
  5. 用 CloudFront 網域開啟網站 → 成功且是 HTTPS
  6. 直接用 S3 URL 開啟 → 應該 403
  7. 改一個檔案，create-invalidation 讓快取失效

階段五：Presigned URL 與盤點

  1. 產生一個 60 秒有效的 presigned URL，測試過期後失效
  2. 執行第 11 節的盤點腳本，檢查自己帳號的所有 bucket
  3. 開啟 S3 Storage Lens 預設儀表板看一眼

驗收清單

  • get-public-access-block 四項全是 true
  • 用 http://（非 https）存取 → AccessDenied
  • 不帶加密標頭上傳 → AccessDenied
  • get-bucket-encryption 顯示 BucketKeyEnabled: true
  • 刪除檔案後 list-object-versions 看得到 DeleteMarkers 且 Versions 還在
  • Glacier 物件直接下載失敗，restore 後成功
  • CloudFront 網域可開，S3 直連 403
  • presigned URL 過期後回傳 AccessDenied

$ aws cloudfront delete-distribution --id E1ABCDEF --if-match ETAG

加碼挑戰

  1. 算一筆帳：1 TB 資料、每月對外傳 500 GB。「S3 直出」與「CloudFront」哪個便宜？差多少？
  2. 設定 SRR 同區複製到另一個 bucket，觀察「設定前」的既有物件不會被複製。
  3. 建一個開啟 Object Lock Governance 模式（1 天）的 bucket，上傳檔案後嘗試刪除，觀察錯誤訊息。
  4. 寫一個 Lambda，S3 有新物件時自動產生縮圖存回另一個 prefix（S3 Event Notification）。
  5. 用 S3 Inventory 產生一份完整的物件清單報表，找出所有未加密的物件。

本章重點回顧

  • Bucket 名稱全球唯一、只能小寫、建好不能改
  • 所有儲存類別的耐久性都是 11 個 9，差別在可用性與取回成本
  • One Zone-IA 只有一個 AZ；IA 有 30 天、Glacier 90 天、Deep Archive 180 天最短計費
  • 不確定存取模式就用 Intelligent-Tiering，但小檔案不划算
  • 每個 bucket 都要加 AbortIncompleteMultipartUpload 規則——殭屍片段看不見卻一直收費
  • 版本控制開了不能關，一定要配 NoncurrentVersionExpiration
  • 刪除只是放 Delete Marker，刪掉它就復原
  • Block Public Access 四項全開；對外提供檔案用 CloudFront + OAC 或 Presigned URL
  • SSE-KMS 一定要開 BucketKeyEnabled，省 99% KMS 費用
  • 「有 s3 權限卻讀不到」→ 檢查 KMS key policy
  • 複製只複製設定後的新物件、不會鏈式複製、兩邊都要開版本控制
  • Object Lock Compliance 模式不可逆，連 root 都刪不掉——設定前務必確認年限
  • 最大的費用通常是對外流量，其次是殭屍片段與失控的版本
