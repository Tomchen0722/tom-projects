1. 先建立地圖：資料的一生

把資料想成自來水：取水（收集）→ 輸水管（傳輸）→ 水庫（儲存）→ 淨水廠（處理）→ 水龍頭（分析與呈現）。AWS 的分析服務就是分別負責這五段,你只要知道每個服務站在哪一段,選型題就答得出來。
① 收集 Ingest Kinesis Data Streams / Firehose ← 即時串流 Snowball / DataSync / DMS ← 批次搬移 ② 儲存 Store S3（資料湖的地基） / Redshift（資料倉儲） ③ 處理 Process Glue（ETL）/ EMR（Spark、Hadoop）/ Lambda ④ 分析 Analyze Athena（查 S3）/ Redshift（查倉儲）/ OpenSearch（查日誌） ⑤ 呈現 Visualize QuickSight（BI 儀表板）
📋 考試的關鍵直覺:S3 是資料湖的中心。幾乎所有分析架構的題目,最後資料都會落在 S3,再由不同服務去查它。看到「最低成本」「不想管伺服器」的字眼,答案通常是 S3 + Athena 這組。

2. Kinesis 四兄弟:最容易混淆的一組

Kinesis 是一整個家族,名字很像但用途完全不同。考試每次都考,這張表要背熟:

服務做什麼資料保留誰來消費關鍵字
Data Streams
(KDS)		即時串流的「管道」,你自己寫程式讀取預設 24 小時
(最長 365 天)		自己寫 Consumer
(Lambda / KCL)		需要自訂處理、需要重播資料
Data Firehose全託管的「輸送帶」,自動送到目的地不保留
(直接送走)		AWS 自動送到
S3/Redshift/OpenSearch/Splunk		不想寫程式、近即時、自動轉檔
Data Analytics用 SQL 直接查串流中的資料—查詢結果再輸出串流上做即時 SQL 聚合
Video Streams把攝影機影像串流進 AWS可設定Rekognition Video、自訂 ML影像、監視器、電腦視覺
陷阱:Data Streams vs Firehose 怎麼選?
這是 SAA 最高頻的一題。三個判斷點:
① 題目說「near real-time(近即時,可接受 60 秒延遲)」→ Firehose
② 題目說「real-time(毫秒級)」或「需要重播/重新處理」→ Data Streams
③ 題目說「不想管理基礎設施」「自動送到 S3」→ Firehose

記憶法:Firehose 是「一條水管直接接到水塔」,你不能中途撈水;Data Streams 是「一條河」,你可以派很多人在不同位置舀水,而且水會停留一段時間。

Firehose 的加值功能(常考)

格式轉換寫入 S3 前自動轉成 Parquet / ORC 這類「欄式格式」,讓後續 Athena 查詢更快更便宜。
Lambda 轉換途中可呼叫 Lambda 做清洗、加欄位、過濾。
壓縮與加密GZIP/Snappy 壓縮,KMS 加密,減少儲存成本。
緩衝設定依「大小」或「時間」觸發寫出(例如 5 MB 或 60 秒,先到先送)。
💰 成本觀念:Firehose 按「送進去的資料量」計費,沒有預先配置的成本;Data Streams 傳統模式要自己配 Shard(分片),不管有沒有資料都在計費(On-Demand 模式則按量計費)。流量不穩定又想省錢 → Firehose 或 Data Streams On-Demand。

3. Athena:直接查 S3

Athena 像是「直接對著倉庫喊話問東西在哪」,不用先把貨搬到辦公室。資料留在 S3 原地不動,你用 SQL 直接查它。
特性說明
Serverless沒有伺服器要管,不用預先配置任何東西
計費方式按掃描的資料量計費(每 TB 計價)——這是所有優化的核心
資料來源S3(也可透過 Federated Query 查 RDS、DynamoDB 等)
底層引擎Presto / Trino,標準 SQL
Schema 來源Glue Data Catalog(表定義存在這裡)

降低 Athena 費用的四個手段(必考)

① 用欄式格式(Columnar) CSV/JSON → Parquet / ORC 只讀取需要的欄位,掃描量可降 80-90% ② 分割(Partition) s3://bucket/logs/year=2026/month=08/day=15/ 查特定日期時只掃該資料夾,不掃全部 ③ 壓縮(Compression) GZIP / Snappy → 檔案變小,掃描量變小 ④ 合併小檔案 大量的小檔案會拖慢查詢,合併成較大的檔案較有效率
陷阱:Athena 的成本題
題目常說「查詢費用太高,怎麼降低?」——標準答案幾乎都是「轉成 Parquet + 分割」。
注意:選項裡如果有「改用 Redshift」,通常是錯的,因為 Redshift 要一直開著、成本更高。Athena 貴在掃描量,不是貴在服務本身。

4. Redshift:資料倉儲

Redshift 是給「大量歷史資料做複雜分析」用的資料倉儲(OLAP),不是拿來當網站的資料庫(OLTP)。

OLTP線上交易處理。頻繁的小筆讀寫,例如「查這個會員的訂單」。→ RDS / DynamoDB
OLAP線上分析處理。少量但巨大的查詢,例如「過去三年各區域每月營收趨勢」。→ Redshift
功能說明考試關鍵字
欄式儲存按欄存放,分析型查詢只讀需要的欄位分析效能
MPP大規模平行處理,查詢分散到多個節點同時跑PB 級資料
Redshift Spectrum讓 Redshift 直接查 S3 上的資料,不用先載入倉儲 + 資料湖一起查
Concurrency Scaling查詢併發高時自動加算力,尖峰過後收回報表尖峰、很多人同時查
Redshift Serverless免管理叢集,按用量計費用量不固定、不想管容量
RA3 節點運算與儲存分離,可獨立擴充儲存資料成長快但算力夠用
陷阱:Spectrum vs Athena
兩者都能查 S3,差別在:
• Athena:完全 Serverless,適合臨時查詢、不需要有 Redshift 叢集
• Spectrum:需要有 Redshift 叢集,適合「倉儲裡的熱資料」要和「S3 上的冷資料」join 在一起查
題目出現「既有 Redshift 資料,又要關聯 S3 歷史資料」→ Spectrum。

5. EMR:託管的 Hadoop / Spark

EMR 像「租一整座工廠加現成的產線設備」。你要跑 Spark、Hadoop、Hive、HBase 這些開源大數據框架,但不想自己裝、自己調、自己修,就用 EMR。
節點類型角色能不能關掉
Master 主節點管理叢集、分派工作不能(關了叢集就掛)
Core 核心節點執行任務 + 存放 HDFS 資料可增減,但減少會影響資料
Task 任務節點只執行任務,不存資料可隨時增減 → 最適合用 Spot
✅ 成本優化標準答案:Master 和 Core 用 On-Demand(穩定),Task 節點用 Spot Instance(最高省 90%)。因為 Task 節點不存資料,被中斷也不會掉資料,重跑就好。這是 EMR 成本題的固定答案。
陷阱:EMR vs Glue 怎麼選?
• 題目說「要用 Spark / Hadoop / Hive / 現有的開源程式碼」「需要調整叢集參數」→ EMR
• 題目說「Serverless ETL」「不想管叢集」「只是做資料格式轉換與編目」→ Glue
Glue 底層其實也是 Spark,但你看不到叢集。要「控制權」選 EMR,要「省事」選 Glue。

6. Glue 與 Lake Formation

AWS Glue 的三個組件

Glue Crawler自動掃描 S3 上的資料,推斷欄位與型別,把表定義寫進 Data Catalog。
Glue Data Catalog中央的「資料目錄」,存放所有表的 Schema。Athena、Redshift Spectrum、EMR 都共用它。
Glue ETL JobServerless 的 Spark 作業,做清洗、轉檔、合併。可用 Python 或 Scala。
💡 Glue Data Catalog 是整個分析生態的「共用戶口名簿」。Crawler 登記完之後,Athena 就查得到、Spectrum 也查得到、EMR 也讀得到。考試看到「統一的中央 metadata 目錄」→ Glue Data Catalog。

AWS Lake Formation

Lake Formation 蓋在 Glue 之上,負責資料湖的權限管理。它最大的價值是提供「欄位級 / 列級」的細緻權限——例如讓行銷部門看得到訂單金額,但看不到客戶身分證字號。

陷阱:權限題選 Lake Formation 還是 IAM?
• 「誰可以存取這個 S3 bucket」→ IAM / Bucket Policy
• 「誰可以看到這張表的哪些欄位、哪些列」→ Lake Formation
題目出現「column-level / row-level security」「集中管理資料湖權限」→ Lake Formation。

7. OpenSearch 與 MSK

⚠️ 名稱已更新:白皮書寫的是「Amazon Elasticsearch Service」,AWS 已在 2021 年將它更名為 Amazon OpenSearch Service。現行考試與主控台都用 OpenSearch 這個名字,看到 Elasticsearch 請自動對應過去。
服務本質典型用途考試關鍵字
OpenSearch Service託管的搜尋與日誌分析引擎日誌分析、全文檢索、應用監控、點擊流分析全文搜尋、日誌即時查詢、Kibana/Dashboards
MSK
(Managed Streaming for Kafka)		託管的 Apache Kafka已有 Kafka 應用要搬上雲、需要 Kafka API題目直接出現 Kafka 這個字
陷阱:MSK vs Kinesis Data Streams
兩者功能高度重疊,判斷點只有一個:
題目有沒有提到「既有的 Kafka 應用程式」或「要用 Kafka API」?
有 → MSK(不用改程式碼就能搬上雲)
沒有,只是要做串流 → Kinesis Data Streams(更 AWS 原生、更省事)

另一個小差異:Kafka 的訊息大小上限預設 1 MB 可調大;Kinesis 單筆上限 1 MB 固定。題目提到「單筆訊息很大」時要注意。

8. QuickSight:把結果變成圖

QuickSight 是 AWS 的 BI(商業智慧)工具,負責最後一哩路——把資料變成老闆看得懂的儀表板。

SPICE 引擎記憶體內的快取引擎。把資料先載進 SPICE,查詢就不用每次打回源頭,速度快又省錢。
資料來源Athena、Redshift、RDS、S3、Aurora,也支援第三方與本地資料。
嵌入式儀表板可把儀表板嵌進自家應用,給客戶做自助分析。
權限控管支援列級安全性(RLS),不同使用者看到不同範圍的資料。
📋 考試看到「不想架 BI 伺服器」「把儀表板嵌入應用程式」「按用量付費的 BI」→ QuickSight。看到 SPICE 這個字,直接對應 QuickSight 的記憶體快取。

10. 考試陷阱整理

陷阱 1:「near real-time」是 Firehose 的暗號
只要題目寫「near real-time」,幾乎都是 Firehose(最短緩衝約 60 秒)。寫「real-time」「sub-second」才是 Data Streams。這一個字就決定答案。
陷阱 2:Athena 降成本 ≠ 換服務
Athena 查詢太貴,答案是「轉 Parquet + 分割 + 壓縮」,不是「改用 Redshift」或「加大機器」。Athena 沒有機器可以加。
陷阱 3:EMR 的 Spot 只能用在 Task 節點
Master 用 Spot = 叢集隨時可能整個掛掉;Core 用 Spot = HDFS 資料可能遺失。只有 Task 節點是安全的。
陷阱 4:Glue Data Catalog 是共用的
題目問「如何讓 Athena、EMR、Redshift Spectrum 用同一套表定義」→ Glue Data Catalog。不要選「各自建立 schema」。
陷阱 5:Kinesis Shard 與吞吐量
傳統(Provisioned)模式下,每個 Shard 寫入上限約 1 MB/秒 或 1,000 筆/秒,讀取約 2 MB/秒。題目給你流量要你算 Shard 數時,用寫入量 ÷ 1 MB 取進位。吞吐不夠的解法是增加 Shard,不是換服務。
陷阱 6:白皮書裡的舊服務名
這份 2020 年的白皮書提到 AWS Data Pipeline 與 Amazon Elastic Transcoder,兩者 AWS 均已停止接受新客戶/走向淘汰,現行考試不會要你選它們。資料搬移與排程請往 Glue / Step Functions / MWAA 方向想。
💡 一句話記憶法:
即時進來找 Kinesis,存起來放 S3,整理交給 Glue,臨時查用 Athena,大報表用 Redshift,跑開源用 EMR,找日誌用 OpenSearch,畫圖用 QuickSight。
