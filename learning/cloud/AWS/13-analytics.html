1. 大數據生命週期地圖：收集 ➔ 儲存 ➔ 處理 ➔ 分析 ➔ 呈現

把大數據想成大型現代水利系統：
• 取水收集 (Ingest)：暴雨湧入的水流（Kinesis Data Streams / MSK / IoT Core）。
• 大壩水庫 (Store)：儲存湖泊，也是整個架構的中心（Amazon S3 資料湖）。
• 沉澱濾淨 (Process)：濾掉雜質、去除泥沙（Glue ETL / EMR Spark / Lambda）。
• 專用蓄水池 (Warehouse)：提供給特定都市的高壓淨水供水（Redshift 資料倉儲）。
• 水龍頭取水 (Analyze)：隨時開水龍頭檢測水質（Athena SQL 隨選查詢）。
• 水情儀表板 (Visualize)：水庫水位監控圖表（QuickSight 儀表板）。
① 收集 (Ingest) ├── 即時串流：Kinesis Data Streams (毫秒級), MSK (Managed Kafka) ├── 自動傳輸：Kinesis Data Firehose (近即時, 60 秒緩衝直達 S3) └── 批次搬移：AWS DataSync, Snowball, AWS DMS ② 儲存 (Store - 中心樞紐) ├── Amazon S3 (Data Lake 地基)：原始資料 (Raw), 清洗後 (Cleaned), 欄式壓縮 (Parquet) └── Amazon Redshift (Data Warehouse)：高效能 OLAP 複雜分析 ③ 處理 (Process / ETL) ├── AWS Glue：無伺服器 Spark ETL, 自動推斷 Schema (Glue Crawler) └── Amazon EMR：全自管 Hadoop / Spark / Hive / Presto 叢集 ④ 分析 (Analyze) ├── Amazon Athena：Serverless, 直接對 S3 執行 Presto SQL 查詢 ├── Redshift Spectrum：直接從 Redshift 叢集 Join 外部 S3 冷資料 └── OpenSearch Service：全文檢索、日誌即時分析 (Log Analytics) ⑤ 呈現 (Visualize) └── Amazon QuickSight：雲端原生 BI 儀表板, 內建 SPICE 記憶體快取加速

2. Kinesis 四兄弟：Data Streams vs Firehose 深度決策

比較維度Kinesis Data Streams (KDS)Kinesis Data Firehose
定位與本質 即時串流儲存管線。資料寫入後會保留在 Shard 中，供多個 Consumer 同時拉取。 全託管資料傳輸輸送帶。不保留資料，資料在管線中轉換後直接輸出至目的地。
資料延遲 超低延遲（毫秒級，Sub-second，約 70~200ms）。 近即時（Near Real-time）。依 Buffer Size (1~128MB) 或 Buffer Interval (60~900 秒) 批量寫出。
資料保留期 預設 24 小時，最長可調至 365 天（支援重播資料）。 不保留（直接拋送到目的地或備份 S3 儲存貯體）。
消費者實作 需要自己編寫或維運消費者程式碼（AWS Lambda, KCL 應用程式, Flink）。 完全免代碼 (Zero-code)。AWS 自動幫你送到 S3, Redshift, OpenSearch, Splunk, HTTP 端點。
容量調整模型 支援 Provisioned 模式（手動配置 Shard 數量）與 On-Demand 模式（自動擴縮容量）。 完全自動擴展。無須管 Shard，底層自動依據輸入流量吞吐自動伸縮。
加值功能 多路消費者獨立讀取、增強型展開 (EFO)。 S3 寫入前自動轉格式（Parquet/ORC）、動態 GZIP/Snappy 壓縮、調用 Lambda 行內轉換。
考試關鍵字秒殺密碼：
• 出現「Near real-time (近即時)」、「不想寫消費者程式碼」、「寫入 S3 前自動轉換為 Parquet 欄式格式」→ 秒選 Kinesis Data Firehose。
• 出現「Sub-second 毫秒級延遲」、「需要重播資料 (Replay data)」、「多個獨立系統消費同一份串流」→ 秒選 Kinesis Data Streams。

3. Kinesis 進階：Shard 容量運算、增強型展開 (EFO) 與 KCL

Shard 容量硬指標運算（經典計算題）

單一 Shard (分片) 物理限制：
• 寫入容量 (Write Ingest)：最大 1 MB/秒 或 1,000 筆記錄/秒（先達到者為準）
• 標準讀取容量 (Read Egress)：最大 2 MB/秒（該 Shard 下所有 Consumer 共享這 2MB！）

Shard 需求數量計算公式：
所需 Shard 數 = MAX( 預估峰值寫入 MB/s ÷ 1 MB, 預估峰值每秒筆數 ÷ 1000 )

增強型展開 (Enhanced Fan-Out, EFO)

如果一個 Stream 有 5 個不同的應用程式（如詐欺偵測、即時分析、警報系統等）同時需要讀取同一份資料：

【模式 A：標準輪詢 (Standard Consumer - 共享 2MB/s)】 Shard 1 (讀取上限 2 MB/s) ├── Consumer A (拉取 0.4 MB/s) ├── Consumer B (拉取 0.4 MB/s) ├── Consumer C (拉取 0.4 MB/s) └── Consumer D (拉取 0.8 MB/s) * 缺點：消費者越多，每個人分到的頻寬越小，平均延遲高達 2~5 秒！ 【模式 B：增強型展開 (Enhanced Fan-Out - 專屬獨立頻寬)】 Shard 1 ├── 專屬 HTTP/2 推播管道 ──→ Consumer A (享有專屬 2 MB/s 頻寬，延遲 ~70ms) ├── 專屬 HTTP/2 推播管道 ──→ Consumer B (享有專屬 2 MB/s 頻寬，延遲 ~70ms) └── 專屬 HTTP/2 推播管道 ──→ Consumer C (享有專屬 2 MB/s 頻寬，延遲 ~70ms) * 核心：每個註冊 EFO 的消費者各自享有獨立的 2 MB/s 吞吐，彼此互不搶頻寬！
KCL 與 DynamoDB 陷阱題：
Kinesis Client Library (KCL) 會自動為每個 Stream 建立一張 Amazon DynamoDB 表格來追蹤每個 Shard 的處理進度（Checkpointing 與 Lease 管理）。
• 故障排查高頻考點：若 KCL 應用程式突然出現延遲甚至停滯，報錯 ProvisionedThroughputExceededException，肇因通常不是 Kinesis 本身，而是底層追蹤狀態的 DynamoDB 表格寫入容量 (WCU) 不足！調大 DynamoDB 容量即可解決。

4. Amazon Athena：S3 伺服器無伺服器 SQL 與成本優化四大金律

Athena 是一項無伺服器 (Serverless) 互動式查詢服務。你只需在 S3 放置檔案，並在 Glue Data Catalog 建立表格定義，即可直接下標準 SQL (ANSI SQL) 進行查詢。它的計費模式極度單純：每掃描 1 TB 資料收費 $5.00 美元！

Athena 降低 90% 查詢帳單與延遲的四大金律 【金律 1：轉換為欄式格式 (Columnar Storage)】 • 原始格式 (CSV / JSON)：即使只查 `SELECT age FROM users`，也必須整行掃描。 • Apache Parquet / ORC：只讀取 `age` 這一欄的硬碟區塊，掃描量直接降 80%~90%！ 【金律 2：資料分割 (Partitioning)】 • 依據時間或地區建立 S3 目錄結構：`s3://my-lake/logs/year=2026/month=09/day=25/` • 下查詢時附帶 `WHERE year='2026' AND month='09'`，Athena 直接跳過其他年份月份，只掃當天！ 【金律 3：壓縮檔案 (Compression)】 • 使用 Snappy / GZIP / ZSTD 壓縮檔案。因為以掃描位元組計費，檔案變小 = 帳單直接打折。 【金律 4：合併小檔案 (Avoid Small Files)】 • S3 上若有數百萬個幾 KB 的微型檔案，會造成極大的 S3 GET 請求開銷與中繼資料尋址延遲。 • 透過 Glue ETL 將小檔案合併成 128MB ~ 512MB 的最適檔案大小。

5. Amazon Redshift：PB 級資料倉儲、RA3 節點與 Spectrum

Amazon Redshift 專為企業級大規模並行處理 (MPP) 與線上分析處理 (OLAP) 而生：

核心特性 / 功能架構原理與優勢典型考點關鍵字
欄式儲存 (Columnar) 相同欄位的資料連續存放在磁碟中，壓縮比極高（可達 3~5 倍），極大化分析查詢 I/O。 複雜巨量資料查詢、跨多欄位聚合。
RA3 節點類型 運算與儲存完全分離 (Separation of Compute and Storage)。資料存放在託管儲存層 (S3 Backed)，按需擴充運算節點。 資料量持續暴增，但日常查詢算力需求穩定的企業。
Redshift Spectrum 讓 Redshift 叢集直接下 SQL 查詢位在 S3 上的外表 (External Tables)，無須預先載入磁碟！ 將 Redshift 內部的最新熱資料與 S3 上的歷史冷資料進行跨表 JOIN 分析。
Concurrency Scaling 當報表查詢併發爆滿時，自動在背景啟動額外的暫態叢集處理排隊查詢，尖峰過後自動收回。 月初/季末財務報表高峰併發、避免查詢卡隊。
Redshift Spectrum vs Athena 選擇題：
• Athena：完全無伺服器，使用者手頭上沒有現成的 Redshift 叢集，只想對 S3 做隨選 ad-hoc 查詢。
• Redshift Spectrum：使用者已經擁有一座運行的 Redshift 叢集，且需要將倉儲內的商業維度表與 S3 上的日誌大表進行 JOIN。

6. Amazon EMR：託管 Spark / Hadoop 節點拓撲與 Spot 節省

Amazon EMR 是託管的巨量資料叢集平台，支援 Apache Spark, Hadoop, Presto, Flink, HBase 等開源框架。EMR 叢集的節點角色分為三種：

EMR 叢集三大節點角色與 Spot 實例策略 1. Master Node (主節點) ├── 職責：管理整個叢集、協調 YARN 資源排程、追蹤任務狀態。 └── 算力選擇：On-Demand (按需實例)。絕不能用 Spot！若 Master 節點被中斷，整座叢集直接瓦解崩潰！ 2. Core Nodes (核心節點) ├── 職責：執行計算任務，同時運行 HDFS 資料節點 (DataNode) 存放分散式資料檔案。 └── 算力選擇：通常使用 On-Demand。若隨意終止 Core 節點，HDFS 副本可能遺失導致資料損毀。 3. Task Nodes (任務節點) ├── 職責：純計算節點！完全不儲存任何 HDFS 資料！ └── 算力選擇：100% 採用 Spot Instances (最高省 90% 費用)！ 即使 Spot 實例被 AWS 回收，Master 節點只會將該運算任務指派給其他 Task 節點重跑，資料毫髮無傷！
✅ EMR 成本考題萬年定律：「如何以最低成本執行大規模 Spark 批次計算？」→ Master 與 Core 使用 On-Demand，Task 節點大量採用 Spot Instances！

7. AWS Glue 與 Lake Formation：資料目錄與列級/行級安全

AWS Glue Data Catalog 統一的中繼資料庫 (Metadata Repository)。Glue Crawler 自動掃描 S3、推斷 Schema，供 Athena、Redshift Spectrum、EMR 共同存取。
AWS Glue ETL 無伺服器 Spark 資料處理引擎。支援排程、依賴性 DAG 工作流程，自動產生 Python (PySpark) 或 Scala 代碼。
AWS Glue DataBrew 視覺化無代碼 (No-code) 資料清洗工具。提供 250+ 種預設轉換規則，讓商業分析師免寫代碼即可去除異常值、遮蔽個資。
AWS Lake Formation 構建在 S3 與 Glue 之上的安全治理層。提供集中式細粒度存取控制：行級安全性 (Row-level) 與列級遮蔽 (Column-level)。

9. Amazon QuickSight：BI 商業智慧與 SPICE 快取

Amazon QuickSight 是 AWS 的雲端原生商業智慧與資料視覺化服務：

QuickSight 核心架構亮點 • SPICE (Super-fast, Parallel, In-memory Calculation Engine)： 專屬的記憶體運算引擎。將 S3 / Athena / RDS 資料預先快取進 SPICE，百萬筆圖表查詢秒級回應，且不會重複打回底層資料庫產生費用！ • 機器學習洞察 (ML Insights)：自動偵測隱藏趨勢、離群值異常檢測 (Anomaly Detection)。 • 嵌入式分析 (Embedded Analytics)：支援將儀表板以 iframe 形式嵌入企業內網或客戶門戶網站。

11. SAA-C03 考試陷阱與高頻考點速查

陷阱 1：Kinesis Data Firehose 延遲限制
Firehose 最小的緩衝間隔是 60 秒（或自訂最小 0.2MB）。如果題目要求「延遲必須小於 1 秒」或「即時處理」，絕對不能選 Firehose，必須選 Kinesis Data Streams！
陷阱 2：EMR 主節點嚴禁使用 Spot
考題中若出現「為了極大化節省 EMR 成本，將 Master Node 設定為 Spot Instance」→ 絕對錯誤！ Master 節點掛掉整座叢集終止。只有 Task 節點 適合全數採用 Spot。
陷阱 3：Athena 降低成本的第一步
Athena 查詢費用的關鍵在於「掃描量」。優化順序：轉換成 Parquet 欄式格式 ➔ 依日期進行 Partition 分割 ➔ 檔案壓縮。切忌在沒有任何優化的情況下無差別全表掃描 CSV！
🎯 分析考題秒殺神經反射：
• 串流免代碼直送 S3 轉 Parquet → Kinesis Data Firehose
• 多路獨立即時消費且需重播 → Kinesis Data Streams (EFO)
• 無伺服器對 S3 執行 SQL 查詢 → Amazon Athena + Parquet
• 跨 Redshift 與 S3 歷史資料聯合查詢 → Redshift Spectrum
• 統一中央 Schema 字典目錄 → AWS Glue Data Catalog
• 資料湖欄位/行級權限隔離 → AWS Lake Formation

12. 實作 Lab：Kinesis 串流建立與 Athena S3 外部表查詢

# 步驟 1：建立具備 2 個 Shard 的 Kinesis Data Stream aws kinesis create-stream \ --stream-name telemetry-stream \ --shard-count 2 # 步驟 2：向串流寫入一筆測試記錄 (使用 PartitionKey 分配到特定 Shard) aws kinesis put-record \ --stream-name telemetry-stream \ --partition-key "device-101" \ --data "eyJkZXZpY2VfaWQiOiAiMTAxIiwgInRlbXAiOiAyNS40fQ==" # 步驟 3：在 Athena 建立指向 S3 Parquet 的外部資料表 (External Table) CREATE EXTERNAL TABLE IF NOT EXISTS web_analytics.page_views ( user_id STRING, page_url STRING, duration_sec INT, device_type STRING ) PARTITIONED BY (year STRING, month STRING, day STRING) STORED AS PARQUET LOCATION 's3://my-analytics-lake-2026/page_views/'; # 步驟 4：執行高效能分區查詢 (只掃描指定日期的 Parquet 欄位，費用逼近 $0) SELECT user_id, AVG(duration_sec) AS avg_duration FROM web_analytics.page_views WHERE year = '2026' AND month = '09' AND day = '25' GROUP BY user_id LIMIT 50;
