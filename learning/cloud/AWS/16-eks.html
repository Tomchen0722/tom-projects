EKS 與容器平台選型

第 11 課講完 ECS，這一課補上另一半：什麼時候該用 Kubernetes、EKS 幫你管了什麼、以及企業選型時真正該問的問題。

1. 先問：你真的需要 Kubernetes 嗎？

ECS 像自排車——AWS 幫你決定大部分的事，上手快、夠用。
EKS 像手排車——控制權全給你，但你要懂離合器。開得好比自排快，開不好比自排慢很多。

SAA 考試與實務都會問「ECS 還是 EKS」。判斷點其實只有四個：

判斷點選 ECS選 EKS
團隊技能沒有 K8s 經驗，人力有限已有 K8s 團隊或專職平台工程師
可攜性需求就長期待在 AWS需要多雲或混合雲，或客戶要求不綁單一雲
生態系需求內建功能夠用要用 Helm、Istio、Argo CD、Prometheus 等 K8s 生態工具
複雜度幾十個服務以內大量微服務、多團隊共用平台
陷阱：考試最愛的一句話
題目出現「希望維持與地端 Kubernetes 一致」「避免供應商鎖定」「要用既有的 Helm chart」→ EKS。
出現「團隊沒有 Kubernetes 經驗」「最少維運負擔」「最快上線」→ ECS（甚至 App Runner）。

AWS 官方立場其實很務實：沒有特殊理由的話，ECS 更簡單。EKS 的價值在可攜性與生態系，不在「比較厲害」。
企業實務：一個常見的誤判
很多團隊選 EKS 的理由是「以後可能要多雲」。但實際上，只要你用了 ALB Ingress Controller、EBS CSI、IRSA、Route 53、ACM，你的 K8s YAML 早就綁定 AWS 了——真要搬到別的雲，改的量不會比 ECS 少太多。

可攜性是要刻意設計才有的，不是選了 K8s 就自動獲得。如果多雲只是「以後可能」，這個理由撐不起 EKS 的維運成本。

2. EKS 架構：AWS 管什麼、你管什麼

控制平面 Control Plane ← AWS 全託管 ├── API Server（跨 3 個 AZ,自動修復） ├── etcd（狀態資料庫,自動備份） ├── Scheduler / Controller Manager └── 按小時計費,不管你有沒有跑 Pod 資料平面 Data Plane ← 你管（或部分託管） ├── 節點（EC2 / Fargate） ├── kubelet、容器執行環境 ├── 版本升級要你自己排 └── 節點的作業系統修補要你負責 附加元件 Add-ons ├── VPC CNI（網路） ├── CoreDNS（服務名稱解析） ├── kube-proxy └── EBS/EFS CSI Driver（儲存） ↑ 這些可以用 EKS Managed Add-ons 讓 AWS 幫你管版本
📋責任分界是考試重點。AWS 保證控制平面的高可用與 SLA，但節點上的作業系統修補、K8s 版本升級的排程、應用的高可用設計，都是你的責任。這是共同責任模型在 EKS 上的具體體現。
陷阱：EKS 版本會過期
Kubernetes 每年出多個版本，AWS 對每個版本的標準支援期有限（約 14 個月，之後進入延長支援並額外收費）。
「買了就不用管」在 EKS 不成立——你必須定期升級，而升級要同時處理控制平面、節點、以及所有 add-on 的相容性。

企業實務上這是 EKS 最被低估的長期成本：每年至少要排 1-2 次升級演練。

3. 三種節點模式

模式誰管節點適合限制
自管節點
Self-managed		你全包需要特殊 AMI、GPU 驅動、自訂核心參數維運負擔最重
Managed Node GroupAWS 協助建立與輪替多數情況的預設選擇仍需你決定升級時機
Fargate完全不用管節點不想碰機器、工作負載零散不支援 GPU、DaemonSet、特權容器；單價較高
陷阱：EKS on Fargate 的限制比 ECS on Fargate 更多
K8s 有很多功能預設依賴「節點」這個概念，在 Fargate 上不成立：
• DaemonSet 不能用（沒有節點可以「每台跑一個」）→ 日誌收集要改用 sidecar 或 Fluent Bit 的 Fargate 日誌路由
• 不支援 GPU
• 不支援特權容器與 HostPath
• 每個 Pod 都是獨立的微型 VM，啟動比 EC2 節點上的 Pod 慢

題目說「跑 GPU 推論的 Pod」→ 一定是 EC2 節點，不是 Fargate。
企業實務：混合配置是常態
成熟的 EKS 叢集通常同時用兩種：
• Managed Node Group（含 Spot） 跑無狀態、可中斷的工作負載——成本低
• Fargate 跑少量但重要的系統元件，或是需要強隔離的租戶工作負載

用 節點親和性（nodeAffinity） 與 污點/容忍（taints/tolerations） 決定哪個 Pod 落在哪裡。

4. EKS 網路：VPC CNI 與 IP 耗盡

這是 EKS 最容易在正式環境炸掉、而且純學理論不會遇到的問題。

AWS VPC CNI 的運作方式 每個 Pod 都拿到一個 VPC 內的真實 IP （不是 overlay 網路的虛擬 IP） 好處： Security Group、VPC Flow Logs、路由都能直接作用在 Pod 上 Pod 與 VPC 內其他資源可直接通訊,沒有額外封裝開銷 代價： Pod 數量 = 消耗的 VPC IP 數量 子網路 /24 只有約 251 個可用 IP → 一個節點跑 30 個 Pod,8 台節點就把子網路吃光 → 新 Pod 卡在 Pending,錯誤訊息是 "failed to assign an IP address"
陷阱：IP 耗盡的四個解法
① 規劃夠大的子網路——EKS 的工作節點子網路建議 /19 以上，不要用 /24
② Prefix Delegation——讓每個節點一次配一段 /28，提高每節點可容納的 Pod 數與 IP 使用效率
③ 自訂網路（Custom Networking）——把 Pod 放到次要 CIDR（例如 100.64.0.0/16 這類非路由的空間），節點本身留在主 CIDR
④ 極端情況才考慮換 CNI（Calico 等 overlay），但會失去「Pod 用 Security Group」的好處

考試看到「Pod 無法啟動、IP 不足」→ 想子網路規劃與 Prefix Delegation。
企業實務：這件事要在建 VPC 時就決定
IP 規劃是建立叢集前的決策，事後幾乎無法補救——你不能把跑著的叢集搬到另一個子網路。
實務建議：EKS 專用 VPC，節點子網路每個 AZ 至少 /19，並預留次要 CIDR 給未來的 Custom Networking。
這條規劃錯了，兩年後整個平台要重建。

5. IRSA：Pod 層級的 IAM 權限

這是 EKS 最重要的安全機制，也是必考題。

錯誤做法（很多團隊一開始都這樣） 把 S3、DynamoDB 權限直接給節點的 Instance Profile → 節點上所有 Pod 都拿得到那些權限 → 一個被入侵的 Pod = 整台節點的權限全洩漏 正確做法：IRSA IAM Roles for Service Accounts K8s ServiceAccount ──綁定──→ IAM Role ↑ ↑ Pod 使用 只給這個 Pod 需要的權限 原理:EKS 提供 OIDC 供應商, Pod 用投影的 SA token 去 STS 換臨時憑證 （和第 10 課 CI/CD 用 OIDC 免金鑰是同一套機制）
✅ 考試關鍵字：「讓特定 Pod 存取 S3，但同節點其他 Pod 不能」→ IRSA。不要選「加在節點的 IAM Role 上」——那是最小權限原則的反面教材。

延伸：較新的 EKS Pod Identity 提供類似效果但設定更簡單，不需要為每個叢集管理 OIDC 供應商。看到兩者都出現時，先確認題目強調的是「跨叢集集中管理」（Pod Identity）還是通用相容性（IRSA）。

6. 兩層擴展：HPA 與 Karpenter

和 ECS 一樣，K8s 的擴展也分兩層，但名字不同：

HPA（Pod 層）Horizontal Pod Autoscaler。依 CPU/記憶體/自訂指標增減 Pod 數量。
VPA（Pod 層）Vertical Pod Autoscaler。調整單一 Pod 的資源規格，而不是數量。
Cluster Autoscaler（節點層）傳統方案。依 Node Group 增減節點數量，受限於預先定義的機型。
Karpenter（節點層）AWS 開源的新一代。直接依待調度 Pod 的實際需求挑機型並開機，更快也更省。
陷阱：Cluster Autoscaler vs Karpenter
• Cluster Autoscaler：只能在你事先定義好的 Node Group 裡加減機器。如果 Pod 需要 GPU 但你沒建 GPU 的 Node Group，它幫不了你。
• Karpenter：看到 Pending 的 Pod，直接依它的 CPU/記憶體/GPU/架構需求去挑最合適也最便宜的機型開機，不需要預先定義群組。

題目強調「更快的節點供應」「自動挑選最省成本的機型」「減少節點群組管理」→ Karpenter。
企業實務：Karpenter + Spot 是目前的成本最佳解
Karpenter 可以設定「優先用 Spot，沒有就退回 On-Demand」，並在 Spot 中斷通知時自動把 Pod 遷走。
搭配 PodDisruptionBudget 確保遷移過程中每個服務至少留幾個副本活著，就能在不影響可用性的前提下大幅降低運算成本。

前提是你的應用要能容忍 Pod 隨時被殺掉——這是雲原生設計的基本要求，不是 Karpenter 的限制。

7. 成本與企業選型

成本項目ECSEKS
控制平面免費按小時計費（每叢集）
運算資源EC2 或 Fargate 用量同左
人力成本低高——通常是真正的大頭
升級維運幾乎不用管每年 1-2 次版本升級
多叢集的成本陷阱
控制平面是按叢集計費的。如果你為 dev / test / staging / prod 各開一個叢集，控制平面費用就是四份。
小團隊常見的替代做法：用 namespace + ResourceQuota + NetworkPolicy 在同一個叢集裡隔離環境，只有 prod 獨立叢集。

但要注意：namespace 不是強隔離邊界。如果是多租戶或有法規要求，還是要分叢集甚至分帳號。
✅ 選型的一句話總結：
「我們有沒有人願意也有能力長期照顧這個平台？」——有，EKS 的彈性與生態系會回報你；沒有，ECS 或 App Runner 才是對的答案。

技術選型失敗最常見的原因不是選錯工具，是選了一個團隊養不起的工具。

8. 考試陷阱整理

陷阱 1：可攜性題目
「與地端 K8s 一致」「避免鎖定」「既有 Helm chart」→ EKS。「團隊沒經驗」「最少維運」→ ECS。
陷阱 2：Pod 權限題目
「只讓某個 Pod 存取 S3」→ IRSA（或 EKS Pod Identity），不是節點 Instance Profile。
陷阱 3：Pod Pending 且 IP 不足
→ VPC CNI 的 IP 耗盡。想 Prefix Delegation、次要 CIDR、子網路規劃。
陷阱 4：EKS on Fargate 不支援 DaemonSet 與 GPU
要跑 GPU 或每節點一份的日誌代理 → 必須用 EC2 節點。
陷阱 5：控制平面免費的是 ECS 不是 EKS
成本比較題常拿這點當差異。
陷阱 6：節點擴展選 Karpenter
看到「自動挑最省的機型」「不想管 Node Group」→ Karpenter，不是 Cluster Autoscaler。
💡一句話記憶：
要不要 K8s 看團隊，節點怎麼開看 Karpenter，Pod 權限看 IRSA，會不會炸看 IP 規劃。
