1. 容器平台選型決策：ECS vs EKS vs App Runner

• App Runner 像搭計程車：直接給代碼或映像檔，連伺服器都不用管，適合小型微服務。
• Amazon ECS 像開自排車：AWS 幫你管定速巡航與變速箱，操作直覺、完全整合 AWS 生態，維運負擔極輕。
• Amazon EKS 像開重型拖曳卡車：提供最大載重、跨廠牌（跨雲）零件通用，但需要專職技工每天保養與換檔。
架構考量維度Amazon ECSAmazon EKS (Kubernetes)AWS App Runner
適用團隊背景 無 K8s 經驗，希望專注在業務邏輯與快速交付。 已有 Kubernetes 團隊、熟悉 kubectl 與 Helm 工具鏈。 前端/全端工程師、無基礎設施維運團隊。
多雲可攜性 (Portability) 深度綁定 AWS API。搬遷至其他公有雲需重寫配置。 高標準可攜性。YAML 與 Helm Charts 可跨地端機房與多雲執行。 完全託管於 AWS。
開源生態工具相容性 主要依靠 AWS 原生工具（CloudWatch, X-Ray, ALB）。 極為龐大：Istio, Prometheus, Grafana, ArgoCD, Linkerd, Cilium。 僅限內建功能。
控制平面計費 完全免費！只收取底層 EC2 / Fargate 資源費。 每個叢集每小時收費 $0.10 美元（約每月 $73 美元）。 無控制平面費用，按請求與記憶體收費。
考試情境秒選關鍵字 「最少維運開銷」、「快速上線」、「無伺服器容器」。 「跨雲/地端混合遷移」、「現有 Helm charts」、「標準 Kubernetes API」。 「直接從 GitHub 部署 Web App」、「完全無伺服器 Web 服務」。

2. EKS 架構拓撲：控制平面 (Control Plane) 與端點存取控制

EKS 的控制平面由 AWS 全權代管。在背後，AWS 在專用的受管 VPC 內跨 3 個可用區 (AZ) 部署了至少 2 個 API Server 實例與 3 個 etcd 節點，保證 99.95% 的 SLA 可用性。

AWS 全託管 VPC (Control Plane) └── API Server (跨 3 AZ 高可用) + etcd 資料庫 (自動加密備份) │ │ 透過跨帳號 ENI (Cross-Account Elastic Network Interfaces) 互聯 ▼ 客戶自管 VPC (Data Plane - 你的子網路) ├── Public Subnet：NAT Gateway、ALB / NLB 網際網路接入點 └── Private Subnet：EKS Worker Nodes (EC2 / Fargate Pods)

EKS API Server 存取端點三種安全拓撲

1. Public Only (預設) Kubernetes API 端點對網際網路開放。kubectl 呼叫從公網進入，節點亦透過公網與控制平面通訊。需嚴格保護 IAM 與憑證。
2. Public and Private (折衷) 工作節點 (Worker Nodes) 與 API Server 透過私有 VPC ENI 溝通；外部維運工程師的 kubectl 仍可從公網透過身分驗證連線。
3. Private Only (金融與軍規首選) 完全對網際網路隱形！API Server 只能從 VPC 內部、VPN 或 Direct Connect 專線存取。徹底杜絕公網連線風險（SAA 高頻資安題）。

3. 資料平面三種節點模式：Self-managed vs Managed vs Fargate

節點架構模式節點管理權限核心優勢主要限制與取捨
Managed Node Groups
(EKS 受管節點群組)		 由 AWS 代為佈建 Auto Scaling Group、打 OS 標籤與自動化節點排乾 (Drain)。 生產環境標準做法。一鍵平滑升級 AMI，並自動處理 Kubernetes 污點與排水。 底層仍是 EC2，需配置容量預估；需定期安排 AMI 升級排程。
Self-managed Nodes
(自管 EC2 節點)		 客戶自行維護 Launch Template、Auto Scaling Group 與節點加入腳本。 支援高度客製化 AMI、特殊客製化 Linux 核心模組、自訂儲存卷配置。 維運負擔沉重。節點退役與排乾必須手動執行腳本處理。
AWS Fargate on EKS
(無伺服器 Pod)		 完全無 EC2 實例。每個 Pod 獨佔一個輕量級 VM (microVM) 與專屬 ENI。 零節點維運。無須打 OS 補丁、無須管理容積率；強隔離性，防容器逃逸。 不支援 GPU、不支援 DaemonSets（如主機級日誌收集）、不支援 HostPath 儲存。
考試必殺陷阱：EKS Fargate 不支援 DaemonSet！
如果題目問：「需要在 EKS 叢集中部署日誌收集代理（如 Fluentd）或 APM 監控代理（如 Datadog），確保每台節點都自動運行一個副本，且期望底層採用無伺服器 Fargate 架構？」
→ 錯誤！Fargate 上沒有實體節點概念，因此 DaemonSet 無法被調度。正確解法是：改用 Sidecar 容器模式 或使用 Managed Node Group！

4. EKS 網路架構：VPC CNI、Prefix Delegation 與次要 CIDR

傳統 Kubernetes 使用 Overlay 網路（如 Flannel/Calico），Pod 擁有內部虛擬 IP。但 EKS 預設採用 AWS VPC CNI (aws-node)，其核心理念是：讓每個 Pod 直接成為 VPC 內部的公民，直接擁有 VPC 私有 IP！

AWS VPC CNI 運作機制 EC2 節點 (主 ENI: 10.0.1.50) ├── 輔助 ENI 1 ── 分配次要 IP: 10.0.1.51 → 賦予 Pod A ├── 輔助 ENI 1 ── 分配次要 IP: 10.0.1.52 → 賦予 Pod B └── 輔助 ENI 2 ── 分配次要 IP: 10.0.1.60 → 賦予 Pod C 極大優勢： 1. Pod 與 RDS 資料庫、本機 EC2 通訊零 NAT 轉發損耗，效能極高。 2. Security Groups for Pods：可以為特定 Pod 綁定專屬的 AWS 安全群組！ 致命隱患：VPC 私有 IP 迅速被耗盡！ 一個 /24 的子網路只有 251 個可用 IP。若叢集有 10 台節點，每台節點跑 25 個 Pod，子網路瞬間被吃光！ 新 Pod 進入 Pending 狀態，報錯："failed to assign an IP address"。

解決 IP 耗盡的四大架構處方

解決手段原理與操作考試核心結論
1. Prefix Delegation (前綴委派) ENI 不再單個綁定 IP，而是一次綁定一段 /28 前綴（16 個 IP）。 大幅減少 ENI 佔用，顯著提高小型節點上的 Pod 密度上限。
2. Custom Networking (自訂網路) 在 VPC 擴充一組次要 CIDR（例如保留網段 100.64.0.0/16 Carrier Grade NAT），將 Pod 專門排在次要網段，節點留在主要網段。 最推薦的企業架構解法。保護核心業務 VPC IP 空間不受容器暴增侵蝕。
3. EKS 專用大子網路 建置 EKS 專用 VPC，子網路預先劃分為 /19 或更大（提供 8,000+ IP）。 規劃初期必備。

5. EKS 身份授權演進：IRSA 與 EKS Pod Identity

【歷史做法（極度危險）】 EC2 節點綁定 IAM Role（包含 S3/DynamoDB 權限） └── 跑在該節點上的所有 50 個 Pod 都能藉由 IMDS 拿到該權限，違反最小權限原則！ 【標準解法 1：IRSA (IAM Roles for Service Accounts)】 利用 OpenID Connect (OIDC) 聯合身分驗證： 1. 建立叢集的 OIDC Identity Provider 2. 建立 IAM Role，Trust Policy 限制只有特定 namespace 與 ServiceAccount 才能 AssumeRole 3. K8s ServiceAccount 標記註解: eks.amazonaws.com/role-arn: arn:aws:iam::... 4. 只有掛載該 ServiceAccount 的 Pod 才能取得臨時憑證，同主機其他 Pod 完全隔離！ 【最新解法 2：EKS Pod Identity (2024+ 新架構)】 無須手動配置 OIDC 供應商！直接在 EKS 控制台或 API 將 IAM Role 與 ServiceAccount 建立繫結關聯。 更加簡潔，適合跨多個 EKS 叢集集中管理權限。
✅ 考題必勝句型：「如何確保只有微服務 Payment Pod 能夠存取 S3 Bucket，而運行在同一台工作節點上的其他 Pod 無法存取？」→ IRSA (IAM Roles for Service Accounts)。

6. 外部流量接入：AWS Load Balancer Controller 與 ALB/NLB

Kubernetes 如何將外部網際網路流量引導至內部 Pod？有兩種截然不同的層次：

模式Kubernetes 物件對應 AWS 資源轉發路徑與效能
傳統 Service 模式 type: LoadBalancer Classic Load Balancer 或舊版 NLB 流量打到 EC2 NodePort，再由 kube-proxy 做二次轉發（增加躍點與延遲）。
AWS LBC
(Ingress 模式)		 kind: Ingress Application Load Balancer (ALB) IP Target Mode 直通 Pod IP！ALB 直接將流量路由到 Pod ENI，支援路徑分流、TLS 卸載與 AWS WAF。
AWS LBC
(NLB IP 模式)		 type: LoadBalancer (附帶 LBC 註解) Network Load Balancer (NLB) 極低延遲、固定 IP、四層 TCP/UDP 流量直通 Pod。
子網路標籤陷阱 (Subnet Tagging Requirement)
AWS Load Balancer Controller 在自動建立 ALB/NLB 時，必須仰賴 VPC Subnet 上的特定標籤來識別放置位置：
• 公開網際網路面向的 ALB 子網路：必須包含 kubernetes.io/role/elb = 1
• 私有內部面向的 ALB 子網路：必須包含 kubernetes.io/role/internal-elb = 1
缺少標籤會導致 Ingress 部署失敗！

7. EKS 儲存外掛整合：EBS CSI vs EFS CSI vs FSx

儲存 CSI 驅動存取模式 (Access Mode)跨 AZ 支援典型 Kubernetes 應用場景
Amazon EBS CSI Driver ReadWriteOnce (RWO)
（同一時間只能掛載給單一 Pod）		 ❌ 只能在單一 AZ 內部存取 單節點關聯式資料庫（PostgreSQL, MySQL Pod）、高效能低延遲磁碟需求。
Amazon EFS CSI Driver ReadWriteMany (RWX)
（支援數千個 Pod 併發讀寫）		 ✅ 支援多 AZ 併發共享 內容管理系統（WordPress 上傳目錄）、共享設定檔、CI/CD 構建暫存。
FSx for Lustre CSI ReadWriteMany (RWX) ✅ 支援跨節點高速平行存取 分散式機器學習模型訓練 (AI/ML)、巨量資料 HPC 批次分析。

8. 兩層彈性擴展：HPA 與 Karpenter 極速節點調度

【層級 1：Pod 橫向擴展 (Horizontal Pod Autoscaler - HPA)】 依據 CPU / 記憶體使用率，或 Prometheus / SQS 佇列深度自訂指標，自動增加或減少 Deployment 的 Pod 副本數。 【層級 2：節點層自動擴展 (Node Autoscaler)】 當 HPA 增加 Pod 導致節點資源不足，新 Pod 陷入 Pending 狀態時： ┌────────────────────────────┬────────────────────────────┐ │ 傳統 Cluster Autoscaler (CAS) │ 現代化 Karpenter (AWS 開源首選) │ ├────────────────────────────┼────────────────────────────┤ │ • 綁定 EC2 Auto Scaling Group │ • 完全不依賴 Auto Scaling Group │ │ • 只能在預設群組規格內加減機器 │ • 直接根據 Pending Pod 規格精準算力│ │ • 供應節點需耗時 3~5 分鐘 │ • 40 秒內極速啟動 EC2 節點 │ │ • 機型靈活性差，容易浪費閒置算力 │ • 自動動態組合 Spot/On-Demand 與 ARM│ │ • 縮容排乾節點速度較慢 │ • 支援 Consolidation 主動將碎片重組 │ └────────────────────────────┴────────────────────────────┘

9. EKS 叢集生命週期與無中斷版本升級

Kubernetes 版本更新頻繁（每年多個次版本）。EKS 升級是企業生產環境的標準必修課，標準零停機升級四部曲：

步驟 1：升級 EKS 控制平面 (Control Plane) └── 透過主控台或 CLI 發起，AWS 自動在後台平滑更新 API Server 與 etcd，服務零中斷。 ▼ 步驟 2：升級 EKS 受管附加元件 (Managed Add-ons) └── 依序升級 VPC CNI、CoreDNS、kube-proxy、EBS CSI Driver 相容版本。 ▼ 步驟 3：滾動更新工作節點群組 (Managed Node Groups) └── AWS 建立新版 AMI 節點 ➔ 發送 Cordon 標記舊節點不可調度 ➔ Drain 排乾並驅逐舊 Pod ➔ 終止舊 EC2。 ▼ 步驟 4：前置防護：配置 PodDisruptionBudget (PDB) └── 強制規定在升級排水過程中，服務至少保持 N 個（或 %）健康副本存活，防止全部被殺！

11. SAA-C03 考試陷阱與關鍵字速查

陷阱 1：EKS Fargate 不支援 EBS 持久儲存
EKS on Fargate 只能使用 Amazon EFS 作為持久化儲存卷（透過 EFS CSI Driver），無法直接掛載 EBS 卷！
陷阱 2：IRSA Trust Policy 的 OIDC Audience 限制
設定 IRSA 的 IAM Role 時，條件必須明確限制 aud: "sts.amazonaws.com" 與特定的 ServiceAccount 名稱，否則 STS 會拒絕核發憑證。
陷阱 3：控制平面是收費的
ECS 叢集完全免費，而 EKS 每個叢集收取 $0.10/hr 控制平面費用。若題目強調「開發測試多環境成本極大化精簡」，避免每個專案開獨立 EKS 叢集。
🎯 EKS 考題直覺反射：
• 跨 Pod 共享持久化讀寫 → Amazon EFS CSI Driver
• Pod 安全取得 AWS API 權限 → IRSA (IAM Roles for Service Accounts)
• 極速節點自動擴展且省成本 → Karpenter (搭配 Spot 實例)
• VPC IP 耗盡問題解決 → Prefix Delegation 或 Custom Networking (次要 CIDR)
• ALB 直通 Pod 路由與 WAF 防禦 → AWS Load Balancer Controller (Ingress IP Mode)
