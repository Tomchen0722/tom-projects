1. 為什麼手動點主控台不可行

手動的問題實際會發生什麼
不可重複正式環境和測試環境設定不一致，「在測試機好好的」
沒有紀錄「這條安全群組規則是誰加的、為什麼？」沒人知道
無法審查危險的變更直接上線，沒有第二個人看過
災難無法重建region 掛掉時要手動重建幾百個資源
組態漂移有人為了救火手動改了設定，之後沒人記得
IaC 帶來的四件事：
  1. 可重複——同一份程式碼，dev / staging / prod 部署出一模一樣的環境
  2. 可審查——Pull Request 讓變更被第二個人看過才上線
  3. 可回溯——git log 就是完整的變更歷史
  4. 災難可重建——第 09 章的 Pilot Light DR，運算層就是靠 IaC 幾分鐘拉起來的
但 IaC 也有代價，要誠實評估：
  • 學習曲線——團隊要先學會工具，初期速度比手點慢
  • 除錯較難——錯誤訊息常常很模糊（尤其 CloudFormation）
  • State 管理（Terraform）本身就是一個要維護的東西
  • 並非所有東西都適合——一次性的實驗、緊急救火，手動快得多
合理的界線：長期存在的基礎設施用 IaC，一次性的實驗用 CLI。

2. CloudFormation vs Terraform vs CDK

CloudFormationTerraformCDK
誰做的AWS 原生HashiCorpAWS（底層產生 CFN）
語言YAML / JSONHCLTypeScript / Python / Java / Go
多雲只有 AWS支援只有 AWS（CDKTF 例外）
StateAWS 幫你管要自己管（S3 + DynamoDB）同 CloudFormation
新服務支援通常最快稍慢（等 provider 更新）同 CFN
迴圈 / 條件很難寫不錯（count、for_each）就是程式語言，最自由
學習曲線中中高（但寫程式的人反而覺得簡單）
費用免費開源免費（Cloud 版收費）免費
怎麼選？
  • 只用 AWS、團隊不寫程式 → CloudFormation（考試考這個）
  • 多雲、或已經有 Terraform 經驗 → Terraform（業界最普及）
  • 團隊是開發者、邏輯複雜 → CDK（可以寫迴圈、抽象、單元測試）
  • 純無伺服器專案 → SAM（CloudFormation 的簡化版）
SAA-C03 只考 CloudFormation，但實務上 Terraform 的市佔率更高。兩個都值得會。
CDK 其實不是第三種工具。你用 TypeScript 寫，cdk synth 會產生 CloudFormation 範本，最後還是由 CloudFormation 部署。所以 CDK = CloudFormation + 更好的撰寫體驗。

3. CloudFormation 實作

範本的五個區段

區段必要做什麼
Parameters否部署時可以傳入的值
Mappings否查表（例如各 region 的 AMI ID）
Conditions否條件判斷（prod 才建 Multi-AZ）
Resources是唯一必要的區段
Outputs否輸出值，可被其他堆疊引用
AWSTemplateFormatVersion: "2010-09-09"
Description: 三層式 VPC 網路層

Parameters:
  EnvName:
    Type: String
    AllowedValues: [dev, staging, prod]
    Default: dev
  VpcCidr:
    Type: String
    Default: 10.0.0.0/16
    # 用正規表示式驗證輸入，避免打錯
    AllowedPattern: '^(\d{1,3}\.){3}\d{1,3}/\d{1,2}$'

Conditions:
  # prod 才建第二個 NAT（省錢）
  IsProd: !Equals [!Ref EnvName, prod]

Resources:
  Vpc:
    Type: AWS::EC2::VPC
    Properties:
      CidrBlock: !Ref VpcCidr
      EnableDnsSupport: true
      EnableDnsHostnames: true          # 第 02 章強調過
      Tags:
        - Key: Name
          Value: !Sub "${EnvName}-vpc"

  PublicSubnetA:
    Type: AWS::EC2::Subnet
    Properties:
      VpcId: !Ref Vpc
      # 自動從 VPC CIDR 切出子網路，不用手算
      CidrBlock: !Select [0, !Cidr [!Ref VpcCidr, 16, 8]]
      AvailabilityZone: !Select [0, !GetAZs ""]
      MapPublicIpOnLaunch: false
      Tags:
        - Key: Name
          Value: !Sub "${EnvName}-public-a"

  Igw:
    Type: AWS::EC2::InternetGateway

  IgwAttach:
    Type: AWS::EC2::VPCGatewayAttachment
    Properties:
      VpcId: !Ref Vpc
      InternetGatewayId: !Ref Igw

  NatEipB:
    Type: AWS::EC2::EIP
    Condition: IsProd                     # 只有 prod 才建
    Properties:
      Domain: vpc

  Database:
    Type: AWS::RDS::DBInstance
    DeletionPolicy: Snapshot            ← 刪除堆疊時先留快照
    UpdateReplacePolicy: Snapshot
    Properties:
      DBInstanceClass: !If [IsProd, db.r6g.large, db.t3.micro]
      MultiAZ: !If [IsProd, true, false]
      StorageEncrypted: true
      PubliclyAccessible: false

Outputs:
  VpcId:
    Value: !Ref Vpc
    Export:
      Name: !Sub "${EnvName}-VpcId"     ← 其他堆疊可以 ImportValue
DeletionPolicy 是最重要也最常被忘記的屬性。預設值是 Delete——刪掉堆疊時資料庫和 S3 內容會一起消失。

值行為用在
Delete（預設）一起刪掉無狀態資源
Retain保留，脫離堆疊管理S3 bucket、重要資源
Snapshot刪除前先建快照RDS、EBS、ElastiCache
所有有狀態的資源都應該設 Retain 或 Snapshot。 
# ═══ 部署 ═══
# 先驗證語法
$ aws cloudformation validate-template --template-body file://network.yaml

# deploy 是 create/update 二合一，比 create-stack 好用
$ aws cloudformation deploy \
    --template-file network.yaml \
    --stack-name dev-network \
    --parameter-overrides EnvName=dev VpcCidr=10.0.0.0/16 \
    --capabilities CAPABILITY_NAMED_IAM \
    --tags Owner=tom Project=learning

# 看事件（部署失敗時第一個要查的）
$ aws cloudformation describe-stack-events --stack-name dev-network \
    --query 'StackEvents[?ResourceStatus==`CREATE_FAILED`].[LogicalResourceId,ResourceStatusReason]' \
    --output table

# 看輸出
$ aws cloudformation describe-stacks --stack-name dev-network \
    --query 'Stacks[0].Outputs' --output table
建立失敗時堆疊會自動 ROLLBACK 並刪掉所有資源，你就看不到現場了。除錯時加上這個參數保留失敗的資源： 
$ aws cloudformation create-stack --stack-name test \
    --template-body file://x.yaml \
    --on-failure DO_NOTHING
查完記得手動刪掉，否則會變成孤兒資源。

4. 變更集、巢狀堆疊與漂移偵測

Change Set：部署前先看會改什麼

$ aws cloudformation create-change-set \
    --stack-name prod-network --change-set-name review-20260805 \
    --template-body file://network.yaml \
    --parameters ParameterKey=EnvName,ParameterValue=prod \
    --capabilities CAPABILITY_NAMED_IAM

$ aws cloudformation describe-change-set \
    --stack-name prod-network --change-set-name review-20260805 \
    --query 'Changes[].ResourceChange.[Action,LogicalResourceId,Replacement,ResourceType]' \
    --output table
---------------------------------------------------------
|  Modify |  Database  |  True   |  AWS::RDS::DBInstance  |
|  Add    |  NatEipB   |  False  |  AWS::EC2::EIP         |
---------------------------------------------------------

# 確認沒問題才執行
$ aws cloudformation execute-change-set \
    --stack-name prod-network --change-set-name review-20260805
Replacement: True 代表這個資源會被刪掉重建。對 RDS 來說這意味著：新的 endpoint、資料要從快照還原、實際的停機時間。

正式環境部署前一定要看 Change Set，特別檢查有沒有 Replacement: True。看到就要停下來評估影響，不要直接執行。

常見會觸發 Replacement 的改動：改 RDS 的 DBInstanceIdentifier、改 EC2 的 AvailabilityZone、改 VPC 的 CIDR。

堆疊分層

不要把所有東西放在一個堆疊裡。依「變動頻率」分層：
層內容變動頻率
networkVPC、子網路、路由表、NAT幾乎不變
securityIAM Role、安全群組、KMS偶爾
dataRDS、DynamoDB、S3偶爾
appALB、ASG、Lambda經常
好處：改應用層時不會意外動到資料庫；部署速度快；權限可以分開授權。 
# 跨堆疊引用：上游 Export，下游 ImportValue
# network.yaml 的 Outputs
Outputs:
  PrivateSubnets:
    Value: !Join [",", [!Ref PrivateSubnetA, !Ref PrivateSubnetC]]
    Export:
      Name: !Sub "${EnvName}-PrivateSubnets"

# app.yaml 引用它
Resources:
  Asg:
    Type: AWS::AutoScaling::AutoScalingGroup
    Properties:
      VPCZoneIdentifier: !Split [",", !ImportValue "dev-PrivateSubnets"]
Export/Import 有個硬限制：被引用的 Export 不能刪除或修改。只要有任何堆疊 Import 了它，上游堆疊就改不動也刪不掉，錯誤訊息是 Export cannot be deleted as it is in use。

解法：改用 SSM Parameter Store 傳值——寫入 Parameter Store，下游用 {{resolve:ssm:/dev/vpc-id}} 讀取。這樣就沒有硬相依，上游可以自由變更。

漂移偵測

# 有人手動改了主控台？查出來
$ aws cloudformation detect-stack-drift --stack-name prod-network
$ aws cloudformation describe-stack-resource-drifts \
    --stack-name prod-network --stack-resource-drift-status-filters MODIFIED DELETED \
    --query 'StackResourceDrifts[].[LogicalResourceId,StackResourceDriftStatus]' --output table
漂移偵測應該排程定期跑。救火時手動改設定是難免的，但改完要補回程式碼。定期偵測能抓到「改了但忘了補」的情況——這是 IaC 最容易失效的方式。

更強的做法：用 Stack Policy 或 SCP 直接禁止手動修改被 IaC 管理的資源。

5. Terraform 實作

# ══ versions.tf ══
terraform {
  required_version = ">= 1.6"
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.60"        # 鎖定主版本，避免破壞性更新
    }
  }

  # 遠端 state —— 團隊協作必備
  backend "s3" {
    bucket         = "my-tfstate-123456789012"
    key            = "prod/network/terraform.tfstate"
    region         = "ap-northeast-1"
    encrypt        = true
    use_lockfile   = true              # S3 原生鎖定（新版；舊版用 dynamodb_table）
  }
}

provider "aws" {
  region = var.region
  # 所有資源自動帶上這些標籤（第 08 章的標籤策略）
  default_tags {
    tags = {
      Env       = var.env
      ManagedBy = "terraform"
      Project   = var.project
    }
  }
}
# ══ variables.tf ══
variable "env" {
  type = string
  validation {
    condition     = contains(["dev", "staging", "prod"], var.env)
    error_message = "env 只能是 dev / staging / prod"
  }
}

variable "vpc_cidr" {
  type    = string
  default = "10.0.0.0/16"
}

# ══ main.tf ══
data "aws_availability_zones" "available" {
  state = "available"
}

locals {
  azs = slice(data.aws_availability_zones.available.names, 0, 2)
}

resource "aws_vpc" "main" {
  cidr_block           = var.vpc_cidr
  enable_dns_support   = true
  enable_dns_hostnames = true
  tags = { Name = "${var.env}-vpc" }
}

# for_each 產生多個子網路 —— 這是 Terraform 比 CFN 好寫的地方
resource "aws_subnet" "public" {
  for_each = { for i, az in local.azs : az => i }

  vpc_id                  = aws_vpc.main.id
  availability_zone       = each.key
  cidr_block              = cidrsubnet(var.vpc_cidr, 8, each.value)
  map_public_ip_on_launch = false
  tags = { Name = "${var.env}-public-${each.key}", Tier = "public" }
}

resource "aws_subnet" "private" {
  for_each = { for i, az in local.azs : az => i }

  vpc_id            = aws_vpc.main.id
  availability_zone = each.key
  cidr_block        = cidrsubnet(var.vpc_cidr, 8, each.value + 10)
  tags = { Name = "${var.env}-private-${each.key}", Tier = "private" }
}

# 只有 prod 才建第二個 NAT
resource "aws_nat_gateway" "this" {
  count = var.env == "prod" ? length(local.azs) : 1

  allocation_id = aws_eip.nat[count.index].id
  subnet_id     = values(aws_subnet.public)[count.index].id
}

resource "aws_db_instance" "main" {
  identifier            = "${var.env}-mysql"
  engine                = "mysql"
  instance_class        = var.env == "prod" ? "db.r6g.large" : "db.t3.micro"
  multi_az              = var.env == "prod"
  storage_encrypted     = true
  publicly_accessible   = false

  # 對應 CFN 的 DeletionPolicy
  skip_final_snapshot       = var.env != "prod"
  final_snapshot_identifier = var.env == "prod" ? "${var.env}-final-${formatdate("YYYYMMDD", timestamp())}" : null
  deletion_protection       = var.env == "prod"

  lifecycle {
    # 防止意外刪除正式資料庫
    prevent_destroy = true
    # 這些欄位會被 AWS 自動改，忽略它們避免每次都顯示有變更
    ignore_changes  = [final_snapshot_identifier]
  }
}
Terraform 比 CloudFormation 好寫的三個地方：
  • for_each / count——CFN 要寫迴圈得用巢狀堆疊或自訂資源，很痛苦
  • 三元運算子——var.env == "prod" ? A : B，比 CFN 的 !If 直覺
  • lifecycle { prevent_destroy }——直接在程式碼裡防止誤刪
# ══ 標準工作流程 ══
$ terraform init                      # 下載 provider、設定 backend
$ terraform fmt -recursive            # 統一格式
$ terraform validate                  # 語法檢查

# plan 存成檔案，確保 apply 的就是你看過的那份
$ terraform plan -out=tfplan
$ terraform show -no-color tfplan | less
$ terraform apply tfplan

# 只針對某個資源（除錯用，正常流程不該常用）
$ terraform plan -target=aws_db_instance.main

# 把手動建立的資源納入管理
$ terraform import aws_vpc.main vpc-0abc123
terraform apply 不帶 plan 檔案是危險習慣。不帶的話它會重新計算一次 plan，而那份 plan 可能跟你剛才看的不一樣（別人同時改了東西、或 AWS 那邊狀態變了）。

正式環境永遠用 plan -out + apply tfplan。

6. State 管理與團隊協作

Terraform State 是最容易出事的地方。它是一個 JSON 檔，記錄「哪個程式碼資源對應到哪個真實資源」。
  • State 檔遺失 → Terraform 不知道資源存在，下次 apply 會想重建一份
  • 兩個人同時 apply → State 互相覆蓋，資源狀態錯亂
  • State 檔裡有明文機密——RDS 密碼、金鑰都可能在裡面
正確做法：遠端 State + 鎖定 + 加密。 
# 建立 state bucket（要開版本控制，這是誤刪的最後防線）
$ aws s3api create-bucket --bucket my-tfstate-123456789012 \
    --region ap-northeast-1 \
    --create-bucket-configuration LocationConstraint=ap-northeast-1

$ aws s3api put-bucket-versioning --bucket my-tfstate-123456789012 \
    --versioning-configuration Status=Enabled

$ aws s3api put-bucket-encryption --bucket my-tfstate-123456789012 \
    --server-side-encryption-configuration \
      '{"Rules":[{"ApplyServerSideEncryptionByDefault":{"SSEAlgorithm":"AES256"}}]}'

$ aws s3api put-public-access-block --bucket my-tfstate-123456789012 \
    --public-access-block-configuration \
      BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true
State bucket 要開版本控制——state 壞掉時可以還原到前一版，這救過很多人。
State 檔含有機密，要當成密碼等級保護。
  • 絕對不要 commit 進 Git——.gitignore 要有 *.tfstate、*.tfstate.backup、.terraform/
  • S3 bucket 要加密 + 封鎖公開存取 + 嚴格的 bucket policy
  • 密碼本身應該用 Secrets Manager，Terraform 只引用 ARN 不要存值

環境分離

# 推薦：目錄分離（清楚、不會誤操作）
infra/
├── modules/
│   ├── network/
│   ├── database/
│   └── app/
├── envs/
│   ├── dev/
│   │   ├── main.tf          # 引用 modules
│   │   ├── terraform.tfvars
│   │   └── backend.tf       # key = "dev/terraform.tfstate"
│   ├── staging/
│   └── prod/
└── .gitignore
不建議用 terraform workspace 分環境。雖然方便，但：
  • 所有環境共用同一份程式碼與 backend，很容易忘記切 workspace 就 apply 到正式環境
  • 環境之間有差異時（prod 要 Multi-AZ、dev 不要）程式碼會塞滿條件判斷
目錄分離雖然有些重複，但「不會誤操作正式環境」這件事值得。

7. CDK：用程式語言寫基礎設施

$ npm install -g aws-cdk
$ mkdir infra && cd infra
$ cdk init app --language typescript
$ cdk bootstrap          # 每個帳號每個 region 做一次
// lib/network-stack.ts
import * as cdk from 'aws-cdk-lib';
import * as ec2 from 'aws-cdk-lib/aws-ec2';
import * as rds from 'aws-cdk-lib/aws-rds';

export interface NetworkStackProps extends cdk.StackProps {
  envName: 'dev' | 'staging' | 'prod';
}

export class NetworkStack extends cdk.Stack {
  public readonly vpc: ec2.Vpc;

  constructor(scope: cdk.App, id: string, props: NetworkStackProps) {
    super(scope, id, props);
    const isProd = props.envName === 'prod';

    // 這 10 行等同 CloudFormation 的 200+ 行
    // VPC、子網路、路由表、IGW、NAT 全部自動建好
    this.vpc = new ec2.Vpc(this, 'Vpc', {
      ipAddresses: ec2.IpAddresses.cidr('10.0.0.0/16'),
      maxAzs: 2,
      natGateways: isProd ? 2 : 1,
      subnetConfiguration: [
        { name: 'public',  subnetType: ec2.SubnetType.PUBLIC,               cidrMask: 24 },
        { name: 'app',     subnetType: ec2.SubnetType.PRIVATE_WITH_EGRESS,  cidrMask: 24 },
        { name: 'data',    subnetType: ec2.SubnetType.PRIVATE_ISOLATED,     cidrMask: 24 },
      ],
    });

    // 一行加上 S3 Gateway Endpoint（第 02 章強調的省錢做法）
    this.vpc.addGatewayEndpoint('S3Endpoint', {
      service: ec2.GatewayVpcEndpointAwsService.S3,
    });

    new rds.DatabaseInstance(this, 'Db', {
      engine: rds.DatabaseInstanceEngine.mysql({
        version: rds.MysqlEngineVersion.VER_8_0,
      }),
      vpc: this.vpc,
      vpcSubnets: { subnetType: ec2.SubnetType.PRIVATE_ISOLATED },
      instanceType: isProd
        ? ec2.InstanceType.of(ec2.InstanceClass.R6G, ec2.InstanceSize.LARGE)
        : ec2.InstanceType.of(ec2.InstanceClass.T3, ec2.InstanceSize.MICRO),
      multiAz: isProd,
      storageEncrypted: true,
      // CDK 自動幫你建 Secrets Manager 密碼並輪替
      credentials: rds.Credentials.fromGeneratedSecret('admin'),
      removalPolicy: isProd
        ? cdk.RemovalPolicy.RETAIN
        : cdk.RemovalPolicy.DESTROY,
    });
  }
}
CDK 最大的價值是 L2/L3 Construct 的「合理預設值」。
  • new ec2.Vpc() 自動建好子網路、路由表、IGW、NAT、並且正確關聯
  • rds.Credentials.fromGeneratedSecret() 自動建 Secrets Manager 並設定輪替
  • 安全群組的 .connections.allowFrom() 自動雙向設定規則
它把「第 02–08 章講的那些最佳實務」變成預設行為，不容易漏掉。 
$ cdk diff                   # 等同 Change Set，部署前必看
$ cdk synth                  # 產生 CloudFormation 範本（想看它做了什麼）
$ cdk deploy NetworkStack
$ cdk destroy NetworkStack
CDK 的抽象是雙面刃。一行 new ec2.Vpc() 會建出幾十個資源——包含兩個 NAT Gateway（每月 US$90）。

第一次用一定要 cdk synth 看它到底產生了什麼，不然帳單會給你驚喜。這是 CDK 新手最常見的意外。

8. SAM：無伺服器專用

AWSTemplateFormatVersion: "2010-09-09"
Transform: AWS::Serverless-2016-10-31    ← 這行讓它變成 SAM

Globals:
  Function:
    Runtime: python3.12
    Architectures: [arm64]              # 便宜 20%
    Timeout: 30
    MemorySize: 512
    Tracing: Active                     # X-Ray
    LoggingConfig:
      LogFormat: JSON
    Environment:
      Variables:
        TABLE_NAME: !Ref OrdersTable

Resources:
  OrderApi:
    Type: AWS::Serverless::HttpApi
    Properties:
      StageName: prod
      Throttle:                         # 第 07 章強調要設限流
        BurstLimit: 200
        RateLimit: 100

  OrderFunction:
    Type: AWS::Serverless::Function
    Properties:
      CodeUri: src/
      Handler: index.handler
      # SAM 自動產生最小權限的 IAM Role
      Policies:
        - DynamoDBCrudPolicy:
            TableName: !Ref OrdersTable
      Events:
        Api:
          Type: HttpApi
          Properties:
            ApiId: !Ref OrderApi
            Path: /orders
            Method: POST
      # 內建金絲雀部署 + 自動回退
      AutoPublishAlias: prod
      DeploymentPreference:
        Type: Canary10Percent5Minutes
        Alarms:
          - !Ref ErrorAlarm

  OrdersTable:
    Type: AWS::Serverless::SimpleTable
    Properties:
      PrimaryKey: { Name: orderId, Type: String }
      # TTL 自動清理（第 05 章）
      SSESpecification: { SSEEnabled: true }
$ sam build
$ sam local invoke OrderFunction -e events/test.json   # 本機測試
$ sam local start-api                                   # 本機跑整個 API
$ sam deploy --guided
$ sam logs -n OrderFunction --tail                     # 即時看日誌
SAM 的三個殺手級功能：
  1. sam local——在本機用 Docker 跑 Lambda 和 API Gateway，不用每次都部署上去測
  2. DeploymentPreference——內建金絲雀部署，綁 CloudWatch 告警自動回退，這是第 07 章提到的最佳實務
  3. Policy Templates——DynamoDBCrudPolicy 會產生剛好夠用的最小權限，不用自己寫 JSON

9. CI/CD 管線

# .github/workflows/infra.yml
name: Infrastructure CI/CD

on:
  pull_request:
    paths: ['infra/**']
  push:
    branches: [main]
    paths: ['infra/**']

permissions:
  id-token: write        # OIDC 需要（第 01 章的無金鑰部署）
  contents: read
  pull-requests: write

jobs:
  plan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      # 不使用任何 Access Key —— 用 OIDC 換臨時憑證
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/GitHubActionsRole
          aws-region: ap-northeast-1

      - uses: hashicorp/setup-terraform@v3

      - name: 格式檢查
        run: terraform fmt -check -recursive

      - name: 安全掃描
        uses: aquasecurity/tfsec-action@v1.0.0

      - name: 成本估算
        uses: infracost/actions/setup@v3
      - run: infracost breakdown --path infra/envs/prod --format json --out-file /tmp/cost.json

      - name: Plan
        working-directory: infra/envs/prod
        run: |
          terraform init
          terraform plan -out=tfplan -no-color | tee plan.txt

      - name: 把 plan 貼到 PR
        uses: actions/github-script@v7
        with:
          script: |
            const fs = require('fs');
            const plan = fs.readFileSync('infra/envs/prod/plan.txt', 'utf8');
            github.rest.issues.createComment({
              issue_number: context.issue.number,
              owner: context.repo.owner, repo: context.repo.repo,
              body: '### Terraform Plan\n```\n' + plan.slice(0, 60000) + '\n```'
            });

  apply:
    needs: plan
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    environment: production      ← GitHub 環境保護：需要人工核准
    steps:
      - uses: actions/checkout@v4
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/GitHubActionsRole
          aws-region: ap-northeast-1
      - run: |
          cd infra/envs/prod
          terraform init
          terraform apply -auto-approve
這個管線的五個重點：
  1. OIDC 而不是 Access Key——GitHub Secrets 裡一個 AWS 金鑰都沒有（第 01 章）
  2. plan 結果貼回 PR——審查的人看得到「這次會改什麼」
  3. tfsec 安全掃描——自動抓出「S3 沒加密」「安全群組開太大」這類問題
  4. Infracost 成本估算——PR 上直接顯示「這次變更每月增加 US$XX」
  5. environment: production——需要指定的人按核准才會 apply
第 4 點特別有價值——很多雲端成本失控是因為「加資源的當下沒人知道要花多少錢」。
正式環境的 apply 不應該全自動。就算 plan 看起來沒問題，也該有人按下核准。理由：
  • plan 不會告訴你「這個變更會不會造成停機」
  • 時機很重要——不該在流量尖峰或週五下午部署基礎設施
應用程式部署可以全自動，基礎設施部署建議保留人工閘門。

10. 實務準則

1
所有東西進 Git包含範本、變數、Runbook。唯一的例外是 state 檔和機密。
2
依變動頻率分層network / security / data / app 分開，改應用層不會動到資料庫。
3
部署前一定看 diffCFN 用 Change Set、Terraform 用 plan -out、CDK 用 cdk diff。特別注意會不會 Replacement。
4
有狀態資源設保護CFN 的 DeletionPolicy: Snapshot、Terraform 的 prevent_destroy、RDS 的 deletion_protection。
5
機密不進程式碼用 Secrets Manager / Parameter Store，IaC 只引用 ARN。
6
鎖定版本Terraform provider、CDK 套件都要鎖主版本，避免自動升級造成非預期變更。
7
定期偵測漂移救火時手動改了設定，事後一定要補回程式碼。排程檢查能抓到漏掉的。
8
用 default_tags讓所有資源自動帶上 Owner / Env / Project，這是第 08 章 FinOps 的基礎。
IaC 最常見的失敗模式：「一半用 IaC，一半手動」。

這比全手動更糟——因為你以為程式碼是真實狀態，實際上不是。下次 apply 時 Terraform 會想把手動改的東西改回去，可能造成意外中斷。

要嘛某個資源完全由 IaC 管，要嘛完全不管。不要混。如果真的必須手動改，改完立刻補進程式碼並跑一次 plan 確認沒有差異。
導入 IaC 的漸進路徑（不要一次全上）：
  1. 新資源一律用 IaC——不要碰既有的
  2. 把既有資源 import 進來——從變動少的開始（VPC、安全群組）
  3. 建立 CI 管線——先只跑 plan，不自動 apply
  4. 開啟漂移偵測——確認沒有人在手動改
  5. 才開始自動 apply——而且正式環境保留人工核准

完整實作 Lab：把整個架構寫成程式碼

約 120 分鐘。這是整個實作篇的收尾。

會建立實際資源（VPC、NAT、RDS）。用 dev 參數（單 NAT、db.t3.micro、單 AZ）把費用壓到最低，跑 2 小時約 US$0.2。
IaC 的好處是清理很簡單——一行 destroy 就全部刪乾淨，不會像手動那樣漏掉資源。

階段一：CloudFormation

  1. 寫 network.yaml：VPC、三層子網路 × 2 AZ、IGW、NAT、路由表
  2. 用 Parameters（EnvName、VpcCidr）與 Conditions（prod 才建第二個 NAT）
  3. 用 !Cidr 自動切子網路，不要手算
  4. Outputs 匯出 VpcId 和子網路 ID
  5. validate-template → deploy 到 dev
  6. 寫 data.yaml 建 RDS，設 DeletionPolicy: Snapshot，用 ImportValue 引用網路層
  7. 改一下 RDS 的 instance class，用 Change Set 看它是不是 Replacement: True
  8. 手動在主控台改一個安全群組規則，然後跑漂移偵測抓出來

階段二：Terraform

  1. 建立 state bucket（版本控制 + 加密 + 封鎖公開）
  2. 用 目錄分離建立 envs/dev 與 envs/prod
  3. 寫 network module，用 for_each 產生子網路
  4. 用 default_tags 自動加上 Owner / Env / Project
  5. RDS 加上 lifecycle { prevent_destroy }，然後試著 destroy 看它擋下來
  6. plan -out=tfplan → 檢視 → apply tfplan
  7. 把階段一手動建的某個資源用 terraform import 納管

階段三：CDK

  1. cdk init + cdk bootstrap
  2. 用 new ec2.Vpc() 建同樣的網路
  3. 先跑 cdk synth，數一數它產生了多少資源、有幾個 NAT Gateway
  4. 比較「10 行 CDK」和「200 行 CloudFormation」
  5. cdk diff → cdk deploy

階段四：CI/CD

  1. 設定 GitHub OIDC（第 01 章），sub 條件鎖到特定 repo 和分支
  2. 寫 workflow：PR 時跑 fmt + validate + plan，並把 plan 貼回 PR
  3. 加上 tfsec 安全掃描
  4. main 分支加 environment: production 需要人工核准
  5. 開一個 PR 改動基礎設施，確認 plan 出現在 PR 留言裡

驗收清單

  • 三種工具都能建出功能相同的 VPC
  • Change Set 正確標示出哪些資源會 Replacement
  • 漂移偵測抓到你手動改的那條規則
  • terraform destroy 對加了 prevent_destroy 的資源會失敗
  • git status 看不到任何 .tfstate 檔
  • GitHub Secrets 裡沒有任何 AWS 金鑰，但 workflow 能成功存取 AWS
  • PR 上看得到完整的 plan 輸出
  • 所有建立的資源都自動帶有 Owner / Env / Project 標籤

加碼挑戰

  1. 加上 Infracost，讓 PR 顯示「這次變更每月增加多少錢」。
  2. 用 CloudFormation StackSets 把同一份範本部署到兩個 region（這就是第 09 章 DR 的基礎）。
  3. 用 SAM 把第 07 章的無伺服器 API 寫成程式碼，包含 Canary10Percent5Minutes 部署。
  4. 故意寫一個有安全問題的範本（S3 公開、SG 開 0.0.0.0/0:22），確認 tfsec 會擋下來。
  5. 寫一個 CDK 單元測試（Template.fromStack()），斷言「RDS 一定有加密且不公開」。

本章重點回顧

  • IaC 的價值：可重複、可審查、可回溯、災難可重建
  • 長期基礎設施用 IaC，一次性實驗用 CLI——不要教條化
  • 選型：只用 AWS → CFN；多雲 → Terraform；團隊會寫程式 → CDK；純無伺服器 → SAM
  • CDK 底層產生 CloudFormation，不是第三種引擎
  • DeletionPolicy 預設是 Delete——有狀態資源一定要設 Retain 或 Snapshot
  • 部署前一定看 Change Set / plan / cdk diff，特別注意 Replacement: True
  • 堆疊依變動頻率分層：network / security / data / app
  • CFN 的 Export 被引用後不能改也不能刪——用 SSM Parameter Store 傳值更彈性
  • Terraform state 要遠端 + 鎖定 + 加密 + 版本控制，且絕不 commit
  • 環境用目錄分離不要用 workspace——避免誤操作正式環境
  • terraform apply 一定要帶 plan 檔案
  • CDK 一行 new ec2.Vpc() 可能建出兩個 NAT（每月 US$90）——先 synth 看清楚
  • CI/CD 用 OIDC 不用 Access Key；plan 貼回 PR；正式環境保留人工核准
  • 最糟的狀態是「一半 IaC 一半手動」——要嘛完全管，要嘛完全不管
IaC 在 SAA-C03 主要考 CloudFormation 的概念（Change Set、DeletionPolicy、巢狀堆疊、StackSets）。去 模擬試題 做最後一輪複習。
