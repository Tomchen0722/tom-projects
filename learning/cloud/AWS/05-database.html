1. 選型決策表

需求關鍵字選這個為什麼
既有 MySQL/PostgreSQL 要上雲、最少改動RDS相容既有應用，託管維運
要 MySQL/PG 相容但效能與可用性更好Aurora3–5 倍效能，6 份副本
個位數毫秒、無限擴展、鍵值查詢DynamoDBNoSQL，無伺服器
流量難以預測、可能歸零Aurora Serverless v2 或 DynamoDB On-Demand自動伸縮，不用時幾乎不收費
TB–PB 級分析、SQL 查詢Redshift資料倉儲，欄式儲存
查詢 S3 上的檔案、偶爾查Athena無伺服器，按掃描量計費
快取、Session、排行榜ElastiCache（Redis）記憶體內，微秒級
圖形關係查詢（社群、詐欺偵測）Neptune圖形資料庫
時序資料（IoT 感測器、監控指標）Timestream時序專用
MongoDB 相容DocumentDB文件資料庫
全文檢索、日誌分析OpenSearch搜尋引擎
不可竄改的帳本QLDB加密驗證的交易紀錄
三個問題就能定案：

① 資料有固定結構而且需要 JOIN？ → 關聯式（RDS / Aurora）
② 查詢模式固定、要求極低延遲與無限擴展？ → DynamoDB
③ 要跑大量聚合分析？ → Redshift（常態）或 Athena（偶爾）
SQL vs NoSQL 最實際的判斷：看查詢模式是否固定。
  • 關聯式：先設計資料，查詢隨便你怎麼寫（WHERE、JOIN、GROUP BY 任意組合）
  • DynamoDB：先確定要怎麼查，再依此設計資料表。查詢模式變了通常要重新設計
所以「需求還在變、報表需求不明確」的系統不要用 DynamoDB——它會逼你在最不確定的時候做最難改的決定。

2. RDS 基礎與引擎選擇

MySQL最普及，生態豐富
PostgreSQL功能最強，支援 JSON、地理資訊、擴充套件
MariaDBMySQL 分支
Oracle企業既有系統，授權貴
SQL Server.NET 生態
AuroraAWS 自研，MySQL/PG 相容
Db2IBM 大型主機遷移
RDS 幫你做什麼、不幫你做什麼：
✅ RDS 負責❌ 你還是要負責
作業系統與資料庫的修補資料表設計與索引
自動備份與 PITRSQL 查詢效能調校
Multi-AZ 故障切換應用程式的連線池管理
硬體更換資料的正確性
RDS 不會讓爛 SQL 變快。慢查詢還是慢查詢，只是你不用管作業系統了。
RDS 沒有作業系統存取權。你不能 SSH 進去、不能裝自訂軟體、不能改設定檔。所有設定都要透過 Parameter Group 和 Option Group 調。

如果你的應用需要資料庫伺服器上的自訂 agent 或特殊擴充，可能得改用 EC2 自架（但那你就要自己管備份、修補、高可用，通常不划算）。 
# Parameter Group：改資料庫參數（等同 my.cnf / postgresql.conf）
$ aws rds create-db-parameter-group \
    --db-parameter-group-name mysql8-custom \
    --db-parameter-group-family mysql8.0 \
    --description "自訂參數"

$ aws rds modify-db-parameter-group \
    --db-parameter-group-name mysql8-custom \
    --parameters \
      "ParameterName=slow_query_log,ParameterValue=1,ApplyMethod=immediate" \
      "ParameterName=long_query_time,ParameterValue=2,ApplyMethod=immediate" \
      "ParameterName=max_connections,ParameterValue=500,ApplyMethod=pending-reboot"
ApplyMethod 有兩種，選錯會有意外：
  • immediate——立刻生效（只有「動態參數」支援）
  • pending-reboot——要重開資料庫才生效
有些參數（例如 max_connections）是靜態的，只能 pending-reboot。改了以為生效、實際上沒有，是常見的困惑。用 describe-db-parameters 看 ApplyType 確認。

3. Multi-AZ vs Read Replica（必考）

Multi-AZRead Replica
目的高可用（HA）效能擴展
複製方式同步非同步
待命副本能不能讀不能（Multi-AZ Cluster 版例外）能
位置同 region 不同 AZ可跨 region
故障時自動切換（1–2 分鐘）要手動提升
資料延遲無有（秒級，負載高時可能更久）
數量1 個待命最多 5 個（Aurora 15 個）
費用兩倍每個副本一份錢
Multi-AZ = 保命　Read Replica = 加速

兩者不是二選一，正式環境通常兩個都要。
最常見的誤解：以為 Read Replica 可以當備援。
  • Read Replica 是非同步複製——主庫掛掉時，最後幾秒的交易可能還沒複製過去
  • 不會自動切換，要人工介入 promote-read-replica
  • 提升之後就變成獨立資料庫，不能再變回副本
要不掉資料的自動故障切換，只有 Multi-AZ 做得到。
考題關鍵字對照：
題目說答案
「高可用」「自動故障切換」「最小停機」Multi-AZ
「讀取效能不足」「報表查詢拖慢主庫」Read Replica
「其他國家使用者讀取太慢」跨區 Read Replica
「災難復原」「整個 region 失效」跨區 Read Replica 或 Aurora Global Database
「讀寫都要擴展」Aurora + 讀寫分離，或改用 DynamoDB
# 開啟 Multi-AZ（既有實例也可以改，會有短暫影響）
$ aws rds modify-db-instance --db-instance-identifier prod-mysql \
    --multi-az --apply-immediately

# 建立 Read Replica
$ aws rds create-db-instance-read-replica \
    --db-instance-identifier prod-mysql-ro-1 \
    --source-db-instance-identifier prod-mysql \
    --db-instance-class db.r6g.large

# 跨區 Read Replica（DR 用）
$ aws rds create-db-instance-read-replica \
    --db-instance-identifier prod-mysql-osaka \
    --source-db-instance-identifier arn:aws:rds:ap-northeast-1:123456789012:db:prod-mysql \
    --region ap-northeast-3

# 檢查副本延遲（要持續監控）
$ aws cloudwatch get-metric-statistics \
    --namespace AWS/RDS --metric-name ReplicaLag \
    --dimensions Name=DBInstanceIdentifier,Value=prod-mysql-ro-1 \
    --start-time 2026-08-05T00:00:00Z --end-time 2026-08-05T12:00:00Z \
    --period 300 --statistics Average Maximum
應用程式要用「兩個 endpoint」。RDS 的 Read Replica 沒有自動的讀寫分離——AWS 給你一個獨立的 endpoint，你的程式要自己判斷「這是讀還是寫」並連到對的地方。

Aurora 有內建的 Reader Endpoint 會自動負載平衡到所有副本，這是 Aurora 比 RDS 方便的地方之一。

4. 實作一：建立生產級 RDS

RDS 是最容易產生意外帳單的服務之一。
· db.t3.micro 在免費方案內（每月 750 小時，12 個月）
· db.r6g.large Multi-AZ 東京區約 US$0.60/小時 = 每月 US$430
· 停止的 RDS 最多 7 天會自動重啟，然後繼續計費
· 儲存空間和備份也另外計費

學習用一律 db.t3.micro、單 AZ、關閉自動備份保留。做完立刻刪除。
# ═══ 步驟 1：DB Subnet Group（指定 RDS 能放在哪些子網路）═══
$ aws rds create-db-subnet-group \
    --db-subnet-group-name db-subnets \
    --db-subnet-group-description "隔離層子網路" \
    --subnet-ids $DB_A $DB_C

# ═══ 步驟 2：把密碼交給 Secrets Manager 管（不要自己想密碼）═══
$ SECRET_ARN=$(aws secretsmanager create-secret \
    --name prod/mysql/master \
    --description "RDS master 密碼" \
    --generate-secret-string \
      '{"SecretStringTemplate":"{\"username\":\"admin\"}","GenerateStringKey":"password","PasswordLength":32,"ExcludeCharacters":"\"@/\\\\"}' \
    --query ARN --output text)

# ═══ 步驟 3：建立資料庫 ═══
$ aws rds create-db-instance \
    --db-instance-identifier prod-mysql \
    --db-instance-class db.r6g.large \
    --engine mysql --engine-version 8.0.35 \
    --allocated-storage 100 --max-allocated-storage 500 \
    --storage-type gp3 --storage-encrypted \
    --master-username admin \
    --manage-master-user-password \
    --db-subnet-group-name db-subnets \
    --vpc-security-group-ids $SG_DB \
    --multi-az \
    --backup-retention-period 7 \
    --preferred-backup-window "18:00-19:00" \
    --preferred-maintenance-window "sun:19:00-sun:20:00" \
    --enable-performance-insights \
    --performance-insights-retention-period 7 \
    --enable-cloudwatch-logs-exports '["error","slowquery"]' \
    --deletion-protection \
    --auto-minor-version-upgrade \
    --no-publicly-accessible

$ aws rds wait db-instance-available --db-instance-identifier prod-mysql
這串參數裡最重要的六個：
  • --no-publicly-accessible — 資料庫絕對不要有公網位址
  • --storage-encrypted — 建立時不加密，之後就不能加（只能快照複製轉換）
  • --manage-master-user-password — 讓 Secrets Manager 管密碼並自動輪替
  • --max-allocated-storage — 啟用儲存自動擴展，空間滿了不會當機
  • --deletion-protection — 防止誤刪
  • --enable-performance-insights — 免費 7 天保留，查慢查詢的神器
加密只能在建立時決定。已存在的未加密 RDS 要加密，流程是：建快照 → 複製快照時指定加密 → 從加密快照還原成新實例 → 切換應用程式連線。這需要停機，而且 endpoint 會變。第一次就開加密。
# 從 Secrets Manager 拿密碼連線（應用程式應該這樣做）
$ aws secretsmanager get-secret-value \
    --secret-id prod/mysql/master \
    --query SecretString --output text | jq -r '.password'

# 取得連線 endpoint
$ aws rds describe-db-instances --db-instance-identifier prod-mysql \
    --query 'DBInstances[0].[Endpoint.Address,Endpoint.Port,DBInstanceStatus]' --output text
更好的做法：完全不用密碼，用 IAM 認證。 
$ aws rds modify-db-instance --db-instance-identifier prod-mysql \
    --enable-iam-database-authentication --apply-immediately

# 應用程式用 IAM 產生 15 分鐘有效的 token 當密碼
$ TOKEN=$(aws rds generate-db-auth-token \
    --hostname prod-mysql.xxx.ap-northeast-1.rds.amazonaws.com \
    --port 3306 --username app_user)
$ mysql -h ... -u app_user --password="$TOKEN" --enable-cleartext-plugin
好處：沒有長期密碼可以外洩、權限用 IAM 統一管理、所有連線都記在 CloudTrail。
限制：每秒最多 200 次新連線，所以應用程式必須用連線池。

5. Aurora 的架構差異

RDS MySQLAurora MySQL
儲存架構一顆 EBS共享儲存層，3 個 AZ × 2 份 = 6 份副本
效能基準約 5 倍
Read Replica 數量515
副本延遲秒級通常 < 100 ms
故障切換1–2 分鐘< 30 秒
儲存擴展手動或自動擴展自動，10 GB 起，最高 128 TB
備份快照持續備份到 S3，不影響效能
費用較低約貴 20%
Aurora 的關鍵設計：運算和儲存分離。
  • 資料存在共享儲存層，所有節點看到同一份
  • Read Replica 不需要複製資料，直接讀共享層 → 這是延遲極低的原因
  • 主節點掛掉，某個副本直接接手同一份儲存 → 這是切換極快的原因
  • 6 份副本，可以掉 2 份不影響寫入、掉 3 份不影響讀取

三個好用的 Aurora 功能

功能做什麼用途
Serverless v2依負載自動伸縮 ACU（0.5–256）流量不固定、開發環境
Global Database跨 region 複製，延遲 < 1 秒災難復原、跨洲讀取
Cloning秒級複製整個資料庫，寫時複製測試環境、資料分析
# Aurora Serverless v2：不用時縮到 0.5 ACU
$ aws rds create-db-cluster \
    --db-cluster-identifier dev-aurora \
    --engine aurora-mysql --engine-version 8.0.mysql_aurora.3.05.2 \
    --serverless-v2-scaling-configuration MinCapacity=0.5,MaxCapacity=8 \
    --master-username admin --manage-master-user-password \
    --db-subnet-group-name db-subnets --vpc-security-group-ids $SG_DB \
    --storage-encrypted

$ aws rds create-db-instance \
    --db-instance-identifier dev-aurora-1 \
    --db-cluster-identifier dev-aurora \
    --db-instance-class db.serverless \
    --engine aurora-mysql

# Cloning：幾秒鐘複製一個 5 TB 的資料庫（只複製指標，不複製資料）
$ aws rds restore-db-cluster-to-point-in-time \
    --db-cluster-identifier test-clone \
    --source-db-cluster-identifier prod-aurora \
    --restore-type copy-on-write --use-latest-restorable-time
Cloning 是 Aurora 最被低估的功能。複製一個 5 TB 的正式資料庫做測試，幾秒鐘完成、幾乎不佔額外空間（只有你改動的部分才真的複製）。傳統做法要還原快照，可能要好幾小時和一整份儲存費。
Aurora 的四種 Endpoint連到哪
Cluster Endpoint（Writer）永遠指向主節點，故障切換自動跟著換
Reader Endpoint自動負載平衡到所有 Read Replica
Custom Endpoint你指定的一組節點（例如「大型分析用的節點」）
Instance Endpoint特定單一節點，除錯用
應用程式一定要用 Cluster Endpoint 和 Reader Endpoint，不要用 Instance Endpoint。用 Instance Endpoint 的話，那個節點故障切換之後你的程式還指著已經變成副本的節點，寫入會失敗。

6. 備份、還原與 PITR

自動備份手動快照
保留期0–35 天永久，直到你刪
支援 PITR可以（精確到秒）不行
刪除資料庫時一起刪掉保留
費用等同資料庫大小的部分免費依大小計費
把 --backup-retention-period 設成 0 等於關閉自動備份，也就關閉了 PITR。正式環境至少設 7 天，關鍵系統設 35 天。

而且刪除 RDS 時自動備份會一起消失——刪除前務必先建一個手動快照（--final-db-snapshot-identifier）。 
# PITR：還原到 5 分鐘前的狀態（會建立一個新實例）
$ aws rds restore-db-instance-to-point-in-time \
    --source-db-instance-identifier prod-mysql \
    --target-db-instance-identifier prod-mysql-restored \
    --restore-time 2026-08-05T02:55:00Z \
    --db-subnet-group-name db-subnets --vpc-security-group-ids $SG_DB

# 查可還原的最早時間點
$ aws rds describe-db-instances --db-instance-identifier prod-mysql \
    --query 'DBInstances[0].[EarliestRestorableTime,LatestRestorableTime]'

# 刪除時一定要留最終快照
$ aws rds delete-db-instance --db-instance-identifier prod-mysql \
    --final-db-snapshot-identifier prod-mysql-final-20260805
還原永遠是建立一個「新的實例」，不會覆蓋原本的。所以還原後你要：
  1. 確認新實例的資料正確
  2. 把應用程式的連線字串指向新的 endpoint（endpoint 名稱不同）
  3. 確認無誤後才刪掉舊的
這代表還原一定會有停機時間。RTO 的估算要把這段切換時間算進去。
災難復原的四種策略與 RDS 對應：
策略RTO / RPORDS 做法成本
Backup & Restore小時 / 小時跨區複製快照最低
Pilot Light10 分鐘 / 分鐘跨區 Read Replica（小規格）低
Warm Standby分鐘 / 秒跨區 Read Replica（正常規格）中
Multi-Site Active秒 / 接近 0Aurora Global Database最高
這張表在 SAA 幾乎每次都會考。記住成本和 RTO 成反比。

7. DynamoDB 核心概念

概念說明
Table資料表，不需要預先定義欄位（除了鍵）
Item一筆資料，最大 400 KB
Partition Key（PK）決定資料存在哪個分區。必填
Sort Key（SK）同一個 PK 內的排序依據。選填
主鍵只有 PK，或 PK + SK 的組合。必須唯一
Item 上限 400 KB。超過就要拆開，或把大內容放 S3 只在 DynamoDB 存指標（這叫 S3 pointer 模式）。存圖片、檔案內容到 DynamoDB 是錯誤用法。

兩種容量模式

On-DemandProvisioned
計費按實際請求數按預留的 RCU/WCU
擴展瞬間，無上限要設 Auto Scaling
適合流量不可預測、有尖峰、新系統流量穩定可預測
價格單價高約 6–7 倍單價低，可買預留容量再省
怎麼選：新系統先用 On-Demand，跑 1–2 個月看清楚流量模式再考慮轉 Provisioned。兩種模式每 24 小時可以切換一次。

流量穩定的話，Provisioned + Auto Scaling 通常能省 50–70%；但如果流量尖峰是平均的 10 倍，Provisioned 反而可能更貴（要預留到尖峰）或會被限流。
容量單位（考試會考計算）

1 RCU = 每秒 1 次「強一致性」讀取 4 KB 以內
　　　　　= 每秒 2 次「最終一致性」讀取 4 KB
1 WCU = 每秒 1 次寫入 1 KB 以內

讀 8 KB、每秒 100 次、最終一致性
→ 8÷4 = 2 個單位 ÷ 2（最終一致）= 1 → 100 RCU
一致性模式行為成本
Eventually Consistent（預設）可能讀到舊資料（通常 1 秒內同步）0.5 RCU
Strongly Consistent一定讀到最新1 RCU
TransactionalACID 交易2 RCU / 2 WCU

8. 分區鍵設計與索引

分區鍵設計錯誤是 DynamoDB 最嚴重的問題，而且事後很難修。DynamoDB 用 PK 的雜湊值決定資料放在哪個實體分區。如果大量資料集中在同一個 PK，就會產生 Hot Partition——那個分區被限流，但整體容量看起來還很空。
❌ 不好的分區鍵為什麼✅ 改成
status（只有 3 種值）基數太低，全擠在 3 個分區orderId
date（今天的資料全在一起）當天所有寫入打同一個分區date#randomSuffix
country（80% 是同一國）分布極度不均country#userId
好的分區鍵三條件：

① 基數高（可能的值很多）
② 存取分布平均（沒有特別熱門的值）
③ 符合你的查詢模式（能直接用它查）

兩種索引

LSI（本地次要索引）GSI（全域次要索引）
分區鍵必須跟主表相同可以不同
建立時機只能在建表時建隨時可增刪
數量上限520
容量共用主表的獨立的 RCU/WCU
一致性支援強一致性只有最終一致性
大小限制同一 PK 下所有項目 ≤ 10 GB無限制
實務上幾乎都用 GSI。LSI 有兩個致命限制：只能建表時建立（需求變了要重建整張表）、10 GB 上限（超過會直接寫入失敗）。除非真的需要強一致性的次要查詢，否則一律用 GSI。
GSI 有兩個容易忽略的行為：
  1. GSI 容量不足會反過來影響主表的寫入被限流。GSI 的 WCU 一定要設得跟主表一樣或更高
  2. 只有包含 GSI 分區鍵的項目才會進索引。這其實是個好用的技巧——叫做 稀疏索引（Sparse Index）
稀疏索引的用法：只有「未處理」的訂單才寫入 pendingFlag 欄位，處理完就刪掉這個欄位。這樣 GSI 裡只會有待處理的訂單，查詢極快且索引很小。

Query vs Scan

QueryScan
做什麼依 PK（可加 SK 條件）查讀整張表再過濾
效率高極低
費用只算讀到的算整張表的容量，就算只回傳 1 筆
正式環境幾乎不應該出現 Scan。一張 100 GB 的表做一次 Scan，就算 filter 之後只回傳 10 筆，你還是要付讀取 100 GB 的錢，而且會把容量吃光導致其他請求被限流。

看到程式碼裡有 Scan，通常代表資料模型設計錯了——應該加一個 GSI 讓它能用 Query。

9. 實作二：DynamoDB 完整操作

# ═══ 建表：單表設計，PK + SK ═══
$ aws dynamodb create-table \
    --table-name Orders \
    --attribute-definitions \
      AttributeName=customerId,AttributeType=S \
      AttributeName=orderDate,AttributeType=S \
      AttributeName=status,AttributeType=S \
    --key-schema \
      AttributeName=customerId,KeyType=HASH \
      AttributeName=orderDate,KeyType=RANGE \
    --billing-mode PAY_PER_REQUEST \
    --global-secondary-indexes '[{
      "IndexName": "status-date-index",
      "KeySchema": [
        {"AttributeName":"status","KeyType":"HASH"},
        {"AttributeName":"orderDate","KeyType":"RANGE"}
      ],
      "Projection": {"ProjectionType":"INCLUDE","NonKeyAttributes":["amount","customerId"]}
    }]' \
    --sse-specification Enabled=true \
    --tags Key=Env,Value=prod

$ aws dynamodb wait table-exists --table-name Orders
ProjectionType 三選一，直接影響費用：
類型索引裡有什麼成本
KEYS_ONLY只有鍵最省，但要拿其他欄位得回主表再查一次
INCLUDE鍵 + 你指定的欄位平衡，實務首選
ALL全部欄位查詢最快，但等於複製一整張表的儲存費
# ═══ 寫入 ═══
$ aws dynamodb put-item --table-name Orders --item '{
    "customerId": {"S": "CUST-001"},
    "orderDate":  {"S": "2026-08-05T10:30:00Z"},
    "status":     {"S": "PENDING"},
    "amount":     {"N": "1580"},
    "items":      {"L": [{"S":"SKU-A"},{"S":"SKU-B"}]}
  }' \
  --condition-expression "attribute_not_exists(customerId)"   # 防止覆蓋既有資料

# ═══ Query：查某客戶 8 月的訂單（效率高）═══
$ aws dynamodb query --table-name Orders \
    --key-condition-expression "customerId = :c AND begins_with(orderDate, :d)" \
    --expression-attribute-values '{
      ":c": {"S": "CUST-001"},
      ":d": {"S": "2026-08"}
    }' \
    --return-consumed-capacity TOTAL

# ═══ 用 GSI 查所有待處理訂單 ═══
$ aws dynamodb query --table-name Orders \
    --index-name status-date-index \
    --key-condition-expression "#s = :st" \
    --expression-attribute-names '{"#s": "status"}' \
    --expression-attribute-values '{":st": {"S": "PENDING"}}'
status 是 DynamoDB 的保留字，不能直接用在表達式裡，要用 --expression-attribute-names 做別名（#s）。保留字有數百個，遇到 ValidationException: Invalid token 就往這裡想。
# ═══ 原子更新（不用先讀再寫）═══
$ aws dynamodb update-item --table-name Orders \
    --key '{"customerId":{"S":"CUST-001"},"orderDate":{"S":"2026-08-05T10:30:00Z"}}' \
    --update-expression "SET #s = :new, updatedAt = :now ADD retryCount :one" \
    --expression-attribute-names '{"#s":"status"}' \
    --expression-attribute-values '{
      ":new":{"S":"SHIPPED"}, ":now":{"S":"2026-08-05T11:00:00Z"},
      ":one":{"N":"1"}, ":old":{"S":"PENDING"}
    }' \
    --condition-expression "#s = :old"    # 樂觀鎖：只有還是 PENDING 才改
--condition-expression 是 DynamoDB 做並行控制的方式。它讓「檢查 + 更新」變成一個原子操作，避免兩個請求同時改同一筆資料造成覆蓋。條件不成立會回傳 ConditionalCheckFailedException，程式要處理這個例外。

三個實用功能

# ① TTL：自動刪除過期資料（免費，不消耗 WCU）
$ aws dynamodb update-time-to-live --table-name Sessions \
    --time-to-live-specification "Enabled=true,AttributeName=expiresAt"
#    expiresAt 要存 Unix timestamp（秒）

# ② Streams：資料變更時觸發 Lambda
$ aws dynamodb update-table --table-name Orders \
    --stream-specification "StreamEnabled=true,StreamViewType=NEW_AND_OLD_IMAGES"

# ③ PITR：35 天內任意時間點還原
$ aws dynamodb update-continuous-backups --table-name Orders \
    --point-in-time-recovery-specification PointInTimeRecoveryEnabled=true
TTL 是省錢神器。Session、快取、日誌這類有時效的資料，設好 TTL 就會自動刪除，完全免費而且不消耗寫入容量。不用寫清理排程。

注意：刪除不是即時的，AWS 通常在過期後 48 小時內刪掉。如果你的邏輯需要「過期就一定讀不到」，程式要自己再檢查一次時間。
DynamoDB Global Tables 是多主寫入。多個 region 都能寫，衝突時用「最後寫入者勝出」解決。這代表可能會掉資料——如果兩個 region 幾乎同時改同一筆，先寫的那筆會被覆蓋且不會有警告。

需要嚴格一致性的場景（例如庫存扣減）不要用 Global Tables 做多region 寫入，改成單一 region 寫入 + 其他 region 唯讀。

10. 快取層：ElastiCache 與 DAX

ElastiCache RedisElastiCache MemcachedDAX

持久化支援不支援不需要
高可用支援（Multi-AZ + 副本）不支援支援
多執行緒否（7.0 起部分支援）是—

選擇很單純：
  • 快取 DynamoDB → DAX（程式幾乎不用改，換個 endpoint 就好）
  • 快取 RDS、存 Session、排行榜、發布訂閱 → Redis
  • 只要單純的鍵值快取且要多執行緒 → Memcached（實務上很少選它）
考試看到「需要持久化」「需要高可用」「需要複雜資料結構」→ 一律選 Redis。

三種快取策略

策略做法優點缺點
Lazy Loading
（Cache-Aside）		查快取 → 沒有就查 DB 再寫入快取只快取真的被用到的資料第一次一定 miss；可能有舊資料
Write-Through寫 DB 時同時寫快取快取永遠是新的寫入變慢；可能快取了沒人用的資料
TTL設定過期時間簡單，限制舊資料的影響要調參數找平衡
實務標準組合：Lazy Loading + TTL。只快取真的被查的資料（省記憶體），再用 TTL 限制資料能舊到什麼程度。純 Write-Through 會快取大量從來沒人查的資料，浪費記憶體。
# DAX：DynamoDB 的快取，程式只要換 endpoint
$ aws dax create-cluster \
    --cluster-name orders-dax \
    --node-type dax.r5.large --replication-factor 3 \
    --iam-role-arn arn:aws:iam::123456789012:role/DAXRole \
    --subnet-group-name dax-subnets --security-group-ids $SG_DAX

# Redis 叢集
$ aws elasticache create-replication-group \
    --replication-group-id session-cache \
    --replication-group-description "Session 快取" \
    --engine redis --cache-node-type cache.r6g.large \
    --num-cache-clusters 2 \
    --automatic-failover-enabled \
    --multi-az-enabled \
    --at-rest-encryption-enabled --transit-encryption-enabled \
    --cache-subnet-group-name cache-subnets --security-group-ids $SG_CACHE
DAX 沒有免費方案，最小的 dax.t3.small 東京區約 US$0.05/小時，三節點約 US$110/月。
Redis cache.t4g.micro 約 US$0.019/小時（免費方案有 750 小時）。
學習用 Redis 的 t4g.micro 就好，不要開 DAX。

完整實作 Lab：RDS + DynamoDB 雙軌

需要第 02 章的 VPC。約 100 分鐘。

這個 Lab 一定要用免費方案規格：RDS 用 db.t3.micro、單 AZ、20 GB gp2；DynamoDB 用 On-Demand（免費方案每月 25 GB 儲存 + 2500 萬次請求）。
這樣費用接近 0。不要開 Multi-AZ、不要開 DAX、不要用 r6g 機型做實驗——那些一天就會花掉數美元。
做完務必刪除，並記得手動快照會永久保留並收費。

階段一：RDS

  1. 建立 DB Subnet Group（用第 02 章的隔離層子網路）
  2. 建立 RDS MySQL：db.t3.micro、單 AZ、加密、不公開存取、--manage-master-user-password
  3. 備份保留設 1 天（省錢但保留 PITR 能力）
  4. 從私有子網路的 EC2（用 SSM 連進去）連上資料庫，建一張表寫幾筆資料
  5. 從公網嘗試連線 → 應該連不到
  6. 建立自訂 Parameter Group，開啟 slow_query_log 與 long_query_time=1
  7. 故意跑一個慢查詢（SELECT SLEEP(3)），到 CloudWatch Logs 找到那筆紀錄

階段二：備份與還原

  1. 建立手動快照
  2. 刪掉一張表（模擬誤刪）
  3. 用 PITR 還原到刪除前一分鐘，建立一個新實例
  4. 連上新實例，確認資料回來了
  5. 比較新舊實例的 endpoint 不同，理解「還原一定要切換連線」

階段三：DynamoDB

  1. 建立 Orders 表：PK=customerId、SK=orderDate、On-Demand、加密
  2. 建立 GSI status-date-index，Projection 用 INCLUDE
  3. 寫入 20 筆訂單，狀態分別是 PENDING / SHIPPED / DONE
  4. 用 Query 查某客戶的訂單，記下 ConsumedCapacity
  5. 用 Scan + filter 查同樣的結果，比較消耗的容量差多少
  6. 用 GSI Query 查所有 PENDING 訂單
  7. 用 condition-expression 做樂觀鎖更新，並故意讓條件失敗一次
  8. 另建一張 Sessions 表，開啟 TTL，寫入一筆 2 分鐘後過期的資料
  9. 開啟 PITR

驗收清單

  • describe-db-instances 的 PubliclyAccessible 是 false、StorageEncrypted 是 true
  • 從公網 telnet 3306 → 不通；從私有 EC2 → 通
  • CloudWatch Logs 的 slowquery log group 裡找得到那筆 SLEEP(3)
  • PITR 還原的新實例有被刪掉的那張表
  • Query 的 ConsumedCapacity 明顯小於 Scan（記下兩個數字）
  • 樂觀鎖條件不成立時回傳 ConditionalCheckFailedException
  • Secrets Manager 裡看得到自動產生的密碼，而且你從沒手動打過它

本章重點回顧

  • 選型三問：要 JOIN → 關聯式；查詢固定要極低延遲 → DynamoDB；大量分析 → Redshift/Athena
  • Multi-AZ 是保命（同步、自動切換）、Read Replica 是加速（非同步、手動提升）
  • Read Replica 不能取代備援——非同步複製可能掉資料
  • RDS 加密只能建立時開；不公開存取；密碼交給 Secrets Manager
  • --max-allocated-storage 開啟儲存自動擴展，避免空間滿了當機
  • 刪 RDS 前務必 --final-db-snapshot-identifier，自動備份會跟著消失
  • Aurora 運算與儲存分離、6 份副本、切換 < 30 秒、Cloning 秒級
  • 應用程式用 Cluster/Reader Endpoint，不要用 Instance Endpoint
  • DR 四策略：Backup&Restore → Pilot Light → Warm Standby → Multi-Site，成本與 RTO 成反比
  • DynamoDB：1 RCU = 4 KB 強一致性讀、1 WCU = 1 KB 寫；最終一致性算一半
  • 分區鍵要基數高、分布平均，否則 Hot Partition
  • LSI 只能建表時建且有 10 GB 上限；實務一律用 GSI
  • 正式環境不該有 Scan——有 Scan 通常代表資料模型設計錯了
  • 快取 DynamoDB 用 DAX，其他用 Redis；策略用 Lazy Loading + TTL
