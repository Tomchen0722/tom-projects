1. 機型命名規則與家族選擇

m6g.2xlarge

m = 家族（用途）　6 = 世代　g = 附加特性　2xlarge = 大小
附加字母意義
gAWS Graviton（ARM 處理器）——同規格便宜約 20%，效能還更好
aAMD 處理器——比 Intel 便宜約 10%
iIntel 處理器（明確標示）
d本機 NVMe 儲存（Instance Store）
n強化網路頻寬
e額外記憶體或儲存
z高時脈 CPU

六大家族

T可爆發型。平常低使用率，偶爾衝高。最便宜，適合開發機、小網站。注意 CPU credit。
M通用型。CPU:記憶體 = 1:4。不知道選什麼就選 M。
C運算優化。CPU:記憶體 = 1:2。批次運算、遊戲伺服器、影音轉檔。
R / X / Z記憶體優化。1:8 到 1:32。資料庫、快取、記憶體內分析。
I / D / H儲存優化。本機高 IOPS NVMe。NoSQL、資料倉儲。
P / G / Inf / Trn加速運算。GPU 或自研晶片。ML 訓練與推論。非常貴。
T 系列的 CPU Credit 是最常見的效能陷阱。
  • t3.micro 的「基準效能」只有 10% 的 vCPU。低於基準時累積 credit，高於基準時消耗
  • credit 用完 → CPU 被強制限制在 10%，網站會突然變得極慢
  • t3 預設是 unlimited 模式——credit 用完會繼續跑，但額外收費（每 vCPU 小時 US$0.05）
  • t2 預設是 standard 模式——用完就限速，不額外收費
症狀：「網站平常很快，流量一大就慢到不能用，但 CPU 使用率看起來才 10%」——那個 10% 就是被限速的證據。
監控：CloudWatch 的 CPUCreditBalance 一直往下掉就要換機型。 
# 查 credit 模式與餘額
$ aws ec2 describe-instance-credit-specifications --instance-ids i-0abc123
$ aws cloudwatch get-metric-statistics \
    --namespace AWS/EC2 --metric-name CPUCreditBalance \
    --dimensions Name=InstanceId,Value=i-0abc123 \
    --start-time 2026-08-04T00:00:00Z --end-time 2026-08-05T00:00:00Z \
    --period 3600 --statistics Average

# 改成 standard（避免 unlimited 產生意外費用）
$ aws ec2 modify-instance-credit-specification \
    --instance-credit-specification InstanceId=i-0abc123,CpuCredits=standard
Graviton（g 結尾）是目前最容易的省錢手段。m7g 比 m7i 便宜約 20%，而且多數工作負載效能還更好。只要你的軟體支援 ARM64（現在絕大多數都支援：Python、Node.js、Java、Go、.NET、Nginx、PostgreSQL、Redis…）就該用。

唯一要注意：Docker 映像檔要是 arm64 版，或用 multi-arch 建置。

2. 五種付費方式（省錢核心）

On-Demand按秒計費，隨開隨關。基準價，最貴但最有彈性。
Savings Plans承諾「每小時花 $X」用 1 或 3 年。省 27~72%。彈性最高。
Reserved Instance承諾「特定機型」1 或 3 年。省 30~72%。可在市集轉售。
Spot用 AWS 的閒置容量。省 70~90%，但可能被 2 分鐘通知後收回。
Dedicated Host整台實體伺服器。最貴，用於自帶授權（BYOL）或合規要求。

Savings Plans vs Reserved Instance（考試常混淆）

Compute Savings PlansEC2 Instance SPStandard RIConvertible RI
承諾什麼每小時花費每小時花費 + 機型家族特定機型特定機型（可換）
能換機型家族可以不行不行可以（同價或更貴）
能換 region可以不行不行不行
涵蓋 Fargate / Lambda可以不行不行不行
最高折扣66%72%72%66%
可轉售不行不行可以不行
Savings Plans 和 RI 都是付錢的承諾，簽下去就不能退。1 年或 3 年期間，就算你不用了也要繼續付。

導入前務必先確認：
  • 用 Cost Explorer 的建議功能看過去 30/60 天的實際使用量
  • 只承諾「穩定基線」的部分，浮動的部分留給 On-Demand 或 Spot
  • 常見做法：基線 70% 用 SP、彈性 30% 用 On-Demand/Spot
  • 新創或需求不確定的公司，先跑 3~6 個月再簽
這是實際的財務承諾，簽約前建議跟財務或主管確認過。 
# 讓 AWS 幫你算該買多少（免費，強烈建議先跑）
$ aws ce get-savings-plans-purchase-recommendation \
    --savings-plans-type COMPUTE_SP \
    --term-in-years ONE_YEAR \
    --payment-option NO_UPFRONT \
    --lookback-period-in-days THIRTY_DAYS

# 看目前 SP / RI 的使用率與涵蓋率
$ aws ce get-savings-plans-utilization \
    --time-period Start=2026-07-01,End=2026-08-01
$ aws ce get-reservation-coverage \
    --time-period Start=2026-07-01,End=2026-08-01
兩個指標要一起看：
  • Utilization（使用率）——買了的 SP/RI 有沒有用滿。低於 95% 代表買太多，在浪費錢
  • Coverage（涵蓋率）——多少 On-Demand 花費被 SP/RI 蓋住。低於 70% 代表還可以再買
理想狀態：Utilization 接近 100%、Coverage 在 70~80%。

付款方式的折扣差異

付款方式折扣現金流
No Upfront（不預付）最低最好，每月付
Partial Upfront（部分預付）中等約一半先付
All Upfront（全額預付）最高（多約 5~7%）最差，一次付清
實務上多數公司選 No Upfront 或 Partial Upfront——多出來那 5~7% 的折扣，通常不值得綁住一整年的現金。除非公司有多餘現金且會計上偏好一次認列。

3. Spot 實戰與中斷處理

Spot 用的是 AWS 的閒置容量，價格只有 On-Demand 的 10~30%。代價是 AWS 需要那些容量時會把你的機器收回，只給 2 分鐘通知。

✅ 適合 Spot❌ 不適合 Spot
批次運算、資料處理資料庫
CI/CD build agent有狀態的單體應用
影音轉檔、算圖需要固定 IP 的服務
ML 訓練（有 checkpoint）License 綁機器的軟體
無狀態的 Web 層（配 ASG）做到一半不能中斷的工作
Spot 的判斷標準：

「這台機器突然消失，我的系統會不會有事？」
不會 → 用 Spot　　會 → 不要用

接收中斷通知並優雅退場

#!/bin/bash
# 放進 user-data，背景執行，監聽中斷通知
while true; do
  TOKEN=$(curl -sX PUT "http://169.254.169.254/latest/api/token" \
      -H "X-aws-ec2-metadata-token-ttl-seconds: 60")

  # 沒有中斷時回 404，有中斷時回 200 + JSON
  ACTION=$(curl -s -H "X-aws-ec2-metadata-token: $TOKEN" \
      http://169.254.169.254/latest/meta-data/spot/instance-action)

  if [[ "$ACTION" == *"action"* ]]; then
    echo "$(date) 收到 Spot 中斷通知，開始善後"
    # ① 從 ALB 目標群組移除自己（停止接新流量）
    aws elbv2 deregister-targets --target-group-arn $TG_ARN \
        --targets Id=$(ec2-metadata --instance-id | cut -d' ' -f2)
    # ② 存 checkpoint
    /opt/app/save-checkpoint.sh
    # ③ 等現有請求處理完
    sleep 90
    break
  fi
  sleep 5
done
2 分鐘看起來很短，但夠用。關鍵是提早把自己從流量路徑移除——先 deregister，讓 ALB 停止送新請求，再處理完手上的工作。

如果你的應用連 2 分鐘都無法優雅結束，那它本來就不該用 Spot，甚至也不適合 Auto Scaling。

企業標準做法：混合容量的 ASG

# 用 Launch Template + 混合實例政策
$ aws autoscaling create-auto-scaling-group \
    --auto-scaling-group-name web-asg \
    --min-size 2 --max-size 20 --desired-capacity 6 \
    --vpc-zone-identifier "$APP_A,$APP_C" \
    --mixed-instances-policy '{
  "LaunchTemplate": {
    "LaunchTemplateSpecification": {
      "LaunchTemplateName": "web-lt", "Version": "$Latest"
    },
    "Overrides": [
      { "InstanceType": "m7g.large" },
      { "InstanceType": "m6g.large" },
      { "InstanceType": "m7i.large" },
      { "InstanceType": "m6i.large" }
    ]
  },
  "InstancesDistribution": {
    "OnDemandBaseCapacity": 2,
    "OnDemandPercentageAboveBaseCapacity": 25,
    "SpotAllocationStrategy": "capacity-optimized"
  }
}'
這段設定的實際意義：
  • 前 2 台一定是 On-Demand（保底容量，就算 Spot 全被收回也不會全掛）
  • 超過 2 台之後，25% On-Demand + 75% Spot
  • 列 4 種機型——Spot 容量是按機型分配的，選項愈多愈不容易被收回
  • capacity-optimized = 「挑目前閒置容量最多的機型」，中斷率最低（不是挑最便宜的）
這個組合通常能省下 50~60% 的運算費用，而可用性幾乎不受影響。是 SAA 考試很愛的答案。 
# 查各機型的 Spot 中斷頻率（決策前必看）
$ aws ec2 describe-spot-price-history \
    --instance-types m7g.large \
    --product-descriptions "Linux/UNIX" \
    --start-time $(date -u -d '7 days ago' +%Y-%m-%dT%H:%M:%S) \
    --query 'SpotPriceHistory[].[AvailabilityZone,SpotPrice,Timestamp]' --output table
AWS 也有一個公開的 Spot Instance Advisor 網頁，直接列出每個機型的「折扣幅度」和「中斷頻率」（<5%、5-10%、>20%）。挑機型時看那個最快——選折扣大且中斷率 <5% 的。

  • Auto Scaling 需要它——ASG 只能用 Launch Template（或舊的 Launch Configuration）

  • 設定集中，開 10 台不用打 10 次參數

Stop / Reboot / Terminate / Hibernate 的差別

EBS 根磁碟Instance Store公網 IP私有 IP還收費嗎
Reboot保留保留保留保留繼續
Stop保留清空釋放（除非 EIP）保留只收 EBS
Hibernate保留（含記憶體內容）清空釋放保留只收 EBS
Terminate依 DeleteOnTermination清空釋放釋放停止
Stop 之後公網 IP 會變。如果你把那個 IP 寫進 DNS 或防火牆白名單，重開之後就全部失效。需要固定 IP 就用 Elastic IP（但要記得 EIP 現在無論有沒有綁定都收費）。

更好的做法：用 ALB 或 Route 53，讓後端機器的 IP 可以自由變動。

防止誤刪

# 開啟終止保護（正式環境的機器一定要開）
$ aws ec2 modify-instance-attribute \
    --instance-id $INSTANCE_ID --disable-api-termination

# 連 stop 都不准（資料庫類的機器）
$ aws ec2 modify-instance-attribute \
    --instance-id $INSTANCE_ID --disable-api-stop

5. User Data 與開機自動化

User Data 是機器第一次開機時執行的腳本，用來安裝軟體、拉設定、註冊到服務。

#!/bin/bash
# 把所有輸出寫進 log，方便排錯（很重要）
exec > >(tee /var/log/user-data.log | logger -t user-data -s 2>/dev/console) 2>&1
set -euxo pipefail

# ── 更新與安裝 ──
dnf update -y
dnf install -y nginx amazon-cloudwatch-agent

# ── 從 Parameter Store 拉設定（不要硬寫在腳本裡）──
DB_HOST=$(aws ssm get-parameter --name /app/prod/db-host \
    --query Parameter.Value --output text --region ap-northeast-1)

# ── 密碼從 Secrets Manager 拉（會自動輪替）──
DB_PASS=$(aws secretsmanager get-secret-value --secret-id prod/db/password \
    --query SecretString --output text --region ap-northeast-1 | jq -r .password)

# ── 寫設定檔 ──
cat > /etc/app/config.yml <<EOF
database:
  host: ${DB_HOST}
  password: ${DB_PASS}
EOF
chmod 600 /etc/app/config.yml

# ── 掛載 EBS 資料碟（如果有）──
if [ -b /dev/nvme1n1 ] && ! blkid /dev/nvme1n1; then
  mkfs -t xfs /dev/nvme1n1
fi
mkdir -p /data
# 用 UUID 而不是裝置名稱，nofail 避免磁碟不在時開不了機
UUID=$(blkid -s UUID -o value /dev/nvme1n1)
echo "UUID=$UUID /data xfs defaults,nofail 0 2" >> /etc/fstab
mount -a

# ── 啟動服務 ──
systemctl enable --now nginx
systemctl enable --now amazon-cloudwatch-agent

echo "user-data 完成於 $(date)"
User Data 的五個重點：
  1. 預設只在第一次開機執行一次。改了 user-data 再 stop/start 不會重跑
  2. 以 root 身分執行，不需要 sudo
  3. 大小上限 16 KB（base64 編碼前）。超過就改成「下載一個腳本再執行」
  4. 絕對不要把密碼寫在裡面——user data 可以被 describe-instance-attribute 讀出來，也能從 metadata endpoint 拿到。用 Secrets Manager
  5. 第一行一定要 #!/bin/bash，不然不會被當成腳本
# 排錯：看 user-data 有沒有跑、跑到哪裡失敗
$ sudo cat /var/log/cloud-init-output.log
$ sudo cat /var/log/user-data.log

# 讓 user-data 每次開機都跑（少數情況需要）
$ sudo rm -f /var/lib/cloud/instances/*/sem/config_scripts_user

# 從外面讀某台機器的 user-data（確認自己有沒有不小心放密碼）
$ aws ec2 describe-instance-attribute \
    --instance-id $INSTANCE_ID --attribute userData \
    --query UserData.Value --output text | base64 -d
更好的做法：用 Golden AMI 取代冗長的 User Data。
  • User Data 開機才裝軟體 → 開機要 3~5 分鐘，Auto Scaling 反應慢，而且套件庫掛掉就開不起來
  • Golden AMI 事先烤好 → 開機 30 秒就能服務，而且每台完全一致
用 EC2 Image Builder 或 Packer 自動化建立 AMI，加進 CI/CD。User Data 只留下「拉環境專屬設定」這種必須在開機時做的事。

6. EBS 五種類型與 IOPS 計算

類型用途IOPS吞吐量東京區價格
gp3（SSD）預設首選3,000 基礎，可到 16,000125 MB/s 基礎，可到 1,000US$0.096/GB/月
gp2（SSD）已過時3 IOPS/GB（最低 100，最高 16,000）最高 250 MB/sUS$0.12/GB/月
io2 Block Express高效能資料庫最高 256,000最高 4,000 MB/sUS$0.142/GB + IOPS 費
st1（HDD）大檔循序讀寫、日誌低（不能開機）最高 500 MB/sUS$0.054/GB/月

gp3 永遠比 gp2 好，沒有例外。
  • 便宜 20%（US$0.096 vs US$0.12 每 GB）
  • IOPS 和容量脫鉤——gp2 要 3000 IOPS 得買 1000 GB，gp3 買 20 GB 就有 3000
  • IOPS 和吞吐量可以獨立調整
  • 可以線上轉換，不用停機
如果你的帳號還有 gp2，現在就全部轉成 gp3，這是最無痛的省錢動作。 
# 找出所有還在用 gp2 的磁碟
$ aws ec2 describe-volumes \
    --filters Name=volume-type,Values=gp2 \
    --query 'Volumes[].[VolumeId,Size,State,Attachments[0].InstanceId]' --output table

# 一鍵轉成 gp3（線上進行，不用停機）
$ aws ec2 modify-volume --volume-id vol-0abc123 \
    --volume-type gp3 --iops 3000 --throughput 125

# 批次轉換全部
$ aws ec2 describe-volumes --filters Name=volume-type,Values=gp2 \
    --query 'Volumes[].VolumeId' --output text | tr '\t' '\n' | \
  while read v; do
    echo "轉換 $v"
    aws ec2 modify-volume --volume-id "$v" --volume-type gp3
  done

# 查轉換進度
$ aws ec2 describe-volumes-modifications --volume-ids vol-0abc123
擴大磁碟是兩個步驟，很多人只做第一步然後困惑「空間沒變大」。 
# ① AWS 端擴大磁碟
$ aws ec2 modify-volume --volume-id vol-0abc123 --size 100

# ② 在 OS 裡擴大分割區和檔案系統（必做！）
$ sudo growpart /dev/nvme0n1 1        # 擴大分割區
$ sudo xfs_growfs /                   # XFS
$ sudo resize2fs /dev/nvme0n1p1       # ext4
$ df -h                               # 確認
另外：EBS 磁碟只能變大，不能變小。要縮小只能建一個小的、把資料複製過去。

IOPS 到底夠不夠？怎麼算

需要的 IOPS ≈ 每秒交易數 × 每筆交易的 I/O 次數

吞吐量(MB/s) = IOPS × 每次 I/O 大小

gp3 基礎 3000 IOPS × 16 KB = 48 MB/s（但基礎吞吐量上限是 125 MB/s）
# 用 CloudWatch 看實際用了多少 IOPS
$ aws cloudwatch get-metric-statistics \
    --namespace AWS/EBS --metric-name VolumeReadOps \
    --dimensions Name=VolumeId,Value=vol-0abc123 \
    --start-time 2026-08-04T00:00:00Z --end-time 2026-08-05T00:00:00Z \
    --period 300 --statistics Sum

# 關鍵指標：VolumeQueueLength 持續 > 1 代表磁碟撐不住
# 在機器裡用 iostat 也看得到
$ iostat -xz 1
#   %util 接近 100 且 await 很高 → I/O 是瓶頸
EBS 的效能也受機型限制。t3.micro 就算掛 io2 也跑不到高 IOPS，因為機器本身的 EBS 頻寬有上限。要高 I/O 效能，機型要選支援 EBS 最佳化的（現代機型多半預設開啟）。用 describe-instance-types 看 EbsInfo.EbsOptimizedInfo。

加密

# 帳號層級預設加密（強烈建議開，新磁碟自動加密）
$ aws ec2 enable-ebs-encryption-by-default
$ aws ec2 get-ebs-encryption-by-default
既有的未加密磁碟不能直接加密。流程是：建快照 → 複製快照時指定加密 → 從加密快照建新磁碟 → 換掛。要停機。

所以一開始就開啟預設加密。加密對效能的影響幾乎測不出來，沒有理由不開。

7. 快照、AMI 與備份策略

Snapshot（快照）AMI（映像檔）
內容單一 EBS 磁碟的資料一或多個快照 + 開機設定（機型、核心、權限）
用途備份資料、換磁碟開新機器
存在哪S3（但你看不到那個 bucket），增量儲存
跨區可複製可複製
快照是「增量」的，但刪除很聰明。第一份快照存全部，之後只存變動的區塊。刪掉中間某一份快照，AWS 會自動把它獨有的區塊合併到下一份，所以你永遠可以用剩下的任何一份還原。不用擔心「刪了中間那份會不會讓後面的壞掉」。
# 建快照
$ SNAP_ID=$(aws ec2 create-snapshot \
    --volume-id vol-0abc123 \
    --description "web-01 root before upgrade" \
    --tag-specifications 'ResourceType=snapshot,Tags=[{Key=Name,Value=web-01-pre-upgrade}]' \
    --query SnapshotId --output text)

$ aws ec2 wait snapshot-completed --snapshot-ids $SNAP_ID

# 從快照建新磁碟
$ aws ec2 create-volume --snapshot-id $SNAP_ID \
    --availability-zone ap-northeast-1a --volume-type gp3

# 建 AMI（--no-reboot 不重開機，但檔案系統可能不一致）
$ aws ec2 create-image \
    --instance-id $INSTANCE_ID \
    --name "web-golden-$(date +%Y%m%d)" \
    --description "Golden AMI with nginx + agent" \
    --no-reboot
--no-reboot 有風險。它不會重開機（服務不中斷），但檔案系統緩衝區的資料可能還沒寫入磁碟，做出來的 AMI 可能檔案不完整。

正確做法：建 AMI 前先在機器裡 sync 並暫停寫入，或乾脆讓它重開機。資料庫類的機器絕對不要用 --no-reboot 做 AMI。

自動備份：Data Lifecycle Manager

# DLM 依標籤自動建快照並自動刪除舊的 —— 免費
$ aws dlm create-lifecycle-policy \
    --execution-role-arn arn:aws:iam::123456789012:role/AWSDataLifecycleManagerDefaultRole \
    --description "每日快照保留 7 天" \
    --state ENABLED \
    --policy-details '{
  "PolicyType": "EBS_SNAPSHOT_MANAGEMENT",
  "ResourceTypes": ["VOLUME"],
  "TargetTags": [{ "Key": "Backup", "Value": "daily" }],
  "Schedules": [{
    "Name": "DailySnapshots",
    "CreateRule": { "Interval": 24, "IntervalUnit": "HOURS", "Times": ["19:00"] },
    "RetainRule": { "Count": 7 },
    "CopyTags": true
  }]
}'
DLM 完全免費（只付快照的儲存費）。做法是幫要備份的磁碟打上 Backup=daily 標籤，DLM 就會自動處理。不用寫 Lambda、不用維護排程。

需要更完整的備份（RDS、DynamoDB、EFS、跨帳號、合規報表）就用 AWS Backup，它是統一的備份服務，但要另外收費。
備份不等於災難復原。快照預設只存在同一個 region。整個 region 出事（很罕見但發生過）你的備份也一起沒了。

合規或關鍵系統要做跨區複製： 
$ aws ec2 copy-snapshot \
    --source-region ap-northeast-1 \
    --source-snapshot-id $SNAP_ID \
    --region ap-northeast-3 \
    --encrypted --description "DR copy"
也可以考慮 快照封存（Archive）——不常還原的快照轉到封存層，儲存費省 75%，但還原要 24~72 小時。

8. 儲存選型：EBS / Instance Store / EFS / S3

類型區塊區塊檔案（NFS）物件

（io2 多重掛載最多 16）		1 台上千台不掛載，走 API

選型的三個問題：

要當開機磁碟或需要單機高效能？→ EBS
多台機器要同時讀寫同一份檔案？→ EFS
存圖片、影片、備份、靜態檔案？→ S3（最便宜）
EBS 綁定 AZ，這是常見的設計陷阱。在 ap-northeast-1a 建的磁碟，不能掛到 1c 的機器上。要跨 AZ 只能：建快照 → 在另一個 AZ 從快照建新磁碟。

所以「EC2 掛 EBS」這種架構天生無法跨 AZ 高可用。真的需要共享儲存就用 EFS。
EFS 比 EBS 貴將近 4 倍（US$0.36 vs US$0.096 每 GB）。不要因為「方便」就把所有東西都放 EFS。

省錢做法：開啟 Lifecycle Management，30 天沒存取的檔案自動轉到 Infrequent Access 層（US$0.027/GB，省 92%），讀取時才收少量取回費。多數檔案系統的資料都是「寫了就很少再讀」，這個設定通常能省下 70% 以上。
# 建立 EFS 並開啟生命週期
$ FS_ID=$(aws efs create-file-system \
    --performance-mode generalPurpose \
    --throughput-mode elastic \
    --encrypted \
    --tags Key=Name,Value=shared-data \
    --query FileSystemId --output text)

$ aws efs put-lifecycle-configuration --file-system-id $FS_ID \
    --lifecycle-policies \
      '[{"TransitionToIA":"AFTER_30_DAYS"},{"TransitionToPrimaryStorageClass":"AFTER_1_ACCESS"}]'

# 每個 AZ 都要建 mount target
$ aws efs create-mount-target --file-system-id $FS_ID \
    --subnet-id $APP_A --security-groups $SG_EFS
$ aws efs create-mount-target --file-system-id $FS_ID \
    --subnet-id $APP_C --security-groups $SG_EFS

# 在 EC2 上掛載（用 efs-utils，支援加密傳輸與 IAM 認證）
$ sudo dnf install -y amazon-efs-utils
$ sudo mkdir -p /mnt/efs
$ sudo mount -t efs -o tls,iam $FS_ID:/ /mnt/efs

# 寫進 fstab（記得 _netdev）
$ echo "$FS_ID:/ /mnt/efs efs _netdev,tls,iam 0 0" | sudo tee -a /etc/fstab
EFS 的安全群組要開 2049（NFS）。忘了開的症狀是 mount 指令卡住幾分鐘然後 timeout，沒有明確錯誤訊息。這是 EFS 最常見的卡關點。
Instance Store 的正確用途：暫存、快取、shuffle 空間。它是實體接在主機上的 NVMe，速度極快（微秒級），而且不額外收費（含在機器價格裡）。但機器一 stop 資料就沒了。適合放 Spark 的中間結果、資料庫的暫存表空間、影片轉檔的工作目錄。絕對不要放唯一一份資料。

9. 放置群組與網路效能

類型做什麼用途風險
Cluster擠在同一個機架HPC、低延遲叢集運算單點故障——機架掛了全掛
Spread分散到不同硬體少量關鍵機器（每 AZ 最多 7 台）數量受限
Partition分成多個分區，區間硬體隔離HDFS、Cassandra、Kafka—
怎麼記：
  • Cluster = 擠在一起 → 追求速度，犧牲可用性
  • Spread = 散開 → 追求可用性，數量有限
  • Partition = 分組散開 → 大型分散式系統，每組資料有副本在不同分區
考試看到「HPC、最低延遲、最高網路吞吐」→ Cluster；看到「關鍵應用、避免同時故障」→ Spread；看到「Hadoop、Cassandra、Kafka」→ Partition。 
$ aws ec2 create-placement-group \
    --group-name hpc-cluster --strategy cluster

$ aws ec2 create-placement-group \
    --group-name critical-spread --strategy spread

$ aws ec2 run-instances --launch-template LaunchTemplateName=web-lt \
    --placement GroupName=hpc-cluster \
    --subnet-id $APP_A --count 4

技術做什麼適合

Cluster Placement Group 的兩個限制：
  • 不能跨 AZ——它的目的就是擠在一起
  • 容量不足時會失敗——一次把所有機器開起來（用同一個 run-instances 呼叫）成功率最高。分批開很容易撞到「該機架沒空間了」

10. 成本優化實戰清單

以下每一項都是實際能省下錢的動作，按投入產出比排序。前五項幾乎沒有風險，建議立刻做。
1
gp2 全部轉 gp3省 20% 磁碟費，線上轉換不用停機、沒有任何風險。
2

3
釋放沒用的 Elastic IP2024 年起所有公網 IPv4 每小時收 US$0.005。
4
刪掉過舊的快照與 AMI用 DLM 自動管理保留期限。三年前的 AMI 沒人會用。
5
開發／測試機下班自動關機只在上班時間開 = 省 70%（週一到五 9-19 點 = 50/168 小時）。
6
x86 換 Graviton省 20%，前提是軟體支援 ARM64。先在測試環境驗證。
7
Right Sizing看 CloudWatch 的 CPU / 記憶體使用率，長期低於 20% 就降規格。Compute Optimizer 會直接給你建議。
8
無狀態工作負載改用 Spot配合混合 ASG，省 50~60% 運算費。
9
穩定基線買 Savings Plans省 27~72%。但這是財務承諾，先確認過使用量再簽。
10
建 VPC Endpoint 取代 NAT 流量S3 / DynamoDB 的 Gateway Endpoint 免費（見第 02 章）。

找出浪費的腳本

#!/bin/bash
# ── ① 沒掛載的 EBS 磁碟 ──
echo "=== 未掛載的磁碟 ==="
aws ec2 describe-volumes --filters Name=status,Values=available \
  --query 'Volumes[].[VolumeId,Size,VolumeType,CreateTime]' --output table

# ── ② 沒綁定的 Elastic IP ──
echo "=== 閒置的 EIP ==="
aws ec2 describe-addresses \
  --query 'Addresses[?AssociationId==null].[PublicIp,AllocationId]' --output table

# ── ③ 還在用 gp2 的磁碟 ──
echo "=== 還沒轉 gp3 的磁碟 ==="
aws ec2 describe-volumes --filters Name=volume-type,Values=gp2 \
  --query 'Volumes[].[VolumeId,Size]' --output table

# ── ④ 停機超過 30 天的機器（磁碟還在收費）──
echo "=== 長期停機的機器 ==="
aws ec2 describe-instances --filters Name=instance-state-name,Values=stopped \
  --query 'Reservations[].Instances[].[InstanceId,Tags[?Key==`Name`].Value|[0],StateTransitionReason]' \
  --output table

# ── ⑤ 沒有 Owner 標籤的機器（找不到主人的孤兒資源）──
echo "=== 沒有 Owner 標籤 ==="
aws ec2 describe-instances \
  --query 'Reservations[].Instances[?!not_null(Tags[?Key==`Owner`].Value)].[InstanceId,InstanceType]' \
  --output table

# ── ⑥ AWS 官方的降規格建議 ──
echo "=== Compute Optimizer 建議 ==="
aws compute-optimizer get-ec2-instance-recommendations \
  --query 'instanceRecommendations[?finding==`OVER_PROVISIONED`].[instanceArn,currentInstanceType,recommendationOptions[0].instanceType]' \

下班自動關機

# 用 EventBridge + SSM Automation，不用寫 Lambda
# 每天 20:00 (台北時間 = UTC 12:00) 關掉所有 AutoStop=true 的機器

$ aws events put-rule \
    --name stop-dev-instances \
    --schedule-expression "cron(0 12 ? * MON-FRI *)" \
    --description "平日 20:00 (JST/CST) 關閉開發機"

# 早上 08:30 開機
$ aws events put-rule \
    --name start-dev-instances \
    --schedule-expression "cron(30 0 ? * MON-FRI *)"
下班關機的效果比想像中大。一週 168 小時，只開週一到五的 9:00–19:00 = 50 小時。省下 70%。

一台 m7g.large（US$71/月）→ 變成 US$21/月。20 台開發機一年就省下 US$12,000。這是所有省錢手段裡投報率最高的。
做成本優化前，先確認標籤策略。沒有 Owner、Env、Project 標籤的話：
  • 你分不出哪台是誰的、能不能關
  • Cost Explorer 沒辦法按專案拆帳
  • 自動化腳本不敢動任何東西

完整實作 Lab：Golden AMI + 混合容量 + 成本優化

需要第 02 章建好的 VPC。約 100 分鐘。

用 t4g.micro（免費方案內）做這個 Lab，運算費用接近 0。
EBS 20 GB × 幾台約 US$0.06/天。做完務必執行清理步驟，特別是快照和 AMI——它們不會自己消失。

階段一：開機器與 User Data

  1. 用 SSM Parameter 取得最新的 AL2023 arm64 AMI ID
  2. 建立 Launch Template：t4g.micro、gp3 20GB 加密、IMDSv2 required、掛 SSM Role、完整標籤
  3. 寫 User Data：安裝 nginx、寫一個顯示主機名稱的首頁、輸出導向 /var/log/user-data.log
  4. 在私有子網路開一台，不給公網 IP
  5. 用 aws ssm start-session 連進去，確認 nginx 有起來
  6. 檢查 /var/log/cloud-init-output.log 確認 user-data 完整執行

階段二：Golden AMI

  1. 在機器裡 sync，然後建立 AMI（這次不要用 --no-reboot）
  2. 用這個 AMI 建一個新的 Launch Template 版本，把 User Data 的安裝步驟拿掉
  3. 用新版本開一台，比較開機到服務可用的時間差

階段三：混合容量 ASG

  1. 建立 ASG：min 2 / max 6 / desired 2，跨兩個 AZ
  2. 設定 混合實例政策：OnDemandBaseCapacity=1、上面 25% On-Demand、列 4 種機型、strategy 用 capacity-optimized
  3. 用 describe-auto-scaling-groups 確認實際開出來的機器有 On-Demand 也有 Spot（看 InstanceLifecycle 欄位）

階段四：儲存實作

  1. 建立一顆 gp2 磁碟掛上去，然後用 modify-volume 線上轉成 gp3，觀察轉換過程中服務不中斷
  2. 把它從 10 GB 擴大到 20 GB，在 OS 裡執行 growpart + xfs_growfs
  3. 建立 EFS，兩個 AZ 都建 mount target，開啟 30 天轉 IA 的生命週期
  4. 兩台不同 AZ 的機器同時掛載 EFS，在一台寫檔案、另一台立刻讀得到
  5. 建立 DLM 政策：對 Backup=daily 標籤的磁碟每日快照、保留 7 份

階段五：成本盤點

  1. 執行第 10 節的浪費盤點腳本，看看你的帳號有沒有孤兒資源
  2. 查 Compute Optimizer 的建議
  3. 建立 EventBridge 規則，平日 20:00 關閉 AutoStop=true 的機器

驗收清單

  • 私有子網路的機器沒有公網 IP，但 SSM 連得進去
  • describe-instances 的 MetadataOptions.HttpTokens 是 required
  • Golden AMI 開出來的機器，開機到 nginx 可服務 < 60 秒
  • ASG 裡同時有 spot 和 On-Demand（InstanceLifecycle 欄位）
  • gp3 轉換期間 df -h 一直正常，服務沒中斷
  • 兩個 AZ 的機器對同一個 EFS 路徑看到相同內容
  • describe-volumes --filters Name=status,Values=available 是空的（沒有孤兒磁碟）
  • describe-addresses 沒有未綁定的 EIP

本章重點回顧

  • 機型命名：家族 + 世代 + 特性 + 大小；g = Graviton，便宜 20% 效能更好
  • T 系列有 CPU Credit；t3 預設 unlimited 會額外收費，用完會被限速到 10%
  • Compute SP 最有彈性（可換家族、換 region、涵蓋 Fargate/Lambda）；Standard RI 折扣最高但綁死機型
  • SP / RI 是不可退的財務承諾，簽之前先看 Cost Explorer 建議，只承諾穩定基線
  • Spot 省 70~90%，判準是「這台突然消失會不會有事」；企業標準是混合容量 ASG + capacity-optimized
  • AMI ID 不要硬寫，用 SSM Parameter 取得最新版
  • 用 Launch Template 不要用 run-instances 裸開；Launch Configuration 已過時
  • System Status 失敗 → stop/start（換實體機）；Instance Status 失敗 → 查 OS
  • User Data 只跑一次、以 root 執行、上限 16 KB、絕不放密碼
  • gp3 永遠優於 gp2，線上轉換無風險；擴大磁碟要兩步（AWS 端 + OS 端）
  • EBS 綁定 AZ；要跨 AZ 共享用 EFS（但貴 4 倍，記得開 IA 生命週期）
  • Instance Store 停機資料就消失，只放暫存
  • Placement Group：Cluster 擠一起、Spread 散開、Partition 分組
  • 省錢優先順序：gp3 → 刪孤兒資源 → 下班關機 → Graviton → Right Sizing → Spot → SP
EC2 與儲存在 SAA-C03 屬於「Design Cost-Optimized Architectures」（20%）和「High-Performing」（24%）兩個領域。去 模擬試題 練一輪。
