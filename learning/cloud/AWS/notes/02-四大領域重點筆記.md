# AWS SAA-C03 四大領域重點筆記

考試資訊：65 題（50 計分 + 15 不計分）｜130 分鐘｜及格 720/1000（約 72%）｜題型：單選 + 多選

> 對應教材第 01–22 章。每一節後面的章號是延伸閱讀的位置。

## 領域 1：設計安全架構（30%）

### 1.1 身分與存取（IAM）〔第 01、12 章〕
- **最小權限原則**是所有題目的底層邏輯。
- 明確 Deny > SCP/Boundary 上限 > 明確 Allow > 預設隱含 Deny。
- EC2/Lambda/ECS 存取 AWS 服務 → 一律用 **IAM Role**，不用 Access Key。
- 跨帳號 → **AssumeRole (STS)**；第三方 → 加 **External ID**。
- 大量終端使用者（App/網站會員）→ **Cognito**，不是 IAM User。
- 企業 AD/SAML 整合 → IAM Identity Center（SSO）或 SAML 聯合。
- 組織強制限制（區域、服務、防止關閉 CloudTrail）→ **SCP**。
- 容器的權限分層：ECS 用 **Task Role**（容器內程式）vs **Task Execution Role**（拉映像檔、寫日誌）；EKS 用 **IRSA** 綁 ServiceAccount。

### 1.2 資料加密〔第 04、05 章〕
- 靜態加密：S3（SSE-S3/SSE-KMS/SSE-C）、EBS、RDS、DynamoDB 皆整合 KMS。
- 需要「金鑰使用稽核 + 自訂輪換」→ **KMS 客戶管理金鑰**。
- 需要「完全掌控金鑰 + 專用硬體」→ **CloudHSM**。
- 傳輸加密：TLS/HTTPS；ACM 免費管理憑證（自動續期）。
- RDS/EBS 已存在的未加密資源 → 建快照 → 複製時加密 → 還原（不能直接開啟加密）。
- **KMS 金鑰是區域性資源**：跨區複製加密快照要用目標區域的金鑰重新加密；要同一份金鑰材料跨區 → **多區域金鑰**。

### 1.3 網路安全〔第 02、19 章〕
- 分層防護：WAF（L7）→ SG（執行個體、有狀態）→ NACL（子網路、無狀態）。
- 私有子網路出網際網路 → NAT Gateway（放在公有子網路）。IPv6 版本是 **Egress-Only IGW**。
- 私有存取 AWS 服務 → VPC Endpoint（S3/DynamoDB 用 Gateway、其他用 Interface）。
- **地端要私有存取 S3 → Interface Endpoint 或 DX Public VIF**；Gateway Endpoint 做不到。
- **出站限制只能連特定網域 → Network Firewall**（SG/NACL 只能比對 IP 與埠）。
- 只曝露單一服務給外部、不想開放整個 VPC → **PrivateLink Endpoint Service**（兩邊網段可重疊）。
- 堡壘機已過時，考題偏好 **SSM Session Manager**（免開 22 埠、有稽核、可做連接埠轉發連私有 RDS）。
- CloudFront 內容保護：**OAC** 鎖住 S3；**Signed URL** 保護單一檔案、**Signed Cookie** 保護整個路徑。

### 1.4 監控與偵測〔第 08、18 章〕
- CloudTrail = 誰做了什麼 API（稽核）。
- Config = 資源組態變更與合規（例如「偵測未加密的 EBS」）。**只能偵測，不能阻止**。
- GuardDuty = 智慧威脅偵測。Inspector = 弱點掃描。Macie = S3 PII。
- Security Hub = 全部彙整。**Detective = 深入調查根因**（需先開 GuardDuty）。
- **Audit Manager = 蒐集我方環境的合規證據**；**Artifact = 下載 AWS 自己的 SOC 2 / ISO 報告**。兩者方向相反。
- **Firewall Manager = 跨帳號統一套用 WAF/Shield/SG/Network Firewall**，且自動涵蓋「未來新建」的資源。這五個字是最強關鍵字。
- Inventory / Config / Inspector 的層次：機器**裡面**裝了什麼 vs AWS **資源**組態 vs 有沒有**已知漏洞**。

### 1.5 多帳號治理〔第 12、22 章〕
- 防護欄三種對應三個時間點：**主動性**（CloudFormation Hooks，部署範本前）→ **預防性**（SCP，API 呼叫時）→ **偵測性**（Config，事後）。
- 題目說「要能**阻止**」而不是「發現」→ SCP 或主動性，不會是 Config。
- **SCP 對管理帳號完全無效** → 管理帳號不放任何工作負載。
- 快速開合規新帳號 → **Control Tower**（Account Factory）；團隊自助佈建但只能用核准架構 → **Service Catalog**（啟動限制讓使用者不需底層權限）。
- 資源跨帳號共用 → **RAM**（子網路、TGW、Resolver Rule、Capacity Reservation…）。
- 目錄三選一：**Managed Microsoft AD**（雲端獨立可運作、可建信任、支援 FSx/RDS SQL）／**AD Connector**（純代理，不存副本，地端斷線即失效）／**Simple AD**（便宜，不支援信任與 MFA）。

## 領域 2：設計彈性架構（26%）

### 2.1 高可用基本功〔第 06 章〕
- 標準組合：**多 AZ 的 ASG + ELB**，資料層 RDS Multi-AZ。
- ELB 健康檢查失敗 → 停止導流；ASG 健康檢查失敗 → 終止並替換。
- 無狀態化：Session 移到 **ElastiCache / DynamoDB**，檔案移到 **S3 / EFS**。
- 開機初始化太久導致擴容跟不上 → **Warm Pool**（預先初始化後停機，只付 EBS 費）。
- 終止前要上傳日誌或排空連線 → **Lifecycle Hook**（不是加長冷卻時間）。

### 2.2 解耦〔第 07 章〕
- 元件間直接呼叫 → 改用 **SQS**（緩衝、削峰）或 **SNS**（fan-out）。
- 佇列深度（ApproximateNumberOfMessagesVisible）可作為 ASG 擴展指標。
- 訊息被重複處理 → **可見性逾時短於處理時間**，調長或用 ChangeMessageVisibility；應用程式本身也要冪等。
- 工作流程協調 → Step Functions。
- **既有 JMS/AMQP/MQTT 應用不想改程式 → Amazon MQ**；全新開發才用 SQS/SNS。

### 2.3 災難復原（必考）〔第 09、20 章〕

| 策略 | RTO/RPO | 成本 | 關鍵字 |
|---|---|---|---|
| Backup & Restore | 小時級 | 最低 | 僅備份到 S3/Glacier |
| Pilot Light | 十分鐘級 | 低 | 核心（DB）常駐複寫，其餘關閉 |
| Warm Standby | 分鐘級 | 中 | 縮小版全系統常駐 |
| Multi-Site Active-Active | 秒級 | 最高 | 雙站全量 + Route 53 分流 |

- RPO = 能容忍遺失多少資料；RTO = 能容忍停機多久。兩者都由 **BIA** 推導，不是拍腦袋訂的。
- Aurora Global Database：RPO 約 1 秒、RTO 1 分鐘內。
- **地端伺服器要 DR、RPO 秒級、平時不想開整套機器 → Elastic Disaster Recovery (DRS)**（持續區塊複寫到低成本暫存區，災難時才啟動）。

### 2.4 備份〔第 20 章〕
- **AWS Backup**：跨服務 + 跨帳號 + 跨區域集中備份政策（EBS/RDS/DynamoDB/EFS/FSx/S3…），用**標籤指派**資源，可用 Organizations 政策強制。
- **DLM 只管 EBS 快照與 AMI**——題目出現 RDS/EFS/DynamoDB/FSx 就不是它。
- **Vault Lock**：Governance 可解除／**Compliance 不可逆，連 root 都刪不掉**。
- **防勒索的標準答案 = 跨帳號複製到獨立備份帳號 + Vault Lock**（同帳號的備份，攻擊者拿到權限一樣刪得掉）。
- **沒測過的備份等於沒有備份**——「從未執行還原測試」通常判重大缺失。
- S3 跨區域複寫 (CRR)：需開 Versioning，僅複寫新物件。

### 2.5 混合連線的韌性〔第 19 章〕
- 每條 VPN 有 **2 條 tunnel**（不同 AZ），單條上限約 1.25 Gbps。客戶端只有一台路由器 → 仍是單點。
- **DX + VPN 備援必須兩邊都跑 BGP**，靜態路由不會自動收斂。
- DX 韌性：兩位置各兩條 = **99.99%**；兩位置各一條 = 99.9%；**LAG 不是跨機房高可用**。
- 「盡快通」→ VPN；「穩定頻寬」→ DX；「DX 施工中」→ 先 VPN 再轉備援。

## 領域 3：設計高效能架構（24%）

### 3.1 運算擴展〔第 03、06、07 章〕
- 垂直（加大機型）有上限；**水平（加台數）**才是雲的答案。
- 突發流量且無法預測 → 無伺服器（Lambda / Fargate / DynamoDB On-Demand）。
- Lambda 冷啟動 → Provisioned Concurrency。
- 容器選型：沒有 K8s 經驗、要最少維運 → **ECS + Fargate**；要多雲可攜或 K8s 生態 → **EKS**。
- EKS 擴展卡住常見於 **VPC CNI 的 IP 耗盡**；節點層擴展用 **Karpenter**。

### 3.2 儲存效能〔第 03、04、20 章〕
- gp3 可獨立調 IOPS/吞吐（不綁容量，比 gp2 划算）。
- >16K IOPS → io2；>64K IOPS → io2 Block Express（需 Nitro）。
- S3 效能：prefix 分散可平行擴展；大檔用 Multipart；範圍讀取用 Byte-Range Fetch。
- **只要大檔中的少數欄位 → S3 Select**（在 S3 端過濾，減少傳輸）；整個資料湖下 SQL → Athena。
- **HPC / ML + 資料在 S3 → FSx for Lustre 連結 S3**（延遲載入 + HSM 匯出）。EFS 撐不起 HPC。
- **EFS 效能忽快忽慢 → Bursting 信用額度用完**（資料量小基準值就低），改 **Elastic** 或 Provisioned。
- 同一份資料要 NFS + SMB 一起用 → **FSx for NetApp ONTAP**。

### 3.3 快取層層疊〔第 05 章〕
使用者 → CloudFront（邊緣） → API Gateway 快取 → ElastiCache / DAX（資料層） → 資料庫
- 「降低資料庫負載」幾乎都選 ElastiCache 或 Read Replica（讀多場景）。
- 「微秒級 DynamoDB 讀取」→ DAX。
- 要 Redis 相容且**資料持久、可當主資料庫** → **MemoryDB**。

### 3.4 網路效能〔第 02、19 章〕
- 同 AZ 延遲最低；Cluster Placement Group 用於 HPC。
- Enhanced Networking (ENA) 免費預設；EFA 用於 MPI HPC 工作負載。
- 全球加速：HTTP → CloudFront；TCP/UDP → Global Accelerator。
- 邊緣運算二選一：**CloudFront Functions**（次毫秒、不能連網、便宜，做標頭/URL 改寫）vs **Lambda@Edge**（可連網、可讀請求主體，須建在 us-east-1 且無環境變數）。
- 混合 DNS 要**雙向**就必須 **Inbound + Outbound Endpoint 兩個都建**。

### 3.5 遷移的效能選擇〔第 15 章〕
- 線上大量檔案 + 有頻寬 → **DataSync**（增量、驗證、排程）。
- 頻寬不足或離線 → **Snowball Edge**（考試常出「網路要幾天 vs 寄送要幾天」的計算題）。
- 異質資料庫 → **SCT 轉結構 + DMS 做完整載入與 CDC**，切換停機僅數分鐘。
- 既有 SFTP 流程不想改 → **Transfer Family**。

## 領域 4：設計成本優化架構（20%）

### 4.1 運算成本〔第 03 章〕
- 穩定基載 → Savings Plans / RI；尖峰 → On-Demand；可中斷 → Spot。
- **Compute Savings Plans** 最彈性（跨家族、跨區域，涵蓋 EC2/Fargate/Lambda）。
- 混合策略：ASG 可同時使用 On-Demand（基載）+ Spot（彈性）。
- 開發環境下班自動關機（Instance Scheduler），省約 70%。
- **改用 Graviton（ARM）**：不改架構就降 20~40% 成本，容器只需重建映像檔。

### 4.2 儲存成本〔第 04、20 章〕
- Lifecycle Policy 是 S3 省錢核心；未知模式用 Intelligent-Tiering。
- 注意隱藏費：IA/Glacier 有**取回費**與**最短儲存天數**（IA 30 天、Glacier 90 天、Deep Archive 180 天）。
- EBS：gp2 → gp3 直接省 20%；刪除未掛載磁碟區與過期快照。
- **EFS 生命週期管理**：N 天未存取自動轉 IA，被讀到自動轉回，應用程式無感——EFS 成本題的標準答案。
- **S3 Requester Pays**：公開資料集讓下載方付傳出費。
- 不確定哪些前綴適合轉冷 → 先用 **Storage Class Analysis** 分析再訂規則。
- **FSx 的吞吐容量與儲存容量分開計費**，一開始常開太大。

### 4.3 網路成本（常被忽略的考點）〔第 02、19 章〕
- 傳入免費、同 AZ 免費、跨 AZ 收費、出網際網路最貴。
- NAT Gateway 資料處理費 → S3/DynamoDB 流量改走 Gateway Endpoint（免費）。
- 大量傳出 → CloudFront 單價較低且有免費額度。
- **Interface Endpoint 是每個 AZ 一個 ENI、每個都在跳表**——為了「安全」開太多會比 NAT Gateway 還貴。
- **TGW 有附件費 + 處理費，VPC Peering 兩者都沒有**——只有兩個 VPC 時 Peering 更省。
- **多帳號能共用一個 VPC 時 → RAM 共享子網路最省**（同 VPC 內沒有處理費）。

### 4.4 監控與治理〔第 08、22 章〕
- Budgets 警示（可用預測值）、Cost Explorer 分析、CUR 明細。
- **Cost Anomaly Detection**：用機器學習抓非預期暴增，比固定門檻更能涵蓋各服務層級。
- Cost Allocation Tags 分部門追蹤；**Cost Categories** 把帳號/服務/標籤組成自訂成本群組。
- Organizations 合併帳單共享 RI / Savings Plans 折扣。
- **License Manager 管的是第三方 BYOL 授權合規，不是 AWS 帳單**。

### 4.5 邊緣與混合的成本判斷〔第 22 章〕
- 只是「使用者延遲要更低」而**沒有資料落地要求** → 先想 CloudFront / Global Accelerator，再想 **Local Zones**。
- **Outposts 是有實體交付與長期承諾的重型方案**，只有「資料必須留在自家機房」時才是最佳解。

## 考試技巧

1. **先找限制條件**：題目中的 MOST cost-effective / HIGHLY available / LEAST operational overhead 決定答案方向。
2. **LEAST operational overhead** → 幾乎都選無伺服器/全受管服務。
3. **刪去法**：先刪明顯錯誤的兩個選項，再比較剩下兩個的差異。
4. 看到「不要走網際網路」→ VPC Endpoint / Direct Connect / PrivateLink。
5. 看到「立即、全域、毫秒」→ 快取類服務。
6. 看到「**包括未來新建的**」→ Firewall Manager 或自動化政策，不是單一資源的設定。
7. 看到「**互相**」（雙向解析、雙向存取）→ 答案通常要選「兩個都建」的那個。
8. 看到具體的**既有協定或產品名**（JMS、ActiveMQ、NetApp、Lustre、Oracle）→ 選對應的相容服務，不要選 AWS 原生替代品。
9. 不確定就選 AWS 原生全受管服務，而非自建方案。
10. 數量詞是暗示：「**兩個** VPC」→ Peering；「**數十個** VPC」→ TGW。
