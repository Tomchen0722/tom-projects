1. AWS Code 家族職責分工與現代架構定位

把 CI/CD 管線想成汽車自動化組裝流水線：
• CodeCommit (或 GitHub) = 設計藍圖保險庫（儲存原始碼）。
• CodeBuild = 工廠衝壓與零件組裝機（編譯代碼、跑單元測試、打包 Docker 映像檔）。
• CodeDeploy = 專業試車特技司機（把新車平順開上高速公路，出狀況秒切備用車道）。
• CodePipeline = 輸送帶中央調度控制器（把上述所有站點串聯成全自動化流水線）。
服務名稱核心功能輸入 (Input) 與輸出 (Output)考試核心定位
AWS CodeCommit 高可用私有 Git 程式碼儲存庫。 開發者 push 代碼 ➔ 觸發 EventBridge 事件。 AWS 原生託管 Git（注：新專案推薦整合 GitHub/GitLab）。
AWS CodeBuild 無伺服器彈性編譯與測試服務。按建置分鐘計費。 輸入原始碼 + buildspec.yml ➔ 輸出可部署構件 (Artifacts) 或 Docker 映像檔。 自動伸縮、容器化隔離環境、支援 Docker in Docker (DinD)。
AWS CodeDeploy 自動化部署排程器。支援 EC2, ECS, Lambda, On-premises。 輸入構件 + appspec.yml ➔ 執行滾動、藍綠、金絲雀換版。 控制「如何換版」與「失敗自動回滾」。
AWS CodePipeline 持續交付編排引擎。提供視覺化多階段流程圖。 串接 Source ➔ Build ➔ Test ➔ Manual Approval ➔ Deploy。 控制「階段順序」與「多帳號協同」。

2. CodeBuild：buildspec.yml 四階段與建置快取

CodeBuild 的一切行為都由專案根目錄下的 buildspec.yml 控制。其執行生命週期嚴格分為四個連續階段：

CodeBuild 生命週期四大階段 1. install ── 安裝編譯所需的運行時環境與外部工具 (如指定 Python 3.11, Node.js 20) 2. pre_build ── 預備工作：登入 Amazon ECR 倉庫、解析版本號、下載相依套件庫 3. build ── 核心動作：執行 npm run test, mvn package, docker build 4. post_build ── 產後收尾：推動 Docker 映像至 ECR、生成測試覆蓋率報告、輸出構件

標準 buildspec.yml 生產級範例

version: 0.2 phases: install: runtime-versions: nodejs: 20 commands: - echo "Installing dependencies..." - npm ci pre_build: commands: - echo "Logging in to Amazon ECR..." - aws ecr get-login-password --region $AWS_DEFAULT_REGION | docker login --username AWS --password-stdin $REPOSITORY_URI - COMMIT_HASH=$(echo $CODEBUILD_RESOLVED_SOURCE_VERSION | cut -c 1-7) - IMAGE_TAG=${COMMIT_HASH:=latest} build: commands: - echo "Running unit tests..." - npm test - echo "Building Docker image..." - docker build -t $REPOSITORY_URI:$IMAGE_TAG . post_build: commands: - echo "Pushing Docker image to ECR..." - docker push $REPOSITORY_URI:$IMAGE_TAG - printf '{"ImageURI":"%s"}' $REPOSITORY_URI:$IMAGE_TAG > imageDetail.json artifacts: files: - imageDetail.json - appspec.yaml cache: paths: - '/root/.npm/**/*'
CodeBuild 快取考點 (Build Cache)：
大型專案若每次編譯都要重新下載數百 MB 的相依套件（如 npm / maven / pip），會浪費大量時間與建置費用。CodeBuild 支援兩種快取：
• S3 快取：適用於跨建置主機共享相依套件目錄。
• 本機自訂快取 (Local Cache)：快取 Docker Layer、原始碼與自訂目錄，建置速度最快！

3. CodeDeploy 五種部署策略深度決策矩陣

部署策略支援運算平台流量切換機制停機時間與回滾速度適用場景
In-Place
(就地覆蓋部署)		 EC2 / On-Premises 專用
(❌ 不支援 ECS/Lambda)		 在原有的 EC2 實例上停止舊版、部署新代碼、再重啟服務。 有短暫停機時間；回滾需耗時重新部署舊版本。 開發測試環境、非關鍵離線批次系統。
Blue/Green
(標準藍綠部署)		 EC2, ECS, Lambda 建立全新的一整套綠色環境，健康檢查全數通過後，ALB 瞬間將 100% 流量切換到綠色。 零停機時間；回滾極快（只需將 ALB 權重指回藍色舊版）。需雙倍硬體資源。 關鍵核心 Web 應用、金融交易系統（SAA 高頻首選）。
Linear
(線性平滑過渡)		 Lambda, ECS 按固定時間比例等額增加流量。例如：Linear10PercentEvery1Minute（每分鐘增加 10% 流量，共耗時 10 分鐘切完）。 零停機時間；觀察期發現異常自動秒級回退。 大規模 API 服務，平穩觀察各項監控指標與資料庫承載力。
Canary
(金絲雀部署)		 Lambda, ECS 先分流極小比例流量給新版試水溫，觀察一段時間無異常後，再一次切換剩餘全部流量。例如：Canary10Percent5Minutes。 零停機時間；極小化爆炸半徑 (Blast Radius)。 Serverless Lambda 函式更新推薦標準。
秒殺考點：In-Place vs Blue/Green 平台限制
題目問：「如何針對 AWS Lambda 或 Amazon ECS 執行 In-Place 部署？」
→ 大陷阱！Lambda 與 ECS 天生是無伺服器/不可變容器，根本不支援 In-Place 部署！ 它們只能使用 Blue/Green、Canary 或 Linear 部署！

4. AppSpec.yml 規範與生命週期掛勾 (Lifecycle Hooks)

appspec.yml 是告訴 CodeDeploy「如何安裝、如何驗證健康狀態、失敗何時回退」的控制檔案。不同平台的掛勾順序截然不同：

【EC2 / On-Premises 部署掛勾順序】 1. ApplicationStop ── 優雅終止正在運行的舊版本服務 2. DownloadBundle ── CodeDeploy Agent 從 S3 下載最新代碼包 3. BeforeInstall ── 預先備份、解密憑證金鑰、建立安裝目錄 4. Install ── 將檔案複製到目標資料夾 (如 /var/www/html) 5. AfterInstall ── 修改檔案擁有權 (chown)、設定檔案權限、安裝依賴套件 6. ApplicationStart ── 啟動服務行程 (如 systemctl start nginx) 7. ValidateService ── 最關鍵鉤子！執行測試腳本確認 HTTP 200，失敗立即自動觸發 Rollback！ 【Lambda 無伺服器部署掛勾順序】 1. BeforeAllowTraffic ── 流量切換前，調用測試 Lambda 檢查新版本能否正常連線 RDS 2. (開始按 Canary/Linear 規則逐步切換流量) 3. AfterAllowTraffic ── 流量全數切換後，執行最後整合驗證

5. CodePipeline：多階段編排與手動核准關卡

CodePipeline 將軟體發布流程塑造成多個依序執行的 Stage（階段）：

CodePipeline 生產標準流程 [Source Stage] ──→ [Build & Test Stage] ──→ [Staging Stage] ──→ [Approval Stage] ──→ [Production Stage] GitHub CodeBuild Deploy to Test Manual Approval Blue/Green Deploy (Webhook觸發) (打包Docker/跑測試) (自動跑E2E測試) (發送 SNS 給主管) (零停機上線)
人工審批關卡 (Manual Approval Action) 必考細節：
  • 在進入生產部署之前，可插入 Manual Approval 動作。
  • CodePipeline 會透過 Amazon SNS Topic 發送電子郵件或 Slack Webhook 通知主管。
  • 主管登入 AWS 控制台或點擊核准連結後，管線才會放行進入 Production 階段。

6. 企業級跨帳號 CI/CD 管線架構（KMS CMK 與 STS AssumeRole）

在大型企業標準三層架構中，CI/CD 管線位於獨立的 Shared Tools Account，負責部署到 Dev / Staging / Prod Account。這是 SAA-C03 與 SAP 的頂級高難度考題：

【共享工具帳號 (Tools Account)】 ├── AWS CodePipeline (編排引擎) ├── Amazon S3 構件儲存貯體 (Artifact Bucket) └── AWS KMS Customer Managed Key (CMK) ← 關鍵考點！ │ │ 透過 STS:AssumeRole 跨帳號 Assume 目標帳號的部署角色 ▼ ┌─────────────────────────────────┬─────────────────────────────────┐ │ 【Staging Account (成員帳號)】 │ 【Production Account (成員帳號)】│ │ • CrossAccountDeployRole │ • CrossAccountDeployRole │ │ • 具備部署到該帳號 EC2/ECS 權限 │ • 具備部署到該帳號 EC2/ECS 權限 │ └─────────────────────────────────┴─────────────────────────────────┘
五星陷阱：S3 預設加密金鑰無法跨帳號共享！
如果 Tools Account 的 S3 Artifact Bucket 使用預設的 AWS Managed Key (aws/s3)，當 Production Account 嘗試下載構件時，必將報錯 AccessDenied！
• 原因：AWS Managed Key 的 Key Policy 無法手動修改，嚴禁跨帳號存取。
• 唯一正確解法：必須在 Tools Account 建立 Customer Managed Key (CMK)，並在其 Key Policy 中明確賦予 Production Account 呼叫 kms:Decrypt 與 kms:DescribeKey 的權限！

7. 現代化最佳實踐：GitHub Actions 與 IAM OIDC 免密碼連線

在過去，要在 GitHub Actions 部署 AWS，工程師必須在 GitHub Secrets 儲存 AWS_ACCESS_KEY_ID 與 AWS_SECRET_ACCESS_KEY。這是一顆定時炸彈——一旦金鑰外洩或員工離職未輪換，攻擊者可藉此洗劫整個雲端環境。
GitHub Actions Workflow 執行 │ 1. 向 GitHub OIDC Provider 請求一組短暫 JWT Token ▼ AWS IAM OpenID Connect (OIDC) Identity Provider │ 2. 驗證 GitHub 的數位簽章與 Repository / Branch 限制條件 ▼ AWS STS │ 3. 呼叫 STS: AssumeRoleWithWebIdentity │ 4. 頒發僅存活 1 小時的 IAM 臨時金鑰 ▼ GitHub Actions 拿臨時憑證直接執行 `aws s3 sync` 或 `aws ecs update-service`！ 雲端完全零長期金鑰！

8. CloudWatch 告警與自動化回滾 (Rollback) 機制

部署失敗不可怕，最怕的是上線後代碼有 Memory Leak 或 500 錯誤率暴增，維運人員卻在睡覺。CodeDeploy 深度整合 CloudWatch Alarms 達成無人值守自動回滾：

監控關鍵指標閾值警報設定CodeDeploy 自動動作
HTTPCode_Target_5XX_Count ALB Target Group 的 5XX 錯誤數在 1 分鐘內大於 10 筆。 立即停止流量切換，秒級將 ALB 流量 100% 切回舊版本（藍色環境）。
TargetResponseTime 平均 API 響應時間超過 1.5 秒。 終止當前部署，標記 Deployment Status 為 Failed 並觸發 SNS 通知。

9. CI/CD 常見失敗原因與排錯手冊

常見報錯訊息根本原因診斷標準排查措施
The CodeDeploy agent did not respond within the expected time frame 1. EC2 上根本未安裝 CodeDeploy Agent。
2. Agent 崩潰未運行。
3. EC2 沒有配置到 S3 的網路路由或缺少 VPC Endpoint。		 SSH 登入 EC2 執行 sudo service codedeploy-agent status；檢查 EC2 Instance Profile 是否包含 AWSCodeDeployRole 權限。
The Step 'ValidateService' failed with exit code 1 在 appspec.yml 中定義的驗證健康檢查腳本執行失敗（如呼叫 curl http://localhost:80 回傳了 404 或 500）。 檢視 /opt/codedeploy-agent/deployment-root/deployment-logs/codedeploy-agent-deployments.log；在本地手動測試驗證腳本。
KMS.AccessDeniedException during S3 GetObject 跨帳號部署時，目標帳號的 IAM Role 缺少 Tools 帳號 KMS Key 的解密權限。 更新 KMS Customer Managed Key Policy，將目標帳號加入 Principal 允許清單。

10. SAA-C03 考試陷阱與關鍵字速查

陷阱 1：CodeCommit 不再開放新客戶
考試如果出現「儲存庫選擇」，若題目提到現有 GitHub，永遠選擇 GitHub + CodePipeline 整合，無須搬移至 CodeCommit。
陷阱 2：Lambda 只能用 Canary / Linear / AllAtOnce
Lambda 的部署是由 CodeDeploy 操作流量比重分配（透過 Lambda Alias 流量權重），絕無 In-Place！
陷阱 3：跨帳號 Artifact S3 桶不能用預設 KMS 金鑰
跨帳號 CodePipeline 構件加密，唯一答案是 KMS Customer Managed Key (CMK)，AWS Managed Key 必死無疑！
🎯 CI/CD 考題秒殺直覺：
• 階段編排與手動審批 → AWS CodePipeline
• 編譯 Docker 映像與單元測試 → AWS CodeBuild (buildspec.yml)
• 零停機快速回滾與流量切換 → AWS CodeDeploy (appspec.yml + 藍綠/金絲雀)
• 跨帳號構件解密授權 → KMS Customer Managed Key (CMK)
• 外部 CI/CD 免金鑰安全存取 → IAM OIDC Identity Provider (AssumeRoleWithWebIdentity)

11. 實作 Lab：編寫 buildspec.yml 與 appspec.yml 完整範例

EC2 專用 appspec.yml 範例：

version: 0.0 os: linux files: - source: / destination: /var/www/html hooks: BeforeInstall: - location: scripts/clean_old_files.sh timeout: 300 runas: root AfterInstall: - location: scripts/install_dependencies.sh timeout: 300 runas: root ApplicationStart: - location: scripts/start_server.sh timeout: 300 runas: root ValidateService: - location: scripts/health_check.sh timeout: 60 runas: root

Lambda 專用 appspec.yaml (Canary 部署) 範例：

version: 0.0 Resources: - myLambdaFunction: Type: AWS::Lambda::Function Properties: Name: "OrderProcessorFunction" Alias: "live" CurrentVersion: "1" TargetVersion: "2" Hooks: - BeforeAllowTraffic: "PreTrafficValidationLambda" - AfterAllowTraffic: "PostTrafficValidationLambda"
