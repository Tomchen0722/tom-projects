1. 為什麼手動部署撐不住

手動部署像每次都手寫一張支票——寫十次可能都對，寫第一百次一定會有一次金額寫錯。
而且出錯的那次，你不會知道是哪裡不一樣。
手動部署的問題造成什麼
步驟靠人記或靠文件換人做就出錯；文件永遠比實際落後
環境之間有差異「在我機器上是好的」
沒有紀錄誰在何時部署了什麼出事時不知道要退回哪個版本
回退要靠手動重來故障時間拉長，壓力下更容易再出錯
部署很痛苦→ 大家減少部署次數 → 每次改動變更大 → 風險更高
📋最後一列是最關鍵的惡性循環。部署越痛苦，部署頻率越低，每次的變更量越大，出事機率越高，於是更害怕部署。CI/CD 真正在解的是這個循環，不只是「省下手動的時間」。

2. AWS 的 Code 家族四兄弟

名字很像，但各管一段，考試常考「哪一個負責什麼」：

服務負責一句話
CodeCommit原始碼託管AWS 版的 Git 儲存庫（多數企業其實用 GitHub/GitLab）
CodeBuild編譯與測試託管的建置環境，跑 buildspec.yml，按分鐘計費
CodeDeploy部署到目標負責怎麼換版：藍綠、金絲雀、滾動
CodePipeline串接與編排把上面三個（或第三方工具）串成一條有階段的流水線
陷阱：CodeDeploy 與 CodePipeline 最容易混
• CodePipeline = 流程。定義「先建置、再測試、要人工核准、最後部署」這個順序。
• CodeDeploy = 換版動作。定義「新版本怎麼取代舊版本，以及失敗怎麼自動退回」。

題目問「如何在部署失敗時自動回退」→ CodeDeploy。
問「如何加入人工核准關卡」→ CodePipeline。
企業實務：不一定要用 CodeCommit
多數企業的原始碼已經在 GitHub 或 GitLab，沒有理由搬家。CodePipeline 可以直接以 GitHub 為來源。
AWS 也已宣布 CodeCommit 不再向新客戶開放，新專案請直接用 GitHub/GitLab 當來源，考試若出現「既有 GitHub 儲存庫」也不用糾結要不要搬。

3. 一條典型的管線長什麼樣

Source GitHub / CodeCommit / S3 └─ 開發者 push 到 main 分支就觸發 Build CodeBuild ├─ 安裝相依套件 ├─ 跑單元測試 ├─ 安全掃描（相依套件漏洞、機密外洩） ├─ 建置 Docker 映像 └─ 推到 ECR,並用 commit SHA 當標籤（不要用 latest） Deploy to Staging └─ 部署到測試環境,跑整合測試 Manual Approval ← 正式環境前的人工關卡 └─ 通知 SNS,主管在主控台按核准 Deploy to Production CodeDeploy ├─ 藍綠或金絲雀切換 ├─ CloudWatch 告警當作健康檢查 └─ 告警觸發 → 自動回退
陷阱：映像標籤不要用 latest
用 latest 會讓你無法確定線上跑的到底是哪一版，回退時也不知道要退到什麼。
正確做法：用 commit SHA 或語意化版本當標籤，讓「線上版本」與「原始碼某一次提交」一對一對應。
這在事故調查時是決定性的——你必須能回答「線上現在跑的是哪一行程式碼」。

4. 四種部署策略

策略怎麼換版回退速度成本適合
In-place
（就地）		直接在原機器上換掉慢（要重新部署舊版）最低開發/測試環境
Rolling
（滾動）		一批一批換中等低一般正式環境
Blue/Green
（藍綠）		另開一整套新環境，驗證後切流量極快（切回去就好）高（雙倍資源）不能停機的關鍵系統
Canary
（金絲雀）		先放 5% 流量給新版，觀察後再全量快中要控制爆炸半徑
藍綠部署的實際運作 Route 53 / ALB Target Group │ ┌─────┴─────┐ ↓ ↓ 藍(舊版) 綠(新版) 100% 流量 0% 流量 ← 先部署好、跑健康檢查 │ │ └── 切換 ──→┘ 0% 流量 100% 流量 出事怎麼辦?把流量切回藍色,幾秒完成 舊環境保留一段時間才刪掉
陷阱：藍綠部署最大的難題不是流量，是資料庫
應用可以有兩套，資料庫通常只有一套。所以：
• 資料庫的 schema 變更必須向前相容——舊版程式碼要能在新 schema 上正常運作
• 常見做法是擴展再收縮（expand / contract）：先加新欄位（不刪舊的）→ 部署新程式 → 確認穩定 → 之後才移除舊欄位
• 絕對不要在同一次部署裡「改 schema + 換程式」並期待能乾淨回退

這是實務上藍綠部署最常翻車的地方，也是進階考題會問的。
企業實務：自動回退的觸發條件要事先定義
「出事就退回」聽起來理所當然，但系統要知道什麼叫「出事」。實務上會綁 CloudWatch 告警當健康檢查：
• 5xx 錯誤率超過門檻
• p99 延遲超過門檻
• 業務指標異常（例如訂單成功率驟降）

第三項最有價值也最常被忽略——技術指標全綠但訂單掉一半的狀況真的會發生。

5. 企業多帳號部署

企業幾乎都是多帳號架構（第 12 課的 Organizations）。管線要能跨帳號部署，這是企業級 CI/CD 的核心設計。

典型的三帳號結構 工具帳號 Tooling ├── CodePipeline / CodeBuild 都在這裡 ├── ECR（映像集中存放） └── KMS 金鑰（跨帳號共用,要設金鑰政策） │ ┌────────┼────────┐ ↓ ↓ ↓ Dev Staging Prod 各自獨立帳號,爆炸半徑互相隔離 跨帳號的做法： 管線用 sts:AssumeRole 取得目標帳號的部署角色 目標帳號的角色只信任工具帳號,且權限最小化
✅ 為什麼要分帳號而不是分 VPC？帳號是 AWS 最強的隔離邊界——權限、配額、帳單、資源命名空間都天然分開。開發環境的失控腳本不可能誤刪正式環境的資源，因為它根本沒有那個帳號的憑證。
企業實務：Control Tower 與 Service Catalog
多帳號管到一定規模，會用到這兩個服務：
• Control Tower——自動化建立符合規範的新帳號（landing zone），內建護欄（guardrails）、集中日誌、SSO。新部門要帳號時不用手工開一堆設定。
• Service Catalog——把核准過的架構包成「產品」，讓開發團隊自助佈建，但只能用 IT 事先審過的組態。兼顧敏捷與治理。

考試關鍵字：「快速建立符合標準的新帳號」→ Control Tower；「讓團隊自助但限制在核准範圍內」→ Service Catalog。

6. 管線本身的資安

最危險的認知：把 CI/CD 當成內部工具就不用管安全
部署管線擁有改變正式環境的權限。攻破管線比攻破應用更值錢——不用找漏洞，直接發一版惡意程式碼上去就好。
不要放長期金鑰CI 用 OIDC 換臨時憑證（第 10 課教過），不要在 GitHub Secrets 放 IAM access key。
最小權限部署角色只給「部署這個應用」需要的權限，不要用 PowerUser 或 Admin。
掃描相依套件Build 階段跑漏洞掃描，ECR 也可開啟映像掃描（背後是 Inspector）。
機密不進原始碼用 Secrets Manager 或 Parameter Store，Build 時才注入。並在管線加機密外洩掃描。
人工核准正式環境前設關卡，並確保核准者不是提交者本人。
稽核軌跡CloudTrail 記錄誰觸發了哪次部署，這在事故調查與法遵都需要。
✅ 考試高頻題：「GitHub Actions 要部署到 AWS，如何不儲存長期憑證？」→ 設定 IAM OIDC 身分供應商，讓 Actions 用 workflow 的 OIDC token 去 AssumeRoleWithWebIdentity。這題在第 10 課與本課都會出現。

7. 選型：什麼時候不用 AWS 的工具

情況建議理由
程式碼已在 GitHub，團隊熟 ActionsGitHub Actions + OIDC不用多學一套；生態系與市集豐富
純 AWS 環境，要與 IAM 深度整合CodePipeline權限模型一致，跨帳號部署較單純
已用 GitLab 全套GitLab CI + OIDC同上，不要為了用 AWS 而搬
K8s 環境要 GitOpsArgo CD / Flux宣告式、以 Git 為單一真實來源
務實建議：混用是常態
很常見的組合是 GitHub Actions 做 CI（建置與測試）+ CodeDeploy 做 CD（換版與回退）。
因為 CI 的生態系 GitHub 較強，而 CD 要深入 AWS 的 ALB、ASG、ECS 與告警，用 AWS 原生工具較順。

不要陷入「一定要全套同一家」的迷思——用各自最擅長的那一段。

8. 考試陷阱整理

陷阱 1：CodeDeploy vs CodePipeline
自動回退 → CodeDeploy；人工核准與階段編排 → CodePipeline。
陷阱 2：藍綠 vs 金絲雀
「立即完整切換、可秒退」→ 藍綠；「先給一小部分使用者、逐步放大」→ 金絲雀。
陷阱 3：免金鑰 CI/CD
「不要儲存長期 access key」→ IAM OIDC 供應商 + AssumeRoleWithWebIdentity。
陷阱 4：跨帳號部署
管線在工具帳號，用 AssumeRole 進目標帳號。不要在每個帳號各建一條管線。
陷阱 5：Control Tower vs Organizations
Organizations 是帳號與 SCP 的基礎；Control Tower 是蓋在它上面的自動化 landing zone。題目說「快速佈建合規的新帳號」選 Control Tower。
陷阱 6：藍綠部署的資料庫
schema 變更要向前相容，用「擴展再收縮」，不要一次改完。
💡一句話記憶：
編排找 CodePipeline，建置找 CodeBuild，換版與回退找 CodeDeploy，免金鑰找 OIDC，多帳號找 AssumeRole + Control Tower。
