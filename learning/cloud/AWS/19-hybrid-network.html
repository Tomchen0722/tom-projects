1. 混合雲的三條路：先看全景

把 AWS 想成你在別的城市新開的分公司：
Site-to-Site VPN = 走高速公路，今天就能通車，但塞不塞車看國道；
Direct Connect = 自己挖一條專用隧道，穩定又快，但要施工好幾個月；
Transit Gateway = 蓋一個交流道樞紐，以後每多一個分公司只要接上樞紐，不用兩兩對接。

混合雲網路的題目，九成都在問三件事的其中之一：「要多快通」「要多穩」「要連多少個 VPC」。先把這張全景圖記起來，後面的細節才有掛勾的地方。

【 你的機房 / 分公司 】 │ ┌───────────────────┼───────────────────┐ │ │ │ Site-to-Site VPN Direct Connect SD-WAN / GRE 走公網 · IPsec 實體專線 · 不加密 TGW Connect 幾分鐘可通 數週~數月施工 1.25 Gbps/tunnel 1 / 10 / 100 Gbps │ │ │ └───────────────────┼───────────────────┘ ▼ ┌──────────────────────────┐ │ Transit Gateway │ ← 區域級樞紐 │ （多路由表 = 網段隔離） │ └──────────────────────────┘ │ │ │ VPC-Prod VPC-Dev VPC-Shared ├─ Route 53 Resolver Endpoint └─ Interface Endpoint（PrivateLink）
為什麼要有 Transit Gateway？因為 VPC Peering 不可遞移。5 個 VPC 要全互連需要 5×4/2 = 10 條 Peering；10 個 VPC 就要 45 條。再加上每條都要各自維護路由表，這在十幾個 VPC 之後就沒有人管得動了。TGW 把它變成 N 條附件 的線性問題。

2. Site-to-Site VPN：最快上線的那條

組成的四個名詞

Customer Gateway (CGW)AWS 這邊建的設定物件，描述你機房那台路由器的公有 IP 與 BGP ASN。它不是實體設備。
Customer Gateway Device你機房裡真正的那台路由器／防火牆。要自己設定 IPsec。
Virtual Private Gateway (VGW)掛在單一 VPC 上的 VPN 端點。一個 VPC 只能有一個 VGW。
Transit Gateway另一種 VPN 端點。要連多個 VPC 或要用 ECMP 聚合頻寬，就必須用它而不是 VGW。
每條 VPN 連線一定是「兩條 tunnel」。AWS 會在兩個不同 AZ 各給一個端點 IP，所以一條 VPN Connection = 2 個 tunnel。單條 tunnel 上限 1.25 Gbps，而且預設只有一條在轉發流量（除非用 TGW + ECMP）。

考試陷阱：「AWS 端已經提供高可用了，客戶端呢？」——如果你機房只有一台路由器，那台掛掉照樣斷線。真正的高可用需要客戶端也有兩台設備，變成 2 條 VPN Connection、4 條 tunnel。

靜態路由 vs BGP（動態）

靜態路由BGP（動態）
設定手動列出對方網段自動交換路由
網段變更要人工改兩邊自動傳播
自動容錯移轉做不到（路由不會自己收斂）可以，tunnel 掛掉自動切另一條
DX 與 VPN 併用不建議必須用 BGP，才能自動主備切換
只要題目出現「自動容錯移轉」「不希望人工介入切換」，答案就是 BGP。靜態路由在考試裡幾乎只出現在「最簡單的 PoC」情境。

CLI 建立一條 VPN 連線

# ── ① 建立 Customer Gateway（描述你機房那台路由器）──
# BgpAsn：你機房的 BGP ASN，私有範圍 64512-65534
$ aws ec2 create-customer-gateway \
    --type ipsec.1 \
    --public-ip 203.0.113.10 \
    --bgp-asn 65000 \
    --tag-specifications 'ResourceType=customer-gateway,Tags=[{Key=Name,Value=hq-router}]'
{
    "CustomerGateway": {
        "CustomerGatewayId": "cgw-0a1b2c3d4e5f",
        "BgpAsn": "65000",
        "IpAddress": "203.0.113.10",
        "State": "available"
    }
}

# ── ② 建立 VPN 連線（這裡接到 Transit Gateway，不是 VGW）──
$ aws ec2 create-vpn-connection \
    --type ipsec.1 \
    --customer-gateway-id cgw-0a1b2c3d4e5f \
    --transit-gateway-id tgw-0abc123def456

# ── ③ 下載設定檔（交給機房的網管工程師）──
# AWS 會依廠牌產生可直接套用的設定：Cisco / Juniper / Fortinet / pfSense…
$ aws ec2 describe-vpn-connections \
    --vpn-connection-ids vpn-0123456789 \
    --query 'VpnConnections[0].CustomerGatewayConfiguration' --output text > hq-vpn.xml

# ── ④ 確認兩條 tunnel 的狀態 ──
$ aws ec2 describe-vpn-connections --vpn-connection-ids vpn-0123456789 \
    --query 'VpnConnections[0].VgwTelemetry[].[OutsideIpAddress,Status,StatusMessage]' \
    --output table
-------------------------------------------------
|  52.x.x.x   |  UP    |  1 BGP ROUTES          |
|  54.x.x.x   |  DOWN  |  IPSEC IS DOWN         |
-------------------------------------------------
只有一條 UP 正常嗎？技術上兩條都可以 UP，但流量預設只走一條。如果一條長期 DOWN，代表客戶端只設了一條 tunnel——這是真實世界最常見的設定疏漏，平時看不出來，AWS 做 tunnel 維護時就會整個斷線。

兩個容易忽略的加值選項

ECMP（等價多路徑）把多條 VPN 連線的頻寬相加。4 條 VPN ≈ 5 Gbps。只有 Transit Gateway 支援，VGW 不支援。
Accelerated VPN流量先進最近的 AWS 邊緣站點，再走 AWS 骨幹。同樣只支援 TGW。適合跨洲、公網品質差的情境。
陷阱：「如何提高 VPN 頻寬？」
答案不是「換更大的 VGW」（VGW 沒有規格可選），也不是「調整 tunnel 參數」。
正解是 改用 Transit Gateway 並建立多條 VPN 連線啟用 ECMP。看到「VPN 頻寬不夠」+「不想拉 DX」，就往 TGW + ECMP 想。

3. Direct Connect：實體專線與三種 VIF

DX 是一條實體光纖，預設「不加密」。很多人以為專線就等於安全——它只是不經過網際網路，資料在線上仍是明文。

合規要求加密時有兩個做法：
① VPN over Direct Connect（在 DX 的 Public VIF 上再跑一層 IPsec）——最常見，任何速率都能用。
② MACsec（L2 加密）——只在專用連線的 10 Gbps / 100 Gbps 連接埠、且該地點有支援時才能用。

三種 Virtual Interface（VIF）——本節重點

VIF 類型連到哪能存取什麼典型題目
Private VIF單一 VPC 的 VGW，或 DX GatewayVPC 內的私有 IP（EC2、RDS、Interface Endpoint）「地端要用私有 IP 連 EC2」
Public VIFAWS 公有服務端點S3、DynamoDB 等的公有端點，可跨區域，也可在上面跑 VPN over DX「地端走專線備份到 S3，不走網際網路」
Transit VIFDX Gateway → Transit GatewayTGW 後面掛的所有 VPC，可跨區域「一條專線連到幾十個 VPC」
三個 VIF 的口訣

Private VIF → 我要進 一個 VPC 的內網。
Public VIF → 我要走專線用 S3 / DynamoDB 這種公有端點。
Transit VIF → 我要進 一堆 VPC（因為後面接的是 TGW）。

看到「一條 DX 要連多個 VPC」就是 Transit VIF + DX Gateway + TGW 這個三件組。只用 Private VIF + VGW 的話，每個 VPC 都要一個 VIF，而每條 DX 連線的 VIF 數量有上限（專用連線預設 50 個），管理上也很痛苦。

Direct Connect Gateway 的兩個關鍵限制

【 東京機房 】 【 倫敦機房 】 │ │ DX 連線 DX 連線 │ │ └──────────┬─────────────────┘ ▼ ┌───────────────────────┐ │ Direct Connect GW │ ← 全球資源，可跨區域 └───────────────────────┘ │ │ VGW（東京） VGW（法蘭克福） │ │ VPC-A VPC-B ✗ VPC-A 與 VPC-B 不能透過 DX Gateway 互通 ✗
限制一：DX Gateway 不做 VPC 之間的轉送。它讓「機房 ↔ 多個區域的 VPC」通，但掛在同一個 DX Gateway 上的兩個 VPC 彼此不通。要 VPC 互通得另外用 Peering 或 TGW。

限制二：一個 DX Gateway 對每個區域只能關聯一個 Transit Gateway。多區域要各自設定關聯，並注意允許的前綴清單（Allowed Prefixes）。

連線種類與速率

Dedicated Connection（專用）Hosted Connection（託管）
誰給你AWS 直接配一個實體埠透過 APN 合作夥伴切分
速率1 / 10 / 100 Gbps50 Mbps 起跳的小額彈性方案
VIF 數量多個（預設 50）只有 1 個
MACsec10G / 100G 且地點支援時可用不支援
前置時間長（要做實體交叉連接）較短
LAG（Link Aggregation Group）把最多 4 條同速率、同一個 DX 地點的實體連線捆成一條邏輯連線，用 LACP 聚合頻寬。
它提升頻寬，但不是跨地點的高可用——LAG 的所有連線都在同一個 DX 位置，那個機房出事一樣全斷。這是很常見的觀念混淆。
實務提醒：DX 的帳單有兩塊——連接埠時數費（不管有沒有流量都在跳表）與資料傳出費。DX 的傳出費率比走網際網路便宜不少，所以「大量資料長期傳出」是 DX 少數能靠省流量費回本的情境。但如果流量不大，DX 幾乎一定比 VPN 貴——選它是為了穩定性，不是為了省錢。

4. DX 的高可用與備援設計（必考）

SAA 幾乎每次都會問「這個 DX 架構的弱點在哪」。AWS 官方把韌性分成幾個等級，把這張表背下來就能直接作答。

等級做法擋得住什麼SLA
最高韌性
Maximum Resiliency		兩個 DX 位置，每個位置各兩條連線（分屬不同裝置）裝置故障 + 整個 DX 機房故障99.99%
高韌性
High Resiliency		兩個 DX 位置，各一條連線整個 DX 機房故障99.9%
開發／測試單一 DX 位置，兩條連線（不同裝置）只擋單一裝置故障無承諾
成本取向備援DX 一條 + Site-to-Site VPN 備援DX 全斷時降速續命依 VPN SLA
解題捷徑：題目說「要最高可用性、預算充足」→ 兩個 DX 位置各兩條（99.99%）。
題目說「要備援但要控制成本」→ DX + VPN 備援，這是出現頻率最高的答案。
題目說「DX 施工要三個月，但下週就要連線」→ 先上 VPN，DX 完成後 VPN 轉備援。

主備怎麼自動切？靠 BGP，不靠人

正常時： DX 斷線後： 機房 ──DX（優先）──▶ AWS 機房 ──DX ✗ └──VPN（待命）───▶ AWS └──VPN（自動接手）──▶ AWS 同一個前綴同時從 DX 與 VPN 傳來時，AWS 端偏好 DX。 DX 的 BGP 工作階段斷掉 → 路由撤銷 → 流量自動落到 VPN。
為什麼 DX 會贏？在相同前綴長度下，AWS 端的路由偏好順序是 Direct Connect 的 BGP 路由 > VPN。所以只要兩邊都跑 BGP 而且宣告相同網段，切換是自動的，不需要任何人工動作。

要自己控制方向時的兩個工具：
① AS_PATH prepending——在備援線路上把自己的 ASN 重複宣告幾次，路徑看起來變長就成為備援。
② 更明確的前綴（longest prefix match）——宣告 /25 一定贏過 /24，這比任何 BGP 屬性都優先。
陷阱：DX 斷線時 VPN 沒接手
十次有九次是因為 VPN 用了靜態路由。靜態路由不會因為對方掛掉而收斂，流量還是往黑洞送。DX + VPN 備援架構必須兩邊都跑 BGP。
陷阱：把 LAG 當成高可用
LAG 的 4 條線都在同一個 DX 位置。它解決的是頻寬與單一裝置故障，不是機房級故障。題目問「如何防止單一 DX 位置故障」→ 答案是第二個 DX 位置，不是 LAG。
實務提醒：備援線路平常沒流量，很容易「以為它好好的」。至少每季做一次切換演練（手動關掉 DX 的 BGP 工作階段，確認流量落到 VPN 且應用程式仍可用）。另外要先算過：VPN 每條 tunnel 只有 1.25 Gbps，如果平常 DX 跑 5 Gbps，切過去會直接塞爆——這時要嘛接受降級、要嘛用 TGW + ECMP 疊多條 VPN。

5. Transit Gateway：區域級路由中樞

它能接什麼

VPC 附件每個 VPC 在每個要通的 AZ 選一個子網路放 TGW 的 ENI。沒選到的 AZ 走不通——這是最常見的連不上原因。
VPN 附件Site-to-Site VPN 接 TGW，可用 ECMP 聚合頻寬。
DX Gateway 附件透過 Transit VIF 進來，一條專線通到所有 VPC。
TGW Peering連到另一個區域的 TGW，走 AWS 骨幹並自動加密。
Connect 附件用 GRE + BGP 接 SD-WAN 設備（例如 EC2 上的第三方虛擬路由器）。

多路由表 = 網段隔離（TGW 真正的價值）

預設路由表會讓所有附件互通。企業真正要的通常是「Prod 與 Dev 不能互通，但兩者都能存取共享服務 VPC 與地端」。TGW 用多張路由表 + 關聯（association）與傳播（propagation）做這件事：

附件「關聯」到哪張路由表 = 它出去時查哪張表 附件「傳播」到哪張路由表 = 它的網段出現在哪張表 RT-Prod RT-Dev RT-Shared ├ VPC-Prod ✓ ├ VPC-Dev ✓ ├ VPC-Shared ✓ ├ VPC-Shared ✓ ├ VPC-Shared ✓ ├ VPC-Prod ✓ └ VPN(地端) ✓ └ VPN(地端) ✓ └ VPC-Dev ✓ （沒有 VPC-Dev） （沒有 VPC-Prod） 結果：Prod ↔ Shared ✓　Dev ↔ Shared ✓　Prod ↔ Dev ✗

CLI 建立 TGW 與隔離路由表

# ── ① 建立 TGW，關掉「自動關聯／自動傳播」才能自己控制隔離 ──
$ aws ec2 create-transit-gateway \
    --description "corp-hub" \
    --options 'DefaultRouteTableAssociation=disable,DefaultRouteTablePropagation=disable,AutoAcceptSharedAttachments=disable,DnsSupport=enable'

# ── ② 把 VPC 接上來（每個 AZ 指定一個 /28 專用子網路）──
$ aws ec2 create-transit-gateway-vpc-attachment \
    --transit-gateway-id tgw-0abc123def456 \
    --vpc-id vpc-prod111 \
    --subnet-ids subnet-tgw-a subnet-tgw-c

# ── ③ 建立自訂路由表 ──
$ aws ec2 create-transit-gateway-route-table \
    --transit-gateway-id tgw-0abc123def456 \
    --tag-specifications 'ResourceType=transit-gateway-route-table,Tags=[{Key=Name,Value=rt-prod}]'

# ── ④ 關聯：Prod 附件出去時查 rt-prod ──
$ aws ec2 associate-transit-gateway-route-table \
    --transit-gateway-route-table-id tgw-rtb-prod \
    --transit-gateway-attachment-id tgw-attach-prod

# ── ⑤ 傳播：讓 Shared 的網段出現在 rt-prod 裡 ──
$ aws ec2 enable-transit-gateway-route-table-propagation \
    --transit-gateway-route-table-id tgw-rtb-prod \
    --transit-gateway-attachment-id tgw-attach-shared

# ── ⑥ 別忘了 VPC 自己的子網路路由表也要指向 TGW ──
$ aws ec2 create-route --route-table-id rtb-prod-private \
    --destination-cidr-block 10.0.0.0/8 \
    --transit-gateway-id tgw-0abc123def456
兩層路由，兩邊都要設。最常見的錯誤是「TGW 路由表設好了但還是不通」——因為 VPC 子網路的路由表沒有指向 TGW。
記住這個鏈：來源子網路路由表 → TGW 附件 → TGW 路由表 → 對方 TGW 附件 → 對方子網路路由表，任何一段漏掉就不通。回程路由也一樣要檢查。
限制／特性內容考點
每個 VPC 對同一 TGW 的附件1 個不能為了隔離而重複掛同一個 VPC
跨區域 TGW Peering需要靜態路由，不支援路由傳播常考：跨區為何學不到路由
多播TGW 支援（VPC Peering 不支援）金融行情推播等情境
網段重疊不能重疊與 Peering 相同的限制
計費每個附件每小時 + 每 GB 處理費Peering 沒有附件費，這是成本題的分水嶺
陷阱：TGW vs VPC Peering 的成本題
只有兩個 VPC、流量很大、要最低成本與最低延遲 → VPC Peering（沒有附件費也沒有處理費，只付跨 AZ／跨區流量）。
很多 VPC、要集中管控與隔離 → TGW。
出題時通常用「兩個」或「數十個」這種數量詞暗示答案。

6. Route 53 Resolver：混合 DNS 的唯一解

網路通了不等於名稱解得出來。混合雲最常見的「明明 ping 得到 IP 卻連不上」，十次有八次是 DNS：地端解不出 db.aws.internal，或 VPC 內解不出 ad.corp.local。這一節就是解決這件事。

先認識 VPC 內建的 .2 Resolver

VPC CIDR 的基底 + 2 = Route 53 Resolver 的位址

VPC 10.0.0.0/16 → Resolver 在 10.0.0.2
VPC 172.31.0.0/16 → Resolver 在 172.31.0.2
也可以用固定位址 169.254.169.253

這個 Resolver 只能從 VPC 內部查詢。地端機器直接指向 10.0.0.2 是查不到的——它不是一個可從外部路由到的端點。要打通就要用兩種 Endpoint。

兩種 Resolver Endpoint：方向相反，常常兩個都要建

Inbound Endpoint（地端 → AWS） 地端 DNS ──查 db.aws.internal──▶ Inbound EP ──▶ Private Hosted Zone （在地端 DNS 上設條件轉送：aws.internal → Inbound EP 的兩個 IP） Outbound Endpoint（AWS → 地端） VPC 內 EC2 ──查 ad.corp.local──▶ .2 Resolver │ 命中 Resolver Rule ▼ Outbound EP ──▶ 地端 DNS 伺服器
Inbound Endpoint地端要解 AWS 的私有名稱時用。地端 DNS 設條件轉送指向它。
Outbound EndpointVPC 內要解地端名稱時用。搭配 Resolver Rule 指定「哪個網域轉給哪台地端 DNS」。
Resolver Rule轉送規則本身。可以用 RAM 分享給整個組織，不必每個帳號重複建。
DNS Firewall依網域清單封鎖查詢，擋惡意中繼站與 DNS 資料外洩。屬於資安題的答案。
每個 Endpoint 至少要指定兩個 IP，且必須在不同 AZ——這是高可用的硬性要求，考題會用「工程師只設了一個 IP」當錯誤選項。

CLI 建立雙向解析

# ── ① Outbound Endpoint：讓 VPC 查得到地端 ──
$ aws route53resolver create-resolver-endpoint \
    --name to-onprem \
    --direction OUTBOUND \
    --security-group-ids sg-resolver \
    --ip-addresses SubnetId=subnet-a SubnetId=subnet-c \
    --creator-request-id $(date +%s)

# ── ② 轉送規則：corp.local 這個網域丟給地端 DNS ──
$ aws route53resolver create-resolver-rule \
    --name fwd-corp-local \
    --rule-type FORWARD \
    --domain-name corp.local \
    --resolver-endpoint-id rslvr-out-0abc123 \
    --target-ips Ip=192.168.10.53,Port=53 Ip=192.168.20.53,Port=53 \
    --creator-request-id $(date +%s)

# ── ③ 規則要「關聯到 VPC」才會生效（最常漏掉的一步）──
$ aws route53resolver associate-resolver-rule \
    --resolver-rule-id rslvr-rr-0abc123 --vpc-id vpc-prod111

# ── ④ Inbound Endpoint：讓地端查得到 AWS ──
$ aws route53resolver create-resolver-endpoint \
    --name from-onprem \
    --direction INBOUND \
    --security-group-ids sg-resolver \
    --ip-addresses SubnetId=subnet-a SubnetId=subnet-c \
    --creator-request-id $(date +%s)

# ── ⑤ 取得 Inbound EP 的兩個 IP，交給地端 DNS 設條件轉送 ──
$ aws route53resolver list-resolver-endpoint-ip-addresses \
    --resolver-endpoint-id rslvr-in-0def456 \
    --query 'IpAddresses[].Ip' --output text
10.0.1.87    10.0.2.145
Security Group 要開 TCP 與 UDP 的 53 埠，兩種都要。DNS 回應超過 512 bytes（例如記錄很多或啟用 DNSSEC）會退回 TCP，只開 UDP 會出現「有些查詢成功、有些逾時」這種非常難查的症狀。
陷阱 1：只建一個方向
題目說「地端與 AWS 要互相解析對方的主機名稱」→ 答案必須同時包含 Inbound 與 Outbound Endpoint。只選一個的選項是錯的。
陷阱 2：以為 Private Hosted Zone 自動給地端用
Private Hosted Zone 只服務「已關聯的 VPC」。地端要查它，一定要經過 Inbound Endpoint。
陷阱 3：把自架 DNS 當標準答案
在 EC2 上架 BIND 做轉送技術上可行，但考試偏好受管服務。看到「最少維運負擔」就選 Route 53 Resolver Endpoint。
企業實務：大型組織會在「共享服務 VPC」建一組 Inbound/Outbound Endpoint，再用 RAM 把 Resolver Rule 分享給整個 Organization，各帳號只要把規則關聯到自己的 VPC 就好。Endpoint 是按每個 ENI 每小時計費的，集中建一組而不是每個帳號各建一組，能省下相當可觀的固定成本。

正解是 S3 的 Interface Endpoint（PrivateLink），或走 DX Public VIF。

PrivateLink 的另一面：把自己的服務曝露出去

【 服務提供者帳號 】 【 消費者帳號 】 應用程式 ──▶ NLB ──▶ Endpoint Service │ ▼ Interface Endpoint（ENI） ──▶ 消費者的 EC2 流量單向：消費者連得到提供者，提供者連不到消費者。 兩邊網段可以完全重疊——因為根本沒有路由層的連通。
PrivateLink vs Peering 的判斷點：
要「整個網路互通」→ Peering / TGW。
只要「曝露一個服務，而且不想讓對方看到我整個 VPC」→ PrivateLink。
網段重疊或跨組織／SaaS 供應商的情境幾乎一定是 PrivateLink。
成本提醒：Interface Endpoint 是每個 AZ 一個 ENI、每個 ENI 都在跳表。一個帳號如果為了「安全」把二十個服務都建 Interface Endpoint、每個都跨三個 AZ，那就是 60 個 ENI 的固定月費，往往比原本的 NAT Gateway 還貴。先確認真的有私有存取需求再建；S3 與 DynamoDB 優先用免費的 Gateway Endpoint。

8. VPC 共享（RAM）與 IPv6 出口

AWS Resource Access Manager：把子網路借給別的帳號

多帳號架構有個現實問題：每個帳號各自建 VPC，網段規劃很快就亂掉，而且跨帳號流量都要繞 TGW（附件費 + 處理費）。VPC Sharing 換一個思路——網路只有一份，帳號分開。

擁有者帳號（Owner）參與者帳號（Participant）
建立 / 修改 VPC、子網路、路由表✓✗
在共享子網路建 EC2、RDS、ALB✓✓
看得到對方建的資源看得到（但不能修改）看不到其他參與者的資源
Security Group自己的可引用擁有者建立的 SG
 
# 分享子網路給 Organizations 內的帳號（先在 Organizations 啟用 RAM 共享）
$ aws ram create-resource-share \
    --name shared-app-subnets \
    --resource-arns arn:aws:ec2:ap-northeast-1:111122223333:subnet/subnet-aaa \
                    arn:aws:ec2:ap-northeast-1:111122223333:subnet/subnet-bbb \
    --principals 444455556666 \
    --allow-external-principals false
VPC Sharing 的三個好處：① 網段集中規劃不會亂；② 帳號之間的流量是同一個 VPC 內的流量，沒有 TGW 附件費也沒有處理費；③ 網路團隊集中管控，應用團隊不用碰路由表。
限制：不能分享 default VPC，而且只能分享子網路，不是整個 VPC。
陷阱：RAM 與 TGW 的成本比較題
「多個帳號的工作負載需要互相通訊，要最低成本」——如果它們可以待在同一個 VPC，答案是 RAM 共享子網路（同 VPC 內沒有處理費），不是 TGW。
但如果題目強調「各團隊要獨立的 VPC 與網路自主權」，那就回到 TGW。

IPv6 與 Egress-Only Internet Gateway

IPv6 位址全部都是公有的，沒有「私有 IPv6」也沒有 NAT。所以只要給子網路配了 IPv6 並掛上 IGW，那台機器就是雙向可達的——這跟 IPv4 私有子網路的直覺完全相反，是很容易踩到的資安坑。
NAT Gateway只處理 IPv4。私有子網路出網際網路用它。
Egress-Only IGWIPv6 專用。只允許出站、拒絕主動入站，等同 IPv6 版的 NAT Gateway。本身免費。
NAT64 + DNS64讓 IPv6-only 子網路的機器連得到只有 IPv4 的服務。
考點一句話：「IPv6 執行個體需要出網際網路更新套件，但不能被外面主動連入」→ Egress-Only Internet Gateway。選 NAT Gateway 是錯的（它不處理 IPv6）。

實作 Lab：用 TGW 串起兩個 VPC 並打通混合 DNS

約 60 分鐘。沒有實體機房也能做——用第二個 VPC 模擬「地端」。

這個 Lab 會產生費用，請務必做完就刪。主要花費是 Transit Gateway 的附件時數費（兩個附件）與 Route 53 Resolver Endpoint 的 ENI 時數費（一個 Endpoint 兩個 IP）。粗估全部開著兩小時大約在 US$1 以內。Resolver Endpoint 是這裡最貴的東西，測完立刻刪。實際費率請以自己區域的定價頁為準。

階段一：建立 TGW 與兩個附件

  1. 建立兩個 VPC：vpc-app（10.10.0.0/16） 與 vpc-sim-onprem（10.20.0.0/16），各開一個私有子網路與一個 /28 的 TGW 專用子網路
  2. 建立 Transit Gateway，把預設關聯與預設傳播都停用
  3. 為兩個 VPC 各建一個 VPC 附件（子網路選 TGW 專用子網路）
  4. 建立一張路由表，把兩個附件都關聯並傳播上去
  5. 兩個 VPC 的子網路路由表各加一條：10.0.0.0/8 → tgw-xxx
  6. 各開一台 EC2（用 SSM Session Manager 連線，不要開 22 埠），互相 ping 私有 IP
ping 不通的檢查順序（照這個順序查，不要亂猜）：
① Security Group 放行 ICMP 了嗎？② 子網路路由表指向 TGW 了嗎？③ TGW 路由表裡看得到對方網段嗎（search-transit-gateway-routes）？④ 對方 VPC 的附件有沒有涵蓋到那台 EC2 所在的 AZ？⑤ 回程路由設了嗎？

階段二：混合 DNS

  1. 在 vpc-sim-onprem 開一台 EC2 裝 dnsmasq 模擬地端 DNS，設一筆 app.corp.local → 10.20.1.50
  2. 在 vpc-app 建 Outbound Resolver Endpoint（兩個 AZ）
  3. 建 Resolver Rule：corp.local 轉送到那台 dnsmasq 的 IP，並關聯到 vpc-app
  4. 在 vpc-app 的 EC2 執行 dig app.corp.local，應該解得出 10.20.1.50
  5. 反向驗證：在 vpc-app 建一個 Private Hosted Zone（aws.internal）與一筆 A 記錄，建 Inbound Endpoint，把 dnsmasq 的上游改指向 Inbound Endpoint 的 IP，再從「地端」那台 dig db.aws.internal
# 驗證用的三個指令
$ dig +short app.corp.local              # 走 Outbound Rule 到地端
$ dig +short db.aws.internal @10.0.1.87   # 直接打 Inbound EP 的 IP
$ aws ec2 search-transit-gateway-routes \
    --transit-gateway-route-table-id tgw-rtb-xxx \
    --filters "Name=state,Values=active" \
    --query 'Routes[].[DestinationCidrBlock,State]' --output table

階段三：清理（重要）

  1. 先刪 Resolver Endpoint（最貴）與 Resolver Rule
  2. 終止 EC2
  3. 刪 TGW 附件 → 等狀態變 deleted → 刪路由表 → 刪 TGW
  4. 刪 VPC
順序不能顛倒：附件還在就刪不掉 TGW，TGW 附件還在就刪不掉 VPC。看到 DependencyViolation 就是這個原因。

10. 考試陷阱整理

陷阱 1：以為 Direct Connect 是加密的
不是。它是實體專線，預設明文。要加密就 VPN over DX（Public VIF）或 MACsec（僅 10G/100G 專用連線且地點支援）。
陷阱 2：以為 DX 可以「很快」建好
不行，前置期以週或月計。題目只要出現「盡快」「立即」「下週上線」，答案就是 Site-to-Site VPN。
陷阱 3：Gateway Endpoint 給地端用
做不到。Gateway Endpoint 只作用在 VPC 的路由表上，DX/VPN 進來的流量用不到它。地端要私有連 S3 → Interface Endpoint 或 DX Public VIF。
陷阱 4：以為 VPC Peering 可以遞移
不能。A↔B、B↔C 不會讓 A↔C 通。多 VPC 互連的答案是 Transit Gateway。而且 Peering 兩邊網段不能重疊。
陷阱 5：以為 VGW 支援 ECMP
不支援。只有 Transit Gateway 支援 ECMP 與 Accelerated VPN。看到「用多條 VPN 提高頻寬」就要換成 TGW。
陷阱 6：LAG = 高可用
LAG 的 4 條線在同一個 DX 位置，只擋裝置故障。要擋機房級故障必須是第二個 DX 位置。
陷阱 7：DX + VPN 備援用靜態路由
切不過去。自動容錯移轉必須用 BGP。
陷阱 8：以為 DX Gateway 能讓兩個 VPC 互通
不能。DX Gateway 連的是「機房 ↔ 各區域 VPC」，掛在上面的 VPC 之間互不相通。要互通得用 TGW 或 Peering。
陷阱 9：混合 DNS 只建一個 Endpoint
「互相解析」= Inbound + Outbound 兩個都要。方向搞反也是常見錯誤選項：地端查 AWS 用 Inbound，AWS 查地端用 Outbound。
陷阱 10：TGW 附件沒涵蓋所有 AZ
VPC 附件是「每個 AZ 選一個子網路」。沒被選到的 AZ 裡的 EC2 走不出去。這是實務上最難查的 TGW 故障，也是題目愛用的錯誤設定。
陷阱 11：以為 Egress-Only IGW 處理 IPv4
不是。它只管 IPv6。IPv4 私有子網路出網際網路仍然是 NAT Gateway。
💡一句話記憶：
要快用 VPN，要穩用 DX，要多用 TGW，只有兩個用 Peering；
專線要加密再疊一層 VPN，備援要自動就跑 BGP；
地端連 S3 用 Interface 不用 Gateway，互相解析 DNS 兩個 Endpoint 都要建。
