1. 開帳號第一天的六件事

AWS 是「用多少付多少，而且沒有上限」。沒有預付、沒有硬性天花板——開錯一台機器忘了關，一個月可能燒掉數萬元。金鑰外洩被拿去挖礦，帳單可以到六位數。

所以「省錢」和「安全」在 AWS 是同一件事，兩者都必須在第一天就處理，不能等出事再說。
1
root 帳號開啟 MFAroot 有無限權限、無法用 Policy 限制、連帳號都能關掉。沒有例外，這是第一件事。
2
刪掉 root 的 Access Key如果有的話（現在新帳號預設沒有）。root 金鑰外洩等於整個帳號被接管。
3
建立一個 IAM 管理者帳號，之後日常都用它root 只在少數幾個非它不可的操作時登入（改帳單資訊、關閉帳號、改支援方案）。
4
設定 Budget 預算告警下一節詳述。這是唯一能在帳單失控前通知你的機制。
5
開啟 CloudTrail記錄「誰在什麼時候呼叫了哪個 API」。出事時這是唯一的證據來源。
6
設定密碼政策與 MFA 強制所有 IAM 使用者都要 MFA，密碼長度至少 14 碼。
root 到底哪些事非它不可？考試會考，實務上也要知道：
  • 修改帳號名稱、email、root 密碼
  • 修改付款方式與帳單聯絡資訊
  • 關閉 AWS 帳號
  • 變更 AWS Support 方案
  • 還原被誤刪的 IAM 管理者權限
  • 建立 CloudFront 金鑰對、註冊 GovCloud
  • 修改 S3 bucket 的某些特殊政策（把自己鎖出去之後）
除此之外的所有事情都應該用 IAM 身分做。

密碼政策設定（CLI）

$ aws iam update-account-password-policy \
    --minimum-password-length 14 \
    --require-symbols \
    --require-numbers \
    --require-uppercase-characters \
    --require-lowercase-characters \
    --allow-users-to-change-password \
    --max-password-age 90 \
    --password-reuse-prevention 5

# 確認結果
$ aws iam get-account-password-policy

檢查帳號目前的安全狀態

# 產生憑證報告：列出所有使用者的 MFA、金鑰、密碼狀態
$ aws iam generate-credential-report
$ aws iam get-credential-report --query Content --output text | base64 -d > report.csv

# 找出「有 Access Key 但從沒用過」的殭屍金鑰
$ aws iam list-users --query 'Users[].UserName' --output text | \
  tr '\t' '\n' | while read u; do
    aws iam list-access-keys --user-name "$u" \
      --query 'AccessKeyMetadata[].[UserName,AccessKeyId,CreateDate,Status]' --output text
  done
憑證報告是稽核的起點。它一次列出所有使用者的：密碼多久沒換、有沒有 MFA、Access Key 建立多久、上次使用是什麼時候。90 天沒用過的金鑰就該停用——那通常是離職員工或早就廢棄的腳本留下的。

2. 先設預算告警（避免帳單意外）

AWS Budgets 每個帳號前兩個預算免費，第三個開始每個每天 US$0.02（約每月 US$0.60）。這是整個 AWS 裡最值得花的錢——它可能幫你省下數萬元的意外帳單。

用 CLI 建立預算

# 先取得自己的帳號 ID
$ aws sts get-caller-identity
{
    "UserId": "AIDXXXXXXXXXXXXXXXXX",
    "Account": "123456789012",
    "Arn": "arn:aws:iam::123456789012:user/tom-admin"
}

# budget.json —— 每月上限 50 美元
$ cat > budget.json <<'EOF'
{
  "BudgetName": "monthly-cost-guard",
  "BudgetLimit": { "Amount": "50", "Unit": "USD" },
  "TimeUnit": "MONTHLY",
  "BudgetType": "COST"
}
EOF

# notify.json —— 三段告警：實際 50%、實際 80%、預測 100%
$ cat > notify.json <<'EOF'
[
  {
    "Notification": {
      "NotificationType": "ACTUAL",
      "ComparisonOperator": "GREATER_THAN",
      "Threshold": 50,
      "ThresholdType": "PERCENTAGE"
    },
    "Subscribers": [
      { "SubscriptionType": "EMAIL", "Address": "you@example.com" }
    ]
  },
  {
    "Notification": {
      "NotificationType": "ACTUAL",
      "ComparisonOperator": "GREATER_THAN",
      "Threshold": 80,
      "ThresholdType": "PERCENTAGE"
    },
    "Subscribers": [
      { "SubscriptionType": "EMAIL", "Address": "you@example.com" }
    ]
  },
  {
    "Notification": {
      "NotificationType": "FORECASTED",
      "ComparisonOperator": "GREATER_THAN",
      "Threshold": 100,
      "ThresholdType": "PERCENTAGE"
    },
    "Subscribers": [
      { "SubscriptionType": "EMAIL", "Address": "you@example.com" }
    ]
  }
]
EOF

$ aws budgets create-budget \
    --account-id 123456789012 \
    --budget file://budget.json \
    --notifications-with-subscribers file://notify.json
FORECASTED 這一條最重要。它用目前的花費速度預測月底會花多少。如果你月初第 3 天就開了一台很貴的機器，ACTUAL 還很低不會告警，但 FORECASTED 會立刻通知你「照這速度月底會超支」。這能提早二十幾天發現問題。
Budget 只會「通知」，不會幫你關掉資源。收到信之後還是要自己去處理。想自動停機的話要另外做：Budget → SNS → Lambda → 停止 EC2。這在第 08 章會實作。

成本異常偵測（免費，強烈建議開）

# Cost Anomaly Detection 會用機器學習找出「不尋常的花費」
# 例如平常每天 3 美元，突然某天變 80 美元 → 立刻通知
$ aws ce create-anomaly-monitor --anomaly-monitor '{
    "MonitorName": "whole-account-monitor",
    "MonitorType": "DIMENSIONAL",
    "MonitorDimension": "SERVICE"
}'
開發／學習用的帳號，建議預算設 US$20–50。多數 SAA 練習用得到的資源（t3.micro、小型 RDS、S3 幾 GB）如果每次用完都關掉，一個月通常在 US$10 以內。會爆掉的都是「忘記關」的東西——NAT Gateway、彈性 IP、RDS、負載平衡器。

三個超好用的 CLI 技巧

$ aws ec2 run-instances --image-id ami-xxx --instance-type t3.micro --dry-run
An error occurred (DryRunOperation) ... ← 看到這個代表「權限沒問題，真跑會成功」

# ② --query：用 JMESPath 只取你要的欄位
$ aws ec2 describe-instances \
    --query 'Reservations[].Instances[].[InstanceId,InstanceType,State.Name,Tags[?Key==`Name`].Value|[0]]' \
    --output table

# ③ --output table / text / yaml，看人不看機器時用 table
$ aws s3api list-buckets --query 'Buckets[].[Name,CreationDate]' --output table
--query 是在本機過濾，--filters 是在AWS 端過濾。資源多的時候用 --filters 效率高很多（少傳輸資料、少 API 分頁）。兩個可以一起用：先 filters 縮小範圍，再 query 取欄位。

4. 四個核心身分：User、Group、Role、Policy

User（使用者）代表一個人或一個程式。有長期憑證（密碼或 Access Key）。
Group（群組）User 的集合，只是為了方便掛 Policy。Group 不能登入，也不能被 AssumeRole。
Role（角色）可以被臨時扮演的身分。沒有長期憑證，發的是有時效的臨時憑證。
Policy（政策）一份 JSON 文件，寫明誰能對什麼資源做什麼事。
比喻：User 是員工識別證——你一直帶著它。Role 是臨時通行證——要進機房時去櫃檯借，用完就過期。Policy 是門禁規則表——寫明「哪張證能開哪扇門」。

為什麼 Role 比較安全？因為臨時憑證幾小時後就失效。就算外洩，攻擊者能用的時間非常有限；長期 Access Key 外洩則是直到你發現並手動撤銷為止都有效。
最重要的一條實務原則：程式不要用 Access Key，要用 Role。
場景❌ 錯誤做法✅ 正確做法
EC2 上的程式要讀 S3把 Access Key 寫進設定檔掛 EC2 Instance Profile
Lambda 要寫 DynamoDB用環境變數存金鑰Lambda 的 Execution Role
ECS 容器要拿 Secretbuild 進 imageTask Role
GitHub Actions 要部署把金鑰存 Repository SecretOIDC + AssumeRole（無金鑰）
這是 SAA 考試的高頻考點：「應用程式如何安全地存取 AWS 服務？」答案永遠是 Role，不是 Access Key。

建立使用者與群組（CLI 完整流程）

# ① 建立群組並掛上政策
$ aws iam create-group --group-name Developers
$ aws iam attach-group-policy \
    --group-name Developers \
    --policy-arn arn:aws:iam::aws:policy/PowerUserAccess

# ② 建立使用者
$ aws iam create-user --user-name alice

# ③ 加入群組（權限由群組來，不要直接掛在使用者身上）
$ aws iam add-user-to-group --user-name alice --group-name Developers

# ④ 給主控台登入密碼，並強制首次登入必須改密碼
$ aws iam create-login-profile \
    --user-name alice \
    --password 'TempP@ssw0rd-2026!' \
    --password-reset-required

# ⑤ 需要 CLI 存取才建 Access Key（能不建就不建）
$ aws iam create-access-key --user-name alice
create-access-key 的 SecretAccessKey 只會顯示這一次。關掉視窗就再也拿不回來，只能刪掉重建。而且這個輸出會留在你的終端機歷史紀錄裡——用完記得 clear 並檢查 ~/.bash_history。
權限一律掛在 Group 上，不要掛在 User 上。理由：新人報到只要加進群組就好；權限稽核時看幾個群組而不是看幾百個人；離職只要移出群組。直接掛在 User 上的權限，半年後沒人記得為什麼要給。

5. Policy JSON 逐欄拆解

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowReadCompanyBucket",
      "Effect": "Allow",
      "Action": [
        "s3:GetObject",
        "s3:ListBucket"
      ],
      "Resource": [
        "arn:aws:s3:::company-reports",
        "arn:aws:s3:::company-reports/*"
      ],
      "Condition": {
        "IpAddress": { "aws:SourceIp": ["203.0.113.0/24"] },
        "Bool": { "aws:MultiFactorAuthPresent": "true" }
      }
    }
  ]
}
欄位必填意義
Version是政策語言版本。永遠寫 2012-10-17，這不是日期，是版本代號
Sid否Statement ID，給人看的備註
Effect是Allow 或 Deny
Action是可以做什麼，格式 服務:動作，支援萬用字元
Resource是*對什麼資源。用 ARN 指定
Principal是**誰。只有「資源型政策」才有這欄
Condition否什麼條件下才成立

* 少數 Action 不支援資源層級限制，只能寫 "*"　** 身分型政策不寫 Principal（因為它掛在誰身上，誰就是 Principal）

兩種 Policy 的差別（考試必考）

Identity-based（身分型）Resource-based（資源型）
掛在哪User / Group / Role資源本身（S3 bucket、SQS queue、KMS key…）
有 Principal 欄位？沒有有（必填）
能不能跨帳號不能單獨做到可以
典型例子「alice 可以讀 S3」「這個 bucket 允許帳號 B 讀」
跨帳號存取一定要「兩邊都設」。帳號 A 的使用者要讀帳號 B 的 bucket：
  1. 帳號 B 的 bucket policy 要 Allow 帳號 A 的 Principal
  2. 帳號 A 的 IAM policy 也要 Allow 對那個 bucket 的動作
只設一邊會失敗。這是 SAA 的經典題型。

ARN 的格式

arn:partition:service:region:account-id:resource

arn:aws:s3:::my-bucket/reports/*
arn:aws:ec2:ap-northeast-1:123456789012:instance/i-0abc123
arn:aws:iam::123456789012:role/AppRole
S3 的 ARN 沒有 region 和 account-id（中間連續三個冒號），因為 bucket 名稱是全球唯一的。IAM 的 ARN 沒有 region（IAM 是全球服務）。這兩個細節考試會考。

常用的 Condition 條件

Condition Key用途
aws:MultiFactorAuthPresent要求必須通過 MFA
aws:SourceIp限制來源 IP（從 VPC endpoint 來的流量不適用）
aws:SourceVpce限制必須從特定 VPC Endpoint 進來
aws:RequestedRegion限制只能在特定 region 操作（省錢＋合規常用）
aws:PrincipalTag/xxx依身分上的標籤判斷（ABAC）
aws:ResourceTag/xxx依資源上的標籤判斷
s3:x-amz-server-side-encryption強制上傳時必須加密
企業常用範例一：限制只能在東京區操作

防止員工誤在昂貴的 region 開資源，也符合資料落地的合規要求。

{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "DenyOutsideTokyo",
    "Effect": "Deny",
    "NotAction": [
      // 全球型服務不能擋，否則整個帳號會壞掉
      "iam:*", "sts:*", "organizations:*", "route53:*",
      "cloudfront:*", "support:*", "budgets:*", "ce:*"
    ],
    "Resource": "*",
    "Condition": {
      "StringNotEquals": { "aws:RequestedRegion": "ap-northeast-1" }
    }
  }]
}
企業常用範例二：ABAC — 用標籤自動配權限

「你只能操作標籤 Team 跟你自己相同的資源」。不用為每個團隊寫一份 policy，加新團隊時完全不用改政策。

{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": ["ec2:StartInstances", "ec2:StopInstances", "ec2:RebootInstances"],
    "Resource": "arn:aws:ec2:*:*:instance/*",
    "Condition": {
      "StringEquals": {
        "aws:ResourceTag/Team": "${aws:PrincipalTag/Team}"
      }
    }
  }]
}
企業常用範例三：強制 S3 上傳必須加密
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyUnencryptedUploads",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:PutObject",
      "Resource": "arn:aws:s3:::company-reports/*",
      "Condition": {
        "StringNotEquals": { "s3:x-amz-server-side-encryption": "aws:kms" }
      }
    },
    {
      "Sid": "DenyInsecureTransport",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:*",
      "Resource": [
        "arn:aws:s3:::company-reports",
        "arn:aws:s3:::company-reports/*"
      ],
      "Condition": { "Bool": { "aws:SecureTransport": "false" } }
    }
  ]
}

建立自訂政策並掛上

$ aws iam create-policy \
    --policy-name TokyoOnly \
    --policy-document file://tokyo-only.json \
    --description "限制只能在 ap-northeast-1 操作"

$ aws iam attach-group-policy \
    --group-name Developers \
    --policy-arn arn:aws:iam::123456789012:policy/TokyoOnly

# 改政策要建新版本，最多保留 5 個版本
$ aws iam create-policy-version \
    --policy-arn arn:aws:iam::123456789012:policy/TokyoOnly \
    --policy-document file://tokyo-only-v2.json \
    --set-as-default

# 出事了？切回舊版本（這是 IAM 內建的回滾機制）
$ aws iam set-default-policy-version \
    --policy-arn arn:aws:iam::123456789012:policy/TokyoOnly \
    --version-id v1

6. 權限判斷邏輯（考試必考）

當一個請求進來，AWS 依這個順序判斷，只要走到「拒絕」就立刻結束：

1
預設是拒絕（Implicit Deny）沒有任何政策明確允許 → 拒絕。
2
有沒有明確的 Deny？只要任何一個政策寫了 Deny → 立刻拒絕，不管有多少 Allow。
3
SCP（Organizations 服務控制政策）允許嗎？SCP 是天花板，它不給的權限，帳號內誰也拿不到——連 root 都不行。
4
Permissions Boundary 允許嗎？如果身分有設邊界，實際權限 = 身分政策 ∩ 邊界。
5
Session Policy 允許嗎？AssumeRole 時可以額外再縮小權限。
6
有明確的 Allow 嗎？身分型或資源型政策裡有 Allow → 允許。否則拒絕。
明確 Deny > 明確 Allow > 預設 Deny

「一票否決制」——只要有人說不行，就是不行
這條規則造成的實務陷阱：使用者掛了 AdministratorAccess（全部允許），卻還是不能操作某個資源。原因通常是：
  • SCP 在組織層級擋掉了
  • Permissions Boundary 限制了
  • 資源型政策（例如 bucket policy）有明確 Deny
  • KMS key policy 沒允許（存取加密資料時常見）
「有 Admin 權限但做不到」的問題，八成要往上面四個地方查。

兩個必學的排錯工具

# ① Policy Simulator：模擬「這個身分能不能做這件事」
$ aws iam simulate-principal-policy \
    --policy-source-arn arn:aws:iam::123456789012:user/alice \
    --action-names s3:GetObject s3:DeleteObject \
    --resource-arns arn:aws:s3:::company-reports/q4.pdf

# 輸出會告訴你 allowed / implicitDeny / explicitDeny，
# 以及「是哪一條政策做的決定」——這比猜快一百倍

# ② Access Analyzer：找出「被外部帳號存取」的資源
$ aws accessanalyzer create-analyzer \
    --analyzer-name account-analyzer --type ACCOUNT
$ aws accessanalyzer list-findings --analyzer-arn <arn>
Access Analyzer 是免費的，開了沒壞處。它會主動找出「這個 bucket 對全世界公開」「這個 role 允許外部帳號扮演」這類問題，而且是用形式化驗證而不是掃描規則，準確度很高。企業帳號應該預設開啟。

7. Role 與 AssumeRole 實作

Role 有兩份政策，兩份缺一不可：

政策回答的問題CLI 參數
Trust Policy
（信任政策）		誰可以扮演這個角色？--assume-role-policy-document
Permissions Policy
（權限政策）		扮演之後能做什麼？attach-role-policy

實作一：EC2 讀 S3（最常見的情境）

# ① Trust Policy：允許 EC2 服務扮演這個角色
$ cat > trust-ec2.json <<'EOF'
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "Service": "ec2.amazonaws.com" },
    "Action": "sts:AssumeRole"
  }]
}
EOF

$ aws iam create-role \
    --role-name EC2-S3-ReadOnly \
    --assume-role-policy-document file://trust-ec2.json

# ② 權限政策：只給這一個 bucket 的讀取權（最小權限）
$ cat > perm-s3.json <<'EOF'
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": ["s3:GetObject", "s3:ListBucket"],
    "Resource": [
      "arn:aws:s3:::company-reports",
      "arn:aws:s3:::company-reports/*"
    ]
  }]
}
EOF

$ aws iam put-role-policy \
    --role-name EC2-S3-ReadOnly \
    --policy-name ReadCompanyReports \
    --policy-document file://perm-s3.json

# ③ EC2 不能直接掛 Role，要透過 Instance Profile 這層包裝
$ aws iam create-instance-profile --instance-profile-name EC2-S3-Profile
$ aws iam add-role-to-instance-profile \
    --instance-profile-name EC2-S3-Profile \
    --role-name EC2-S3-ReadOnly

# ④ 掛到既有的執行個體上（不用重開機）
$ aws ec2 associate-iam-instance-profile \
    --instance-id i-0abc123def456 \
    --iam-instance-profile Name=EC2-S3-Profile
掛好之後，EC2 上的程式什麼都不用改。AWS SDK 和 CLI 會自動去 Instance Metadata Service 拿臨時憑證，而且會自動輪替。程式碼裡一行金鑰都不用寫。 
# 在 EC2 上驗證（IMDSv2，需要先取 token）
$ TOKEN=$(curl -X PUT "http://169.254.169.254/latest/api/token" \
    -H "X-aws-ec2-metadata-token-ttl-seconds: 21600")
$ curl -H "X-aws-ec2-metadata-token: $TOKEN" \
    http://169.254.169.254/latest/meta-data/iam/security-credentials/
一定要強制 IMDSv2。舊版 IMDSv1 只要一個 GET 就能拿到憑證，SSRF 漏洞可以直接偷走你的 Role 憑證（2019 年 Capital One 的重大外洩事件就是這樣發生的）。IMDSv2 要求先 PUT 拿 token，SSRF 打不進去。 
$ aws ec2 modify-instance-metadata-options \
    --instance-id i-0abc123 \
    --http-tokens required \
    --http-put-response-hop-limit 1

實作二：跨帳號 AssumeRole

# ═══ 在「被存取」的帳號 B (999988887777) 建立角色 ═══
$ cat > trust-cross.json <<'EOF'
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "AWS": "arn:aws:iam::123456789012:root" },
    "Action": "sts:AssumeRole",
    "Condition": {
      "StringEquals": { "sts:ExternalId": "unique-shared-secret-2026" },
      "Bool": { "aws:MultiFactorAuthPresent": "true" }
    }
  }]
}
EOF

$ aws iam create-role --role-name CrossAccountAudit \
    --assume-role-policy-document file://trust-cross.json
$ aws iam attach-role-policy --role-name CrossAccountAudit \
    --policy-arn arn:aws:iam::aws:policy/SecurityAudit

# ═══ 在帳號 A 使用它 ═══
$ aws sts assume-role \
    --role-arn arn:aws:iam::999988887777:role/CrossAccountAudit \
    --role-session-name tom-audit-20260805 \
    --external-id unique-shared-secret-2026 \
    --duration-seconds 3600

# 回傳三個值，設成環境變數就能用
$ export AWS_ACCESS_KEY_ID=ASIA...
$ export AWS_SECRET_ACCESS_KEY=...
$ export AWS_SESSION_TOKEN=...          ← 臨時憑證特有，不能漏
Trust Policy 寫 :root 是什麼意思？它不是「root 使用者」，而是「帳號 123456789012 裡任何被授權的身分」。實際能不能扮演，還要看帳號 A 那邊的 IAM policy 有沒有給 sts:AssumeRole。兩邊都要同意，跟跨帳號 S3 是同一個道理。
ExternalId 是給第三方廠商用的，不是裝飾。如果你讓一家監控廠商 AssumeRole 進你的帳號，而 Trust Policy 只寫了他們的帳號 ID，那麼那家廠商的其他客戶也可能猜到你的 Role ARN 並扮演它（這叫 confused deputy 問題）。ExternalId 是你和廠商之間的獨有暗號，能堵住這個漏洞。

用 config 讓 AssumeRole 自動化

# ~/.aws/config —— 設好之後直接 --profile audit，CLI 自動幫你換身分
[profile audit]
role_arn = arn:aws:iam::999988887777:role/CrossAccountAudit
source_profile = default
external_id = unique-shared-secret-2026
mfa_serial = arn:aws:iam::123456789012:mfa/tom
role_session_name = tom-audit
duration_seconds = 3600

# 用起來就像一般 profile，CLI 會自動提示輸入 MFA 碼並快取憑證
$ aws s3 ls --profile audit
Enter MFA code for arn:aws:iam::123456789012:mfa/tom: 123456

8. 企業實務：多帳號與 SSO

企業不會把所有東西放在一個 AWS 帳號裡。原因：
  • 爆炸半徑——開發環境出事不該影響正式環境
  • 帳單分離——每個部門／專案的花費要能單獨看
  • 權限邊界——帳號是 AWS 最強的隔離單位，比 IAM policy 可靠
  • 服務配額——很多配額是「每帳號每 region」，共用一個帳號會撞上限

典型的 Organizations 結構

Root（管理帳號 — 只做帳務與治理，不放任何工作負載）
├── OU: Security
│   ├── Log Archive 帳號      （集中收 CloudTrail / Config 記錄）
│   └── Audit 帳號            （安全團隊的唯讀存取）
├── OU: Infrastructure
│   ├── Network 帳號          （Transit Gateway、共用 VPC）
│   └── Shared Services 帳號  （AD、CI/CD、映像檔）
└── OU: Workloads
    ├── OU: Prod
    │   └── prod-app-a 帳號
    ├── OU: Staging
    │   └── stg-app-a 帳號
    └── OU: Dev（可套用較寬鬆但費用受限的 SCP）
        └── dev-app-a 帳號

SCP：組織層級的權限天花板

# SCP 範例：禁止 Dev OU 開昂貴的機型
{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "DenyExpensiveInstances",
    "Effect": "Deny",
    "Action": "ec2:RunInstances",
    "Resource": "arn:aws:ec2:*:*:instance/*",
    "Condition": {
      "StringNotLike": {
        "ec2:InstanceType": ["t3.*", "t4g.*", "m5.large", "m5.xlarge"]
      }
    }
  }]
}
SCP 的三個重要特性（考試常考）：
  • SCP 不會給予任何權限，它只能限制。還是要有 IAM policy 才能做事
  • SCP 對管理帳號（Management Account）無效——所以管理帳號絕對不要放工作負載
  • SCP 連 root 使用者都限制得住，這是它比 IAM 強的地方

IAM Identity Center（原 AWS SSO）

傳統 IAM UserIAM Identity Center
憑證類型長期 Access Key臨時憑證（登入後才發）
多帳號每個帳號都要建使用者一次登入，切換所有帳號
離職處理要一個一個帳號刪在身分來源停用即可
整合 AD / Okta要自己接 SAML內建支援
費用免費免費
# CLI 用 SSO 登入（不需要任何長期金鑰）
$ aws configure sso
SSO session name: mycompany
SSO start URL: https://mycompany.awsapps.com/start
SSO region: ap-northeast-1

$ aws sso login --profile prod-admin       # 開瀏覽器驗證，憑證有時效
$ aws s3 ls --profile prod-admin
企業導入建議：新專案直接用 IAM Identity Center，不要建 IAM User。它免費、憑證有時效、離職只要停用一個地方。IAM User 只保留給真的無法用 SSO 的機器帳號（而那些多半也能改用 Role 或 OIDC）。

GitHub Actions 用 OIDC 部署（無金鑰）

# ① 註冊 GitHub 為 OIDC 身分提供者（每個帳號做一次）
$ aws iam create-open-id-connect-provider \
    --url https://token.actions.githubusercontent.com \
    --client-id-list sts.amazonaws.com \
    --thumbprint-list 6938fd4d98bab03faadb97b34396831e3780aea1

# ② Trust Policy —— 注意 sub 條件要鎖死 repo 和分支
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {
      "Federated": "arn:aws:iam::123456789012:oidc-provider/token.actions.githubusercontent.com"
    },
    "Action": "sts:AssumeRoleWithWebIdentity",
    "Condition": {
      "StringEquals": {
        "token.actions.githubusercontent.com:aud": "sts.amazonaws.com"
      },
      "StringLike": {
        "token.actions.githubusercontent.com:sub": "repo:myorg/myrepo:ref:refs/heads/main"
      }
    }
  }]
}
sub 條件寫成 repo:myorg/* 或漏掉，等於任何人的 GitHub Actions 都能扮演你的角色。務必鎖到特定 repo + 特定分支或環境。這是 OIDC 設定最常見也最嚴重的錯誤。

9. 稽核：誰做了什麼

服務回答的問題費用
CloudTrail「誰在什麼時候呼叫了哪個 API？」管理事件前一份免費；資料事件要錢
Config「這個資源的設定什麼時候被改成這樣？符合規範嗎？」依記錄的組態項目計費
CloudWatch Logs「應用程式輸出了什麼？」依攝入量與儲存量
GuardDuty「有沒有可疑行為？」（挖礦、異常登入、外洩金鑰）依分析量，30 天免費試用
金鑰外洩最有效的偵測是 GuardDuty。它會抓到「這把金鑰平常從台北用，現在從某個陌生 IP 呼叫 RunInstances 開了 20 台 GPU 機器」這種行為。沒有 GuardDuty，多數人是收到帳單才發現。

用 CloudTrail 查特定操作

# 誰刪掉了那個 bucket？
$ aws cloudtrail lookup-events \
    --lookup-attributes AttributeKey=EventName,AttributeValue=DeleteBucket \
    --start-time 2026-08-01T00:00:00Z \
    --query 'Events[].[EventTime,Username,Resources[0].ResourceName]' \
    --output table

# 某個使用者最近做了什麼
$ aws cloudtrail lookup-events \
    --lookup-attributes AttributeKey=Username,AttributeValue=alice \
    --max-results 30 \
    --query 'Events[].[EventTime,EventName,EventSource]' --output table

# 找出所有失敗的 API 呼叫（可能是攻擊探測）
$ aws cloudtrail lookup-events \
    --query "Events[?contains(CloudTrailEvent, 'AccessDenied')].[EventTime,Username,EventName]" \
    --output table
CloudTrail 預設只保留 90 天的事件歷史，而且不含資料事件。要長期保存必須建立 Trail 並輸出到 S3。合規要求通常是 1–7 年，記得搭配 S3 生命週期規則轉到 Glacier 省錢，並開啟 Object Lock 防止被竄改。 
$ aws cloudtrail create-trail \
    --name org-audit-trail \
    --s3-bucket-name my-cloudtrail-logs \
    --is-multi-region-trail \
    --enable-log-file-validation
$ aws cloudtrail start-logging --name org-audit-trail

完整實作 Lab：從零建立安全基線

需要一個 AWS 帳號（可用免費方案）。約 90 分鐘。

這個 Lab 用到的資源幾乎全部免費：IAM、Budgets（前兩個）、Access Analyzer、CloudTrail 管理事件（第一份）都不收費。唯一可能產生費用的是 CloudTrail 輸出到 S3 的儲存（幾 MB，不到 US$0.01）。做完不需要刪任何東西。

階段一：帳號基線

  1. root 開啟 MFA（用手機 App，不要用簡訊）
  2. 設定密碼政策：14 碼、四種字元、90 天更換、不可重複前 5 次
  3. 建立 Budget：月上限 US$20，三段告警（實際 50%、實際 80%、預測 100%）
  4. 開啟 Cost Anomaly Detection
  5. 建立多區域 CloudTrail，輸出到 S3 並開啟 log file validation
  6. 開啟 Access Analyzer

階段二：身分結構

  1. 建立群組 Admins（AdministratorAccess）與 Developers（PowerUserAccess）
  2. 建立使用者 tom-admin 加入 Admins，開啟 MFA，之後不再用 root 登入
  3. 建立使用者 alice 加入 Developers，設定強制首次改密碼
  4. 寫一個自訂政策 TokyoOnly（用 aws:RequestedRegion），掛到 Developers
  5. 用 aws configure 設定 CLI，確認 aws sts get-caller-identity 顯示的是 tom-admin

階段三：Role 實作

  1. 建立 Role EC2-S3-ReadOnly，Trust Policy 給 ec2.amazonaws.com
  2. 權限政策只允許讀一個特定 bucket（最小權限）
  3. 建立 Instance Profile 並把 Role 放進去
  4. 寫一個 Role ReadOnlyAudit，Trust Policy 要求 MFA 才能扮演
  5. 在 ~/.aws/config 設定 [profile audit] 自動 AssumeRole

階段四：驗證權限判斷

  1. 用 Policy Simulator 測試 alice 能不能 s3:DeleteObject
  2. 幫 Developers 加一條明確 Deny 刪除 S3 的政策，再模擬一次，觀察結果變化
  3. 用 --profile audit 執行指令，確認會提示輸入 MFA 碼
  4. 產生憑證報告，確認所有使用者都有 MFA

驗收清單

  • aws iam get-account-summary 的 AccountMFAEnabled = 1
  • aws budgets describe-budgets 看得到預算與三個通知
  • 用 alice 的身分在 us-east-1 開 EC2 → 被拒絕；在 ap-northeast-1 → 可以
  • Policy Simulator 對 s3:DeleteObject 回傳 explicitDeny，且指出是哪條政策
  • aws sts assume-role 不帶 MFA → AccessDenied；帶 MFA → 成功
  • 憑證報告裡 沒有任何 root 的 Access Key
  • Access Analyzer 的 findings 是空的（沒有意外對外公開的資源）

加碼挑戰

  1. 寫一個 Permissions Boundary，讓 Developers 就算掛了 AdministratorAccess 也不能改 IAM。
  2. 實作 ABAC：幫使用者和 EC2 都打上 Team 標籤，寫一條政策讓人只能操作同隊的機器。
  3. 寫一個 Bash 腳本，找出所有 90 天沒使用過的 Access Key 並列出來（先不要真的刪）。
  4. 設定 GitHub Actions OIDC，做出一個不需要任何 Secret 就能部署到 S3 的 workflow。
  5. 用 CloudTrail 查出「你自己今天做了哪些變更類的 API 呼叫」，並用 --query 過濾掉所有 Describe* 和 List*。

本章重點回顧

  • 第一天六件事：root MFA → 刪 root 金鑰 → 建 IAM 管理者 → 設 Budget → 開 CloudTrail → 密碼政策
  • Budget 的 FORECASTED 告警能提早二十幾天發現超支；但它只通知不會關資源
  • 做任何危險操作前先 aws sts get-caller-identity
  • 程式一律用 Role，不要用 Access Key——EC2 用 Instance Profile、Lambda 用 Execution Role、CI/CD 用 OIDC
  • 權限判斷：明確 Deny > 明確 Allow > 預設 Deny，一票否決
  • 「有 Admin 卻做不到」→ 往 SCP、Permissions Boundary、資源型政策、KMS key policy 查
  • 跨帳號存取兩邊都要設；第三方廠商務必用 ExternalId
  • 強制 IMDSv2，防 SSRF 偷走 Role 憑證
  • SCP 只能限制不能授權，且對管理帳號無效——管理帳號不放工作負載
  • 新專案用 IAM Identity Center，不要建 IAM User
  • 排錯用 Policy Simulator，防外洩用 Access Analyzer + GuardDuty
安全與 IAM 在 SAA-C03 屬於「Design Secure Architectures」領域，佔 30%，是四大領域裡最重的。去 模擬試題 練一輪確認觀念。
