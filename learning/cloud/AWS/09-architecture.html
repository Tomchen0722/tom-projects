1. Well-Architected 六大支柱

卓越營運用程式碼管理基礎設施、小步頻繁變更、從失敗中學習
安全性最小權限、縱深防禦、全程加密、可追溯
可靠性自動從故障復原、水平擴展、停止猜測容量
效能效率用託管服務、實驗更多、考慮機制的親和性
成本優化採用消費模式、衡量整體效率、分析歸因支出
永續性降低碳足跡、提高使用率、採用高效硬體
六大支柱在考試裡的用法：題目會暗示「優先考量什麼」。
題目說優先支柱傾向的答案
「最具成本效益」「最低成本」成本Spot、S3 生命週期、Serverless、關掉閒置資源
「最少營運負擔」「最少管理」營運託管服務（Aurora > RDS > EC2 自架）
「高可用」「容錯」可靠性Multi-AZ、ASG、跨區複製
「最低延遲」效能CloudFront、ElastiCache、Global Accelerator
「符合法規」「稽核」安全KMS、CloudTrail、Config、Object Lock
SAA 的情境題幾乎都能用這張表縮小到 1–2 個選項。
「最少營運負擔」是最常見也最容易答錯的關鍵字。看到它就要往「越託管越好」的方向選：
Lambda > Fargate > ECS on EC2 > EC2 自架
DynamoDB > Aurora Serverless > Aurora > RDS > EC2 上的 MySQL
S3 > EFS > EBS
就算託管服務貴一點，只要題目說「最少營運負擔」它就是答案。

2. 範式一：三層式 Web 應用

　　　　　　　　　　　　[ Route 53 ]
　　　　　　　　　　　　　　　│ Alias
　　　　　　　　　　　　[ CloudFront ] ── [ WAF ]
　　　　　　　　　　　　　　　│
　　　　　　　　　┌───────────┴───────────┐
　　　　　　　[ S3 靜態資源 ]　　　　[ ALB ]（公有子網路 × 2 AZ）
　　　　　　　　（OAC 私有）　　　　　　　│
　　　　　　　　　　　　　　　┌──────────┴──────────┐
　　　　　　　　　　　　[ EC2/ECS ]　　　　　　[ EC2/ECS ]
　　　　　　　　　　　　　1a 私有子網路　　　　 1c 私有子網路
　　　　　　　　　　　　　　　└────── ASG ──────┘
　　　　　　　　　　　　　　　　　　　　│
　　　　　　　　　　　　┌───────────────┼───────────────┐
　　　　　　　　[ ElastiCache ]　　[ RDS Multi-AZ ]　　[ S3 使用者上傳 ]
　　　　　　　　　（快取／Session）　（隔離子網路）　　（VPC Endpoint）
層元件關鍵設計
邊緣CloudFront + WAF快取靜態內容、擋 SQL injection 與 DDoS
入口ALB（公有子網路）跨 2 AZ、HTTPS、健康檢查
應用ASG（私有子網路）無狀態、health-check-type=ELB、跨 AZ
快取ElastiCache Redis放 Session（讓應用無狀態）、快取熱資料
資料RDS Multi-AZ（隔離子網路）加密、不公開、自動備份、Read Replica
檔案S3 + VPC Endpoint不走 NAT，省流量費
這個架構的五個關鍵決策，每一個都是考點：
  1. 應用層放私有子網路——只有 ALB 能連到它們
  2. 資料庫放隔離子網路——連對外路由都沒有
  3. Session 放 Redis——應用無狀態才能自由擴縮（第 06 章）
  4. S3 走 VPC Endpoint——省 NAT 流量費（第 02 章）
  5. 安全群組互相引用——ALB→App→DB 層層限制，擴縮不用改規則
這個架構的成本要有心理準備。最小規模（2 台 t3.small + ALB + RDS Multi-AZ db.t3.small + Redis + NAT×2）東京區每月約 US$250–350。

個人專案或小型內部系統不需要這麼完整：可以省掉 Redis（用 JWT）、RDS 用單 AZ、NAT 用一個或改用 VPC Endpoint、應用層直接放公有子網路配好 SG。這樣可以壓到 每月 US$50 以下。

架構要配合實際規模，不是越完整越好。

3. 範式二：無伺服器 API

[ 使用者 ] ──► [ CloudFront ] ──► [ API Gateway (HTTP API) ]
　　　　　　　　　　　　　　　　　　　　　│
　　　　　　　　　　　　　　　　　　[ Cognito 授權 ]
　　　　　　　　　　　　　　　　　　　　　│
　　　　　　　　　　　　　　　　　　　[ Lambda ]
　　　　　　　　　　　　　　　┌──────────┼──────────┐
　　　　　　　　　　　　[ DynamoDB ]  [ S3 ]  [ SQS ] ──► [ Lambda 背景處理 ]
　　　　　　　　　　　　　　　│　　　　　　　　　　　　　　　　　│
　　　　　　　　　　　　[ DynamoDB Streams ]　　　　　　　　 [ DLQ ]
　　　　　　　　　　　　　　　└──► [ Lambda 同步到分析 ]
什麼時候選這個架構：
  • 流量不固定、會歸零（內部工具、季節性業務）
  • 團隊小，沒有人力管伺服器
  • 需要快速從零到上線
  • 成本要跟使用量嚴格掛鉤
這個架構的三個必做設計（第 07 章詳述）：
  1. 所有寫入操作要冪等——訊息一定會重複
  2. 每個佇列都要有 DLQ——否則毒藥訊息會無限重試燒錢
  3. 設 Reserved Concurrency——保護下游、當保險絲
如果後面接的是 RDS 而不是 DynamoDB，一定要加 RDS Proxy。Lambda 瞬間 1000 個併發會把 RDS 連線打爆。這是「Lambda + 關聯式資料庫」的標準配置。

4. 範式三：非同步批次處理

[ 使用者上傳大檔 ] ──► [ S3 input/ ]
　　　　　　　　　　　　　　　│ Event Notification
　　　　　　　　　　　　　[ SQS ]  ◄── 削峰填谷，避免瞬間爆量
　　　　　　　　　　　　　　　│
　　　　　　　　　　　[ ASG (Spot) ] 或 [ AWS Batch ]
　　　　　　　　　　　　　　　│ 依佇列長度自動擴縮
　　　　　　　　　　　　[ S3 output/ ]  ◄── 不同 prefix，避免遞迴
　　　　　　　　　　　　　　　│
　　　　　　　　　　　　　[ SNS 通知 ]
這個架構的精髓：用「佇列長度」而不是 CPU 來擴縮。
目標值 = 每台機器應該處理的積壓訊息數

佇列有 1000 則、每台處理 100 則 → 需要 10 台
# 自訂指標：每台機器的積壓量
$ aws autoscaling put-scaling-policy \
    --auto-scaling-group-name worker-asg \
    --policy-name backlog-per-instance \
    --policy-type TargetTrackingScaling \
    --target-tracking-configuration '{
      "CustomizedMetricSpecification": {
        "MetricName": "BacklogPerInstance",
        "Namespace": "MyApp/Workers",
        "Statistic": "Average"
      },
      "TargetValue": 100
    }'
批次處理最適合用 Spot（省 70–90%），但必須做三件事：
  1. 訊息處理要冪等——機器被收回時訊息會回到佇列被別人處理
  2. Visibility Timeout 要夠長——比最長處理時間長，否則會重複處理
  3. 接收中斷通知後優雅退場——2 分鐘內存好進度（第 03 章有腳本）
運算選項適合
Lambda單次 < 15 分鐘、記憶體 < 10 GB
Fargate需要容器、時間不限、不想管機器
ASG + Spot成本最低、需要 GPU 或特殊機型
AWS Batch大規模科學運算，自動管理佇列與相依性

5. 範式四：資料湖與分析

各種來源 ──► [ Kinesis Data Streams ] ──► [ Firehose ] ──► [ S3 資料湖 ]
（App/IoT/日誌）　　　　　　　　　　　　　　（緩衝＋轉 Parquet）　　│
　　　　　　　　　　　　　　　　　　　　　　　　　　　　　　┌───────┴───────┐
　　　　　　　　　　　　　　　　　　　　　　　　　　　[ Glue Catalog ]  [ 生命週期 ]
　　　　　　　　　　　　　　　　　　　　　　　　　　　　　　│　　　　　（轉 Glacier）
　　　　　　　　　　　　　　　　　　　┌──────────────────────┼──────────────┐
　　　　　　　　　　　　　　　　[ Athena ]　　　　　[ Redshift ]　　[ QuickSight ]
　　　　　　　　　　　　　　　　（偶爾查詢）　　　　（常態 BI）　　　（視覺化）
AthenaRedshift
資料在哪S3（原地查詢）載入 Redshift 叢集
計費按掃描量（US$5/TB）按叢集執行時間
適合偶爾查、探索性分析每天大量查詢、固定報表
效能秒到分鐘更快（資料已最佳化）
Athena 省錢的三個關鍵（考試會考）：
  1. 用欄式格式（Parquet / ORC）——只讀需要的欄位，可以省 90% 掃描量
  2. 分區（依日期 s3://.../year=2026/month=08/day=05/）——查一天的資料就只掃一天
  3. 壓縮（Snappy / GZIP）——直接減少掃描的位元組數
1 TB CSV 全表掃描 = US$5
同樣資料轉成分區的 Parquet，只查一天的三個欄位 = 約 US$0.01
Kinesis 三兄弟很容易混淆：
用途保留消費者
Data Streams即時串流，需要自己寫消費者1–365 天多個，可重播
Data Firehose直接送到目的地（S3、Redshift、OpenSearch）不保留固定目的地
Managed Flink用 SQL 做即時分析——
只是要把資料送進 S3 → Firehose（最簡單、無伺服器）。
需要多個消費者或重播 → Data Streams。

6. 範式五：靜態網站與 SPA

[ Route 53 ] ──► [ CloudFront ] ──► [ S3（私有，OAC）]
　　　　　　　　　　　　│
　　　　　　　　　　[ ACM 憑證 ]（必須在 us-east-1）
　　　　　　　　　　　　│
　　　　　　　　[ /api/* 行為 ] ──► [ API Gateway ] ──► [ Lambda ]
這是成本最低的架構，小網站每月可能不到 US$1。
  • S3 儲存幾百 MB ≈ US$0.01
  • CloudFront 每月前 1 TB 傳輸免費（永久免費方案）
  • ACM 憑證免費
  • Route 53 每個 hosted zone US$0.50/月
SPA 的三個必設項目：
  1. 錯誤頁面導向 index.html——前端路由（/about）在 S3 上不存在會回 403/404，要設成回傳 /index.html 且狀態碼 200
  2. index.html 不要快取（Cache-Control: no-cache），但 JS/CSS 檔名帶雜湊快取一年
  3. ACM 憑證必須在 us-east-1——CloudFront 只認那個 region 的憑證
# SPA 的錯誤頁面設定
"CustomErrorResponses": {
  "Quantity": 2,
  "Items": [
    {"ErrorCode":403,"ResponsePagePath":"/index.html",
     "ResponseCode":"200","ErrorCachingMinTTL":0},
    {"ErrorCode":404,"ResponsePagePath":"/index.html",
     "ResponseCode":"200","ErrorCachingMinTTL":0}
  ]
}

7. 範式六：混合雲

連線方式頻寬延遲費用適合
Site-to-Site VPN最高 1.25 Gbps/tunnel不穩定（走網際網路）低（US$0.05/小時 + 流量）一般連線、DX 的備援
Direct Connect50 Mbps – 100 Gbps穩定且低高（要簽約，數月建置）大量資料、穩定需求
DX + VPN 備援——高正式環境標準做法
Transit Gateway——每連接每小時多 VPC + 多站點
Direct Connect 本身沒有加密。它是專線，資料不走網際網路，但線路上是明文。合規要求加密的話要在 DX 上再跑 VPN（叫 DX + VPN），或用 MACsec。這是 SAA 的考點。

資料遷移工具怎麼選

資料量工具時間
< 10 TBDataSync（走網路）幾小時到幾天
10–80 TBSnowball Edge約 1 週（含運送）
> 100 TBSnowmobile（貨櫃車）數週
持續同步Storage Gateway持續
資料庫遷移DMS（+ SCT 轉換異質資料庫）可線上遷移
網路傳輸時間估算

100 TB ÷ 1 Gbps 專線 ≈ 9.3 天（還是理想值）
100 TB 用 Snowball ≈ 1 週（含來回運送）

考題問「最快的方式」時，算一下就知道該選實體運送還是網路傳輸
Storage Gateway 三種模式：
  • File Gateway——本地看到 NFS/SMB，實際存在 S3
  • Volume Gateway——本地看到 iSCSI 磁碟，備份到 S3
  • Tape Gateway——模擬磁帶櫃，讓既有的備份軟體不用改就能備份到 Glacier
考題看到「想淘汰實體磁帶但不想換備份軟體」→ Tape Gateway。

8. 災難復原四策略

RTO（Recovery Time Objective）= 可以停多久
RPO（Recovery Point Objective）= 可以掉多少資料

這兩個數字決定了架構和預算，而且是商業決策不是技術決策
策略RTORPO備援區平常狀態相對成本
Backup & Restore數小時–數天數小時什麼都沒有，只有備份$
Pilot Light數十分鐘分鐘資料庫在跑，運算層關著$$
Warm Standby數分鐘秒縮小版全套在跑$$$
Multi-Site Active/Active近乎零近乎零全量在跑並承載流量$$$$
選 DR 策略是「花多少錢買多少保障」的取捨，這牽涉實際預算，應該由業務單位決定而不是工程師自己決定。

問對方三個問題：
  • 「系統停 1 小時，公司損失多少？停 1 天呢？」
  • 「掉 5 分鐘的資料可以接受嗎？1 小時呢？」
  • 「願意每月多花 X 元把 RTO 從 4 小時降到 10 分鐘嗎？」
如果 Multi-Site 每月多花 US$5000，但停機一小時只損失 US$500，那就不該做 Multi-Site。

各策略的實作對照

元件Backup&RestorePilot LightWarm StandbyMulti-Site
資料庫跨區複製快照跨區 Read Replica跨區 Read ReplicaAurora Global DB
運算無（事後建）AMI 準備好，不開機ASG min=1 在跑ASG 全量在跑
S3跨區複製跨區複製跨區複製雙向複製
DNS事後手動改Failover 政策Failover 政策Latency / 加權
基礎設施IaC 範本IaC 已部署網路層已部署已部署
大多數企業的合理選擇是 Pilot Light。資料庫用跨區 Read Replica（持續同步，RPO 短），運算層只準備 AMI 和 IaC 範本但不開機（成本低）。

災難發生時：提升 Read Replica → 用 IaC 開起運算層 → 切 DNS，通常 20–40 分鐘可以恢復。成本大約是 Warm Standby 的 1/3。

9. 實作：Pilot Light DR

跨區 DR 一定會增加費用：跨區資料傳輸（US$0.09/GB）+ 備援區的資料庫 + 備援區的儲存。
Pilot Light 大約是主區成本的 25–35%。這是要編列預算的項目，導入前先算清楚並取得核准。

建置步驟

# ═══ ① 備援區先用 IaC 建好網路層（不花錢的部分）═══
#     VPC、子網路、路由表、安全群組、IGW —— 這些都免費
#     用第 10 章的 CloudFormation / Terraform 建

# ═══ ② 資料庫：跨區 Read Replica ═══
$ aws rds create-db-instance-read-replica \
    --db-instance-identifier prod-mysql-dr \
    --source-db-instance-identifier arn:aws:rds:ap-northeast-1:123456789012:db:prod-mysql \
    --region ap-northeast-3 \
    --db-instance-class db.t3.medium \
    --db-subnet-group-name dr-db-subnets

# ═══ ③ S3：跨區複製 ═══
#     只複製關鍵 prefix，不要整個 bucket（省錢）

# ═══ ④ AMI 跨區複製（定期執行）═══
$ aws ec2 copy-image \
    --source-region ap-northeast-1 --source-image-id ami-0abc123 \
    --region ap-northeast-3 --name "web-golden-dr-$(date +%Y%m%d)"

# ═══ ⑤ Route 53 Failover ═══
$ aws route53 create-health-check --caller-reference "primary-$(date +%s)" \
    --health-check-config '{
      "Type":"HTTPS","FullyQualifiedDomainName":"app.example.com",
      "ResourcePath":"/health","RequestInterval":30,"FailureThreshold":3
    }'
#     主要記錄綁健康檢查、備援記錄設 SECONDARY（第 06 章）

切換手冊（Runbook）

#!/bin/bash
# ══ DR 切換腳本 —— 必須事先演練過 ══
set -euo pipefail
DR_REGION=ap-northeast-3

echo "⚠ 這會把服務切換到 $DR_REGION，確定嗎？"
read -p "輸入 CONFIRM 繼續：" ans
[ "$ans" = "CONFIRM" ] || exit 1

echo "① 提升 Read Replica 為獨立資料庫…"
aws rds promote-read-replica --db-instance-identifier prod-mysql-dr --region $DR_REGION
aws rds wait db-instance-available --db-instance-identifier prod-mysql-dr --region $DR_REGION

echo "② 用 IaC 部署運算層…"
aws cloudformation deploy --region $DR_REGION \
  --template-file compute-tier.yaml --stack-name dr-compute \
  --parameter-overrides DbEndpoint=$(aws rds describe-db-instances \
      --db-instance-identifier prod-mysql-dr --region $DR_REGION \
      --query 'DBInstances[0].Endpoint.Address' --output text) \
  --capabilities CAPABILITY_IAM

echo "③ 等待 ALB 目標健康…"
# 這裡應該輪詢 describe-target-health 直到有健康目標

echo "④ 切換 Route 53…"
# 健康檢查會自動切，但也可以手動強制

echo "✅ 切換完成，請驗證：https://app.example.com/health"
沒有演練過的 DR 計畫等於沒有 DR 計畫。真實災難時你會發現：
  • 備援區的 AMI 是三個月前的，缺了新的相依套件
  • Secrets Manager 的密碼沒有跨區複製，應用連不上資料庫
  • ACM 憑證只在主區申請，備援區的 ALB 沒有憑證
  • 服務配額不夠——備援區從沒開過那麼多機器，撞到預設上限
  • 寫 Runbook 的人已經離職，沒人知道步驟
至少每半年做一次完整演練，而且要換人執行（驗證文件寫得夠清楚）。
DR 演練檢查清單：
  • 備援區的服務配額夠嗎？（EC2 vCPU、EIP、VPC 數量）
  • Secrets / Parameter Store 有跨區複製嗎？
  • ACM 憑證在備援區申請了嗎？
  • AMI 和容器映像是最新的嗎？
  • IAM Role 是全球的（沒問題），但資源型政策裡的 ARN 有寫死 region 嗎？
  • Runbook 上次更新是什麼時候？

10. 故障演練

AWS Fault Injection Service（FIS）可以受控地製造故障，驗證你的架構真的禁得起。

$ aws fis create-experiment-template --cli-input-json '{
  "description": "驗證單一 AZ 失效時服務仍可用",
  "targets": {
    "instances-in-1a": {
      "resourceType": "aws:ec2:instance",
      "resourceTags": { "Env": "staging" },
      "filters": [
        {"path":"Placement.AvailabilityZone","values":["ap-northeast-1a"]},
        {"path":"State.Name","values":["running"]}
      ],
      "selectionMode": "ALL"
    }
  },
  "actions": {
    "stop-instances": {
      "actionId": "aws:ec2:stop-instances",
      "parameters": { "startInstancesAfterDuration": "PT10M" },
      "targets": { "Instances": "instances-in-1a" }
    }
  },
  "stopConditions": [{
    "source": "aws:cloudwatch:alarm",
    "value": "arn:aws:cloudwatch:...:alarm/P1-錯誤率過高"
  }],
  "roleArn": "arn:aws:iam::123456789012:role/fis-role"
}'
stopConditions 是 FIS 最重要的設定。它綁定一個 CloudWatch 告警——實驗造成的影響超過閾值時自動中止並復原。

沒設 stopCondition 就跑實驗，等於自己製造一場真實事故。而且第一次一定要在 staging 跑，確認 stopCondition 真的會觸發，才考慮在正式環境做。

11. 情境題解題法

1
先找「優先支柱」關鍵字「最低成本」「最少營運負擔」「最高可用」「最低延遲」——這一步通常能刪掉兩個選項。
2
找數字限制RTO/RPO、資料量、延遲要求、預算。數字會直接指向特定方案（100 TB → Snowball；RPO 秒級 → 同步複製）。
3
刪掉「明顯錯誤」的選項把資料庫放公有子網路、用 root 帳號、把 Access Key 寫進程式碼、S3 設成公開——這些永遠是錯的。
4
刪掉「能做但不是最佳」的選項用 EC2 自架 MySQL 也能運作，但題目問「最少營運負擔」時它就不是答案。
5
剩下兩個時，比「託管程度」和「AWS 原生程度」AWS 考試偏好託管服務與原生方案。
永遠是錯的選項（看到就刪）：
  • 資料庫放公有子網路或設 PubliclyAccessible=true
  • 把 Access Key 寫進程式碼或 User Data（正解永遠是 Role）
  • 用 root 帳號做日常操作
  • 把 S3 bucket 設成公開來提供內容（正解是 CloudFront + OAC 或 presigned URL）
  • 安全群組開 0.0.0.0/0 的 22 或 3389
  • 用 Read Replica 當高可用方案（那是 Multi-AZ 的工作）
常見的「最佳答案」模式：
需求標準答案
EC2 存取 S3IAM Role（Instance Profile）
應用程式要密碼Secrets Manager（要輪替）或 Parameter Store（不用輪替）
解耦兩個服務SQS
一個事件通知多個系統SNS（+ 各自的 SQS）
全球使用者低延遲存取靜態內容CloudFront
全球使用者低延遲存取動態內容Global Accelerator
資料庫讀取壓力大Read Replica 或 ElastiCache
不知道存取模式的 S3 資料Intelligent-Tiering
跨帳號存取AssumeRole（+ ExternalId 給第三方）
私有子網路存取 AWS 服務VPC Endpoint
連進私有子網路的機器SSM Session Manager（不是堡壘主機）
兩個容易混淆的配對，考試很愛出：
  • CloudFront vs Global Accelerator——前者快取靜態內容（HTTP/HTTPS），後者加速動態流量（任何 TCP/UDP）並提供固定 IP
  • Secrets Manager vs Parameter Store——前者會自動輪替密碼（每月 US$0.40/個），後者免費但不會輪替。題目提到「自動輪替」就是 Secrets Manager

完整實作 Lab：三層式架構 + Pilot Light DR

這是總整合 Lab，會用到第 02–08 章的所有元件。約 150 分鐘。

這個 Lab 會產生實際費用，主要來自 ALB（US$0.025/小時）、NAT Gateway（US$0.062/小時）、RDS。
全套跑 3 小時大約 US$0.5–1。跨區 DR 部分會再加上跨區傳輸費。

強烈建議：先確認第 01 章的 Budget 告警已設定，並在單一個下午完成後立刻清理。不要讓它過夜。

階段一：主區三層式架構

  1. 用第 02 章的 VPC（三層子網路、NAT、VPC Endpoint）
  2. 建立 ALB + 目標群組 + ASG（第 06 章），health-check-type=ELB
  3. 建立 RDS db.t3.micro 單 AZ（省錢，正式環境要 Multi-AZ）
  4. 應用程式從 Secrets Manager 取得資料庫密碼
  5. 建立 S3 bucket 存使用者上傳，走 Gateway Endpoint
  6. 安全群組層層引用：ALB → App → DB

階段二：可觀測性

  1. 建立 CloudWatch Dashboard，放 ALB、ASG、RDS 的關鍵指標
  2. 設定 P1 告警：5XX 錯誤率、無健康主機
  3. 所有 log group 設保留 14 天
  4. 啟用 Cost Anomaly Detection

階段三：故障演練

  1. 手動 terminate 一台機器 → 驗證服務不中斷且 ASG 自動補
  2. 停掉某台的應用程式（機器還活著）→ 驗證 ASG 會替換它
  3. 把 ALB 的目標群組健康檢查路徑改成不存在的路徑 → 觀察全部變 unhealthy，體會「健康檢查雪崩」，然後改回來
  4. 用 reboot-db-instance --force-failover 測試（如果你有開 Multi-AZ）

階段四：Pilot Light DR

  1. 在 ap-northeast-3（大阪） 建立 VPC 網路層（免費的部分）
  2. 建立跨區 Read Replica
  3. 設定 S3 跨區複製（只複製一個 prefix）
  4. 把 AMI 複製到大阪
  5. 寫一份 DR Runbook（步驟、指令、驗證方式）
  6. 實際執行一次切換：提升 Read Replica、開運算層、驗證可用
  7. 記錄實際花了多久（這就是你真實的 RTO）

驗收清單

  • 從網際網路可以連到 ALB，看得到應用程式
  • 應用程式能連資料庫，且密碼從沒出現在程式碼或 User Data 裡
  • 資料庫 PubliclyAccessible=false，且從公網連不到
  • terminate 一台機器時，持續重新整理網頁不會看到錯誤
  • 停掉應用程式的那台被 ASG 替換（不只被隔離）
  • DR 切換後，大阪的 endpoint 能正常提供服務且資料完整
  • 你能說出實際的 RTO 是幾分鐘，以及 RPO 大約多少

本章重點回顧

  • 六大支柱在考試裡是關鍵字對照表——先找「優先考量什麼」
  • 「最少營運負擔」= 越託管越好：Lambda > Fargate > EC2；DynamoDB > Aurora > RDS > 自架
  • 三層式：應用在私有、資料庫在隔離、Session 在 Redis、S3 走 Endpoint、SG 互相引用
  • 架構要配合實際規模——小專案不需要完整的高可用架構
  • 批次處理用佇列長度而不是 CPU 擴縮；配 Spot 但必須冪等
  • Athena 省錢三招：Parquet + 分區 + 壓縮，可省 90% 以上
  • 只是送資料進 S3 用 Firehose；要多消費者或重播用 Data Streams
  • SPA 要設錯誤頁面導向 index.html；CloudFront 憑證必須在 us-east-1
  • Direct Connect 本身不加密，合規要 DX + VPN
  • 資料遷移：<10TB 用 DataSync、10–80TB 用 Snowball；先算傳輸時間再決定
  • DR 四策略成本與 RTO 成反比；多數企業合理選擇是 Pilot Light
  • 沒演練過的 DR 計畫等於沒有——至少每半年一次，換人執行
  • FIS 一定要設 stopConditions，否則就是自己製造事故
  • 永遠錯的選項：資料庫公開、金鑰寫死、用 root、S3 設公開、Read Replica 當高可用
  • CloudFront 快取靜態、Global Accelerator 加速動態；Secrets Manager 會輪替、Parameter Store 免費
