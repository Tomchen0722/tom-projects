機器開起來之後才是真正的工作：怎麼登入、怎麼修補、怎麼確認組態沒跑掉、怎麼讓公司的網域帳號在雲上也能用。這一課把 SSM 全家與 Directory Service 三種一次講完。

1. SSM 不是一個服務，是一組維運工具

SSM 像一整套工具箱，不是單一把螺絲起子。考試不會問「SSM 是什麼」，只會問「這個維運需求用工具箱裡的哪一把」。所以重點是把每把工具的用途邊界記清楚。
工具回答什麼問題考題關鍵字
Session Manager我怎麼登入這台機器？不開 22 埠、不要堡壘主機、要稽核紀錄
Run Command我怎麼對 500 台一次下指令？一次性、大量、免 SSH
Automation我怎麼把多步驟流程自動化？Runbook、自動修復、建立 AMI
State Manager我怎麼確保組態一直是對的？期望狀態、防止漂移、定期套用
Patch Manager我怎麼修補作業系統？修補、合規報表、維護時段
Parameter Store組態與密文放哪？免費、階層式、SecureString
Inventory我的機器上裝了什麼？軟體清單、資產盤點
Fleet Manager我怎麼用 GUI 管機器？看檔案系統、登錄檔、程序
SSM 在 SAA 裡的地位：它是「減少維運負擔」與「不開連接埠」這兩類題目的萬用答案。只要選項裡出現「在 EC2 上自己裝 agent／寫 cron／架堡壘主機」，而另一個選項是 SSM 的某個功能，答案幾乎都是 SSM。

2. 三個前置條件（連不上都是這裡出問題）

「機器沒出現在 Systems Manager 清單裡」是實務與考試都超高頻的題目。原因永遠是下面三個之一，而且要照順序檢查。
1
SSM Agent 有沒有裝、有沒有在跑Amazon Linux 2／2023、Ubuntu 較新版與 Windows 官方 AMI 都預設內建。自訂 AMI 或舊映像檔要自己裝。
2
EC2 有沒有掛 IAM 執行個體設定檔需要 AmazonSSMManagedInstanceCore 這個 AWS 受管政策。沒有 Role 就一定看不到機器——這是最常見的原因。
3
網路通不通Agent 要能對外連到 SSM 服務端點。走 NAT／IGW，或在私有子網路建 Interface Endpoint。

私有子網路需要哪些 Endpoint

Endpoint做什麼不建會怎樣
com.amazonaws.region.ssmSSM 核心 API機器完全不上線
com.amazonaws.region.ssmmessagesSession Manager 的連線通道看得到機器但連不進去
com.amazonaws.region.ec2messagesRun Command 等訊息通道指令送不到
S3 Gateway EndpointPatch Manager 取得修補程式、工作階段日誌寫入修補失敗、日誌寫不出去
這張表就是考題本身。「私有子網路的 EC2 出現在 SSM 清單，但 Session Manager 連不上」→ 少了 ssmmessages Endpoint。這個「看得到但連不上」的症狀對應到哪個 Endpoint，是很典型的細節題。
# 一次建好三個 Interface Endpoint（私有子網路的標準做法）
$ for svc in ssm ssmmessages ec2messages; do
    aws ec2 create-vpc-endpoint \
      --vpc-id vpc-0abc123 \
      --vpc-endpoint-type Interface \
      --service-name com.amazonaws.ap-northeast-1.$svc \
      --subnet-ids subnet-a subnet-c \
      --security-group-ids sg-ssm-endpoint \
      --private-dns-enabled
  done

# Endpoint 的 SG 要放行來自 EC2 的 HTTPS(443)
# 沒開 443 的話症狀跟「沒建 Endpoint」一模一樣，很難查

# 確認機器有沒有上線
$ aws ssm describe-instance-information \
    --query 'InstanceInformationList[].[InstanceId,PingStatus,PlatformName,AgentVersion]' \
    --output table
成本提醒：三個 Interface Endpoint × 每個 AZ 一個 ENI，在多 AZ 環境是一筆固定月費。如果 VPC 本來就有 NAT Gateway 而且流量不大，走 NAT 反而更便宜——Endpoint 是為了「不出網際網路」的合規需求，不是為了省錢。這個取捨在成本題與安全題會有不同的正確答案，要看題目強調哪一邊。

3. Session Manager：淘汰堡壘主機

傳統做法（考題裡的錯誤選項） Session Manager（正解） 工程師 ──SSH──▶ 堡壘主機 工程師 ──▶ AWS API │ 公有 IP │ IAM 驗證 │ 開 22 埠 ▼ ▼ SSM Agent 主動外連 私有 EC2 │ ▼ ✗ 要維護一台機器 私有 EC2 ✗ 要管 SSH 金鑰 ✗ 要開放入站連接埠 ✓ 零入站規則 ✓ 無金鑰 ✓ 全程稽核 ✗ 誰登入做了什麼很難查

它為什麼安全

零入站連接埠Agent 是主動向外建立連線的，Security Group 可以完全不開任何入站規則。
不需要 SSH 金鑰權限用 IAM 政策控制，員工離職停用 IAM 即可，不用去每台機器刪公鑰。
完整稽核誰在什麼時間連了哪台機器記在 CloudTrail；指令與輸出可送 S3 或 CloudWatch Logs。
連接埠轉發可以把遠端連接埠轉到本機，例如安全地連私有子網路的 RDS，不用開 VPN。

用 IAM 精準控制「誰能連哪一台」

只允許連 Env=dev 的機器
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": "ssm:StartSession",
    "Resource": "arn:aws:ec2:*:*:instance/*",
    "Condition": {
      "StringEquals": {
        // 用標籤限制範圍，比列 instance-id 好維護
        "ssm:resourceTag/Env": "dev"
      }
    }
  }]
}
# 開一個工作階段（本機要先裝 session-manager-plugin）
$ aws ssm start-session --target i-0abc123def456

# 連接埠轉發：把私有 RDS 的 3306 轉到本機 13306
$ aws ssm start-session --target i-0abc123def456 \
    --document-name AWS-StartPortForwardingSessionToRemoteHost \
    --parameters '{"host":["mydb.abc123.ap-northeast-1.rds.amazonaws.com"],
                   "portNumber":["3306"],"localPortNumber":["13306"]}'

# 之後本機就能這樣連，完全不用開任何入站規則
$ mysql -h 127.0.0.1 -P 13306 -u admin -p
連接埠轉發是實務上最被低估的功能。「開發人員需要從筆電連到私有子網路的資料庫做查詢」——標準答案是 Session Manager 連接埠轉發，不是「開 VPN」也不是「把 RDS 設成公開存取」。
陷阱：以為 Session Manager 要開 SSH 埠
完全不用。Security Group 可以零入站規則。選項裡出現「開放 22 埠給公司 IP」的都是錯的——那正是題目想淘汰的做法。

4. Run Command / Automation / State Manager

這三個常被搞混，差別在執行次數與對象。

Run Command執行一次命令在一批機器上。例如「所有 web 機重啟 nginx」。
Automation執行一次多步驟流程，對象可以是任何 AWS 資源。例如「建 AMI → 修補 → 測試 → 註冊」。
State Manager持續維持某個狀態。例如「確保 CloudWatch Agent 永遠是裝著且在跑的」。
一句話區分

Run Command = 現在幫我做一件事。
Automation = 現在幫我做一連串事（可跨服務）。
State Manager = 以後也要一直是這樣（防組態漂移）。

# Run Command：對所有帶 Role=web 標籤的機器重啟服務
$ aws ssm send-command \
    --document-name "AWS-RunShellScript" \
    --targets "Key=tag:Role,Values=web" \
    --parameters 'commands=["systemctl restart nginx","systemctl is-active nginx"]' \
    --max-concurrency "20%" --max-errors "5" \
    --output-s3-bucket-name my-ssm-logs

# 看執行結果（不用一台一台 SSH 進去看）
$ aws ssm list-command-invocations --command-id 1234-abcd --details \
    --query 'CommandInvocations[].[InstanceId,Status]' --output table
--max-concurrency 與 --max-errors 是正式環境的救命參數。一次對 500 台下指令，如果指令有問題就是 500 台一起壞。設成「一次 20%、錯 5 台就停」，出事時還有 80% 的機器是好的。考題會用「如何安全地大規模執行變更」來問這兩個參數的概念。

Automation 的典型用途：自動修復

AWS Config 偵測到「S3 儲存貯體未加密」 │ ▼ EventBridge 規則 │ ▼ SSM Automation Runbook AWS-EnableS3BucketEncryption │ ▼ 自動改回合規狀態 + 通知
「偵測到不合規要自動修正」= Config 規則 + SSM Automation 修復動作。這在第 08 章的自動修復出現過，這裡補上 SSM 這一端的細節：真正動手改的是 Automation Runbook。

5. Patch Manager：修補基準與維護時段

修補是稽核第一個會問的事。Patch Manager 把它變成「宣告規則 → 自動執行 → 產生合規報表」。

元件作用要記的重點
Patch Baseline
（修補基準）		定義「哪些修補要裝」可設自動核准延遲天數（例如發布 7 天後才裝，避開有問題的更新）、嚴重性條件、明確核准／拒絕清單
Patch Group
（修補群組）		把機器分組套用不同基準用標籤 Patch Group 指定（鍵名固定，中間有空格）
Maintenance Window
（維護時段）		什麼時候可以動手cron 排程 + 持續時間 + 截止前停止新任務的緩衝
Compliance
（合規檢視）		誰修好了、誰沒有可送 Security Hub、可產生稽核報表
典型的分階段修補策略

Patch Group = dev → 基準：核准延遲 0 天，維護時段：每週二 02:00 → 最快踩到問題。
Patch Group = staging → 核准延遲 3 天，維護時段：每週四 02:00。
Patch Group = prod → 核准延遲 7 天，維護時段：每月第二個週日 03:00。

這個「延遲天數」設計就是 Patch Baseline 最重要的參數——它讓你不必人工審核每一個更新，也不會第一時間吃到有問題的修補。

# 建立修補基準：只裝重要與安全性更新，且發布 7 天後才核准
$ aws ssm create-patch-baseline \
    --name "prod-linux-baseline" \
    --operating-system AMAZON_LINUX_2 \
    --approval-rules '{
      "PatchRules":[{
        "PatchFilterGroup":{"PatchFilters":[
           {"Key":"CLASSIFICATION","Values":["Security","Bugfix"]},
           {"Key":"SEVERITY","Values":["Critical","Important"]}]},
        "ApproveAfterDays":7,
        "ComplianceLevel":"CRITICAL"
      }]}' \
    --rejected-patches "kernel-5.10.0-buggy"

# 把基準關聯到 Patch Group（機器要打 tag: Patch Group = prod）
$ aws ssm register-patch-baseline-for-patch-group \
    --baseline-id pb-0abc123 --patch-group "prod"

# 先「只掃描不安裝」，看看目前缺哪些（正式環境務必先做這一步）
$ aws ssm send-command \
    --document-name "AWS-RunPatchBaseline" \
    --targets "Key=tag:Patch Group,Values=prod" \
    --parameters 'Operation=Scan'

# 看合規結果
$ aws ssm list-compliance-summaries --output table
標籤鍵名是 Patch Group，中間有一個空格，而且大小寫敏感。寫成 PatchGroup 或 patch group 都不會生效，而且不會報錯——機器就是默默地套用預設基準。這是實務上很難查的坑，考題也愛拿它當錯誤選項。
陷阱：修補要開 SSH 或裝第三方工具
都不用。Patch Manager 走 SSM Agent，零入站連接埠。選項裡出現「架 WSUS 伺服器」「用 Ansible 從堡壘主機推」的，在 SAA 裡都是要被淘汰的做法。
實務提醒：Patch Manager 預設裝完不會自動重開機（可設定），但很多更新要重開才生效——結果就是「合規報表說已修補，實際上還在跑舊核心」。正式環境要把重開機策略連同 ASG 的滾動更新一起設計，或乾脆走不可變基礎設施：修補做在 AMI 上（用 Automation + Image Builder），機器直接換新的，不在跑的機器上動手術。

6. Parameter Store vs Secrets Manager

SSM Parameter StoreSecrets Manager
費用Standard 免費（Advanced 付費）每個密文每月計費 + API 呼叫費
自動輪換沒有內建（要自己寫 Lambda）原生支援，與 RDS / Redshift / DocumentDB 整合
大小上限Standard 4 KB / Advanced 8 KB64 KB
跨帳號共享不支援（Advanced 也不行）支援（資源型政策）
加密SecureString 用 KMS一律 KMS 加密
階層與版本階層式路徑、自動版本版本與階段標籤
判斷只看一句話：「要不要自動輪換」。
要自動輪換（尤其是資料庫密碼）→ Secrets Manager。
只是存組態、API 端點、功能開關，或要免費 → Parameter Store。
這是 SAA 最愛考的一組二選一，答案幾乎都由「輪換」這個詞決定。

階層式命名：實務上一定要這樣做

# 用路徑分層，一次抓一整組
$ aws ssm put-parameter --name "/myapp/prod/db/host" \
    --value "mydb.abc.ap-northeast-1.rds.amazonaws.com" --type String
$ aws ssm put-parameter --name "/myapp/prod/db/password" \
    --value "..." --type SecureString --key-id alias/myapp-kms

# 應用程式啟動時一次讀整棵子樹並自動解密
$ aws ssm get-parameters-by-path --path "/myapp/prod/" \
    --recursive --with-decryption \
    --query 'Parameters[].[Name,Value]' --output table
階層命名的好處是權限也能分層：IAM 政策寫 arn:aws:ssm:*:*:parameter/myapp/prod/*，就能讓正式環境的角色只讀得到正式環境的參數，開發角色碰不到。扁平命名（myapp-prod-db-password）做不到這件事。
陷阱：把密碼寫在 User Data 或環境變數
User Data 對任何能呼叫 describe-instance-attribute 的人都是可見的明文，環境變數也會出現在程序清單與日誌裡。
正解是 SecureString 參數或 Secrets Manager，執行期用 IAM Role 取用。

7. Inventory / Fleet Manager / 合規

Inventory定期蒐集每台機器的已安裝軟體、更新、網路組態、服務，可匯總到 S3 用 Athena 查詢。
Fleet Manager用瀏覽器 GUI 看檔案系統、Windows 登錄檔、效能計數器、程序——不用登入機器。
Compliance彙總修補合規與組態合規，可送到 Security Hub 統一檢視。
Inventory 的經典考題：「安全團隊需要知道全公司哪些機器裝了某個有漏洞的套件版本」——
答案是 SSM Inventory 匯總到 S3 再用 Athena 查詢。
不是 Config（它看的是 AWS 資源組態，不是機器裡面裝了什麼），也不是 Inspector（它掃漏洞，但題目問的是「盤點清單」）。
Inventory vs Config vs Inspector 的分界：
Inventory = 機器裡面有什麼（軟體清單）。
Config = AWS 資源的組態與變更歷史（SG 開了什麼埠、S3 有沒有加密）。
Inspector = 有沒有已知漏洞（CVE）與網路可達性風險。
三個都跟「檢查」有關，但看的層次完全不同，考題常拿來互相當誘答。

8. Directory Service 三種怎麼選

企業上雲最現實的一題：「公司有幾千個 AD 帳號，難道要在 AWS 重建一套嗎？」Directory Service 提供三個答案，差別在目錄資料放哪。

AWS Managed Microsoft AD 真正的 Microsoft AD 跑在 AWS 目錄資料在 AWS 可與地端 AD 建立信任關係 地端斷線仍可獨立驗證 AD Connector 只是一個代理／轉送器 目錄資料留在地端 驗證請求原路轉回地端 AD 地端斷線就無法驗證 Simple AD Samba 4 相容的輕量目錄 目錄資料在 AWS 不支援信任關係、不支援 MFA 小規模、低成本
Managed Microsoft ADAD ConnectorSimple AD
本質AWS 代管的真 AD代理，不存資料Samba 4 相容目錄
與地端 AD 建立信任✓不適用（本來就用地端）✗
地端斷線時仍可運作無法驗證不適用
群組原則（GPO）✓用地端的有限
MFA✓（RADIUS）✓（RADIUS）✗
支援 FSx for Windows
/ RDS SQL Server / WorkSpaces		✓部分服務不支援部分支援
典型選用理由要在雲端有獨立可用的 AD不想在雲端存放目錄副本小型、成本最低、無 AD 需求
三題典型情境

Q：「公司已有地端 AD，希望員工用既有帳號登入 AWS 資源，但安全政策不允許在雲端存放目錄副本。」
A：AD Connector——關鍵字是「不存放副本」。

Q：「要在 AWS 部署 FSx for Windows 與 RDS for SQL Server，需要 AD 驗證，並希望與地端 AD 共用身分，即使專線中斷仍要能登入。」
A：AWS Managed Microsoft AD 並與地端建立信任——關鍵字是「斷線仍要能運作」。

Q：「50 人的新創要一個便宜的目錄做 Linux 機器與 WorkSpaces 的基本驗證，不需要與任何既有 AD 整合。」
A：Simple AD——關鍵字是「不需整合、成本最低」。

陷阱 1：AD Connector 拿來給 FSx for Windows 用
FSx for Windows 需要真正的 AD（AWS Managed Microsoft AD 或自建 AD）。AD Connector 只是驗證代理，撐不起這類服務的目錄需求。
陷阱 2：把 Cognito 當成企業目錄
Cognito 是給「應用程式的終端使用者」用的（App 註冊、社交登入、發放暫時 AWS 憑證）。
Directory Service 是給「公司員工」用的（AD、GPO、Windows 驗證）。
題目主角是「客戶／App 使用者」→ Cognito；是「員工／網域帳號」→ Directory Service 或 IAM Identity Center。
與 IAM Identity Center 的關係：Identity Center 負責「員工登入多個 AWS 帳號」這件事，它的身分來源可以是自己的目錄、AWS Managed Microsoft AD，或外部 IdP（Okta、Entra ID 等）。
所以完整的企業做法常是：地端 AD ←信任→ Managed Microsoft AD ←身分來源→ IAM Identity Center → 各 AWS 帳號的權限集。

實作 Lab：無堡壘主機登入 + 自動修補

約 50 分鐘。做完你會有一台沒有任何入站規則、沒有公有 IP，卻能登入與自動修補的 EC2。

費用極低：一台 t3.micro 加上私有子網路的 NAT 或 Endpoint。如果為了省錢用 NAT Gateway，記得 Lab 結束一定要刪——NAT Gateway 是這裡唯一會持續跳表的東西。想避開它就改用三個 Interface Endpoint（也有時數費，但這個 Lab 開一小時的差距不大）。

階段一：建立零入站的 EC2

  1. 建立 IAM Role，附加 AmazonSSMManagedInstanceCore，建立執行個體設定檔
  2. 在私有子網路開一台 Amazon Linux 2023，掛上該 Role，不要配公有 IP
  3. Security Group：入站規則留空，出站允許 443
  4. 建立三個 Interface Endpoint（ssm、ssmmessages、ec2messages）與一個 S3 Gateway Endpoint
  5. 執行 aws ssm describe-instance-information，確認機器 PingStatus=Online
  6. 用 aws ssm start-session 登入——入站規則是空的，但你進得去
機器沒上線？照第 2 節的三個前置條件依序檢查：① Role 掛了嗎（describe-instances 看 IamInstanceProfile）② Endpoint 的 SG 有沒有放行 EC2 過來的 443 ③ Endpoint 有沒有開 --private-dns-enabled。
看得到機器但連不進去 → 一定是少了 ssmmessages。

階段二：開啟工作階段稽核

  1. 建一個 S3 儲存貯體，在 Session Manager 的偏好設定指定日誌輸出位置（也可同時送 CloudWatch Logs）
  2. 再連一次線，隨便下幾個指令
  3. 到 S3 看那份逐字稿——你打的每個字都在裡面
這一步是稽核題的實體證據。「如何證明誰在什麼時候對正式機器做了什麼」→ Session Manager 工作階段日誌 + CloudTrail。

階段三：Patch Manager

  1. 幫機器打標籤 Patch Group = lab（注意中間有空格）
  2. 建立 Patch Baseline（Amazon Linux 2023，只收 Security + Critical，ApproveAfterDays=0 方便測試）
  3. 把基準註冊到 Patch Group lab
  4. 先用 Operation=Scan 掃描，看報表列出缺哪些修補
  5. 再用 Operation=Install 實際安裝
  6. 用 list-compliance-summaries 確認變成合規

階段四：Parameter Store

  1. 建立 /lab/app/db/password（SecureString）與 /lab/app/db/host（String）
  2. 在 EC2 上用 get-parameters-by-path --with-decryption 讀出來——沒有任何金鑰寫在機器上
  3. 把 Role 的權限縮成只能讀 /lab/app/*，驗證讀別的路徑會被拒絕

階段五：清理

  1. 終止 EC2
  2. 刪除 NAT Gateway 或 Interface Endpoint（這是唯一持續計費的部分）
  3. 刪除 Patch Baseline、參數、S3 日誌儲存貯體

10. 考試陷阱整理

陷阱 1：EC2 沒出現在 SSM 清單
依序查：① SSM Agent ② IAM 執行個體設定檔（AmazonSSMManagedInstanceCore） ③ 網路。第二項是最常見的原因。
陷阱 2：看得到機器但 Session Manager 連不上
少了 ssmmessages Endpoint。這個「看得到／連不上」的症狀對應非常明確。
陷阱 3：以為 Session Manager 要開 22 埠
不用。Security Group 零入站規則也能連。選項出現「開 22 給公司 IP」的都是被淘汰的做法。
陷阱 4：Patch Group 標籤寫錯
鍵名固定是 Patch Group（中間有空格、大小寫敏感）。寫錯不會報錯，只會默默套用預設基準。
陷阱 5：Parameter Store 要自動輪換
它沒有內建輪換。題目一出現「自動輪換」就是 Secrets Manager；一出現「免費／單純存組態」就是 Parameter Store。
陷阱 6：Run Command / Automation / State Manager 混用
做一次在機器上 → Run Command；做一連串跨資源 → Automation；一直維持某狀態 → State Manager。
陷阱 7：Inventory 與 Config 搞混
機器裡面裝了什麼 → Inventory；AWS 資源的組態與變更歷史 → Config；有沒有已知漏洞 → Inspector。
陷阱 8：AD Connector 用在需要真 AD 的服務
FSx for Windows、RDS for SQL Server 這類需要 AWS Managed Microsoft AD 或自建 AD。AD Connector 只是驗證代理。
陷阱 9：AD Connector 在專線中斷時還能用
不能。它不存目錄資料，地端 AD 連不到就驗證不了。要「斷線仍可運作」→ Managed Microsoft AD。
陷阱 10：Simple AD 拿來做信任關係或 MFA
兩個都不支援。有這些需求就要 Managed Microsoft AD。
陷阱 11：用 Cognito 管員工帳號
Cognito 是應用程式的終端使用者；員工／網域帳號是 Directory Service 或 IAM Identity Center。
💡一句話記憶：
要登入用 Session Manager，要下指令用 Run Command，要維持狀態用 State Manager，要修補用 Patch Manager；
要輪換找 Secrets Manager，要免費找 Parameter Store；
目錄放雲上是 Managed Microsoft AD，留地端是 AD Connector，都不要就 Simple AD。
