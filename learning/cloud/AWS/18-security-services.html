1. AWS 縱深防禦全景：三大維度與服務對照

把企業雲端架構想成一座現代化金庫大樓：
• 邊界警衛與外圍護城河 (WAF / Shield / Network Firewall)：擋住門外的暴徒與網路癱瘓攻擊。
• 主動保全監視器 (GuardDuty)：AI 全天候監控誰在異常角落做可疑動作（挖礦、偷摸金庫）。
• 結構消防安檢 (Inspector)：檢查建築牆面有沒有偷工減料或已知的脆弱裂縫（CVE 漏洞）。
• 金庫內帳冊盤點 (Macie)：找出哪份機密顧客個資被亂扔在未上鎖的抽屜（S3 桶公開）。
• 安全中控指揮室 (Security Hub)：把所有警報統整呈現在一面大螢幕上並計算合規評分。
• 密碼鎖與保險箱 (KMS / Secrets Manager)：確保即使強盜攻破大門，拿到的也是一堆無法解讀的密文！

2. AWS KMS 與信封加密（Envelope Encryption）底層機制

在 SAA-C03 考試中，KMS 是資料加密的核心。必須理解：KMS 本身的 API（kms:Encrypt）最多只能加密 4KB 大小的資料！如何加密數十 GB 的資料庫備份或高解析影片？答案就是信封加密 (Envelope Encryption)。

【加密流程 (Encrypt Workflow)】 業務應用程式 (Application) │ │ 1. 呼叫 KMS: GenerateDataKey(KeyId="arn:aws:kms...CMK") ▼ AWS KMS 硬體安全模組 (HSM) │ 2. KMS 產生一把全新的資料金鑰 (Data Key, AES-256)，並回傳兩樣東西： ├── 明文資料金鑰 (Plaintext Data Key) └── 密文資料金鑰 (Encrypted Data Key)，由 KMS CMK 主金鑰加密包裹 ▼ 業務應用程式 (本地記憶體中) │ 3. 使用【明文資料金鑰】在本地高速對 100GB 大檔案進行 AES-GCM 加密 │ 4. 立即從記憶體徹底抹除 (Wipe) 明文資料金鑰！ ▼ 儲存至 Amazon S3 / 磁碟 └── 儲存【加密後的資料本體】+【密文資料金鑰】（放在檔案頭部 metadata，像信封一樣） 【解密流程 (Decrypt Workflow)】 業務應用程式讀取 S3 檔案 │ 1. 取出頭部的【密文資料金鑰】，呼叫 KMS: Decrypt(CiphertextBlob) ▼ AWS KMS │ 2. KMS 內部使用 CMK 解密出【明文資料金鑰】，回傳給應用程式 ▼ 業務應用程式 │ 3. 在本地解密資料本體，使用完畢再次抹除記憶體中的明文金鑰！
為什麼必須使用信封加密？三大優勢：
  • 突破 4KB 限制：無論檔案是 1MB 還是 5TB，皆可在本機加密。
  • 極致網路效能：無須將龐大的資料透過網路傳輸到 KMS 伺服器，只傳輸 256 位元的短金鑰。
  • 最小化 KMS 呼叫成本與 API 配額消耗。

3. KMS 金鑰類型與跨區域 / 跨帳號存取決策

金鑰類型建立與管理方能否輪換金鑰？能否刪除金鑰？典型使用場景
AWS Owned Key AWS 內部全權擁有 由 AWS 自行維護 ❌ 無法查看也無法刪除 DynamoDB 預設免費加密、S3 預設加密。
AWS Managed Key AWS 代為建立（如 aws/s3、aws/ebs） 每 1 年（365 天）自動輪換 ❌ 無法修改 Policy 也無法刪除 單一帳號內一般日常服務快速加密。
Customer Managed Key (CMK) 客戶自行建立與全權管理 可開關自動每年輪換，或手動建立新版本 ✅ 支援設定 7~30 天等待期後刪除 需要跨帳號授權、需審計金鑰存取日誌、需隨時撤銷金鑰（SAA 首選）。

KMS Multi-Region Keys（跨區域多區域金鑰）

傳統 KMS Key 是嚴格綁定在單一 Region 的（Region-bound）。如果使用 S3 Cross-Region Replication (CRR) 複製加密物件，目標區域必須重新使用目標區域的金鑰重加密。若使用 KMS Multi-Region Key，則可在主要區域（Primary）建立金鑰，並將其金鑰材料複製到多個副本區域（Replicas）。兩者擁有相同的 Key ID 與金鑰材料，在異地災難復原 (DR) 時可無縫直接解密！

跨帳號存取 KMS CMK 的雙重授權必備條件：
若帳號 A 的 EC2 想要使用帳號 B 的 KMS Key 解密 S3 物件：
1. 帳號 B 的 KMS Key Policy 必須明確 Allow 帳號 A 的 IAM Role 呼叫 kms:Decrypt。
2. 帳號 A 的 IAM Role Policy 亦必須明確 Allow 對帳號 B 的 KMS Key ARN 執行 kms:Decrypt。
兩邊缺一不可！

4. Secrets Manager vs SSM Parameter Store 深度對比

比較指標AWS Secrets ManagerSystems Manager Parameter Store
定位與核心強項 機密資訊生命週期管理與自動輪換 (Rotation)。 通用系統組態參數與層級式鍵值儲存。
自動輪換能力 ✅ 內建支援（開箱即用支援 RDS、Redshift、DocumentDB；自訂 Lambda 輪換其他 API Key）。 ❌ 無原生內建輪換（需自己撰寫複雜的 EventBridge + Lambda 腳本）。
計費模型 每個 Secret 收費 $0.40 美元/月 + API 呼叫費。成本較高。 Standard 方案完全免費（上限 10,000 個參數）；Advanced 支援超大參數與政策。
跨帳號存取支援 ✅ 原生支援 Resource Policy，跨帳號讀取非常直覺。 需透過 RAM 或跨帳號 STS AssumeRole。
考題情境秒選法 「資料庫密碼需要定期自動更換且不中斷服務」、「管理 RDS 憑證」。 「無額外成本儲存授權字串」、「微服務組態檔設定」、「免費儲存非機密參數」。

5. 邊界防護：AWS WAF 規則鏈與 Shield DDoS 防禦

網際網路流量流入 ↓ 1. AWS Shield Standard (免費自動啟用) └── 阻斷第 3/4 層 SYN Flood、UDP Reflection 等網路基礎設施攻擊 ↓ 2. AWS WAF WebACL (第 7 層檢查) ├── 規則 1：IP 封鎖清單 (IP Sets) ── 命中惡意 IP ──→ [BLOCK 403] ├── 規則 2：AWS 受管規則組 (AWSManagedRulesCommonRuleSet) ── 檢測 SQLi / XSS ──→ [BLOCK 403] ├── 規則 3：Rate-based Rule (速率限制) ── 5 分鐘內超過 2000 請求 ──→ [BLOCK 429/403] └── 規則 4：Geo Match (地理位置) ── 阻斷未營運國家 ──→ [BLOCK 403] ↓ 全部規則通過 轉發至 CloudFront / ALB / API Gateway
防禦維度AWS Shield StandardAWS Shield Advanced
成本費用 完全免費，自動啟用。 每月 $3,000 美元固定基本月費（需綁定 1 年合約）。
防護範圍 OSI 第 3 層（網路層）與第 4 層（傳輸層）。 涵蓋第 3、4、7 全層級 DDoS 攻擊。
專業專家支援 無。 24/7 Shield Response Team (SRT) 專屬架構師介入減緩。
財務費用保護 ❌ 無費用補償。被攻擊時 EC2 / ALB 擴容費用需自付。 ✅ DDoS Cost Protection！攻擊期間因 Auto Scaling 暴增的運算費用由 AWS 補償抵免！

6. GuardDuty：基於日誌分析的無代理威脅偵測

GuardDuty 是 AWS 的核心威脅情報大腦。最關鍵的架構特點：它完全不需要在虛擬機或容器上安裝任何 Agent 或 Daemon，對系統效能與網路頻寬造成零干擾！

GuardDuty 四大核心日誌分析源 (無代理程式) ├── AWS CloudTrail 管理與資料事件（偵測 API 異常、未授權憑證調用） ├── VPC Flow Logs（偵測異常連線、連接埠掃描、與黑客 C2 伺服器通訊） ├── DNS Query Logs（偵測惡意網域查詢、DNS 隧道資料竊取） └── EKS 稽核日誌與控制台事件 加值擴充防禦功能 (可一鍵開啟) ├── S3 Protection：監控 S3 API 異常資料外洩與不尋常讀寫 ├── RDS Protection：偵測資料庫密碼暴力破解與異常登入 ├── Lambda Protection：偵測 Serverless 函式遭惡意操控 └── Malware Protection：發現異常時，自動對 EC2 的 EBS 卷建立快照並進行無代理木馬病毒掃描！

7. Inspector：運算資源漏洞掃描 (CVE)

EC2 執行個體掃描 透過 AWS Systems Manager (SSM) Agent 深入作業系統，盤點已安裝的應用套件，持續對照 CVE 漏洞庫。

必備：EC2 需安裝 SSM Agent 且網路可連通 SSM。
Amazon ECR 映像檔掃描 容器映像檔推送到 ECR 時自動觸發，亦支援持續評估掃描 (Continuous Scanning)。當外界新公布 CVE 時，回溯比對倉庫中的歷史映像檔。
AWS Lambda 函式掃描 掃描 Lambda 函式代碼相依套件庫（如 Python pip, Node.js npm 套件中的已知安全漏洞）。
秒殺考點：GuardDuty vs Inspector 究竟怎麼分？
• Inspector：看的是「靜態弱點」（系統有沒有已知的軟體 CVE 漏洞，未發生攻擊也存在）。需要 SSM Agent。
• GuardDuty：看的是「動態行為」（系統當前是不是正在做壞事，如挖礦、被遠端操控）。不需要 Agent。

8. Macie：S3 敏感資料與 PII 盤點

Amazon Macie 運用自然語言處理 (NLP) 與機器學習，專門掃描與識別儲存在 Amazon S3 中的機密資料：

識別範疇涵蓋的具體敏感資訊
個人身分識別資訊 (PII)身分證字號、護照號碼、駕照號碼、姓名與聯絡地址。
金融財務資訊信用卡卡號 (PCI)、銀行帳戶資訊、SWIFT 碼。
醫療健康機密 (HIPAA)病歷號碼、健康檢查結果、保險檔案。
開發機敏憑證私鑰、AWS Access Key / Secret Key、JWT 密鑰。

9. Security Hub：合規儀表板與發現彙整

Security Hub 是整個企業資安的「中控總儀表板」。它自己不發明威脅，而是扮演收集器 (Aggregator) 與 評分員 (Auditor)：

收集輸入來源 GuardDuty + Inspector + Macie + IAM Access Analyzer + AWS Config + 第三方廠商工具 │ 全部轉化為標準 AWS 安全發現格式 (ASFF) ▼ AWS Security Hub 集中彙整 ├── 跨帳號、跨區域聚合 └── 自動對照業界合規基準打分數： ├── CIS AWS Foundations Benchmark ├── PCI DSS (支付卡產業標準) └── AWS Foundational Security Best Practices

10. 事後調查與稽核：Detective、Audit Manager、Artifact

Amazon Detective 事件根本原因調查。自動從 VPC Flow Logs、CloudTrail 與 GuardDuty 構建「行為圖形 (Graph Model)」，視覺化展示攻擊者在過去數週的滲透路徑。
AWS Audit Manager 企業自身的合規稽核。持續自動採集客戶 AWS 資源上的控制項證據（如備份記錄、加密狀態），一鍵導出合規評估報告。
AWS Artifact 下載 AWS 自身的合規認證。向外部審計師出示 AWS 資料中心的 SOC 1/2/3、ISO 27001、PCI 稽核報告，以及簽署 BAA 協議。

11. Firewall Manager：多帳號組織級集中資安政策

單一帳號的 WAF 只能保護自己帳號下的幾台 ALB；但當跨國集團擁有 100 個 AWS Member Accounts 時，如何確保「所有帳號目前與未來新建的每一台 ALB 都強制掛上防 SQL 注入的 WAF」？這必須依靠 AWS Firewall Manager！
必備三大前置條件具體要求與功能
1. AWS Organizations必須開啟所有功能 (All Features)，而非僅開 Consolidated Billing。
2. 委派管理員指定一個獨立的 Security Account 作為 Firewall Manager 的委派管理員。
3. AWS Config組織下的所有帳號必須啟用 AWS Config，Firewall Manager 依賴 Config 發現新建立的資源。

12. 企業級 SecOps 自動化應變與事件聯防閉環

當 GuardDuty 偵測到有黑客正在暴力破解 SSH 或發起攻擊時，秒級全自動阻斷的標準雲端架構如下：

惡意黑客 IP 發動攻擊 │ ▼ Amazon GuardDuty ──偵測到異常行為，生成 Finding (例如: UnauthorizedAccess:EC2/SSHBruteForce) │ ▼ Amazon EventBridge ──比對 Event Pattern 命中資安規則 │ ▼ AWS Lambda 應變函式 ├── 1. 解析事件中的攻擊者 IP (Malicious IP) ├── 2. 調用 WAF API: UpdateIPSet，將惡意 IP 加入封鎖黑名單 ├── 3. 調用 EC2 API: 修改遭感染 EC2 的 Security Group，替換為隔離隔離區 SG └── 4. 發送緊急簡訊與 Slack 警報通知資安團隊 (SNS)

13. SAA-C03 考試陷阱與高頻對照速查

陷阱 1：WAF 無法掛載至 NLB 或 EC2
WAF 是第 7 層應用防火牆，只能掛載在 CloudFront、ALB、API Gateway、AppSync、Cognito User Pool。若題目架構為 NLB → EC2 且要求防禦 SQL 注入，標準解法是將 NLB 改為 ALB，或在 NLB 前置 CloudFront + WAF。
陷阱 2：KMS Key 刪除的安全性
KMS CMK 無法立即瞬間刪除！AWS 強制要求設定 7 到 30 天的等待期 (Waiting Period)。在等待期內，金鑰狀態變更為 Pending Deletion，若發現誤刪尚可呼叫 CancelKeyDeletion 救援。
陷阱 3：Artifact vs Audit Manager
• AWS Artifact：證明「AWS 雲端基礎設施」是否合規（責任共擔模型中 AWS 的部分）。
• Audit Manager：證明「客戶自己託管在 AWS 的系統」是否合規（責任共擔模型中客戶的部分）。
🎯 資安家族考前通關口訣：
• 大檔案本地加密 → KMS 信封加密 (GenerateDataKey)
• 資料庫密碼定期自轉 → Secrets Manager (自動輪換)
• 實體/無代理行為偵測 → Amazon GuardDuty
• 主機 CVE 漏洞盤點 → Amazon Inspector (搭配 SSM Agent)
• S3 機密個資掃描 → Amazon Macie
• 全組織新舊資源強套 WAF → AWS Firewall Manager

14. 實作 Lab：KMS 信封加密與 WAF WebACL 配置實戰

# 步驟 1：建立客戶自管 KMS 主金鑰 (CMK) 並啟用自動每年輪換 aws kms create-key --description "Prod-Data-Encryption-Key" aws kms enable-key-rotation --key-id <KMS_KEY_ID> # 步驟 2：執行信封加密——請求產生一組 Data Key (回傳明文與密文金鑰) aws kms generate-data-key \ --key-id <KMS_KEY_ID> \ --key-spec AES_256 # 步驟 3：建立 WAF WebACL 規則並掛載至 ALB aws wafv2 create-web-acl \ --name "prod-app-protection" \ --scope REGIONAL \ --default-action Allow={} \ --visibility-config SampledRequestsEnabled=true,CloudWatchMetricsEnabled=true,MetricName=ProdWafMetric \ --rules '[ { "Name": "AWS-AWSManagedRulesCommonRuleSet", "Priority": 0, "Statement": { "ManagedRuleGroupStatement": { "VendorName": "AWS", "Name": "AWSManagedRulesCommonRuleSet" } }, "OverrideAction": { "None": {} }, "VisibilityConfig": { "SampledRequestsEnabled": true, "CloudWatchMetricsEnabled": true, "MetricName": "CRSMetric" } } ]' # 步驟 4：將 WAF WebACL 關聯到 Application Load Balancer aws wafv2 associate-web-acl \ --web-acl-arn <WEB_ACL_ARN> \ --resource-arn <ALB_ARN>
