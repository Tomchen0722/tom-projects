1. 無伺服器到底是什麼

無伺服器 ≠ 沒有伺服器

是「你不用管伺服器」——不用開機器、不用打補丁、不用設容量
而且沒有請求就不收費

什麼時候該用無伺服器？
✅ 很適合❌ 不適合
流量不固定、會歸零穩定的高流量（EC2 + RI 更便宜）
事件驅動（檔案上傳、訊息到達）執行超過 15 分鐘的工作
排程工作（每天跑報表）需要極低且穩定延遲的服務
API 後端（流量不大）需要持久連線（WebSocket 長連線除外）

無伺服器最大的隱藏成本是「複雜度」。一個 EC2 上的單體應用，出事時你 SSH 進去看日誌就好。同樣功能拆成 20 支 Lambda + SQS + EventBridge 之後，一個請求跨越十幾個服務，追蹤問題困難很多。

這就是為什麼無伺服器架構必須從第一天就導入分散式追蹤（X-Ray）和結構化日誌。

2. Lambda 核心限制（必背）

項目限制踩到會怎樣
執行時間最長 15 分鐘（預設 3 秒）被強制中止，沒有任何清理機會
記憶體128 MB – 10,240 MBOOM 直接失敗
vCPU依記憶體等比配給（1769 MB = 1 vCPU）算力不足
/tmp 暫存空間512 MB – 10,240 MB寫不下
部署包（zip）50 MB 壓縮 / 250 MB 解壓後上傳失敗 → 改用容器映像（10 GB）
環境變數總共 4 KB放不下 → 用 Parameter Store
同步呼叫 payload6 MB超過就失敗 → 用 S3 傳大檔
非同步呼叫 payload256 KB同上
預設併發每帳號每 region 1,000被限流（可申請提高）
Layer最多 5 個，總計 250 MB—
記憶體設定同時決定 CPU，這是最重要的調校參數。
128 MB ≈ 0.07 vCPU　　1,769 MB = 1 vCPU　　10,240 MB ≈ 6 vCPU
所以「調高記憶體」常常反而更便宜——因為執行時間縮短的幅度大於單價上升的幅度。

實例：一支函式 128 MB 跑 10 秒 vs 1024 MB 跑 1 秒
· 128 MB：128 × 10 = 1280 MB-秒
· 1024 MB：1024 × 1 = 1024 MB-秒 → 反而便宜 20%，而且快 10 倍
用 AWS Lambda Power Tuning 自動找最佳記憶體設定。它是官方提供的 Step Functions 工具，會用不同記憶體各跑幾次，畫出「成本 vs 執行時間」的曲線讓你選。免費（只付測試執行的費用），通常能省 20–50%。
15 分鐘上限沒有例外。時間到就是被砍，程式碼來不及做任何善後。要處理長時間工作：
  • 拆成多支 Lambda 用 Step Functions 串起來
  • 改用 Fargate（無時間限制）或 Batch
  • 做成可續作的設計：處理一部分、存進度、重新觸發自己

3. 實作一：部署一支 Lambda

Lambda 永久免費方案：每月 100 萬次請求 + 40 萬 GB-秒運算。
一支 512 MB 的函式跑 200ms，每月可以免費跑約 400 萬次。學習用途幾乎不可能超過。
但要小心無限迴圈——Lambda 寫回觸發自己的 S3 bucket，會遞迴爆炸。第 9 節會講怎麼防。
# ═══ 步驟 1：執行角色 ═══
$ cat > trust-lambda.json <<'EOF'
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "Service": "lambda.amazonaws.com" },
    "Action": "sts:AssumeRole"
  }]
}
EOF

$ ROLE_ARN=$(aws iam create-role --role-name order-processor-role \
    --assume-role-policy-document file://trust-lambda.json \
    --query Role.Arn --output text)

# 基本執行權限（寫 CloudWatch Logs）—— 一定要有
$ aws iam attach-role-policy --role-name order-processor-role \
    --policy-arn arn:aws:iam::aws:policy/service-role/AWSLambdaBasicExecutionRole

# 額外權限：寫 DynamoDB（最小權限）
$ aws iam put-role-policy --role-name order-processor-role \
    --policy-name write-orders --policy-document '{
      "Version":"2012-10-17",
      "Statement":[{
        "Effect":"Allow",
        "Action":["dynamodb:PutItem","dynamodb:UpdateItem","dynamodb:GetItem"],
        "Resource":"arn:aws:dynamodb:ap-northeast-1:123456789012:table/Orders"
      }]
    }'
# ═══ 步驟 2：程式碼 ═══
$ mkdir order-processor && cd order-processor
$ cat > index.py <<'PYEOF'
import json, os, boto3, logging
from decimal import Decimal

logger = logging.getLogger()
logger.setLevel(logging.INFO)

# ⚠ 在 handler 外面初始化 —— 這樣可以在多次呼叫之間重複使用
dynamodb = boto3.resource("dynamodb")
table = dynamodb.Table(os.environ["TABLE_NAME"])


def handler(event, context):
    # 結構化日誌：方便之後用 CloudWatch Logs Insights 查
    logger.info(json.dumps({
        "msg": "invoked",
        "requestId": context.aws_request_id,
        "remainingMs": context.get_remaining_time_in_millis(),
    }))

    try:
        body = json.loads(event.get("body") or "{}")
        order_id = body["orderId"]

        table.put_item(
            Item={
                "customerId": body["customerId"],
                "orderDate": body["orderDate"],
                "orderId": order_id,
                "amount": Decimal(str(body["amount"])),
            },
            # 冪等性：同一筆訂單重複送不會覆蓋
            ConditionExpression="attribute_not_exists(orderId)",
        )
        return {"statusCode": 201, "body": json.dumps({"orderId": order_id})}

    except KeyError as e:
        logger.warning(f"缺少欄位 {e}")
        return {"statusCode": 400, "body": json.dumps({"error": f"missing {e}"})}

    except dynamodb.meta.client.exceptions.ConditionalCheckFailedException:
        # 重複送達 —— 回 200 而不是錯誤，這才是冪等的做法
        logger.info(f"訂單 {order_id} 已存在，略過")
        return {"statusCode": 200, "body": json.dumps({"duplicate": True})}

    except Exception:
        logger.exception("處理失敗")
        raise          # 讓 Lambda 標記失敗，觸發重試 / DLQ
PYEOF

$ zip -r function.zip index.py
三個寫 Lambda 的關鍵習慣（程式碼裡都示範了）：
  1. 在 handler 外面初始化 SDK client——Lambda 會重複使用執行環境，放外面就不用每次重建連線，可以省下數十到數百毫秒
  2. 用結構化日誌（JSON）——CloudWatch Logs Insights 才能有效查詢
  3. 失敗要 raise 不要吞掉——吞掉例外的話 Lambda 認為成功，訊息就不會重試也不會進 DLQ，資料默默遺失
# ═══ 步驟 3：建立函式 ═══
$ aws lambda create-function \
    --function-name order-processor \
    --runtime python3.12 \
    --architecture arm64 \
    --handler index.handler \
    --role $ROLE_ARN \
    --zip-file fileb://function.zip \
    --timeout 30 \
    --memory-size 512 \
    --environment "Variables={TABLE_NAME=Orders}" \
    --tracing-config Mode=Active \
    --logging-config LogFormat=JSON,ApplicationLogLevel=INFO

# 測試
$ aws lambda invoke --function-name order-processor \
    --payload '{"body":"{\"orderId\":\"O-1\",\"customerId\":\"C-1\",\"orderDate\":\"2026-08-05\",\"amount\":100}"}' \
    --cli-binary-format raw-in-base64-out response.json
$ cat response.json
--architecture arm64（Graviton）比 x86 便宜約 20%，效能通常更好。Python、Node.js、Java、Go 都完全支援。只有在依賴的原生套件沒有 ARM 版時才用 x86。

版本與別名：安全部署

# 發布一個不可變的版本
$ aws lambda publish-version --function-name order-processor

# 建立別名指向該版本
$ aws lambda create-alias --function-name order-processor \
    --name prod --function-version 3

# 金絲雀：10% 流量給新版本
$ aws lambda update-alias --function-name order-processor --name prod \
    --function-version 3 \
    --routing-config '{"AdditionalVersionWeights":{"4":0.1}}'
永遠讓觸發器指向「別名」而不是 $LATEST。指向 $LATEST 的話，你一上傳程式碼全部流量立刻用新版，沒有金絲雀也沒有回退。指向別名就能控制切換節奏，出事把別名指回舊版本即可（秒級回退）。

4. 冷啟動與效能優化

冷啟動 = 下載程式碼 + 啟動執行環境 + 初始化你的程式

之後同一個環境的呼叫叫「暖啟動」，只跑 handler 內的程式碼
Runtime典型冷啟動
Python / Node.js100–400 ms
Go / Rust50–150 ms
Java / .NET1–10 秒（最嚴重）
+ 放在 VPC 內以前 +10 秒，現在幾乎無影響（Hyperplane ENI）
「Lambda 放進 VPC 會很慢」這個說法已經過時了。2019 年 AWS 改用 Hyperplane ENI 之後，VPC Lambda 的冷啟動額外開銷降到幾乎可以忽略。舊教材和舊考古題可能還在講 10 秒，那是錯的。

但仍要注意：VPC 內的 Lambda 沒有網際網路存取，除非放在有 NAT Gateway 的私有子網路，或建 VPC Endpoint。

降低冷啟動的六個方法

1
縮小部署包只打包必要的依賴。Python 用 --no-deps 挑選、Node.js 用 esbuild 打包。包越小下載越快。
2
調高記憶體CPU 跟著變多，初始化也變快。通常 512–1024 MB 是甜蜜點。
3
SDK client 放 handler 外暖啟動時就不用重建。
4
延遲載入不常用的模組只在需要時才 import 大型套件。
5
Provisioned Concurrency預先開好並保持暖機。完全消除冷啟動，但要付錢。
6
SnapStart（Java）把初始化後的狀態存快照，冷啟動降低約 90%。免費。
# Provisioned Concurrency：保持 5 個環境隨時待命
$ aws lambda put-provisioned-concurrency-config \
    --function-name order-processor --qualifier prod \
    --provisioned-concurrent-executions 5

# 配合 Auto Scaling 依時段調整（不然離峰也在付錢）
$ aws application-autoscaling register-scalable-target \
    --service-namespace lambda \
    --resource-id function:order-processor:prod \
    --scalable-dimension lambda:function:ProvisionedConcurrency \
    --min-capacity 2 --max-capacity 20
Provisioned Concurrency 是按「保持暖機的時間」收費，不管有沒有請求。
512 MB × 5 個環境保持一整月 ≈ US$18，這是在一般執行費用之外的支出。

先確認你真的需要：如果冷啟動只有 200ms 而你的 API 允許 1 秒回應，那不需要花這筆錢。只有對延遲極度敏感的使用者面向 API 才值得。
不要用「定時 ping 自己」來保溫。這是網路上常見但錯誤的做法：
  • 只能保溫一個執行環境，併發一上來還是會冷啟動
  • 污染日誌和監控指標
  • Provisioned Concurrency 才是正解

5. 併發模型與限流

併發數 = 每秒請求數 × 平均執行時間（秒）

每秒 100 次請求 × 每次 0.5 秒 = 50 個併發
每秒 100 次請求 × 每次 3 秒 = 300 個併發
類型意義用途
帳號併發上限每帳號每 region 預設 1,000可申請提高到數萬
Reserved Concurrency幫某支函式保留額度（也是它的上限）保護關鍵函式不被其他函式吃光額度
Provisioned Concurrency預先暖好的環境數消除冷啟動
Reserved Concurrency 是雙面刃。它同時是「保留」也是「上限」：
  • 設 100 → 這支函式保證有 100 個額度可用，其他函式搶不走
  • 但它也永遠不能超過 100，超過就被限流（回 TooManyRequestsException）
  • 設成 0 = 完全停用這支函式（緊急止血時很好用）
Reserved Concurrency 最重要的用途：保護下游資料庫。

Lambda 可以瞬間衝到 1000 個併發，但你的 RDS 只能承受 200 個連線。不設限的話，流量一來就把資料庫連線打爆，整個系統一起掛掉。

設 --reserved-concurrent-executions 50 就能確保最多只有 50 個 Lambda 同時連資料庫。 
$ aws lambda put-function-concurrency \
    --function-name db-writer --reserved-concurrent-executions 50

# 緊急停用某支失控的函式
$ aws lambda put-function-concurrency \
    --function-name runaway-func --reserved-concurrent-executions 0
更好的做法：用 RDS Proxy。它在 Lambda 和 RDS 之間做連線池，幾百個 Lambda 共用少量資料庫連線。這是「Lambda + RDS」架構的標準配置。
費用：每 vCPU 每小時 US$0.015（db.r6g.large 是 2 vCPU → 約 US$22/月）。

監控併發

6. 事件來源與觸發模式

模式來源失敗處理回傳值
同步API Gateway、ALB、直接 invoke不重試，錯誤直接回給呼叫方有
非同步S3、SNS、EventBridge自動重試 2 次，再失敗進 DLQ無
輪詢（Poll）SQS、Kinesis、DynamoDB Streams依設定重試，可設 DLQ無
這三種模式的失敗行為完全不同，設計時一定要分清楚。
  • 同步失敗 → 使用者立刻看到 500。要重試得靠呼叫方自己做
  • 非同步失敗 → AWS 幫你重試 2 次（間隔 1 分鐘、2 分鐘），之後訊息就消失了，除非有設 DLQ
  • 輪詢失敗 → 訊息回到佇列再被拿出來，可能無限重試，一定要設 maxReceiveCount
沒設 DLQ 的非同步 Lambda，失敗的資料就是永久遺失。 
# 非同步呼叫的失敗處理設定
$ aws lambda put-function-event-invoke-config \
    --function-name order-processor \
    --maximum-retry-attempts 2 \
    --maximum-event-age-in-seconds 3600 \
    --destination-config '{
      "OnFailure": { "Destination": "arn:aws:sqs:ap-northeast-1:123456789012:order-dlq" },
      "OnSuccess": { "Destination": "arn:aws:sns:ap-northeast-1:123456789012:order-done" }
    }'
Lambda Destinations 比傳統 DLQ 好。DLQ 只能收失敗的訊息，Destinations 可以同時處理成功和失敗，而且會附上完整的執行結果與錯誤內容（DLQ 只有原始事件）。新專案用 Destinations。

SQS 觸發的細節

$ aws lambda create-event-source-mapping \
    --function-name order-processor \
    --event-source-arn arn:aws:sqs:ap-northeast-1:123456789012:orders \
    --batch-size 10 \
    --maximum-batching-window-in-seconds 5 \
    --function-response-types ReportBatchItemFailures \
    --scaling-config '{"MaximumConcurrency": 50}'
ReportBatchItemFailures 一定要開，否則會重複處理成功的訊息。

預設行為：一批 10 筆，只要有一筆失敗，整批 10 筆都會重新送——包含已經成功處理的 9 筆。如果你的處理不是冪等的，那 9 筆就會被重複執行。

開啟後，程式可以回報「只有第 3 筆失敗」，AWS 就只重送那一筆： 
def handler(event, context):
    failures = []
    for record in event["Records"]:
        try:
            process(record)
        except Exception:
            failures.append({"itemIdentifier": record["messageId"]})
    return {"batchItemFailures": failures}
SQS 的 Visibility Timeout 必須大於等於 Lambda 的 timeout。建議設成 Lambda timeout 的 6 倍（AWS 官方建議）。

設太短的後果：Lambda 還在處理，訊息就重新出現在佇列被另一個 Lambda 拿走 → 同一筆訊息被處理兩次。

預設選 HTTP API——便宜 71%、延遲更低。只有在需要 API Key 計量、請求轉換、快取、WAF 這些功能時才用 REST API。

考題如果強調「成本最低的 API 方案」→ HTTP API；強調「需要 API 用量方案給不同客戶不同配額」→ REST API。
# ═══ 建立 HTTP API 並接上 Lambda ═══
$ API_ID=$(aws apigatewayv2 create-api \
    --name orders-api --protocol-type HTTP \
    --target arn:aws:lambda:ap-northeast-1:123456789012:function:order-processor \
    --query ApiId --output text)

# 允許 API Gateway 呼叫 Lambda（很多人漏掉這步）
$ aws lambda add-permission \
    --function-name order-processor \
    --statement-id apigw-invoke \
    --action lambda:InvokeFunction \
    --principal apigateway.amazonaws.com \
    --source-arn "arn:aws:execute-api:ap-northeast-1:123456789012:$API_ID/*/*"

# 設定限流（保護後端）
$ aws apigatewayv2 update-stage --api-id $API_ID --stage-name '$default' \
    --default-route-settings '{
      "ThrottlingBurstLimit": 200,
      "ThrottlingRateLimit": 100,
      "DetailedMetricsEnabled": true
    }'
API Gateway 一定要設限流。不設的話：
  • 惡意流量或程式錯誤會把 Lambda 併發吃光，連帶影響其他函式
  • 如果後面接 RDS，連線會被打爆
  • 而且你要付所有請求的錢——DDoS 攻擊會直接反映在帳單上
預設帳號層級是每秒 10,000 次，這對多數應用來說遠遠太高。
API Gateway 的整合逾時上限是 29 秒。就算 Lambda 設 15 分鐘，透過 API Gateway 呼叫超過 29 秒就會回 504。

長時間工作的正確做法：API 收到請求後立刻回 202 Accepted 和一個 job ID，把工作丟到 SQS 非同步處理，讓客戶端輪詢或用 WebSocket 通知。

Lambda Authorizer 記得開快取。不開的話每一個請求都會多呼叫一次 Lambda——延遲加倍、費用加倍。設 --authorizer-result-ttl-in-seconds 300，同一個 token 在 5 分鐘內只驗證一次。

經典架構：Fan-out

　　　　　　　　　　　　　┌──► SQS-庫存 ──► Lambda-扣庫存
訂單建立 ──► SNS Topic ──┼──► SQS-通知 ──► Lambda-寄信
　　　　　　　　　　　　　└──► SQS-分析 ──► Lambda-寫數倉

為什麼中間要放 SQS，不讓 SNS 直接觸發 Lambda？
  · Lambda 掛掉時訊息還在佇列裡，不會遺失
  · 每個下游可以用自己的速度處理（削峰）
  · 單一下游失敗不影響其他下游
  · 可以各自設定 DLQ 和重試策略
# 建立佇列 + DLQ（DLQ 幾乎是必要的）
$ DLQ_URL=$(aws sqs create-queue --queue-name orders-dlq --query QueueUrl --output text)
$ DLQ_ARN=$(aws sqs get-queue-attributes --queue-url $DLQ_URL \
    --attribute-names QueueArn --query 'Attributes.QueueArn' --output text)

$ aws sqs create-queue --queue-name orders \
    --attributes '{
      "VisibilityTimeout": "180",
      "MessageRetentionPeriod": "1209600",
      "RedrivePolicy": "{\"deadLetterTargetArn\":\"'$DLQ_ARN'\",\"maxReceiveCount\":\"3\"}"
    }'
沒設 DLQ 的 SQS 會無限重試「毒藥訊息」。一筆格式錯誤的訊息會被拿出來、失敗、回到佇列、再拿出來……一直到 14 天保留期滿為止。這段期間它會不斷消耗 Lambda 執行次數（你要付錢），而且可能塞住整個佇列。

設 maxReceiveCount: 3：失敗 3 次就丟進 DLQ，之後人工處理。

9. 冪等性：最常被忽略的坑

分散式系統的鐵律：訊息一定會被重複送達。
  • SQS Standard 是「至少一次」——設計上就會重複
  • Lambda 非同步呼叫失敗會自動重試 2 次
  • 網路逾時導致呼叫方重送，但實際上第一次已經成功了
  • Visibility Timeout 設太短造成同一訊息被兩個 consumer 拿走
如果你的 Lambda 是「扣款」或「發貨」，重複執行 = 重複扣錢、重複出貨。這是真的會發生的財務事故。
冪等 = 同一個操作執行 N 次，結果跟執行 1 次一樣

三種實作方式

# ── 方法 1：DynamoDB 條件寫入（最簡單，前面示範過）──
table.put_item(
    Item={"orderId": order_id, ...},
    ConditionExpression="attribute_not_exists(orderId)"
)
# 第二次會拋 ConditionalCheckFailedException → 捕捉後當成功回傳
# ── 方法 2：獨立的冪等表（適合複雜流程）──
import hashlib, time, boto3
from botocore.exceptions import ClientError

idem = boto3.resource("dynamodb").Table("IdempotencyKeys")

def already_processed(key: str, ttl_seconds: int = 86400) -> bool:
    """回傳 True 代表這個 key 之前處理過"""
    try:
        idem.put_item(
            Item={"key": key, "expiresAt": int(time.time()) + ttl_seconds},
            ConditionExpression="attribute_not_exists(#k)",
            ExpressionAttributeNames={"#k": "key"},
        )
        return False
    except ClientError as e:
        if e.response["Error"]["Code"] == "ConditionalCheckFailedException":
            return True
        raise


def handler(event, context):
    for record in event["Records"]:
        # 用訊息內容的雜湊當 key，不要用 messageId
        # （messageId 每次重送都不同，起不到去重作用）
        key = hashlib.sha256(record["body"].encode()).hexdigest()

        if already_processed(key):
            print(f"重複訊息，略過 {key[:12]}")
            continue

        do_the_actual_work(record)
用 IdempotencyKeys 表記得開 TTL（第 05 章講過），讓舊的 key 自動清掉，否則這張表會無限成長。TTL 設多久？比你的最大重試視窗長就好，通常 24 小時很夠。
# ── 方法 3：用官方的 Powertools（推薦，不用自己造輪子）──
$ pip install aws-lambda-powertools

from aws_lambda_powertools.utilities.idempotency import (
    DynamoDBPersistenceLayer, idempotent_function, IdempotencyConfig
)

persistence = DynamoDBPersistenceLayer(table_name="IdempotencyKeys")
config = IdempotencyConfig(event_key_jmespath="orderId", expires_after_seconds=86400)

@idempotent_function(data_keyword_argument="order",
                     config=config, persistence_store=persistence)
def process_order(order: dict):
    charge_credit_card(order)     # 保證只會執行一次
    return {"status": "charged"}
另一個相關的坑：Lambda 遞迴。
S3 上傳 → 觸發 Lambda → Lambda 寫回同一個 bucket → 又觸發 Lambda → …
這會無限迴圈，幾分鐘內產生數十萬次執行，帳單非常可觀。

防範方式：
  • 輸出寫到不同的 bucket（最簡單也最可靠）
  • 或用 prefix 過濾：只有 input/ 觸發，輸出寫到 output/
  • AWS 現在有 遞迴迴圈偵測，同一個請求鏈超過 16 次會自動中止並通知你——但這是最後一道防線，不要依賴它
  • 加 Reserved Concurrency 當保險絲

10. Step Functions 編排

當流程有多個步驟、需要判斷分支、需要重試、可能要等人工審核時，把邏輯寫在一支大 Lambda 裡會變成災難。Step Functions 把流程本身變成一個可視覺化、可追蹤的狀態機。

{
  "Comment": "訂單處理流程",
  "StartAt": "ValidateOrder",
  "States": {
    "ValidateOrder": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:...:function:validate",
      "Retry": [{
        "ErrorEquals": ["States.TaskFailed"],
        "IntervalSeconds": 2,
        "MaxAttempts": 3,
        "BackoffRate": 2.0
      }],
      "Catch": [{
        "ErrorEquals": ["ValidationError"],
        "Next": "RejectOrder"
      }],
      "Next": "CheckAmount"
    },
    "CheckAmount": {
      "Type": "Choice",
      "Choices": [{
        "Variable": "$.amount",
        "NumericGreaterThan": 10000,
        "Next": "ManualApproval"
      }],
      "Default": "ChargePayment"
    },
    "ManualApproval": {
      "Type": "Task",
      "人工審核：等待外部回呼，最長可等 1 年"
      "Resource": "arn:aws:states:::lambda:invoke.waitForTaskToken",
      "Parameters": {
        "FunctionName": "request-approval",
        "Payload": { "taskToken.$": "$$.Task.Token", "order.$": "$" }
      },
      "TimeoutSeconds": 86400,
      "Next": "ChargePayment"
    },
    "ChargePayment": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:...:function:charge",
      "Catch": [{ "ErrorEquals": ["States.ALL"], "Next": "CompensateOrder" }],
      "Next": "ShipOrder"
    },
    "ShipOrder": { "Type": "Task", "Resource": "...", "End": true },
    "CompensateOrder": { "Type": "Task", "Resource": "...:function:refund", "End": true },
    "RejectOrder": { "Type": "Fail", "Error": "ValidationError" }
  }
}
Step Functions 幫你解決的四件事：
  1. 重試與退避——不用自己寫 retry 邏輯，宣告式設定
  2. 錯誤補償（Saga 模式）——付款失敗時自動觸發退款
  3. 等待人工——waitForTaskToken 可以等到一年，遠超 Lambda 的 15 分鐘
  4. 視覺化執行歷史——主控台可以看到每一次執行走了哪些步驟、在哪裡失敗、輸入輸出是什麼
最後一點在排錯時價值極高——分散式系統最難的就是「知道發生了什麼」。
Standard 工作流程Express 工作流程
最長執行1 年5 分鐘
執行語意恰好一次至少一次
執行歷史完整保留只在 CloudWatch Logs
計費按狀態轉換次數（US$25/百萬）按執行時間（便宜很多）
適合長流程、需要稽核、人工審核高頻短流程（IoT、串流處理）
Standard 按「狀態轉換次數」計費——一個有 10 個步驟的流程跑一次 = 10 次轉換。
每天跑 10 萬次 × 10 步 = 每月 3000 萬次轉換 = US$750。

同樣的量用 Express 大約 US$30。高頻流程一定要評估 Express，但要接受「至少一次」語意（所以每一步都要冪等）。

12. 整合服務補充：MQ / AppFlow / SES

第 8 節講完 SQS / SNS / EventBridge 這組主力，但考試還會出現三個「特定情境才選」的整合服務。它們的共同點是：都有一個很明確的關鍵字，一出現就是它。

Amazon MQ受管的 ActiveMQ / RabbitMQ。支援 JMS、AMQP、MQTT、STOMP、OpenWire 等標準協定。
AppFlowSaaS 與 AWS 之間的免寫程式資料流。Salesforce、SAP、Slack、Zendesk、Google Analytics 等。
Amazon SES大量電子郵件收發。交易信、通知信、行銷信。

Amazon MQ vs SQS/SNS：只看「要不要改程式」

SQS / SNSAmazon MQ
協定AWS 專屬 API業界標準（JMS / AMQP / MQTT…）
擴展性幾乎無限、全受管受限於代理程式規格，要自己選機型
高可用天生跨 AZ要選 Active/Standby 部署
什麼時候選新開發的雲原生應用既有應用程式遷移上雲、不想改程式碼
Amazon MQ 的考題句型幾乎只有一種：「公司要把地端使用 ActiveMQ / RabbitMQ / JMS 的應用程式遷移到 AWS，希望盡量不修改應用程式碼」→ Amazon MQ。
如果題目允許改程式或是全新開發，答案就回到 SQS / SNS（更便宜、更好擴展、免維運）。判斷點是「既有協定」四個字。
陷阱：看到「訊息佇列」就選 SQS
只要題目提到 JMS、AMQP、MQTT、ActiveMQ、RabbitMQ 這些具體協定或產品名稱，就是 Amazon MQ。SQS 不支援這些標準協定，遷移過去必須改寫程式。

AppFlow：SaaS 資料流不用自己寫 Lambda

典型情境是「每天把 Salesforce 的訂單同步到 S3 / Redshift 做分析」。
傳統做法要寫 Lambda 呼叫 SaaS API、處理分頁、處理權杖更新、處理重試——AppFlow 把這些變成主控台上的設定。支援排程、事件觸發與隨選執行，傳輸中可做欄位對應、過濾與遮罩。
考題關鍵字：「SaaS 應用程式（Salesforce / SAP / Zendesk）的資料要進 AWS」＋「最少的開發工作」。

Amazon SES：寄信的正解

「應用程式要寄大量交易信或通知信」→ Amazon SES。
不要選 SNS 寄 email——SNS 的 email 訂閱是給告警通知用的純文字，沒有 HTML 範本、沒有退信處理、沒有信譽管理，不能拿來當產品的寄信管道。
EC2 上自己架郵件伺服器是錯誤選項。AWS 預設封鎖 EC2 的對外 25 埠，而且自架的 IP 幾乎一定進黑名單、信送不到。實務與考試的答案都是 SES。
另外 SES 新帳號預設在沙箱模式（只能寄給已驗證的地址、每日有限額），要正式使用必須申請解除——這個細節偶爾會出現在「為什麼信寄不出去」的題目裡。

事件路由、排程、SaaS 事件EventBridge

完整實作 Lab：事件驅動的訂單系統

約 110 分鐘。

這個 Lab 幾乎全部在免費額度內（Lambda、DynamoDB、SQS、SNS、EventBridge 都有永久免費額度）。
唯一風險是遞迴迴圈——階段五會故意做一次，記得照指示加上保險絲，並在觀察完後立刻停用。

階段一：Lambda 基礎

  1. 建立執行角色（基本執行權限 + 最小化的 DynamoDB 權限）
  2. 寫 order-processor，用 arm64、512 MB、timeout 30
  3. SDK client 放在 handler 外，用 JSON 結構化日誌
  4. 用 invoke 測試成功與失敗兩種情況
  5. 設定 log group 保留 14 天

階段二：API Gateway

  1. 建立 HTTP API 接上 Lambda
  2. 加 lambda add-permission（漏掉會 500）
  3. 設定限流：rate 100、burst 200
  4. 用 curl 打 API，確認回 201
  5. 用 hey -n 1000 -c 50 灌流量，觀察限流生效（429）

階段三：非同步與 DLQ

  1. 建立 SQS orders 與 orders-dlq，設 maxReceiveCount 3
  2. Visibility Timeout 設成 Lambda timeout 的 6 倍
  3. 建立 event source mapping，開啟 ReportBatchItemFailures
  4. 丟一筆格式錯誤的訊息，觀察它重試 3 次後進入 DLQ
  5. 丟一批 10 筆其中 1 筆壞的，驗證只有那 1 筆被重送

階段四：Fan-out

  1. 建立 SNS Topic，訂閱兩個不同的 SQS 佇列
  2. 各接一支 Lambda（一支寫 DynamoDB、一支只印日誌）
  3. 發一則訊息，確認兩支 Lambda 都被觸發
  4. 故意讓其中一支失敗，確認另一支不受影響

階段五：冪等性與遞迴（重點）

  1. 建立 IdempotencyKeys 表並開啟 TTL
  2. 在 Lambda 加上冪等檢查，同一筆訊息送三次，驗證只處理一次
  3. 先設 Reserved Concurrency = 2 當保險絲
  4. 建一個 S3 bucket，讓 Lambda 被上傳觸發並寫回同一個 bucket
  5. 上傳一個檔案，觀察遞迴發生，立刻把 Reserved Concurrency 設成 0 止血
  6. 改成「輸出寫到不同 bucket」，驗證問題解決

階段六：Step Functions

  1. 建立一個有 Choice 分支和 Retry 的狀態機
  2. 金額 > 10000 走人工審核分支，否則直接處理
  3. 加上 Catch → 補償（退款）步驟
  4. 在主控台觀察視覺化的執行歷史

驗收清單

  • API 回 201，重複送同一個 orderId 回 200 且不重複寫入
  • 灌流量時看得到 429 限流
  • 壞訊息重試 3 次後出現在 DLQ
  • 批次中只有壞的那筆被重送（看 CloudWatch Logs 的處理次數）
  • SNS 一則訊息 → 兩個佇列各收到一份
  • 同一訊息送 3 次，DynamoDB 只有 1 筆
  • 遞迴發生時 Reserved Concurrency 成功止住
  • Step Functions 主控台看得到走過的路徑與每步的輸入輸出

加碼挑戰

  1. 用 Lambda Power Tuning 測試 128 / 256 / 512 / 1024 / 2048 MB，找出成本最低的設定。
  2. 用 版本 + 別名 + routing-config 做一次 10% 金絲雀部署，然後回退。
  3. 建一個 EventBridge 規則，只有 amount > 10000 的事件才觸發，驗證小額訂單完全不會觸發 Lambda。
  4. 把 Standard 狀態機改成 Express，比較兩者的計費方式與執行歷史差異。
  5. 算一題：每月 3000 萬次請求、每次 512 MB 跑 300ms，Lambda + HTTP API 的月費是多少？跟 2 台 m7g.large + ALB 比呢？

本章重點回顧

  • Lambda 15 分鐘上限、6 MB 同步 payload、250 MB 解壓後大小、預設 1000 併發
  • 記憶體同時決定 CPU（1769 MB = 1 vCPU）——調高常常反而更便宜
  • SDK client 放 handler 外、用 JSON 日誌、失敗要 raise 不要吞
  • arm64 便宜 20%；觸發器指向別名不要指 $LATEST
  • 「VPC Lambda 冷啟動 10 秒」已經過時，但 VPC 內沒有網際網路
  • Reserved Concurrency 既是保留也是上限，設 0 = 緊急停用
  • Lambda + RDS 要用 RDS Proxy 做連線池
  • 三種呼叫模式失敗行為不同：同步不重試、非同步重試 2 次、輪詢可能無限重試
  • SQS 觸發一定要開 ReportBatchItemFailures，Visibility Timeout 設 Lambda timeout 的 6 倍
  • 沒設 DLQ 的佇列會無限重試毒藥訊息並持續燒錢
  • 選型：SQS 削峰、SNS 一對多、EventBridge 內容路由與排程
  • Fan-out 要在 SNS 和 Lambda 之間放 SQS，才不會掉訊息
  • 訊息一定會重複，扣款類的操作必須做冪等
  • Lambda 寫回觸發自己的 bucket 會遞迴爆炸——輸出寫不同 bucket
  • Step Functions 提供重試、補償、等待人工、視覺化歷史；高頻用 Express
  • Lambda 的 log group 預設永久保留，記得設保留期
