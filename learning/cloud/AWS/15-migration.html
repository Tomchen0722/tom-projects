1. 遷移的 7R 策略

搬家時每件家具你都要決定:直接搬走、換新的、修一修再搬、還是乾脆丟掉。7R 就是 AWS 幫每個應用程式做的這個決定。
① Rehost(重新託管)—— 俗稱 Lift & Shift

原封不動搬上 EC2,不改程式。最快、風險最低,但也最沒享受到雲的好處。大型遷移專案通常先全部 Rehost,上雲後再慢慢優化。

② Replatform(平台轉換)—— Lift, Tinker & Shift

搬的時候順手換掉一小塊,例如自建 MySQL 換成 RDS、自建 Tomcat 換成 Elastic Beanstalk。改動小、效益明顯,是實務上最常見的甜蜜點。

③ Refactor / Re-architect(重構)

打掉重寫成雲原生架構,例如單體改微服務、改成 Serverless。效益最高、成本與風險也最高,通常只對核心系統做。

④ Repurchase(重新購買)

不搬了,直接換成 SaaS。例如自建 CRM 改用 Salesforce、自建郵件改用 Microsoft 365。

⑤ Relocate(重新安置)

整個 VMware 環境搬到 VMware Cloud on AWS,不用改任何虛擬機。適合大量 VMware 資產的企業。

⑥ Retain(保留)

暫時不搬。可能因為法規、剛投資完硬體、或系統即將除役。

⑦ Retire(除役)

直接關掉。實務上盤點後常發現 10-20% 的系統根本沒人在用——這是遷移專案最快的省錢方式。

陷阱:題目怎麼暗示要選哪個 R?
• 「盡快搬完」「最少改動」「時間壓力大」→ Rehost
• 「想減少維運負擔但不想改程式」→ Replatform(例如換 RDS)
• 「要享受自動擴展與雲原生」「願意投入開發」→ Refactor
• 「大量 VMware 虛擬機」→ Relocate

2. 遷移三階段與對應工具

階段一:評估與探索 Assess Application Discovery Service └── 蒐集現有伺服器的規格、使用率、相依關係 └── 匯出 CSV,用來估算上雲後的 TCO 階段二:規劃與追蹤 Mobilize Migration Hub └── 一個地方看所有遷移工具的進度 └── 跨 DMS / MGN / 合作夥伴工具的統一儀表板 階段三:執行 Migrate 資料 → DataSync / Snow 家族 / Transfer Family 資料庫 → DMS(+ SCT 做異質轉換) 伺服器 → MGN(Application Migration Service)
📋 考試怎麼分辨這兩個「規劃類」服務:
• Discovery Service = 我還不知道機房裡有什麼 → 去「發現」
• Migration Hub = 我已經在搬了,要看進度 → 是「儀表板」
題目說「找出應用程式之間的相依關係」→ Discovery Service。

3. Snow 家族:實體搬運

當資料太多、網路太慢,AWS 會「寄一台加固的儲存設備給你」,你把資料倒進去再寄回 AWS。這聽起來很土,但幾百 TB 的資料用貨運真的比拉網路快得多。
裝置容量級距特色典型情境
SnowconeTB 級(最小)可手提、耐惡劣環境,可用電池供電無人機、車載、狹小空間的邊緣蒐集
Snowball Edge
Storage Optimized		約 80 TB 可用以儲存為主,附帶運算能力大量資料遷移(數十 TB 到 PB 級)
Snowball Edge
Compute Optimized		儲存較少以運算為主,可選配 GPU斷網環境的邊緣運算、影像分析、ML 推論
Snowmobile最高 100 PB一整台貨櫃拖車EB 級、整個資料中心搬遷
安全性防篡改外殼、256 位元加密(金鑰由 KMS 管理)、TPM 模組。AWS 收到後會執行軟體抹除。
追蹤電子墨水運送標籤自動更新,可用 SNS 或主控台追蹤狀態。
邊緣運算Snowball Edge 可跑特定 EC2 執行個體與 Lambda 函數,適合離線現場先處理再回傳。
叢集多台 Snowball Edge 可組成叢集,構成較大的臨時儲存空間。
陷阱:Snowball 選哪一款?
判斷順序很固定:
① 資料量 PB 級以上、整個機房 → Snowmobile
② 資料量 數十 TB 到數 PB → Snowball Edge Storage Optimized
③ 需要在現場運算(GPU、ML 推論、影像處理) → Snowball Edge Compute Optimized
④ 空間受限、要能手提、環境嚴苛 → Snowcone

看到「GPU」「斷線環境做機器學習」就選 Compute Optimized,不要看到大資料就反射選 Storage Optimized。

4. 線上傳輸:DataSync 與 Transfer Family

服務做什麼來源 / 目的考試關鍵字
DataSync自動化的大量檔案同步,內建加密、驗證、排程地端 NFS/SMB ↔ S3 / EFS / FSx持續同步、排程複製、比開源工具快很多
Transfer Family託管的 SFTP / FTPS / FTP 端點,背後直通 S3 或 EFS合作夥伴上傳 → S3題目直接出現 SFTP / FTP
Storage Gateway地端與雲端之間的常駐橋樑(見第 8 節)地端應用 ↔ S3 / Glacier混合雲、地端要保留快取
⚠️ 名稱已更新:白皮書寫的是「AWS Transfer for SFTP」。此服務已擴充並更名為 AWS Transfer Family,現在同時支援 SFTP、FTPS 與 FTP。考試用的是新名字。
陷阱:DataSync vs Storage Gateway
這兩個最容易混:
• DataSync = 一次性或排程的「搬運」。搬完就結束,地端不需要保留這份資料。
• Storage Gateway = 長期的「橋樑」。地端應用程式持續讀寫,雲端當作無限容量的後端。

題目說「遷移完成後地端就退役」→ DataSync;說「地端應用要繼續使用,但想把冷資料放雲端」→ Storage Gateway。
✅ DataSync 常考的加分點:內建資料完整性驗證、支援增量同步(只傳異動)、可設頻寬節流(避免佔滿公司對外網路)、可走 Direct Connect 或網際網路。題目提到「不能影響上班時間的網路」→ 頻寬節流 + 排程在離峰。

5. DMS:資料庫遷移

同質遷移 Homogeneous (同一種資料庫) Oracle → Oracle,MySQL → RDS MySQL 只需要 DMS 異質遷移 Heterogeneous (換一種資料庫) Oracle → Aurora PostgreSQL,SQL Server → MySQL 需要 SCT(Schema Conversion Tool) + DMS └── SCT 先轉換結構與預存程序 └── DMS 再搬資料
來源不中斷遷移期間來源資料庫維持可用,把停機時間壓到最低。
CDC 持續複製Change Data Capture:先做全量搬移,再持續同步異動,直到你決定切換。
可當複寫工具不只搬家,也能長期做跨區/跨引擎的持續複製。
可送進分析把交易資料庫的異動持續串流到 Redshift 或 S3,做即時分析。
陷阱:最小停機時間怎麼做?
標準答案是 DMS + CDC(持續複製):
① 先做 full load 把既有資料搬過去(此時來源照常運作)
② 開啟 CDC,持續同步新產生的異動
③ 選一個離峰時段,停掉應用、等最後幾筆同步完、把連線切到新資料庫

停機時間只有第 ③ 步的幾分鐘。看到「minimal downtime」「near-zero downtime」就是這個組合。

6. 伺服器與應用程式遷移

⚠️ 白皮書已過時之處:白皮書介紹的 AWS Server Migration Service(SMS) 已經淘汰,AWS 現在的主力是 AWS Application Migration Service(MGN)。若考題出現伺服器 Lift & Shift,答案應該是 MGN。白皮書適合理解「AWS 有伺服器遷移這類服務」,但服務名稱要更新。
服務用途特點
MGN
(Application Migration Service)		把地端/其他雲的伺服器 Lift & Shift 到 EC2持續區塊級複製,切換時停機極短;Rehost 的主力工具
DRS
(Elastic Disaster Recovery)		災難復原,不是遷移技術和 MGN 同源,但目的是「平常待命,出事時接手」
VMware Cloud on AWS整套 VMware 環境搬到 AWS對應 7R 的 Relocate,VM 不用轉換
Migration Hub跨工具的進度追蹤本身不搬東西,只是儀表板
陷阱:MGN vs DRS
兩者機制幾乎一樣,差在意圖:
• 題目說「把地端伺服器搬到 AWS」→ MGN
• 題目說「地端繼續運作,但要在 AWS 準備災難備援」→ DRS
關鍵字:migration / cutover → MGN;disaster recovery / RTO / RPO → DRS。

7. 動手算:該用網路還是 Snowball?

這是 SAA 很愛考的計算題,公式其實只有一條:

傳輸時間(小時) = 資料量(Gb) ÷ 頻寬(Gbps) ÷ 3600

※ 注意單位!TB 是 Byte,頻寬是 bit。
1 TB = 8,000 Gb(粗算用 1 Byte = 8 bit)
範例:要搬 100 TB,公司對外頻寬 500 Mbps(且只有一半可用於遷移)

① 資料量換算:100 TB × 8,000 = 800,000 Gb
② 可用頻寬:500 Mbps × 50% = 250 Mbps = 0.25 Gbps
③ 時間:800,000 ÷ 0.25 ÷ 3600 ≈ 889 小時 ≈ 37 天

→ 37 天顯然太久,而且整段期間會嚴重影響公司正常網路。
→ 結論:改用 Snowball Edge(通常一週內可完成往返)。

💡 考場上的快速判斷法(不用真的算):
• 資料量 < 10 TB 且頻寬還可以 → 走網路(DataSync)
• 資料量 10 TB ~ 幾百 TB,或算出來要好幾週 → Snowball Edge
• 資料量 PB 級以上 → Snowmobile
• 題目強調「頻寬有限」「不能影響現有業務網路」→ 幾乎都是 Snow 家族

8. 混合雲的資料橋樑

不是所有東西都要搬完。很多企業會長期維持「一腳在地端、一腳在雲端」,這時要用 Storage Gateway:

類型地端看起來像什麼用途
File GatewayNFS / SMB 網路磁碟檔案存到雲端 S3,地端保留熱資料快取
Volume GatewayiSCSI 區塊磁碟備份地端磁碟到雲端,可做快照
Tape Gateway虛擬磁帶櫃(VTL)用既有備份軟體,把磁帶備份改存到 S3 Glacier
✅ Tape Gateway 是很好認的送分題:只要題目提到「公司有既有的磁帶備份流程,不想改備份軟體,但想淘汰實體磁帶櫃」→ 一定是 Tape Gateway。
Direct Connect專線。頻寬穩定、延遲低,但要幾週到幾個月才申裝好。長期混合雲的標準做法。
Site-to-Site VPN走網際網路的加密通道。幾小時就能建好,常用來當 Direct Connect 的備援或過渡方案。
Outposts把 AWS 的機架直接放進你的機房,適合法規要求資料落地、或延遲極度敏感的場景。
DataSync over DXDataSync 可以走 Direct Connect,兼顧速度與不佔用公司對外頻寬。
陷阱:急著要專線怎麼辦?
題目說「Direct Connect 還要 3 個月才裝好,但下個月就要開始遷移」→ 答案是先用 Site-to-Site VPN 過渡,等專線好了再切換。這題常出現在混合雲與遷移的組合題。

10. 考試陷阱整理

陷阱 1:單位換算是計算題的唯一考點
TB 是 Byte,Mbps 是 bit。忘了乘 8 會算出小八倍的時間,然後選錯答案。這是最常見的失分點。
陷阱 2:DataSync 不是長期橋樑
「地端應用程式要持續存取」→ Storage Gateway,不是 DataSync。DataSync 是搬運工,搬完就走。
陷阱 3:異質遷移不能只用 DMS
Oracle → PostgreSQL 這種換引擎的情況,一定要先用 SCT 轉結構。只選 DMS 的選項是錯的,因為預存程序、觸發器、資料型別都需要轉換。
陷阱 4:Snowcone 容量很小
Snowcone 是 TB 級的小裝置,看到「幾十 TB」不要選它。它的賣點是體積小、能在惡劣環境運作,不是容量大。
陷阱 5:Migration Hub 不搬東西
它只是儀表板。題目問「用什麼工具執行遷移」時選它就錯了。它回答的是「怎麼追蹤遷移」。
陷阱 6:白皮書的服務名已更新
這份 2020 年的白皮書提到 AWS Server Migration Service(SMS) 與 AWS Transfer for SFTP,現行對應為 Application Migration Service(MGN) 與 Transfer Family。白皮書用來建立全貌很好用,但個別服務的現況請以 AWS 官方文件為準。
💡 一句話記憶法:
搬前先 Discovery,搬中看 Migration Hub;
搬檔案用 DataSync,搬資料庫用 DMS,搬伺服器用 MGN;
網路不夠快就寄 Snowball,不打算全搬就架 Storage Gateway。
