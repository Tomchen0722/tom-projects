1. ECS 核心架構階層與抽象模型

把 ECS 想成「AWS 幫你管的企業級 Docker 叢集」：你提供容器的建築藍圖（Task Definition），指派需要常態運行的服務規模（Service），ECS 負責排程排程運算節點、自動替換不良實例、無縫對接負載平衡器。
ECS Cluster（叢集邏輯邊界） ├── Capacity Providers（算力提供者） │ ├── Fargate / Fargate Spot（AWS 全託管算力池） │ └── Auto Scaling Group（EC2 虛擬機算力池） │ ├── Service（常態長時間運行的 Web / API 服務） │ ├── 維持 Desired Count（預期任務數，如 4） │ ├── 對接 Application Load Balancer (ALB) 進行健康檢查 │ ├── 執行 Rolling Update（滾動更新策略） │ └── 包含多個運行的 Tasks │ ├── One-off Tasks（一次性排程 / 批次任務） │ └── 由 EventBridge Cron、Step Functions 或手動 `RunTask` 呼叫執行 │ └── Task Definition（任務藍圖，不可變 Versioning） ├── 容器映像路徑（ECR / Docker Hub） ├── CPU 與 Memory 資源配額（Hard / Soft limit） ├── 網路模式（awsvpc / bridge / host / none） ├── IAM 角色繫結（Task Role vs Task Execution Role） └── 外部資源掛載（EFS Volumes / Secret 注入）
Cluster運算與資源排程的邏輯邊界。跨 AZ 分散，可同時容納 Fargate 與 EC2 兩種類型的運算節點。
Task Definition應用程式的不可變藍圖。每次修改配置（如更換映像版本）都會自動遞增修訂版本號（如 `app:1`, `app:2`）。
TaskTask Definition 的單一執行實例。在 Fargate 下擁有獨立的虛擬網卡（ENI）與私有 IP。
Service維護指定數量 Task 的排程器。負責健康檢查、自動自癒、滾動更新與 ALB 註冊卸載。

2. Task Definition 關鍵參數與生產級 JSON 語法

在 SAA-C03 考試中，Task Definition 的參數配置直接關係到高可用性、資安審計與容器運算效能。以下為核心關鍵參數解析：

參數名稱所屬層級功能說明考試核心重點
networkMode Task 層級 定義容器網路堆疊。可選 awsvpc、bridge、host、none。 Fargate 強制要求只能使用 awsvpc；EC2 Launch Type 才能選 bridge 或 host。
cpu / memory Task 或 Container Task 層級定義整組任務上限；Container 層級可定義個別容器保留量。 Fargate 必須在 Task 層級明確指定。256 CPU units = 0.25 vCPU。記憶體設太小會觸發 OOM (137)。
taskRoleArn Task 層級 容器內業務代碼呼叫 AWS 服務時所使用的 IAM 角色。 例如代碼需要 s3:PutObject 或 dynamodb:GetItem，由 Task Role 授權。
executionRoleArn Task 層級 ECS Agent 基礎設施所需的 IAM 角色。 負責從 ECR 拉取映像檔、將日誌寫入 CloudWatch、從 Secrets Manager 讀取密碼。
secrets Container 層級 從 AWS Systems Manager Parameter Store 或 Secrets Manager 動態注入環境變數。 絕不在 Task Definition 明文寫入資料庫密碼。考試唯一推薦的最佳實踐做法。
logConfiguration Container 層級 日誌收集驅動程式。主流為 awslogs（CloudWatch）與 awsfirelens（Fluent Bit）。 日誌跨帳號聚合或傳送至 S3 / OpenSearch / Splunk 時，標準答案為 FireLens。
essential Container 層級 布林值。標記此容器是否為關鍵核心容器。 若標記為 essential 的容器崩潰或結束，整個 Task 下的所有其他容器都會被強制停止。
readOnlyRootFilesystem Container 層級 設定根檔案系統為唯讀，防止容器運行時遭到篡改注入惡意二進位檔。 現代 DevSecOps 與 CIS 基準強烈推薦，可搭配 tmpfs 或 EFS 掛載可寫目錄。

生產等級 Task Definition JSON 範例

{ "family": "order-api-prod", "networkMode": "awsvpc", "requiresCompatibilities": ["FARGATE"], "cpu": "1024", "memory": "2048", "taskRoleArn": "arn:aws:iam::123456789012:role/OrderApiTaskRole", "executionRoleArn": "arn:aws:iam::123456789012:role/ecsTaskExecutionRole", "containerDefinitions": [ { "name": "app", "image": "123456789012.dkr.ecr.ap-northeast-1.amazonaws.com/order-api:v2.4", "essential": true, "portMappings": [ { "containerPort": 8080, "protocol": "tcp" } ], "secrets": [ { "name": "DB_PASSWORD", "valueFrom": "arn:aws:secretsmanager:ap-northeast-1:123456789012:secret:prod/rds/password-AbCdEf" } ], "environment": [ { "name": "APP_ENV", "value": "production" } ], "logConfiguration": { "logDriver": "awslogs", "options": { "awslogs-group": "/ecs/order-api-prod", "awslogs-region": "ap-northeast-1", "awslogs-stream-prefix": "app" } }, "healthCheck": { "command": ["CMD-SHELL", "curl -f http://localhost:8080/health || exit 1"], "interval": 30, "timeout": 5, "retries": 3, "startPeriod": 60 } } ] }
考試高頻陷阱：Task Role vs Task Execution Role 混淆
• Task Role：給容器內的 Python / Java 程式存取 S3 Bucket、讀寫 DynamoDB。
• Task Execution Role：給 AWS 底層 ECS Agent 用的！如果在部署時報錯 CannotPullContainerError 或 Fetching secret failed，必定是 Task Execution Role 缺少 ECR 讀取權限或 Secrets Manager / KMS 解密權限！

3. Fargate vs EC2 Launch Type 深度決策

EC2 Launch Type 就像「自己買貨車」：你需要定期保養、更換機油（作業系統修補、ECS Agent 更新）、計算車位裝載率；Fargate 則是「無人機配送」：你只需給出包裹尺寸（CPU/RAM），AWS 保證送達，底層硬體與虛擬化完全隱形。
架構決策維度AWS Fargate（無伺服器容器）EC2 Launch Type（虛擬機自管）
維運負擔 (Ops Overhead) 接近零：無須管理 AMI、無須打 OS 補丁、無須管理 ECS Agent。 高：需自管 EC2 容量規劃、Auto Scaling Group、OS 安全更新、Agent 升級。
網路模式限制 僅支援 awsvpc。每個 Task 綁定獨立 ENI 與專用私有 IP。 支援 awsvpc、bridge（動態埠映射）、host、none。
硬體特化需求（GPU） ❌ 不支援 GPU 加速運算。 ✅ 支援。可搭配 G4dn / P4d 等 GPU 實例進行深度學習推論與訓練。
底層主機存取（SSH） ❌ 無底層作業系統可供 SSH 連線。僅能透過 ECS Exec 進入容器層。 ✅ 可以透過 SSH 或 SSM Session Manager 登入底層 EC2 Host。
極大規格容器 最大支援 16 vCPU 與 120 GB RAM（或自訂上限）。 可使用極高規格實例（如 128 vCPU、1TB+ RAM 的 x2gd / u-6tb1）。
計費模型與成本結構 按每個 Task 所請求的 vCPU 與記憶體秒數計費。 按底層 EC2 Instance 運行的整機時間計費，不管上面 Task 是否跑滿。
高密度併發成本效益 平穩高併發長期運行時，單元成本通常高於飽和運行的 EC2。 將大量小型 Task 高密度打包（Binpack）進少數 EC2 時，性價比極高。
考試情境關鍵字 「無伺服器」、「最小化維運管理負擔」、「突發或間歇性負載」。 「需要 GPU 加速」、「自訂核心模組」、「既有 EC2 預留合約 (RI)」。
決策速記口訣：
  • 題目出現「Minimal operational overhead（最小維運成本）」且為容器化 → 秒選 Fargate。
  • 題目出現「GPU / Machine Learning Inference on Containers」→ 秒選 EC2 Launch Type。

4. ECS IAM 三層角色與權限模型

ECS 的權限架構分為三個明確獨立的層級。理解這三層是通過 SAA-C03 架構設計題目的必備知識：

層級 ①：EC2 Instance Profile (僅 EC2 Launch Type) └── 綁定在底層 EC2 虛擬機本體。 ECS Agent 用此憑證與 ECS Control Plane 握手、註冊 Cluster、發送健康心跳。 必備受管政策：AmazonEC2ContainerServiceforEC2Role 層級 ②：Task Execution Role (Fargate 與 EC2 皆需要) └── 綁定在 Task Definition 的 executionRoleArn。 授權 ECS 平台底層執行啟動前準備工作： ├── 從 Amazon ECR 驗證並拉取私有映像檔 (ecr:GetDownloadUrlForLayer 等) ├── 將容器 stdout / stderr 寫入 CloudWatch Logs (logs:CreateLogStream, PutLogEvents) └── 啟動時從 Secrets Manager / SSM 解密敏感金鑰 (secretsmanager:GetSecretValue, kms:Decrypt) 層級 ③：Task Role (業務代碼實際身份) └── 綁定在 Task Definition 的 taskRoleArn。 授權 容器內部執行的程式碼存取 AWS 雲端資源： ├── 後端 API 讀取 S3 儲存貯體中的訂單報表 (s3:GetObject) ├── 寫入審計日誌至 DynamoDB (dynamodb:PutItem) └── 發送異步任務到 SQS 佇列 (sqs:SendMessage)
陷阱：EC2 Instance Profile 絕不能替代 Task Role！
如果在 EC2 Launch Type 下，開發者偷懶把 S3 的讀取權限直接給了 EC2 Instance Profile，這意味著跑在這台 EC2 上的所有 Task（即使屬於不同專案或不同客戶）都能藉由 Instance Metadata (IMDS) 拿到這個 S3 權限，嚴重違反最小權限原則！正確做法是一律在 Task Definition 內給予獨立的 Task Role。

5. 網路模式與 ALB 整合（動態埠映射 vs awsvpc）

容器如何接通外界網路？ECS 支援四種網路模式，其中最核心的兩大對比為 bridge 與 awsvpc：

比較項目bridge 模式（搭配 EC2）awsvpc 模式（Fargate 強制 / EC2 可選）
網路拓撲架構 多容器共享宿主機（Host）的單一網路介面與 IP，透過 Docker Bridge 轉發。 每個 Task 獲取專屬的 Elastic Network Interface (ENI) 與私有 VPC IP。
Port 埠號衝突問題 若兩 Task 都想監聽 8080，同台 EC2 會衝突。必須使用動態埠映射 (Dynamic Port Mapping)。 絕無埠號衝突。每個 Task 有獨立 IP，所有 Task 都可以直接綁定 8080。
ALB Target Group 類型 Target Type 必須設為 instance。由 ALB 自動對接動態 High Port。 Target Type 必須設為 ip。ALB 直接轉發流量至 Task 的 ENI IP。
Security Group 套用對象 套用在 EC2 Instance 上。防火牆規則必須開放大範圍高位埠（32768–65535）。 套用在 Task 專屬的 ENI 上。只需精準放行容器實際埠（如 8080）。安全性極高！

架構對比圖：ALB 路由如何運作

【情境 A：EC2 + bridge 模式 + 動態埠映射】 ALB (Public) └── Target Group (Target Type: instance) ├── EC2-A (10.0.1.10) : Port 32768 → 轉發至 Task 1 (Container Port 8080) ├── EC2-A (10.0.1.10) : Port 32769 → 轉發至 Task 2 (Container Port 8080) └── EC2-B (10.0.1.11) : Port 32768 → 轉發至 Task 3 (Container Port 8080) * 注意：Task Definition 的 hostPort 必須設為 0，Docker 才會自動隨機分配 32768-65535。 【情境 B：Fargate + awsvpc 模式 + IP 模式】 ALB (Public) └── Target Group (Target Type: ip) ├── ENI-1 (10.0.1.50) : Port 8080 (Task 1 直通) ├── ENI-2 (10.0.1.51) : Port 8080 (Task 2 直通) └── ENI-3 (10.0.2.70) : Port 8080 (Task 3 直通，跨 AZ)

6. Task Placement 策略與約束（EC2 專用）

當使用 EC2 Launch Type 時，你擁有數十台 EC2 實例構成的叢集。新 Task 該放在哪一台機器？當需要關閉機器時先殺哪一台？這由 Placement Strategies（排程策略） 與 Placement Constraints（約束條件） 決定：

策略類型 (Strategies)演算法運作邏輯核心優勢典型使用場景
binpack 優先把機器塞滿！依據剩餘 CPU 或 Memory，將 Task 塞入剩餘空間最小的主機。 極大化節省成本。讓未使用的 EC2 騰出空位，以便 Auto Scaling 縮容並終止機器。 成本敏感型批次計算、開發測試環境。
spread 均勻分散！依據指定的維度（如 attribute:ecs.availability-zone 或 instanceId）平均打散。 極大化高可用性 (HA)。避免單一可用區或單一機器故障導致所有容器癱瘓。 生產環境 Web / API 核心服務（SAA 考試首選）。
random 完全隨機挑選合適的可用實例放置。 排程速度極快，無須運算全局負載分佈。 短暫的一次性任務或測試任務。

五星考點：組合策略 (Strategy Chaining)

經典生產架構配置：
1. 先依 AZ 平均打散（高可用）：spread(attribute:ecs.availability-zone)
2. 再依實例打散（防止單機故障）：spread(instanceId)
3. 最後依記憶體緊湊打包（節省成本）：binpack(memory)

Placement Constraints（硬性約束條件）

distinctInstance每個 EC2 實例上最多只能運行該 Task 的一個副本。防止多個相同的 Task 擠在同一台機器。
memberOf使用 Cluster Query Language 篩選。例如只部署在指定標籤的主機：attribute:ecs.instance-type =~ t3.*。
💡 考試記憶：Fargate 不支援 Task Placement Strategies！
因為 Fargate 底層根本沒有「EC2 實例」的概念供你挑選，AWS 會自動為你在多個 AZ 間做高可用排程。

7. Fargate + EFS 持久化儲存掛載

容器天生是無狀態（Stateless）且短暫短命（Ephemeral）的。一旦 Task 被重啟，容器內寫入的資料就會隨之消失。如何在無伺服器 Fargate 下實現有狀態（Stateful）持久化儲存？

Fargate Task 1 (AZ-A) ──┐ ├──掛載 NFS4.1──→ Amazon EFS (跨 AZ 彈性檔案系統) Fargate Task 2 (AZ-B) ──┘ ├── POSIX 權限控制 ├── EFS Access Points (隔離目錄) └── 支援數千個 Task 同時讀寫
儲存方案支援 Fargate?跨 Task 共享讀寫生命週期與特性
Ephemeral Storage ✅ 支援（預設 20GB，最高可調至 200GB） ❌ 無法跨 Task 共享 生命週期隨 Task 結束而銷毀。用於暫存暫存檔、快取。
Amazon EFS ✅ 完全支援 ✅ 支援多 AZ 併發讀寫 (ReadWriteMany) 獨立於 Task 的完全持久儲存。支援 WordPress 上傳目錄、機器學習共享資料集。
Amazon EBS ❌ 不支援直接掛載為標準 Volume ❌ 只能單掛載 (ReadWriteOnce) 僅 EC2 Launch Type 才能掛載本機 EBS。
EFS + Fargate 安全最佳實踐考點：EFS Access Point
將 EFS 掛載至 Fargate 時，強烈建議啟用 EFS Access Point。它可以：
1. 強制設定 POSIX 使用者身份（UID/GID），避免容器以 root 身份寫入惡意檔案。
2. 將容器限制在 EFS 的特定子目錄，防止容器越權存取檔案系統根目錄。

8. ECS 滾動部署與更新百分比運算

當你在 ECS Service 更新映像版本時，ECS 會採用滾動更新（Rolling Update）。如何控制部署期間的容量與停機時間？完全由這兩個關鍵參數決定：

minimumHealthyPercent = 部署過程中，健康 Task 數量不得低於 Desired Count 的百分比。
maximumPercent = 部署過程中，允許運行的 Task 總數不得超過 Desired Count 的百分比。
場景設定 (Desired = 4)最低健康數最高允許數部署過程行為剖析適用場景
min: 100%, max: 200%
（標準零停機）		 4 × 100% = 4 台 4 × 200% = 8 台 先啟動 4 個新版本 Task，等 ALB 健康檢查通過後，再一次停掉 4 個舊版本 Task。服務容量永不縮水。 生產環境標準配置，確保高可用零停機。需足夠的 IP 或 EC2 餘量。
min: 50%, max: 100%
（資源節約型）		 4 × 50% = 2 台 4 × 100% = 4 台 先停掉 2 個舊 Task（容量降為 2），騰出名額啟動 2 個新 Task；待新 Task 健康後，再替換剩餘 2 個。 硬體資源受限（如固定 4 台 EC2 無法加開新機器），允許部署期間吞吐降載。
min: 0%, max: 100%
（先全停再啟動）		 4 × 0% = 0 台 4 × 100% = 4 台 先把 4 個舊版本全部強制終止，然後一次啟動 4 個新版本。部署期間服務完全中斷！ 開發測試環境、或資料庫 Migration 不允許新舊版本同時並存的系統。
考試算術題速解：
如果題目問：「現有 4 個 Task，要求部署時服務容量絕不能降到 4 個以下，且因為預算考量，同時運行的 Task 最多只能有 6 個，該如何設定？」
→ minimumHealthyPercent = 100% (至少 4 個)，maximumPercent = 150% (最多 4 × 1.5 = 6 個)！

9. ECS Service Auto Scaling 與 Capacity Provider

ECS 擁有兩個維度的自動擴展：Task 層級擴展 與 底層算力擴展 (Capacity Provider)。

【維度 1：Task 數量擴展 (Application Auto Scaling)】 監控指標： ├── ALBRequestCountPerTarget：每個 Task 的每分鐘 HTTP 請求數（如目標 1000 Req/min） ├── ECSServiceAverageCPUUtilization：平均 CPU 使用率（如目標 70%） └── ECSServiceAverageMemoryUtilization：平均記憶體使用率 擴展策略模式： ├── Target Tracking Scaling（目標追蹤，推薦）：設定理想數值，AWS 自動計算增減數量 ├── Step Scaling（階梯擴展）：根據 CloudWatch Alarm 閾值幅度（如 >80% 加 2 台，>90% 加 4 台） └── Scheduled Scaling（排程擴展）：固定每週一早上 9:00 預先擴展 【維度 2：算力提供者策略 (Capacity Provider Strategy)】 結合 Fargate 與 Fargate Spot 達成 70% 費用節省： base: 2, weight: 1 (FARGATE) ← 保證至少 2 個高可用任務跑在穩定 Fargate base: 0, weight: 4 (FARGATE_SPOT) ← 超過 2 個以後，80% 的擴容採用 Spot 實例
Fargate Spot 中斷處理考點：SIGTERM 與 Graceful Shutdown
當 AWS 需要回收 Spot 算力時，會向容器發送 SIGTERM 信號，並給予 2 分鐘（120 秒）的終止倒數通知（可透過 EventBridge 監聽 ECS Task State Change）。應用程式必須攔截 SIGTERM，拒絕新連線、跑完處理中的連線，然後主動退出。ECS Service 會自動在標準 Fargate 或其他 Spot 算力上拉起新 Task。

10. ECS Exec 深度除錯：免跳板機穿透 Private 容器

在過去，如果私有子網路（Private Subnet）中的容器出現故障，維運人員必須透過 Bastion Host（跳板機）開 SSH，甚至必須在容器中安裝 SSH Daemon，這極不安全且違反容器不可變原則。ECS Exec 徹底解決了這個問題！

工程師本機 (AWS CLI) ↓ `aws ecs execute-command --interactive` AWS Systems Manager (SSM) Session Manager ← 經由 TLS 加密通道，免開 Port 22！ ↓ 透過 VPC Endpoint (PrivateLink) 直通 Private Subnet 內的 Fargate / EC2 Task └── 容器內自動掛載的 SSM Agent 二進位檔直接開啟 bash / sh 會話！
啟用 ECS Exec 的四大必要條件具體配置細節常見報錯原因
1. Task Role 權限 Task Role 必須允許 ssmmessages:* 動作。 權限誤加到 Task Execution Role。
2. 網路連通性 Private Subnet 必須具備 NAT Gateway，或配置 SSM 相關的 VPC Endpoints。 私有網路無法連通 ssmmessages.region.amazonaws.com。
3. Service / Task 開啟旗標 在建立或更新 Service 時，必須加上參數 --enable-execute-command。 預設為關閉狀態，未開啟前無法 exec。
4. 稽核日誌記錄 可以在 Cluster 層級配置，將工程師在容器內執行的所有指令上傳至 S3 或 CloudWatch Logs。 企業合規審計必備條件。

12. ECS 生產常見故障診斷手冊

常見錯誤代碼 / 現象根本原因剖析標準排查與修復措施
CannotPullContainerError 1. ECR 映像檔路徑拼錯或 Tag 不存在。
2. Task Execution Role 缺少 ECR 存取權限。
3. Fargate 運行在 Private Subnet 但沒有 NAT Gateway 也沒有 ECR 的 VPC Endpoints。		 檢查 Task Execution Role 政策；確認私網到 ECR 的網路連通性（開通 ecr.dkr, ecr.api, s3 Gateway Endpoint）。
Exit Code 137 (OOMKilled) 容器記憶體用量超過了 Task Definition 中定義的上限，遭 Linux 核心 OOM-Killer 強制終止。 檢視 CloudWatch Container Insights 記憶體用量曲線；調大 Task Definition 的 memory 配額或排查應用程式記憶體洩漏。
Task failed ELB health checks 容器成功啟動，但在指定時間內未能通過 ALB Target Group 的 HTTP 健康檢查（如連線超時或回傳 500）。 調大 Target Group 的 HealthCheckGracePeriodSeconds（啟動寬限期）；檢查容器 Security Group 是否放行 ALB 的流量；測試 /health 端點。
Essential container in task exited 標記為 "essential": true 的主容器因代碼異常或缺少環境變數主動退出，導致整個 Task 被銷毀。 執行 aws ecs describe-tasks 查看 containers[].reason 與退出碼；到 CloudWatch Logs 查看容器崩潰日誌（Stack trace）。

13. SAA-C03 考試陷阱與考題關鍵字速查

陷阱 1：Fargate 儲存大小的限制
題目問「需要在無伺服器 Fargate 上處理 80GB 的大型影片暫存檔」→ 預設 Fargate 只有 20GB，但 Task Definition 中可以擴增 ephemeralStorage 最高至 200GB！若超過 200GB 則必須掛載 Amazon EFS。
陷阱 2：ECS Anywhere 混合雲概念
題目問「如何使用同一套 AWS ECS API 與控制台，統一調度部署在客戶地端機房（On-Premises）實體伺服器上的容器」→ 答案秒選 ECS Anywhere。地端伺服器需安裝 AWS Systems Manager Agent 與 ECS Agent。
陷阱 3：健康檢查雙層架構
• Container Health Check：在 Task Definition 內部定義（例如用 CMD-SHELL curl 測試），由 Docker / ECS 監控。
• ALB Target Group Health Check：從外部測試 HTTP 端點。
如果只有 ALB 的健康檢查失敗，ECS Service 會移除該 Target 並重啟新 Task。
🎯 速記天條：
• 無伺服器容器首選 → AWS Fargate
• 容器持久多讀寫共享檔案系統 → Amazon EFS
• 容器極大化省成本部署 → Placement Strategy: binpack
• 微服務內部低延遲尋址 → AWS Cloud Map (Service Discovery)
• 敏感密鑰安全傳入容器 → Task Definition Secrets 參照 Secrets Manager
