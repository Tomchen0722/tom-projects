1. ECS 架構概覽

把 ECS 想成「AWS 幫你管的 Docker Compose 升級版」：你告訴 AWS 要跑什麼容器、要幾個，AWS 負責找機器、排程、監控健康狀態。
Cluster（叢集） ├── Service（服務） ← 維持 N 個 Task 持續運行 │ ├── Task（任務） ← 一次性工作（批次處理） │ └── Task（任務） ← 一個以上容器的組合 └── Task Definition（任務定義） ← 藍圖（不是跑起來的東西） ├── 映像 URI ├── CPU / 記憶體 ├── 環境變數 / Secrets └── 網路模式（awsvpc / bridge / host）
Cluster資源的邏輯邊界，可包含多個 Service 和 Task。EC2 Launch Type 時，EC2 Instance 也在 Cluster 裡。
Task Definition不可變的藍圖（有版本號），定義「要跑什麼」；每次修改產生新版本。
TaskTask Definition 的一個執行實例。Fargate 時每個 Task 有自己的獨立 ENI（彈性網路介面）。
Service確保指定數量的 Task 持續運行，支援 Rolling Update、Auto Scaling、與 ALB 整合。

2. Task Definition 關鍵參數

參數說明考試重點
Network Modeawsvpc：每個 Task 獨立 ENI（Fargate 強制）
bridge：共享 Host 的 ENI（EC2 Launch Type，動態埠映射）
host：直接用 Host 的網路介面		Fargate = 只能 awsvpc；EC2 = 三種都可以
Task Role容器內的應用程式 call AWS API 用的 IAM Role（如 S3、DynamoDB）這是授予應用程式的權限
Task Execution RoleECS Agent 代替你拉映像、送日誌用的 Role（AmazonECSTaskExecutionRolePolicy）這是授予 ECS 基礎設施的權限
Secrets從 SSM Parameter Store 或 Secrets Manager 注入環境變數，不用硬編碼需要 Task Execution Role 有讀取 SSM/SM 的權限
CPU/記憶體Fargate 需要在 Task Definition 指定（256 CPU 單位 = 0.25 vCPU）設太小會有 OOM；設太大浪費錢
Log Driverawslogs：送到 CloudWatch Logs；awsfirelens：送到 Fluent Bit（可轉到 Splunk、Kinesis 等）FireLens 是 log aggregation 的標準答案
陷阱：Task Role vs Task Execution Role
Task Role = 你的應用程式要存取 DynamoDB，設這個。
Task Execution Role = ECS 要從 ECR 拉映像或從 SSM 拿密鑰，設這個。
考試題常混淆兩者！

3. Fargate vs EC2 Launch Type

特性FargateEC2 Launch Type
基礎設施管理AWS 全管（無伺服器）你管 EC2 Instance（打補丁、容量規劃）
計費按 Task 使用的 vCPU + 記憶體，精確到秒按 EC2 Instance 計費（不管 Task 是否跑滿）
成本低流量時更貴（每個 Task 獨立計費）高密度 Task 時更划算（Instance 可塞很多 Task）
GPU 支援❌（Fargate 不支援 GPU Task）✅（用 GPU Instance 如 g4dn）
Windows Container✅ 支援✅ 支援
Network Mode只能 awsvpcawsvpc / bridge / host
ECS AgentAWS 管（你看不到）需在 EC2 安裝 ECS Agent
適合情境無伺服器、Dev/Test、不確定流量GPU 工作負載、需要自訂 AMI、高密度部署
Fargate 像叫 Uber（隨叫隨到，依趟計費）；EC2 Launch Type 像買一輛車（固定成本，自己管保養，但每公里成本更低）。

4. ECS IAM 三層角色

① EC2 Instance Profile （只有 EC2 Launch Type 才有） └── EC2 Instance 本身需要的權限 ECS Agent 用這個 Role 向 ECS Control Plane 回報 需要：AmazonEC2ContainerServiceforEC2Role ② Task Execution Role （Fargate + EC2 都需要） └── ECS 基礎設施的權限 拉 ECR 映像、送 CloudWatch 日誌、讀 SSM/Secrets Manager 需要：AmazonECSTaskExecutionRolePolicy ③ Task Role （你的應用程式需要的權限） └── 應用程式 call AWS API 的權限 如：S3 GetObject、DynamoDB PutItem、SQS SendMessage 自訂，按最小權限原則設定
💡 最小權限原則：Task Role 只給應用程式實際需要的最小 IAM 權限。不要用 AdministratorAccess！

5. ECS + ALB 動態埠映射

EC2 Launch Type 的動態埠映射

bridge 網路模式下，多個 Task 可以在同一個 EC2 Instance 上用不同的隨機 Host Port 運行同一個容器（容器 Port 固定，Host Port 動態分配）。ALB Target Group 用 Instance 模式，會追蹤動態分配的埠。

EC2 Instance ├── Task 1: Container Port 8080 → Host Port 32768 ├── Task 2: Container Port 8080 → Host Port 32769 └── Task 3: Container Port 8080 → Host Port 32770 ALB → Target Group (Instance 模式) → 自動知道每個 Task 的 Host Port

Fargate 的 IP 模式

Fargate 每個 Task 有獨立 ENI（有自己的私有 IP）。ALB Target Group 用 IP 模式，直接指向 Task 的私有 IP。不需要動態埠映射。

陷阱：EC2 Launch Type 的 Security Group
EC2 Launch Type（bridge 模式）：Security Group 設在 EC2 Instance 上，允許 ALB 到 EC2 的任意高位埠（32768-65535）。
Fargate（awsvpc 模式）：Security Group 設在 Task 的 ENI 上，允許 ALB 到 Task 的容器埠（如 8080）。更安全！

6. Capacity Provider 與 Fargate Spot

類型說明折扣適合場景
Fargate標準 Fargate，任何時候可用無生產環境，需要穩定性
Fargate Spot利用 AWS 閒置容量，隨時可能被中斷（2 分鐘通知）最高 70%批次處理、CI/CD、可重試的工作
Auto Scaling Group
(EC2)		EC2 Auto Scaling 與 ECS Cluster 整合，自動增減 EC2依 EC2 類型需要 GPU、高密度工作負載

Capacity Provider Strategy（混合策略）

Service 設定：
FARGATE: base=1, weight=1 ← 至少維持 1 個穩定 Task
FARGATE_SPOT: weight=4 ← 其餘 Task 盡量用 Spot（70% 折扣）

最終效果：1 個穩定 + 80% 的擴充都用 Spot
Fargate Spot 中斷處理
AWS 會給 2 分鐘停機通知（SIGTERM 信號）。你的應用必須實作 Graceful Shutdown：收到 SIGTERM 後停止接受新請求、完成進行中的請求、退出。ECS Service 會自動啟動新的替換 Task。

7. 服務探索（Service Discovery）

微服務之間需要互相找到對方。在 ECS 裡有幾種方式：

方法機制適合場景
ALB / NLB固定 DNS（ALB 的 DNS Name），服務透過 Load Balancer 互訪HTTP 服務的南北向流量（外部到內部）
AWS Cloud Map
(ECS Service Discovery)		自動在 Route 53 Private Hosted Zone 登記 Task 的 IP（SRV/A 記錄），服務透過 DNS 直接找 Task東西向微服務通訊（Service to Service），延遲更低
App MeshService Mesh（每個 Task 注入 Envoy Proxy Sidecar），提供流量控制、熔斷、mTLS需要進階流量管理、安全需求的微服務架構

Cloud Map 整合

Service A 想找 Service B → DNS 查詢：api.prod.local → Route 53 Private Zone 回傳 Task B 的私有 IP → Service A 直接連線到 Task B → 新 Task 啟動時自動登記；Task 結束時自動登出

8. 考試陷阱整理

陷阱 1：Fargate 不支援 GPU
題目問「要跑 GPU 工作負載的 Container」→ 只能用 EC2 Launch Type + GPU Instance（g4dn / p3）。Fargate 目前不支援 GPU。
陷阱 2：ECS Anywhere
ECS Anywhere = 讓你用 ECS 管理自己的 on-premises 伺服器（不是 AWS 的機器）。這些機器不是 EC2，也不是 Fargate。用 SSM Agent 溝通。適合混合雲場景。
陷阱 3：Auto Scaling 有兩個層次
① ECS Service Auto Scaling = Task 數量的自動擴縮（基於 CPU/記憶體/自訂指標）
② EC2 Auto Scaling = EC2 Instance 的自動擴縮（只有 EC2 Launch Type 需要）
Fargate 只需要 ① ，不需要 ②（AWS 管基礎設施）。
陷阱 4：ECS 健康檢查有兩個
① Task Definition 裡的 Container Health Check（Docker HEALTHCHECK）：判斷容器本身是否健康
② ALB Target Group Health Check：判斷 HTTP 端點是否可用
ALB 的 Health Check 失敗，ECS Service 會移除並重啟 Task。
陷阱 5：Fargate 費用計算
Fargate 按 vCPU 和記憶體的「預留量」計費，不是「實際使用量」。設了 0.5 vCPU / 1 GB 的 Task 即使 CPU 使用率只有 5%，仍然按 0.5 vCPU 收費。
📋 快速記憶：Fargate vs EC2 三個關鍵差異
① GPU → EC2 ② 管理負擔高 → EC2 ③ 不確定流量 / 無伺服器 → Fargate
