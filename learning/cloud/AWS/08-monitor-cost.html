1. 四個服務各自回答什麼問題

CloudWatch「現在系統健康嗎？」
指標、日誌、告警、儀表板
CloudTrail「誰做了什麼？」
API 呼叫的稽核紀錄
Config「設定合規嗎？」
資源組態的歷史與規則
X-Ray「這個請求慢在哪？」
跨服務的分散式追蹤
情境用哪個
「網站變慢了，是 CPU 還是資料庫？」CloudWatch 指標
「誰刪掉了那個 S3 bucket？」CloudTrail
「這個安全群組什麼時候被改成開放 0.0.0.0/0？」Config（組態歷史）
「有哪些 EBS 磁碟沒有加密？」Config（規則）
「這支 API 花了 3 秒，是哪一段慢？」X-Ray
「應用程式印了什麼錯誤訊息？」CloudWatch Logs
CloudTrail 和 Config 很容易混淆，用一句話分清楚：
CloudTrail = 「動作」的紀錄（誰在幾點呼叫了 ModifySecurityGroup）

Config = 「狀態」的紀錄（這個安全群組在各個時間點長什麼樣）
查「誰做的」用 CloudTrail，查「當時是什麼設定」用 Config。兩個一起用才能還原完整事件。

2. CloudWatch Metrics 與自訂指標

類型頻率費用
基本監控（預設）5 分鐘免費
詳細監控1 分鐘EC2 每台每月約 US$2.10
高解析度自訂指標最低 1 秒US$0.30/指標/月 + API 費
EC2 的預設指標沒有記憶體和磁碟使用率。因為那需要從作業系統內部取得，AWS 從外面看不到。

要監控記憶體必須裝 CloudWatch Agent。這是很多人「為什麼看不到記憶體」的答案。 
$ sudo dnf install -y amazon-cloudwatch-agent
$ sudo /opt/aws/amazon-cloudwatch-agent/bin/amazon-cloudwatch-agent-ctl \
    -a fetch-config -m ec2 -c ssm:AmazonCloudWatch-linux -s

各服務最該盯的指標

服務關鍵指標看什麼
EC2CPUUtilization持續 > 80% 要擴容
CPUCreditBalanceT 系列，往下掉就要換機型
StatusCheckFailed> 0 代表機器有問題
ALBHTTPCode_ELB_5XX_CountALB 自己的錯誤
TargetResponseTime用 p99 不要用平均
UnHealthyHostCount> 0 立刻要看
RDSCPUUtilization
DatabaseConnections接近上限要用連線池
FreeableMemory太低會開始用 swap，效能崩潰
ReadIOPS / WriteIOPS撞到上限就是瓶頸
LambdaThrottles> 0 代表被限流
Duration接近 timeout 要注意
ConcurrentExecutions接近帳號上限
SQSApproximateAgeOfOldestMessage持續增加 = 消費者跟不上
用 p99 而不是平均值。平均回應時間 200ms 看起來很好，但如果 p99 是 5 秒，代表每 100 個使用者就有 1 個等 5 秒。

平均值會把問題藏起來。SLO 應該用 p95 或 p99 定義，不要用平均。 
$ aws cloudwatch get-metric-statistics \
    --namespace AWS/ApplicationELB --metric-name TargetResponseTime \
    --dimensions Name=LoadBalancer,Value=app/web-alb/xxx \
    --start-time 2026-08-05T00:00:00Z --end-time 2026-08-05T12:00:00Z \
    --period 300 --extended-statistics p50 p95 p99

自訂指標

# 方法 1：直接呼叫 API（會產生 API 費用）
$ aws cloudwatch put-metric-data \
    --namespace "MyApp/Orders" \
    --metric-name OrdersCreated \
    --value 1 \
    --dimensions Env=prod,Region=tw

# 方法 2：EMF（Embedded Metric Format）—— 推薦，只要印 log
# CloudWatch 會自動從日誌解析出指標，不用額外 API 呼叫
import json, time

def emit_metric(name, value, unit="Count", **dims):
    print(json.dumps({
        "_aws": {
            "Timestamp": int(time.time() * 1000),
            "CloudWatchMetrics": [{
                "Namespace": "MyApp/Orders",
                "Dimensions": [list(dims.keys())],
                "Metrics": [{"Name": name, "Unit": unit}]
            }]
        },
        name: value,
        **dims,
    }))

# 用法：只是 print，但 CloudWatch 會把它變成指標
emit_metric("OrderAmount", 1580, "None", Env="prod", PaymentType="credit")
EMF 比 put-metric-data 好在三點：
  1. 不需要額外的 API 呼叫——省下延遲和費用
  2. 不會阻塞——put-metric-data 是同步呼叫，會拖慢你的函式
  3. 日誌和指標關聯——看到指標異常可以直接跳到對應的日誌
Lambda 裡一律用 EMF，不要用 put-metric-data。

3. 告警設計：不要製造雜訊

告警疲勞是監控系統最常見的失敗模式。設了 200 個告警，每天響 50 次，結果是所有人都把通知靜音——真正的事故發生時沒人看到。

好的告警只有一個標準：收到它時，你必須做點什麼。不需要行動的就不該是告警，應該放進儀表板。
告警分兩級：
等級意義通知方式例子
P1 立即處理使用者已經受影響電話 / PagerDuty5XX 錯誤率 > 5%、健康主機數 = 0
P2 上班時間處理還沒影響但趨勢不對Slack / Email磁碟 80%、憑證 30 天到期
# ═══ 建立 SNS 通知管道 ═══
$ TOPIC_ARN=$(aws sns create-topic --name ops-alerts --query TopicArn --output text)
$ aws sns subscribe --topic-arn $TOPIC_ARN --protocol email --notification-endpoint you@example.com

# ═══ 好的告警：多個評估週期，避免瞬間抖動就響 ═══
$ aws cloudwatch put-metric-alarm \
    --alarm-name "P1-ALB-5XX-率過高" \
    --alarm-description "5 分鐘內 5XX 超過 5%，使用者已受影響" \
    --metrics '[
      {
        "Id": "errors",
        "MetricStat": {
          "Metric": {"Namespace":"AWS/ApplicationELB","MetricName":"HTTPCode_ELB_5XX_Count",
                     "Dimensions":[{"Name":"LoadBalancer","Value":"app/web-alb/xxx"}]},
          "Period": 300, "Stat": "Sum"
        }, "ReturnData": false
      },
      {
        "Id": "total",
        "MetricStat": {
          "Metric": {"Namespace":"AWS/ApplicationELB","MetricName":"RequestCount",
                     "Dimensions":[{"Name":"LoadBalancer","Value":"app/web-alb/xxx"}]},
          "Period": 300, "Stat": "Sum"
        }, "ReturnData": false
      },
      {
        "Id": "errorRate",
        "Expression": "IF(total > 100, errors / total * 100, 0)",
        "Label": "5XX 百分比", "ReturnData": true
      }
    ]' \
    --threshold 5 --comparison-operator GreaterThanThreshold \
    --evaluation-periods 2 --datapoints-to-alarm 2 \
    --treat-missing-data notBreaching \
    --alarm-actions $TOPIC_ARN --ok-actions $TOPIC_ARN
這個告警的三個設計重點：
  • 用「錯誤率」不是「錯誤數」——流量大的時候 10 個錯誤很正常，流量小的時候 10 個錯誤是災難
  • IF(total > 100, ...)——請求數太少時不告警，避免半夜 3 個請求裡有 1 個失敗就把人吵醒
  • --datapoints-to-alarm 2——連續兩個週期都超標才響，過濾瞬間抖動
--treat-missing-data 設錯是常見的誤報來源。
設定沒有資料時什麼時候用
notBreaching當成正常流量型指標（沒流量就沒錯誤，是正常的）
breaching當成異常心跳型指標（沒資料代表系統掛了）
ignore保持原狀態間歇性的指標
missing（預設）進入 INSUFFICIENT_DATA—
批次工作的「每天應該執行一次」告警要設 breaching——沒資料代表沒跑，那正是你要知道的事。

複合告警：減少雜訊

# 只有「錯誤率高」且「健康主機數正常」時才響
# （如果主機全掛了，那是另一個告警的事，不用重複通知）
$ aws cloudwatch put-composite-alarm \
    --alarm-name "P1-應用層錯誤" \
    --alarm-rule "ALARM('P1-ALB-5XX-率過高') AND NOT ALARM('P1-無健康主機')" \
    --alarm-actions $TOPIC_ARN
異常偵測（Anomaly Detection）適合「沒有固定閾值」的指標。它學習過去 2 週的模式，自動畫出正常範圍的帶狀區間。例如「週一早上流量本來就高」它會知道，不會誤報。 
$ aws cloudwatch put-anomaly-detector \
    --namespace AWS/ApplicationELB --metric-name RequestCount \
    --dimensions Name=LoadBalancer,Value=app/web-alb/xxx --stat Sum

4. Logs 與 Logs Insights

CloudWatch Logs 的 log group 預設永久保留，這是最常見的隱形成本。
儲存費 US$0.033/GB/月看起來很少，但一個中型系統一年累積幾 TB 之後就是每月數百美元。而且沒有人會去查三年前的日誌。 
# 找出所有沒設保留期的 log group
$ aws logs describe-log-groups \
    --query 'logGroups[?!retentionInDays].[logGroupName,storedBytes]' --output table

# 一次全部設成 30 天
$ aws logs describe-log-groups --query 'logGroups[?!retentionInDays].logGroupName' \
    --output text | tr '\t' '\n' | while read lg; do
      aws logs put-retention-policy --log-group-name "$lg" --retention-in-days 30
    done
保留期的建議：
  • 應用程式日誌：14–30 天（排錯用，超過就沒人看）
  • 存取日誌：90 天
  • 稽核日誌（CloudTrail）：1–7 年，但要匯出到 S3 + Glacier，不要放 CloudWatch Logs
長期保存一律用 S3——S3 Glacier Deep Archive 每 GB US$0.002，是 CloudWatch Logs 的 1/16。

Logs Insights：查日誌的正確方式

# ① 找出最慢的 20 個請求
fields @timestamp, @message, @duration
| filter @type = "REPORT"
| sort @duration desc
| limit 20

# ② 統計各種錯誤出現次數
fields @message
| filter @message like /ERROR/
| parse @message /"errorType":\s*"(?<errType>[^"]+)"/
| stats count() as 次數 by errType
| sort 次數 desc

# ③ Lambda 記憶體使用率（找出設定過大的函式）
filter @type = "REPORT"
| stats max(@memorySize / 1000 / 1000) as 設定MB,
        max(@maxMemoryUsed / 1000 / 1000) as 實際用MB,
        max(@maxMemoryUsed / @memorySize * 100) as 使用率
  by @log
| sort 使用率 asc

# ④ 找出冷啟動與其耗時
filter @type = "REPORT" and ispresent(@initDuration)
| stats count() as 冷啟動次數, avg(@initDuration) as 平均初始化ms,
        pct(@initDuration, 99) as p99
  by bin(1h)

# ⑤ ALB 存取日誌：找出 5XX 來自哪個後端
fields @timestamp, target_ip, elb_status_code, target_status_code, request_url
| filter elb_status_code >= 500
| stats count() by target_ip, target_status_code
| sort count desc
# CLI 執行查詢
$ QID=$(aws logs start-query \
    --log-group-names /aws/lambda/order-processor \
    --start-time $(date -d '1 hour ago' +%s) \
    --end-time $(date +%s) \
    --query-string 'fields @timestamp, @message | filter @message like /ERROR/ | limit 20' \
    --query queryId --output text)

$ aws logs get-query-results --query-id $QID
Logs Insights 按掃描的資料量計費（US$0.0076/GB）。
查詢時一定要縮小時間範圍——查一個月的 100 GB 日誌就是 US$0.76 一次。多查幾次就有感了。
技巧：先用 filter 縮小範圍再做 stats，可以大幅減少掃描量。
Metric Filter：把日誌變成指標。如果你要對「日誌裡出現某個關鍵字」告警，不要用 Logs Insights 定時查（貴又慢），改用 Metric Filter： 
$ aws logs put-metric-filter \
    --log-group-name /aws/lambda/order-processor \
    --filter-name payment-failures \
    --filter-pattern '{ $.level = "ERROR" && $.msg = "payment_failed" }' \
    --metric-transformations \
      metricName=PaymentFailures,metricNamespace=MyApp,metricValue=1,defaultValue=0
這樣就能對它設一般的 CloudWatch 告警，即時且便宜。

5. X-Ray 分散式追蹤

微服務或無伺服器架構下，一個請求會經過 API Gateway → Lambda → DynamoDB → SQS → 另一支 Lambda。「這個請求為什麼花 3 秒」用日誌很難查，因為日誌分散在各個服務。

X-Ray 把整個請求鏈串成一張圖，直接告訴你「3 秒裡有 2.4 秒花在等 DynamoDB」。
# Lambda 開啟追蹤（一個參數）
$ aws lambda update-function-configuration \
    --function-name order-processor --tracing-config Mode=Active

# API Gateway 開啟
$ aws apigatewayv2 update-stage --api-id $API_ID --stage-name '$default' \
    --default-route-settings '{"DetailedMetricsEnabled":true}'
# 程式碼裡加上細部追蹤（Python）
$ pip install aws-xray-sdk

from aws_xray_sdk.core import xray_recorder, patch_all

# 自動追蹤所有 boto3 / requests 呼叫
patch_all()

@xray_recorder.capture("validate_order")
def validate(order):
    ...

def handler(event, context):
    # 加上業務註解，方便之後過濾查詢
    xray_recorder.put_annotation("customerId", event["customerId"])
    xray_recorder.put_metadata("orderDetail", event)

    with xray_recorder.in_subsegment("外部支付 API"):
        charge()
Annotation 和 Metadata 差別很大：
  • Annotation——可以被索引和搜尋，最多 50 個。放 customerId、orderId 這種你會拿來查的
  • Metadata——不能搜尋，只是附加資料。放完整的請求內容
放錯的話你會發現「資料有記錄但搜尋不到」。 
# 用 annotation 過濾追蹤
$ aws xray get-trace-summaries \
    --start-time $(date -d '1 hour ago' +%s) --end-time $(date +%s) \
    --filter-expression 'annotation.customerId = "CUST-001" AND duration > 2'

# 找出所有錯誤的追蹤
$ aws xray get-trace-summaries \
    --start-time ... --end-time ... \
    --filter-expression 'error = true OR fault = true'
X-Ray：每月前 10 萬筆追蹤免費，之後 US$5/百萬筆。
高流量系統要開取樣（sampling）——預設是「每秒第一筆 + 之後 5%」，這樣既能看到問題又不會爆費用。不要 100% 取樣。

6. Config：合規自動檢查

Config 持續記錄每個資源的組態，並用規則持續檢查它們合不合規。

# 啟用 Config（先要有 Role 和 S3 bucket）
$ aws configservice put-configuration-recorder \
    --configuration-recorder name=default,roleARN=arn:aws:iam::123456789012:role/config-role \
    --recording-group allSupported=true,includeGlobalResourceTypes=true

$ aws configservice put-delivery-channel \
    --delivery-channel name=default,s3BucketName=my-config-bucket

$ aws configservice start-configuration-recorder --configuration-recorder-name default

常用的託管規則（不用自己寫）

規則檢查什麼
s3-bucket-public-read-prohibitedS3 沒有公開讀取
s3-bucket-server-side-encryption-enabledS3 有加密
encrypted-volumesEBS 都加密
rds-instance-public-access-checkRDS 沒有公開存取
rds-storage-encryptedRDS 有加密
restricted-ssh安全群組沒有對 0.0.0.0/0 開 22
iam-user-mfa-enabledIAM 使用者都有 MFA
root-account-mfa-enabledroot 有 MFA
required-tags資源有必要的標籤
cloudtrail-enabledCloudTrail 有開
# 套用一條規則
$ aws configservice put-config-rule --config-rule '{
    "ConfigRuleName": "encrypted-volumes",
    "Source": { "Owner": "AWS", "SourceIdentifier": "ENCRYPTED_VOLUMES" }
  }'

# 要求所有資源都有 Owner 和 Env 標籤
$ aws configservice put-config-rule --config-rule '{
    "ConfigRuleName": "required-tags",
    "Source": { "Owner": "AWS", "SourceIdentifier": "REQUIRED_TAGS" },
    "InputParameters": "{\"tag1Key\":\"Owner\",\"tag2Key\":\"Env\"}"
  }'

# 看哪些資源不合規
$ aws configservice get-compliance-details-by-config-rule \
    --config-rule-name encrypted-volumes \
    --compliance-types NON_COMPLIANT \
    --query 'EvaluationResults[].EvaluationResultIdentifier.EvaluationResultQualifier.ResourceId'
Conformance Pack 一次套用一整組規則。AWS 提供現成的合規包（CIS、PCI-DSS、HIPAA、NIST），一個指令就把幾十條規則裝好。要通過稽核的公司這是最快的起點。
Config 按記錄的組態項目計費（US$0.003/項）+ 規則評估（US$0.001/次）。
資源多的帳號一個月可能數十到數百美元。

省錢做法：allSupported=true 會記錄所有資源類型，包含變動極頻繁的（例如 Auto Scaling 每次擴縮都算一次）。可以改成只記錄你真正在意的資源類型。

7. 自動修復（Auto Remediation）

發現不合規只是第一步。Config + SSM Automation 可以自動修好。

# 發現 S3 公開就自動關閉公開存取
$ aws configservice put-remediation-configurations \
    --remediation-configurations '[{
      "ConfigRuleName": "s3-bucket-public-read-prohibited",
      "TargetType": "SSM_DOCUMENT",
      "TargetId": "AWSConfigRemediation-ConfigureS3BucketPublicAccessBlock",
      "Automatic": true,
      "MaximumAutomaticAttempts": 3,
      "RetryAttemptSeconds": 60,
      "Parameters": {
        "AutomationAssumeRole": {
          "StaticValue": {"Values":["arn:aws:iam::123456789012:role/remediation-role"]}
        },
        "BucketName": { "ResourceValue": {"Value":"RESOURCE_ID"} }
      }
    }]'
自動修復要非常小心，它會真的改動正式環境。
  • 先設 "Automatic": false 跑一陣子，觀察它「想改什麼」，確認判斷正確再開自動
  • 某些「不合規」是刻意的例外（例如故意公開的靜態網站 bucket）——要用標籤或 Config 的排除清單把它們排除
  • 自動關掉正在服務的 bucket 公開存取，等於讓網站掛掉
建議先從低風險項目開始自動化：加標籤、關閉未使用的存取金鑰、開啟日誌。

另一種做法：EventBridge + Lambda

# 有人建立了對 0.0.0.0/0 開放 22 埠的安全群組 → 立刻通知並記錄
$ aws events put-rule --name detect-open-ssh \
    --event-pattern '{
      "source": ["aws.ec2"],
      "detail-type": ["AWS API Call via CloudTrail"],
      "detail": {
        "eventSource": ["ec2.amazonaws.com"],
        "eventName": ["AuthorizeSecurityGroupIngress"]
      }
    }'

# 費用異常時自動停掉開發環境的機器
$ aws events put-rule --name budget-breach-action \
    --event-pattern '{"source":["aws.budgets"],"detail-type":["Budget Threshold Exceeded"]}'
「預算超標自動停機」是很實用的保險，但只該用在開發環境。 
import boto3
ec2 = boto3.client("ec2")

def handler(event, context):
    # 只停「AutoStop=true 且 Env=dev」的機器 —— 條件要嚴格
    r = ec2.describe_instances(Filters=[
        {"Name": "tag:AutoStop", "Values": ["true"]},
        {"Name": "tag:Env", "Values": ["dev"]},
        {"Name": "instance-state-name", "Values": ["running"]},
    ])
    ids = [i["InstanceId"] for res in r["Reservations"] for i in res["Instances"]]
    if ids:
        ec2.stop_instances(InstanceIds=ids)
    print(f"已停止 {len(ids)} 台")
絕對不要對正式環境做自動停機——帳單超標不是讓服務中斷的理由，那是要人來判斷的商業決策。

8. 標籤策略：FinOps 的基礎

沒有標籤 = 沒有成本管理。Cost Explorer 只能告訴你「EC2 花了 5 萬」，但不能告訴你「哪個專案花的」。沒有這個資訊就無法做任何優化決策。
標籤用途範例值
Owner誰負責（出事找誰、能不能刪）tom@example.com
Env環境（決定能不能自動關機）prod / staging / dev
Project專案（分帳）order-system
CostCenter會計成本中心CC-1024
AutoStop能不能自動停機true / false
DataClass資料敏感度（決定加密與備份要求）public / internal / confidential
# ═══ 用 SCP 強制要求標籤（沒帶就不准建立）═══
{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "RequireTagsOnEC2",
    "Effect": "Deny",
    "Action": ["ec2:RunInstances"],
    "Resource": ["arn:aws:ec2:*:*:instance/*", "arn:aws:ec2:*:*:volume/*"],

      "Null": {
        "aws:RequestTag/Owner": "true",

$ aws ce update-cost-allocation-tags-status \

所以標籤策略要在專案第一天就定好——等三個月後才想到要分帳，前三個月的資料就永遠沒有了。

Cost Anomaly Detection 是免費的，一定要開。它用機器學習建立「正常花費」的模型，偵測到異常時主動通知。

典型能抓到的情況：金鑰外洩被拿去挖礦、忘記關的大型機器、程式 bug 造成的 API 呼叫暴增、誤設的資料傳輸。這些通常在帳單出來前 2–3 週就會被抓到。

10. FinOps 月度流程

FinOps 不是「一次性的省錢專案」，是持續的流程。把下面這套變成每月固定要做的事，通常第一次能砍掉 20–40%，之後維持在合理水位。
1
看趨勢Cost Explorer 比較本月與前三個月，找出漲最多的服務。漲幅超過 20% 的一定要有解釋。
2
依標籤分帳用 Project / CostCenter 分組，把數字交給各團隊。看得到自己花多少，行為就會改變。
3
清孤兒資源跑盤點腳本：未掛載的 EBS、閒置 EIP、舊快照、沒用的 ALB、殭屍分段上傳。
4
看 Compute Optimizer把標記為 OVER_PROVISIONED 的資源降規格。
5
檢查 SP / RI 使用率Utilization < 95% 代表買太多；Coverage < 70% 代表還能再買。
6
檢查資料傳輸用 USAGE_TYPE 分組。跨 AZ 流量高 → 檢查架構是否有不必要的跨 AZ 呼叫。
7
回顧異常告警這個月觸發了哪些 Anomaly，原因查清楚了嗎。

整合盤點腳本

#!/bin/bash
# ══ AWS 每月成本盤點 ══
set -u
MONTH_START=$(date +%Y-%m-01)
NEXT_MONTH=$(date -d "$MONTH_START +1 month" +%Y-%m-01)

echo "════ 1. 本月各服務花費（> US$5）════"
aws ce get-cost-and-usage \
  --time-period Start=$MONTH_START,End=$NEXT_MONTH \
  --granularity MONTHLY --metrics UnblendedCost \
  --group-by Type=DIMENSION,Key=SERVICE \
  --query "ResultsByTime[0].Groups[?Metrics.UnblendedCost.Amount>\`5\`].[Keys[0],Metrics.UnblendedCost.Amount]" \
  --output table

echo "════ 2. 未掛載的 EBS 磁碟 ════"
aws ec2 describe-volumes --filters Name=status,Values=available \
  --query 'Volumes[].[VolumeId,Size,VolumeType]' --output table

echo "════ 3. 閒置的 Elastic IP ════"
aws ec2 describe-addresses \
  --query 'Addresses[?AssociationId==null].[PublicIp,AllocationId]' --output table

echo "════ 4. 還在用 gp2 的磁碟 ════"
aws ec2 describe-volumes --filters Name=volume-type,Values=gp2 \
  --query 'Volumes[].[VolumeId,Size]' --output table

echo "════ 5. 沒設保留期的 Log Group ════"
aws logs describe-log-groups \
  --query 'logGroups[?!retentionInDays].[logGroupName,storedBytes]' --output table

echo "════ 6. 超過一年的手動快照 ════"
YEAR_AGO=$(date -d '1 year ago' +%Y-%m-%d)
aws ec2 describe-snapshots --owner-ids self \
  --query "Snapshots[?StartTime<=\`$YEAR_AGO\`].[SnapshotId,VolumeSize,StartTime]" --output table

echo "════ 7. Compute Optimizer 建議降規格 ════"
aws compute-optimizer get-ec2-instance-recommendations \
  --query 'instanceRecommendations[?finding==`OVER_PROVISIONED`].[instanceArn,currentInstanceType,recommendationOptions[0].instanceType]' \
  --output table 2>/dev/null || echo "  （尚未啟用 Compute Optimizer）"

echo "════ 8. Savings Plans 使用率 ════"
aws ce get-savings-plans-utilization \
  --time-period Start=$MONTH_START,End=$NEXT_MONTH \
  --query 'Total.[UtilizationPercentage,NetSavings.NetSavings]' --output table 2>/dev/null \
  || echo "  （沒有 Savings Plans）"

echo "════ 9. 沒有 Owner 標籤的資源 ════"
aws resourcegroupstaggingapi get-resources \
  --resource-type-filters ec2:instance rds:db lambda:function \
  --query 'ResourceTagMappingList[?!(Tags[?Key==`Owner`])].ResourceARN' --output text

echo "════ 10. 公開存取的 RDS（安全風險）════"
aws rds describe-db-instances \
  --query 'DBInstances[?PubliclyAccessible==`true`].[DBInstanceIdentifier]' --output table
把這個腳本排成每月 1 號自動跑，結果寄到 Slack。用 EventBridge Scheduler + Lambda 就能做（第 07 章講過）。自動化的盤點才會真的每月執行——靠人記得做的事情，三個月後就沒人做了。

完整實作 Lab：可觀測性與成本治理

約 90 分鐘。

大部分免費：CloudWatch 基本指標、10 個告警、Cost Anomaly Detection、Compute Optimizer、前 2 個 Budget 都免費。
要注意的是 Config——它按組態項目計費，資源多的帳號可能有感。學習用途不要開 allSupported，只記錄兩三種資源類型就好，做完記得停用。

階段一：指標與告警

  1. 建立 SNS Topic 並訂閱你的 email（記得去信箱點確認）
  2. 建立一個用 metric math 算錯誤率的告警（不是錯誤數）
  3. 加上 IF(total > N) 條件避免低流量誤報
  4. 設 datapoints-to-alarm 2 和正確的 treat-missing-data
  5. 用 set-alarm-state 手動觸發，確認真的收得到通知
  6. 建立一個 Composite Alarm 組合兩個告警

階段二：日誌

  1. 找出帳號內所有沒設保留期的 log group，全部設成 14 天
  2. 用 Logs Insights 跑第 4 節的五個查詢（挑有資料的跑）
  3. 建立一個 Metric Filter，把日誌中的 ERROR 變成指標
  4. 對那個指標設告警

階段三：追蹤

  1. 對第 07 章的 Lambda 開啟 X-Ray Active tracing
  2. 在程式碼加 annotation（customerId）和 subsegment
  3. 呼叫幾次，到 X-Ray 主控台看服務地圖與時間分佈
  4. 用 --filter-expression 依 annotation 過濾追蹤

階段四：合規

  1. 啟用 Config，只記錄 EC2 Instance、Volume、SecurityGroup 三種（省錢）
  2. 套用規則：encrypted-volumes、restricted-ssh、required-tags
  3. 故意建一個對 0.0.0.0/0 開 22 埠的安全群組，觀察它被標為 NON_COMPLIANT
  4. 建一個沒有 Owner 標籤的資源，觀察 required-tags 規則觸發
  5. 設定 remediation 但先用 Automatic: false，觀察它「想做什麼」

階段五：成本

  1. 啟用 成本分配標籤（Owner、Env、Project）
  2. 開啟 Cost Anomaly Detection
  3. 執行第 10 節的完整盤點腳本
  4. 依腳本結果實際清掉至少三項浪費（孤兒磁碟、閒置 EIP、無保留期的 log group）
  5. 用 get-cost-and-usage 依 USAGE_TYPE 分組看資料傳輸費

驗收清單

  • 手動觸發告警後信箱真的收到通知（很多人設完從沒驗證過）
  • describe-log-groups 查詢沒有保留期的 log group 回傳空的
  • Logs Insights 的記憶體查詢找出至少一支設定過大的 Lambda
  • X-Ray 服務地圖看得到完整的呼叫鏈與各段耗時
  • Config 把那個開放 22 埠的安全群組標為 NON_COMPLIANT
  • Cost Explorer 能依 Project 標籤分組顯示費用
  • 盤點腳本的前四項都回傳空的（代表清乾淨了）

加碼挑戰

  1. 用 EventBridge Scheduler + Lambda 把盤點腳本排程成每月 1 號自動執行，結果寄到 SNS。
  2. 建立一個 CloudWatch Dashboard，把 ALB、ASG、RDS、Lambda 的關鍵指標放在同一頁。
  3. 設定 Anomaly Detection 告警（不是固定閾值），觀察它學習出來的正常範圍帶狀區間。
  4. 用 CUR + Athena 查詢「上個月每個 Project 標籤各花了多少，依服務細分」。
  5. 寫一條 SCP 強制要求 EC2 必須帶 Owner 和 Env 標籤，測試不帶標籤時真的建立失敗。

本章重點回顧

  • CloudWatch 看健康、CloudTrail 看誰做的、Config 看設定狀態、X-Ray 看請求慢在哪
  • EC2 預設沒有記憶體和磁碟指標，要裝 CloudWatch Agent
  • 回應時間用 p95 / p99，不要用平均值
  • Lambda 自訂指標用 EMF（印 log）不要用 put-metric-data
  • 好的告警標準：收到它時你必須做點什麼；用錯誤率不用錯誤數
  • treat-missing-data 流量型設 notBreaching、心跳型設 breaching
  • Log group 預設永久保留——這是最常見的隱形成本
  • 長期稽核日誌放 S3 + Glacier，不要放 CloudWatch Logs（貴 16 倍）
  • 對日誌關鍵字告警用 Metric Filter，不要定時跑 Logs Insights
  • X-Ray 的 Annotation 可搜尋、Metadata 不行；高流量要開取樣
  • Config 自動修復先跑 Automatic: false 觀察，確認後才開自動
  • 成本分配標籤不會回溯——第一天就要定好標籤策略
  • Cost Anomaly Detection 免費，一定要開——能在帳單出來前 2–3 週抓到問題
  • 容易被忽略的大額費用：跨 AZ 傳輸、對外傳輸、NAT Gateway 處理費
  • FinOps 是每月固定流程，不是一次性專案
