1. 為什麼不要用預設 VPC

每個 region 都有一個 AWS 幫你建好的 Default VPC。它很方便——開 EC2 直接就有公網 IP、能上網、能被連進來。但正因為方便，它的預設值全部偏向「能通」而不是「安全」。

Default VPC自建 VPC
CIDR固定 172.31.0.0/16（所有帳號都一樣）自己決定
子網路每個 AZ 一個，全部是公有公有／私有／資料庫分層
自動配公網 IP開啟預設關閉
對外路由已接 IGW自己決定哪些子網路能出去
問題資料庫也會被放在公有子網路；CIDR 撞在一起無法 Peering
Default VPC 的 CIDR 全世界都一樣是 172.31.0.0/16。這代表：你的帳號 A 和帳號 B 的 Default VPC 永遠無法做 VPC Peering（網段重疊）。等公司長大要串接時才發現，那時搬遷成本非常高。從第一個專案就自建 VPC。
但也不要刪掉 Default VPC。某些服務（部分 SageMaker、Elastic Beanstalk 快速部署、少數 Marketplace AMI）預設會找它，刪掉會出現難查的錯誤。留著但不要用就好。真要刪，記得它刪掉後可以用 aws ec2 create-default-vpc 重建。

2. 網段規劃：CIDR 怎麼切

VPC 的 CIDR 建立後不能縮小，只能額外新增次要 CIDR。所以第一次就要規劃好。而且子網路一旦建立，CIDR 完全不能改，只能刪掉重建（意味著裡面的資源要全部搬走）。

三個規劃原則

1
用 /16，不要小氣私有 IP 不用錢。給 VPC 一個 /16（65536 個位址），未來擴充才有空間。AWS 允許 /16 到 /28。
2
不同環境、不同帳號用不同網段prod 用 10.0.0.0/16、staging 用 10.1.0.0/16、dev 用 10.2.0.0/16。重疊了就永遠不能互連。
3
避開公司內網已用的網段將來要拉 VPN 或 Direct Connect 回機房時，網段撞到就通不了。建工前先問網管要一份現有網段清單。

本章要建的架構

VPC: 10.0.0.0/16　(ap-northeast-1)

　　　　　　　　 ap-northeast-1a　　　　　　 ap-northeast-1c
　　　　　　┌──────────────────────┐　┌──────────────────────┐
公有層　　　│ 10.0.0.0/24　        │　│ 10.0.1.0/24          │
(Public)　  │ ALB / NAT GW / 堡壘  │　│ ALB / NAT GW         │
　　　　　　└──────────┬───────────┘　└──────────┬───────────┘
　　　　　　　　　　　　│　　　　　　　　　　　　　│
應用層　　　┌──────────▼───────────┐　┌──────────▼───────────┐
(Private)　 │ 10.0.10.0/24         │　│ 10.0.11.0/24         │
　　　　　　│ EC2 / ECS / Lambda   │　│ EC2 / ECS            │
　　　　　　└──────────┬───────────┘　└──────────┬───────────┘
　　　　　　　　　　　　│　　　　　　　　　　　　　│
資料層　　　┌──────────▼───────────┐　┌──────────▼───────────┐
(Isolated)　│ 10.0.20.0/24         │　│ 10.0.21.0/24         │
　　　　　　│ RDS 主　             │　│ RDS 待命 (Multi-AZ)  │
　　　　　　└──────────────────────┘　└──────────────────────┘
　　　　　　　　　　　　　　　　　　　　　剩餘 10.0.2~9 / 12~19 / 22~255 留給未來擴充
公有子網路路由表有指向 IGW 的 0.0.0.0/0。放 ALB、NAT Gateway、堡壘主機。
私有子網路路由表指向 NAT Gateway。能主動出網，但外面連不進來。放應用伺服器。
隔離子網路路由表沒有對外路由。完全封閉。放資料庫。
每個子網路 AWS 會保留 5 個 IP，不是 2 個。
位址用途
.0網路位址
.1VPC 路由器
.2DNS 伺服器（VPC CIDR 的 base + 2）
.3保留給未來使用
.255廣播位址（VPC 不支援廣播，但仍保留）
所以 /24 只有 251 個可用，/28 只有 11 個可用。這是 SAA 常考的計算題。
/24 → 256 − 5 = 251 個可用
/26 → 64 − 5 = 59 個可用
/28 → 16 − 5 = 11 個可用（AWS 允許的最小子網路）
子網路不能跨 AZ。一個子網路綁死一個 AZ。所以「高可用」的最低要求是至少兩個 AZ，每層各一個子網路——這也是為什麼上面的圖每一層都有兩個。ALB 要求至少兩個 AZ 的子網路，RDS Multi-AZ 也是。

3. 實作：11 個步驟建起完整 VPC

這一節建立的資源中，VPC、子網路、IGW、路由表、SG、NACL 全部免費。
要錢的只有兩個：NAT Gateway（每小時約 US$0.062 + 每 GB US$0.062，一個月不關約 US$45）和 Elastic IP（未綁定時每小時 US$0.005）。
做完 Lab 一定要刪 NAT Gateway 和釋放 EIP，否則會持續計費。
# ═══ 步驟 1：建立 VPC ═══
$ VPC_ID=$(aws ec2 create-vpc \
    --cidr-block 10.0.0.0/16 \
    --tag-specifications 'ResourceType=vpc,Tags=[{Key=Name,Value=main-vpc}]' \
    --query Vpc.VpcId --output text)
$ echo $VPC_ID
vpc-0a1b2c3d4e5f6789a

# 開啟 DNS 支援（RDS endpoint、VPC Endpoint 都需要）
$ aws ec2 modify-vpc-attribute --vpc-id $VPC_ID --enable-dns-support
$ aws ec2 modify-vpc-attribute --vpc-id $VPC_ID --enable-dns-hostnames
enable-dns-hostnames 沒開，之後 RDS 的 endpoint 名稱會解析不出來，VPC Endpoint 的私有 DNS 也不會生效。自建 VPC 這個屬性預設是關的（Default VPC 才預設開），是最常見的「照著做卻不通」原因。
# ═══ 步驟 2：建立 6 個子網路（3 層 × 2 AZ）═══
# 公有層
$ PUB_A=$(aws ec2 create-subnet --vpc-id $VPC_ID \
    --cidr-block 10.0.0.0/24 --availability-zone ap-northeast-1a \
    --tag-specifications 'ResourceType=subnet,Tags=[{Key=Name,Value=public-1a},{Key=Tier,Value=public}]' \
    --query Subnet.SubnetId --output text)
$ PUB_C=$(aws ec2 create-subnet --vpc-id $VPC_ID \
    --cidr-block 10.0.1.0/24 --availability-zone ap-northeast-1c \
    --tag-specifications 'ResourceType=subnet,Tags=[{Key=Name,Value=public-1c},{Key=Tier,Value=public}]' \
    --query Subnet.SubnetId --output text)

# 應用層
$ APP_A=$(aws ec2 create-subnet --vpc-id $VPC_ID \
    --cidr-block 10.0.10.0/24 --availability-zone ap-northeast-1a \
    --tag-specifications 'ResourceType=subnet,Tags=[{Key=Name,Value=app-1a},{Key=Tier,Value=private}]' \
    --query Subnet.SubnetId --output text)
$ APP_C=$(aws ec2 create-subnet --vpc-id $VPC_ID \
    --cidr-block 10.0.11.0/24 --availability-zone ap-northeast-1c \
    --tag-specifications 'ResourceType=subnet,Tags=[{Key=Name,Value=app-1c},{Key=Tier,Value=private}]' \
    --query Subnet.SubnetId --output text)

# 資料層
$ DB_A=$(aws ec2 create-subnet --vpc-id $VPC_ID \
    --cidr-block 10.0.20.0/24 --availability-zone ap-northeast-1a \
    --tag-specifications 'ResourceType=subnet,Tags=[{Key=Name,Value=db-1a},{Key=Tier,Value=isolated}]' \
    --query Subnet.SubnetId --output text)
$ DB_C=$(aws ec2 create-subnet --vpc-id $VPC_ID \
    --cidr-block 10.0.21.0/24 --availability-zone ap-northeast-1c \
    --tag-specifications 'ResourceType=subnet,Tags=[{Key=Name,Value=db-1c},{Key=Tier,Value=isolated}]' \
    --query Subnet.SubnetId --output text)
# ═══ 步驟 3：建立並掛上 Internet Gateway ═══
$ IGW_ID=$(aws ec2 create-internet-gateway \
    --tag-specifications 'ResourceType=internet-gateway,Tags=[{Key=Name,Value=main-igw}]' \
    --query InternetGateway.InternetGatewayId --output text)

$ aws ec2 attach-internet-gateway --vpc-id $VPC_ID --internet-gateway-id $IGW_ID
IGW 是免費的，而且沒有頻寬上限、不會是效能瓶頸。它是 VPC 層級的資源，一個 VPC 只能掛一個。它同時做兩件事：提供對網際網路的路由，以及幫有公網 IP 的執行個體做 1:1 NAT。
# ═══ 步驟 4：建立 NAT Gateway（放在公有子網路）═══
$ EIP_ALLOC=$(aws ec2 allocate-address --domain vpc \
    --tag-specifications 'ResourceType=elastic-ip,Tags=[{Key=Name,Value=nat-eip-1a}]' \
    --query AllocationId --output text)

$ NAT_ID=$(aws ec2 create-nat-gateway \
    --subnet-id $PUB_A \
    --allocation-id $EIP_ALLOC \
    --tag-specifications 'ResourceType=natgateway,Tags=[{Key=Name,Value=nat-1a}]' \
    --query NatGateway.NatGatewayId --output text)

# 建立要 2~3 分鐘，等它變 available
$ aws ec2 wait nat-gateway-available --nat-gateway-ids $NAT_ID
NAT Gateway 一定要放在公有子網路。放進私有子網路會建得起來但完全不通——因為它自己也需要走 IGW 出去。這是很常見的錯誤，而且不會有明顯的錯誤訊息，只會表現成「私有子網路的機器上不了網」。
# ═══ 步驟 5：公有路由表 ═══
$ RT_PUB=$(aws ec2 create-route-table --vpc-id $VPC_ID \
    --tag-specifications 'ResourceType=route-table,Tags=[{Key=Name,Value=rt-public}]' \
    --query RouteTable.RouteTableId --output text)

# 這一行是「公有子網路」的唯一定義
$ aws ec2 create-route --route-table-id $RT_PUB \
    --destination-cidr-block 0.0.0.0/0 --gateway-id $IGW_ID

$ aws ec2 associate-route-table --route-table-id $RT_PUB --subnet-id $PUB_A
$ aws ec2 associate-route-table --route-table-id $RT_PUB --subnet-id $PUB_C

# ═══ 步驟 6：私有路由表（指向 NAT）═══
$ RT_APP=$(aws ec2 create-route-table --vpc-id $VPC_ID \
    --tag-specifications 'ResourceType=route-table,Tags=[{Key=Name,Value=rt-app}]' \
    --query RouteTable.RouteTableId --output text)

$ aws ec2 create-route --route-table-id $RT_APP \
    --destination-cidr-block 0.0.0.0/0 --nat-gateway-id $NAT_ID

$ aws ec2 associate-route-table --route-table-id $RT_APP --subnet-id $APP_A
$ aws ec2 associate-route-table --route-table-id $RT_APP --subnet-id $APP_C

# ═══ 步驟 7：資料層路由表（完全不加對外路由）═══
$ RT_DB=$(aws ec2 create-route-table --vpc-id $VPC_ID \
    --tag-specifications 'ResourceType=route-table,Tags=[{Key=Name,Value=rt-db}]' \
    --query RouteTable.RouteTableId --output text)

$ aws ec2 associate-route-table --route-table-id $RT_DB --subnet-id $DB_A
$ aws ec2 associate-route-table --route-table-id $RT_DB --subnet-id $DB_C
資料層的路由表什麼都不用加。每張路由表天生就有一條 10.0.0.0/16 → local（VPC 內互通，無法刪除也無法覆蓋）。不加 0.0.0.0/0 就代表這個子網路完全出不了 VPC——資料庫本來就該這樣。
# ═══ 步驟 8：安全群組 —— ALB ═══
$ SG_ALB=$(aws ec2 create-security-group \
    --group-name alb-sg --description "ALB from internet" --vpc-id $VPC_ID \
    --query GroupId --output text)

$ aws ec2 authorize-security-group-ingress --group-id $SG_ALB \
    --protocol tcp --port 443 --cidr 0.0.0.0/0
$ aws ec2 authorize-security-group-ingress --group-id $SG_ALB \
    --protocol tcp --port 80 --cidr 0.0.0.0/0

# ═══ 步驟 9：安全群組 —— 應用層（只接受來自 ALB 的流量）═══
$ SG_APP=$(aws ec2 create-security-group \
    --group-name app-sg --description "App tier" --vpc-id $VPC_ID \
    --query GroupId --output text)

# 關鍵：來源寫「安全群組」而不是 IP 網段
$ aws ec2 authorize-security-group-ingress --group-id $SG_APP \
    --protocol tcp --port 8080 --source-group $SG_ALB

# ═══ 步驟 10：安全群組 —— 資料庫（只接受應用層）═══
$ SG_DB=$(aws ec2 create-security-group \
    --group-name db-sg --description "Database tier" --vpc-id $VPC_ID \
    --query GroupId --output text)

$ aws ec2 authorize-security-group-ingress --group-id $SG_DB \
    --protocol tcp --port 3306 --source-group $SG_APP
安全群組互相引用是 AWS 最好用的設計之一。--source-group 的意思是「任何掛著那個安全群組的資源都能進來」。

好處：Auto Scaling 增減機器時完全不用改規則。用 IP 網段的話，每次擴容都要改 SG。這是 SAA 的高頻考點——題目問「如何讓 Web 層存取 App 層且不受擴縮影響」，答案就是引用安全群組。 
# ═══ 步驟 11：確認整體結構 ═══
$ aws ec2 describe-subnets --filters "Name=vpc-id,Values=$VPC_ID" \
    --query 'Subnets[].[Tags[?Key==`Name`].Value|[0],CidrBlock,AvailabilityZone,AvailableIpAddressCount]' \
    --output table

4. 路由表：公有與私有的唯一差別

公有子網路的定義：它關聯的路由表有一條
0.0.0.0/0 → Internet Gateway

沒有這條，就是私有子網路。就這樣，沒有別的判準。
「子網路」本身沒有公有／私有這個屬性。AWS 主控台上看不到一個叫「Public」的開關。是路由表決定的。所以：
  • 把一個私有子網路的路由表改成指向 IGW → 它立刻變成公有
  • 把公有子網路的那條路由刪掉 → 裡面的機器立刻斷網
考試常出這種題：「這個子網路是公有還是私有？」——去看它的路由表。

路由表比對規則

目的地目標說明
10.0.0.0/16local自動存在、不可刪除、不可覆蓋。VPC 內互通
0.0.0.0/0igw-xxx公有子網路的對外路由
0.0.0.0/0nat-xxx私有子網路的對外路由
172.16.0.0/12pcx-xxx指向 VPC Peering
192.168.0.0/16vgw-xxx指向 VPN Gateway（回公司機房）
跟 CH 3-1 的路由器一樣：最長前綴匹配優先。如果同時有 0.0.0.0/0 → NAT 和 54.230.0.0/16 → IGW，那麼去 54.230.x.x 的流量走 IGW，其他走 NAT。local 那條永遠最優先，這是它不能被覆蓋的原因。

Main Route Table 的陷阱

沒有明確關聯路由表的子網路，會自動使用 VPC 的 Main Route Table。如果有人不小心在 Main 加了一條指向 IGW 的路由，所有「忘了關聯」的子網路就全部變成公有——包含你的資料庫。

防護做法：把 Main Route Table 保持乾淨（只有 local），並且每個子網路都明確關聯到自己的路由表。可以用 AWS Config 規則持續監控。 
# 找出沒有明確關聯路由表的子網路
$ aws ec2 describe-route-tables --filters "Name=vpc-id,Values=$VPC_ID" \
    --query 'RouteTables[?Associations[?Main==`true`]].RouteTableId'

5. NAT Gateway 與它的帳單

NAT Gateway 是 AWS 帳單上最常見的「意外支出」前三名。

· 每小時 US$0.062（東京區）→ 一個月不關 ≈ US$45
· 每處理 1 GB 再收 US$0.062
· 而且三個 AZ 就要三個（做高可用的話）→ 一個月 ≈ US$135，還沒算流量

很多人做完 Lab 忘了刪，下個月看到帳單才發現。學習用途做完就刪。

NAT Gateway vs NAT Instance

NAT Gateway（AWS 託管）NAT Instance（自己開 EC2）
可用性AZ 內自動高可用自己要做（ASG + 腳本）
頻寬自動擴展到 100 Gbps看機型
維運零要自己打補丁、監控
費用約 US$45/月起t4g.nano 約 US$3/月
安全群組不能掛可以掛
可當堡壘主機不行可以
需要關 Source/Dest Check不用必須關，忘了就不通
怎麼選？
  • 正式環境 → NAT Gateway，沒得商量。省下的錢不值得承擔單點故障
  • 學習／開發環境 → NAT Instance（t4g.nano）可以省 90% 費用
  • 更省的做法 → 大部分「出網」需求其實是去 S3、ECR、CloudWatch，用 VPC Endpoint 完全不需要 NAT（下一節）
考試題目如果強調「高可用」「免維運」→ 選 NAT Gateway；強調「成本最低」→ 可能是 NAT Instance 或 VPC Endpoint。

高可用架構：每個 AZ 一個 NAT

只放一個 NAT Gateway 有兩個問題：
  1. 單點故障——那個 AZ 掛掉，所有私有子網路一起斷網
  2. 跨 AZ 流量費——1c 的機器走 1a 的 NAT，每 GB 要多付跨 AZ 傳輸費（US$0.01/GB 雙向）
正確做法：每個 AZ 各一個 NAT Gateway，每個 AZ 的私有子網路指向自己 AZ 的那個。 
# 1c 也建一個 NAT，並給 1c 的私有子網路自己的路由表
$ EIP_C=$(aws ec2 allocate-address --domain vpc --query AllocationId --output text)
$ NAT_C=$(aws ec2 create-nat-gateway --subnet-id $PUB_C --allocation-id $EIP_C \
    --query NatGateway.NatGatewayId --output text)
$ aws ec2 wait nat-gateway-available --nat-gateway-ids $NAT_C

$ RT_APP_C=$(aws ec2 create-route-table --vpc-id $VPC_ID \
    --tag-specifications 'ResourceType=route-table,Tags=[{Key=Name,Value=rt-app-1c}]' \
    --query RouteTable.RouteTableId --output text)
$ aws ec2 create-route --route-table-id $RT_APP_C \
    --destination-cidr-block 0.0.0.0/0 --nat-gateway-id $NAT_C

# 把 1c 從共用路由表改關聯到自己的
$ ASSOC=$(aws ec2 describe-route-tables --route-table-ids $RT_APP \
    --query "RouteTables[0].Associations[?SubnetId=='$APP_C'].RouteTableAssociationId" --output text)
$ aws ec2 replace-route-table-association --association-id $ASSOC --route-table-id $RT_APP_C

刪除（做完 Lab 一定要做）

$ aws ec2 delete-nat-gateway --nat-gateway-id $NAT_ID
$ aws ec2 wait nat-gateway-deleted --nat-gateway-ids $NAT_ID
$ aws ec2 release-address --allocation-id $EIP_ALLOC      # EIP 沒釋放也會收費

# 檢查有沒有漏掉的 EIP（未綁定的每小時 US$0.005）
$ aws ec2 describe-addresses \
    --query 'Addresses[?AssociationId==null].[PublicIp,AllocationId]' --output table
2024 年起 AWS 對所有公有 IPv4 收費（每小時 US$0.005，約每月 US$3.6/個），不論有沒有綁定。以前只有「閒置的 EIP」才收費，現在連正在用的也收。這讓「盡量少用公網 IP」變成實際的省錢手段——多用私有子網路 + ALB + VPC Endpoint。

6. SG vs NACL 完整對比

Security Group（安全群組）Network ACL
作用層級ENI（網卡）子網路
有狀態？Stateful（有狀態）Stateless（無狀態）
規則類型只有 AllowAllow 和 Deny
評估方式所有規則一起看，有一條符合就通過依規則號碼由小到大，第一個符合就決定
回程流量自動放行要自己開規則
來源可寫安全群組可以不行（只能寫 CIDR）
預設值入站全擋、出站全開預設 NACL 進出全開；自建的全擋
比喻：NACL 是社區大門的警衛——管整個社區的人車進出，而且他記性不好，你出去再回來還要再檢查一次（無狀態）。SG 是每一戶的門鎖——只管自己這一戶，而且他記得「這是剛剛出去的那個人」，回來直接放行（有狀態）。
「有狀態」的實際意義，用一個例子講清楚：

EC2 要去外面下載更新（出去 tcp/443，回來的封包來源埠是 443、目的埠是隨機高位埠）。
  • SG：只要出站規則允許 443 出去，回程自動放行，入站規則完全不用動
  • NACL：出站要允許 443，入站還要額外允許 1024–65535 的回應埠（ephemeral ports）
忘記開 ephemeral port 是 NACL 最常見的故障：症狀是「連得出去但沒有回應」。 
# NACL 正確寫法：出站 443 + 入站 ephemeral
$ aws ec2 create-network-acl-entry --network-acl-id $NACL_ID \
    --rule-number 100 --protocol tcp --port-range From=443,To=443 \
    --cidr-block 0.0.0.0/0 --rule-action allow --egress

$ aws ec2 create-network-acl-entry --network-acl-id $NACL_ID \
    --rule-number 100 --protocol tcp --port-range From=1024,To=65535 \
    --cidr-block 0.0.0.0/0 --rule-action allow          ← 沒有 --egress 就是入站
企業實務建議：主要用 SG，NACL 只做粗粒度的封鎖。
  • SG 做精細的分層控制（ALB→App→DB），因為有狀態、可引用安全群組、好維護
  • NACL 只用來做「封鎖特定惡意 IP 網段」這種SG 做不到的 Deny
  • 不要用 NACL 做細部應用層控制——規則號碼管理很快就會亂掉

SG 的三個容易忽略的細節

細節說明
預設出站是全開新建 SG 的 outbound 是 0.0.0.0/0 全部允許。高安全需求要手動收緊
一個 ENI 可掛多個 SG規則聯集生效。最多 5 個（可申請提高）
刪不掉？被其他 SG 引用、或還有 ENI 掛著，就刪不掉。要先解除引用
# 查某個 SG 被誰引用了（刪不掉的時候用）
$ aws ec2 describe-security-groups \
    --query "SecurityGroups[?IpPermissions[?UserIdGroupPairs[?GroupId=='sg-0abc123']]].[GroupId,GroupName]" \
    --output table

# 查哪些 ENI 還掛著它
$ aws ec2 describe-network-interfaces \
    --filters Name=group-id,Values=sg-0abc123 \
    --query 'NetworkInterfaces[].[NetworkInterfaceId,Description,Status]' --output table

7. VPC Endpoint：省錢又安全

私有子網路的 EC2 要讀 S3。走 NAT Gateway 的話：流量出到公網 → 繞一圈 → 再回到 AWS 的 S3。又慢、又要付 NAT 流量費、又暴露在公網上。

VPC Endpoint 讓流量完全走 AWS 內部網路，不經過網際網路。

Gateway EndpointInterface Endpoint（PrivateLink）
支援服務只有 S3 和 DynamoDB其他上百個服務
實作方式加一條路由表項目在子網路裡建一張 ENI
費用完全免費每小時 US$0.01/AZ + 每 GB US$0.01
能不能跨 VPC / 跨帳號不行可以
用 SG 控制不行（用 Endpoint Policy）可以
Gateway Endpoint 免費，S3 和 DynamoDB 一律建起來，沒有理由不建。光是省下的 NAT 流量費就很可觀——如果你的應用每天讀寫 S3 100 GB，走 NAT 一個月要多付 US$186，走 Gateway Endpoint 是 US$0。
# ═══ Gateway Endpoint（S3）—— 免費，直接建 ═══
$ aws ec2 create-vpc-endpoint \
    --vpc-id $VPC_ID \
    --service-name com.amazonaws.ap-northeast-1.s3 \
    --vpc-endpoint-type Gateway \
    --route-table-ids $RT_APP $RT_DB

# DynamoDB 同理
$ aws ec2 create-vpc-endpoint \
    --vpc-id $VPC_ID \
    --service-name com.amazonaws.ap-northeast-1.dynamodb \
    --vpc-endpoint-type Gateway --route-table-ids $RT_APP
建立之後，去看路由表會多出一條 pl-61a54008 → vpce-xxx。pl- 開頭的是 Prefix List，代表「S3 在這個 region 的所有 IP 範圍」，AWS 會自動維護。
# ═══ Interface Endpoint —— 常用的幾個 ═══
# SSM（Session Manager 連線用，取代堡壘主機）
$ for SVC in ssm ssmmessages ec2messages; do
    aws ec2 create-vpc-endpoint \
      --vpc-id $VPC_ID \
      --service-name com.amazonaws.ap-northeast-1.$SVC \
      --vpc-endpoint-type Interface \
      --subnet-ids $APP_A $APP_C \
      --security-group-ids $SG_ENDPOINT \
      --private-dns-enabled
  done

# ECR（容器拉映像檔）—— 注意要 api + dkr 兩個，還要加 S3 Gateway
$ for SVC in ecr.api ecr.dkr; do
    aws ec2 create-vpc-endpoint --vpc-id $VPC_ID \
      --service-name com.amazonaws.ap-northeast-1.$SVC \
      --vpc-endpoint-type Interface --subnet-ids $APP_A $APP_C \
      --security-group-ids $SG_ENDPOINT --private-dns-enabled
  done
Interface Endpoint 的三個常見坑：
  1. SG 要放行 443——Endpoint 的 ENI 也是網卡，要有安全群組允許來源存取 tcp/443，否則會 timeout
  2. VPC 要開 enable-dns-hostnames——不然 --private-dns-enabled 不會生效，程式還是會解析到公網 IP
  3. ECR 需要三個 endpoint——ecr.api、ecr.dkr，加上 S3 Gateway Endpoint（映像檔的 layer 實際存在 S3）。少一個就會拉不下來，而且錯誤訊息很模糊
SSM Session Manager 可以完全取代堡壘主機。建好三個 SSM endpoint 之後：
  • 私有子網路的 EC2 不需要公網 IP
  • 不需要開放 22 埠，SG 可以完全沒有入站規則
  • 不需要管理 SSH 金鑰
  • 所有操作自動記錄到 CloudTrail 和 S3，稽核直接過關
$ aws ssm start-session --target i-0abc123def456
這是目前 AWS 推薦的標準做法，SAA 考試也偏好這個答案。

Endpoint Policy：再收緊一層

# 只允許透過這個 endpoint 存取自家的 bucket
$ aws ec2 modify-vpc-endpoint --vpc-endpoint-id vpce-0abc123 \
    --policy-document '{
  "Statement": [{
    "Effect": "Allow",
    "Principal": "*",
    "Action": ["s3:GetObject", "s3:PutObject"],
    "Resource": ["arn:aws:s3:::company-data/*"]
  }]
}'
反過來，bucket policy 也可以要求「只接受從特定 VPC Endpoint 來的請求」，用 aws:SourceVpce 條件。兩邊搭配起來，就能做到「這個 bucket 只有這個 VPC 裡的機器讀得到，連有正確 IAM 權限的人從外面也讀不到」。這是處理敏感資料的標準做法。

8. VPC 之間怎麼連

方式適合可傳遞路由？費用
VPC Peering少數幾個 VPC 互連不行只收跨 AZ/跨區流量費
Transit Gateway多個 VPC + 本地機房可以每個連接每小時 + 流量費
PrivateLink只暴露單一服務給別人—Interface Endpoint 費用
Site-to-Site VPN連回公司機房（走網際網路）—每小時 + 流量
Direct Connect連回機房（專線，穩定低延遲）—昂貴，要簽約
VPC Peering 的兩個硬限制（必考）：
  1. 不支援傳遞路由（no transitive peering）。A↔B、B↔C 都通，但 A 和 C 不通。要通就得再建一條 A↔C。
    N 個 VPC 全互連需要 N(N−1)/2 條——跟 CH 3-3 的 iBGP 全網狀是同一個數學問題，解法也類似（用 Transit Gateway 當中心點，等同 Route Reflector）。
  2. CIDR 不能重疊。兩個 VPC 都是 10.0.0.0/16 就無法 Peering。這就是第 2 節強調網段規劃的原因。
# ═══ VPC Peering：三步驟 ═══
# ① 發起請求
$ PCX=$(aws ec2 create-vpc-peering-connection \
    --vpc-id $VPC_ID \
    --peer-vpc-id vpc-0target123 \
    --peer-owner-id 999988887777 \
    --query VpcPeeringConnection.VpcPeeringConnectionId --output text)

# ② 對方接受（在對方帳號執行）
$ aws ec2 accept-vpc-peering-connection --vpc-peering-connection-id $PCX

# ③ 兩邊都要加路由 —— 這步最常被忘記
$ aws ec2 create-route --route-table-id $RT_APP \
    --destination-cidr-block 10.1.0.0/16 --vpc-peering-connection-id $PCX
# 對方也要加一條指回 10.0.0.0/16
Peering 建好了還是不通？依序檢查：① 對方接受了嗎 ② 兩邊路由表都加了嗎 ③ 兩邊的安全群組允許對方網段嗎 ④ NACL 呢。四項缺一不可，而且「接受了」不代表「通了」——路由要自己加。

Transit Gateway：中心輻射式

　　　　　　　  [ VPC-Prod ]　　[ VPC-Stg ]　　[ VPC-Dev ]
　　　　　　　　　　 │　　　　　　　│　　　　　　　│
　　　　　　　　　　 └───────┬─────┴──────┬──────┘
　　　　　　　　　　　　　　　│             │
　　　　　　　　　　　  [ Transit Gateway ]
　　　　　　　　　　　　　　　│
　　　　　　　　　　　　  [ VPN / DX ]
　　　　　　　　　　　　　　　│
　　　　　　　　　　　  [ 公司機房 ]

每個 VPC 只要連 TGW 一次 → N 條連接，而不是 N(N−1)/2 條
Transit Gateway：每個 VPC attachment 每小時 US$0.07（約每月 US$50/個）+ 每 GB US$0.02。
5 個 VPC 接上去，光是連接費一個月就 US$250。VPC 數量少於 4~5 個時，Peering 通常更便宜；超過就換 TGW（省下的是管理成本和路由複雜度）。

9. Flow Logs 與網路排錯

VPC Flow Logs 記錄每個網路介面的流量摘要——誰連誰、哪個埠、被允許還是拒絕。這是 VPC 裡唯一能回答「封包到底有沒有到」的工具。

$ aws ec2 create-flow-logs \
    --resource-type VPC \
    --resource-ids $VPC_ID \
    --traffic-type ALL \
    --log-destination-type s3 \
    --log-destination arn:aws:s3:::my-flow-logs/vpc/ \
    --max-aggregation-interval 60

判讀 ACCEPT / REJECT 就能定位問題出在哪一層：
  • 看到 REJECT → 被 SG 或 NACL 擋了。去查那兩個
  • 看到 ACCEPT 但應用還是沒回應 → 封包有到，問題在作業系統防火牆或應用程式本身（服務沒起來、沒監聽該埠）
  • 完全沒有紀錄 → 封包根本沒到達。問題在路由表或來源端
這三種情況的排查方向完全不同，Flow Log 能省下大量時間。
Flow Logs 不記錄的內容（考試會考）：
  • DHCP 流量
  • 到 Amazon DNS 伺服器（VPC+2）的流量——用自己的 DNS 則會記錄
  • Windows 執行個體的授權啟用流量
  • 到 169.254.169.254（instance metadata）和 169.254.169.123（時間同步）的流量
  • 封包內容——Flow Log 只有摘要，要看內容得用 Traffic Mirroring

Reachability Analyzer：不用送封包就能查路徑

# 建立一個「從 A 能不能到 B」的分析
$ PATH_ID=$(aws ec2 create-network-insights-path \
    --source $BASTION_ENI \
    --destination $DB_ENI \
    --protocol tcp --destination-port 3306 \
    --query NetworkInsightsPath.NetworkInsightsPathId --output text)

$ aws ec2 start-network-insights-analysis --network-insights-path-id $PATH_ID
Reachability Analyzer 會直接告訴你「在哪一個元件被擋住」。例如「路由表 rtb-xxx 沒有到目的地的路由」或「安全群組 sg-xxx 的入站規則不允許 3306」。它是靜態分析，不需要真的開機器送封包，所以在資源還沒部署前就能驗證設計。每次分析約 US$0.10。

10. 連不上的九個檢查點

1
子網路的路由表對嗎？公有要有 0.0.0.0/0 → igw，私有要有 0.0.0.0/0 → nat。而且要確認子網路真的關聯到那張路由表，不是用到 Main。
2
IGW 掛到 VPC 了嗎？建立和掛載是兩個動作。describe-internet-gateways 看 Attachments。
3
執行個體有公網 IP 嗎？公有子網路的機器如果沒有公網 IP，一樣連不出去也連不進來。--associate-public-ip-address 或用 EIP。
4
SG 入站允許嗎？來源寫對了嗎（IP vs 安全群組）？埠對嗎？
5
SG 出站允許嗎？如果有人收緊過出站規則，回應可能出不去。
6
NACL 兩個方向都開了嗎？無狀態，入站和出站都要，而且回程要開 1024–65535。
7
NAT Gateway 在公有子網路嗎？狀態是 available 嗎？放錯子網路會建得起來但不通。
8
作業系統層的防火牆？Windows Firewall、Linux 的 iptables/firewalld。Flow Log 顯示 ACCEPT 卻連不上，就往這裡查。
9
服務真的起來了嗎？ss -tlnp 確認有在監聽，而且是監聽 0.0.0.0 不是 127.0.0.1——只綁 localhost 是很常見的疏忽。
真實案例：「私有子網路的機器裝不了套件」

症狀：yum update 卡住，但 ping 內網其他機器正常。

排查：路由表有 0.0.0.0/0 → nat-xxx，看起來正常。查 NAT Gateway → 它被建在 app-1a（私有子網路）裡。

原因：NAT Gateway 自己也需要走 IGW 才能出去，放在私有子網路等於自己也出不去。修法：刪掉重建在公有子網路。

真實案例：「RDS 的 endpoint 解析不出來」

症狀：nslookup mydb.xxx.rds.amazonaws.com 沒有結果。

排查：aws ec2 describe-vpc-attribute --attribute enableDnsHostnames → false。

原因：自建 VPC 的 enableDnsHostnames 預設是關的。修法：開啟它，立即生效。這也會影響 VPC Endpoint 的私有 DNS。

真實案例：「ECS 拉不到映像檔，但錯誤訊息看不懂」

症狀：Task 一直在 PROVISIONING 然後失敗，訊息只寫 CannotPullContainerError。

排查：Task 在私有子網路，建了 ecr.api 和 ecr.dkr 兩個 Interface Endpoint。

原因：ECR 的映像檔 layer 實際存在 S3，還需要 S3 Gateway Endpoint。修法：補上 S3 Gateway Endpoint（免費），立刻就通。

完整實作 Lab：三層式 VPC + 私有子網路上網

約 100 分鐘。建議用 CLI 而不是主控台——CLI 逼你理解每個參數。

這個 Lab 會產生費用，主要是 NAT Gateway（每小時約 US$0.062）和公網 IPv4（每小時 US$0.005/個）。
做兩小時大約 US$0.15，可以接受。但務必照最後的清理步驟刪乾淨——忘記刪一個月就是 US$45。
建議在開始前先確認第 01 章的 Budget 告警已經設好。

階段一：建立網路骨架

  1. 建立 VPC 10.0.0.0/16，開啟 dns-support 與 dns-hostnames
  2. 建立 6 個子網路（公有／應用／資料層 × 2 AZ），全部打上 Name 和 Tier 標籤
  3. 建立 IGW 並掛到 VPC
  4. 建立 3 張路由表：rt-public（→IGW）、rt-app（→NAT）、rt-db（不加對外路由）
  5. 每個子網路都明確關聯到對應的路由表（不要用 Main）

階段二：NAT 與出網

  1. 配置 EIP，在 public-1a 建立 NAT Gateway
  2. 把 rt-app 的 0.0.0.0/0 指向它
  3. 用 describe-route-tables 確認三張表的內容都正確

階段三：安全群組分層

  1. alb-sg：允許 0.0.0.0/0 的 80、443
  2. app-sg：只允許 來源 = alb-sg 的 8080
  3. db-sg：只允許 來源 = app-sg 的 3306
  4. endpoint-sg：允許來自 VPC CIDR 的 443

階段四：VPC Endpoint 與免堡壘連線

  1. 建立 S3 Gateway Endpoint（免費），關聯 rt-app 和 rt-db
  2. 建立三個 SSM Interface Endpoint（ssm、ssmmessages、ec2messages）
  3. 在 app-1a 開一台 t3.micro，不給公網 IP，掛上有 AmazonSSMManagedInstanceCore 的 Role
  4. 用 aws ssm start-session 連進去（不用 SSH 金鑰、不用開 22 埠）

階段五：驗證與排錯

  1. 開啟 VPC Flow Logs 輸出到 S3
  2. 在私有機器上 curl https://aws.amazon.com → 應該成功（走 NAT）
  3. aws s3 ls → 應該成功（走 Gateway Endpoint，不經過 NAT）
  4. 用 Reachability Analyzer 分析「app-1a 的機器 → db-1a 的 3306」
  5. 故意把 db-sg 的規則刪掉，再跑一次分析，觀察它指出哪個元件擋住

驗收清單

  • describe-subnets 顯示 6 個子網路，AvailableIpAddressCount 是 251（有 NAT 的那個是 250）
  • rt-db 的 Routes 只有一條 local
  • 私有子網路的 EC2 沒有公網 IP，但 curl 得到外網
  • aws ssm start-session 能連進去，且該機器的 SG 沒有任何入站規則
  • Flow Log 裡看得到 ACCEPT 和 REJECT 兩種紀錄
  • Reachability Analyzer 對正常路徑回傳 reachable，刪掉 SG 規則後回傳 not reachable 並指出 sg-xxx

清理（一定要做）

$ aws ec2 delete-vpc-endpoints --vpc-endpoint-ids $VPCE_S3 $VPCE_SSM ...

$ aws ec2 delete-internet-gateway --internet-gateway-id $IGW_ID
$ aws ec2 delete-vpc --vpc-id $VPC_ID     # 這會連帶刪掉子網路、路由表、SG

# 最後確認沒有漏掉的 EIP
$ aws ec2 describe-addresses --query 'Addresses[].[PublicIp,AssociationId]' --output table

加碼挑戰

  1. 在 1c 也建一個 NAT Gateway，做出每個 AZ 各自的私有路由表，並解釋這樣省下什麼費用。
  2. 寫一條 bucket policy，要求「只接受從你的 VPC Endpoint 來的請求」（aws:SourceVpce），然後從公網嘗試存取，確認被拒絕。
  3. 建立一個自訂 NACL，只允許 443 出站，觀察為什麼機器完全連不出去，再補上 ephemeral port 入站規則修好它。
  4. 把整個 VPC 用 CloudFormation 或 Terraform 重寫一次，體會 IaC 的價值（第 10 章會詳談）。
  5. 計算：如果應用每月從 S3 讀 500 GB，走 NAT Gateway 和走 Gateway Endpoint 的費用差多少？

本章重點回顧

  • 不要用 Default VPC——CIDR 全世界一樣，未來無法 Peering；但也不要刪掉它
  • VPC CIDR 建好不能縮小，子網路 CIDR 完全不能改。第一次就要規劃好
  • 每個子網路 AWS 保留 5 個 IP：/24 只有 251 個可用
  • 子網路不能跨 AZ；高可用最低要求是兩個 AZ
  • 公有子網路的唯一定義：路由表有 0.0.0.0/0 → IGW
  • 自建 VPC 記得開 enable-dns-hostnames，不然 RDS endpoint 和私有 DNS 都會出問題
  • NAT Gateway 必須放在公有子網路；一個月不關約 US$45，做完 Lab 要刪
  • SG 有狀態、只有 Allow、可引用安全群組；NACL 無狀態、有 Deny、要開 ephemeral port
  • SG 用 --source-group 互相引用，Auto Scaling 時完全不用改規則
  • S3 / DynamoDB 的 Gateway Endpoint 免費，一律建起來
  • ECR 需要 ecr.api + ecr.dkr + S3 Gateway 三個 endpoint
  • SSM Session Manager 取代堡壘主機：不用公網 IP、不開 22 埠、自動稽核
  • VPC Peering 不支援傳遞路由且 CIDR 不能重疊；多 VPC 用 Transit Gateway
  • 排錯順序：路由表 → IGW → 公網 IP → SG → NACL → OS 防火牆 → 服務有沒有起來
VPC 是 SAA-C03 最容易失分的地方，因為題目常常把路由表、SG、NACL 混在一起考。去 模擬試題 練一輪，特別注意「有狀態 vs 無狀態」的題型。
