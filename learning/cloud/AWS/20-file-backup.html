1. 三種儲存型態：先確定題目在問哪一種

區塊儲存（EBS）像一顆外接硬碟——插在一台機器上，你自己格式化、自己管檔案系統。
檔案儲存（EFS / FSx）像辦公室的網路磁碟機——很多人同時掛載，有資料夾與權限。
物件儲存（S3）像雲端硬碟的分享連結——用 API 上傳下載，沒有真正的目錄結構。

SAA 的儲存題第一步永遠是判斷型態。判斷錯了，後面選什麼都是錯的。

題目出現這些字型態候選服務
「掛載成磁碟」「單一 EC2」「作業系統開機碟」「高 IOPS 資料庫磁碟」區塊EBS、Instance Store
「多台同時存取」「NFS」「SMB」「共用目錄」「既有應用程式不改寫」檔案EFS、FSx 四種、Storage Gateway
「HTTP 存取」「靜態網站」「資料湖」「無限容量」「生命週期分層」物件S3、Glacier
最重要的分辨句：「應用程式無法修改，必須用檔案系統介面」——這句話一出現就不是 S3。這是 Lift-and-Shift 遷移題最愛的設計，答案一定在 EFS / FSx / Storage Gateway 裡面。
【 需要檔案系統介面 】 │ ┌───────────────┴───────────────┐ Linux / NFS Windows / SMB │ │ ┌──────┴──────┐ ┌──────┴──────┐ EFS FSx for FSx for FSx for 全受管 Lustre Windows NetApp ONTAP 自動擴展 HPC / ML AD 整合 NFS + SMB 都要 最省事 連結 S3 DFS iSCSI 也要 FSx for OpenZFS ← 地端 ZFS / Linux NFS 搬上來

2. FSx 家族四種：一次分清楚

FSx 是「AWS 幫你代管別人家的檔案系統」。四種各自對應一個既有生態，考試考的就是「哪個生態」。

種類協定為誰設計關鍵字
FSx for Windows
File Server		SMBWindows 檔案伺服器搬上雲Active Directory、NTFS ACL、DFS、使用者配額、Windows 應用程式
FSx for LustrePOSIX / LustreHPC、機器學習訓練高吞吐量、與 S3 連結、基因分析、影片轉檔、模型訓練
FSx for NetApp
ONTAP		NFS + SMB + iSCSI既有 NetApp 環境遷移多協定同時、SnapMirror、去重壓縮、FlexClone
FSx for OpenZFSNFS地端 ZFS / Linux NFS 遷移ZFS 快照、低延遲高 IOPS、不需改用戶端
四選一的判斷順序（照這個順序問，一定選得出來）

① 是 Windows 或需要 AD 驗證嗎？ → FSx for Windows File Server
② 是 HPC / ML，而且資料本來就在 S3？ → FSx for Lustre
③ 同時要 NFS 和 SMB（或提到 NetApp、iSCSI）？ → FSx for NetApp ONTAP
④ 只要 Linux NFS，而且從地端 ZFS 搬過來？ → FSx for OpenZFS
⑤ 都不是，就是單純的 Linux 共用目錄？ → EFS（不要硬選 FSx）

陷阱：Linux 共用目錄硬選 FSx
題目只說「多台 Linux EC2 要共用檔案、要跨 AZ、要全受管、要自動擴展」→ 答案是 EFS，不是 FSx for OpenZFS。
OpenZFS 是有特定理由才選（要 ZFS 快照語意、要極低延遲、要從地端 ZFS 平移）。EFS 才是 Linux 共用的預設答案。
FSx 都是「檔案系統」而不是「服務端點」，所以它們都活在你的 VPC 裡、有 ENI、要設 Security Group、要選子網路。這跟 S3 那種區域級服務端點是完全不同的東西——考題會用「要放在私有子網路且不經網際網路」來測試你有沒有搞混。

3. FSx for Windows 深入

它解決的是什麼

企業機房裡那台跑了十年的 Windows 檔案伺服器：AD 帳號登入、NTFS 權限、使用者家目錄、對應成 Z: 磁碟機。這種東西沒辦法改寫成 S3 API，也不能用 EFS（EFS 沒有 SMB、沒有 AD、沒有 NTFS ACL）。FSx for Windows 就是為了原封不動搬過來。

AD 整合可接 AWS Managed Microsoft AD，也可接自建／地端 AD。使用者用原本的帳號登入，NTFS ACL 照舊。
Single-AZ vs Multi-AZMulti-AZ 會在另一個 AZ 建待命檔案伺服器並同步複寫，自動容錯移轉。正式環境選 Multi-AZ。
DFS Namespaces把多個檔案系統合成一個命名空間（\\corp\shares），也可用 DFS Replication 做跨區複本。
使用者自助還原Windows 的「先前版本」（VSS 陰影複製）——使用者自己右鍵還原誤刪的檔案，不用開單給 IT。
資料去重與配額去重對一般檔案共享常見可省下相當比例的空間；配額可限制每個使用者用量。
SSD / HDDHDD 便宜很多，適合冷資料與大量文件；需要低延遲就選 SSD。
考題關鍵字對照：
「使用者要能自己還原誤刪的檔案」→ 陰影複製（先前版本）。
「要用現有網域帳號登入共用資料夾」→ FSx for Windows + AD 整合。
「檔案伺服器要跨 AZ 容錯」→ Multi-AZ 部署。
「地端使用者要低延遲存取雲端的 Windows 共用」→ FSx File Gateway（見第 6 節）。
# 建立 Multi-AZ 的 FSx for Windows，接上 AWS Managed Microsoft AD
$ aws fsx create-file-system \
    --file-system-type WINDOWS \
    --storage-capacity 300 \
    --storage-type SSD \
    --subnet-ids subnet-a subnet-c \
    --security-group-ids sg-fsx \
    --windows-configuration '{
        "ActiveDirectoryId": "d-9067f8abcd",
        "ThroughputCapacity": 32,
        "DeploymentType": "MULTI_AZ_1",
        "PreferredSubnetId": "subnet-a",
        "AutomaticBackupRetentionDays": 30,
        "DailyAutomaticBackupStartTime": "18:00",
        "CopyTagsToBackups": true
    }'

# Windows 端掛載（用 DNS 名稱，不要用 IP，容錯移轉時 IP 會變）
> net use Z: \\amznfsxabc123.corp.example.com\share
Multi-AZ 一定要用 DNS 名稱掛載。容錯移轉時 AWS 會把 DNS 指向待命端，如果你寫死 IP，切換後就再也連不上。這是實務上最常見的 FSx 事故，也是考題的錯誤選項。
成本提醒：FSx for Windows 的費用由儲存容量與吞吐容量（ThroughputCapacity）兩塊組成，而吞吐容量是獨立計費的——很多人一開始把它開得太大，帳單有一半是吞吐費而不是儲存費。先用小的、看 CloudWatch 的吞吐指標再往上調（吞吐容量可以線上調整）。冷資料多的話 HDD + 去重可以省下很可觀的比例。

4. FSx for Lustre 深入（與 S3 連結）

Lustre 是 HPC 界的標準平行檔案系統。它在 AWS 上最關鍵的能力不是「快」，而是能把 S3 儲存貯體當成自己的後端。

資料平常躺在 S3（便宜、耐久） s3://genomics-data/run-042/ │ │ ① 建立 FSx for Lustre 並連結該前綴 ▼ ┌────────────────────────┐ │ FSx for Lustre │ ← 物件變成 POSIX 檔案 │ /fsx/run-042/... │ 首次讀取時才真正載入（延遲載入） └────────────────────────┘ │ │ 運算節點 運算節點 ← 數百 GB/s 的總吞吐量 │ │ ② 算完把結果匯出回 S3 ▼ s3://genomics-data/results/ │ │ ③ 刪掉檔案系統，只留 S3 ▼ 運算費歸零，資料還在

Scratch vs Persistent：這是必考的一組

ScratchPersistent
資料複寫不複寫在同一個 AZ 內複寫
硬體故障時資料遺失自動偵測並修復
價格便宜較貴
適用短期批次運算、算完就丟長期執行、要求可用性
考題關鍵字「暫存」「臨時處理」「成本最低」「長時間執行」「不能遺失」
Lustre 的吞吐量是「跟著容量走」的——你選的是「每 TiB 多少 MB/s」，所以要更高吞吐就要買更大的容量。這跟 EBS 可以獨立調 IOPS 的直覺不一樣，成本題會用這點出題。
# 建立 Scratch 檔案系統並連結 S3（算完就刪的批次工作）
$ aws fsx create-file-system \
    --file-system-type LUSTRE \
    --storage-capacity 1200 \
    --subnet-ids subnet-a \
    --lustre-configuration '{
        "DeploymentType": "SCRATCH_2",
        "DataRepositoryConfiguration": {
            "ImportPath": "s3://genomics-data/run-042",
            "ExportPath": "s3://genomics-data/results",
            "ImportedFileChunkSize": 1024
        }
    }'

# 運算節點掛載
$ sudo mount -t lustre fs-0abc123.fsx.ap-northeast-1.amazonaws.com@tcp:/xyz1234 /fsx

# 把新產生的結果推回 S3（HSM 匯出）
$ sudo lfs hsm_archive /fsx/results/*.vcf
Lustre 題的標準句型：「資料在 S3，運算需要高吞吐量的 POSIX 檔案存取，結果要寫回 S3」——看到這句直接選 FSx for Lustre 連結 S3。EFS 是錯的（吞吐量與延遲都不到 HPC 等級），把 S3 用 aws s3 cp 抓下來也是錯的（要複製整份、又慢又佔磁碟）。

5. EFS 深入：儲存類別與吞吐模式

EFS 在第 03 章出現過，但只講了「Linux 共用、跨 AZ、自動擴展」。SAA 真正考的是成本分層與吞吐模式。

四種儲存類別（成本題核心）

類別耐久性用途相對成本
Standard多 AZ熱資料基準
Standard-IA多 AZ低頻存取，有取回費明顯較低
One Zone單一 AZ可重建的資料、開發環境約 Standard 的一半
One Zone-IA單一 AZ單 AZ 的冷資料最低
One Zone 的取捨要說清楚。它只存在一個 AZ，那個 AZ 掛掉檔案系統就不可用。省下來的錢是拿可用性換的。考題會用「開發測試環境要最低成本」暗示 One Zone，用「生產環境需高可用」排除它。

生命週期管理：自動把冷資料降級

# 30 天沒被存取就轉 IA，被存取到就自動轉回 Standard
$ aws efs put-lifecycle-configuration \
    --file-system-id fs-0abc123 \
    --lifecycle-policies \
        '[{"TransitionToIA":"AFTER_30_DAYS"},
          {"TransitionToPrimaryStorageClass":"AFTER_1_ACCESS"}]'
這是 EFS 成本題的標準答案。「EFS 費用太高，但不知道哪些檔案還在用」→ 啟用生命週期管理自動轉入 IA。不需要自己分析、不需要搬檔案，而且被讀到會自動轉回來。

吞吐模式

Elastic（建議預設）依實際需求自動伸縮，按用量付費。工作負載不可預測時最省事。
Bursting吞吐量跟著儲存容量走，用信用額度爆發。檔案少但要高吞吐時會撞牆。
Provisioned手動指定吞吐量，與容量脫鉤。適合「資料量小但吞吐需求高」且流量穩定的情況。
陷阱：EFS「效能突然變慢」
典型症狀是 Bursting 模式的信用額度用完了——因為儲存的資料量很小（例如只有幾 GB），基準吞吐量自然也很低。
解法：改用 Elastic（最省事）或 Provisioned 吞吐模式。不是「加大 EC2 規格」也不是「改用 EBS」。

Access Point：多租戶與 Lambda 的必備

EFS Access Point 讓你為每個應用程式指定強制的 POSIX 使用者身分與根目錄。掛上去之後，那個應用程式看到的就只有自己的目錄，也一定是以指定的 UID/GID 執行。
這是 Lambda 掛載 EFS 的標準做法，也是多團隊共用一個檔案系統時做隔離的方式。
實務提醒：EFS 每個 AZ 有一個 Mount Target（就是一個 ENI），EC2 一定要連自己那個 AZ 的 Mount Target——連到別的 AZ 不但多一跳延遲，還會產生跨 AZ 流量費。用 DNS 名稱掛載時 AWS 會自動導到正確的 Mount Target，所以永遠用 DNS 不要用 IP。另外掛載時加 -o tls（透過 amazon-efs-utils）才有傳輸加密，這在合規題裡常被考。

6. Storage Gateway 四種閘道

Storage Gateway 是「放在你機房的一台虛擬機（或實體裝置），把雲端儲存偽裝成地端的檔案／磁碟／磁帶」。它的價值在於地端應用程式一行都不用改。

閘道類型地端看到的介面雲端實際存在哪典型題目
S3 File GatewayNFS / SMBS3 物件（一個檔案 = 一個物件）「地端要用檔案介面把資料寫進 S3」
FSx File GatewaySMBFSx for Windows「分公司存取雲端 Windows 共用太慢，要在地端快取」
Volume Gateway
— Cached		iSCSI 磁碟主資料在 S3，熱資料在地端快取「地端磁碟空間不夠，但要保留低延遲存取」
Volume Gateway
— Stored		iSCSI 磁碟主資料在地端，非同步備份成 EBS 快照「地端要完整低延遲，雲端只當災備」
Tape Gateway虛擬磁帶庫（VTL）S3 → Glacier / Deep Archive「淘汰實體磁帶庫，但備份軟體不能換」
Cached vs Stored 的一句話區分

Cached：資料的家在雲上，地端只放常用的那些。→ 解決「地端空間不夠」。
Stored：資料的家在地端，雲上是備份。→ 解決「要災難復原」。

記法：Cached = 快取在地端（所以主體不在地端）；Stored = 儲存在地端（所以主體在地端）。名字說的就是「地端有什麼」。

陷阱 1：Tape Gateway 的關鍵字是「備份軟體不變」
題目通常會寫「公司使用 Veeam / NetBackup / Commvault，希望淘汰實體磁帶但不想更換備份軟體」→ Tape Gateway。因為它對備份軟體來說就是一台磁帶庫。
陷阱 2：把 DataSync 和 Storage Gateway 搞混
DataSync = 搬家（一次性或排程的資料傳輸，搬完就結束）。
Storage Gateway = 長住（持續的混合存取，地端一直透過它讀寫雲端）。
題目說「遷移」「同步一次」→ DataSync；說「地端持續存取」→ Storage Gateway。這組在第 15 章也考過，是高頻出題點。
實務提醒：Storage Gateway 的效能幾乎完全取決於地端快取磁碟的大小與速度。快取太小會不停回源到 S3，使用者的感受就是「這個網路磁碟機好慢」。部署前先估算工作集（實際會被反覆存取的資料量），快取至少要蓋得住它。另外閘道本身是單台 VM——它是單點故障，正式環境要規劃備援或至少有快速重建的流程。

7. AWS Backup：把備份收成一件事

沒有 AWS Backup 之前，備份是散的：EBS 靠快照排程、RDS 靠自動備份設定、DynamoDB 靠 PITR、EFS 靠自己寫 Lambda……每個服務一套介面、一套保留政策，稽核要交報表時沒有人答得出「我們到底備份了什麼、保留多久」。AWS Backup 就是為了回答這個問題。

四個核心元件

Backup Plan（備份計畫）定義什麼時候備、保留多久、何時轉冷儲存、要不要複製到別的區域／帳號。
Resource Assignment（資源指派）用標籤或資源 ID 決定哪些資源套用這個計畫。用標籤最好——新資源打上標籤就自動納管。
Backup Vault（保存庫）備份存放的地方，用 KMS 金鑰加密。可以分成生產／測試不同 Vault。
Backup Policy（組織政策）在 Organizations 層級套用，強制所有成員帳號都有備份，成員帳號無法關掉。

支援哪些服務（考點）

運算與儲存EC2、EBS、EFS、FSx（全部四種）、S3、Storage Gateway 磁碟區
資料庫RDS、Aurora、DynamoDB、DocumentDB、Neptune、Redshift
其他VMware 工作負載、Timestream、CloudFormation 堆疊
「多個帳號、多種服務、統一的備份與保留政策、還要跨區域複製」——只要題目湊齊這幾個條件，答案就是 AWS Backup + Organizations 備份政策。自己寫 Lambda 排程快照是常見的錯誤選項（它「可行」，但維運負擔高，考試不選）。
# ── ① 建立備份計畫：每日備份、保留 35 天、90 天後轉冷、跨區複製 ──
$ aws backup create-backup-plan --backup-plan '{
    "BackupPlanName": "prod-daily",
    "Rules": [{
        "RuleName": "daily-35d",
        "TargetBackupVaultName": "prod-vault",
        "ScheduleExpression": "cron(0 18 * * ? *)",
        "StartWindowMinutes": 60,
        "CompletionWindowMinutes": 180,
        "Lifecycle": {
            "MoveToColdStorageAfterDays": 90,
            "DeleteAfterDays": 365
        },
        "CopyActions": [{
            "DestinationBackupVaultArn": "arn:aws:backup:us-west-2:111122223333:backup-vault:dr-vault",
            "Lifecycle": {"DeleteAfterDays": 365}
        }]
    }]
}'

# ── ② 用標籤指派資源：所有 Backup=prod 的資源自動納管 ──
$ aws backup create-backup-selection \
    --backup-plan-id abcd-1234 \
    --backup-selection '{
        "SelectionName": "tag-prod",
        "IamRoleArn": "arn:aws:iam::111122223333:role/AWSBackupDefaultServiceRole",
        "ListOfTags": [{"ConditionType":"STRINGEQUALS","ConditionKey":"Backup","ConditionValue":"prod"}]
    }'

# ── ③ 查有沒有漏網之魚（哪些資源沒被任何計畫涵蓋）──
$ aws backup list-protected-resources \
    --query 'Results[].[ResourceArn,LastBackupTime]' --output table
用標籤指派是關鍵設計。如果用資源 ID 一個一個列，下個月新開的機器就漏了。用 Backup=prod 這種標籤，再搭配 SCP 或 Config 規則強制新資源必須有標籤，備份覆蓋率才不會隨時間衰退。

還原測試：稽核最愛問的一題

AWS Backup 的「還原測試計畫」可以定期自動還原備份、驗證可用性、再自動清掉。這解決了備份界的經典問題——備份天天成功，但沒有人確認過真的還原得回來。考題會用「如何證明備份是可還原的」來問這個功能。
實務提醒：導入 AWS Backup 時最常見的意外是帳單跳高——因為它把原本沒在備份的東西也一起納管了。上線前先用「標籤指派 + 只掛少數資源」跑一個月，看清楚成本結構再擴大。另外冷儲存有最短保留天數，提前刪除仍會按最短天數計費，設定生命週期時要把這點算進去。

8. Vault Lock 與 DLM 的分界

Backup Vault Lock：讓備份連管理員都刪不掉

模式能不能反悔用途
Governance 模式可以——具備特定 IAM 權限的人可以解除防止誤刪，但保留管理彈性
Compliance 模式不可以——冷卻期過後任何人都無法解除，包括 root 與 AWS法規要求的 WORM（一次寫入多次讀取）
Compliance 模式是不可逆的。設定時有一段冷卻期（可以反悔），冷卻期一過就再也沒有退路——保留期內誰都刪不掉，而且你要一直付這些備份的儲存費直到期滿。
只在法規真的要求 WORM 時才用，而且務必先用短保留期在測試帳號演練過。
考題對照：
「備份必須防止被惡意刪除，包括擁有管理員權限的內部人員」→ Vault Lock（Compliance 模式）。
對照 S3 那邊的等價功能是 S3 Object Lock——同樣有 Governance / Compliance 兩種模式，同樣的邏輯。
再對照勒索軟體題型：跨帳號複製到獨立的備份帳號 + Vault Lock 是標準答案，因為攻擊者拿到生產帳號權限也動不了備份帳號。

Data Lifecycle Manager（DLM）：輕量版

DLM 管什麼只有 EBS 快照與 EBS-backed AMI。依標籤觸發，可設保留數量、跨區複製、快速快照還原。
AWS Backup 管什麼十幾種服務，加上跨帳號、組織政策、Vault Lock、還原測試、合規報表。
怎麼選只有 EBS 而且需求單純 → DLM（更輕、免費）。
多服務或有稽核需求 → AWS Backup。
陷阱：看到「快照排程」就選 DLM
如果題目裡出現 RDS、EFS、DynamoDB、FSx 任何一個，DLM 就不成立——它只管 EBS。
反過來，如果題目只講 EBS 快照、而且強調「最簡單、原生、不想多裝東西」，那 DLM 才是比 AWS Backup 更貼切的答案。

備份三個層次，別搞混

① 服務原生備份 RDS 自動備份、DynamoDB PITR、EFS 自動備份 → 最快啟用，但各自為政 ② DLM EBS 快照 / AMI 的排程與保留 → 輕量，只管區塊儲存 ③ AWS Backup 跨服務 · 跨帳號 · 跨區域 · Vault Lock · 稽核報表 → 企業級答案，SAA 的預設選擇

實作 Lab：EFS 生命週期 + AWS Backup 完整流程

約 60 分鐘（含等待備份完成）。這個 Lab 走完「建立共用檔案系統 → 納入集中備份 → 驗證還原」的完整循環。

費用很低但不是零：EFS 幾 GB 的儲存費、備份的儲存費、兩台 t3.micro。全部做完約在 US$0.5 以內。Vault Lock 這一段請用 Governance 模式演練，絕對不要在自己的帳號開 Compliance 模式——那是不可逆的，會讓你被迫付費到保留期滿。

階段一：建立 EFS 並讓兩台 EC2 共用

  1. 建立 EFS 檔案系統（Regional、加密開啟），在兩個 AZ 各建一個 Mount Target
  2. Security Group 規劃：EC2 的 SG 當來源，EFS 的 SG 放行 NFS 2049 埠（來源指定 EC2 的 SG，不要用 CIDR）
  3. 兩個 AZ 各開一台 EC2，安裝 amazon-efs-utils 並掛載
  4. 在 A 機寫檔案，到 B 機確認看得到——驗證共用生效
# 掛載（-o tls 才有傳輸加密，合規題必考）
$ sudo yum install -y amazon-efs-utils
$ sudo mkdir -p /mnt/efs
$ sudo mount -t efs -o tls fs-0abc123:/ /mnt/efs

# 寫進 /etc/fstab 才會開機自動掛載
$ echo "fs-0abc123:/ /mnt/efs efs _netdev,tls 0 0" | sudo tee -a /etc/fstab

# 確認掛到的是「自己這個 AZ」的 Mount Target
$ df -h /mnt/efs && mount | grep efs

階段二：開啟生命週期管理

  1. 設定 30 天未存取轉入 IA、被存取時轉回 Standard
  2. 到 CloudWatch 看 StorageBytes 指標，確認有分 Standard 與 IA 兩個維度

階段三：納入 AWS Backup

  1. 幫 EFS 打上標籤 Backup=lab
  2. 建立 Backup Vault（用預設 KMS 金鑰即可）
  3. 建立 Backup Plan：每日一次、保留 7 天（測試用短保留）
  4. 用標籤建立資源指派（不要用資源 ID）
  5. 手動觸發一次 On-Demand Backup，不用等排程
  6. 備份完成後，在 EFS 裡刪掉一個檔案，然後從備份還原到新的檔案系統，確認檔案回來了
# 立即備份一次
$ aws backup start-backup-job \
    --backup-vault-name lab-vault \
    --resource-arn arn:aws:elasticfilesystem:ap-northeast-1:111122223333:file-system/fs-0abc123 \
    --iam-role-arn arn:aws:iam::111122223333:role/service-role/AWSBackupDefaultServiceRole

# 看備份工作狀態
$ aws backup list-backup-jobs --by-state COMPLETED \
    --query 'BackupJobs[].[ResourceType,BackupSizeInBytes,CompletionDate]' --output table

# 列出可還原點
$ aws backup list-recovery-points-by-backup-vault --backup-vault-name lab-vault \
    --query 'RecoveryPoints[].[RecoveryPointArn,CreationDate,Status]' --output table
還原 EFS 會建立「新的」檔案系統或還原到指定目錄，不會覆蓋原本的。這是好事（不會二次災難），但也代表還原後要自己切換掛載點。演練時要把這一步也走過，不然真正出事時才發現流程沒接上。

階段四：清理

  1. 刪除還原出來的檔案系統
  2. 刪除還原點 → 刪除 Backup Vault（Vault 裡還有還原點就刪不掉）
  3. 刪除 Backup Plan 與資源指派
  4. 終止 EC2，刪除 Mount Target 與 EFS

10. 考試陷阱整理

陷阱 1：Windows 共用選 EFS
EFS 是 NFS，沒有 SMB、沒有 AD 整合、沒有 NTFS ACL。Windows 檔案共用一定是 FSx for Windows File Server。
陷阱 2：HPC 選 EFS
EFS 的吞吐與延遲撐不起 HPC。「高吞吐 POSIX + 資料在 S3」→ FSx for Lustre。
陷阱 3：Linux 共用硬選 FSx for OpenZFS
單純的 Linux 共用目錄，EFS 才是預設答案。OpenZFS 是有 ZFS 快照或極低延遲需求時才選。
陷阱 4：同時要 NFS 和 SMB 卻選了兩套
「同一份資料要同時給 Linux（NFS）和 Windows（SMB）存取」→ FSx for NetApp ONTAP（多協定），不是建兩個檔案系統。
陷阱 5：Lustre Scratch 用在正式環境
Scratch 不做複寫，硬體故障資料就沒了。長期執行、不能遺失 → Persistent。
陷阱 6：EFS 變慢就加大 EC2
典型原因是 Bursting 模式信用額度用完（資料量小 → 基準吞吐低）。解法是改 Elastic 或 Provisioned 吞吐模式。
陷阱 7：Cached 與 Stored Volume Gateway 反了
Cached = 主資料在雲（解決地端空間不足）；Stored = 主資料在地端（解決災難復原）。名字說的是「地端有什麼」。
陷阱 8：DataSync 與 Storage Gateway 混用
DataSync 是搬家（一次性／排程傳輸），Storage Gateway 是長住（持續混合存取）。
陷阱 9：DLM 拿來備份 RDS
DLM 只管 EBS 快照與 AMI。題目出現 RDS / EFS / DynamoDB / FSx → AWS Backup。
陷阱 10：以為 Governance 模式擋得住管理員
Governance 模式可以被有權限的人解除。要連 root 都刪不掉必須是 Compliance 模式（且不可逆）。
陷阱 11：勒索軟體題只答「開啟備份」
備份跟生產在同一個帳號，攻擊者拿到權限一樣刪得掉。標準答案是 跨帳號複製到獨立備份帳號 + Vault Lock。
陷阱 12：FSx Multi-AZ 用 IP 掛載
容錯移轉後 IP 會變。永遠用 DNS 名稱掛載——EFS 也一樣。
💡一句話記憶：
Windows 找 FSx Windows，HPC 找 Lustre，雙協定 找 ONTAP，Linux 一般共用 找 EFS；
地端搬一次用 DataSync，地端一直用就架 Storage Gateway；
備份要統一用 AWS Backup，要刪不掉加 Vault Lock，只有 EBS 才輪得到 DLM。
