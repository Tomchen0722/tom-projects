1. Cognito 兩個池：本質定位與核心差異

User Pool (用戶池) = 「你是誰？」 → 身分驗證 (Authentication / AuthN) → 發放 JWT Token
Identity Pool (身分池) = 「你能做什麼？」 → 授權 (Authorization / AuthZ) → 發放 AWS STS 臨時憑證

Cognito User Pool (IdP 身分提供者)

  • 使用者資料庫目錄（儲存 Email、帳號、密碼雜湊、自訂屬性）。
  • 內建註冊、忘記密碼、MFA、信箱簡訊驗證機制。
  • 支援外部第三方社交登入（Google、Apple、Facebook）及企業 SAML 2.0 / OIDC SSO。
  • 登入成功後，客戶端取得 三種 JWT Token（ID / Access / Refresh Token）。
  • 無法直接調用底層 AWS 原生 API（如不能直接拿 JWT 去 s3:PutObject）。

Cognito Identity Pool (聯合身分聯合器)

  • 不儲存任何使用者帳密，沒有使用者目錄。
  • 作為身分轉換器：接收外部 Token 並向 AWS STS 換取 IAM 臨時憑證（AccessKeyId, SecretAccessKey, SessionToken）。
  • 支援來源：Cognito User Pool、Google、Facebook、SAML、OpenID Connect、甚至是未認證匿名訪客 (Guest)。
  • 換出的憑證具備關聯的 IAM Role，可以直接呼叫 S3、DynamoDB、Kinesis。
  • 支援精細化行級權限（Row-Level Security / Column-Level Security）。
考試絕對高頻組合題：
題目問：「行動 App 需要讓使用者透過 Facebook 或 Email 登入，並能直接將個人自拍照上傳到專屬的 S3 資料夾，且不經過任何後端伺服器 EC2/Lambda 中轉？」
→ 標準答案：Cognito User Pool（負責身分鑑別）+ Cognito Identity Pool（換發 STS 憑證並綁定 S3 權限政策）！

2. Cognito User Pool：三種 JWT Token 與進階功能

當使用者在 User Pool 成功通過身分鑑別後，AWS 會向客戶端發回三種標準 JSON Web Tokens (JWT)：

Token 類型格式與特性包含酬載內容 (Claims)核心用途與目標
ID Token JWT (經 RSA 私鑰簽章) 使用者個人身份檔案（sub, email, cognito:groups, 自訂屬性等）。 前端客戶端消費。App 根據裡面的名字或頭像渲染使用者介面。
Access Token JWT (經 RSA 私鑰簽章) 授權範圍（scope）、權限組別（cognito:groups）、發行者（iss）。不包含用戶隱私欄位。 呼叫後端 API Gateway。API Gateway 的 Cognito Authorizer 主要以此 Token 驗證權限。
Refresh Token 非 JWT 加密字串 長期有效憑證（預設 30 天，可設 1 小時至 10 年）。 用於向 User Pool 換取全新的 ID Token 與 Access Token，使使用者不需頻繁重複輸入密碼。

Lambda 觸發器（Lambda Triggers）四大核心時機

User Pool 的生命週期各個階段均可掛載 Lambda 函式注入客製化邏輯：

觸發時機 (Trigger)執行時機點典型企業實戰場景
Pre Sign-up使用者送出註冊表單，尚未寫入資料庫前白名單驗證：只允許公司特定網域（如 @company.com）註冊，拒絕其餘公開信箱。
Post Confirmation使用者點擊驗證信或輸入簡訊驗證碼後資料同步：自動在 DynamoDB 建立新使用者專屬的檔案記錄，或發送 Slack 迎新通知。
Pre Token Generation即將簽發 JWT Token 之前動態加料：向關聯式資料庫查詢用戶的 VIP 訂閱等級或角色，動態注入至 JWT Claims 中。
Custom Message系統準備寄送驗證碼信件或簡訊前客製化郵件主旨、樣板風格與企業 Logo。

進階安全功能 (Advanced Security Features - ASF)

外洩憑證檢查 (Compromised Credentials)自動比對網路上黑客洩漏的公開帳密字典庫，若用戶使用外洩密碼，強制要求其重設密碼。
自適應風險驗證 (Adaptive Authentication)監控用戶登入的 IP 位置、裝置特徵與時間。若判定為高風險可疑登入，動態強制觸發 SMS / TOTP 二次驗證 (MFA)。

3. Cognito Identity Pool：STS 臨時憑證與精細化授權

Identity Pool 是連接外部身分與 AWS IAM 雲端資源的樞紐。以下為標準憑證交換時序圖：

使用者 App │ 1. 帳號密碼登入 ▼ Cognito User Pool (或 Google / Facebook / SAML) │ 2. 驗證成功，發送 JWT ID / Access Token ▼ 使用者 App │ 3. 攜帶 JWT Token 呼叫 Identity Pool ▼ Cognito Identity Pool │ 4. 驗證 JWT 合法性，呼叫 STS: AssumeRoleWithWebIdentity ▼ AWS STS (Security Token Service) │ 5. 回傳 IAM 臨時金鑰 (AccessKeyId, SecretAccessKey, SessionToken，有效期 1~12 小時) ▼ 使用者 App (持有 STS 憑證) │ 6. 直連 AWS 資源，無需後端伺服器！ ├── 直接 `s3:PutObject` 上傳圖片至 S3 └── 直接 `dynamodb:PutItem` 寫入遙測數據

精細化行級安全 (Row-Level Security) 實務政策

{ "Version": "2012-10-17", "Statement": [ { "Effect": "Allow", "Action": [ "s3:GetObject", "s3:PutObject", "s3:DeleteObject" ], "Resource": [ "arn:aws:s3:::my-secure-app-bucket/home/${cognito-identity.amazonaws.com:sub}/*" ] } ] }
💡 變數 ${cognito-identity.amazonaws.com:sub} 是每個使用者在 Identity Pool 中的全域唯一識別碼。如此一來，只需寫一份通用 IAM Policy，數百萬使用者即可完全隔離在各自的 S3 目錄，絕無越權風險！

5. API Gateway 三種端點類型（Edge vs Regional vs Private）

1. Edge-Optimized (邊緣最佳化) 請求由全球 CloudFront Edge Locations 就近接入，再透過 AWS 高速骨幹網路送達 API Gateway。

適用：跨國全球用戶、分散式客戶端存取。
備註：此端點自帶 CloudFront，不可在外層再套一層 CloudFront！
2. Regional (區域端點) 端點位於特定 AWS 區域（如 ap-northeast-1）。請求直接打到該區域。

適用：用戶集中在同一地理區域、或架構師想自訂 CloudFront 分發（例如前置 WAF 或快取）。
3. Private (私有端點) 完全不對網際網路開放！只能從指定的 VPC 內部，透過 Interface VPC Endpoint (AWS PrivateLink) 存取。

適用：金融內網、企業專有微服務、嚴格合規禁止外網暴露之系統。
考試避坑：CloudFront + API Gateway 的搭配禁忌
如果題目要求在 API Gateway 前方部署自訂的 CloudFront 分發（用以自訂網域名稱、SSL 或自訂快取策略），API Gateway 端點類型必須設定為 Regional，絕對不能設為 Edge-Optimized（不能將 CloudFront 指向另一個由 AWS 全託管的 Edge CloudFront）！

6. API Gateway 三種授權防護機制全解

授權方式底層原理快取支援 (Cache)最佳應用場景
Cognito User Pool Authorizer API Gateway 原生解析並校驗 Cognito 簽發的 JWT Access/ID Token。無須自寫代碼。 由 AWS 託管驗證，高併發效能極佳。 終端使用者以手機 App 或瀏覽器登入後的 API 呼叫。
Lambda Authorizer
(自訂授權器)		 API Gateway 收到請求後先呼叫自訂 Lambda 函式，由代碼解析 Token 或 Header，回傳一份 IAM Allow/Deny Policy。 ✅ 支援快取！可設定 TTL（預設 300 秒，最高 3600 秒），避免每次請求重複打 Lambda。 使用第三方 Auth0、Okta、自建 OAuth2 伺服器，或需要自訂多重簽名運算。
IAM 授權 (SigV4) 客戶端使用 AWS AccessKey/SecretKey，透過 Signature Version 4 演算法對 HTTP 請求進行數位簽署。 無需額外驗證步驟，AWS 原生支援。 微服務內部通訊、EC2 / Lambda 角色互相呼叫（Service-to-Service）。不適合前台用戶。

Resource Policy（API 資源政策）

除了用戶身份授權外，API Gateway 還具備自身的 Resource Policy。即使客戶端持有合法的 JWT，若 Resource Policy 不允許其來源 IP 或來源 VPC Endpoint，請求同樣會被阻斷在最外層。

7. 流量控制與防護：Usage Plans、Throttling 與快取

客戶端請求流入 ↓ 1. API Gateway 快取檢查 (Cache Cluster) ──命中 (Hit)──→ 直接回傳資料（不打後端 Lambda / 節省成本） ↓ 未命中 (Miss) 2. Token Bucket 演算法限流 (Throttling) ├── Rate（速率）：穩定允許的每秒請求數 (RPS) └── Burst（突發上限）：Token 桶容量，短時間內允許的最大爆發數 ↓ 超過閾值 → 即刻回傳 HTTP 429 Too Many Requests 3. Usage Plans (使用量計劃) 檢查 └── 檢查 API Key 當月配額（例如 Basic 方案每月限 10,000 次） ↓ 轉發至後端 Lambda / ECS / RDS
快取金鑰 (Cache Keys) 與自訂覆寫
在 API Gateway 啟用快取時，預設是以整條路徑為快取鍵。但如果你的 API 是 /products?category=shoes，必須在 Method Request 設定中將 category 查詢字串參數勾選為 Cache Key，否則查詢衣服與鞋子會回傳相同的快取結果！

8. AWS Organizations 與 SCP 階層繼承樹

SCP（Service Control Policy）是整個企業集團的「公司最高憲章」：它不授予任何權限，它只設定「絕對邊界（Guardrails）」。就算某個子公司的 IT 總監擁有 AdministratorAccess，如果總公司的 SCP 寫了 Deny ec2:*，該總監也休想啟動任何一台 EC2！
Root (根目錄) ── 套用 [SCP-1: 禁止離開組織] ├── Management Account ⚠️ 核心考點：SCP 對 Management Account 完全無效！ │ ├── Security OU ── 套用 [SCP-2: 禁止關閉 CloudTrail] │ └── Log Archive Account │ └── Production OU ── 套用 [SCP-3: 僅允許日本區域 ap-northeast-1] ├── App-Prod-1 Account └── Finance Sub-OU ── 套用 [SCP-4: 嚴禁刪除 S3 Glacier] └── Fin-Ledger Account (同時繼承 SCP-1 + SCP-3 + SCP-4)
繼承與評估規則運作機制細節常見實務陷阱
白名單模式 vs 黑名單模式 預設所有 OU 都附帶 FullAWSAccess（允許所有）。黑名單模式即保留 FullAWSAccess，只附加特定 Deny 陳述句。 若意外移除了某節點的 FullAWSAccess 且未給予相應 Allow，該 OU 下所有帳號將失去一切權限！
Explicit Deny 絕對優先 在繼承路徑上的任何一層 OU 出現 Deny，子層級無論如何都無法覆寫或解除該阻斷。 父層 Deny S3，子層再怎麼 Allow S3 也無濟於事。
對 Root 使用者有效 SCP 能夠有效封鎖 Member Account 的 Root 使用者！ 常考：防範成員帳號的 Root 帳密遭駭，唯一能在全組織層級限制其權限的就是 SCP。

9. AWS IAM 權限評估決策流（Evaluation Logic）全景

當一個請求（例如使用者張三嘗試 s3:DeleteBucket）送達 AWS 時，系統是如何做出最終決策的？以下為六大權限防線的交集判定邏輯：

請求發起 (RequestContext) │ ▼ 【步驟 1：Explicit Deny 檢查】── 只要任何一處有 Deny ──→ [DENY 拒絕] │ (SCP、Permissions Boundary、Identity Policy、Resource Policy 任一 Deny 立即終止) ▼ 【步驟 2：Organizations SCP 檢查】── 是否屬於被允許範圍？ ── 否 ──→ [DENY 拒絕] │ 是 ▼ 【步驟 3：Permissions Boundary (權限邊界) 檢查】── 超出邊界？ ── 是 ──→ [DENY 拒絕] │ 落在邊界內 ▼ 【步驟 4：Identity-based Policy ∩ Resource-based Policy】 ├── 同帳號內部存取：兩者只要任一者 Explicit Allow 即可通行！ └── 跨帳號 (Cross-Account) 存取：必須兩邊同時 Explicit Allow 才能放行！ │ ▼ 所有檢查通過 ──→ [ALLOW 允許執行]
權限交集核心公式：
最終有效權限 = SCP ∩ Permissions Boundary ∩ Identity-based Policy ∩ Session Policy
任何一個集合沒有包含該操作，結果必定為 Implicit Deny（隱式拒絕）！

10. 常見認證與 API Gateway 故障排查手冊

狀態碼 / 錯誤訊息根本原因診斷標準排查措施
403 Forbidden: Missing Authentication Token 1. 呼叫的路徑 (Path) 或 HTTP Method 根本不存在。
2. 忘記在 API Gateway 進行 Deploy API 至對應的 Stage（如 prod）。		 核對 URL 是否有拼錯字；檢查該變更是否已發布部署到 Stage。
401 Unauthorized 1. 未攜帶 Authorization Header。
2. JWT Token 已過期或簽章無效。
3. 誤傳了 ID Token 代替 Access Token。		 檢查客戶端 Token 有效期限；確認 API Gateway Cognito Authorizer 的 Token Source Header 設定。
CORS Error: No 'Access-Control-Allow-Origin' header 前端瀏覽器跨域呼叫時，API Gateway 未針對 OPTIONS 預檢請求 (Preflight) 回傳相應的 CORS 標頭。 在 API Gateway 主控台點選 Enable CORS；在後端 Lambda 的回傳值字典中明確加上 headers: {"Access-Control-Allow-Origin": "*"}。
504 Gateway Timeout 後端整合服務（如 Lambda 或內部 EC2）處理時間超過了 API Gateway 的最大硬性超時限制（29 秒）。 將同步架構改為異步解耦架構：API Gateway 接收請求後直接丟入 SQS 佇列回傳 202 Accepted，由後台 Worker 非同步處理。

11. SAA-C03 經典四大跨服務架構組合

模式一：App 直連 S3 安全架構 User Pool 驗證 → Identity Pool 換 STS → 透過 ${cognito-identity.amazonaws.com:sub} 寫入專屬 S3 目錄。零伺服器開銷。
模式二：B2B API 計費商業模式 REST API + Usage Plans + API Keys。將不同付費等級的企業客戶綁定至不同的 RPS 限流與每月呼叫額度。
模式三：極致低成本微服務 HTTP API + JWT Authorizer (驗證 OIDC/Cognito) + Lambda Proxy + DynamoDB。比傳統 REST API 節省 70% 費用。
模式四：大型多帳號安全登陸區 AWS Control Tower + Organizations。使用 SCP 強制封鎖非營運區域、強制啟用 CloudTrail、並將日誌集中至獨立審計帳號。

12. 考試陷阱速查與關鍵字對照

題目關鍵字描述標準解法常見干擾選項（避坑）
「匿名訪客需要下載公開範例檔案」 Cognito Identity Pool (Enable Unauthenticated Identities) 不要選建立公開的 IAM 使用者！
「阻止成員帳號的管理員擅自關閉 VPC Flow Logs」 Organizations SCP (Deny ec2:DeleteFlowLogs) 不要選在成員帳號設定 IAM Policy，因為該管理員可自行修改 IAM！
「微服務即時雙向聊天室通知」 API Gateway WebSocket API 不要選 HTTP 長輪詢 (Polling) 或 REST API！
「REST API 需要防禦 SQL 注入與 XSS 攻擊」 API Gateway REST API + AWS WAF WebACL 注意：HTTP API 原生不支援直接掛載 WAF！
