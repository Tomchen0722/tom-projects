1. 高可用的三個層級

層級抵禦什麼做法成本
單一 AZ 多台單台機器故障ASG min=2低
多 AZ整個資料中心故障ASG 跨 2–3 個 AZ + ALB中（標準做法）
多 Region整個地區故障Route 53 + 跨區複製高
可用性計算

99%　　= 每年停機 3.65 天
99.9%　= 每年停機 8.77 小時
99.95% = 每年停機 4.38 小時
99.99% = 每年停機 52.6 分鐘
99.999% = 每年停機 5.26 分鐘
串聯的元件，可用性是相乘的。
ALB(99.99%) × EC2(99.99%) × RDS(99.95%) = 99.93%

不是 99.99%，是比最弱的那個還低
所以提升可用性要從最弱的環節下手。上面這個例子裡，把 RDS 開 Multi-AZ 的效益遠大於把 EC2 從 2 台加到 4 台。
多 AZ 的最低要求（AWS 建議）：
  • 至少 2 個 AZ，每個 AZ 的容量要能單獨撐住全部流量
  • 更省的做法是 3 個 AZ——掛一個還剩 2/3 容量，所以每個 AZ 只要準備 50% 冗餘而不是 100%
  • 資料庫、快取、儲存每一層都要跨 AZ，只有應用層跨 AZ 沒有意義

2. 四種負載平衡器怎麼選

ALB第 7 層（HTTP/HTTPS）。絕大多數 Web 應用用它。可依路徑、網域、標頭分流。
NLB第 4 層（TCP/UDP/TLS）。極低延遲、每秒數百萬連線、可給靜態 IP。
GWLB第 3 層。串接第三方防火牆 / IDS 設備。
CLB舊版，已不建議使用。只有既有系統還在用。
ALBNLB
OSI 層級7（應用層）4（傳輸層）
協定HTTP、HTTPS、gRPCTCP、UDP、TLS
依內容分流可以（路徑、Host、標頭、查詢字串、來源 IP）不行
靜態 IP不行（只有 DNS 名稱）可以（每 AZ 一個）
延遲約 400 微秒約 100 微秒
保留來源 IP放在 X-Forwarded-For 標頭直接保留
WAF 整合可以不行
Lambda 當目標可以不行
考題關鍵字對照：
題目說答案
「依 URL 路徑分流到不同服務」「微服務」ALB
「需要固定 IP 讓客戶加白名單」NLB
「每秒數百萬請求」「極低延遲」「遊戲伺服器」NLB
「UDP」「MQTT」「非 HTTP 協定」NLB
「需要 WAF 防護」ALB（+ WAF）
「串接第三方防火牆設備」GWLB
ALB 沒有固定 IP，而且 IP 會變。它的 IP 由 AWS 動態管理，擴展時會增加、縮減時會回收。

如果客戶要求「給我一個 IP 加防火牆白名單」：
  • 方案 A：改用 NLB（可綁 Elastic IP）
  • 方案 B：NLB 前置 + ALB 當 NLB 的目標（兩者優點兼具，但多一層費用與延遲）
  • 方案 C：用 Global Accelerator，它提供 2 個固定的 anycast IP
絕對不要去解析 ALB 的 DNS 拿到 IP 然後寫死——那些 IP 隨時會變。

3. 實作一：建立 ALB

ALB 東京區：每小時 US$0.0243（約每月 US$18）+ LCU 費用（依連線數、頻寬、規則數計算）。
小流量的話一個月大約 US$20–25。學習做完要刪掉，它是按小時計費不管有沒有流量。
# ═══ 步驟 1：建立 ALB（要至少兩個 AZ 的公有子網路）═══
$ ALB_ARN=$(aws elbv2 create-load-balancer \
    --name web-alb \
    --subnets $PUB_A $PUB_C \
    --security-groups $SG_ALB \
    --scheme internet-facing \
    --type application \
    --ip-address-type ipv4 \
    --query 'LoadBalancers[0].LoadBalancerArn' --output text)

# ═══ 步驟 2：建立目標群組 ═══
$ TG_ARN=$(aws elbv2 create-target-group \
    --name web-tg \
    --protocol HTTP --port 8080 \
    --vpc-id $VPC_ID \
    --target-type instance \
    --health-check-protocol HTTP \
    --health-check-path /health \
    --health-check-interval-seconds 15 \
    --health-check-timeout-seconds 5 \
    --healthy-threshold-count 2 \
    --unhealthy-threshold-count 3 \
    --matcher HttpCode=200 \
    --query 'TargetGroups[0].TargetGroupArn' --output text)

# 縮短連線耗盡時間（預設 300 秒，部署會等很久）
$ aws elbv2 modify-target-group-attributes --target-group-arn $TG_ARN \
    --attributes \
      Key=deregistration_delay.timeout_seconds,Value=30 \
      Key=stickiness.enabled,Value=false
# ═══ 步驟 3：HTTPS Listener（先在 ACM 申請憑證）═══
$ CERT_ARN=$(aws acm request-certificate \
    --domain-name "app.example.com" \
    --validation-method DNS \
    --query CertificateArn --output text)

# 依提示到 Route 53 加 CNAME 驗證，等它變 ISSUED
$ aws acm wait certificate-validated --certificate-arn $CERT_ARN

$ aws elbv2 create-listener --load-balancer-arn $ALB_ARN \
    --protocol HTTPS --port 443 \
    --certificates CertificateArn=$CERT_ARN \
    --ssl-policy ELBSecurityPolicy-TLS13-1-2-2021-06 \
    --default-actions Type=forward,TargetGroupArn=$TG_ARN

# ═══ 步驟 4：HTTP 自動轉 HTTPS ═══
$ aws elbv2 create-listener --load-balancer-arn $ALB_ARN \
    --protocol HTTP --port 80 \
    --default-actions '[{
      "Type": "redirect",
      "RedirectConfig": {
        "Protocol": "HTTPS", "Port": "443", "StatusCode": "HTTP_301"
      }
    }]'
ACM 憑證在 ALB / CloudFront / API Gateway 上是免費的，而且自動續期。不用再管憑證到期。

兩個注意事項：
  • 用 DNS 驗證不要用 Email 驗證——DNS 驗證才能自動續期
  • CloudFront 的憑證必須在 us-east-1 申請，其他服務在自己的 region 申請

依路徑 / 網域分流（ALB 的核心價值）

# /api/* 送到 api-tg
$ aws elbv2 create-rule --listener-arn $LISTENER_ARN \
    --priority 10 \
    --conditions '[{"Field":"path-pattern","Values":["/api/*"]}]' \
    --actions "[{\"Type\":\"forward\",\"TargetGroupArn\":\"$API_TG\"}]"

# admin.example.com 送到 admin-tg，且限制來源 IP
$ aws elbv2 create-rule --listener-arn $LISTENER_ARN --priority 20 \
    --conditions '[
      {"Field":"host-header","Values":["admin.example.com"]},
      {"Field":"source-ip","SourceIpConfig":{"Values":["203.0.113.0/24"]}}
    ]' \
    --actions "[{\"Type\":\"forward\",\"TargetGroupArn\":\"$ADMIN_TG\"}]"

# 加權轉發：金絲雀部署，5% 流量到新版
$ aws elbv2 modify-listener --listener-arn $LISTENER_ARN \
    --default-actions '[{
      "Type": "forward",
      "ForwardConfig": {
        "TargetGroups": [
          {"TargetGroupArn": "'$TG_V1'", "Weight": 95},
          {"TargetGroupArn": "'$TG_V2'", "Weight": 5}
        ]
      }
    }]'
規則按 priority 由小到大評估，第一個符合的就執行。跟 ACL 一樣是「先中先贏」。建議留間隔（10、20、30…）方便之後插入新規則。

4. 健康檢查與連線耗盡

健康檢查的路徑不要用首頁（/）。理由：
  • 首頁可能很重（查資料庫、算首頁推薦），健康檢查每 15 秒打一次會造成不必要的負載
  • 首頁掛了不一定代表整台機器該被移除
應該做一個專用的 /health 端點，只回傳 200 和一個字串。
健康檢查應該檢查什麼？兩種設計：
類型檢查內容用途
Liveness（淺層）只回 200，證明程序還活著給 ALB 用
Readiness（深層）連得到資料庫、快取、下游 API部署時判斷能否接流量
ALB 的健康檢查用淺層就好。用深層的話，資料庫短暫抖動會讓所有機器同時變成 unhealthy，ALB 把全部移除 → 服務完全中斷。這叫「健康檢查造成的雪崩」，比原本的問題嚴重得多。

參數怎麼調

偵測到故障的時間 = interval × unhealthy_threshold

15 秒 × 3 次 = 45 秒才會把壞掉的機器移除

恢復時間 = interval × healthy_threshold = 15 × 2 = 30 秒
參數預設建議說明
interval30 秒15 秒太短會增加後端負載
timeout5 秒5 秒必須小於 interval
healthy_threshold52恢復要快
unhealthy_threshold23避免瞬間抖動就被踢掉
deregistration_delay300 秒30 秒預設太長，部署會很慢
Deregistration Delay（連線耗盡）在做什麼？當一台機器要被移除時，ALB 停止送新請求，但等現有請求處理完才真的斷開。

預設 300 秒代表每次部署每台機器都要等 5 分鐘。如果你的請求都在 10 秒內完成，設 30 秒就夠了，部署時間立刻縮短一大截。

但如果有長時間的請求（檔案上傳、報表產生），要設得比最長請求還久，否則使用者會斷線。 
# 看目標的健康狀態與「為什麼不健康」
$ aws elbv2 describe-target-health --target-group-arn $TG_ARN
{
  "TargetHealthDescriptions": [
    {
      "Target": { "Id": "i-0abc123", "Port": 8080 },
      "TargetHealth": {
        "State": "unhealthy",
        "Reason": "Target.ResponseCodeMismatch",
        "Description": "Health checks failed with these codes: [404]"
      }
    }
  ]
}
Reason代表怎麼修
Target.ResponseCodeMismatch回傳的狀態碼不對檢查 /health 路徑存不存在、matcher 設對沒
Target.Timeout逾時沒回應服務太慢，或 安全群組沒放行
Target.FailedHealthChecks連不上SG 沒開、服務沒起來、埠號錯
Elb.RegistrationInProgress剛註冊，還在檢查正常，等一下
Elb.InitialHealthChecking初次檢查中正常
健康檢查失敗最常見的原因是安全群組。後端 EC2 的 SG 必須允許來自 ALB 安全群組的健康檢查埠。用 --source-group 引用 ALB 的 SG（第 02 章講過），不要寫 IP。

5. Sticky Session 與無狀態設計

Sticky Session 是一種妥協，不是好設計。它讓同一個使用者永遠連到同一台機器。問題：
  • 那台機器掛了，使用者的 session 就沒了（會被登出）
  • 負載會分布不均——有些機器綁了很多使用者
  • Auto Scaling 縮容時一定會斷掉一些人的 session
正確做法：把 session 存到外部，讓應用程式無狀態。
存哪適合
ElastiCache Redis最常見，快、支援 TTL
DynamoDB無伺服器架構，配 TTL 自動清理
JWT（存在客戶端）完全無狀態，但無法主動撤銷
無狀態之後：任何一台機器掛掉都不影響使用者、可以自由擴縮、部署不用擔心踢人。 
# 真的需要 sticky 時的兩種模式
$ aws elbv2 modify-target-group-attributes --target-group-arn $TG_ARN \
    --attributes \
      Key=stickiness.enabled,Value=true \
      Key=stickiness.type,Value=lb_cookie \
      Key=stickiness.lb_cookie.duration_seconds,Value=3600
類型Cookie 誰產生特性
lb_cookieALB（AWSALB）ALB 自己管，設定簡單
app_cookie你的應用程式可以跟應用的 session 生命週期一致

6. Auto Scaling 完整設定

$ aws autoscaling create-auto-scaling-group \
    --auto-scaling-group-name web-asg \
    --launch-template LaunchTemplateName=web-lt,Version='$Latest' \
    --min-size 2 --max-size 12 --desired-capacity 4 \
    --vpc-zone-identifier "$APP_A,$APP_C" \
    --target-group-arns $TG_ARN \
    --health-check-type ELB \
    --health-check-grace-period 180 \
    --default-cooldown 180 \
    --termination-policies OldestLaunchTemplate Default \
    --capacity-rebalance \
    --tags "Key=Name,Value=web,PropagateAtLaunch=true" \
                  "Key=Env,Value=prod,PropagateAtLaunch=true"
三個參數設錯就會出事：
參數設錯的後果
--health-check-type EC2（預設）只檢查機器有沒有開機。應用程式當掉但機器還活著 → ASG 認為健康，流量繼續送給壞掉的機器。掛了 ALB 就一定要改成 ELB
--health-check-grace-period 太短新機器還在開機就被判定不健康 → 殺掉 → 再開 → 再殺，無限迴圈燒錢
--min-size 設 1那一台掛掉時服務中斷，直到新的開起來。正式環境至少 2
Grace Period 怎麼抓？從「機器啟動」到「應用程式能回應健康檢查」的時間，再加 60 秒緩衝。
  • Golden AMI（軟體已預裝）→ 60–120 秒
  • User Data 現裝軟體 → 300–600 秒
這也是第 03 章推薦 Golden AMI 的原因之一——擴容反應快非常多。

終止政策：縮容時先殺誰

政策先終止
Default先平衡 AZ → 再挑最舊的 Launch Template → 再挑最接近計費整點的
OldestInstance最舊的機器（適合定期汰換）
NewestInstance最新的（測試新設定時方便回退）
OldestLaunchTemplate用舊版範本開的（滾動更新常用）
ClosestToNextInstanceHour最接近計費整點的（現在按秒計費，意義不大）
ASG 永遠優先維持 AZ 之間的平衡。就算你設了 OldestInstance，如果 1a 有 3 台、1c 有 1 台，它會先從 1a 殺來平衡，而不是全網最舊的那台。這是內建行為，無法關閉。

7. 五種擴展政策

政策怎麼運作適合
Target Tracking「CPU 維持在 60%」，AWS 自己算要幾台90% 的情況用這個
Step Scaling依超標幅度分級加不同數量需要精細控制擴展速度
Simple Scaling觸發就加 N 台，然後 cooldown舊做法，不建議
Scheduled指定時間擴縮已知的規律尖峰
PredictiveML 學習歷史模式，提前擴容有明顯週期性的流量
# ═══ Target Tracking：最簡單也最好用 ═══
$ aws autoscaling put-scaling-policy \
    --auto-scaling-group-name web-asg \
    --policy-name cpu-target-60 \
    --policy-type TargetTrackingScaling \
    --target-tracking-configuration '{
      "PredefinedMetricSpecification": {
        "PredefinedMetricType": "ASGAverageCPUUtilization"
      },
      "TargetValue": 60.0,
      "DisableScaleIn": false
    }'

# 更好的指標：每台機器承受的請求數（比 CPU 更直接反映負載）
$ aws autoscaling put-scaling-policy \
    --auto-scaling-group-name web-asg \
    --policy-name req-per-target \
    --policy-type TargetTrackingScaling \
    --target-tracking-configuration '{
      "PredefinedMetricSpecification": {
        "PredefinedMetricType": "ALBRequestCountPerTarget",
        "ResourceLabel": "app/web-alb/xxx/targetgroup/web-tg/yyy"
      },
      "TargetValue": 1000.0
    }'
Target Tracking 為什麼比 Step Scaling 好？
  • 它會自動建立 CloudWatch 告警，你不用手動設
  • 它擴容積極、縮容保守——這正是你要的（寧可多開一下也不要不夠用）
  • 它會算出「需要幾台」而不是「加幾台」，避免震盪
除非有特殊需求，一律用 Target Tracking。
用 CPU 當指標不一定準。如果你的應用是 I/O 密集（等資料庫、等外部 API），CPU 可能一直很低但已經塞爆了。

更好的指標：
  • ALBRequestCountPerTarget——每台承受多少請求
  • TargetResponseTime——回應時間（用自訂指標）
  • SQS 佇列長度 / 機器數——批次處理系統的標準指標
# ═══ Scheduled：每天早上 8:50 先擴容 ═══
$ aws autoscaling put-scheduled-update-group-action \
    --auto-scaling-group-name web-asg \
    --scheduled-action-name morning-warmup \
    --recurrence "50 0 * * 1-5" \
    --time-zone "Asia/Taipei" \
    --min-size 6 --desired-capacity 8

# 晚上縮回去
$ aws autoscaling put-scheduled-update-group-action \
    --auto-scaling-group-name web-asg \
    --scheduled-action-name evening-scaledown \
    --recurrence "0 12 * * 1-5" --time-zone "Asia/Taipei" \
    --min-size 2 --desired-capacity 2
Scheduled + Target Tracking 一起用是最佳實務。Scheduled 負責「已知的規律」（上班前先開好），Target Tracking 負責「意外的尖峰」。

純靠 Target Tracking 的問題：流量瞬間湧入時，從偵測到機器可服務要 2–5 分鐘，這段期間使用者會很慢。Scheduled 提前把機器準備好就沒這個問題。

Warm Pool：讓擴容更快

$ aws autoscaling put-warm-pool \
    --auto-scaling-group-name web-asg \
    --min-size 4 \
    --pool-state Stopped
Warm Pool 預先開好機器、跑完初始化，然後停機。需要擴容時直接 start（幾十秒）而不是從零開機（幾分鐘）。
停機狀態只付 EBS 費用不付運算費，所以成本很低。適合「開機很慢但需要快速擴容」的應用。

8. 生命週期掛勾與健康檢查

Lifecycle Hook 讓機器在「準備啟動」或「準備終止」時暫停，等你做完事再繼續。

# 終止前先暫停，讓你把日誌傳走、優雅關閉
$ aws autoscaling put-lifecycle-hook \
    --auto-scaling-group-name web-asg \
    --lifecycle-hook-name drain-before-terminate \
    --lifecycle-transition autoscaling:EC2_INSTANCE_TERMINATING \
    --heartbeat-timeout 300 \
    --default-result CONTINUE

# 機器上的腳本做完事後回報「我好了」
$ aws autoscaling complete-lifecycle-action \
    --auto-scaling-group-name web-asg \
    --lifecycle-hook-name drain-before-terminate \
    --lifecycle-action-result CONTINUE \
    --instance-id i-0abc123
Lifecycle Hook 的典型用途：
  • 終止前：把本機日誌上傳到 S3、從服務註冊中心移除、把工作交接給其他機器
  • 啟動時：等設定拉完、等資料預熱完才開始接流量
注意 --default-result：超時後預設要 CONTINUE（繼續）還是 ABANDON（放棄並終止）。設 ABANDON 的話，腳本掛掉會導致機器被砍，可能形成迴圈。
ASG 健康檢查與 ALB 健康檢查的關係要搞清楚：
  • ALB 判定 unhealthy → 只是停止送流量給它，機器還在
  • ASG（health-check-type=ELB）看到 ALB 說不健康 → 終止並開一台新的
所以 --health-check-type ELB 才是「自動修復」的關鍵。設成 EC2 的話，壞掉的機器會被 ALB 隔離但永遠不會被替換，容量就這樣慢慢流失。

手動控制

# 暫時保護某台不被縮容殺掉（除錯用）
$ aws autoscaling set-instance-protection \
    --auto-scaling-group-name web-asg --instance-ids i-0abc123 \
    --protected-from-scale-in

# 把機器移出 ASG 但不終止（保留現場查問題）
$ aws autoscaling detach-instances \
    --auto-scaling-group-name web-asg --instance-ids i-0abc123 \
    --should-decrement-desired-capacity

9. 部署策略：滾動、藍綠、金絲雀

策略做法停機回退速度成本
In-place直接在原機器上更新有慢最低
Rolling一次換幾台，逐批替換無中（要再滾一次）低
Blue/Green建一整套新的，測好再切流量無極快（切回去）高（雙倍資源）
Canary先給 5% 流量，觀察後再全推無快中

Instance Refresh：ASG 內建的滾動更新

$ aws autoscaling start-instance-refresh \
    --auto-scaling-group-name web-asg \
    --preferences '{
      "MinHealthyPercentage": 90,
      "InstanceWarmup": 180,
      "CheckpointPercentages": [20, 50, 100],
      "CheckpointDelay": 600,
      "SkipMatching": true,
      "AutoRollback": true
    }'

# 查進度
$ aws autoscaling describe-instance-refreshes \
    --auto-scaling-group-name web-asg \
    --query 'InstanceRefreshes[0].[Status,PercentageComplete,StatusReason]'

# 出事了立刻取消
$ aws autoscaling cancel-instance-refresh --auto-scaling-group-name web-asg
這組參數的意義：
  • MinHealthyPercentage: 90 — 過程中至少保持 90% 容量
  • CheckpointPercentages: [20,50,100] — 換到 20% 時停下來等 10 分鐘，讓你觀察有沒有問題
  • SkipMatching: true — 已經是最新版的機器不重複替換（省時間）
  • AutoRollback: true — 失敗自動回退到上一版 Launch Template
Checkpoint 就是內建的金絲雀機制，不需要額外工具。

藍綠部署（用 ALB 加權轉發）

# ① 建立綠色環境（新版），先給 0% 流量
# ② 內部測試綠色環境（用 host-header 規則導特定測試網域過去）
# ③ 逐步調整權重
$ for W in 5 25 50 100; do
    aws elbv2 modify-listener --listener-arn $LISTENER_ARN \
      --default-actions '[{
        "Type":"forward",
        "ForwardConfig":{"TargetGroups":[
          {"TargetGroupArn":"'$TG_BLUE'","Weight":'$((100-W))'},
          {"TargetGroupArn":"'$TG_GREEN'","Weight":'$W'}
        ]}
      }]'
    echo "綠色 $W%，觀察 5 分鐘…"
    sleep 300
    # 這裡應該檢查錯誤率指標，異常就中止
  done
藍綠部署的資料庫問題沒有標準解。應用程式可以有兩套，但資料庫通常只有一套。所以：
  • 資料庫 schema 變更必須向前相容——舊版程式也要能跑
  • 做法：先加欄位（不刪不改）→ 部署新版 → 確認穩定 → 之後才清理舊欄位。這叫 expand-contract 模式
  • 絕對不要在部署時同時做破壞性的 schema 變更，那會讓回退變得不可能

10. Route 53 路由政策

政策做什麼用途
Simple一個名稱對一組 IP最基本
Weighted按權重分配A/B 測試、金絲雀
Latency導到延遲最低的 region多 region 效能優化
Failover主要掛了切備援災難復原
Geolocation依使用者所在國家內容在地化、法規遵循
Geoproximity依地理距離，可調偏差值逐步把流量搬到新 region
Multivalue Answer回傳多個健康的 IP簡易負載平衡
考題關鍵字：
  • 「最低延遲」→ Latency
  • 「特定國家看到不同內容」「法規要求資料不出境」→ Geolocation
  • 「主站掛了自動切備援」→ Failover
  • 「10% 流量給新版」→ Weighted
  • 「逐步把流量從東京搬到大阪」→ Geoproximity（調 bias）
Latency 和 Geolocation 很容易混淆：Latency 看的是「網路延遲」，Geolocation 看的是「使用者在哪個國家」。日本使用者可能連東京最快（Latency 會選東京），但如果法規要求日本使用者必須連日本主機，就得用 Geolocation。

Alias Record 比 CNAME 好，而且免費。
AliasCNAME
能用在根網域（example.com）可以不行
查詢費用免費（指向 AWS 資源時）要錢
健康檢查整合EvaluateTargetHealth要另外設

DNS 故障切換不是即時的。就算健康檢查 30 秒發現問題，使用者的本機 DNS 快取還是會指向舊位址，直到 TTL 過期。

  • 需要快速切換 → TTL 設 60 秒（費用會增加，因為查詢次數變多）
  • 但很多電信商和瀏覽器不完全遵守 TTL，實際切換可能要幾分鐘
  • 要秒級切換 → 用 Global Accelerator（固定 anycast IP，切換在 AWS 網路層完成，不依賴 DNS）

11. 故障排除

1
目標一直 unhealthy看 describe-target-health 的 Reason。八成是 SG 沒放行 ALB 的健康檢查埠，或 /health 路徑不存在。
2
機器一直被殺掉重開describe-scaling-activities 看原因。通常是 grace period 太短，機器還沒開好就被判定不健康。
3
ALB 回 502 Bad Gateway後端回了 ALB 看不懂的回應。查後端應用的日誌——常見是應用當掉、回傳格式錯誤、或 keep-alive 逾時設定比 ALB 短。
4
ALB 回 503 Service Unavailable目標群組裡沒有健康的目標。回到第 1 點。
5
ALB 回 504 Gateway Timeout後端太慢，超過 idle timeout（預設 60 秒）。調高 timeout 或優化應用。
6
不會自動擴容檢查有沒有設擴展政策、是否已達 max-size、CloudWatch 告警狀態、以及是否還在 cooldown。
7
擴容了但流量沒分過去新機器可能還在 health check 中。describe-target-health 看是不是 initial 狀態。
8
使用者一直被登出沒有 sticky 也沒有外部 session store。回到第 5 節，把 session 搬到 Redis。

真實案例：「部署後容量慢慢變少，最後服務掛掉」

症狀：desired 是 6，但幾小時後只剩 2 台在服務，ASG 卻沒有補機器。

排查：describe-target-health → 4 台 unhealthy。describe-auto-scaling-groups → HealthCheckType: EC2。

原因：ASG 用 EC2 健康檢查，只看機器有沒有開機。應用程式當掉了但機器還活著 → ASG 認為健康不替換，ALB 卻把它們隔離。修法：改成 --health-check-type ELB。

真實案例：「ASG 不斷開機殺機，一天燒掉幾百美元」

症狀：describe-scaling-activities 顯示每 5 分鐘就有一輪 launch + terminate。

排查：Cause 寫 an instance was taken out of service in response to a ELB system health check failure。

原因：User Data 要裝 3 分鐘軟體，但 health-check-grace-period 只設 60 秒。修法：grace period 調到 300 秒，並改用 Golden AMI 縮短開機時間。

完整實作 Lab：高可用 Web 架構

需要第 02、03 章的 VPC 與 Launch Template。約 110 分鐘。

這個 Lab 會產生費用：ALB 約 US$0.025/小時（不管有沒有流量），EC2 用 t4g.micro（免費方案內）。
做 3 小時大約 US$0.08。但 ALB 忘記刪一個月就是 US$18，做完務必執行清理。

階段一：ALB

  1. 建立 ALB（兩個 AZ 的公有子網路）與目標群組
  2. 健康檢查設 /health、interval 15、unhealthy 3、healthy 2
  3. deregistration_delay 改成 30 秒
  4. 建立 HTTP listener（先不做 HTTPS，避免需要網域）
  5. 後端 SG 只允許來源 = ALB 的 SG（不要用 IP）

階段二：ASG

  1. 建立 ASG：min 2 / max 6 / desired 2，跨兩個 AZ，掛到目標群組
  2. health-check-type 設 ELB、grace period 設 180
  3. User Data 讓每台顯示自己的 instance-id，並提供 /health 端點
  4. 用瀏覽器多次重新整理 ALB 網址，確認會輪流看到不同的 instance-id

階段三：驗證高可用

  1. 手動 terminate 一台機器，觀察：
    ① ALB 幾秒後標記 unhealthy ② ASG 自動開新的一台 ③ 過程中服務不中斷
  2. 把一台的應用程式停掉（但機器還活著），觀察 ASG 是否會替換它（驗證 ELB 健康檢查生效）
  3. 用 describe-scaling-activities 看完整的活動紀錄

階段四：自動擴展

  1. 建立 Target Tracking 政策，目標 CPU 50%
  2. 在某台機器上跑 stress-ng --cpu 2 或 yes > /dev/null 灌高 CPU
  3. 觀察 3–5 分鐘後 ASG 自動擴容
  4. 停掉負載，觀察約 15 分鐘後自動縮容（縮容比擴容保守很多）
  5. 再建一個 Scheduled 政策，設定在 10 分鐘後把 desired 改成 4，驗證它會執行

階段五：滾動更新

  1. 修改 Launch Template（改個首頁文字），建立新版本
  2. 執行 Instance Refresh，帶 CheckpointPercentages [50,100] 和 AutoRollback
  3. 觀察它換到 50% 時停下來等待
  4. 整個過程持續重新整理網頁，確認服務沒有中斷

驗收清單

  • describe-target-health 兩個目標都是 healthy，且分屬不同 AZ
  • Terminate 一台後，2 分鐘內有新機器加入且變 healthy
  • 停掉應用程式的那台會被 ASG 替換（不是只被隔離）
  • CPU 灌高後 ASG 有擴容紀錄
  • Instance Refresh 在 50% 時暫停，且全程可正常瀏覽
  • 後端 SG 的入站規則來源是 sg-xxx 不是 IP 網段

本章重點回顧

  • 串聯元件的可用性是相乘的——要從最弱的環節下手改善
  • ALB 看內容分流、NLB 快且有固定 IP；需要 WAF 或 Lambda 目標一定是 ALB
  • ALB 沒有固定 IP，客戶要白名單就用 NLB 或 Global Accelerator
  • 健康檢查用專用的淺層 /health，不要檢查資料庫（會造成雪崩）
  • deregistration_delay 預設 300 秒太長，一般調成 30 秒
  • ASG 一定要設 --health-check-type ELB，否則應用當掉不會被替換
  • grace period 太短會導致無限開機殺機迴圈
  • 擴展政策 90% 情況用 Target Tracking；I/O 密集的應用用 RequestCountPerTarget 比 CPU 準
  • Scheduled + Target Tracking 一起用：前者處理已知尖峰，後者處理意外
  • Instance Refresh 的 CheckpointPercentages 就是內建的金絲雀，配 AutoRollback
  • Sticky Session 是妥協——正解是把 session 存到 Redis / DynamoDB
  • 藍綠部署的資料庫要用 expand-contract，schema 變更必須向前相容
  • Route 53：Latency 看網路延遲、Geolocation 看使用者國家；指向 AWS 資源用 Alias
  • DNS 切換受快取影響不是即時，要秒級切換用 Global Accelerator
