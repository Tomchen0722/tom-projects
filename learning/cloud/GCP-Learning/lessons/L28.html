LESSON 28

Terraform：用程式碼管理基礎設施

到目前為止你都在打 gcloud 指令。但手打的東西無法重現、無法審閱、無法回滾。這一課把基礎設施變成程式碼。

操作 50 分實作

一、為什麼需要 IaC

問自己三個問題：

  • 「我們的正式環境現在到底是什麼設定？」——如果答案要靠人去 Console 一個一個看，那你已經有問題了。
  • 「能不能在 30 分鐘內在另一個 Region 重建整套環境？」——災難復原的真實考驗。
  • 「上週誰改了防火牆規則、為什麼改？」——沒有 IaC 的話，只能查稽核日誌猜。

IaC（Infrastructure as Code）把基礎設施變成 Git 裡的檔案，於是它獲得了程式碼的所有好處：版本控制、Code Review、可重現、可測試、可回滾。

二、Terraform 的核心概念

Terraform 工作流程
.tf 檔案（你寫的期望狀態）
      ↓ terraform plan
比對「期望狀態」與「state 檔記錄的實際狀態」
      ↓ 產生執行計畫（要建立什麼、修改什麼、刪除什麼）
      ↓ terraform apply
呼叫 GCP API 執行變更
      ↓
更新 state 檔
小心踩雷
State 檔是 Terraform 的命脈，也是最大的風險點。它記錄了「Terraform 認為現在有什麼資源」。
• State 檔遺失 → Terraform 不知道資源存在，會想重新建立（可能導致重複資源或衝突）。
• State 檔被兩個人同時修改 → 狀態損壞。
• State 檔含有機密（資料庫密碼會明文存在裡面）。

所以 state 一定要放遠端且加鎖——用 GCS backend，它天生支援物件版本控制與鎖定。

三、實作：第一份 Terraform 設定

動手實作

實作：用 Terraform 建立完整環境

  1. 建立 state 用的 bucket（這個要手動建，雞生蛋問題）：
    bash
    gcloud storage buckets create gs://$PROJECT-tfstate \
  --location=asia-east1 --uniform-bucket-level-access
gcloud storage buckets update gs://$PROJECT-tfstate --versioning
  2. 建立 versions.tf：
    bash
    terraform {
  required_version = ">= 1.7"
  required_providers {
    google = {
      source  = "hashicorp/google"
      version = "~> 5.0"
    }
  }
  backend "gcs" {
    bucket = "你的專案ID-tfstate"
    prefix = "env/dev"
  }
}

provider "google" {
  project = var.project_id
  region  = var.region
}
  3. 建立 variables.tf：
    bash
    variable "project_id" {
  type        = string
  description = "GCP 專案 ID"
}

variable "region" {
  type    = string
  default = "asia-east1"
}

variable "env" {
  type    = string
  default = "dev"
  validation {
    condition     = contains(["dev", "staging", "prod"], var.env)
    error_message = "env 必須是 dev / staging / prod 其中之一"
  }
}
  4. 建立 main.tf：
    bash
    locals {
  labels = {
    env         = var.env
    managed_by  = "terraform"
    cost_center = "engineering"
  }
}

# VPC
resource "google_compute_network" "vpc" {
  name                    = "${var.env}-vpc"
  auto_create_subnetworks = false
  routing_mode            = "GLOBAL"
}

resource "google_compute_subnetwork" "subnet" {
  name                     = "${var.env}-subnet-${var.region}"
  network                  = google_compute_network.vpc.id
  ip_cidr_range            = "10.10.0.0/20"
  region                   = var.region
  private_ip_google_access = true

  secondary_ip_range {
    range_name    = "gke-pods"
    ip_cidr_range = "10.100.0.0/16"
  }
}

# 防火牆
resource "google_compute_firewall" "allow_iap_ssh" {
  name          = "${var.env}-allow-iap-ssh"
  network       = google_compute_network.vpc.name
  source_ranges = ["35.235.240.0/20"]

  allow {
    protocol = "tcp"
    ports    = ["22"]
  }
}

# Cloud NAT
resource "google_compute_router" "router" {
  name    = "${var.env}-router"
  network = google_compute_network.vpc.id
  region  = var.region
}

resource "google_compute_router_nat" "nat" {
  name                               = "${var.env}-nat"
  router                             = google_compute_router.router.name
  region                             = var.region
  nat_ip_allocate_option             = "AUTO_ONLY"
  source_subnetwork_ip_ranges_to_nat = "ALL_SUBNETWORKS_ALL_IP_RANGES"
}

# 儲存桶
resource "google_storage_bucket" "data" {
  name                        = "${var.project_id}-${var.env}-data"
  location                    = var.region
  uniform_bucket_level_access = true
  public_access_prevention    = "enforced"
  labels                      = local.labels

  versioning { enabled = true }

  lifecycle_rule {
    condition { age = 30 }
    action {
      type          = "SetStorageClass"
      storage_class = "NEARLINE"
    }
  }
}

# 服務帳號
resource "google_service_account" "app" {
  account_id   = "${var.env}-app-sa"
  display_name = "應用程式服務帳號"
}

resource "google_project_iam_member" "app_storage" {
  project = var.project_id
  role    = "roles/storage.objectViewer"
  member  = "serviceAccount:${google_service_account.app.email}"
}
  5. 建立 outputs.tf：
    bash
    output "vpc_id" {
  value = google_compute_network.vpc.id
}

output "bucket_url" {
  value = google_storage_bucket.data.url
}

output "service_account_email" {
  value = google_service_account.app.email
}
  6. 執行：
    bash
    terraform init
terraform fmt          # 自動排版
terraform validate     # 語法檢查
terraform plan -var="project_id=$PROJECT"     # ★ 一定要先看 plan！
terraform apply -var="project_id=$PROJECT"

terraform output
terraform state list
  7. 清理：
    bash
    terraform destroy -var="project_id=$PROJECT"

四、Terraform 的十個實務原則

  1. 永遠先跑 plan 再 apply。而且要真的讀 plan 的輸出，特別注意 -/+（銷毀後重建）的資源。
  2. State 放遠端並開啟版本控制。GCS backend 天生支援鎖定。
  3. 每個環境分開 state。用 prefix 或不同 bucket，絕不共用。
  4. 不要把密鑰寫在 .tf 檔。用 Secret Manager 資料源或環境變數。注意：即使不寫在 .tf，密鑰仍會明文存在 state 裡——所以 state bucket 的權限要嚴格控管。
  5. 用模組（module）減少重複。但不要過早抽象——重複三次以上才考慮抽成模組。
  6. 對關鍵資源加 prevent_destroy。
  7. 把 apply 放進 CI/CD，禁止本機 apply 到 prod。本機 apply 無法審閱、無法追溯。
  8. 用 terraform import 收編既有資源，而不是砍掉重建。
  9. 鎖定 provider 版本。不鎖版本的話，某天 provider 更新可能讓你的 plan 突然要重建整個資料庫。
  10. 把 plan 的結果貼到 PR 上，讓 reviewer 看得到實際會發生什麼。
bash
# 保護關鍵資源不被誤刪
resource "google_sql_database_instance" "prod" {
  name = "prod-db"
  # ...
  deletion_protection = true

  lifecycle {
    prevent_destroy = true              # Terraform 層級的保護
    ignore_changes  = [settings[0].disk_size]   # 忽略自動擴充造成的差異
  }
}

# 從 Secret Manager 讀取，不寫在檔案裡
data "google_secret_manager_secret_version" "db_password" {
  secret = "db-password"
}

五、模組化：多環境管理

目錄結構
infra/
├── modules/
│   ├── network/          # 可重用的網路模組
│   │   ├── main.tf
│   │   ├── variables.tf
│   │   └── outputs.tf
│   └── app-service/
└── environments/
    ├── dev/
    │   ├── main.tf       # 呼叫模組，傳入 dev 的參數
    │   └── backend.tf    # prefix = "env/dev"
    ├── staging/
    └── prod/

# environments/prod/main.tf
module "network" {
  source = "../../modules/network"

  env           = "prod"
  region        = "asia-east1"
  subnet_cidr   = "10.48.0.0/20"
  enable_flow_logs = true          # prod 才開啟
}

六、CI/CD 中的 Terraform

bash
# .github/workflows/terraform.yml 的關鍵步驟
- name: Terraform Plan
  run: |
    terraform plan -no-color -out=tfplan
    terraform show -no-color tfplan > plan.txt

- name: 把 plan 貼到 PR
  uses: actions/github-script@v7
  # 讓 reviewer 直接在 PR 看到會發生什麼變更

- name: Terraform Apply
  if: github.ref == 'refs/heads/main'
  run: terraform apply -auto-approve tfplan
  # 只在合併到 main 後執行，且用 PR 時產生的 plan 檔案
  # 確保「審閱的內容」就是「執行的內容」

七、本課檢核

  • 能寫出一份完整的 Terraform 設定並成功 apply
  • 知道 state 要放遠端並分環境
  • 知道密鑰會明文存在 state 裡，需嚴格控管權限
  • 會用 prevent_destroy 保護關鍵資源
  • 理解「apply 應該在 CI 執行而非本機」的理由

自我檢測

terraform plan 顯示要「銷毀並重建」你的正式資料庫。你怎麼處理？
立刻停手，絕對不要 apply。逐步診斷：

① 看是哪個屬性觸發的——plan 輸出會標示 # forces replacement。常見的有：改 name、改 region、改 database_version（大版本升級）。
② 確認是不是有人手動改過（configuration drift）——有人在 Console 動了設定，Terraform 想改回來。用 terraform refresh 或 terraform plan -refresh-only 確認。
③ 確認是不是 provider 升級造成的——某些版本會改變預設值或屬性行為。回退 provider 版本測試看看。

處置手段：
• 如果是不該變的屬性 → 把 .tf 改回原本的值。
• 如果是必要的變更 → 用 lifecycle { ignore_changes = [...] } 忽略，或規劃一次有停機視窗的正式遷移。
• 加上 prevent_destroy = true，讓這種 plan 直接失敗而不是等人發現。

教訓：正式環境的關鍵資源都應該預先加 prevent_destroy。它把「危險的 apply」變成「明確的錯誤」。
兩個工程師同時執行 terraform apply，會發生什麼？
如果用 GCS backend：第二個人會被鎖住並收到明確錯誤，這是正確行為。GCS backend 使用物件的 generation 條件式寫入實作分散式鎖。

如果用本機 state（沒有 backend）：災難。兩份 state 各自記錄不同的現實，之後的 plan 會產生無法預測的結果——可能重複建立資源，也可能刪掉對方建的東西。

如果鎖卡住了（例如有人 apply 到一半當機）：
bash
terraform force-unlock LOCK_ID
但執行前務必確認真的沒有其他 apply 在跑，強制解鎖後同時 apply 會損壞 state。

更根本的解法：禁止本機 apply，全部走 CI。CI 天然是序列化的，而且每次 apply 都有記錄、有審閱、有觸發者。
既有環境有 200 個資源是手動建的，現在想改用 Terraform 管理。怎麼進行？
不要砍掉重建，用漸進式收編。四階段：

① 先寫，不執行——用 gcloud ... --format=export 或 Terraformer 產生初步的 .tf 檔案，然後人工整理（自動產生的通常很醜，需要重構成模組與變數）。

② 用 import block 收編（Terraform 1.5+ 的新語法，比舊的 terraform import 指令好用）：
bash
import {
  to = google_compute_network.vpc
  id = "projects/my-project/global/networks/prod-vpc"
}
然後跑 terraform plan，目標是讓 plan 顯示「No changes」。有差異就修 .tf 直到完全對上。

③ 從低風險資源開始——順序建議：儲存桶 → 網路 → IAM → 運算資源 → 資料庫。資料庫留到最後，因為誤操作的代價最高。

④ 收編後立即上鎖——關閉團隊在 Console 的寫入權限（改成 Viewer），強制所有變更走 Terraform。否則手動變更會持續產生 drift，收編的努力會慢慢瓦解。

時程預期：200 個資源大約需要 2～4 週，不要想一週搞定。
