LESSON 13

防火牆規則與網路分段

防火牆是你的第一道也是最重要的一道防線。GCP 的防火牆設計很優雅——用標籤而不是 IP 來綁定規則，這讓大規模管理變得可行。

操作 40 分實作

一、GCP 防火牆的五個特性

  • 狀態感知（stateful）：允許進來的連線，回應封包自動放行，不用設反向規則。
  • 套用在 VM 網路介面上，不是子網路上。所以同一個子網路的機器可以有完全不同的規則。
  • 預設兩條隱含規則：允許所有對外（egress allow）、拒絕所有對內（ingress deny）。
  • 用優先度數字決定順序：0～65535，數字越小越優先，第一條符合的就決定結果。
  • 透過標籤或服務帳號綁定目標，這是最重要的設計。

二、規則的組成

防火牆規則結構
每條防火牆規則包含：

方向      INGRESS（進入 VM）或 EGRESS（離開 VM）
優先度    0~65535，數字小的先比對
動作      ALLOW 或 DENY
目標      哪些 VM 要套用這條規則
            ├── 所有 VM（不指定）
            ├── 網路標籤 --target-tags=web
            └── 服務帳號 --target-service-accounts=xxx@...
來源/目的 對方是誰
            ├── IP 網段 --source-ranges=10.0.0.0/8
            ├── 網路標籤 --source-tags=frontend
            └── 服務帳號 --source-service-accounts=xxx@...
協定/埠   tcp:80,tcp:443,udp:53,icmp

三、標籤 vs 服務帳號：該用哪個綁定？

網路標籤 Network Tag服務帳號 Service Account
設定難度簡單，任何人都能加要有 IAM 權限才能指派
安全性較弱——任何有 compute.instances.setTags 權限的人，都能自己貼上標籤取得防火牆通行權較強——要指派服務帳號需要 iam.serviceAccountUser 權限
適用開發測試、簡單環境正式環境、有資安要求的環境
實務提醒
這是一個常被忽略的安全議題。如果你用 tag 綁定「允許連資料庫」的規則，那麼任何能建立 VM 的開發者，只要把 tag 貼上去就能連資料庫。
用服務帳號綁定則需要額外的 IAM 授權，形成雙重把關。金融、醫療等產業的稽核通常會要求用服務帳號。

四、實作：三層式架構的網路分段

動手實作

實作：建立 Web → App → DB 的分層防火牆

  1. 先建立明確的拒絕規則作為基礎（優先度設大，讓其他規則能覆蓋）：
    bash
    # 記錄所有被拒絕的流量，方便排查
gcloud compute firewall-rules create deny-all-ingress \
  --network=prod-vpc --direction=INGRESS --priority=65000 \
  --action=DENY --rules=all --source-ranges=0.0.0.0/0 \
  --enable-logging
  2. 第一層：允許 LB 和健康檢查連 web 層：
    bash
    gcloud compute firewall-rules create allow-lb-to-web \
  --network=prod-vpc --direction=INGRESS --priority=1000 \
  --action=ALLOW --rules=tcp:80,tcp:443 \
  --source-ranges=130.211.0.0/22,35.191.0.0/16 \
  --target-tags=web
  3. 第二層：只有 web 層能連 app 層的 8080：
    bash
    gcloud compute firewall-rules create allow-web-to-app \
  --network=prod-vpc --direction=INGRESS --priority=1000 \
  --action=ALLOW --rules=tcp:8080 \
  --source-tags=web --target-tags=app
  4. 第三層：只有 app 層能連資料庫的 3306：
    bash
    gcloud compute firewall-rules create allow-app-to-db \
  --network=prod-vpc --direction=INGRESS --priority=1000 \
  --action=ALLOW --rules=tcp:3306 \
  --source-tags=app --target-tags=db
  5. 管理用：只允許 IAP 連 SSH（不開放公網）：
    bash
    gcloud compute firewall-rules create allow-iap-ssh \
  --network=prod-vpc --direction=INGRESS --priority=900 \
  --action=ALLOW --rules=tcp:22 \
  --source-ranges=35.235.240.0/20
  6. 限制對外連線（Egress 也要管，這是很多人忽略的）：
    bash
    # 禁止資料庫層主動對外連網際網路（防資料外洩）
gcloud compute firewall-rules create deny-db-egress \
  --network=prod-vpc --direction=EGRESS --priority=1000 \
  --action=DENY --rules=all \
  --destination-ranges=0.0.0.0/0 \
  --target-tags=db

# 但允許連 Google API（更新、備份需要）
gcloud compute firewall-rules create allow-db-egress-google \
  --network=prod-vpc --direction=EGRESS --priority=900 \
  --action=ALLOW --rules=tcp:443 \
  --destination-ranges=199.36.153.8/30 \
  --target-tags=db
  7. 檢視所有規則，確認優先度順序正確：
    bash
    gcloud compute firewall-rules list --filter="network=prod-vpc" \
  --sort-by=priority \
  --format="table(priority, name, direction, allowed[].map().firewall_rule().list(), sourceRanges.list(), targetTags.list())"

五、排查防火牆問題：連線測試工具

不要用猜的。GCP 有一個工具可以直接告訴你封包會不會通，以及被哪一條規則擋下：

連線測試（Connectivity Tests）
gcloud network-management connectivity-tests create web-to-db-test \
  --source-instance=projects/PROJ/zones/asia-east1-b/instances/web-01 \
  --destination-instance=projects/PROJ/zones/asia-east1-b/instances/db-01 \
  --destination-port=3306 --protocol=TCP

gcloud network-management connectivity-tests describe web-to-db-test \
  --format="yaml(reachabilityDetails)"

# 輸出會明確告訴你：
#   result: UNREACHABLE
#   causeCode: FIREWALL_RULE  ← 被哪條規則擋的
實務提醒
這個工具能省下你大量時間。它做的是靜態設定分析，不需要真的發封包，所以連機器關機也能測。
另一個好用的是 VPC Flow Logs + Cloud Logging 查詢：
bash
resource.type="gce_subnetwork"
jsonPayload.connection.dest_port=3306
jsonPayload.reporter="DEST"

六、階層式防火牆政策（企業級）

上面的規則是專案級的。企業環境需要在 Organization 或 Folder 層級強制一些規則，讓底下所有專案都無法繞過：

bash
# 建立階層式防火牆政策
gcloud compute firewall-policies create \
  --organization=ORG_ID --short-name=corp-baseline

# 加入一條「全公司禁止對外開放 RDP」的強制規則
gcloud compute firewall-policies rules create 100 \
  --firewall-policy=POLICY_ID --organization=ORG_ID \
  --direction=INGRESS --action=deny \
  --layer4-configs=tcp:3389 \
  --src-ip-ranges=0.0.0.0/0

# 套用到某個 Folder，底下所有專案自動生效且無法覆寫
gcloud compute firewall-policies associations create \
  --firewall-policy=POLICY_ID --organization=ORG_ID \
  --folder=FOLDER_ID

評估順序：Organization 政策 → Folder 政策 → VPC 防火牆規則。上層的 deny 下層無法解除。

七、本課檢核

  • 知道 GCP 防火牆是 stateful 且套用在 VM 上
  • 理解優先度數字越小越優先
  • 知道用服務帳號綁定比用 tag 更安全
  • 能設計三層式架構的防火牆規則
  • 會用 Connectivity Tests 排查問題
  • 知道 Egress 規則也需要管理

自我檢測

你設了 priority=1000 的 ALLOW 規則和 priority=500 的 DENY 規則，兩者都符合某個封包。結果是？
被拒絕。因為 priority=500 數字較小，先被評估，一旦符合就直接決定結果，不再往下比對。
常見誤解：以為 DENY 一定優先於 ALLOW。實際上 GCP 純粹看優先度數字，跟動作類型無關。
實務建議：把「基礎拒絕規則」放在很大的數字（如 65000），把「特例允許」放在中間（1000），把「絕對禁止」放在很小的數字（100）。
開發者抱怨「我 VM 上的服務連不到另一台 VM，但兩台都在同一個 VPC 同一個子網路」。可能原因？
同 VPC 內網路層是通的（子網路路由自動存在），所以問題在防火牆或 OS 層：
① 沒有允許內部流量的 ingress 規則——這是最常見的。GCP 預設拒絕所有 ingress，包括同 VPC 內部。custom mode VPC 不會自動幫你建 allow-internal 規則。
② 目標機器的 OS 防火牆（ufw / firewalld / Windows Defender）擋著。
③ 服務綁在 127.0.0.1 而非 0.0.0.0。
用 gcloud network-management connectivity-tests 可以一秒區分是①還是②③——如果測試說 REACHABLE 但實際連不上，那就是 OS 層問題。
資安稽核要求「資料庫伺服器絕對不能主動連上網際網路」。但資料庫需要定期更新套件。怎麼設計？
分三步：
① Egress DENY 全部：--direction=EGRESS --action=DENY --destination-ranges=0.0.0.0/0 --target-tags=db，優先度 1000。
② ALLOW 特定目的地，優先度設更小（如 900）：Private Google Access 的端點 199.36.153.8/30（連 GCP API 與 GCS）。
③ 套件更新改走內部鏡像：在 VPC 內架一台 apt/yum 鏡像伺服器，或把套件放 Cloud Storage，資料庫透過 Private Google Access 抓。

關鍵洞察：「不能上網」和「不能更新」不是同一件事。把外部依賴內部化，就能同時滿足兩個需求。這也是所有高安全環境的標準做法。
