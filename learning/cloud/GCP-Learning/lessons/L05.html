LESSON 05

IAM 入門：誰、能對什麼、做什麼

IAM 是 GCP 的門禁系統，也是新手最容易卡住的地方。這一課用一個公式把它拆開，之後你看任何權限問題都能對號入座。

閱讀 25 分核心觀念

一、一條公式解決 IAM

IAM 的心智模型
誰（Principal / Member）
  ├─ 使用者      user:tom@example.com
  ├─ 群組        group:devs@example.com
  ├─ 網域        domain:example.com
  └─ 服務帳號    serviceAccount:app@proj.iam.gserviceaccount.com

  ↓ 被授予（bind）

什麼角色（Role）
  └─ 例如 roles/storage.objectViewer

  ↓ 作用在

哪個資源（Resource）
  └─ 例如 專案 my-project 或 特定的 bucket

= 一條 IAM Policy Binding

整套 IAM 就是這條公式的排列組合。沒有「拒絕某人某事」的概念（除非用進階的 Deny Policy），預設全部拒絕，你只做加法。

生活比喻
把 GCP 想成一棟大樓：

Principal（誰） = 持卡人。可以是員工、外包、也可以是機器人（服務帳號）。
Role（角色） = 門禁卡的等級。「訪客卡」只能進大廳，「工程卡」能進機房。
Resource（資源） = 哪一層樓、哪一個房間。

重點：你發卡是發在某一層樓，那個人自動也能進這層樓底下的所有房間——這就是繼承。

二、角色的三種類型

類型範例用途建議
基本角色
Basic		roles/owner
roles/editor
roles/viewer		GCP 早期留下的粗粒度角色，一個角色管幾千個權限正式環境不要用。Editor 幾乎能做任何事，包括刪光資料
預先定義角色
Predefined		roles/storage.objectViewer
roles/compute.instanceAdmin		Google 幫每個服務設計好的細粒度角色，共數百個日常首選。90% 情況用這個就夠
自訂角色
Custom		你自己組合權限清單預先定義角色都不夠精準時需求明確再做。維護成本高，Google 新增權限時你要自己跟
小心踩雷
Editor 角色是最常見的安全債。「先給 Editor 讓他能動工，之後再收回來」——那個「之後」永遠不會來。
正確做法：一開始就給最小必要角色，缺什麼再加。GCP 的錯誤訊息會明確告訴你缺哪個權限，補起來很快。

三、角色的命名規律（看懂就不用背）

bash
roles/<服務>.<資源><權限等級>

roles/storage.objectViewer      → Storage 服務 . 物件 . 檢視者
roles/storage.objectCreator     → 只能上傳，不能讀、不能刪
roles/storage.objectAdmin       → 物件的完整權限
roles/storage.admin             → 整個 Storage 服務的完整權限（含建桶刪桶）

常見的權限等級後綴：
  Viewer  → 唯讀
  User    → 使用（但不能改設定）
  Editor  → 讀 + 寫
  Creator → 只能建立（無法讀取既有的，適合 log 寫入）
  Admin   → 完整控制，含權限管理
實務提醒
找角色的最快方法：不要背，用查的。
bash
# 列出所有含 storage 的角色
gcloud iam roles list --filter="name:storage" --format="table(name, title)"

# 看某個角色到底包含哪些權限
gcloud iam roles describe roles/storage.objectViewer

四、服務帳號（Service Account）：機器人的身分

這是 GCP 最重要、也最容易搞錯的概念。服務帳號是給程式用的身分，不是給人用的。

當你的應用程式要讀 Cloud Storage、寫 BigQuery，它需要一個身分。用你個人的帳號？那你離職服務就掛了。所以要用服務帳號。

bash
# 建立一個服務帳號
gcloud iam service-accounts create app-backend \
    --display-name="訂單服務後端"

# 它的完整名稱長這樣（Email 格式）
# app-backend@tom-gcp-lab-2026.iam.gserviceaccount.com

# 授予它讀取某個 bucket 的權限
gcloud storage buckets add-iam-policy-binding gs://my-bucket \
    --member="serviceAccount:app-backend@tom-gcp-lab-2026.iam.gserviceaccount.com" \
    --role="roles/storage.objectViewer"

# 把服務帳號綁到一台 VM 上（VM 上的程式就自動有這個身分）
gcloud compute instances create my-vm \
    --service-account=app-backend@tom-gcp-lab-2026.iam.gserviceaccount.com \
    --scopes=cloud-platform
小心踩雷
絕對不要下載服務帳號金鑰檔（.json）。
金鑰檔是一個永不過期的密碼。它會出現在：Git commit、Slack 訊息、Docker image、同事的下載資料夾……雲端資料外洩事件中，外洩的服務帳號金鑰是第一大宗。

正確做法：
① 在 GCP 內執行的程式 → 直接附加服務帳號到 VM / Cloud Run / GKE，完全不需要金鑰。
② 在 GCP 外執行（例如 GitHub Actions）→ 用 Workload Identity Federation，用短期 token 換取權限。

五、權限繼承與生效規則

權限往下累加
Organization  ── 授予 tom: roles/viewer
      │                    ↓ 繼承
  Folder「正式」  ── 授予 tom: roles/compute.admin
      │                    ↓ 繼承
  Project「shop-prod」──  授予 tom: roles/storage.admin
      │
  Bucket「gs://logs」

結果：tom 在 gs://logs 上實際擁有
      viewer + compute.admin + storage.admin 的<b>聯集</b>
  • 權限只往下繼承，不往上。
  • 多個來源的權限是聯集（取最寬鬆），不是交集。
  • 不能在下層「減少」上層給的權限——這是最常見的誤解。要限縮只能改上層，或改用 IAM Deny Policy（進階功能）。

六、最小權限原則的實務做法

  1. 永遠授權給群組，不要給個人。人員異動時只要改群組成員，不用翻遍所有專案的 IAM 設定。
  2. 權限給在最低的必要層級。只需要讀一個 bucket，就綁在那個 bucket 上，不要綁在專案上。
  3. 用 IAM Recommender 定期清理。GCP 會自動分析過去 90 天的實際使用狀況，建議你收回沒用到的權限。
  4. 臨時權限用 Conditional Binding 加時效。
bash
# 授予一個 30 天後自動失效的權限
gcloud projects add-iam-policy-binding my-project \
  --member="user:contractor@example.com" \
  --role="roles/compute.viewer" \
  --condition='expression=request.time < timestamp("2026-09-01T00:00:00Z"),title=外包合約期限'

# 查看 IAM Recommender 的建議
gcloud recommender recommendations list \
  --project=my-project \
  --location=global \
  --recommender=google.iam.policy.Recommender

七、排查權限問題的標準流程

  1. 看錯誤訊息。GCP 通常直接寫出缺少的權限名稱，例如 Permission 'storage.objects.get' denied。
  2. 確認身分是誰。是你本人？還是 VM 上的服務帳號？用 gcloud auth list 或看程式的 ADC 設定。
  3. 用 Policy Troubleshooter（Console → IAM → 政策疑難排解）輸入「誰 / 什麼資源 / 什麼權限」，它會告訴你為什麼通過或不通過。
  4. 檢查是不是 Organization Policy 擋的（那不是 IAM 問題，加角色沒用）。
  5. 檢查 API 是否啟用。API 沒開也會回 403。

八、本課檢核

  • 能寫出 IAM 的「誰 + 角色 + 資源」公式
  • 知道 Basic 角色（owner/editor/viewer）不該用在正式環境
  • 能從角色名稱猜出它的權限範圍
  • 理解服務帳號是機器人身分，且不該下載金鑰檔
  • 知道權限是聯集、只往下繼承、下層無法縮減

自我檢測

外包工程師需要在 dev 專案「開關虛擬機，但不能刪除」。該給什麼角色？
roles/compute.instanceAdmin.v1 包含刪除權限，太大。
正確做法是建立自訂角色，只包含：compute.instances.start、compute.instances.stop、compute.instances.get、compute.instances.list。
另外加上 Conditional Binding 設定合約到期日，避免忘記回收。
你的 Cloud Run 服務要寫入 BigQuery，程式在本機測試正常，部署後卻 403。為什麼？
因為本機用的是你個人的 ADC 憑證（你是 Owner），部署後用的是 Cloud Run 的服務帳號。
Cloud Run 預設使用 Compute Engine 預設服務帳號，它不一定有 BigQuery 權限。
解法：建立專屬服務帳號 → 授予 roles/bigquery.dataEditor → 部署時用 --service-account 指定。
這是「本機好好的、上線就爆」最常見的原因，記起來能省你好幾小時。
主管在 Organization 層級給了全公司 roles/viewer，但你希望某個機密專案的成員名單完全保密。IAM 做得到嗎？
單靠一般 IAM 做不到，因為權限往下繼承且無法在下層縮減。
三個可行方向：
① 把該專案移出那個階層（放到獨立 Folder 或獨立 Organization）。
② 使用 IAM Deny Policy（可以明確拒絕特定 principal 的特定權限，優先於 allow）。
③ 用 VPC Service Controls 建立資料邊界。
正確答案通常是①，因為架構分離比疊政策更可靠。
