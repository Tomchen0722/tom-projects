LESSON 07

機器類型、磁碟與映像：規格怎麼挑

選錯機器類型是雲端成本超支的頭號原因。這一課給你一套可以直接套用的選型準則，以及三種能省下 60～90% 費用的定價機制。

閱讀 28 分成本關鍵

一、機器家族：先選家族，再選大小

家族代表型號特性典型用途
E2 通用經濟型e2-micro～e2-standard-32最便宜，CPU 不保證特定型號開發測試、小型網站、學習
不確定時的預設選擇
N2 / N2D 通用均衡型n2-standard-4效能穩定，可自訂 CPU/RAM 比例一般正式環境的應用伺服器
C3 / C4 運算最佳化c3-highcpu-8最新世代 CPU、單核效能最強遊戲伺服器、高頻交易、影音編碼
M3 / M4 記憶體最佳化m3-ultramem-64記憶體可達數 TBSAP HANA、大型記憶體資料庫
A3 / G2 加速器a3-highgpu-8g配備 NVIDIA GPUAI 訓練與推論
極貴，務必設預算警報

同一家族內還有三種配置後綴，決定 CPU 與記憶體的比例：

  • -standard：每 vCPU 約 4GB 記憶體。不知道選什麼就選這個。
  • -highmem：每 vCPU 約 8GB。適合資料庫、快取、大量資料處理。
  • -highcpu：每 vCPU 約 1GB。適合純運算、批次任務、CI/CD Runner。
實務提醒
選型的實務流程不是「一開始就算準」，而是「先猜、再量、後調」：
① 先用 e2-standard-2 之類的中間值上線。
② 跑一到兩週，看 Cloud Monitoring 的 CPU / 記憶體使用率。
③ 用 Rightsizing Recommendations（GCP 自動根據實際用量給建議）調整。
試圖在開機前算出完美規格是浪費時間——真實負載永遠跟你想的不一樣。

二、自訂機器類型：只有 GCP 有的優勢

AWS 只能從固定清單挑，GCP 可以自己指定 CPU 與記憶體。這在「需要 6 顆 CPU 但只要 8GB 記憶體」這種情況能省不少錢：

bash
gcloud compute instances create custom-vm \
  --zone=asia-east1-b \
  --custom-cpu=6 \
  --custom-memory=12GB \
  --custom-vm-type=n2

# 對照：n2-standard-8 是 8vCPU/32GB，你只需要 6/12，硬選會多付 40%

三、三種能大幅省錢的定價機制

機制折扣風險 / 條件適用場景
持續使用折扣
Sustained Use		最高 30%無，機器跑滿一個月自動生效任何長時間執行的機器
不用做任何事
承諾使用折扣
Committed Use		37%（1年）
55%（3年）		綁約，用不用都要付已知穩定的基礎負載
建議只承諾最低水位的 60～70%
Spot VM
（原 Preemptible）		60～91%Google 隨時可回收，最多給 30 秒通知批次運算、CI/CD、影片轉檔、可重試的工作
絕對不要放有狀態的服務
Spot VM 範例
# 開一台 Spot VM（省 60~91%）
gcloud compute instances create batch-worker \
  --zone=asia-east1-b \
  --machine-type=n2-standard-4 \
  --provisioning-model=SPOT \
  --instance-termination-action=DELETE \
  --metadata=startup-script='#!/bin/bash
# 被回收前的優雅關閉處理
trap "gsutil cp /tmp/progress.json gs://my-bucket/checkpoints/; exit" SIGTERM
/opt/run-batch-job.sh'
小心踩雷
Spot VM 的正確用法是「設計成可被中斷」，不是「祈禱不要被中斷」。
必備三件事：① 定期存檢查點（checkpoint）到 Cloud Storage；② 攔截 SIGTERM 做善後；③ 工作可以從中斷處重跑。
做到這三件事，Spot VM 是雲端最划算的資源；沒做到就是災難。

四、磁碟：四種類型與怎麼選

類型代號效能價格（每GB/月）用途
標準永久磁碟pd-standard慢（HDD）約 $0.04備份、冷資料、開發機
平衡永久磁碟pd-balanced中等（SSD）約 $0.10大多數正式環境的預設選擇
SSD 永久磁碟pd-ssd快約 $0.17資料庫、高 IOPS 需求
極致永久磁碟pd-extreme / hyperdisk最快，IOPS 可自訂高關鍵資料庫、SAP
本機 SSDlocal-ssd極快（實體貼著 CPU）固定 375GB 一顆機器一停資料就沒了
只放快取、暫存、shuffle 資料

永久磁碟（Persistent Disk）有兩個關鍵性質新手常忽略：

  • 容量越大，效能越好。PD 的 IOPS 與吞吐量跟容量成正比。如果你的資料庫慢，把 100GB 換成 500GB 可能就解決了——即使你根本用不到 500GB 的空間。
  • 可以線上擴大，不能縮小。擴大不用停機，但一旦擴大就回不去。所以寧可從小開始。
bash
# 線上擴大磁碟（不用停機）
gcloud compute disks resize my-disk --size=200GB --zone=asia-east1-b

# 擴大後還要在作業系統內擴展檔案系統（這一步很多人忘記！）
# SSH 進 VM 後執行：
sudo growpart /dev/sda 1
sudo resize2fs /dev/sda1     # ext4
# 或 sudo xfs_growfs /       # xfs

五、映像檔與快照

概念是什麼用途
公開映像 Public ImageGoogle 維護的 OS 映像（Debian、Ubuntu、Windows Server、RHEL...）開新機器的起點
自訂映像 Custom Image你把一台調好的機器凍結成範本黃金映像（golden image），讓所有機器起點一致
快照 Snapshot磁碟在某個時間點的增量備份備份還原、跨 Region 複製資料
機器映像 Machine Image整台機器（含多顆磁碟、設定、metadata）完整搬遷、複製整台機器
bash
# 把調好的機器做成自訂映像（要先停機）
gcloud compute instances stop web-01 --zone=asia-east1-b
gcloud compute images create web-golden-v1 \
  --source-disk=web-01 --source-disk-zone=asia-east1-b \
  --family=web-golden          # 加入 family，之後可用 --image-family 自動抓最新版

# 之後開新機器直接用它
gcloud compute instances create web-02 \
  --image-family=web-golden --image-project=tom-gcp-lab-2026

# 建立快照排程（自動每日備份，保留 14 天）
gcloud compute resource-policies create snapshot-schedule daily-backup \
  --region=asia-east1 \
  --max-retention-days=14 \
  --daily-schedule --start-time=18:00 \
  --on-source-disk-delete=KEEP_AUTO_SNAPSHOTS

gcloud compute disks add-resource-policies my-disk \
  --resource-policies=daily-backup --zone=asia-east1-b
實務提醒
自訂映像 vs 開機腳本，該用哪個？
開機腳本彈性高但開機慢（每次都要重跑安裝）；自訂映像開機快但要維護版本。
實務常見組合：把不常變的東西（OS 調校、系統套件、監控代理）烤進映像，把常變的東西（應用程式版本、設定）留在開機腳本。這樣自動擴充時新機器 30 秒內就能上線。

  • 能說出 E2 / N2 / C3 / M3 各適合什麼

  • 理解 Spot VM 的省錢幅度與必要的容錯設計

自我檢測

每晚 2 點跑一次、需時 3 小時的資料轉檔工作，怎麼配置最省？
Spot VM + 自動化排程。
① 用 Cloud Scheduler 在 2 點觸發 → ② 建立 Spot VM（省 60～91%）→ ③ 開機腳本自動跑工作 → ④ 完成後gcloud compute instances delete 自己。
因為是離峰批次、可重跑、無狀態，完美符合 Spot 的適用條件。
再進一步可以用 Batch 或 Cloud Run Jobs，連機器管理都省了。
正式環境資料庫抱怨磁碟 I/O 慢，但空間只用了 40%。你的第一個處置是？
把磁碟容量調大（例如 200GB → 1TB），即使空間根本用不完。
因為 GCP 的 Persistent Disk IOPS 和吞吐量與容量線性相關。500GB 的 pd-balanced 大約有 240 MB/s，而 100GB 只有 48 MB/s。
其次才考慮換 pd-ssd 或 hyperdisk。
這是 GCP 特有的行為，從 AWS 過來的人常常想不到。
公司要求「未來一年成本降 30%，但不能影響服務穩定性」。你會怎麼組合？
四層依序處理，風險由低到高：
① Rightsizing——先砍過大的機器。通常這一項就有 15～25%，且零風險。
② 承諾使用折扣——只對「過去一年最低水位的 70%」下 1 年約，可再省 25%。留 buffer 是為了避免業務萎縮時被綁約。
③ 非正式環境用 Spot——dev / CI Runner 全部改 Spot。
④ 排程關機——dev 環境下班自動關，週末不開，等於省 65% 的執行時數。
注意順序：先把浪費砍掉再談承諾折扣，否則你會對著浪費簽三年約。
