LESSON 19

Firestore、Memorystore 與 NoSQL 選擇

不是所有資料都適合塞進關聯式資料庫。這一課講 GCP 的 NoSQL 與快取選項，以及什麼時候該用它們。

閱讀 25 分架構決策

一、Firestore：無伺服器的文件資料庫

Firestore 儲存的是文件（document）——類似 JSON 物件，放在集合（collection）裡。它有三個殺手級特性：

  • 完全無伺服器：不用選規格、不用管擴充、不用付閒置費用。
  • 即時監聽：資料變動時自動推播到用戶端。做聊天室、協作編輯、即時儀表板不用自己寫 WebSocket。
  • 離線支援：行動端 SDK 內建離線快取與自動同步。
Firestore 資料模型
# 資料結構範例
users (collection)
  └── user_abc123 (document)
        ├── name: "王小明"
        ├── email: "ming@example.com"
        ├── created_at: timestamp
        └── orders (subcollection)
              ├── order_001 (document)
              │     ├── amount: 1200
              │     └── items: ["A", "B"]
              └── order_002 (document)
Firestore 操作
# 建立資料庫（新專案用 Native mode）
gcloud firestore databases create --location=asia-east1 --type=firestore-native

# Python 範例
from google.cloud import firestore
db = firestore.Client()

# 寫入
db.collection("users").document("user_abc123").set({
    "name": "王小明",
    "email": "ming@example.com",
    "created_at": firestore.SERVER_TIMESTAMP,
})

# 查詢
docs = (db.collection("users")
          .where("city", "==", "台北")
          .order_by("created_at", direction=firestore.Query.DESCENDING)
          .limit(20)
          .stream())

# 即時監聽
def on_change(col_snapshot, changes, read_time):
    for change in changes:
        print(change.type.name, change.document.id)

db.collection("messages").on_snapshot(on_change)
小心踩雷
Firestore 的查詢能力比 SQL 弱很多，這是最大的限制。
不支援：JOIN、聚合查詢（部分支援）、OR 條件（有限）、大於小於同時用在多個欄位。
而且所有查詢都必須有對應的索引，複合查詢要手動建立複合索引。
如果你的資料有複雜的關聯與查詢需求，Firestore 會讓你痛苦——那是 Cloud SQL 或 BigQuery 的場子。

二、Memorystore：託管的 Redis / Memcached

Memorystore 是記憶體快取，延遲在亞毫秒級。它解決三個典型問題：

用途說明為什麼不能用資料庫做
快取把熱門查詢結果存起來資料庫查詢 5～50ms，Redis 0.2ms
Session 儲存多台無狀態伺服器共享登入狀態這是無狀態架構的必要元件
速率限制計算「這個 IP 一分鐘打了幾次」需要極高頻的原子遞增操作
分散式鎖確保同一時間只有一個程序執行某任務需要原子操作
排行榜 / 佇列Redis 的 Sorted Set / List 資料結構SQL 做這個又慢又複雜
bash
gcloud redis instances create app-cache \
  --size=1 --region=asia-east1 \
  --tier=STANDARD_HA \
  --redis-version=redis_7_0 \
  --network=projects/PROJECT/global/networks/prod-vpc \
  --connect-mode=PRIVATE_SERVICE_ACCESS \
  --redis-config maxmemory-policy=allkeys-lru

gcloud redis instances describe app-cache --region=asia-east1 \
  --format="value(host, port)"
實務提醒
設定 maxmemory-policy=allkeys-lru 很重要。當記憶體滿了，Redis 預設會拒絕寫入（noeviction），導致你的應用開始報錯。
作為純快取用途應該設 allkeys-lru（淘汰最少使用的鍵）；作為 session 儲存則要小心——淘汰 session 等於把使用者登出，這種情況要監控記憶體使用率並及時擴容。

三、快取的三個經典陷阱

  1. 快取穿透：查詢一個不存在的鍵，每次都打到資料庫。解法：把「不存在」這個結果也快取起來（存一個空值，設短 TTL）。
  2. 快取雪崩：大量鍵在同一時間過期，瞬間全部打到資料庫。解法：TTL 加上隨機抖動，例如 3600 + random(0, 300) 秒。
  3. 快取擊穿：某個熱門鍵過期的瞬間，成千上萬個請求同時去重建它。解法：用分散式鎖，只讓一個請求去重建，其他等待。
bash
# 帶抖動與空值保護的快取模式（Python 示意）
import random, json, redis

def get_product(pid):
    key = f"product:{pid}"
    cached = r.get(key)
    if cached is not None:
        return None if cached == b"__NULL__" else json.loads(cached)

    # 用分散式鎖避免擊穿
    lock_key = f"lock:{key}"
    if r.set(lock_key, "1", nx=True, ex=10):
        try:
            data = db_query(pid)
            ttl = 3600 + random.randint(0, 300)          # 抖動防雪崩
            r.setex(key, ttl,
                    json.dumps(data) if data else "__NULL__")  # 空值也快取防穿透
            return data
        finally:
            r.delete(lock_key)
    else:
        time.sleep(0.05)
        return get_product(pid)   # 等鎖釋放後重試

四、其他 NoSQL 選項速覽

服務類型何時用何時不用
Firestore文件行動 App 後端、即時協作、簡單查詢複雜查詢、大量分析
Bigtable寬欄位單表超過 1TB、每秒數十萬次讀寫、時序資料、IoT資料量小（成本不划算，最低約 $500/月）、需要多欄位查詢
Memorystore鍵值（記憶體）快取、session、速率限制持久化儲存（重啟可能遺失）
Spanner關聯式（全球分散）需要 SQL + 全球一致性 + 無限水平擴充小型應用（成本高）
BigQuery分析型欄式分析、報表、資料倉儲線上交易（單筆查詢延遲高、有寫入限制）

自我檢測

一個電商網站，商品頁每秒 5000 次瀏覽，但商品資料一天只更新幾次。怎麼設計？
Cloud SQL（來源真相）+ Memorystore（快取）+ CDN（邊緣快取）三層。

① CDN 層：商品頁 HTML/JSON 設 Cache-Control: public, max-age=300。這一層能擋掉 90%+ 的流量，成本最低。
② Memorystore 層：CDN 未命中時查 Redis，TTL 1 小時 + 隨機抖動。
③ Cloud SQL：只有快取未命中才查。
④ 更新時主動清除快取（cache invalidation），而不是等 TTL 過期。

結果：資料庫實際 QPS 可能只有個位數。5000 QPS 的問題用一台小資料庫就能解決——關鍵是分層，不是加大資料庫。
IoT 專案，10 萬個感測器每 10 秒回報一次資料，要保存 2 年並支援時間範圍查詢。用什麼？
資料量估算：10萬 × 6次/分 × 60 × 24 × 365 × 2 ≈ 1.05 兆筆。這個量體排除了大部分選項。

建議架構：
• Pub/Sub 接收 → Dataflow 處理 →
• Bigtable（近期熱資料，如 90 天）：專為時序設計，row key 用 裝置ID#反轉時間戳，時間範圍掃描極快。
• BigQuery（歷史冷資料）：按日期分區，做長期分析與報表。
• 生命週期規則自動把 Bigtable 舊資料匯出到 BigQuery / GCS。

為什麼不用 Cloud SQL：1 兆筆遠超單機關聯式資料庫的能力，即使分片也會非常痛苦。
為什麼不全用 BigQuery：BigQuery 的單筆查詢延遲在秒級，不適合即時儀表板；而且高頻串流寫入的成本比 Bigtable 高。
這種「熱資料快查 + 冷資料便宜」的分層是所有大規模時序系統的標準做法。
團隊說「我們用 Redis 存訂單資料，因為快」。你的評估？
危險，這是把快取當資料庫用。三個問題：
① 持久性——Memorystore 雖有 RDB 快照，但預設是非同步的，故障時可能遺失最近幾分鐘的寫入。訂單資料遺失是不能接受的。
② 記憶體成本——Redis 資料全在記憶體，1TB 資料的 Memorystore 費用是 Cloud SQL 的數十倍。
③ 查詢能力——沒有交易、沒有 JOIN、沒有複雜查詢、沒有報表能力。「查上個月台北地區訂單總額」在 Redis 上做不到。

正確做法：訂單寫入 Cloud SQL（有 ACID 交易），Redis 只快取「訂單狀態查詢」這類高頻讀取。
判斷準則很簡單：資料遺失能不能接受？不能接受的資料就不該只存在快取裡。
