LESSON 14

對外連線：Cloud NAT、外部 IP 與 Cloud DNS

私有機器怎麼連外網？外部 IP 怎麼管？網域怎麼指到 GCP？這三個問題是每個實務專案都會碰到的。

操作 35 分實作

一、Cloud NAT：讓私有機器能對外，但外面連不進來

這是雲端網路最重要的模式之一。你的機器需要：下載套件、呼叫外部 API、更新系統——但你不希望它們有公開 IP，因為那等於把門開向全世界。

生活比喻
Cloud NAT 就像公司的總機。

員工（私有 VM）可以打電話出去，對方看到的是公司總機號碼（NAT 的外部 IP）。
但外面的人打總機進來，沒辦法直接接到某個員工的分機——因為沒有人幫他轉接。

這就是「單向可通」：出得去，進不來。這正是絕大多數後端伺服器該有的狀態。
動手實作

實作：建立 Cloud NAT

  1. 先建立 Cloud Router（NAT 需要它來管理路由）：
    bash
    gcloud compute routers create prod-router \
  --network=prod-vpc --region=asia-east1
  2. 建立 NAT 閘道：
    bash
    gcloud compute routers nats create prod-nat \
  --router=prod-router --region=asia-east1 \
  --auto-allocate-nat-external-ips \
  --nat-all-subnet-ip-ranges \
  --enable-logging \
  --log-filter=ERRORS_ONLY
  3. 開一台完全沒有外部 IP的機器測試：
    bash
    gcloud compute instances create private-test \
  --zone=asia-east1-b --machine-type=e2-micro \
  --subnet=prod-asia-east1 --no-address \
  --image-family=debian-12 --image-project=debian-cloud
  4. 透過 IAP 連進去（記得先建 allow-iap-ssh 防火牆規則）：
    bash
    gcloud compute ssh private-test --zone=asia-east1-b --tunnel-through-iap
  5. 在機器裡驗證能對外，且看到的是 NAT 的 IP：
    bash
    curl -s ifconfig.me          # 顯示 NAT 的外部 IP
sudo apt update              # 應該成功
ping -c 3 8.8.8.8            # ICMP 也走 NAT
小心踩雷
Cloud NAT 的隱藏陷阱：連接埠耗盡（port exhaustion）。
一個 NAT IP 有約 64,000 個埠，預設每台 VM 分配 64 個。如果你的機器要對同一個目的地開大量連線（例如爬蟲、高頻 API 呼叫），會出現「連線隨機失敗」的詭異現象。
解法：
bash
# 增加每台 VM 的最小埠數，並允許動態擴充
gcloud compute routers nats update prod-nat \
  --router=prod-router --region=asia-east1 \
  --min-ports-per-vm=1024 \
  --max-ports-per-vm=8192 \
  --enable-dynamic-port-allocation

# 或改用手動指定多個靜態 IP（每多一個 IP 就多 64K 個埠）
gcloud compute addresses create nat-ip-1 nat-ip-2 --region=asia-east1
gcloud compute routers nats update prod-nat \
  --router=prod-router --region=asia-east1 \
  --nat-external-ip-pool=nat-ip-1,nat-ip-2
實務提醒
使用靜態 NAT IP 的另一個重要理由：對方要白名單。
很多第三方 API（金流、簡訊、企業客戶）要求你提供固定的來源 IP 才放行。用 --auto-allocate-nat-external-ips 的話 IP 會變動，你就無法給對方一個穩定的白名單。正式環境請一律用固定的 NAT IP 池。

二、外部 IP 的兩種類型

臨時 Ephemeral靜態 Static
取得方式建立 VM 時自動分配gcloud compute addresses create
機器停止後釋放，重啟會拿到不同 IP保留
費用使用中免費使用中免費，閒置未綁定時收費
適用測試、可拋棄的機器DNS 指向、第三方白名單、NAT
小心踩雷
「未使用的靜態 IP 要收費」是最常見的隱形帳單。Google 這樣設計是為了避免有人囤積 IP。
每個閒置的靜態 IP 約每月 $7。開了 10 個忘記刪，一年就是 $840。
定期檢查：gcloud compute addresses list --filter="status=RESERVED"

三、Cloud DNS：把網域指到你的服務

Cloud DNS 是 Google 的權威 DNS 服務，SLA 100%（是的，Google 對這個服務承諾 100% 可用性）。

動手實作

實作：設定公開網域

  1. 建立代管區域（managed zone）：
    bash
    gcloud dns managed-zones create example-zone \
  --dns-name=example.com. \
  --description="主要網域" \
  --visibility=public
  2. 查出 Google 給你的名稱伺服器：
    bash
    gcloud dns managed-zones describe example-zone \
  --format="value(nameServers)"
  3. 到你買網域的地方（GoDaddy、Cloudflare、Gandi 等）把 NS 記錄改成上面四筆。這一步在 GCP 外面做，通常要等 1～48 小時生效。
  4. 新增 A 記錄指向你的負載平衡器：
    bash
    gcloud dns record-sets create www.example.com. \
  --zone=example-zone --type=A --ttl=300 \
  --rrdatas=34.1.2.3

# CNAME 範例
gcloud dns record-sets create blog.example.com. \
  --zone=example-zone --type=CNAME --ttl=300 \
  --rrdatas=ghs.googlehosted.com.

# MX 記錄（Google Workspace 郵件）
gcloud dns record-sets create example.com. \
  --zone=example-zone --type=MX --ttl=3600 \
  --rrdatas="1 aspmx.l.google.com.,5 alt1.aspmx.l.google.com."
  5. 驗證：
    bash
    dig +short www.example.com @$(gcloud dns managed-zones describe example-zone --format='value(nameServers[0])')

四、私有 DNS 區域（企業必用）

你不會希望內部服務的名稱暴露在公開 DNS 上。私有區域只在指定的 VPC 內解析得到：

bash
gcloud dns managed-zones create internal-zone \
  --dns-name=internal.corp. \
  --visibility=private \
  --networks=prod-vpc \
  --description="內部服務名稱"

gcloud dns record-sets create db.internal.corp. \
  --zone=internal-zone --type=A --ttl=60 \
  --rrdatas=10.10.0.5

# 現在 VPC 內的機器可以用 db.internal.corp 連資料庫
# 從外面查詢完全解析不到
實務提醒
私有 DNS 是「換機器不用改設定」的關鍵。
如果應用程式連的是 10.10.0.5，換一台資料庫就要改所有應用的設定檔。連 db.internal.corp 的話，只要改一筆 DNS 記錄即可。
把 TTL 設短（60 秒）讓切換能快速生效。

五、DNS 轉發：混合雲場景

bash
# 情境一：GCP 的機器要解析地端的內部網域
gcloud dns managed-zones create onprem-forward \
  --dns-name=corp.local. --visibility=private \
  --networks=prod-vpc \
  --forwarding-targets=192.168.1.10,192.168.1.11

# 情境二：地端的機器要解析 GCP 的私有網域
# 建立 DNS 伺服器政策，開放 inbound 轉發
gcloud dns policies create hybrid-dns-policy \
  --networks=prod-vpc --enable-inbound-forwarding \
  --description="讓地端 DNS 能查詢 GCP 私有區域"

自我檢測

Cloud NAT 建好了，機器還是連不到外網。列出檢查項目。
五項依序檢查：
① NAT 有沒有涵蓋這個子網路——如果沒用 --nat-all-subnet-ip-ranges，要確認子網路有被列入。
② Egress 防火牆有沒有擋——NAT 只處理位址轉換，防火牆規則仍然生效。
③ 機器是不是真的沒有外部 IP——有外部 IP 的機器不會走 NAT，它直接走自己的 IP 出去。
④ Region 對不對——Cloud Router 和 NAT 是區域級的，只服務同 Region 的子網路。
⑤ DNS 能不能解析——連 IP 通但連網域不通的話，問題在 DNS 而非 NAT。
你的爬蟲服務有 20 台 VM，抓同一個網站，開始出現大量連線逾時。NAT 設定該怎麼調？
典型的 NAT 連接埠耗盡。NAT 的埠是以「來源VM + 目的地IP + 目的地Port」的組合配置的，全部連同一個目標網站時，可用埠數被同一個目的地吃光。
三個調整方向：
① 提高每 VM 的埠數：--min-ports-per-vm=2048 並啟用 --enable-dynamic-port-allocation。
② 增加 NAT IP 數量：每個 IP 提供額外 64K 埠，20 台機器建議至少 3～4 個 IP。
③ 應用層優化：使用連線池（connection pooling）與 HTTP Keep-Alive，減少連線建立次數。這一項效果通常最好，因為它治本。
另外開啟 NAT logging（--log-filter=ERRORS_ONLY）可以直接看到 OUT_OF_RESOURCES 錯誤確認診斷。
公司同時有地端資料中心和 GCP。內部服務名稱該怎麼統一管理？
雙向 DNS 轉發，讓兩邊都能用名稱互相找到對方：

① GCP → 地端：建立私有轉發區域，--forwarding-targets 指向地端 DNS 伺服器 IP。GCP 的機器查 *.corp.local 時會被轉發過去。
② 地端 → GCP：建立 DNS 政策並 --enable-inbound-forwarding，GCP 會提供一個內部 IP（透過 VPN/Interconnect 可達），地端 DNS 設定條件轉發指向它。

命名規劃建議：用不同的子網域區分位置，例如 *.gcp.corp.internal 和 *.dc.corp.internal。不要讓同一個名稱在兩邊解析到不同結果——那會產生極難排查的問題。
