LESSON 41

Cloud Composer：企業排程與資料工作流

十幾條資料處理腳本、彼此有先後關係、還常常要回補歷史——這是 cron 撐不住的地方。這一課用託管的 Airflow 把它們變成看得見、管得動的工作流。

操作 60 分實作

一、為什麼 cron 撐不住企業的排程

大部分團隊的排程都是這樣長出來的：先在一台機器上寫 crontab，跑一支每天匯總資料的腳本。半年後，那台機器上有 40 條 cron，彼此之間有隱形的先後關係，沒人敢動。

生活比喻
cron 像鬧鐘：時間到就響，不管你前一件事做完沒有。
早上 7:00 的鬧鐘不會知道「昨晚的洗衣機還沒洗完」。

Airflow 像廚房的出菜流程：前菜出完才做主菜，主菜失敗就重做那一道，甜點不受影響。
而且整個流程畫在牆上，誰都看得到現在卡在哪一道。
需求cron 能不能Airflow
「A 跑完才跑 B」只能靠猜時間差直接宣告相依關係
失敗自動重試 3 次要自己寫設定一個參數
某天資料遲到，重跑那一天手動改腳本指定日期回補（backfill）
看得到歷史每一次執行結果翻 log網頁 UI 一目了然
失敗通知負責人要自己寫內建

Cloud Composer 就是 Google 託管的 Apache Airflow。你不用自己架 Airflow 的 scheduler、webserver、資料庫與 worker，但寫的還是標準 Airflow DAG，換到別的雲或地端也帶得走。

二、Airflow 的五個核心名詞

Airflow 概念圖
DAG（有向無環圖）= 一整條工作流程
 │   例：「每日營收報表」
 │
 ├─→ Task A：從 Cloud SQL 匯出訂單    ─┐
 ├─→ Task B：從 GA4 匯出流量           ─┤ 這兩個可以同時跑
 │                                      │
 └─→ Task C：合併寫進 BigQuery       ←─┘ 要等 A 和 B 都成功
      │
      └─→ Task D：寄出報表

Operator = 這個 Task 實際做什麼事
   BashOperator / PythonOperator / BigQueryInsertJobOperator …

Scheduler = 判斷「現在該跑哪些 Task」的大腦
Executor  = 實際去執行的工人（Composer 2 用 Kubernetes）
最容易搞錯的一個字
DAG 的 A 是 Acyclic（無環）——流程不能繞回去。
「A → B → C → A」在 Airflow 是非法的，因為那會永遠跑不完。
如果你的流程真的需要迴圈（例如「重試到成功為止」），那是重試機制要處理的事，不是用 DAG 畫圈。

三、Composer 的版本與計費模型

版本底層特點
Composer 1GKE Standard舊版，節點要自己配。新專案不要選
Composer 2GKE Autopilot可自動擴充 worker，目前的主流選擇
Composer 3Google 全託管更少維運、啟動更快；可用地區與功能仍在擴充中
先講錢，這是 Composer 最大的坑
Composer 環境是「常駐」的，不是按 DAG 執行次數計費。
只要環境開著，scheduler、webserver、資料庫就一直在燒錢——即使你一整天沒跑任何 DAG。

小型環境一個月大約數十到上百美元起跳，實際依地區、規模與版本而異，請以官方計價頁為準。

所以：如果你只是要「每天半夜跑一支腳本」，不要用 Composer。用 Cloud Scheduler + Cloud Run Job，一個月幾乎不用錢。Composer 要到「十幾條 DAG、彼此有相依、需要回補歷史」才划算。

動手實作

實作二：每日營收彙總 DAG

這支 DAG 做一件企業每天都在做的事：把昨天的訂單彙總進報表表，成功後匯出給業務單位。

daily_revenue.py
from datetime import datetime, timedelta
from airflow import DAG
from airflow.providers.google.cloud.operators.bigquery import (
    BigQueryInsertJobOperator,
)
from airflow.providers.google.cloud.transfers.bigquery_to_gcs import (
    BigQueryToGCSOperator,
)

default_args = {
    "owner": "data-team",
    "retries": 3,                          # 失敗自動重試 3 次
    "retry_delay": timedelta(minutes=5),
    "email_on_failure": True,
    "email": ["data-oncall@example.com"],
}

with DAG(
    dag_id="daily_revenue",
    start_date=datetime(2026, 1, 1),
    schedule="0 3 * * *",       # 每天凌晨 3 點
    catchup=False,              # 不要把過去每一天都補跑一次
    default_args=default_args,
    max_active_runs=1,          # 同時只允許一次執行，避免互相打架
    tags=["finance", "daily"],
) as dag:

    # ① 彙總昨天的訂單
    aggregate = BigQueryInsertJobOperator(
        task_id="aggregate_orders",
        configuration={
            "query": {
                "query": """
                    MERGE `mart.daily_revenue` T
                    USING (
                      SELECT
                        DATE('{{ ds }}') AS report_date,
                        store_id,
                        COUNT(*)         AS order_count,
                        SUM(amount)      AS revenue
                      FROM `raw.orders`
                      WHERE DATE(created_at) = DATE('{{ ds }}')
                      GROUP BY store_id
                    ) S
                    ON  T.report_date = S.report_date
                    AND T.store_id    = S.store_id
                    WHEN MATCHED THEN UPDATE SET
                      order_count = S.order_count, revenue = S.revenue
                    WHEN NOT MATCHED THEN INSERT ROW
                """,
                "useLegacySql": False,
            }
        },
    )

    # ② 匯出成 CSV 給業務單位
    export = BigQueryToGCSOperator(
        task_id="export_csv",
        source_project_dataset_table="mart.daily_revenue",
        destination_cloud_storage_uris=[
            "gs://my-reports/revenue/{{ ds }}.csv"
        ],
        export_format="CSV",
    )

    aggregate >> export        # 宣告相依：彙總成功才匯出
  1. 上傳 DAG：
    bash
    gcloud composer environments storage dags import \
  --environment=demo-airflow \
  --location=asia-east1 \
  --source=daily_revenue.py
  2. 打開 Airflow UI，等 1~2 分鐘 DAG 會出現。手動觸發一次驗證。
兩個模板變數要記住
{{ ds }} = 這次執行對應的邏輯日期（YYYY-MM-DD），不是今天的日期。
{{ ds_nodash }} = 同上但沒有橫線（20260817）。

這個區別很重要：凌晨 3 點跑的排程處理的是「昨天」的資料，Airflow 會自動把 ds 設成正確的那一天，所以回補歷史時同一份程式碼不用改。

另外注意上面用的是 MERGE 而不是 INSERT——這樣重跑同一天不會產生重複列，也就是冪等。排程一定會有重跑的一天。

五、企業最常踩的四個坑

坑一：catchup 忘了關
catchup 預設是 True。如果你的 start_date 寫成一年前，DAG 一上線 Airflow 會立刻嘗試補跑 365 次。
輕則帳單爆炸，重則把下游資料庫打掛。新 DAG 一律先寫 catchup=False，要回補再手動指定區間。
坑二：DAG 檔案不是即時生效
你上傳到 GCS 之後，Composer 要同步到 worker 再由 scheduler 解析，通常有幾十秒到幾分鐘的延遲。
改完沒看到變化不要急著再改一次，先等一下、重新整理 UI。
坑三：在 DAG 檔的最外層寫重活
Scheduler 會反覆解析每個 DAG 檔。如果你在檔案最外層直接查資料庫或呼叫 API，那段程式碼會被執行無數次。
規則：DAG 檔的最外層只做「定義」，所有實際工作都要放進 Operator 裡。
坑四：時區
Airflow 內部一律用 UTC。schedule="0 3 * * *" 如果沒設時區，跑的是 UTC 3 點 = 台灣時間 11 點。
要用當地時間就明確指定：pendulum.timezone("Asia/Taipei")。

六、什麼時候「不要」用 Composer

你的情況建議理由
一支腳本，每天跑一次Cloud Scheduler + Cloud Run Job幾乎不用錢，不用養環境
事件觸發（檔案上傳就處理）Eventarc + Cloud RunAirflow 是排程導向，不擅長即時事件
串流資料Dataflow（第 29 課）Airflow 處理的是批次
只要串接幾個 API、邏輯簡單Cloud Workflows用 YAML 定義，按執行步數計費
十幾條 DAG、有相依、要回補Composer ✅這才是它的主場
實務提醒
Airflow 是「編排器」，不是「執行引擎」。
正確用法是讓 Airflow 去觸發 BigQuery、Dataflow、Dataproc 做事，然後等結果。
錯誤用法是把幾 GB 的資料拉進 Airflow worker 用 pandas 處理——worker 記憶體會爆，而且完全沒用到雲端的擴充能力。

  • 做完實作已刪除 Composer 環境

自我檢測

你把一個 start_date 設為 2025-01-01 的新 DAG 上線，結果帳單暴增、下游資料庫被打掛。發生什麼事？
catchup 沒關。Airflow 預設 catchup=True，會把 start_date 到現在之間每一個排程週期都補跑一次。日排程 × 一年多 = 400 多次執行同時湧出。

立即處置：
① 在 Airflow UI 把 DAG 設為 Paused，停止繼續派工
② 清掉佇列中的 task instance
③ 確認下游資料有沒有被重複寫入（這就是為什麼寫入邏輯要冪等，例如用 MERGE 而不是純 INSERT）

根本修正：catchup=False，並加上 max_active_runs=1 限制同時執行數。真的需要回補時，用 backfill 指定明確區間，分批來。
主管問：「我們只有 3 支每日腳本，要不要導入 Composer？」你怎麼回答？
不要。理由是成本結構不匹配。

Composer 環境是常駐計費，不管你跑不跑 DAG 都在收錢。3 支腳本用 Cloud Scheduler + Cloud Run Job，費用趨近於零。

那什麼時候該換過去？出現這些訊號再考慮：
• 腳本之間開始有先後相依，而你在用「睡 10 分鐘」來對齊
• 常常需要回補特定某一天的資料
• 沒人講得清楚「昨天那批到底跑成功沒有」
• 腳本數量到十幾支，散在不同機器上

建議的講法：先用便宜的方案跑，等痛點真的出現再遷移。中間還有 Cloud Workflows 這個選項，比 cron 強、比 Composer 便宜。
同事的 DAG 檔在最外層寫了「查詢 Cloud SQL 取得店家清單，再用迴圈動態產生 Task」。這樣有什麼問題？
Scheduler 會反覆重新解析 DAG 檔，那段查詢也會跟著被執行。一天下來就是幾千次不必要的資料庫查詢。

更糟的是：如果 Cloud SQL 暫時連不上，整個 DAG 檔會解析失敗、直接從 UI 消失，連帶其他 Task 也不能跑。

解法（由簡到繁）：
① 把清單改成靜態設定——存成 Airflow Variable 或 JSON 檔，用另一支 DAG 定期更新它。解析時只讀本地值，不打資料庫。
② 改用動態任務對應（dynamic task mapping）——在執行時而非解析時展開，這才是正解。
③ 如果店家清單很少變，直接寫死在程式碼裡也完全可以接受。

通則：DAG 檔的最外層只放「定義」，任何 I/O 都該在 Operator 執行時才發生。
