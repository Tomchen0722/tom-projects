LESSON 26

GKE 實戰：部署一個可擴充的服務

從建立叢集到服務上線、自動擴充、滾動更新，完整走一遍。重點放在 Autopilot 模式——它讓你享受 K8s 的能力而不用管節點。

操作 60 分約 1 美元實作

一、Autopilot vs Standard：先選對模式

AutopilotStandard
節點管理Google 全包，你看不到節點你自己管節點池、規格、升級
計費按 Pod 實際請求的資源按節點（即使 Pod 沒用滿也要付）
安全預設強制安全基準（非 root、Shielded、Workload Identity）要自己設定
彈性受限（不能用 DaemonSet 改核心參數、不能用特權容器）完全彈性
適合絕大多數應用需要 GPU 特殊設定、特權容器、自訂核心參數
建議新專案的預設選擇有明確需求才選
補充
Autopilot 的計費模式對成本控制很有幫助。Standard 模式下，你付的是節點費用——如果節點只用了 40%，那 60% 是純浪費。Autopilot 只算你的 Pod requests，裝箱效率的問題由 Google 承擔。
代價是每 vCPU 的單價較高，所以如果你的叢集裝箱率能穩定維持在 80% 以上，Standard 可能較便宜。

二、實作：建立叢集與部署

動手實作

實作：完整流程

  1. 啟用 API 並建立 Autopilot 叢集（建立要 5～10 分鐘）：
    bash
    gcloud services enable container.googleapis.com

gcloud container clusters create-auto lab-cluster \
  --region=asia-east1 \
  --release-channel=regular
  2. 取得憑證，讓 kubectl 能連上：
    bash
    gcloud container clusters get-credentials lab-cluster --region=asia-east1
kubectl cluster-info
kubectl get nodes
  3. 建立 namespace（正式環境一定要用 namespace 隔離）：
    bash
    kubectl create namespace demo
  4. 寫 Deployment 與 Service：
    bash
    cat > app.yaml <<'YAML'
apiVersion: apps/v1
kind: Deployment
metadata:
  name: hello-app
  namespace: demo
spec:
  replicas: 3
  selector:
    matchLabels: {app: hello}
  template:
    metadata:
      labels: {app: hello}
    spec:
      containers:
      - name: hello
        image: us-docker.pkg.dev/google-samples/containers/gke/hello-app:1.0
        ports: [{containerPort: 8080}]
        resources:
          requests: {cpu: 100m, memory: 128Mi}
          limits:   {cpu: 500m, memory: 256Mi}
        readinessProbe:
          httpGet: {path: /, port: 8080}
          periodSeconds: 5
        livenessProbe:
          httpGet: {path: /, port: 8080}
          periodSeconds: 15
---
apiVersion: v1
kind: Service
metadata:
  name: hello-svc
  namespace: demo
spec:
  type: LoadBalancer
  selector: {app: hello}
  ports: [{port: 80, targetPort: 8080}]
YAML

kubectl apply -f app.yaml
  5. 觀察部署過程：
    bash
    kubectl get pods -n demo -w          # -w 持續觀察，Ctrl+C 離開
kubectl get svc -n demo              # 等 EXTERNAL-IP 出現（1~2 分鐘）
kubectl describe deployment hello-app -n demo
  6. 測試服務：
    bash
    IP=$(kubectl get svc hello-svc -n demo -o jsonpath='{.status.loadBalancer.ingress[0].ip}')
for i in {1..6}; do curl -s http://$IP; done   # 看到不同的 Pod 名稱
  7. 設定自動擴充（HPA）：
    bash
    kubectl autoscale deployment hello-app -n demo \
  --cpu-percent=60 --min=3 --max=15

kubectl get hpa -n demo
  8. 製造負載觀察擴充：
    bash
    kubectl run -n demo load-gen --image=busybox --restart=Never -- \
  /bin/sh -c "while true; do wget -q -O- http://hello-svc; done"

# 另開視窗觀察
kubectl get hpa -n demo -w
kubectl get pods -n demo -w
  9. 滾動更新到新版本：
    bash
    kubectl set image deployment/hello-app -n demo \
  hello=us-docker.pkg.dev/google-samples/containers/gke/hello-app:2.0

kubectl rollout status deployment/hello-app -n demo
kubectl rollout history deployment/hello-app -n demo

# 回滾
kubectl rollout undo deployment/hello-app -n demo

三、Workload Identity：Pod 怎麼取得 GCP 權限

這是 GKE 最重要的安全機制。不要下載服務帳號金鑰放進 Pod，用 Workload Identity 讓 K8s 服務帳號直接對應到 GCP 服務帳號。

bash
# 1. 建立 GCP 服務帳號並授權
gcloud iam service-accounts create gke-app-sa
gcloud projects add-iam-policy-binding $PROJECT \
  --member="serviceAccount:gke-app-sa@$PROJECT.iam.gserviceaccount.com" \
  --role="roles/storage.objectViewer"

# 2. 建立 K8s 服務帳號
kubectl create serviceaccount app-ksa -n demo

# 3. 綁定兩者
gcloud iam service-accounts add-iam-policy-binding \
  gke-app-sa@$PROJECT.iam.gserviceaccount.com \
  --role="roles/iam.workloadIdentityUser" \
  --member="serviceAccount:$PROJECT.svc.id.goog[demo/app-ksa]"

kubectl annotate serviceaccount app-ksa -n demo \
  iam.gke.io/gcp-service-account=gke-app-sa@$PROJECT.iam.gserviceaccount.com

# 4. Pod 使用它 —— 程式碼完全不需要處理認證
#    spec:
#      serviceAccountName: app-ksa
實務提醒
Workload Identity 消除了金鑰檔的存在。Pod 內的應用程式呼叫 Google Cloud client library 時，會自動透過 metadata server 取得短期 token。沒有金鑰檔可以外洩、不用輪換、權限可以隨時撤銷。
Autopilot 叢集強制啟用這個功能，這也是選 Autopilot 的好處之一。

四、正式環境必備的四個設定

正式環境設定
# ① PodDisruptionBudget：節點維護時保證可用性
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata: {name: hello-pdb, namespace: demo}
spec:
  minAvailable: 2                 # 任何時候至少要有 2 個
  selector:
    matchLabels: {app: hello}
---
# ② 反親和性：把 Pod 分散到不同節點與 Zone
spec:
  template:
    spec:
      topologySpreadConstraints:
      - maxSkew: 1
        topologyKey: topology.kubernetes.io/zone
        whenUnsatisfiable: DoNotSchedule
        labelSelector:
          matchLabels: {app: hello}
---
# ③ NetworkPolicy：預設拒絕所有 Pod 間流量
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: {name: default-deny, namespace: demo}
spec:
  podSelector: {}
  policyTypes: [Ingress, Egress]
---
# ④ ResourceQuota：限制 namespace 的總資源用量
apiVersion: v1
kind: ResourceQuota
metadata: {name: demo-quota, namespace: demo}
spec:
  hard:
    requests.cpu: "10"
    requests.memory: 20Gi
    limits.cpu: "20"
    limits.memory: 40Gi
    pods: "50"

五、Ingress：用一個 IP 服務多個應用

bash
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: main-ingress
  namespace: demo
  annotations:
    kubernetes.io/ingress.class: "gce"
    kubernetes.io/ingress.global-static-ip-name: "web-ip"
    networking.gke.io/managed-certificates: "web-cert"
spec:
  rules:
  - host: api.example.com
    http:
      paths:
      - path: /*
        pathType: ImplementationSpecific
        backend: {service: {name: api-svc, port: {number: 80}}}
  - host: www.example.com
    http:
      paths:
      - path: /*
        pathType: ImplementationSpecific
        backend: {service: {name: web-svc, port: {number: 80}}}
---
apiVersion: networking.gke.io/v1
kind: ManagedCertificate
metadata: {name: web-cert, namespace: demo}
spec:
  domains: [api.example.com, www.example.com]

GKE 的 Ingress 會自動建立一個 Global External Application LB——就是第 9 課學的那個。所以你其實一直都在用同一套底層。

六、成本控制

  • Autopilot 沒有節點閒置成本，但要注意 Pod 的 requests 設太大會直接反映在帳單上。
  • Standard 模式用 Spot 節點池跑可中斷的工作，省 60～91%。
  • 設定 Cluster Autoscaler 的下限，離峰時把節點縮到最少。
  • dev 叢集用單一 Zone（--zone 而非 --region），省下跨區流量與備援節點費用。
  • 叢集管理費：每個叢集約 $0.10/小時（約 $73/月），所以不要為每個環境開一個叢集，用 namespace 隔離即可。

  • 會做滾動更新與回滾

自我檢測

HPA 設定好了但 Pod 數量一直不變，即使 CPU 已經 100%。可能原因？
四個依序檢查：
① Pod 沒有設定 resources.requests.cpu——HPA 的 CPU 百分比是相對於 requests 計算的。沒設 requests，HPA 無法計算百分比，會顯示 <unknown>。這是最常見的原因。
② metrics-server 沒運作——kubectl top pods 如果報錯就是這個問題（GKE 通常自動裝好）。
③ 已達 maxReplicas 上限。
④ 叢集資源不足——Pod 卡在 Pending 狀態。kubectl describe pod 會顯示 Insufficient cpu。Standard 模式要檢查 Cluster Autoscaler 有沒有開、有沒有達到節點上限。

診斷指令：kubectl describe hpa -n demo 會直接顯示計算過程與問題。
節點升級時服務中斷了 30 秒，但 replicas 有 3 個。為什麼？
三個 Pod 可能都排在同一個節點上。節點被抽掉時三個一起消失。

兩個必要的防護：
① PodDisruptionBudget——設定 minAvailable: 2。這會讓節點排空（drain）操作暫停等待，直到新 Pod 在其他節點就緒，才繼續移除。沒有 PDB 的話，K8s 認為可以一次全部趕走。
② topologySpreadConstraints——強制 Pod 分散到不同節點與不同 Zone。這樣單一節點或單一 Zone 的問題不會影響全部。

另外要檢查 preStop hook 與優雅關閉（第 25 課提過），確保正在處理的請求不會被硬中斷。

「有 3 個副本」不等於「高可用」——關鍵是它們有沒有分散在不同的故障域。
公司有 dev / staging / prod 三個環境，該開三個叢集還是一個叢集三個 namespace？
prod 一定要獨立叢集，dev 和 staging 可以共用。

prod 獨立的理由（不可妥協）：
• 爆炸半徑——叢集層級的操作（升級控制平面、修改 CNI、RBAC 誤設）會影響所有 namespace。
• 版本策略——prod 應該用穩定的 release channel 並延後升級，dev 可以用 rapid channel 提早發現問題。
• 資安邊界——namespace 的隔離是軟隔離。容器逃逸漏洞、節點層級的攻擊可以跨 namespace。稽核通常不接受 prod 與 dev 同叢集。
• 資源競爭——dev 的壓力測試不該影響 prod。

dev + staging 共用的理由：
• 每個叢集固定 ~$73/月管理費 + 最小節點成本，開太多不划算。
• 用 namespace + ResourceQuota + NetworkPolicy 隔離已經足夠。

建議配置：prod-cluster（regional，穩定 channel）+ nonprod-cluster（zonal 省錢，含 dev/staging/qa 三個 namespace）。
