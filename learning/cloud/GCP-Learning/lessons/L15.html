LESSON 15

混合雲連線：VPN 與 Interconnect

企業上雲極少是一次搬完，多半是地端與雲端並存好幾年。這一課講怎麼把兩邊接起來，以及三種方案的成本與可用性取捨。

閱讀 25 分企業級

一、三種連線方式的取捨

方案頻寬延遲月成本（概估）建置時間SLA
Cloud VPN
（走網際網路加密）		最高 3 Gbps
（每條通道 1.25~3G）		中等，受公網影響低
$0.05/小時/通道 + 流量		數小時HA VPN 99.99%
Partner Interconnect
（透過電信商）		50 Mbps ~ 50 Gbps低且穩定中
視電信商方案		數天～數週99.9% / 99.99%
Dedicated Interconnect
（直接拉專線到 Google）		10 或 100 Gbps最低高
連接埠費 + 跨接費		數週～數月99.9% / 99.99%

選擇準則很簡單：

  1. 從 HA VPN 開始。便宜、快、99.99% SLA，能滿足絕大多數需求。
  2. 頻寬需求超過 3 Gbps，或對延遲極度敏感（例如即時交易、資料庫同步）→ Partner Interconnect。
  3. 需要 10 Gbps 以上、且你的資料中心在 Google 的據點附近 → Dedicated Interconnect。

二、HA VPN：高可用的正確做法

Classic VPN 已經是舊架構（SLA 只有 99.9%）。新專案一律用 HA VPN，它有兩個介面、兩個外部 IP，天生就是雙通道。

HA VPN 架構
GCP 端                          地端
┌─────────────────┐            ┌──────────────┐
│  HA VPN Gateway  │            │  你的 VPN 設備  │
│   ├ interface 0 ─┼── 通道 1 ──┼→ Peer 設備 1   │
│   └ interface 1 ─┼── 通道 2 ──┼→ Peer 設備 2   │
└─────────────────┘            └──────────────┘
        │
   Cloud Router（BGP 動態學習路由）

要拿到 99.99% SLA 的條件：
  ✅ 兩條通道分別接到「兩台不同的地端設備」
  ❌ 兩條通道接到同一台設備 → 只有 99.9%
動手實作

實作：建立 HA VPN（示意流程）

  1. 建立 HA VPN 閘道（會自動配發兩個外部 IP）：
    bash
    gcloud compute vpn-gateways create gcp-ha-vpn \
  --network=prod-vpc --region=asia-east1

# 記下這兩個 IP，要給網路工程師設定地端設備
gcloud compute vpn-gateways describe gcp-ha-vpn --region=asia-east1
  2. 建立 Cloud Router（負責 BGP）：
    bash
    gcloud compute routers create vpn-router \
  --network=prod-vpc --region=asia-east1 \
  --asn=65001 \
  --advertisement-mode=CUSTOM \
  --set-advertisement-ranges=10.10.0.0/20,10.20.0.0/20
  3. 註冊地端的 VPN 設備：
    bash
    gcloud compute external-vpn-gateways create onprem-gw \
  --interfaces=0=203.0.113.10,1=203.0.113.11
  4. 建立兩條 VPN 通道：
    bash
    for i in 0 1; do
gcloud compute vpn-tunnels create tunnel-$i \
  --peer-external-gateway=onprem-gw \
  --peer-external-gateway-interface=$i \
  --region=asia-east1 \
  --ike-version=2 \
  --shared-secret="請用強隨機字串，並存進 Secret Manager" \
  --router=vpn-router \
  --vpn-gateway=gcp-ha-vpn \
  --interface=$i
done
  5. 建立 BGP 工作階段：
    bash
    for i in 0 1; do
gcloud compute routers add-interface vpn-router \
  --interface-name=if-tunnel-$i --vpn-tunnel=tunnel-$i \
  --ip-address=169.254.$i.1 --mask-length=30 --region=asia-east1

gcloud compute routers add-bgp-peer vpn-router \
  --peer-name=bgp-peer-$i --interface=if-tunnel-$i \
  --peer-ip-address=169.254.$i.2 --peer-asn=65002 \
  --region=asia-east1
done
  6. 驗證通道與 BGP 狀態：
    bash
    gcloud compute vpn-tunnels list --format="table(name, status, detailedStatus)"
gcloud compute routers get-status vpn-router --region=asia-east1
小心踩雷
網段重疊是混合雲最痛的問題，沒有優雅的解法。
如果地端用 10.0.0.0/16，GCP 也用 10.0.0.0/16，BGP 會拒絕交換路由，連線建不起來。
解法只有：① 重新規劃其中一邊的網段（要停機、要改所有設定）；或 ② 在中間加 NAT 做位址轉換（複雜、難維護、除錯地獄）。
這就是為什麼第 12 課要你在動工前先做 IP 規劃——這件事沒有事後補救的空間。

三、私有服務存取（Private Service Access）

這是另一個常見需求：你的 VM 要連 Cloud SQL，但不想走公網。

bash
# 配置一段 IP 給 Google 託管服務使用
gcloud compute addresses create google-managed-services \
  --global --purpose=VPC_PEERING --prefix-length=16 \
  --network=prod-vpc

# 建立 VPC Peering 連線
gcloud services vpc-peerings connect \
  --service=servicenetworking.googleapis.com \
  --ranges=google-managed-services \
  --network=prod-vpc

# 之後建立 Cloud SQL 時指定私有 IP
gcloud sql instances create prod-db \
  --network=prod-vpc --no-assign-ip \
  --database-version=POSTGRES_15 --tier=db-custom-2-8192 \
  --region=asia-east1
補充
三種「私有連線」名詞很容易混淆，一次釐清：

Private Google Access：讓沒有外部 IP 的 VM 能存取 Google 的公開 API（GCS、BigQuery）。子網路層級開關。

Private Service Access：讓你的 VPC 能用內部 IP 連到 Google 託管的服務實例（Cloud SQL、Memorystore）。用 VPC Peering 實作。

Private Service Connect：更新的機制，讓你用自己 VPC 內的 IP連到 Google API 或第三方服務，不需要 Peering，且能跨專案、跨組織發布服務。新專案優先考慮這個。

四、遷移期間的網路策略

實務上的混合雲不是永久狀態，而是遷移過程。建議的推進順序：

  1. 第 1 階段：建立連線。HA VPN 打通，確認雙向 ping 得到、DNS 互相解析得到。
  2. 第 2 階段：搬無狀態的東西。前端、API 伺服器先上雲，資料庫留地端。此時流量會頻繁跨越 VPN——要監控頻寬與延遲，這通常是第一個瓶頸。
  3. 第 3 階段：搬資料。用 Database Migration Service 做持續複製，最後切換時只需要短暫停機。
  4. 第 4 階段：斷開。確認地端沒有任何東西被依賴後，才拆 VPN。這一步常常拖好幾年，因為總有某個沒人記得的系統還在用。
實務提醒
遷移期最大的成本陷阱：跨 VPN 的資料庫查詢。
應用程式在雲端、資料庫在地端，每一次查詢都要跨 VPN 來回。原本 1ms 的查詢變成 30ms，一個頁面如果有 50 次查詢，回應時間從 50ms 變成 1.5 秒。
所以「應用先搬、資料庫後搬」雖然風險低，但要有心理準備效能會暫時變差。反過來「資料庫先搬」則風險高但效能好。這是真實的取捨，沒有標準答案。

  • 理解網段重疊沒有好的事後解法
  • 能區分 Private Google Access / Private Service Access / Private Service Connect

自我檢測

公司要求「雲端與地端連線不得中斷超過 5 分鐘/月」。用 HA VPN 夠嗎？
5 分鐘/月 ≈ 99.99% 可用性。HA VPN 的 SLA 正好是 99.99%（約 4.3 分鐘/月），理論上剛好卡在邊緣。

但要滿足這個 SLA 有嚴格條件：
① 兩條通道必須接到兩台不同的地端設備；
② 地端設備本身也要有 99.99% 以上的可用性（SLA 是取最弱環節）；
③ 網際網路路徑的品質不在 Google SLA 保障範圍。

務實建議：如果這是硬性合約要求，用 99.99% SLA 的 Interconnect（需要兩個不同 metro 的連接埠），或 Interconnect + VPN 備援的組合。純 VPN 在合約層面說得過去，但實務上公網品質不可控。
地端和 GCP 都用了 172.16.0.0/12，現在要接 VPN。有什麼選項？
沒有輕鬆的解法，三個選項依痛苦程度排序：

① 重新規劃 GCP 端網段（推薦）——GCP 端通常比地端年輕、機器少、自動化程度高。建新的 VPC 用不衝突的網段，逐步搬遷。痛苦但乾淨。
② 只讓不重疊的子網段互通——如果實際使用的部分不重疊（例如地端用 172.16.x、GCP 用 172.20.x），可以只通告這些具體網段而非整個 /12。這是最快的權宜之計。
③ 加 NAT 轉換——在 VPN 兩端做位址轉換。技術上可行，但會讓所有的日誌、追蹤、防火牆規則變得極難理解，長期維護成本很高。

我的判斷：選①或②。選③的團隊通常在兩年後會後悔。
遷移到一半，應用在 GCP、資料庫在地端，使用者抱怨網站很慢。有哪些做法？
按「效果 / 代價」排序：
① 加快取層（Memorystore Redis 放在 GCP）——把讀取密集的查詢擋在雲端，命中率 80% 的話跨 VPN 查詢就減少 80%。最快見效，改動小。
② 減少查詢次數——檢查有沒有 N+1 查詢問題，合併查詢、加 eager loading。經常能發現一個頁面打了 200 次 DB 的驚人事實。
③ 把唯讀副本放到 GCP——地端主庫、GCP 唯讀副本，讀取走本地。寫入仍跨 VPN 但通常量少。
④ 升級到 Interconnect——降低延遲，但成本高且要數週。
⑤ 加速資料庫遷移——治本，但風險最高。

正確順序是 ①②（幾天內完成）→ ③（幾週）→ ⑤（幾個月）。④ 只在前面都做完還不夠時才考慮。
