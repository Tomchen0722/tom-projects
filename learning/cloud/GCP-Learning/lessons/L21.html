LESSON 21

BigQuery 入門：用 SQL 查 TB 級資料

BigQuery 是 GCP 最強的服務，沒有之一。它讓你不用管任何伺服器，就能在幾秒內掃過幾 TB 的資料。這一課從零開始查一個真實的公開資料集。

操作 45 分免費額度內實作

一、BigQuery 跟一般資料庫的根本差異

一般資料庫（OLTP）BigQuery（OLAP）
儲存方式列式——一整筆資料存在一起欄式——同一欄的所有值存在一起
優勢操作查詢單筆、頻繁寫入更新掃描大量資料做聚合
典型查詢SELECT * WHERE id=123SELECT country, SUM(sales) GROUP BY country
延遲毫秒秒級（即使掃 1TB）
擴充要自己分片自動，數千台機器並行
計費機器規格 × 時間掃描的資料量
生活比喻
欄式儲存為什麼快？

想像一份 100 萬人的問卷，每人回答 50 題。

列式＝每個人一張紙，100 萬張紙疊著。你想統計「第 7 題的平均分數」，必須翻過每一張紙，讀完 50 題才能找到第 7 題。

欄式＝每一題一疊紙，共 50 疊。統計第 7 題？只拿第 7 疊來看，其他 49 疊完全不碰。

這就是為什麼 BigQuery 按「掃描的資料量」計費——你只查兩個欄位，它就只讀那兩個欄位。也是為什麼 SELECT * 在 BigQuery 上是很貴的行為。

二、實作：查詢公開資料集

動手實作

實作：分析真實資料

  1. 在 Cloud Shell 執行第一個查詢（BigQuery 有大量免費的公開資料集）：
    bash
    bq query --use_legacy_sql=false '
SELECT
  name,
  gender,
  SUM(number) AS total
FROM `bigquery-public-data.usa_names.usa_1910_2013`
WHERE state = "TX"
GROUP BY name, gender
ORDER BY total DESC
LIMIT 10
'
  2. 先估算成本再執行（--dry_run 不會真的跑，只告訴你會掃多少資料）：
    bash
    bq query --use_legacy_sql=false --dry_run '
SELECT * FROM `bigquery-public-data.wikipedia.pageviews_2023`
WHERE DATE(datehour) = "2023-06-15"
'
# 輸出：Query successfully validated. ... will process 1234567890 bytes
  3. 建立自己的資料集與表：
    bash
    bq mk --dataset --location=asia-east1 --description="學習用" lab_data

bq mk --table lab_data.sales \
  order_id:STRING,customer:STRING,product:STRING,amount:NUMERIC,order_date:DATE,region:STRING
  4. 載入資料：
    bash
    cat > sales.csv <<'EOF'
order_id,customer,product,amount,order_date,region
A001,王小明,筆電,35000,2026-01-15,北區
A002,李小華,滑鼠,890,2026-01-16,中區
A003,王小明,鍵盤,2400,2026-02-03,北區
A004,張大同,螢幕,8900,2026-02-14,南區
A005,李小華,筆電,42000,2026-03-01,中區
EOF

bq load --source_format=CSV --skip_leading_rows=1 \
  lab_data.sales sales.csv
  5. 查詢自己的資料：
    bash
    bq query --use_legacy_sql=false '
SELECT
  region,
  COUNT(*) AS order_count,
  SUM(amount) AS revenue,
  ROUND(AVG(amount), 0) AS avg_order
FROM `lab_data.sales`
GROUP BY region
ORDER BY revenue DESC
'
  6. 從 Cloud Storage 大量載入（實務上的常見做法）：
    bash
    bq load --source_format=PARQUET \
  --autodetect \
  lab_data.events \
  gs://my-bucket/events/*.parquet

BigQuery 最恐怖的故事都是同一種：有人在幾 PB 的表上執行 SELECT *。
掃描 1PB = 約 $6,250，一個查詢。

三道必設的防線：
① 設定查詢量上限：bq query --maximum_bytes_billed=10000000000（10GB），超過就拒絕執行。
② 在專案層級設定每日配額：Console → IAM → 配額 → BigQuery → Query usage per day。
③ 養成 --dry_run 的習慣，跑大查詢前先估算。

四、省錢的四個核心技巧

  1. 絕對不要用 SELECT *。只選你要的欄位。一個 100 欄的表，只選 3 欄就是省 97% 的費用。
  2. 用分區（Partitioning）。按日期分區後，WHERE date = '2026-07-01' 只掃一天的資料，而不是整張表。這通常是最大的一筆節省。
  3. 用叢集（Clustering）。在分區內再依常用的篩選欄位排序，進一步減少掃描量。
  4. 用具體化檢視表（Materialized View）。把常用的聚合結果預先算好並自動增量更新。
分區與叢集
-- 建立分區 + 叢集的表（正式環境的標準做法）
CREATE TABLE lab_data.events_optimized
PARTITION BY DATE(event_time)
CLUSTER BY user_id, event_type
OPTIONS(
  partition_expiration_days = 90,        -- 90 天後自動刪除舊分區
  require_partition_filter = true        -- 強制查詢必須帶分區條件！
)
AS SELECT * FROM lab_data.events;

-- 有了 require_partition_filter，這個查詢會被「拒絕執行」
SELECT * FROM lab_data.events_optimized;   -- ❌ 錯誤

-- 必須這樣寫
SELECT user_id, event_type
FROM lab_data.events_optimized
WHERE DATE(event_time) BETWEEN "2026-07-01" AND "2026-07-07"
  AND event_type = "purchase";              -- ✅ 只掃 7 天 × 特定類型
實務提醒
require_partition_filter = true 是我最推薦的一個設定。它強制所有查詢都必須帶分區條件，從根本上防止「不小心全表掃描」。
對正式環境的大表，這一個設定能省下的錢比其他所有優化加起來還多。

-- 用 SQL 訓練一個預測模型（BigQuery ML）
CREATE OR REPLACE MODEL lab_data.churn_model
OPTIONS(model_type='LOGISTIC_REG', input_label_cols=['churned']) AS
SELECT days_since_last_order, total_orders, avg_order_value, churned
FROM lab_data.customer_features;

-- 預測
SELECT * FROM ML.PREDICT(MODEL lab_data.churn_model,
  (SELECT * FROM lab_data.new_customers));

-- Time Travel：救回一小時前誤刪的資料
CREATE TABLE lab_data.sales_restored AS
SELECT * FROM lab_data.sales
FOR SYSTEM_TIME AS OF TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 1 HOUR);

自我檢測

同事寫了一個查詢，dry run 顯示要掃 800GB。表有 200 個欄位、5 年資料。怎麼優化？
三步驟，效果由大到小：
① 加分區篩選——如果只需要最近 30 天，掃描量從 5 年降到 30 天，約降 98%。這一步通常最有效。
② 只選需要的欄位——200 欄選 5 欄，再降 97.5%。
③ 加叢集篩選——如果表有 CLUSTER BY user_id，加上 WHERE user_id = X 可以再大幅減少。

三者相乘後，800GB 可能降到 200MB 以下。

如果表沒有分區，那第一件事是重建成分區表——這是一次性成本，但之後每個查詢都受益。
財務問「上個月 BigQuery 花了 $8000，為什麼？」你怎麼查？
查 INFORMATION_SCHEMA.JOBS，這是 BigQuery 的稽核視圖：
bash
SELECT
  user_email,
  COUNT(*) AS query_count,
  SUM(total_bytes_billed)/POW(1024,4) AS tb_billed,
  ROUND(SUM(total_bytes_billed)/POW(1024,4) * 6.25, 2) AS estimated_usd
FROM `region-asia-east1`.INFORMATION_SCHEMA.JOBS
WHERE creation_time >= TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 30 DAY)
  AND job_type = "QUERY"
GROUP BY user_email
ORDER BY tb_billed DESC
LIMIT 20
通常會發現：80% 的費用來自 3～5 個排程查詢或某個 BI 工具的自動重新整理。

後續處置：① 對那幾個查詢做分區優化；② 對 BI 工具啟用 BI Engine 或改查具體化檢視表；③ 評估是否該切換到容量定價（Editions）。
團隊想把 BigQuery 當成應用程式的主資料庫，理由是「反正都能存」。你的評估？
不行，這是嚴重的架構錯誤。四個具體原因：
① 延遲——即使是最簡單的 SELECT ... WHERE id=X，BigQuery 也要 0.5～2 秒（它要啟動分散式查詢引擎）。使用者面向的 API 無法接受。
② 沒有交易——不支援跨表的 ACID 交易，無法保證扣款與入帳的一致性。
③ DML 有嚴格限制——UPDATE / DELETE 有並行數限制，且每次操作成本高。高頻更新會直接撞牆。
④ 成本模型不符——按掃描量計費，對「每秒數千次的小查詢」是最糟的計費方式。

正確架構：Cloud SQL / Firestore（交易）→ Datastream 或 Pub/Sub（同步）→ BigQuery（分析）。

核心觀念：OLTP 與 OLAP 是兩種不同的工作負載，需要兩種不同的系統。試圖用一個系統做兩件事，結果是兩件事都做不好。這是資料架構最基本的原則。
