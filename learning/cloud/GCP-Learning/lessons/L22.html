LESSON 22

資料庫選型：一張決策表定生死

這一課不教新服務，而是把前面五課的知識整合成一套可以直接在會議上用的決策框架。附上真實情境的完整推演。

閱讀 18 分總整理

一、五個問題定選型

五問決策流程
Q1. 這是交易系統（OLTP）還是分析系統（OLAP）？
      交易 → 往下走
      分析 → BigQuery，結束

Q2. 資料有沒有複雜的關聯與查詢需求？
      有（需要 JOIN、交易、複雜 WHERE）→ 往 Q3
      沒有（單純的 key-value 或文件存取）→ 往 Q5

Q3. 單一資料庫撐得住嗎？（估算：資料量 < 10TB、寫入 QPS < 5000）
      撐得住 → Cloud SQL           ← 這裡是 80% 的答案
      快撐不住 → AlloyDB
      完全撐不住 → 往 Q4

Q4. 需要跨地區同時寫入且強一致嗎？
      需要 → Spanner
      不需要 → Cloud SQL 分片 或 AlloyDB

Q5. 存取模式是什麼？
      需要即時同步 / 離線支援（行動 App）→ Firestore
      極高吞吐、單純 key 查詢、TB~PB 級  → Bigtable

三、四個真實情境的完整推演

情境 1：新創的社群 App（月活 10 萬）

需求：使用者資料、貼文、留言、按讚、即時通知。

推演：資料量小（估計 < 100GB）、有關聯（使用者 ↔ 貼文 ↔ 留言）、需要交易（按讚計數）。Q1 交易 → Q2 有關聯 → Q3 撐得住。

答案：Cloud SQL (PostgreSQL) 為主 + Memorystore 快取熱門貼文 + Firestore 處理即時通知。

為什麼不全用 Firestore：「查某使用者的追蹤者發的貼文，按時間排序」這種查詢在 Firestore 上要靠反正規化與扇出寫入（fan-out），複雜度高很多。而 10 萬月活的量體，Cloud SQL 一台 4 核機器綽綽有餘。

情境 2：製造業設備監控（500 台機台，每秒 10 筆資料）

需求：即時儀表板（近 1 小時）、歷史趨勢分析（3 年）、異常告警。

推演：每天 4.32 億筆，3 年約 4700 億筆。這個量體排除所有關聯式選項。查詢模式是「某機台 + 某時間範圍」——非常適合 row key 範圍掃描。

答案：Pub/Sub（接收）→ Dataflow（處理與告警）→ Bigtable（近 30 天熱資料，即時儀表板）+ BigQuery（全歷史，趨勢分析）。

關鍵設計：Bigtable row key 用 機台ID#反轉時間戳，並設定 GC 政策自動刪除 30 天前的資料；Dataflow 同時寫入 BigQuery 做長期保存。

情境 3：跨國電商（美、歐、亞三地）

需求：庫存必須全球一致（不能超賣）、訂單、商品目錄、使用者行為分析。

推演：這是混合需求，不同資料有不同特性——不要試圖用一個資料庫解決全部。

資料選擇理由
庫存Spanner唯一需要全球強一致的部分。超賣是不能接受的
訂單Spanner 或區域 Cloud SQL訂單通常有地域性，可依下單地區分開
商品目錄Cloud SQL + Memorystore + CDN讀多寫少，快取效果極好
購物車Memorystore（Redis）短生命週期，可容忍少量遺失
行為分析BigQuery事後分析，不需即時

情境 4：政府機關的檔案管理系統

需求：文件必須保存 30 年、不可竄改、有稽核軌跡、內部使用者約 500 人。

答案：Cloud SQL（中繼資料與權限）+ Cloud Storage Archive + Bucket Lock（檔案本體）+ Cloud Audit Logs（稽核）。

關鍵：檔案本體不放資料庫（成本高且不必要），只在資料庫存指向 GCS 的路徑與中繼資料。Bucket Lock 保留政策確保連管理員都無法刪除。整體加上 VPC Service Controls 建立資料邊界。

四、常見的選型錯誤

錯誤後果正解
為了「未來可能很大」直接上 Spanner成本高 10 倍、團隊學習成本高、生態工具少Cloud SQL 起步，但主鍵用 UUID 保留遷移彈性
用 BigQuery 當交易資料庫延遲高、無交易、DML 受限OLTP 與 OLAP 分離
用 Redis 存不能遺失的資料故障時資料遺失持久化資料放 Cloud SQL，Redis 只做快取
所有資料塞同一個資料庫分析查詢拖垮交易效能分析流量導到唯讀副本或 BigQuery
用 Firestore 做複雜報表查詢能力不足，反正規化到失控報表資料同步到 BigQuery
一開始不做分區就建大表BigQuery 費用失控建表當下就設好 PARTITION BY 與 require_partition_filter

自我檢測

面試官問：「什麼時候你會選 Bigtable 而不是 BigQuery？」
關鍵在延遲需求與查詢模式，而非資料量：

選 Bigtable：
• 需要個位數毫秒的延遲（例如即時儀表板、線上推薦、廣告投放決策）
• 查詢模式固定且單純（單筆查詢或 row key 範圍掃描）
• 極高的寫入吞吐（每秒數十萬筆以上）

選 BigQuery：
• 可以接受秒級延遲
• 需要任意的 SQL 聚合與 JOIN
• 查詢模式不固定（分析師會臨時想到各種問題）

加分回答：實務上兩者常常一起用——Bigtable 服務即時查詢，同時把資料匯出到 BigQuery 做分析。這叫 Lambda 架構的簡化版。
既有系統用 MySQL，資料 3TB，查詢越來越慢。老闆問「要不要換 Spanner」？
先診斷，不要先換技術。「慢」有很多種原因，換資料庫只解決其中一種。

診斷順序：
① 是哪些查詢慢？——開慢查詢日誌。通常 80% 的問題來自少數幾個查詢。
② 是缺索引嗎？——EXPLAIN 看執行計畫。這是最常見的原因，而且改起來只要幾分鐘。
③ 是分析查詢拖垮交易嗎？——如果是報表查詢佔用資源，把它們導到唯讀副本或同步到 BigQuery。
④ 是硬體不夠嗎？——升級規格或改用 AlloyDB（PostgreSQL）。
⑤ 真的是單機瓶頸嗎？——只有在寫入 QPS 持續打滿、且無法用讀寫分離解決時，才需要考慮分散式資料庫。

3TB 對現代硬體其實不大，一台 32 核 128GB 的 Cloud SQL 通常能輕鬆處理。換到 Spanner 要重寫 schema、重新設計主鍵、成本增加 10 倍——這個代價要有明確的技術理由，不能因為「慢」這種模糊描述就做決定。
你被要求設計一個「什麼都能存」的統一資料平台。你的回應？
這個需求本身需要被挑戰。「什麼都能存」通常反映的是治理需求（不想管太多系統），而不是技術需求。

我會這樣重構問題：真正的目標可能是「降低維運複雜度」和「讓資料容易被找到與使用」。這兩件事不需要靠單一資料庫達成。

務實的架構：
• 統一的分析層：所有系統的資料都同步到 BigQuery，分析師只需要學一套 SQL。這解決了「資料容易被使用」。
• 各自最適的交易層：每個系統用最適合自己的資料庫。
• 統一的治理層：Dataplex 做資料目錄與血緣追蹤，Data Catalog 讓人找得到資料。這解決了「容易被找到」。
• 統一的 IaC 與監控：用 Terraform 管理所有資料庫，用同一套 Cloud Monitoring 儀表板。這解決了「維運複雜度」。

核心觀念：統一「介面」而不是統一「實作」。強求單一資料庫的結果，往往是所有場景都只有 60 分。
