LESSON 42

Dataproc：把 Spark 與 Hadoop 搬上雲

企業上雲的第一站往往不是重寫，而是先讓既有的幾百支 Spark 程式跑起來。這一課教你怎麼搬，以及怎麼不要把地端的燒錢習慣一起搬過來。

操作 50 分實作

一、為什麼企業還在用 Spark 和 Hadoop

如果你今天從零開始做資料處理，在 GCP 上該用 Dataflow 或 BigQuery，不太會選 Spark。但實務上，Dataproc 是很多企業上雲的第一站——原因很現實：他們已經有幾百支 Spark 程式了。

生活比喻
公司搬新辦公室，舊辦公室有 200 台設備。

Dataflow 的路線：全部換成新規格的設備。長遠來說更好，但要重買、重學、重測。
Dataproc 的路線：舊設備直接搬過去插電就能用，先讓業務不中斷，之後再慢慢汰換。

Dataproc 就是那個「插電就能用」的選項——你原本的 Spark 程式碼幾乎不用改。
情境選擇理由
地端已有大量 Spark / Hive 程式要上雲Dataproc相容既有程式碼，遷移成本最低
全新的串流管線Dataflow（第 29 課）全託管、自動擴充、不用管叢集
資料已在 BigQuery，只是要做 SQL 轉換BigQuery不需要任何叢集，最省事也最便宜
團隊只會 SQL，不寫 Java/Scala/PythonBigQuery不要為了用而用
要跑 Spark ML 或特定開源生態工具Dataproc能裝任意元件
選型的一句話
「有沒有既有的 Spark/Hadoop 資產？」——有就 Dataproc，沒有就先看 BigQuery 夠不夠、再看 Dataflow。
不要因為「聽起來比較厲害」而選 Dataproc，它是三者中維運負擔最重的。

二、Dataproc 的兩種形態

Dataproc 兩種用法
① 叢集模式（Dataproc on Compute Engine）
   你建一個叢集 → 提交作業 → 用完刪掉
   ├─ Master 節點：管理與排程
   ├─ Worker 節點：實際運算（可用 Spot VM 省錢）
   └─ 可安裝 Jupyter、Zeppelin、Hive、HBase 等元件
   適合：需要自訂元件、長時間互動分析

② Serverless（Dataproc Serverless for Spark）
   直接提交 Spark 作業，Google 幫你配資源
   ├─ 不用建叢集、不用調參數
   ├─ 按作業實際用量計費
   └─ 作業結束資源自動回收
   適合：批次作業、不想管基礎設施 ← 新專案優先考慮這個
觀念修正：不要養一個「長期存在」的叢集
從地端搬上來的團隊最常見的錯誤，是把地端的思維也搬過來——建一個 24 小時開著的叢集。

地端的機器買了就在那裡，開著不開著都一樣。雲端不是：叢集開著就是在計費。

雲端的正確作法是「用完即刪」（ephemeral cluster）：每次要跑作業時建叢集，跑完立刻刪。因為資料本來就存在 Cloud Storage，不在叢集裡，刪掉不會掉資料。

三、關鍵觀念：把 HDFS 換成 Cloud Storage

這是地端 Hadoop 搬上雲最重要的一個改變，也是「用完即刪」能成立的前提。

存算分離
地端 Hadoop（存算綁在一起）
   資料存在 HDFS = 存在 worker 節點的磁碟上
   → 關掉叢集 = 資料不見
   → 所以叢集不能關
   → 所以要一直付錢

GCP（存算分離）
   資料存在 Cloud Storage（gs://）
   運算叢集只是「臨時借來的算力」
   → 關掉叢集，資料還在 GCS
   → 所以可以用完就刪
   → 只付實際運算的時間

程式碼的改動:  hdfs:///data/orders  →  gs://my-bucket/data/orders
              （就這樣，其他幾乎不用動）
為什麼可以這樣做
Dataproc 內建 Cloud Storage 連接器，讓 Spark 把 gs:// 當成一般檔案系統存取。
而且 GCS 的吞吐量對批次作業來說綽綽有餘——瓶頸通常在運算而不是讀取。

四、實作：建立叢集並跑 PySpark

動手實作

實作一：用完即刪的叢集

  1. 建立一個帶自動刪除的叢集（重點在最後兩個參數）：
    bash
    gcloud services enable dataproc.googleapis.com

gcloud dataproc clusters create demo-spark \
  --region=asia-east1 \
  --single-node \
  --master-machine-type=e2-standard-2 \
  --image-version=2.2-debian12 \
  --max-idle=30m \
  --max-age=2h

    --max-idle=30m：閒置 30 分鐘自動刪除。
    --max-age=2h：不管有沒有在用，2 小時後一定刪除。
    這兩個參數是防止忘記關機的保險絲，練習時務必加上。

  2. 準備一支 PySpark 程式，存成 wordcount.py：
    wordcount.py
    import sys
from pyspark.sql import SparkSession
from pyspark.sql import functions as F

spark = SparkSession.builder.appName("wordcount").getOrCreate()

src, dst = sys.argv[1], sys.argv[2]

df = spark.read.text(src)

result = (
    df.select(F.explode(F.split(F.col("value"), r"\s+")).alias("word"))
      .filter(F.col("word") != "")
      .groupBy("word")
      .count()
      .orderBy(F.col("count").desc())
)

result.write.mode("overwrite").parquet(dst)   # 寫成 Parquet,後續 BigQuery 好讀
spark.stop()
  3. 上傳程式與測試資料到 GCS，然後提交作業：
    bash
    BUCKET=gs://$(gcloud config get-value project)-dataproc-demo
gsutil mb -l asia-east1 $BUCKET

gsutil cp wordcount.py $BUCKET/code/
gsutil cp /usr/share/dict/words $BUCKET/input/words.txt 2>/dev/null \
  || echo -e "hello world\nhello gcp\ngcp rocks" | gsutil cp - $BUCKET/input/words.txt

gcloud dataproc jobs submit pyspark $BUCKET/code/wordcount.py \
  --cluster=demo-spark \
  --region=asia-east1 \
  -- $BUCKET/input/ $BUCKET/output/
  4. 看結果，然後手動刪除叢集（不要等 max-age）：
    bash
    gsutil ls $BUCKET/output/

gcloud dataproc clusters delete demo-spark --region=asia-east1 --quiet
動手實作

實作二：Serverless 版本（不用建叢集）

同一支程式，改用 Serverless 提交——沒有叢集要建、也沒有叢集要刪：

bash
gcloud dataproc batches submit pyspark $BUCKET/code/wordcount.py \
  --region=asia-east1 \
  --version=2.2 \
  -- $BUCKET/input/ $BUCKET/output-serverless/

# 看執行狀態
gcloud dataproc batches list --region=asia-east1
比較一下你剛剛做的兩件事
叢集模式：建叢集（2~3 分鐘）→ 提交 → 刪叢集。要管生命週期。
Serverless：直接提交。啟動稍慢，但完全不用管資源。

新專案的批次 Spark 作業，先試 Serverless。只有在需要自訂元件（Jupyter、HBase、特定版本套件）或要做長時間互動分析時，才回頭用叢集模式。

五、成本優化：三個手段

手段怎麼做省多少
Spot VM 當 worker--num-secondary-workers 搭配 Spot最高約 60~91%，依機型與時段浮動
用完即刪--max-idle / --max-age，或改用 Serverless省下所有閒置時間
自動擴充設定 autoscaling policy尖峰才加機器
Spot VM 只能給 secondary worker
Spot 會被隨時回收。Master 和 primary worker 不能用 Spot——master 被收走整個叢集就掛了。
secondary worker 只做運算、不存 HDFS 資料，被收走 Spark 會把那部分工作重新分配，所以安全。

這個「哪些節點可以用便宜但會被回收的資源」的判斷邏輯，和 AWS EMR 的 Task 節點用 Spot 是同一個道理。

六、企業實務：一條典型的資料管線

Dataproc 在企業管線中的位置
Cloud Composer（第 41 課）負責排程與編排
      │
      │  每天 02:00 觸發
      ↓
 ① Dataproc Serverless 作業
      讀 gs://raw/（前一天的原始檔）
      清洗、去重、轉成 Parquet
      寫 gs://curated/
      ↓
 ② BigQuery 外部表或載入作業
      把 curated 的 Parquet 載進 BigQuery
      ↓
 ③ BigQuery SQL 建立彙總表（第 30 課）
      ↓
 ④ Looker Studio 儀表板

重點:Composer 只負責「叫」,實際運算在 Dataproc 和 BigQuery
     資料一路都在 GCS / BigQuery,不在叢集裡
遷移的務實順序
地端 Hadoop 上雲，實務上很少一步到位。常見的三階段：

階段一：程式碼不動，把 hdfs:// 改成 gs://，用 Dataproc 叢集跑。先讓它會動。
階段二：改成用完即刪 + Spot，把成本壓下來。
階段三：逐支評估——能用 BigQuery SQL 表達的就改寫成 SQL，剩下真的需要 Spark 的才留在 Dataproc。

很多團隊做到階段三會發現，原本七成的 Spark 作業其實用 BigQuery 就能做，而且更快更便宜。

七、本課檢核

  • 講得出 Dataproc、Dataflow、BigQuery 三者的選擇時機
  • 理解「存算分離」為什麼讓叢集可以用完即刪
  • 知道 --max-idle 與 --max-age 是防呆保險絲
  • 能用叢集模式與 Serverless 兩種方式提交 PySpark 作業
  • 知道 Spot 只能用在 secondary worker，以及為什麼
  • 做完實作已刪除叢集與測試 bucket

自我檢測

公司從地端搬了一套 Hadoop 上來，建了一個 20 節點叢集全天候開著。月帳單很難看。你會怎麼改？
他們把地端的思維整套搬上來了。地端機器買了就在那裡，開著不花額外的錢；雲端開著就是在計費。

第一步：確認資料在哪
如果資料還存在 HDFS（叢集磁碟裡），那叢集確實不能關。所以真正的第一步是把資料搬到 Cloud Storage，程式碼把 hdfs:// 改成 gs://。這一步做完，叢集才變成「可拋棄」的。

第二步：改成用完即刪
用 Composer 或 Cloud Scheduler 在作業開始前建叢集、結束後刪掉。加上 --max-idle 當保險。

第三步：secondary worker 改用 Spot
批次作業被中斷可以重試，很適合 Spot。

第四步：盤點哪些能改 BigQuery
純 SQL 式的彙總作業改寫成 BigQuery，連 Spark 都不用跑。

前三步通常就能把費用降到原本的兩三成，而且不太需要改業務邏輯。
同事說「我們要即時處理 IoT 資料，用 Dataproc 跑 Spark Streaming 吧」。你同意嗎？
技術上可行，但在 GCP 上通常不是最好的選擇。

Spark Streaming 跑在 Dataproc 上，代表你要養一個 24 小時不關的叢集——「用完即刪」的優勢完全用不到，還要自己管故障轉移、擴充、狀態儲存。

GCP 上串流的標準組合是 Pub/Sub + Dataflow（第 29 課）：
• Dataflow 全託管，自動擴充
• 內建視窗、遲到資料處理、精確一次語意
• 不用管叢集

什麼情況才留在 Spark Streaming？
只有一個好理由：已經有大量寫好的 Spark Streaming 程式碼，短期內沒有人力改寫。那就先搬上 Dataproc 讓它動，列進技術債，之後再遷移。

「新東西用 Dataflow，舊東西先用 Dataproc 接住」——這是務實的分界線。
你的 Dataproc 作業設定了 secondary worker 用 Spot，結果作業常常跑很久甚至失敗。怎麼判斷與處理？
先確認是不是 Spot 回收造成的。看作業日誌有沒有大量 executor lost / preempted 的訊息。

如果是，三個處理方向：

① 調整 Spot 比例——不要 100% 都用 Spot。常見配置是 primary worker（穩定）搭配一部分 secondary Spot，讓作業即使被回收一批也還有基本算力撐著。

② 檢查作業的容錯設計——Spark 本來就能重算遺失的 partition，但如果你的作業有大量 shuffle，被回收的代價會很高（要重算的東西多）。可以考慮增加 partition 數讓每塊小一點，或啟用外部 shuffle 服務。

③ 評估要不要放棄 Spot——如果作業有明確的完成時限（例如早上 8 點前要出報表），穩定性比省錢重要。Spot 適合「跑久一點沒關係」的作業。

另外要檢查的非 Spot 因素：資料傾斜（某個 key 的資料量特別大）、小檔案太多、GCS 讀取沒有平行化。這些問題會被誤判成「Spot 的錯」。
