LESSON 10

無伺服器三兄弟：Cloud Run、Functions、App Engine

虛擬機讓你管機器，無伺服器讓你只管程式碼。這一課釐清三個服務的差別，並給你一條明確的選擇準則——結論是：多數情況用 Cloud Run。

閱讀 25 分架構決策

一、無伺服器不是沒有伺服器

「Serverless」是行銷術語，實際意思是：伺服器還在，但不是你管的，而且沒有請求時你不用付錢。

虛擬機（Compute Engine）無伺服器（Cloud Run 等）
機器管理你負責 OS 更新、修補、監控Google 全包
擴充你設定 MIG 與自動擴充規則自動，從 0 到數千個實例
閒置成本機器開著就要錢可以縮到 0，完全不收費
啟動速度1～3 分鐘毫秒～數秒
執行時間限制無限制有上限（Cloud Run 最長 60 分鐘）
適合有狀態、長時間執行、需要控制 OS無狀態、事件驅動、流量起伏大

二、三兄弟的差別

Cloud RunCloud Functions
（現為 Cloud Run functions）		App Engine
部署單位容器映像單一函式應用程式原始碼
語言限制任何語言（只要能包成容器）支援的執行環境（Node/Python/Go/Java/.NET/Ruby/PHP）支援的執行環境
最長執行60 分鐘9 分鐘（第 2 代 60 分鐘）標準版 10 分鐘 / 彈性版無限
縮到 0✅✅標準版 ✅ / 彈性版 ❌
適合API、網站、微服務、批次工作事件觸發的小工具（檔案上傳後處理、訊息轉發）舊有 App Engine 專案
建議新專案的預設選擇膠水程式碼新專案不建議
補充
2024 年後 Cloud Functions 已整併進 Cloud Run，改名為「Cloud Run functions」。底層跑的是同一套系統。所以現在的決策簡化成：「要不要一個完整的容器？」要 → Cloud Run 服務；只要一段事件處理函式 → Cloud Run functions。App Engine 則進入維護模式，除非你有既有專案，否則不需要學。

三、Cloud Run 的關鍵運作模型

Cloud Run 生命週期

   有 → 直接處理（熱啟動，毫秒級）
   沒有 → 建立新實例（冷啟動，數百毫秒～數秒）

三個你必須理解的參數：

參數意思調整時機
--concurrency一個實例同時處理幾個請求（預設 80）CPU 密集型調低（如 8）；I/O 等待多的可調高
--min-instances保留幾個永遠不關的實例要消除冷啟動就設 1 以上，但會持續收費
--max-instances最多能擴到幾個成本護欄。務必設定，否則流量暴增時帳單會失控
小心踩雷
Cloud Run 的並行模型跟 AWS Lambda 完全不同，這是最大的認知落差。
Lambda 是「一個實例同時只處理一個請求」；Cloud Run 預設「一個實例同時處理 80 個請求」。
這代表：① 成本通常比 Lambda 低很多；② 但你的程式碼必須是執行緒安全的。如果你的程式用了全域可變狀態，在 Cloud Run 上會出現詭異的資料互串問題，在 Lambda 上卻正常。

四、冷啟動：唯一需要認真對待的缺點

實例從無到有需要時間，這段延遲叫冷啟動。影響程度依語言差很多：

執行環境典型冷啟動時間備註
Go / Rust（靜態編譯）50～200 ms幾乎無感
Node.js / Python300 ms～1.5 s看依賴套件多寡
Java (Spring Boot)3～10 s最痛。建議用 GraalVM native image 或 Quarkus
.NET1～3 s可用 ReadyToRun 改善
  • 縮小映像：用 multi-stage build 和 distroless 基底，映像從 800MB 降到 30MB，冷啟動可以快好幾倍。
  • 設定 min-instances=1：直接消除冷啟動，代價是每月固定約 5～15 美元。對正式環境的使用者面向服務，這錢值得花。
  • 啟用 Startup CPU Boost：啟動期間給更多 CPU，Java 應用可以快 50%。
  • 避免在啟動時做重活：不要在全域範圍載入大模型、連很多資料庫。改成第一次用到才載入（lazy loading）。

五、選擇準則（實務決策樹）

決策樹
你的工作負載是什麼？

├─ 需要控制作業系統 / 要裝特殊驅動 / 有 GPU 長期需求
│    → Compute Engine（VM）

實務提醒
一個誠實的建議：新專案先用 Cloud Run，等到真的碰到限制再搬。
Cloud Run 用標準容器，所以搬到 GKE 或任何地方都不難。反過來從 GKE 搬到 Cloud Run 也容易。
但如果一開始就上 GKE，你會花大量時間在維護叢集而不是寫功能——對小團隊來說這是最常見的過度工程。

六、成本比較（實際數字感）

假設一個 API：每月 200 萬次請求，每次處理 200ms，需要 1 vCPU / 512MB：

方案估算月費用
Cloud Run200萬 × 0.2秒 = 400,000 vCPU 秒

但流量成長要自己加機器
Compute Engine（2 台做高可用）×2約 $24
GKE AutopilotPod 資源 + 叢集管理費約 $80+

結論：小到中等規模，Cloud Run 幾乎總是最便宜，而且它免費附贈高可用與自動擴充。規模非常大且流量穩定時，VM + 承諾折扣才會反超。

自我檢測

一個 Python API 部署到 Cloud Run 後，偶爾回傳其他使用者的資料。程式在本機測試完全正常。原因？
幾乎確定是全域可變狀態（global mutable state）。
本機用單執行緒或每次請求獨立的開發伺服器測試，看不出問題；Cloud Run 預設一個實例同時處理 80 個請求，共用同一份記憶體。
典型錯誤寫法：
bash
# ❌ 危險：全域變數被所有並行請求共用
current_user = None

@app.route("/profile")
def profile():
    global current_user
    current_user = get_user_from_token()   # A 請求寫入
    return render(current_user)             # B 請求可能讀到 A 的資料
短期止血：設 --concurrency=1（但成本會暴增數十倍）。
正確解法：把狀態放進請求範圍（request context）或外部儲存，移除所有全域可變變數。
服務尖峰時段回應變慢，查看發現 Cloud Run 實例數卡在 100 不動。怎麼辦？
--max-instances 預設上限被打到了。但不要直接無腦調高，先確認兩件事：
① 下游能不能承受——如果後面是 Cloud SQL，1000 個實例同時連線會把資料庫連線數打爆。這種情況要先加 連線池（Cloud SQL Auth Proxy / PgBouncer）。
② 成本上限在哪——max-instances 就是你的成本天花板，調高前要算清楚最壞情況的帳單。
正確順序：先確認瓶頸在 Cloud Run 而非下游，再調高，同時調整 concurrency 讓每個實例吃更多請求。
主管說「我們要用 Kubernetes，因為那是業界標準」。你的專案是一個 3 人團隊的內部工具。你會怎麼回應？
先承認 K8s 的價值，再把決策拉回成本效益：

K8s 解決的是「多團隊共用資源、複雜的服務拓撲、需要細緻的排程控制」這類問題。3 人團隊的內部工具沒有這些問題，但會實實在在付出代價：叢集升級、節點維護、YAML 複雜度、至少 $80/月的固定成本、以及一個人份的學習曲線。

務實的折衷：用 Cloud Run，但把應用容器化並用 Terraform 管理。這樣保留了所有可攜性——真的需要 K8s 那天，同一個容器映像直接部署到 GKE，遷移成本接近零。
「未來可能需要」不是現在就承擔複雜度的理由，前提是你保留了退路。
