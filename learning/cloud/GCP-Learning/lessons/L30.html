LESSON 30

BigQuery 進階：分區、成本與資料建模

第 21 課教你查詢，這一課教你把 BigQuery 用成一個真正的企業資料倉儲——包含建模方法、成本控管與治理。

閱讀 28 分進階

一、資料倉儲的分層架構

不要把所有資料丟進一個資料集就開始查。成熟的資料團隊用分層管理，這是資料工程的標準做法：

三層架構
RAW 原始層（bronze）
  「原封不動的來源資料」
  • 不做任何轉換，保留原始格式
  • 用途：可重跑、可追溯、出問題時的真相來源
  • 存取權限：只有資料工程師
        ↓ 清洗、去重、型別轉換
STAGING 整理層（silver）
  「清洗過但仍接近原始結構」
  • 統一命名、處理 NULL、去除重複、修正型別
  • 用途：下游轉換的共同基礎
        ↓ 業務邏輯、聚合、join
MART 資料超市層（gold）
  「面向業務的分析表」
  • 例：每日營收、客戶 360 視圖、商品成效
  • 用途：BI 工具、分析師直接查詢
  • 存取權限：業務單位

為什麼要分層？因為業務邏輯會變，但原始資料不會。當你發現三個月前的計算邏輯有錯，有 RAW 層才能重算；只有最終結果表的話，錯誤就是永久的。

二、分區與叢集的正確用法

分區 Partitioning叢集 Clustering
原理把表實體切成多個區塊區塊內依欄位值排序
可用欄位數只能 1 個最多 4 個（有順序性）
適用欄位日期 / 時間戳 / 整數範圍任何高基數欄位（user_id、product_id）
效果大幅減少掃描量中度減少掃描量
查詢時的要求WHERE 分區欄 = ...WHERE 叢集欄 = ...（要照順序用）
bash
-- 標準的事實表設計
CREATE TABLE mart.fact_orders
PARTITION BY DATE(order_time)
CLUSTER BY store_id, product_category, customer_id
OPTIONS(
  partition_expiration_days = 1095,
  require_partition_filter = true,
  description = "訂單事實表。分區：訂單日期；叢集：門市>類別>客戶"
)
AS ...;

-- ✅ 好的查詢：用到分區 + 第一個叢集欄
SELECT SUM(amount) FROM mart.fact_orders
WHERE DATE(order_time) BETWEEN '2026-07-01' AND '2026-07-31'
  AND store_id = 'ST001';

-- ❌ 差的查詢：跳過第一個叢集欄，叢集效果大打折扣
SELECT SUM(amount) FROM mart.fact_orders
WHERE DATE(order_time) = '2026-07-15'
  AND customer_id = 'C123';    -- customer_id 是第三個叢集欄
實務提醒
叢集欄位的順序很重要，要按「篩選頻率由高到低」排。因為叢集是階層式排序——先按第一欄排，同值再按第二欄排。跳過第一欄直接篩第三欄，就無法有效跳過區塊。
決定順序前先看實際的查詢日誌（INFORMATION_SCHEMA.JOBS），不要靠猜。

三、成本控管的完整方案

① 隨用隨付模式的護欄

bash
# 專案層級：每日查詢量上限（在 Console → IAM → 配額設定）
# Quota: "Query usage per day" → 設為 5 TiB

# 使用者層級：每人每日上限
# Quota: "Query usage per day per user" → 設為 500 GiB

# 單次查詢上限（在程式或 CLI 中強制）
bq query --maximum_bytes_billed=100000000000 '...'   # 100GB

# 在 Python client 中設定
from google.cloud import bigquery
job_config = bigquery.QueryJobConfig(maximum_bytes_billed=100_000_000_000)

② 容量定價（Editions）

查詢量穩定且大時，改用 slot 預留會比隨用隨付便宜且可預測：

版本特性適合
Standard基本功能，可自動擴充小團隊
Enterprise加上 VPC-SC、CMEK、跨區複製企業標準選擇
Enterprise Plus加上進階災難復原關鍵業務
bash
# 建立預留（可設定基準 + 自動擴充上限）
bq mk --reservation --project_id=$PROJECT --location=asia-east1 \
  --slots=500 --edition=ENTERPRISE prod-reservation

# 把不同工作負載分配到不同預留，避免互相干擾
bq mk --reservation_assignment \
  --reservation_id=prod-reservation \
  --job_type=QUERY \
  --assignee_type=FOLDER --assignee_id=BI_FOLDER_ID

③ 儲存成本優化

  • 長期儲存自動折扣：連續 90 天未修改的分區，儲存費自動降 50%，不用做任何事。但注意：對表做任何寫入會重置整張表的計時器嗎？不會——BigQuery 是按分區計算的，所以分區表天生受益。
  • 設定分區到期：partition_expiration_days 自動刪除舊資料。
  • 用具體化檢視表取代重複的聚合查詢：自動增量更新，查詢時只掃聚合結果。
  • 大型歷史資料匯出到 GCS：用外部表查詢，儲存費從 $0.02/GB 降到 $0.004/GB。
bash
-- 具體化檢視表：常用聚合預先算好
CREATE MATERIALIZED VIEW mart.daily_revenue
PARTITION BY order_date
CLUSTER BY store_id
AS
SELECT
  DATE(order_time) AS order_date,
  store_id,
  COUNT(*) AS order_count,
  SUM(amount) AS revenue
FROM mart.fact_orders
GROUP BY 1, 2;

-- BigQuery 會自動判斷：查原表時如果能用 MV 回答，就自動改用 MV
-- 你不用改查詢，成本自動下降

列級權限（業務只能看自己區域的資料）Row-Level Security

-- 列級安全性：業務只看得到自己負責的區域
CREATE ROW ACCESS POLICY north_sales_policy
ON mart.fact_orders
GRANT TO ("group:north-sales@corp.com")
FILTER USING (region = "北區");

-- 動態資料遮罩
ALTER TABLE mart.customers
ALTER COLUMN phone SET OPTIONS (

五、常見的效能反模式

反模式為什麼慢/貴正確做法
SELECT *掃描所有欄位明確列出需要的欄位
WHERE DATE(ts) = '2026-07-01' 但 ts 未分區全表掃描先建分區表
在 WHERE 中對分區欄位做函式運算可能無法裁剪分區用範圍比較：ts >= TIMESTAMP('...')
ORDER BY 大量資料後才 LIMIT排序全部資料盡量在子查詢先篩選
自我 JOIN 做去重資料重排成本高用 ROW_NUMBER() OVER (PARTITION BY ...)
COUNT(DISTINCT x) 在超大表精確去重很貴用 APPROX_COUNT_DISTINCT(x)（誤差 < 1%）
大表 JOIN 大表資料 shuffle 量巨大先各自聚合再 JOIN；或用巢狀/重複欄位取代 JOIN
補充
巢狀與重複欄位是 BigQuery 特有的優化。傳統資料庫要正規化避免重複，但 BigQuery 是欄式儲存，把訂單明細直接存成訂單表的 ARRAY 欄位，可以完全避免 JOIN：
bash
CREATE TABLE orders_nested (
  order_id STRING,
  order_time TIMESTAMP,
  customer STRUCT<id STRING, name STRING, tier STRING>,
  items ARRAY<STRUCT<sku STRING, qty INT64, price NUMERIC>>
);

-- 查詢時用 UNNEST 展開
SELECT o.order_id, i.sku, i.qty
FROM orders_nested o, UNNEST(o.items) AS i
WHERE i.qty > 5;

自我檢測

分析師寫的查詢 dry run 顯示 2TB，但表明明有分區。為什麼沒生效？
分區裁剪失效的四個常見原因：
① 對分區欄做了函式運算——WHERE DATE(ts) = '2026-07-01' 在某些情況下無法裁剪。改成 WHERE ts >= TIMESTAMP('2026-07-01') AND ts < TIMESTAMP('2026-07-02')。
② 用變數或子查詢當篩選條件——WHERE date = (SELECT MAX(date) FROM ...) 在查詢規劃階段無法確定值，所以無法裁剪。解法是用兩段式查詢或宣告變數。
③ JOIN 條件裡的分區欄——分區裁剪只對 WHERE 生效。
④ 用了 OR 連接非分區條件。

驗證方法：在 Console 的查詢編輯器右上角會即時顯示「此查詢將處理 X」，改寫後對比就知道有沒有生效。
BigQuery 每月費用從 $2000 漲到 $12000，怎麼找原因？
查 INFORMATION_SCHEMA.JOBS，從三個角度切：
bash
-- ① 按使用者/服務帳號
SELECT user_email, COUNT(*) AS jobs,
       SUM(total_bytes_billed)/POW(1024,4) AS tb
FROM `region-asia-east1`.INFORMATION_SCHEMA.JOBS
WHERE creation_time >= TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 30 DAY)
GROUP BY 1 ORDER BY tb DESC LIMIT 10;

-- ② 按查詢樣式（找出重複執行的昂貴查詢）
SELECT
  SUBSTR(query, 1, 200) AS query_prefix,
  COUNT(*) AS runs,
  SUM(total_bytes_billed)/POW(1024,4) AS tb
FROM `region-asia-east1`.INFORMATION_SCHEMA.JOBS
WHERE creation_time >= TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 30 DAY)
  AND job_type = 'QUERY'
GROUP BY 1 ORDER BY tb DESC LIMIT 20;

-- ③ 按時間趨勢（找出是哪天開始漲的）
SELECT DATE(creation_time) AS d,
       SUM(total_bytes_billed)/POW(1024,4) AS tb
FROM `region-asia-east1`.INFORMATION_SCHEMA.JOBS
WHERE creation_time >= TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 60 DAY)
GROUP BY 1 ORDER BY 1;
最常見的三個真兇：① BI 工具（Looker / Tableau）的自動重新整理設得太頻繁；② 新上線的排程查詢沒優化；③ 有人建了新表但忘記分區。

處置：對 BI 工具啟用 BI Engine 或改查具體化檢視表；對排程查詢做分區優化；並立即設定專案配額避免再次失控。
公司要求「分析師可以查客戶表，但看不到身分證號與完整電話」。怎麼實作？
用 Policy Tags + 資料遮罩，而不是建一個「脫敏副本表」。

為什麼不用副本表：資料會不同步、儲存加倍、且分析師仍可能有辦法拿到原表。

實作步驟：
① 在 Data Catalog 建立分類（taxonomy），定義 PII/高度敏感 標籤。
② 對 id_number、phone 欄位套用該 policy tag。
③ 授予分析師群組 roles/bigquery.dataViewer（表層級），但不授予 roles/datacatalog.categoryFineGrainedReader（標籤層級）。
④ 結果：分析師 SELECT * 會直接報錯（提示無權限存取某欄位），必須明確排除敏感欄位。
⑤ 若希望「能看到但遮罩」而非報錯，另外設定 Data Masking 規則（例如電話顯示為 0912-***-678）。

補強措施：用 Sensitive Data Protection 定期掃描所有資料集，自動發現「有人把身分證號放到沒有標籤的新表」。治理的難點從來不是設定既有的表，而是持續發現新的違規。
