LESSON 11

Cloud Run 實戰：把 API 從零推上線

這一課從空白資料夾開始，寫一個 API、包成容器、部署到 Cloud Run、設定自訂網域，全程約一小時。做完你就有了一個真正能用的線上服務。

操作 60 分約 0 元實作

一、準備：確認環境

bash
gcloud config set project 你的專案ID
gcloud config set run/region asia-east1

# 啟用必要 API
gcloud services enable run.googleapis.com \
  cloudbuild.googleapis.com \
  artifactregistry.googleapis.com

二、寫一個 API

動手實作

實作 1：建立應用程式

  1. 在 Cloud Shell 建立專案資料夾：
    bash
    mkdir -p ~/task-api && cd ~/task-api
  2. 建立 main.py（用 cloudshell edit main.py 開編輯器，或直接用下面的 heredoc）：
    bash
    cat > main.py <<'EOF'
import os
from flask import Flask, jsonify, request

app = Flask(__name__)

# 注意：這只是示範。正式環境資料要放外部資料庫，
# 因為 Cloud Run 實例隨時會被回收，記憶體資料會消失。
tasks = []

@app.get("/")
def index():
    return jsonify({
        "service": "task-api",
        "version": os.environ.get("APP_VERSION", "dev"),
        "instance": os.environ.get("K_REVISION", "local"),
        "task_count": len(tasks),
    })

@app.get("/healthz")
def healthz():
    return "ok", 200

@app.get("/tasks")
def list_tasks():
    return jsonify(tasks)

@app.post("/tasks")
def create_task():
    data = request.get_json(silent=True) or {}
    title = data.get("title")
    if not title:
        return jsonify({"error": "title 為必填"}), 400
    task = {"id": len(tasks) + 1, "title": title, "done": False}
    tasks.append(task)
    return jsonify(task), 201

if __name__ == "__main__":
    # 關鍵：一定要讀 PORT 環境變數，且綁 0.0.0.0
    port = int(os.environ.get("PORT", 8080))
    app.run(host="0.0.0.0", port=port)
EOF
  3. 建立 requirements.txt：
    bash
    cat > requirements.txt <<'EOF'
Flask==3.0.3
gunicorn==22.0.0
EOF
  4. 本機先測試（Cloud Shell 也算本機）：
    bash
    pip install -r requirements.txt --quiet
python main.py &
sleep 2
curl localhost:8080
curl -X POST localhost:8080/tasks -H "Content-Type: application/json" -d '{"title":"學會 Cloud Run"}'
curl localhost:8080/tasks
kill %1
小心踩雷
Cloud Run 最常見的部署失敗原因，就是沒有監聽 $PORT 環境變數。
Cloud Run 會透過 PORT（預設 8080）告訴你的程式該監聽哪個埠。寫死 port=5000 或綁 127.0.0.1 都會導致「容器啟動失敗」。
兩個鐵則：① 讀 os.environ['PORT']；② 綁 0.0.0.0 不是 localhost。

三、包成容器

動手實作

實作 2：撰寫 Dockerfile

  1. 建立 Dockerfile：
    bash
    cat > Dockerfile <<'EOF'
# 用 slim 版本，映像小很多，冷啟動更快
FROM python:3.12-slim

ENV PYTHONUNBUFFERED=1 \
    PYTHONDONTWRITEBYTECODE=1

WORKDIR /app

# 先複製 requirements 再安裝，讓 Docker 快取這一層
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

# 用 gunicorn 而不是 Flask 內建伺服器（內建的不適合正式環境）
# --workers 1 + --threads 8 搭配 Cloud Run 的並行模型
CMD exec gunicorn --bind :$PORT --workers 1 --threads 8 --timeout 0 main:app
EOF
  2. 建立 .dockerignore，避免把垃圾打包進去：
    bash
    cat > .dockerignore <<'EOF'
__pycache__/
*.pyc
.git/
.env
venv/
EOF

四、部署

動手實作

實作 3：一行指令部署

  1. 最簡單的方式——讓 Cloud Run 自己處理建置與部署：
    bash
    gcloud run deploy task-api \
  --source=. \
  --region=asia-east1 \
  --allow-unauthenticated \
  --memory=512Mi \
  --cpu=1 \
  --concurrency=80 \
  --min-instances=0 \
  --max-instances=10 \
  --timeout=60 \
  --set-env-vars=APP_VERSION=1.0.0
  2. 第一次會問你要不要建立 Artifact Registry 儲存庫，選 y。
    整個流程約 2～4 分鐘：上傳原始碼 → Cloud Build 建置映像 → 推到 Artifact Registry → 部署 → 產生網址。
  3. 測試線上服務：
    bash
    URL=$(gcloud run services describe task-api --region=asia-east1 --format="value(status.url)")
echo $URL

curl $URL
curl -X POST $URL/tasks -H "Content-Type: application/json" -d '{"title":"第一個雲端任務"}'
curl $URL/tasks
  4. 看看擴充行為——同時打 50 個請求，觀察實例數：
    bash
    for i in {1..50}; do curl -s $URL > /dev/null & done; wait
gcloud run services describe task-api --region=asia-east1 \
  --format="value(status.traffic)"

五、修訂版本與流量分配

Cloud Run 每次部署都會產生一個修訂版本（Revision），舊版本不會消失。這讓金絲雀發布和秒級回滾變得非常簡單。

藍綠 / 金絲雀部署
# 部署新版本，但先不給流量
gcloud run deploy task-api --source=. --region=asia-east1 \
  --set-env-vars=APP_VERSION=2.0.0 \
  --no-traffic --tag=v2

# 用專屬網址單獨測試新版（不影響正式流量）
# 網址格式：https://v2---task-api-xxxxx.a.run.app

# 確認沒問題後，分 10% 流量給新版做金絲雀
gcloud run services update-traffic task-api --region=asia-east1 \
  --to-tags=v2=10

# 觀察錯誤率沒問題，全量切換
gcloud run services update-traffic task-api --region=asia-east1 \
  --to-latest

# 出事了？秒級回滾
gcloud run revisions list --service=task-api --region=asia-east1
gcloud run services update-traffic task-api --region=asia-east1 \
  --to-revisions=task-api-00001-abc=100
實務提醒
這是 Cloud Run 最被低估的功能。在 VM 或 K8s 上做金絲雀發布要設定一堆東西，Cloud Run 一行指令就完成，而且回滾是瞬間的（只是改路由，不用重新部署）。
正式環境請養成習慣：永遠用 --no-traffic --tag 部署，測試過再切流量。

六、安全設定：關閉公開存取

bash
# 移除公開存取
gcloud run services remove-iam-policy-binding task-api \
  --region=asia-east1 \
  --member="allUsers" --role="roles/run.invoker"

# 只允許特定服務帳號呼叫（微服務之間互相呼叫的標準做法）
gcloud run services add-iam-policy-binding task-api \
  --region=asia-east1 \
  --member="serviceAccount:frontend@PROJECT.iam.gserviceaccount.com" \
  --role="roles/run.invoker"

# 用自己的身分測試（帶 identity token）
curl -H "Authorization: Bearer $(gcloud auth print-identity-token)" $URL

# 敏感設定用 Secret Manager，不要用環境變數
echo -n "super-secret-key" | gcloud secrets create api-key --data-file=-
gcloud run services update task-api --region=asia-east1 \
  --set-secrets=API_KEY=api-key:latest
小心踩雷
不要把密碼、API 金鑰放進 --set-env-vars。環境變數會出現在部署設定裡，任何有 Viewer 權限的人都看得到，也會被記進稽核日誌。一律用 Secret Manager。

七、綁定自訂網域

bash
# 方法一：Cloud Run 網域對應（設定簡單，但功能較少）
gcloud beta run domain-mappings create \
  --service=task-api --domain=api.example.com --region=asia-east1

# 方法二（推薦）：用 Global External Application LB
#   優點：可搭配 Cloud Armor、Cloud CDN、多服務共用同一個網域
#   作法：建立 serverless NEG 當作 LB 的後端
gcloud compute network-endpoint-groups create task-api-neg \
  --region=asia-east1 \
  --network-endpoint-type=serverless \
  --cloud-run-service=task-api

gcloud compute backend-services create task-api-backend --global
gcloud compute backend-services add-backend task-api-backend \
  --global --network-endpoint-group=task-api-neg \
  --network-endpoint-group-region=asia-east1

bash
gcloud run services delete task-api --region=asia-east1 --quiet

# 別忘了 Artifact Registry 裡的映像也會佔空間收費
gcloud artifacts repositories list
gcloud artifacts repositories delete cloud-run-source-deploy \

九、本課檢核

  • 寫出一個能在 Cloud Run 上跑的容器化應用
  • 知道必須監聽 $PORT 且綁 0.0.0.0
  • 會用 --no-traffic --tag 做金絲雀部署
  • 會用 update-traffic 做秒級回滾
  • 知道密鑰要用 Secret Manager 而非環境變數
  • 已刪除服務與映像倉庫

自我檢測

部署後一直失敗，錯誤訊息是「The user-provided container failed to start and listen on the port defined by the PORT environment variable」。你會依序檢查什麼？
四件事，由高頻到低頻：
① 有沒有讀 PORT 環境變數，而不是寫死埠號。
② 有沒有綁 0.0.0.0，綁 127.0.0.1 的話容器外部連不進來。
③ 啟動時間有沒有超過 --timeout（預設容器啟動有 4 分鐘上限），例如啟動時載入大型模型。
④ 看建置與執行日誌：gcloud run services logs read task-api --region=asia-east1 --limit=50，通常會直接看到 Python traceback。
這個範例的 tasks 存在記憶體裡。實際上線會發生什麼問題？
資料會隨機消失，而且不同使用者看到不同結果。兩個原因：
① Cloud Run 實例閒置一段時間就被回收，記憶體清空。
② 有多個實例時，使用者 A 的請求進實例 1，B 的請求進實例 2，兩邊的 tasks 陣列完全獨立。

正確做法依需求選：Firestore（簡單、免管理、適合這種小型 API）、Cloud SQL（需要交易與關聯查詢）、Memorystore（純快取）。
「無狀態」不是限制，是設計要求——所有狀態必須外部化。
服務平常沒流量，但每次有人第一次呼叫都要等 3 秒。有哪些選項，各自的成本與效果？
四個選項，依成本排序：
① 優化映像大小（免費）：用 slim/distroless 基底、multi-stage build。從 800MB 降到 50MB 通常能省一半冷啟動時間。
② 啟用 Startup CPU Boost（幾乎免費）：--cpu-boost，啟動期間給更多 CPU。
③ 延後載入重物件（免費）：不要在模組載入時連資料庫或載模型，改成第一次用到才做。
④ 設定 --min-instances=1（約 $5～15/月）：徹底消除冷啟動，但要付常駐費用。

順序很重要：先做前三項（免費且治本），還不夠再花錢買 min-instances。很多團隊直接跳到第四項，結果既花錢、冷啟動在擴充時還是會發生。
