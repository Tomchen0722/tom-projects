LESSON 37

備份、災難復原與高可用設計

這一課處理一個問題：當最壞的情況發生時，你多久能恢復、會失去多少資料？答案應該來自事先的設計與演練，而不是事發時的祈禱。

閱讀 25 分企業級

一、兩個定義一切的指標

RPO 與 RTO
        故障發生
            ↓
─────┬──────┴──────┬─────→ 時間
  最後備份         恢復完成
     ├──── RPO ────┤
     （可容忍的資料遺失量）
            ├──── RTO ────┤
            （可容忍的停機時間）

RPO = Recovery Point Objective  「能接受失去多少資料？」
RTO = Recovery Time Objective   「能接受停機多久？」

這兩個數字必須由業務方決定，不是技術方決定。技術方的工作是說明「達到這個數字需要多少成本」，然後一起做取捨。

二、四種災難復原策略

策略RTORPO成本說明
備份與還原
Backup & Restore		數小時 ~ 數天數小時最低只有備份，災難時從零重建
冷備援
Pilot Light		數十分鐘 ~ 數小時數分鐘低核心元件（資料庫副本）常駐，其餘關閉
溫備援
Warm Standby		數分鐘數秒 ~ 數分鐘中完整但縮小規模的環境持續運行
熱備援 / 雙活
Hot / Active-Active		近乎零近乎零最高（2倍以上）兩地同時服務流量
實務提醒
務實的建議：不同系統用不同策略。
• 結帳與付款 → 溫備援或雙活
• 商品瀏覽 → 冷備援
• 內部報表系統 → 備份與還原

對所有系統套用同一個標準，不是最貴就是最脆弱。

三、GCP 上的高可用層級

高可用層級
層級 1：單一 VM
   ❌ 任何故障都中斷        可用性 ~99.5%

層級 2：同 Zone 多台 + 負載平衡
   ✅ 單機故障可容忍
   ❌ Zone 故障全掛          可用性 ~99.9%

層級 3：跨 Zone（Regional MIG + Regional LB + HA 資料庫）
   ✅ 單一 Zone 故障可容忍
   ❌ Region 故障全掛        可用性 ~99.95%
   ★ 大多數服務的正確選擇，成本增加有限

層級 4：跨 Region（多 Region 部署 + 全域 LB + 跨區資料複製）
   ✅ 整個 Region 故障可容忍
   ❌ 成本大幅增加           可用性 ~99.99%

層級 5：多雲
   ✅ 單一雲廠商故障可容忍
   ❌ 複雜度極高，多數情況不值得
小心踩雷
絕大多數團隊應該停在層級 3。跨 Region 的成本不只是「兩倍基礎設施」，還包括：資料同步的延遲與費用、雙倍的部署與監控複雜度、以及資料一致性問題。
而 Region 級別的故障極其罕見（幾年一次），Zone 級別的問題則常見得多。把資源花在層級 3 做紮實，投報率遠高於勉強做層級 4。

四、備份策略：3-2-1 原則

這是資料保護的經典法則，在雲端一樣適用：

  • 3 份資料副本（1 份正式 + 2 份備份）
  • 2 種不同的儲存媒介／位置
  • 1 份異地（不同 Region，或不同雲／地端）
bash
# Cloud SQL：自動備份 + PITR + 跨區副本
gcloud sql instances patch prod-db \
  --backup-start-time=18:00 \
  --retained-backups-count=30 \
  --enable-point-in-time-recovery \
  --retained-transaction-log-days=7

gcloud sql instances create prod-db-dr \
  --master-instance-name=prod-db --region=asia-northeast1

# Persistent Disk：排程快照 + 跨區複製
gcloud compute resource-policies create snapshot-schedule daily-backup \
  --region=asia-east1 \
  --daily-schedule --start-time=18:00 \
  --max-retention-days=30 \
  --storage-location=asia \
  --on-source-disk-delete=KEEP_AUTO_SNAPSHOTS

# Cloud Storage：版本控制 + 跨區複製 + 保留鎖定
gcloud storage buckets update gs://critical-data --versioning
gcloud storage buckets update gs://critical-data --retention-period=90d

# BigQuery：跨區資料集複製
bq mk --transfer_config --data_source=cross_region_copy \
  --target_dataset=backup_dataset \
  --params='{"source_dataset_id":"prod_dataset","source_project_id":"PROJ"}'
小心踩雷
備份必須與正式環境隔離，否則勒索軟體或誤操作會一起吃掉。
具體措施：
① 備份放在不同的專案，且該專案的權限與正式環境完全分開。
② 使用 Bucket Lock 保留政策——鎖定後連 Owner 都無法刪除。
③ 對備份專案設定 Deny Policy，禁止任何人執行刪除操作。

「攻擊者拿到管理員權限後把備份也刪了」是真實發生過很多次的情境。

五、演練：沒演練過的計畫等於沒有計畫

災難復原計畫的價值不在文件，在於團隊真的做過。建議的演練節奏：

頻率演練內容目標
每月從備份還原單一資料庫到測試環境驗證備份可用、熟悉流程
每季模擬 Zone 故障（實際關閉一個 Zone 的資源）驗證自動故障轉移
每年完整的 Region 故障演練驗證 DR 計畫、量測真實 RTO
bash
# 混沌工程：主動注入故障驗證韌性

# ① 隨機終止一個 Pod
kubectl delete pod $(kubectl get pods -n prod -o name | shuf -n 1)

# ② 模擬 Zone 故障
gcloud compute instance-groups managed resize web-mig \
  --region=asia-east1 --size=0 --zone-to-drain=asia-east1-b

# ③ 模擬資料庫故障轉移
gcloud sql instances failover prod-db

# ④ 模擬網路延遲（在測試環境）
tc qdisc add dev eth0 root netem delay 500ms 100ms
實務提醒
演練要記錄的三件事：
① 實際花了多久（跟 RTO 目標比對）
② 哪一步卡住了（通常是文件過時、權限不足、或某個人才知道的隱性知識）
③ 有誰不知道該做什麼（訓練缺口）

第一次演練幾乎必定會超過 RTO 目標，這很正常——重點是每次演練後改善，讓時間逐次縮短。

六、災難復原手冊（Runbook）該包含什麼

  1. 觸發條件——什麼情況下啟動 DR？誰有權決定？（模糊的決策權會浪費最多時間）
  2. 聯絡清單——含備援聯絡人與外部廠商，且要在系統掛掉時也拿得到（不要只存在內部 Wiki）
  3. 逐步操作指令——可以複製貼上的具體指令，不是「切換資料庫」這種描述
  4. 驗證步驟——怎麼確認恢復成功？有哪些檢查點？
  5. 回切計畫——主要 Region 恢復後，怎麼切回去？（這一步最常被遺漏，而且比切過去更難）
  6. 對外溝通範本——給客戶、給主管的訊息草稿

七、本課檢核

  • 能定義自己系統的 RPO 與 RTO
  • 知道四種 DR 策略的成本與能力取捨
  • 理解大多數服務停在「跨 Zone」層級即可
  • 知道備份要與正式環境隔離並用 Bucket Lock 保護
  • 有排定的演練節奏，且演練過至少一次還原

自我檢測

你的備份跑了兩年從沒失敗過。可以信任它嗎？
不行。「備份成功」和「能還原」是兩件事。

真實發生過的失敗模式：
• 備份的是錯誤的資料庫（改過名字後腳本沒更新）
• 備份檔案損毀但備份程序回報成功
• 備份有加密，但金鑰已經遺失或輪換過
• 備份存在同一個帳號，帳號被入侵時一起被刪
• 還原需要的相依項目（schema、設定、憑證）沒有一起備份
• 資料量成長後，還原時間從 30 分鐘變成 8 小時，遠超 RTO

唯一的驗證方法是實際還原：
① 每月自動還原到隔離的測試環境
② 執行資料完整性檢查（筆數、關鍵資料抽樣比對）
③ 記錄還原耗時，追蹤趨勢
④ 把這整套自動化，讓它變成 CI 的一部分

格言：「你沒有備份系統，你只有還原系統——而且它的狀態是未知的，直到你測試它。」
電商網站，老闆說「絕對不能停機」。你怎麼設計？
先把「絕對不能停機」翻譯成可執行的數字與預算。

① 釐清需求——「不能停機」通常指的是結帳流程，而不是後台報表。先做業務衝擊分析：停機一小時損失多少營收？哪些功能停了會損失最大？

② 分級設計（把錢花在刀口上）：
  • 結帳與付款：跨 Region 雙活，RTO < 1 分鐘
  • 商品瀏覽：跨 Zone + CDN 快取，即使後端全掛，CDN 仍能提供靜態內容
  • 推薦、評論：可降級（服務不可用時隱藏該區塊，不影響主流程）
  • 後台管理：跨 Zone 即可

③ 技術配置：
  • 全域 LB + 多 Region 後端
  • 庫存與訂單用 Spanner（多 Region 強一致，這是唯一能同時滿足「雙活」與「不能超賣」的選擇）
  • 靜態資源全上 CDN
  • 所有服務實作優雅降級與斷路器

④ 誠實說明限制——即使做到這樣，仍會有：部署期間的短暫異常、DNS 傳播延遲、以及使用者端的網路問題。「絕對不能停機」在物理上不存在。

最後要提醒：大多數停機不是來自基礎設施故障，而是來自變更（部署、設定改動）。把錢花在部署流程與測試上，投報率往往高於多買一個 Region。
Region 完全故障，你切換到 DR Region。三小時後主 Region 恢復了。怎麼切回去？
切回去（failback）通常比切過去更危險，因為此時兩邊的資料都不完整。

核心問題：這三小時的新資料只存在 DR Region，而主 Region 停留在故障前的狀態。如果直接切回去，這三小時的訂單就消失了。

正確步驟：
① 不要急——DR Region 正常服務中就先讓它繼續跑。failback 應該安排在計畫性的低流量時段，不是恢復後立刻做。

② 資料同步——把 DR Region 的資料反向複製回主 Region，並持續同步直到延遲趨近於零。這一步可能需要數小時。

③ 驗證資料一致性——比對兩邊的關鍵資料（筆數、金額總和、最新交易時間）。如果故障期間主 Region 曾短暫接受過寫入（腦裂），這裡會發現衝突，需要人工處理。

④ 計畫性切換——公告維護視窗 → 停止 DR 寫入 → 等待同步完成 → 切換 DNS/LB → 驗證 → 恢復服務。

⑤ 觀察期——切回後保持 DR Region 待命至少 24 小時，確認穩定再縮容。

要事先準備的：
• 雙向複製的能力（不是只有單向）
• 資料一致性檢查工具
• 明確的「誰有權決定 failback」

經驗談：很多團隊的 DR 計畫只寫了怎麼切過去，沒寫怎麼切回來。結果切過去之後在 DR Region 待了三個月，因為沒人知道怎麼安全地切回去。
