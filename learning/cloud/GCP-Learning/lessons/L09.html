LESSON 09

負載平衡器：流量的交通指揮

負載平衡器是雲端架構的心臟。它決定了你的服務能不能承受流量、能不能零停機更新、能不能擋掉攻擊。GCP 的 LB 設計跟其他雲很不一樣，值得花時間搞懂。

操作 50 分約 0.5 美元實作

一、負載平衡器解決什麼問題

你有 5 台一模一樣的網頁伺服器。使用者要連哪一台？總不能叫他們自己挑。負載平衡器（Load Balancer, LB）站在最前面，對外只有一個 IP，收到請求後決定送給哪一台後端。

但它做的遠不只「分流量」，這四件事同樣重要：

  • 健康檢查：發現某台掛了，自動不再送流量過去。
  • SSL 終結：憑證裝在 LB 上，後端不用各自管憑證。
  • 零停機部署：新版機器通過健康檢查才接流量，舊機器排空後才下線。
  • 攻擊防護：搭配 Cloud Armor 擋 DDoS 與 OWASP 攻擊。

二、GCP 負載平衡器的獨特之處

補充
GCP 的全域外部 HTTP(S) LB 是「真・全域」的。
你拿到一個 Anycast IP，全世界任何地方連這個 IP，都會被導到離自己最近的 Google 邊緣節點，然後走 Google 的私有骨幹網路到後端。
對比 AWS 的 ALB 是區域級的，要做全球架構得自己搭 Route 53 + 多個 ALB。這是 GCP 少數明顯領先的地方。

三、七種 LB，用兩個問題就能選對

GCP 的 LB 種類看起來很多，但你只要問兩個問題：

選型的兩個問題
問題 1：流量從哪來？
   外部（Internet） → External LB
   內部（VPC 內部）   → Internal LB

問題 2：要在第幾層處理？
   看得懂 HTTP、要做路徑分流 / SSL 終結 → Application LB（L7）
   只認 IP 和 Port，要求極低延遲          → Network LB（L4）
需求選這個說明
公開網站、API、需要路徑分流Global External Application LB最常用。支援 HTTP/2、gRPC、Cloud CDN、Cloud Armor
公開的 TCP/UDP 服務（遊戲、DNS）Global External Network LB（Proxy 或 Passthrough）極低延遲，保留來源 IP
VPC 內部的微服務互相呼叫Regional Internal Application LB不對外，走內部 IP
VPC 內部的資料庫、快取前端Regional Internal Passthrough Network LBL4，效能最好

四、Application LB 的五層元件

這是 GCP LB 最讓新手困惑的地方——它不是一個物件，而是五個物件串起來。理解這個結構，你才能做出複雜的流量規則。

五層元件
     使用者
       ↓
[1] Forwarding Rule（轉發規則）
    「監聽哪個 IP 和 Port」  例：34.1.2.3:443
       ↓
[2] Target HTTPS Proxy（目標代理）
    「掛哪張 SSL 憑證」
       ↓
[3] URL Map（網址對應表）
    「/api/* 送 A 組，/static/* 送 B 組，其他送 C 組」
       ↓
[4] Backend Service（後端服務）
    「這組後端的健康檢查、逾時、Session 黏著、CDN 設定」
       ↓
[5] Backend（後端）
    「實際的 MIG、Cloud Run 服務、或 Cloud Storage 桶」
實務提醒
記憶技巧：由外而內，越來越具體。
轉發規則管「入口」→ Proxy 管「加密」→ URL Map 管「路由」→ Backend Service 管「策略」→ Backend 管「實體」。
考證照時這五層的順序是必考題。

五、實作：建立一個全球 HTTPS 負載平衡器

動手實作

實作：把上一課的 MIG 掛上全域 LB

  1. 先確認你有一個 MIG（沿用上一課的 web-mig，若已刪除請重建）。
    設定具名連接埠——LB 要知道往哪個 port 送：
    bash
    gcloud compute instance-groups managed set-named-ports web-mig \
  --region=asia-east1 --named-ports=http:80
  2. 健康檢查（LB 用的健康檢查與 MIG 的可以共用，但建議分開設定）：
    bash
    gcloud compute health-checks create http lb-hc \
  --port=80 --request-path=/ --check-interval=5s --timeout=5s
  3. 建立 Backend Service 並加入後端：
    bash
    gcloud compute backend-services create web-backend \
  --protocol=HTTP --port-name=http \
  --health-checks=lb-hc \
  --global \
  --enable-cdn \
  --timeout=30s

gcloud compute backend-services add-backend web-backend \
  --instance-group=web-mig \
  --instance-group-region=asia-east1 \
  --balancing-mode=UTILIZATION \
  --max-utilization=0.8 \
  --capacity-scaler=1.0 \
  --global
  4. 建立 URL Map（先做最簡單的：全部送同一組）：
    bash
    gcloud compute url-maps create web-urlmap \
  --default-service=web-backend
  5. 建立 HTTP Proxy 與轉發規則（先用 HTTP 驗證，HTTPS 下一步）：
    bash
    gcloud compute target-http-proxies create web-proxy \
  --url-map=web-urlmap

gcloud compute addresses create web-lb-ip --global --ip-version=IPV4

gcloud compute forwarding-rules create web-fr \
  --address=web-lb-ip --global \
  --target-http-proxy=web-proxy --ports=80
  6. 開放健康檢查的來源網段（這一步忘了的話後端會永遠 unhealthy）：
    bash
    gcloud compute firewall-rules create allow-lb-health-check \
  --allow=tcp:80 \
  --source-ranges=130.211.0.0/22,35.191.0.0/16 \
  --target-tags=http-server \
  --description="GCP 負載平衡器與健康檢查的固定來源網段"
  7. 取得 IP 並測試（LB 生效要 3～8 分鐘，請耐心等，別急著判定失敗）：
    bash
    IP=$(gcloud compute addresses describe web-lb-ip --global --format="value(address)")
echo "http://$IP"

# 重複打幾次，觀察回應來自不同的後端機器
for i in {1..10}; do curl -s http://$IP | grep Server; sleep 1; done
  8. 檢查後端健康狀態：
    bash
    gcloud compute backend-services get-health web-backend --global

六、加上 HTTPS 與 Google 託管憑證

Google 可以幫你免費簽發並自動續期 SSL 憑證，前提是你有一個網域。

bash
# 1. 建立 Google 託管憑證（需要你擁有這個網域）
gcloud compute ssl-certificates create web-cert \
  --domains=www.example.com,example.com \
  --global

# 2. 把 DNS 的 A 記錄指向 LB 的 IP（在你的 DNS 供應商操作）
#    www.example.com  A  34.1.2.3

# 3. 建立 HTTPS Proxy 與 443 轉發規則
gcloud compute target-https-proxies create web-https-proxy \
  --url-map=web-urlmap --ssl-certificates=web-cert

gcloud compute forwarding-rules create web-fr-https \
  --address=web-lb-ip --global \
  --target-https-proxy=web-https-proxy --ports=443

# 4. 把 HTTP 自動導向 HTTPS
gcloud compute url-maps create http-redirect \
  --default-url-redirect-action=HTTPS_REDIRECT \
  --default-url-redirect-response-code=MOVED_PERMANENTLY_DEFAULT
小心踩雷
Google 託管憑證必須等 DNS 指向 LB 之後才會簽發成功，狀態從 PROVISIONING 變成 ACTIVE 可能要 15～60 分鐘。
用這個指令追蹤：gcloud compute ssl-certificates describe web-cert --global。
卡在 FAILED_NOT_VISIBLE 就是 DNS 沒設對。

七、進階路由：URL Map 的真正威力

多主機多路徑路由
# 建立多組後端後，用 YAML 定義複雜路由
cat > urlmap.yaml <<'YAML'
name: web-urlmap
defaultService: projects/PROJECT/global/backendServices/web-backend
hostRules:
  - hosts: ["api.example.com"]
    pathMatcher: api-matcher
  - hosts: ["*.example.com"]
    pathMatcher: web-matcher
pathMatchers:
  - name: api-matcher
    defaultService: projects/PROJECT/global/backendServices/api-backend
    pathRules:
      - paths: ["/v2/*"]
        service: projects/PROJECT/global/backendServices/api-v2-backend
  - name: web-matcher
    defaultService: projects/PROJECT/global/backendServices/web-backend
    pathRules:
      - paths: ["/static/*", "/assets/*"]
        service: projects/PROJECT/global/backendServices/gcs-backend
YAML

gcloud compute url-maps import web-urlmap --source=urlmap.yaml --global
實務提醒
靜態資源請一律導到 Cloud Storage 後端桶（backend bucket）+ Cloud CDN。
圖片、CSS、JS 由 CDN 邊緣節點直接回應，完全不打到你的 VM。這通常能砍掉 60～80% 的後端負載，而且使用者體感速度差很多。

八、Cloud Armor：LB 上的防火牆

bash
# 建立安全政策
gcloud compute security-policies create web-armor \
  --description="網站防護政策"

# 擋掉特定國家（規則優先度數字小的先執行）
gcloud compute security-policies rules create 1000 \
  --security-policy=web-armor \
  --expression="origin.region_code == 'XX'" \
  --action=deny-403

# 速率限制：每個 IP 每分鐘最多 100 次請求
gcloud compute security-policies rules create 2000 \
  --security-policy=web-armor \
  --src-ip-ranges="*" \
  --action=rate-based-ban \
  --rate-limit-threshold-count=100 \
  --rate-limit-threshold-interval-sec=60 \
  --ban-duration-sec=600 \
  --conform-action=allow --exceed-action=deny-429 \
  --enforce-on-key=IP

# 啟用 OWASP Top 10 防護（SQL Injection）
gcloud compute security-policies rules create 3000 \
  --security-policy=web-armor \
  --expression="evaluatePreconfiguredExpr('sqli-v33-stable')" \
  --action=deny-403

# 套用到 Backend Service
gcloud compute backend-services update web-backend \
  --security-policy=web-armor --global

十、本課檢核

  • 能說出 Application LB 的五層元件與順序
  • 知道健康檢查的來源網段要開防火牆（130.211.0.0/22, 35.191.0.0/16）
  • 知道 GCP 全域 LB 用的是 Anycast IP
  • 會用 URL Map 做路徑與主機分流
  • 知道靜態資源該掛 backend bucket + CDN

自我檢測

建好 LB 後所有後端都顯示 UNHEALTHY，機器本身用外部 IP 直連卻正常。最可能的原因？
沒有開放健康檢查探測器的來源網段：130.211.0.0/22 和 35.191.0.0/16。
這兩個網段是 Google 健康檢查系統的固定來源。你開的 0.0.0.0/0 規則若綁的 target tag 跟機器不符，健康檢查一樣進不來。
其他要檢查的：① 具名連接埠（named port）有沒有設；② 健康檢查的 request path 是否真的回 200（有些應用根路徑會 302 導向）。
台灣公司的服務，使用者也都在台灣。還需要用「全域」LB 嗎？
需要，而且成本差異很小。三個理由：
① 全域 LB 用 Anycast IP，使用者從離自己最近的 Google 邊緣節點進入，之後走 Google 私有骨幹——即使後端只在彰化，這樣的路徑通常比走公網更快更穩。
② 只有全域 Application LB 支援 Cloud CDN 和 Cloud Armor。
③ 未來要拓展海外時，架構不用重做。
反例：如果你需要保留客戶端來源 IP 且要求極低延遲（例如遊戲伺服器），才選 Regional Passthrough Network LB。
使用者反映「登入後過一下就被登出」，服務跑在 5 台機器的 MIG 後面。診斷與解法？
Session 狀態存在單台機器的記憶體裡，但 LB 把後續請求送到別台，那台不認得這個 session。

兩種解法，優劣分明：
❌ 短期繞過：開啟 Session Affinity（--session-affinity=CLIENT_IP），讓同一個 IP 固定送同一台。但這會破壞負載均衡、且該機器掛掉時使用者仍會被登出。
✅ 正確解法：把 session 外部化，存到 Memorystore（Redis）。這樣任何一台機器都能處理任何請求，機器變成真正的無狀態。
這題的本質是：Session Affinity 是在幫有狀態的設計打補丁，不是解決方案。
