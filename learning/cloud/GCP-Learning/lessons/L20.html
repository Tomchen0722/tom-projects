LESSON 20

Spanner 與 Bigtable：Google 的兩把重武器

這兩個服務是 Google 內部撐起搜尋、YouTube、Gmail 的基礎設施。你不一定會用到，但理解它們能讓你在架構討論中判斷「什麼時候需要」。

閱讀 20 分進階

一、Spanner：既是 SQL 又能無限擴充

傳統上你必須二選一：關聯式資料庫（有 SQL 和交易，但難以水平擴充） vs NoSQL（能擴充，但沒有交易與 SQL）。Spanner 打破了這個取捨。

特性說明
水平無限擴充自動分片，從 1 個節點擴到數千個，不用改應用程式
強一致性 + ACID 交易而且是跨區域的。這是 Spanner 最獨特的地方
標準 SQL支援 GoogleSQL 與 PostgreSQL 方言
99.999% SLA多區域配置，每年停機 < 5.3 分鐘
TrueTime用原子鐘 + GPS 讓全球節點的時鐘誤差在幾毫秒內，這是全球強一致性的技術基礎
補充
TrueTime 是為什麼只有 Google 做得出 Spanner。分散式系統的核心難題是「兩個相隔萬里的節點怎麼知道誰的寫入先發生」。Google 在每個資料中心裝了原子鐘和 GPS 接收器，把時鐘不確定性壓到幾毫秒，然後讓交易等待這個不確定區間過去再提交。
這是硬體投資買來的能力，不是軟體技巧。
bash
gcloud spanner instances create prod-spanner \
  --config=regional-asia-east1 \
  --processing-units=100 \
  --description="正式環境"

gcloud spanner databases create appdb --instance=prod-spanner \
  --ddl="CREATE TABLE Orders (
    OrderId STRING(36) NOT NULL,
    CustomerId STRING(36) NOT NULL,
    Amount NUMERIC,
    CreatedAt TIMESTAMP OPTIONS (allow_commit_timestamp=true),
  ) PRIMARY KEY (OrderId)"
小心踩雷
Spanner 很貴。最小單位 100 processing units 約每月 $65，但實務上正式環境至少要 1000 PU（約 $650/月），多區域配置會更高。
準則：除非你確定需要「全球強一致 + 無限擴充」，否則 Cloud SQL 便宜太多。不要為了「以後可能會很大」而現在就上 Spanner。

Spanner 的設計重點：主鍵選擇

小心踩雷
不要用單調遞增的主鍵（如自動遞增 ID 或時間戳）。
Spanner 依主鍵範圍分片，遞增主鍵會讓所有寫入集中到最後一個分片——這叫熱點（hotspot），會讓你付了 1000 個節點的錢卻只有 1 個節點在工作。

正確做法：
• 用 UUID 當主鍵；
• 或把雜湊值放在主鍵前面：PRIMARY KEY (ShardId, Timestamp)，其中 ShardId = hash(id) % 100。

二、Bigtable：極致的吞吐量

Bigtable 是寬欄位（wide-column）資料庫。它放棄了 SQL、JOIN、交易，換來的是單一叢集每秒數百萬次操作、單表 PB 級的能力。

Bigtable 資料模型
Bigtable 的資料模型

Row Key（唯一，且是唯一的索引！）
  └── Column Family（欄位族，建表時定義）
        └── Column Qualifier（欄位名，可動態新增）
              └── Cell（值 + 時間戳，可保留多版本）

範例：IoT 感測器資料
Row Key: "sensor#00123#9223370554-1234567"   ← 裝置ID + 反轉時間戳
  cf_data:temperature  → 25.3
  cf_data:humidity     → 62
  cf_meta:firmware     → "v2.1.0"

Row Key 設計是 Bigtable 的一切。因為它是唯一的索引，查詢只能靠：① 單一 row key 精準查；② row key 範圍掃描。

需求Row Key 設計理由
查某裝置的時間序列裝置ID#時間戳範圍掃描同一裝置的連續資料
查最新資料優先裝置ID#(Long.MAX - 時間戳)反轉時間戳讓最新的排在前面
避免熱點hash(裝置ID)前2碼#裝置ID#時間戳把寫入分散到不同分片
❌ 錯誤示範時間戳#裝置ID所有寫入集中在同一個分片，效能崩潰

三、決策：什麼時候用哪個

資料庫決策樹
你的資料庫需求是什麼？

├─ 資料量 < 10TB，需要 SQL 與交易
│    → Cloud SQL          ← 90% 的專案在這裡
│
├─ 需要 SQL + 交易，但單區域資料庫已經撐不住
│    → 先試 AlloyDB（相容 PostgreSQL，效能高 4 倍）
│    → 再考慮 Spanner
│
├─ 需要全球多地同時讀寫，且要強一致性
│    → Spanner              ← 金融核心、全球遊戲帳號系統
│
├─ 每秒數十萬次以上的簡單讀寫，查詢模式單純
│    → Bigtable             ← IoT、廣告投放、金融行情、監控指標
│
├─ 行動 App 後端，需要即時同步與離線
│    → Firestore
│
└─ 分析、報表、資料倉儲
     → BigQuery

四、AlloyDB：常被忽略的中間選項

AlloyDB 是 GCP 較新的 PostgreSQL 相容資料庫，定位在 Cloud SQL 與 Spanner 之間：

  • 100% PostgreSQL 相容——現有應用不用改程式碼
  • 交易處理效能比標準 PostgreSQL 快約 4 倍，分析查詢快 100 倍（有欄式引擎加速）
  • 讀取節點可獨立擴充到 15 個，跨區可用
  • 適合：Cloud SQL 已經吃力，但還不需要 Spanner 的全球一致性

五、本課檢核

  • 知道 Spanner 的獨特價值是「全球強一致 + 水平擴充」
  • 理解 Spanner 與 Bigtable 都會因主鍵設計不當產生熱點
  • 知道 Bigtable 的 row key 是唯一索引，決定所有查詢能力
  • 知道 AlloyDB 是 Cloud SQL 與 Spanner 之間的選項
  • 能用決策樹選出正確的資料庫

自我檢測

架構師提議「我們用 Spanner，因為未來會全球化」。目前是台灣單一市場、日活 5 萬。你的意見？
現在上 Spanner 是過早最佳化，代價很具體。

成本對比：Cloud SQL（4 核 16GB + HA）約 $400/月；Spanner 正式規格至少 $650/月起，多區域配置 $2000+/月。日活 5 萬用 Cloud SQL 綽綽有餘。

但更重要的是隱形成本：Spanner 的 schema 設計、主鍵策略、交易模式都跟 PostgreSQL 不同，團隊要重新學；生態系工具（ORM、遷移工具、監控）也少得多。

務實建議：
① 現在用 Cloud SQL，但從一開始就避免使用 PostgreSQL 特有的功能，保持 SQL 的可攜性。
② 主鍵用 UUID 而非自動遞增——這樣未來遷移到 Spanner 時不會踩熱點問題。
③ 訂一個明確的觸發條件：例如「當寫入 QPS 持續超過 5000，或需要在三個以上國家同時寫入時，重新評估」。

保留未來的選項 ≠ 現在就付出代價。
Bigtable 叢集有 10 個節點，但監控顯示只有 1 個節點的 CPU 很高，其他都閒置。原因？
典型的 row key 熱點。幾乎確定是主鍵用了單調遞增的值——最常見的是 時間戳 開頭，或流水號 ID。

Bigtable 依 row key 的字典順序把資料切成連續的區塊（tablet）分給不同節點。如果所有新資料的 key 都是「現在時間」，它們全部落在同一個 tablet，只有負責那個 tablet 的節點在工作。

解法（需要重新設計 row key 並遷移資料）：
• 加雜湊前綴：{hash(id)%100:02d}#{原本的key}，把寫入均勻分散到 100 個範圍。
• 欄位順序調換：從 時間#裝置ID 改成 裝置ID#時間。
• 反轉時間戳：如果要最新資料優先。

用 Key Visualizer 工具（Console 內建）可以直接看到熱點圖，紅色區塊就是問題所在。
金融公司要做「全球都能即時查詢與交易的帳戶餘額系統」，跨美國、歐洲、亞洲。技術選型？
這正是 Spanner 為之而生的場景。需求拆解：
• 全球即時 → 需要多區域部署
• 帳戶餘額 → 需要 ACID 交易與強一致性（絕不能有兩個地方同時扣款）
• 金融 → 需要極高可用性與稽核

配置建議：
• --config=nam-eur-asia1（多區域，99.999% SLA）
• 主鍵用 hash(AccountId)#AccountId 避免熱點
• 用 交錯表（interleaved table） 把交易明細與帳戶存在一起，讓 JOIN 在同一分片內完成
• 開啟 Change Streams 串接稽核與風控系統

其他選項為什麼不行：
• Cloud SQL —— 無法多地同時寫入，跨區複製是非同步的，會有資料不一致
• Bigtable —— 沒有跨列交易，無法保證扣款與入帳的原子性
• Firestore —— 交易能力有限，且不適合高頻寫入

這題的關鍵字是「強一致性」。一旦出現這四個字，多數情況答案就是 Spanner。
