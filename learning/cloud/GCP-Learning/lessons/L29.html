LESSON 29

資料管線：Pub/Sub 與 Dataflow

企業資料很少是靜態的——它從各處不斷流入，需要清洗、轉換、分流。這一課建立一條可以承受每秒數十萬筆訊息的資料管線。

操作 45 分實作

一、Pub/Sub：系統之間的緩衝墊

Pub/Sub 是訊息佇列。它解決一個核心問題：讓生產者和消費者互相解耦。

生活比喻
沒有訊息佇列：訂單系統直接呼叫庫存系統、通知系統、分析系統。
庫存系統掛了 → 訂單系統也失敗；新增一個消費者 → 要改訂單系統的程式碼。

有訊息佇列：訂單系統只管把訊息丟進 Pub/Sub。
庫存系統掛了 → 訊息留在佇列裡，等它恢復再處理；新增消費者 → 訂單系統完全不用改，新系統自己來訂閱。

這就像公司的收發室——寄件人不用知道收件人在不在座位上。
Pub/Sub 架構
Publisher（發布者）
   └─→ Topic（主題）
          ├─→ Subscription A ──→ Subscriber A（庫存系統）
          ├─→ Subscription B ──→ Subscriber B（通知系統）
          └─→ Subscription C ──→ Subscriber C（分析管線）

重點：每個 Subscription 都會收到「完整的一份」訊息
      同一個 Subscription 的多個消費者則是「分攤」訊息
動手實作

實作：建立訊息管線

  1. 建立主題與訂閱：
    bash
    gcloud pubsub topics create orders

# 拉取式訂閱（消費者主動拉）
gcloud pubsub subscriptions create orders-processor \
  --topic=orders \
  --ack-deadline=60 \
  --message-retention-duration=7d \
  --dead-letter-topic=orders-dlq \
  --max-delivery-attempts=5

# 死信主題（處理失敗的訊息會被丟到這裡）
gcloud pubsub topics create orders-dlq
gcloud pubsub subscriptions create orders-dlq-sub --topic=orders-dlq
  2. 發送與接收：
    bash
    gcloud pubsub topics publish orders \
  --message='{"order_id":"A001","amount":1200,"customer":"王小明"}' \
  --attribute=region=north,priority=high

gcloud pubsub subscriptions pull orders-processor --auto-ack --limit=5
  3. 推送式訂閱（Pub/Sub 主動打你的 HTTP 端點，搭配 Cloud Run 最方便）：
    bash
    gcloud pubsub subscriptions create orders-push \
  --topic=orders \
  --push-endpoint=https://task-api-xxxx.a.run.app/pubsub \
  --push-auth-service-account=pubsub-invoker@$PROJECT.iam.gserviceaccount.com
  4. 監控積壓（這是最重要的健康指標）：
    bash
    gcloud pubsub subscriptions describe orders-processor

# 用 Cloud Monitoring 查看未確認訊息數
gcloud monitoring time-series list \
  --filter='metric.type="pubsub.googleapis.com/subscription/num_undelivered_messages"'

二、訊息傳遞的四個關鍵觀念

觀念說明對你的影響
至少一次傳遞Pub/Sub 保證訊息至少送到一次，但可能送多次你的處理邏輯必須是冪等的
Ack 期限消費者要在期限內確認，否則訊息重新投遞處理慢的工作要延長期限或用 modifyAckDeadline
死信佇列重試 N 次仍失敗的訊息移到 DLQ必設，否則毒訊息會無限重試佔滿資源
訊息排序預設不保證順序需要順序要設 ordering key，但會降低吞吐量
小心踩雷
冪等性是使用訊息佇列的必修課。
「至少一次」意味著同一筆訂單訊息可能被處理兩次。如果你的邏輯是「扣庫存 -1」，重複處理就會扣兩次。

實作冪等的三種方式：
① 用訊息 ID 去重：處理前先查 Redis / 資料庫「這個 message_id 處理過嗎」。
② 用資料庫唯一約束：INSERT ... ON CONFLICT DO NOTHING。
③ 設計成冪等操作：「設定庫存 = 95」而非「庫存 -1」。這是最乾淨的做法。

三、Dataflow：託管的資料處理引擎

Dataflow 執行 Apache Beam 程式，最大的特色是同一份程式碼可以處理批次與串流。

Dataflow 串流管線
# 一個串流管線範例（Python）
import apache_beam as beam
from apache_beam.options.pipeline_options import PipelineOptions
import json

class ParseAndValidate(beam.DoFn):
    def process(self, element):
        try:
            data = json.loads(element.decode("utf-8"))
            if data.get("amount", 0) <= 0:
                yield beam.pvalue.TaggedOutput("invalid", element)
            else:
                data["processed_at"] = beam.window.TimestampedValue
                yield data
        except Exception:
            yield beam.pvalue.TaggedOutput("invalid", element)

options = PipelineOptions(
    streaming=True,
    project="my-project",
    region="asia-east1",
    runner="DataflowRunner",
    temp_location="gs://my-bucket/temp",
    max_num_workers=10,
)

with beam.Pipeline(options=options) as p:
    results = (
        p
        | "讀取 Pub/Sub" >> beam.io.ReadFromPubSub(
              subscription="projects/PROJ/subscriptions/orders-processor")
        | "解析驗證" >> beam.ParDo(ParseAndValidate()).with_outputs("invalid", main="valid")
    )

    # 有效資料寫進 BigQuery
    (results.valid
        | "寫入 BQ" >> beam.io.WriteToBigQuery(
              "PROJ:dataset.orders",
              schema="order_id:STRING,amount:NUMERIC,customer:STRING",
              write_disposition=beam.io.BigQueryDisposition.WRITE_APPEND))

    # 無效資料存到 GCS 供事後檢查
    (results.invalid
        | "寫入錯誤桶" >> beam.io.WriteToText("gs://my-bucket/errors/invalid"))

    # 同時做 5 分鐘視窗聚合，寫進即時儀表板用的表
    (results.valid
        | "開視窗" >> beam.WindowInto(beam.window.FixedWindows(300))
        | "取金額" >> beam.Map(lambda x: (x["region"], x["amount"]))
        | "加總" >> beam.CombinePerKey(sum)
        | "寫入即時表" >> beam.io.WriteToBigQuery("PROJ:dataset.realtime_revenue"))

四、視窗（Windowing）：串流資料的時間切片

串流資料是無限的，要做聚合就必須先切成有限的片段。這是串流處理最核心的觀念。

視窗類型說明範例用途
固定視窗 Fixed不重疊的等長區間每 5 分鐘的訂單總額
滑動視窗 Sliding重疊的區間每分鐘計算「過去 10 分鐘」的移動平均
工作階段視窗 Session依活動間隔自動切分使用者一次瀏覽行為（30 分鐘無動作即結束）
全域視窗 Global不切批次處理
小心踩雷
遲到資料（late data）是串流處理最容易出錯的地方。
手機離線 30 分鐘後才把資料傳上來——這筆資料屬於半小時前的視窗，但那個視窗已經計算完並輸出了。

Beam 用 watermark（水位線） 與 trigger（觸發器） 處理這個問題：
bash
beam.WindowInto(
    beam.window.FixedWindows(300),
    trigger=beam.trigger.AfterWatermark(
        late=beam.trigger.AfterCount(1)),      # 遲到資料一來就重新輸出
    allowed_lateness=3600,                     # 容忍 1 小時的遲到
    accumulation_mode=beam.trigger.AccumulationMode.ACCUMULATING)

五、什麼時候不需要 Dataflow

Dataflow 很強，但也複雜且有固定成本（至少一台 worker 常駐）。輕量場景有更簡單的選擇：

需求更簡單的方案
Pub/Sub → BigQuery，不需轉換Pub/Sub BigQuery 訂閱（原生功能，零程式碼）
Pub/Sub → GCSPub/Sub Cloud Storage 訂閱
簡單的事件處理Cloud Run + Pub/Sub 推送訂閱
定時的批次 ETLBigQuery 排程查詢 或 Dataform
現成的常見管線Dataflow 範本（Google 提供數十種，不用寫程式）
bash
# 零程式碼：Pub/Sub 直接寫入 BigQuery
gcloud pubsub subscriptions create orders-to-bq \
  --topic=orders \
  --bigquery-table=PROJECT:dataset.orders \
  --use-table-schema \
  --dead-letter-topic=orders-dlq
實務提醒
先問「能不能不寫程式」。Dataflow 管線寫起來容易，維護起來昂貴——你要管版本、管相依套件、管 worker 規模、管管線更新時的狀態遷移。
如果 Pub/Sub 的原生 BigQuery 訂閱就能解決，那就是更好的答案。

自我檢測

訂單處理系統偶爾會重複扣款。訊息來自 Pub/Sub。原因與解法？
Pub/Sub 的「至少一次」語意 + 非冪等的處理邏輯。

重複投遞的常見觸發原因：
• 消費者處理超過 ack deadline，Pub/Sub 認為失敗而重送（但你的第一次處理其實成功了）
• 消費者處理完但 ack 之前崩潰
• Pub/Sub 內部的重試機制

解法（按可靠度排序）：
① 資料庫唯一約束——最可靠。在 transactions 表對 message_id 建唯一索引，重複插入會失敗，直接 ack 跳過。這個方法即使在分散式環境也絕對正確。
② 冪等的業務設計——用「設定餘額為 X」取代「扣款 Y」。
③ Redis 去重——快但有邊界情況（Redis 掛掉、TTL 過期）。

另外要調整：如果重複的根因是處理太慢，延長 --ack-deadline 或在處理過程中呼叫 modifyAckDeadline 續期。
Pub/Sub 訂閱的未確認訊息數持續上升，從 100 漲到 50 萬。怎麼處理？
消費速度跟不上生產速度。先止血，再治本。

立即處置：
① 擴充消費者——Cloud Run 調高 max-instances，或 MIG 依 num_undelivered_messages 自動擴充（第 8 課教過）。
② 確認不是毒訊息造成的——如果某筆訊息一直處理失敗並重試，會拖慢整體。檢查 DLQ 有沒有訊息，看錯誤日誌。

診斷根因：
• 消費者的處理邏輯變慢了嗎？（例如下游資料庫變慢）
• 生產量突然暴增嗎？（活動、爬蟲、上游 bug）
• 消費者有沒有異常重啟？

長期改善：
• 設定 告警：積壓數 > 10000 或訊息最舊年齡 > 5 分鐘就通知。50 萬才發現表示監控缺失。
• 加大 批次處理：一次拉 1000 筆一起寫入，而非一筆一筆。
• 檢查是否該用 Dataflow 取代自寫消費者——它的擴充能力好得多。
團隊要做「即時營收儀表板」，資料從各門市 POS 傳來。你會怎麼設計？
先問一個問題：「即時」到底是多即時？這決定了架構複雜度與成本，差距可以是 10 倍。

方案 A：分鐘級延遲（推薦起點）
POS → Pub/Sub → BigQuery 訂閱（零程式碼）→ Looker Studio（每 1 分鐘刷新）
優點：幾乎沒有維運成本、當天就能上線、費用極低。90% 的「即時儀表板」需求這樣就滿足了。

方案 B：秒級延遲
POS → Pub/Sub → Dataflow（開視窗聚合）→ BigQuery + Bigtable → 自製前端
需要時才做，成本與複雜度高一個量級。

共通的必要設計：
• 離線緩衝——門市網路會斷，POS 端要能暫存並補傳。
• 冪等處理——補傳會造成重複，用交易編號去重。
• 資料驗證——POS 可能送出格式錯誤的資料，要有 DLQ 收容並告警。
• 時區處理——用 UTC 儲存，顯示時才轉換。

我的建議：先做方案 A 上線，實際觀察業務方是不是真的需要秒級。多數情況他們說「即時」的意思是「不要等到隔天」。
