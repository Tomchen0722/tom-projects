LESSON 08

執行個體群組與自動擴充

一台機器會壞、會不夠用。這一課讓你從「養寵物」升級到「管牛群」——機器變成可拋棄、可複製、能隨流量自動增減的單位。

操作 45 分約 0.3 美元實作

一、寵物與牛群：心態的轉變

生活比喻
寵物（Pet）：你幫它取名叫「小白」，生病了帶去看醫生，細心照料。這是傳統的伺服器管理——一台機器出問題，你 SSH 進去修。

牛群（Cattle）：編號 #0042，生病了就淘汰，補一頭新的進來。這是雲端原生的做法。

自動擴充的前提是你的機器必須是牛，不是寵物。如果某台機器上有別台沒有的設定或資料，它就不能被隨意替換。這就是為什麼無狀態（stateless）設計是雲端架構的基本要求。

二、三個組件：範本、群組、健康檢查

三個組件的關係
Instance Template（範本）
   「機器的設計圖」— 機型、映像、磁碟、開機腳本、標籤
        ↓ 依照範本產生
Managed Instance Group / MIG（受管執行個體群組）
   「一群一模一樣的機器」— 負責維持數量、自動修復、滾動更新
        ↓ 依據
Autoscaler + Health Check（自動擴充器 + 健康檢查）
   「什麼時候該加機器、什麼時候該砍、哪台壞了」

三、實作：建立一個會自動擴充的網頁服務

動手實作

實作 1：從範本到自動擴充

  1. 建立執行個體範本。注意開機腳本讓每台機器顯示自己的主機名稱，方便等一下驗證：
    bash
    gcloud compute instance-templates create web-template-v1 \
  --machine-type=e2-small \
  --image-family=debian-12 --image-project=debian-cloud \
  --tags=http-server \
  --labels=env=lab,app=web \
  --metadata=startup-script='#!/bin/bash
apt update -y && apt install -y nginx stress-ng
NAME=$(curl -s -H "Metadata-Flavor: Google" \
  http://metadata.google.internal/computeMetadata/v1/instance/name)
ZONE=$(curl -s -H "Metadata-Flavor: Google" \
  http://metadata.google.internal/computeMetadata/v1/instance/zone | cut -d/ -f4)
cat > /var/www/html/index.html <<HTML
<h1>Server: $NAME</h1><p>Zone: $ZONE</p>
HTML
systemctl restart nginx'
  2. 建立健康檢查。這決定「什麼叫做這台機器是活的」：
    bash
    gcloud compute health-checks create http web-hc \
  --port=80 --request-path=/ \
  --check-interval=10s \
  --timeout=5s \
  --healthy-threshold=2 \
  --unhealthy-threshold=3
  3. 建立受管執行個體群組（跨 3 個 Zone，這是高可用的關鍵）：
    bash
    gcloud compute instance-groups managed create web-mig \
  --template=web-template-v1 \
  --size=2 \
  --region=asia-east1 \
  --health-check=web-hc \
  --initial-delay=90

# 設定分散在哪些 zone
gcloud compute instance-groups managed update web-mig \
  --region=asia-east1 \
  --target-distribution-shape=EVEN
  4. 設定自動擴充規則：
    bash
    gcloud compute instance-groups managed set-autoscaling web-mig \
  --region=asia-east1 \
  --min-num-replicas=2 \
  --max-num-replicas=6 \
  --target-cpu-utilization=0.60 \
  --cool-down-period=90
  5. 確認機器都起來了（可能要等 1～2 分鐘）：
    bash
    gcloud compute instance-groups managed list-instances web-mig --region=asia-east1
  6. 驗證自動修復：手動刪掉其中一台，觀察 MIG 自動補一台回來。
    bash
    # 挑一台刪掉
NAME=$(gcloud compute instance-groups managed list-instances web-mig \
  --region=asia-east1 --format="value(instance)" | head -1 | xargs basename)
gcloud compute instances delete $NAME --zone=asia-east1-b --quiet

# 過 1 分鐘再看，數量會回到 2
gcloud compute instance-groups managed list-instances web-mig --region=asia-east1
  7. 驗證自動擴充：SSH 進一台機器製造 CPU 負載，觀察機器數量增加。
    bash
    # 在 VM 內
sudo stress-ng --cpu 2 --timeout 600s

# 從 Cloud Shell 觀察（約 2~4 分鐘後會開始長）
watch -n 20 'gcloud compute instance-groups managed list-instances web-mig --region=asia-east1'

四、Zonal MIG vs Regional MIG

Zonal MIGRegional MIG
機器分布全部在同一個 Zone自動分散到 Region 內多個 Zone
Zone 故障時全部掛掉其他 Zone 的機器繼續服務
設定方式--zone=asia-east1-b--region=asia-east1
建議僅測試用正式環境一律用這個
實務提醒
Regional MIG 幾乎沒有額外成本，卻直接把可用性從「單一機房」提升到「多機房」。正式環境沒有理由用 Zonal MIG。這是最划算的可用性投資。

五、擴充的四種觸發指標

  • CPU 使用率：最常用，適合運算密集型。--target-cpu-utilization=0.6
  • 負載平衡器容量：依每台機器承受的請求數擴充，比 CPU 更貼近使用者體驗。--target-load-balancing-utilization
  • Cloud Monitoring 自訂指標：例如「佇列長度」。對非同步工作系統，這是唯一正確的指標——CPU 可能很閒但任務堆積如山。
  • 排程式擴充：已知的尖峰（例如每天 9 點上班、雙十一）預先加機器，不用等指標飆升才反應。
bash
# 依佇列長度擴充（每台機器負責 100 則訊息）
gcloud compute instance-groups managed set-autoscaling worker-mig \
  --region=asia-east1 --min-num-replicas=1 --max-num-replicas=50 \
  --update-stackdriver-metric=pubsub.googleapis.com/subscription/num_undelivered_messages \
  --stackdriver-metric-filter='resource.type="pubsub_subscription" AND resource.label.subscription_id="jobs-sub"' \
  --stackdriver-metric-single-instance-assignment=100

# 排程式擴充：週一到週五 08:30 預先擴到 10 台
gcloud compute instance-groups managed update-autoscaling web-mig \
  --region=asia-east1 \
  --set-schedule=morning-peak \
  --schedule-cron='30 8 * * 1-5' \
  --schedule-duration-sec=39600 \
  --schedule-min-required-replicas=10
小心踩雷
自動擴充最常見的兩個失敗模式：
① 擴充風暴（thrashing）：機器剛開起來還在初始化，CPU 就被算進平均值，導致又擴又縮。解法是把 --cool-down-period 設成大於機器完整啟動所需時間。
② 擴充追不上流量：從偵測到指標、開機、裝軟體、通過健康檢查，可能要 3～5 分鐘，而流量尖峰 30 秒就到了。解法是把軟體烤進自訂映像縮短開機時間，加上排程式預先擴充。

六、滾動更新：不停機換版本

bash
# 1. 建立新版本範本
gcloud compute instance-templates create web-template-v2 \
  --machine-type=e2-small --image-family=debian-12 --image-project=debian-cloud \
  --tags=http-server --metadata-from-file=startup-script=startup-v2.sh

# 2. 滾動更新（一次替換一台，永遠保持服務量）
gcloud compute instance-groups managed rolling-action start-update web-mig \
  --region=asia-east1 \
  --version=template=web-template-v2 \
  --max-surge=1 \          # 允許暫時多開 1 台
  --max-unavailable=0       # 不允許任何一台下線 → 零停機

# 3. 出問題？回滾就是換回舊範本
gcloud compute instance-groups managed rolling-action start-update web-mig \
  --region=asia-east1 --version=template=web-template-v1

# 進階：金絲雀部署（只讓 20% 流量跑新版）
gcloud compute instance-groups managed set-instance-template web-mig \
  --region=asia-east1 --template=web-template-v1
gcloud compute instance-groups managed rolling-action start-update web-mig \
  --region=asia-east1 \
  --version=template=web-template-v1 \
  --canary-version=template=web-template-v2,target-size=20%

七、清理

bash
gcloud compute instance-groups managed delete web-mig --region=asia-east1 --quiet
gcloud compute instance-templates delete web-template-v1 web-template-v2 --quiet
gcloud compute health-checks delete web-hc --quiet

八、本課檢核

  • 理解無狀態設計為什麼是自動擴充的前提
  • 能建立 範本 → MIG → 自動擴充 的完整鏈路
  • 知道正式環境要用 Regional MIG
  • 能為非同步工作系統選對擴充指標（佇列長度而非 CPU）
  • 會用 rolling update 做零停機部署與回滾

自我檢測

你的 MIG 一直在 2 台和 5 台之間反覆震盪，服務不穩。原因與解法？
典型的擴充風暴。新機器啟動期間 CPU 衝到 100%（安裝套件），被算進群組平均值，觸發再擴充；等安裝完成 CPU 掉下來，又觸發縮減。
三個解法一起上：
① 拉長 --cool-down-period 到大於完整啟動時間（例如 180 秒）。
② 設定 --initial-delay，讓新機器在初始化期間不被計入指標。
③ 把套件烤進自訂映像，讓啟動時間從 3 分鐘降到 30 秒——這是治本的做法。
一個影片轉檔服務，任務進 Pub/Sub 佇列，每個任務要跑 20 分鐘。為什麼不該用 CPU 擴充？
因為 CPU 使用率無法反映「還有多少事沒做」。
如果目前 2 台機器都在 100% 忙碌，佇列裡積了 5000 個任務，CPU 指標會說「滿載了，該擴充」——這沒錯，但它不知道要擴多少台。反之如果任務是 I/O 密集，CPU 可能只有 20%，指標會叫你縮減，但佇列還在堆積。
正確做法是用 num_undelivered_messages，設定「每台機器負責 N 則訊息」，這樣佇列長度直接線性對應機器數。
另外要注意：長任務要設定 --instance-redistribution-type=NONE 或改用 Cloud Run Jobs，避免縮減時砍掉正在跑的機器。
Regional MIG 設定 min=3，asia-east1 有 3 個 Zone。某個 Zone 完全故障時會發生什麼？
MIG 偵測到該 Zone 的機器失聯，會在剩餘的健康 Zone 補足到 3 台（變成一個 Zone 1 台、另一個 Zone 2 台）。
但有兩個現實限制要注意：
① 補機需要時間（開機 + 健康檢查，約 2～5 分鐘），這段期間容量是不足的。
② 剩餘 Zone 要有足夠配額與實體容量。大規模 Zone 故障時，其他 Zone 可能也擠爆。
所以關鍵服務的 min 值要設在「少一個 Zone 也還撐得住」的水位，而不是剛好夠用。這叫做 N+1 容量規劃。
