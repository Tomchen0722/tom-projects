LESSON 27

CI/CD：Cloud Build 與自動部署

手動部署遲早會出事。這一課建立一條「推程式碼 → 自動測試 → 自動建置 → 自動部署」的流水線，並加上必要的品質關卡。

操作 50 分實作

一、CI/CD 到底在自動化什麼

完整流水線
開發者 git push
      ↓
CI（持續整合）—— 每次提交都驗證
      ├── 靜態檢查（lint、型別檢查）
      ├── 單元測試
      ├── 建置容器映像
      ├── 漏洞掃描
      └── 推送到 Artifact Registry
      ↓
CD（持續部署）—— 自動送到環境
      ├── 部署到 staging
      ├── 整合測試 / 冒煙測試
      ├── ★ 人工核准關卡（正式環境）
      ├── 金絲雀部署（10% 流量）
      ├── 監控錯誤率與延遲
      └── 全量部署 或 自動回滾

二、Cloud Build 的設定檔

cloudbuild.yaml
# cloudbuild.yaml
steps:
# ① 執行測試
- name: 'python:3.12-slim'
  id: 'test'
  entrypoint: 'bash'
  args:
    - '-c'
    - |
      pip install -r requirements.txt -q
      pip install pytest ruff -q
      ruff check .
      pytest -v --tb=short

# ② 建置映像（用前一版當快取，加速建置）
- name: 'gcr.io/cloud-builders/docker'
  id: 'build'
  args:
    - 'build'
    - '--cache-from=$_REPO/$_SERVICE:latest'
    - '-t=$_REPO/$_SERVICE:$SHORT_SHA'
    - '-t=$_REPO/$_SERVICE:latest'
    - '.'

# ③ 推送
- name: 'gcr.io/cloud-builders/docker'
  id: 'push'
  args: ['push', '--all-tags', '$_REPO/$_SERVICE']

# ④ 等待漏洞掃描並檢查結果
- name: 'gcr.io/cloud-builders/gcloud'
  id: 'scan-check'
  entrypoint: 'bash'
  args:
    - '-c'
    - |
      sleep 30
      CRITICAL=$(gcloud artifacts docker images describe \
        $_REPO/$_SERVICE:$SHORT_SHA --show-package-vulnerability \
        --format="value(package_vulnerability_summary.vulnerabilities.CRITICAL)" || echo 0)
      if [ "${CRITICAL:-0}" -gt 0 ]; then
        echo "❌ 發現 $CRITICAL 個 CRITICAL 漏洞"
        exit 1
      fi

# ⑤ 部署到 Cloud Run（不給流量）
- name: 'gcr.io/cloud-builders/gcloud'
  id: 'deploy'
  args:
    - 'run'
    - 'deploy'
    - '$_SERVICE'
    - '--image=$_REPO/$_SERVICE:$SHORT_SHA'
    - '--region=$_REGION'
    - '--no-traffic'
    - '--tag=sha-$SHORT_SHA'

# ⑥ 冒煙測試
- name: 'gcr.io/cloud-builders/curl'
  id: 'smoke-test'
  entrypoint: 'bash'
  args:
    - '-c'
    - |
      URL=$(gcloud run services describe $_SERVICE --region=$_REGION \
        --format="value(status.traffic[0].url)")
      curl -f "$URL/healthz" || exit 1

# ⑦ 切 10% 流量做金絲雀
- name: 'gcr.io/cloud-builders/gcloud'
  id: 'canary'
  args:
    - 'run'
    - 'services'
    - 'update-traffic'
    - '$_SERVICE'
    - '--region=$_REGION'
    - '--to-tags=sha-$SHORT_SHA=10'

substitutions:
  _REGION: 'asia-east1'
  _SERVICE: 'task-api'
  _REPO: 'asia-east1-docker.pkg.dev/${PROJECT_ID}/my-apps'

options:
  logging: CLOUD_LOGGING_ONLY
  machineType: 'E2_HIGHCPU_8'

timeout: '1200s'
動手實作

實作：連接 GitHub 並設定觸發器

  1. 把程式碼推上 GitHub（或用 Cloud Source Repositories）。
  2. 在 Console 進入 Cloud Build → 觸發條件 → 連接存放區，授權 GitHub 並選擇儲存庫。
  3. 或用指令建立觸發器：
    bash
    gcloud builds triggers create github \
  --name=deploy-on-main \
  --repo-owner=YOUR_GITHUB_USER \
  --repo-name=task-api \
  --branch-pattern="^main$" \
  --build-config=cloudbuild.yaml \
  --substitutions=_SERVICE=task-api,_REGION=asia-east1

# PR 觸發器：只跑測試不部署
gcloud builds triggers create github \
  --name=test-on-pr \
  --repo-owner=YOUR_GITHUB_USER --repo-name=task-api \
  --pull-request-pattern=".*" \
  --build-config=cloudbuild-test.yaml
  4. 授予 Cloud Build 服務帳號部署權限（這一步常被忘記，會導致部署失敗）：
    bash
    PROJECT_NUMBER=$(gcloud projects describe $PROJECT --format="value(projectNumber)")
CB_SA="$PROJECT_NUMBER@cloudbuild.gserviceaccount.com"

gcloud projects add-iam-policy-binding $PROJECT \
  --member="serviceAccount:$CB_SA" --role="roles/run.admin"
gcloud projects add-iam-policy-binding $PROJECT \
  --member="serviceAccount:$CB_SA" --role="roles/iam.serviceAccountUser"
  5. 推一個 commit 測試：
    bash
    git commit --allow-empty -m "test: 觸發 CI/CD"
git push origin main

gcloud builds list --limit=5
gcloud builds log $(gcloud builds list --limit=1 --format="value(id)")

三、部署策略比較

策略作法風險回滾速度適合
重建 Recreate關掉舊的再開新的有停機慢dev 環境
滾動 Rolling逐批替換中（新舊版本並存）中大多數服務
藍綠 Blue-Green兩套環境，一次全切低極快（切回去即可）關鍵服務，但成本 ×2
金絲雀 Canary先給少量流量，觀察後擴大最低快正式環境最佳實務
實務提醒
金絲雀部署的關鍵不是「切 10% 流量」，而是「觀察什麼指標、多久、什麼條件回滾」。
沒有明確的判斷標準，金絲雀就只是「慢一點的全量部署」。

建議的判斷標準：觀察 15 分鐘，若新版本的 5xx 錯誤率 高於舊版 0.5 個百分點，或 P95 延遲 高於舊版 20%，自動回滾。

四、加入人工核准關卡

bash
# 正式環境部署前需要人工核准
gcloud builds triggers create github \
  --name=deploy-prod \
  --repo-owner=USER --repo-name=task-api \
  --tag-pattern="^v.*" \
  --build-config=cloudbuild-prod.yaml \
  --require-approval

# 核准者需要 roles/cloudbuild.builds.approver 角色
gcloud projects add-iam-policy-binding $PROJECT \
  --member="group:release-managers@corp.com" \
  --role="roles/cloudbuild.builds.approver"

五、Cloud Deploy：更完整的發布管線

Cloud Build 適合 CI，但多環境的漸進式發布用 Cloud Deploy 更合適——它原生支援環境推進、核准、自動回滾。

bash
# clouddeploy.yaml
apiVersion: deploy.cloud.google.com/v1
kind: DeliveryPipeline
metadata:
  name: task-api-pipeline
serialPipeline:
  stages:
  - targetId: dev
    profiles: [dev]
  - targetId: staging
    profiles: [staging]
    strategy:
      canary:
        runtimeConfig:
          cloudRun: {automaticTrafficControl: true}
        canaryDeployment:
          percentages: [25, 50]
  - targetId: prod
    profiles: [prod]
    strategy:
      canary:
        canaryDeployment:
          percentages: [5, 25, 50]
          verify: true
---
apiVersion: deploy.cloud.google.com/v1
kind: Target
metadata: {name: prod}
requireApproval: true          # 進 prod 需要核准
run: {location: projects/PROJ/locations/asia-east1}

六、CI/CD 的六個實務原則

  1. 建置一次，到處部署。同一個映像從 dev 一路推到 prod，只有設定不同。絕不為不同環境重新建置——那樣就無法保證測過的東西跟上線的東西一樣。
  2. 快速失敗。把最快的檢查（lint、型別）放最前面。測試跑 20 分鐘才發現拼字錯誤是浪費。
  3. 流水線要在 10 分鐘內完成。超過這個時間開發者會開始繞過它。
  4. 每個部署都要可回滾。不只是技術上可以，而是有人演練過、知道怎麼做、且指令寫在 runbook 裡。
  5. 資料庫遷移要向後相容。新版程式要能配舊 schema 跑，舊版程式要能配新 schema 跑——否則回滾時資料庫會爆。
  6. 把部署變成無聊的事。如果每次部署都讓人緊張，那是流程有問題，不是人的問題。

七、本課檢核

  • 能寫出一份含測試、建置、掃描、部署的 cloudbuild.yaml
  • 知道要授予 Cloud Build 服務帳號部署權限
  • 能說出四種部署策略的取捨
  • 理解「建置一次、到處部署」的原則
  • 知道資料庫遷移需要向後相容

自我檢測

你的 CI 流水線要跑 35 分鐘，團隊開始手動部署繞過它。怎麼改善？
先承認問題的本質：35 分鐘的流水線是壞掉的工具，開發者繞過它是理性反應。

優化手段（按效果排序）：
① 平行化——Cloud Build 的 step 可以用 waitFor: ['-'] 讓不相依的步驟同時跑。lint、單元測試、建置常常可以並行。
② 善用快取——--cache-from 重用上一版映像層；依賴套件的安裝層獨立出來。這通常能省 50%+。
③ 測試分層——PR 只跑單元測試（2 分鐘），合併到 main 才跑整合測試，夜間跑完整的 E2E 測試。
④ 加大建置機器——machineType: E2_HIGHCPU_32，成本增加但時間大減。工程師的時間比機器貴得多。
⑤ 只測改動的部分——monorepo 用路徑篩選，只跑受影響的模組。

目標：PR 檢查 < 5 分鐘，完整部署 < 15 分鐘。
部署新版後，你需要回滾，但新版已經對資料庫做了 ALTER TABLE DROP COLUMN。怎麼辦？
你回不去了——這是最痛的部署事故之一。舊版程式碼會因為找不到欄位而全面崩潰。

當下的處置：只能往前修（roll forward），緊急發一個修正版，而不是回滾。

正確的預防做法：擴充-收縮模式（expand-contract），把 schema 變更拆成多次部署：
• 第 1 次部署：新增欄位（不刪舊的）。新舊程式都能跑。
• 第 2 次部署：程式改成同時寫入新舊欄位，讀取仍用舊欄位。
• 第 3 次部署：程式改成讀取新欄位。此時仍可回滾到第 2 次。
• 資料遷移：把歷史資料補到新欄位。
• 第 4 次部署：程式停止寫入舊欄位。
• 第 5 次部署：確認一段時間（如兩週）無問題後，才 DROP 舊欄位。

麻煩，但每一步都可以安全回滾。破壞性的 schema 變更永遠要跟程式碼部署分開，且延後執行。
團隊想「每次 push 到 main 就自動部署到正式環境」。你同意嗎？
取決於三個前提條件是否具備。持續部署（continuous deployment）是好目標，但沒有這些基礎就是災難：

必要條件：
① 可信的自動化測試——測試覆蓋率與品質要足以攔下大部分問題。如果測試常常「紅了但其實沒事」，團隊會習慣性忽略，那自動部署就等於沒有把關。
② 漸進式發布 + 自動回滾——金絲雀部署，配合明確的指標門檻自動判斷。
③ 完整的可觀測性——出事時能在幾分鐘內發現並定位。

務實的推進路徑：
• 階段一：main → 自動部署 staging，prod 需要人工核准。
• 階段二：累積信心後，prod 改成自動金絲雀 + 人工確認擴大。
• 階段三：指標門檻明確且驗證過後，才全自動。

另外考慮業務因素：電商在雙十一期間應該有變更凍結期，這與技術成熟度無關，是風險管理。
