LESSON 16

Shared VPC 與多專案網路架構

當公司有 50 個專案時，每個專案各自建 VPC 會變成災難。Shared VPC 是 GCP 對企業級網路治理的答案，這一課講它的設計與權責劃分。

閱讀 22 分企業級

一、問題：專案一多，網路就亂了

每個 GCP 專案預設有自己的 VPC。當你有 50 個專案：

  • 50 套 IP 規劃，彼此可能衝突
  • 要互通就要建 50×49/2 = 1225 條 VPC Peering（實際上有上限，根本做不到）
  • 50 套防火牆規則，資安團隊管不動
  • 每個專案各建一套 VPN 到地端，成本與維護爆炸

二、Shared VPC：一個網路，多個專案共用

Shared VPC 架構
              Host Project（主專案）
              「網路團隊擁有」
              ┌──────────────────────┐
              │  VPC: corp-shared     │
              │  ├ subnet-a  10.10/20 │
              │  ├ subnet-b  10.20/20 │
              │  ├ 防火牆規則          │
              │  ├ Cloud NAT          │
              │  └ VPN 到地端          │
              └──────────────────────┘
                 ↑        ↑        ↑
        ┌────────┘        │        └────────┐
   Service Project    Service Project   Service Project
   「電商團隊」        「行銷團隊」       「資料團隊」
   在 subnet-a 開 VM   在 subnet-a 開 VM  在 subnet-b 開 VM

權責劃分是這套架構的核心價值：

角色擁有什麼能做什麼不能做什麼
網路團隊
（Host Project）		VPC、子網路、防火牆、路由、VPN、NAT制定網路政策、分配子網路、稽核流量不需要碰各團隊的應用
應用團隊
（Service Project）		VM、GKE、Cloud SQL 等資源在被授權的子網路建立資源、獨立計費、獨立 IAM不能改防火牆、不能改網段、不能建 VPN
實務提醒
這正是「集中管控 + 分散自主」的實現。資安與網路是全公司一致的，但每個團隊在自己的專案裡有完全的自主權與獨立帳單。
這是大型企業 GCP 落地的標準架構，也是 PCA 考試的高頻主題。

三、實作：設定 Shared VPC

bash
# 前提：你需要 Organization，且有 Shared VPC Admin 角色
# 角色：roles/compute.xpnAdmin（要在 Organization 或 Folder 層級授予）

# 1. 啟用主專案
gcloud compute shared-vpc enable HOST_PROJECT_ID

# 2. 掛載服務專案
gcloud compute shared-vpc associated-projects add SERVICE_PROJECT_ID \
  --host-project=HOST_PROJECT_ID

# 3. 授權特定團隊使用特定子網路（最小權限的關鍵）
gcloud compute networks subnets add-iam-policy-binding subnet-a \
  --region=asia-east1 --project=HOST_PROJECT_ID \
  --member="group:ecommerce-team@corp.com" \
  --role="roles/compute.networkUser"

# 4. 服務專案的人現在可以在該子網路建立資源
gcloud compute instances create app-vm \
  --project=SERVICE_PROJECT_ID \
  --zone=asia-east1-b \
  --subnet=projects/HOST_PROJECT_ID/regions/asia-east1/subnetworks/subnet-a \
  --no-address

# 5. 查看目前的掛載狀況
gcloud compute shared-vpc list-associated-resources HOST_PROJECT_ID
小心踩雷
權限授予的粒度很重要。
把 roles/compute.networkUser 授予在整個主專案，等於讓該團隊能用所有子網路——這破壞了隔離。
正確做法是授予在特定子網路上（如上面的範例），這樣電商團隊只能用 subnet-a，碰不到資料團隊的 subnet-b。

四、VPC Peering：另一種互通方式

Shared VPCVPC Peering
關係一個 VPC 被多個專案共用兩個獨立 VPC 互相連通
管理集中式，網路團隊統一管分散式，各自管自己的
IP 規劃天生不重疊（同一個 VPC）必須手動確保不重疊
傳遞性N/A不可傳遞：A↔B、B↔C 不代表 A↔C
適用同一個組織內的多團隊跨組織、跨公司、SaaS 供應商與客戶
上限一個 host 可掛 1000 個服務專案每個 VPC 最多 25 個 peering
bash
# VPC Peering 需要雙方各建一次（互相同意）
# 在 VPC-A 的專案
gcloud compute networks peerings create peer-to-b \
  --network=vpc-a --peer-project=PROJECT_B --peer-network=vpc-b \
  --export-custom-routes --import-custom-routes

# 在 VPC-B 的專案
gcloud compute networks peerings create peer-to-a \
  --network=vpc-b --peer-project=PROJECT_A --peer-network=vpc-a \
  --export-custom-routes --import-custom-routes
小心踩雷
Peering 不可傳遞，這是最常見的架構誤判。
如果 A↔B、B↔C，A 想連 C 必須直接建立 A↔C。
當你有 10 個 VPC 要全互通，就需要 45 條 peering，而上限是 25 條——架構會直接撞牆。
這就是為什麼企業要用 Shared VPC 或 Network Connectivity Center（星狀拓撲），而不是靠 Peering 拼網狀網路。

五、VPC Service Controls：資料外洩的最後防線

IAM 管「誰能存取」，但如果一個有權限的人（或被盜的帳號）把資料複製到外部呢？VPC Service Controls 建立一道資料邊界：

bash
# 建立存取範圍（Perimeter）
gcloud access-context-manager perimeters create prod-perimeter \
  --title="正式環境資料邊界" \
  --resources=projects/123456789 \
  --restricted-services=storage.googleapis.com,bigquery.googleapis.com \
  --policy=POLICY_ID

# 效果：
# ✅ 邊界內的 VM → 邊界內的 GCS   通過
# ❌ 邊界內的 GCS → 邊界外的專案   阻擋（即使 IAM 允許）
# ❌ 外部的人用合法憑證下載資料     阻擋
補充
VPC-SC 與 IAM 是正交的兩層防護。
IAM 回答「你有沒有權限」，VPC-SC 回答「資料能不能離開這個範圍」。
即使攻擊者拿到了有效的服務帳號金鑰，只要他從邊界外發起請求，VPC-SC 就會擋下。金融、醫療、政府專案幾乎必備。

六、企業級網路架構的完整樣貌

企業級參考架構
Organization: corp.com
│
├── Folder: 共用基礎設施
│   └── Project: net-host-prod  ← Shared VPC 主專案
│       ├── VPC: corp-prod（全球）
│       │   ├── subnet asia-east1  10.48.0.0/20
│       │   ├── subnet us-central1 10.49.0.0/20
│       │   ├── 階層式防火牆政策（Org 層強制）
│       │   ├── Cloud NAT（固定 IP 池，給第三方白名單）
│       │   └── HA VPN → 地端資料中心
│       └── Project: net-host-dev  ← 開發環境的 Shared VPC
│

│   ├── Project: shop-prod     ← 服務專案
│   ├── Project: payment-prod  ← 服務專案
│   └── Project: data-prod     ← 服務專案
│
└── Folder: 開發環境
    ├── Project: shop-dev
    └── Project: data-dev

七、本課檢核

  • 理解 Shared VPC 的權責劃分（網路團隊 vs 應用團隊）
  • 知道 networkUser 角色要授予在子網路層級而非專案層級
  • 知道 VPC Peering 不可傳遞且有數量上限
  • 理解 VPC Service Controls 與 IAM 的差異
  • 能畫出一個企業級的專案與網路架構

自我檢測

公司有 8 個 VPC 需要全互通。用 Peering 可行嗎？
技術上勉強可行，架構上是錯的。
8 個 VPC 全互通需要 8×7/2 = 28 條 peering，每個 VPC 要維護 7 條連線。上限是每 VPC 25 條，所以還沒撞牆——但：
① 新增第 9 個 VPC 要建 8 條新連線，維護成本呈平方成長；
② 任何路由變更要在 8 個地方確認；
③ 除錯時要追 28 條連線。

正確做法：
• 同一組織內 → Shared VPC，直接消除互通需求。
• 必須保持 VPC 獨立 → Network Connectivity Center，用星狀拓撲，加一個 VPC 只要接 1 條。
判斷準則：任何需要 O(n²) 連線的架構，在 n>4 時就該換設計。
Shared VPC 環境下，應用團隊說「我需要開一個防火牆規則讓服務互通」。你怎麼處理？
他們不能自己開，這是設計使然。但直接說「不行」會讓網路團隊變成瓶頸，正確做法是建立流程：

① 短期：網路團隊代為建立，但要求提供來源/目的/協定/埠/業務理由。
② 中期：把防火牆規則納入 Terraform + Git PR 流程。應用團隊提 PR，網路團隊 review 後合併，CI 自動套用。這樣既保留把關，又不需要人工開單。
③ 長期：制定標準化的網路標籤（如 tier-web、tier-app），預先建好對應規則。團隊只要貼標籤，不用每次申請。

關鍵洞察：治理的目的是「可控」不是「難用」。如果流程太痛，團隊會想辦法繞過去——例如全部塞進同一台 VM，那反而更糟。
稽核問：「如果開發者的筆電被入侵，攻擊者拿到他的 gcloud 憑證，能不能把 BigQuery 的客戶資料下載走？」
只靠 IAM 的話：能。因為攻擊者用的是合法憑證，IAM 無法區分是本人還是攻擊者。

需要疊三層防護：
① VPC Service Controls——建立資料邊界，只允許來自公司 VPC 或指定 IP 範圍的請求。攻擊者從外部網路發起的請求會被擋，即使憑證有效。這是針對這個問題最直接的答案。
② Context-Aware Access——要求存取必須來自受管理的裝置、特定地理位置、且裝置符合安全基準。
③ 短期憑證 + 稽核——禁止服務帳號金鑰、縮短 token 有效期、開啟 Data Access Audit Logs 並設定異常下載量告警。

這題的核心觀念：身分驗證不等於存取控制。現代零信任架構要同時檢查「你是誰」「你從哪來」「你的裝置安不安全」「你要做什麼」。
