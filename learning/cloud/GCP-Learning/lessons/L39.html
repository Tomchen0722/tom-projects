LESSON 39

企業級參考架構：三個案例拆解

把前面 38 課的所有知識整合起來。這一課用三個真實情境的完整架構，示範各個元件怎麼組合成一個能上線的系統。

閱讀 30 分總整理

案例一：中型電商平台

需求：日活 50 萬、尖峰 QPS 3000、需要高可用、每日營運報表、成本敏感。

電商參考架構
                        使用者
                          ↓
              Cloud DNS（www.shop.com）
                          ↓
        Global External Application LB（Anycast IP）
              ├── Cloud Armor（WAF + 速率限制 + DDoS）
              └── Cloud CDN（靜態資源快取）
                          ↓
        ┌─────────────────┼─────────────────┐
        ↓                 ↓                 ↓
   /static/*          /api/*            /admin/*
   Backend Bucket    Cloud Run          Cloud Run
   (GCS + CDN)       (api-service)      (admin-service)
                     min=2, max=100     min=0, max=10
                     ↓
        ┌────────────┼────────────┬──────────────┐
        ↓            ↓            ↓              ↓
   Cloud SQL    Memorystore   Pub/Sub      Secret Manager
   PostgreSQL   Redis         (訂單事件)     (DB密碼/API金鑰)
   REGIONAL HA  STANDARD_HA        ↓
   + 2 唯讀副本  (session/快取)  Cloud Run Job
        ↓                        (訂單後處理：
        ↓ Datastream              寄信/更新庫存/
        ↓ (CDC 變更擷取)           推播)
   BigQuery
   (分析 + 每日報表)
        ↓
   Looker Studio（營運儀表板）

【橫向支撐】
  Cloud Logging / Monitoring / Trace  ← 可觀測性
  Cloud Build + Artifact Registry     ← CI/CD
  Terraform（全部基礎設施）             ← IaC
  Shared VPC + Private Service Access ← 網路

關鍵設計決策

決策選擇理由
運算層Cloud Run 而非 GKE流量起伏大，縮到 0 省錢；團隊小，不想維護叢集
資料庫Cloud SQL REGIONAL + 2 唯讀副本資料量 < 1TB，不需要 Spanner；HA 提供自動故障轉移
快取Memorystore Redis放 session（無狀態必要）+ 商品快取
非同步Pub/Sub + Cloud Run Job訂單後處理不阻塞使用者，且可重試
分析Datastream → BigQueryOLTP/OLAP 分離，報表查詢不影響交易
靜態資源GCS + Cloud CDN擋掉 70%+ 流量，成本極低

估算月成本：Cloud Run ~$200、Cloud SQL (HA + 2 副本) ~$800、Memorystore ~$150、LB + CDN ~$150、BigQuery ~$200、其他 ~$100 = 約 $1,600/月。

案例二：金融科技的核心帳務系統

需求：跨三地（台/新/日）、絕對不能超賣或重複扣款、法規要求 7 年稽核、RPO=0、RTO<5 分鐘。

金融核心架構
              使用者（三地）
                    ↓
        Global External Application LB
              + Cloud Armor
                    ↓
        ┌───────────┼───────────┐
        ↓           ↓           ↓
   asia-east1  asia-southeast1  asia-northeast1
        │           │           │
     GKE Autopilot（各區域，Regional 叢集）
        │  ├── API Gateway Pod
        │  ├── 帳務服務 Pod（Workload Identity）
        │  └── 風控服務 Pod
        └───────────┼───────────┘
                    ↓
        ┌───────────┴───────────┐
        ↓                       ↓
   Cloud Spanner            Cloud KMS
   (multi-region:            (CMEK 加密所有資料)
    asia1 配置)
   ★ 全球強一致                Secret Manager
   ★ 99.999% SLA              (憑證，90天輪換)
        ↓
   Change Streams
        ↓
   Pub/Sub → Dataflow → BigQuery（分析）
                     → GCS Archive + Bucket Lock（7年稽核）

【資安層】
  VPC Service Controls        ← 資料邊界，防外洩
  Binary Authorization        ← 只跑經簽署的映像
  Organization Policy         ← 強制護欄
  Privileged Access Manager   ← JIT 特權存取
  Security Command Center     ← 持續監控
  Data Access Audit Logs（全開）→ 不可竄改儲存

為什麼是這些選擇

  • Spanner 是唯一選項——「三地同時寫入 + 絕不超賣」等於需要全球強一致的 ACID 交易。Cloud SQL 的跨區複製是非同步的，做不到；Bigtable 沒有跨列交易。
  • GKE 而非 Cloud Run——需要 mTLS 服務網格、細緻的流量控制、以及對 Pod 層級的資安控制。金融稽核通常也要求這種控制粒度。
  • CMEK 全面加密——法規要求客戶控制金鑰，且能證明資料可被撤銷存取。
  • VPC-SC 是關鍵——即使攻擊者取得有效憑證，從邊界外仍無法取出資料。
  • Bucket Lock 的稽核歸檔——保留鎖定後連 Org Admin 也刪不掉，滿足「不可竄改」要求。
小心踩雷
這套架構的成本是案例一的 10 倍以上（Spanner multi-region 起跳就數千美元）。只有在法規與業務真的需要時才這樣做。
「我們也是金融業所以要這樣」是錯誤的推論——先確認你的系統真的需要全球強一致。多數金融應用其實可以按地區分區，用區域級資料庫就夠。

案例三：製造業的 IoT 資料平台

需求：3000 台機台、每 5 秒回報、即時異常告警、3 年歷史分析、預測性維護。

IoT 平台架構
    3000 台機台（每 5 秒一筆 → 每秒 600 筆 → 每日 5,184 萬筆）
              ↓ MQTT / HTTPS
        邊緣閘道（各廠區）
              ↓ 批次上傳，含離線緩衝
        Cloud Pub/Sub（topic: sensor-data）
              ↓
        ┌─────┴─────────────────────┐
        ↓                           ↓
   Dataflow 串流管線            Pub/Sub BigQuery 訂閱
   ├ 資料清洗與驗證              （原始資料直入，零程式碼）
   ├ 5 分鐘視窗聚合                    ↓
   ├ 異常偵測（規則 + ML）        BigQuery RAW 層
   │      ↓ 異常時                （分區 + 90天過期）
   │  Pub/Sub → Cloud Run
   │            → 推播/簡訊/工單
   ↓
   Bigtable（近 30 天熱資料）
   row key: 機台ID#反轉時間戳
        ↓
   即時儀表板（Cloud Run + 前端）

【離線分析】
   BigQuery RAW → Dataform 轉換 → STAGING → MART
        ↓
   ├─ Looker Studio（產線效率儀表板）
   ├─ BigQuery ML（預測性維護模型）
   └─ Vertex AI（進階模型訓練與部署）

關鍵設計要點

  1. 邊緣要有離線緩衝——工廠網路會斷，資料不能丟。閘道端要能暫存並在恢復後補傳。
  2. 補傳會造成重複——所以下游必須冪等。用 機台ID + 時間戳 當唯一鍵。
  3. 熱冷分層——Bigtable 服務即時儀表板（毫秒級），BigQuery 服務歷史分析（秒級）。試圖用一個系統同時滿足兩者會兩邊都不好。
  4. Row key 設計——用 機台ID#(MAX-時間戳)，避免熱點且最新資料排前面。
  5. 用 Pub/Sub 原生 BigQuery 訂閱寫 RAW 層——零程式碼、零維護，Dataflow 只處理需要轉換的部分。

四、三個案例的共通模式

看完三個差異極大的架構，你會發現有些東西永遠都在：

共通元件為什麼永遠需要
Terraform 管理全部資源可重現、可審閱、可回滾
CI/CD 自動化部署手動部署遲早出事
Cloud Logging + Monitoring + 告警看不見就管不動
Secret Manager憑證絕不落地
私有網路 + 最小權限 IAM縱深防禦的基礎
備份 + 演練過的 DR 計畫不是「會不會出事」，是「什麼時候」
成本標籤與預算警報成本要能歸因才能控制
OLTP 與 OLAP 分離交易與分析是不同的工作負載

如果你的架構圖上少了這八項中的任何一項，那不是「簡化」，是「還沒做完」。

  • 能說明為什麼案例二需要 Spanner 而案例一不需要
  • 理解熱冷資料分層的設計理由

自我檢測

案例一的電商，黑色星期五流量預估是平常的 20 倍。要調整什麼？
逐層檢查瓶頸，重點是「哪些會自動擴、哪些不會」。

① Cloud Run（會自動擴，但要調上限）——max-instances 從 100 調到 500；提前設定 min-instances 預熱（例如活動前一小時調到 20），避免冷啟動。

② Cloud SQL（不會自動擴，最大瓶頸）——這是最需要注意的一層：
  • 提前垂直擴充（需要短暫重啟，要在活動前做）
  • 增加唯讀副本，把讀取分流
  • 務必加連線池——500 個 Cloud Run 實例 × 每個 10 條連線 = 5000 條，會直接打爆資料庫。用 PgBouncer 或 Cloud SQL Auth Proxy 的連線池。

③ Memorystore——擴大記憶體，並預熱快取（活動前把熱門商品資料先載入）。

④ CDN——延長靜態資源的 TTL，最大化命中率。

⑤ 配額檢查——提前兩週向 GCP 申請提高配額（CPU、IP、連線數）。這一步最常被忘記，而且臨時申請可能來不及。

⑥ 非同步化——把「寄確認信、更新推薦、寫分析」等非關鍵路徑全部丟進 Pub/Sub，讓結帳路徑最短。

⑦ 降級預案——準備好功能開關，必要時關閉推薦、評論等非核心功能。

最後：活動前一週做一次真實的壓力測試。沒測過的容量規劃只是猜測。
案例三的 IoT 平台，資料量三年後成長到 10 倍。架構要重做嗎？
不用重做，但要調整幾個參數與策略。這個架構的可擴充性本來就不錯：

① Pub/Sub——完全託管，自動擴充。不用改。
② Dataflow——調高 max-num-workers，它會自動擴。不用改架構。
③ Bigtable——增加節點數即可線性擴充。但要檢查 row key 有沒有熱點——資料量大時熱點的影響會被放大。用 Key Visualizer 確認。
④ BigQuery——這是要注意的一層：
  • 儲存成本會線性成長 → 加強分區到期政策，把超過 1 年的資料匯出到 GCS 用外部表查詢
  • 查詢成本可能非線性成長 → 建立具體化檢視表，讓常用報表不再掃原始資料
  • 考慮從隨用隨付切換到容量定價

⑤ 成本結構要重新檢視——10 倍資料量下，原本佔比小的項目可能變成主要成本。例如 Dataflow 的常駐 worker、Bigtable 的節點數。

真正需要重新設計的訊號：
• 如果查詢模式改變了（例如從「查單一機台」變成「跨全廠即時比對」），那 Bigtable 的 row key 設計可能不再適用。
• 如果需要跨廠區的即時關聯分析，可能要引入串流 JOIN。

好架構的特徵：擴充時調參數，不是改設計。這個架構的每一層都是水平可擴充的託管服務，這就是為什麼它撐得住。
你要向沒有技術背景的 CTO 說明為什麼案例二比案例一貴 10 倍。怎麼講？
用「保險」的比喻，並把成本對應到具體的業務風險。

「兩套系統的差別，就像一般汽車保險和運鈔車的保全規格。」

① 資料一致性的代價
「電商如果庫存算錯，最壞的情況是超賣一件商品，我們道歉退款，損失幾千元。
帳務系統如果算錯，就是某個客戶的錢憑空消失或憑空出現——這會是金管會的重大裁罰、上新聞、失去營業許可。
為了保證『三個國家的機房同時運作，但帳目永遠一致』，我們必須用 Spanner——這是全世界少數幾個做得到的技術，Google 為此在機房裡裝了原子鐘。這項技術本身就佔了成本差距的一半以上。」

② 法規遵循的代價
「7 年不可竄改的稽核紀錄、客戶自持的加密金鑰、每一次資料存取都要留證——這些不會讓系統跑得更快，但少了任何一項，稽核就過不了。這是營業執照的成本，不是技術的成本。」

③ 停機的代價
「電商停機一小時，損失是那一小時的營業額。
帳務系統停機一小時，是客戶無法轉帳、無法交易——那是信任的損失，而信任一旦失去，客戶不會回來。」

④ 給出對比數字
「這套系統每月多花的錢，大約等於一次資安事故的公關費用，或一次法規裁罰的十分之一。」

關鍵技巧：不要講技術規格，講「如果不這樣做會發生什麼」。決策者需要的是風險與代價的對照，不是架構圖。
