LESSON 25

Kubernetes 觀念：Pod、Service、Deployment

K8s 的學習曲線很陡，但核心觀念其實只有幾個。這一課不碰指令，先把心智模型建立起來——理解了「宣告式」這個概念，其他都是細節。

閱讀 30 分核心觀念

一、Kubernetes 到底在做什麼

K8s 是一個「維持期望狀態」的系統。你不告訴它「怎麼做」，你告訴它「我要什麼樣子」，它自己想辦法達成並持續維持。

生活比喻
命令式 vs 宣告式：兩種請人幫忙的方式。

命令式（傳統做法）：「去開一台機器、裝好 nginx、設定好、啟動它。」
如果那台機器掛了，你得再說一次。

宣告式（K8s）：「我要永遠有 3 個 nginx 在跑。」
然後你就不用管了。掛一個？K8s 自動補一個。你改成 5 個？它自動加 2 個。節點故障？它把 Pod 排到其他節點。

這就是 K8s 的全部精神：你寫下期望狀態（YAML），控制迴路（controller）不斷比對實際狀態並修正差異。

二、五個核心物件

五個核心物件
Deployment（部署）
   「我要 3 個這樣的應用，用這個映像，滾動更新」
        ↓ 管理
ReplicaSet（副本集）
   「確保剛好有 3 個 Pod 在跑」
        ↓ 管理
Pod（豆莢）
   「一個或多個容器的最小部署單位，共用網路與儲存」
        ↓ 被找到
Service（服務）
   「給這群 Pod 一個穩定的名稱與 IP，並做負載平衡」
        ↓ 對外
Ingress（入口）
   「HTTP 路由：/api 給 A 服務，/web 給 B 服務，加上 TLS」

Pod：為什麼不是「容器」？

Pod 是 K8s 的最小單位，通常裡面只有一個容器——但它可以有多個。同一個 Pod 內的容器共用網路（同一個 IP、可用 localhost 互連）與儲存卷。

多容器 Pod 的典型用途叫 sidecar 模式：

  • 日誌收集：主容器寫日誌到共用卷，sidecar 讀取並轉發
  • 服務網格代理：Istio 的 Envoy sidecar 攔截所有進出流量
  • 設定同步：sidecar 定期從 Git 拉取設定檔
小心踩雷
Pod 是「可拋棄」的。它隨時可能被刪除、被重新排程到其他節點、IP 會改變。
所以：永遠不要直接建立 Pod（要用 Deployment），永遠不要依賴 Pod 的 IP（要用 Service），永遠不要把資料存在 Pod 裡（要用 PersistentVolume 或外部儲存）。

Service：解決「Pod 的 IP 一直變」的問題

類型作用使用場景
ClusterIP（預設）叢集內部的虛擬 IP + DNS 名稱微服務之間互相呼叫
NodePort在每個節點開一個埠對外測試用，正式環境少用
LoadBalancer自動建立 GCP 負載平衡器對外暴露單一服務（L4）

三、一份完整的 Deployment YAML（逐行解說）

deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: task-api
  labels:
    app: task-api
spec:
  replicas: 3                    # 我要 3 個副本
  selector:
    matchLabels:
      app: task-api              # 管理帶有這個標籤的 Pod
  strategy:
    type: RollingUpdate          # 滾動更新，不停機
    rollingUpdate:
      maxSurge: 1                # 更新時最多多開 1 個
      maxUnavailable: 0          # 不允許任何一個下線
  template:                      # ↓ Pod 的範本
    metadata:
      labels:
        app: task-api            # 產生的 Pod 會有這個標籤
    spec:
      serviceAccountName: task-api-sa    # 用 Workload Identity 取得 GCP 權限
      containers:
      - name: app
        image: asia-east1-docker.pkg.dev/PROJ/my-apps/task-api:a3f9c21
        ports:
        - containerPort: 8080

        # ★ 資源請求與上限：K8s 排程與穩定性的關鍵
        resources:
          requests:              # 保證分配到的量（排程依據）
            cpu: 100m            # 0.1 核
            memory: 128Mi
          limits:                # 上限（超過 memory 會被殺，超過 cpu 會被限速）
            cpu: 500m
            memory: 512Mi

        # ★ 三種探針，作用完全不同
        startupProbe:            # 啟動慢的應用用這個，通過前不執行其他探針
          httpGet: {path: /healthz, port: 8080}
          failureThreshold: 30
          periodSeconds: 5       # 最多容忍 150 秒啟動時間

        readinessProbe:          # 「準備好接流量了嗎」失敗 → 從 Service 移除
          httpGet: {path: /healthz, port: 8080}
          periodSeconds: 10

        livenessProbe:           # 「還活著嗎」失敗 → 重啟容器
          httpGet: {path: /healthz, port: 8080}
          periodSeconds: 20
          failureThreshold: 3

        env:
        - name: DB_HOST
          valueFrom:
            configMapKeyRef: {name: app-config, key: db_host}
        - name: DB_PASSWORD
          valueFrom:
            secretKeyRef: {name: app-secrets, key: db_password}

        securityContext:
          runAsNonRoot: true
          readOnlyRootFilesystem: true
          allowPrivilegeEscalation: false
---
apiVersion: v1
kind: Service
metadata:
  name: task-api
spec:
  type: ClusterIP
  selector:
    app: task-api                # 找到帶這個標籤的所有 Pod
  ports:
  - port: 80
    targetPort: 8080

四、三種探針：最常被搞錯的觀念

探針問的問題失敗的後果設定要點
startupProbe「啟動完成了嗎？」持續等待，不重啟啟動慢的應用（Java）必設，否則會被 liveness 誤殺
readinessProbe「可以接流量了嗎？」從 Service 端點移除（不接新流量，但不重啟）應該檢查下游依賴（資料庫連得上嗎）
livenessProbe「還活著嗎？」重啟容器只檢查程序本身，不要檢查下游
小心踩雷
最經典的 K8s 事故：livenessProbe 檢查資料庫連線。
資料庫暫時抖動 → 所有 Pod 的 liveness 失敗 → 全部同時重啟 → 重啟後湧入大量連線 → 資料庫更慘 → 無限循環。

鐵則：liveness 只檢查「這個程序卡死了嗎」，readiness 才檢查「依賴健康嗎」。

五、資源請求與上限：穩定性的根本

這是最常被忽略、但影響最大的設定。K8s 依 requests 決定把 Pod 排到哪個節點，依 limits 決定什麼時候該制裁它。

情況結果
沒設 requests排程器不知道你要多少資源，可能把 Pod 塞到已經滿載的節點
沒設 limits一個記憶體洩漏的 Pod 可以吃光整個節點，拖垮同節點的其他服務
超過 memory limit容器被 OOMKilled 立刻殺掉（沒有寬限）
超過 cpu limit被限速（throttled），變慢但不會死
requests = limitsQoS 等級為 Guaranteed，節點資源不足時最後才被驅逐
實務提醒
正式環境的建議設定：
• 關鍵服務：requests = limits（Guaranteed QoS），保證穩定。
• 一般服務：limits = requests × 2，允許突發。
• 記憶體的 limit 要設得比實測峰值高 50%——OOMKilled 沒有預警，直接殺。
• CPU 的 limit 可以設寬鬆些，因為限速比被殺好。

六、其他你會遇到的物件

物件用途
ConfigMap非機密的設定（環境變數、設定檔）
Secret密碼、金鑰（注意：預設只是 base64 編碼，不是加密）

自我檢測

你的 Pod 一直在 CrashLoopBackOff。列出排查步驟。
五步驟：
① kubectl describe pod POD_NAME —— 看 Events 區段，通常直接寫明原因（映像拉不到、掛載失敗、探針失敗）。
② kubectl logs POD_NAME --previous —— 加 --previous 很重要，因為容器已經重啟，要看上一次崩潰的日誌。
③ 檢查 OOMKilled：kubectl get pod POD_NAME -o jsonpath='{.status.containerStatuses[0].lastState.terminated.reason}'。如果是 OOMKilled 就是記憶體 limit 太小。
④ 檢查 探針設定——最常見的是 livenessProbe 的 initialDelaySeconds 太短，應用還沒啟動完就被判定失敗並重啟，形成死循環。解法是加 startupProbe。
⑤ 檢查 ConfigMap / Secret 是否存在——引用不存在的 Secret 會讓 Pod 卡在 CreateContainerConfigError。
服務更新後有短暫的 502 錯誤，明明設定了 maxUnavailable: 0。為什麼？
因為「Pod 被標記為 Ready」和「LB 真的知道它 Ready」之間有時間差，反過來關閉時也有時間差。

關閉時的競態條件：K8s 送 SIGTERM 給 Pod 的同時，也開始從 Service 端點移除它。但這兩件事是並行的——LB 可能還在送流量過來，而 Pod 已經開始關閉。

解法（三個一起做）：
① 加 preStop hook 延遲：
bash
lifecycle:
  preStop:
    exec:
      command: ["sleep", "15"]     # 給 LB 時間更新端點
② 應用要優雅處理 SIGTERM：停止接受新請求，但把手上的請求處理完再退出。
③ 設定 terminationGracePeriodSeconds 大於「preStop 延遲 + 最長請求處理時間」。

這是 K8s 零停機部署最常被忽略的細節。maxUnavailable: 0 只保證「數量」，不保證「流量正確切換」。
同事說「K8s 太複雜了，我們直接用 Cloud Run 就好」。你同意嗎？
多數情況我同意，但要看具體條件。

Cloud Run 就夠的情況（大部分）：無狀態 HTTP 服務、團隊 < 20 人、不需要複雜的服務拓撲、沒有特殊的排程需求。

真正需要 K8s 的情況：
• 需要跑非 HTTP 的長駐服務（例如消費 Kafka 的 worker）
• 需要 DaemonSet（每個節點跑監控代理）
• 需要複雜的服務網格（mTLS、細緻流量控制、金絲雀依 header 分流）
• 有狀態服務需要穩定的網路識別與儲存
• 已經有大量 K8s 資產與專業知識
• 多雲或混合雲策略（K8s 是可攜性最好的抽象層）

中間路線：GKE Autopilot——你寫 K8s YAML，但不用管節點、不用管升級、按 Pod 資源計費。它保留了 K8s 的能力，去掉了大部分維運負擔。

判斷準則：「複雜度應該花在你的業務問題上，不是基礎設施上。」如果你的團隊有一半時間在調 K8s，那就是選錯了。
