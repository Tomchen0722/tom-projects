LESSON 24

Artifact Registry 與映像管理

映像建好之後要放哪？誰能拉？怎麼確保沒有漏洞？這一課處理容器供應鏈的安全與治理。

操作 30 分實作

一、Artifact Registry：不只放容器

Artifact Registry 是 Container Registry（GCR）的後繼者，支援的格式多很多：

  • Docker / OCI 容器映像
  • Maven、npm、Python (PyPI)、Go 模組
  • APT / YUM 系統套件
  • Helm chart
補充
Container Registry (gcr.io) 已經停止支援，新專案一律用 Artifact Registry。差別在於 Artifact Registry 有：區域級控制、更細的 IAM 權限、CMEK 加密、以及原生的漏洞掃描整合。
動手實作

實作：建立倉庫並推送映像

  1. 建立倉庫：
    bash
    gcloud artifacts repositories create my-apps \
  --repository-format=docker \
  --location=asia-east1 \
  --description="應用程式容器映像" \
  --immutable-tags
  2. 設定 Docker 認證：
    bash
    gcloud auth configure-docker asia-east1-docker.pkg.dev
  3. 標記並推送：
    bash
    REPO=asia-east1-docker.pkg.dev/$(gcloud config get-value project)/my-apps

docker tag task-api:v1 $REPO/task-api:v1.0.0
docker tag task-api:v1 $REPO/task-api:$(git rev-parse --short HEAD)   # 用 commit hash

docker push $REPO/task-api:v1.0.0
  4. 查看與管理：
    bash
    gcloud artifacts docker images list $REPO/task-api
gcloud artifacts docker images describe $REPO/task-api:v1.0.0

# 查看某個映像的漏洞掃描結果
gcloud artifacts docker images list $REPO/task-api \
  --show-occurrences --format=json
實務提醒
--immutable-tags 是很重要的設定。它禁止覆蓋已存在的標籤——意思是 v1.0.0 永遠指向同一個映像。
沒有這個設定的話，有人可以推一個新映像覆蓋 v1.0.0，你的「回滾到 v1.0.0」就會拿到不同的東西。這是供應鏈安全的基本要求。

二、標籤策略：不要用 latest

標籤方式範例優點缺點
latestapp:latest方便不知道在跑什麼、無法回滾、快取行為詭異
語意版本app:1.4.2人類可讀需要維護版本號
Git commit SHAapp:a3f9c21絕對可追溯到原始碼不易記憶
映像摘要app@sha256:abc...不可變、最安全很長
組合（推薦）同時打 1.4.2 和 a3f9c21兼顧可讀性與可追溯—
bash
# CI 中的標準做法
SHA=$(git rev-parse --short HEAD)
VERSION=$(cat VERSION)

docker build -t $REPO/app:$SHA -t $REPO/app:$VERSION .
docker push $REPO/app:$SHA
docker push $REPO/app:$VERSION

# 部署時用摘要，確保部署的絕對是這個映像
DIGEST=$(gcloud artifacts docker images describe $REPO/app:$SHA \
  --format="value(image_summary.digest)")
gcloud run deploy app --image=$REPO/app@$DIGEST

三、漏洞掃描：Artifact Analysis

bash
# 啟用自動掃描（推送時自動觸發）
gcloud services enable containerscanning.googleapis.com

# 查詢掃描結果
gcloud artifacts docker images list $REPO/task-api \
  --show-occurrences \
  --occurrence-filter='kind="VULNERABILITY"'

# 在 CI 中阻擋高風險映像
CRITICAL=$(gcloud artifacts docker images describe $REPO/app:$SHA \
  --show-package-vulnerability \
  --format="value(package_vulnerability_summary.vulnerabilities.CRITICAL)")

if [ "$CRITICAL" -gt 0 ]; then
  echo "發現 $CRITICAL 個 CRITICAL 等級漏洞，停止部署"
  exit 1
fi
小心踩雷
漏洞掃描會讓你面對一個不舒服的事實：幾乎所有映像都有漏洞。
一個標準的 python:3.12-slim 掃出來可能有幾十個 CVE，多數是基底作業系統的套件。

務實的處理原則：
① 只阻擋 CRITICAL 且有修補可用 的漏洞；
② 定期（每週）自動重建映像拉取最新基底，這能解決 80% 的問題；
③ 用 distroless 基底大幅減少套件數量，也就大幅減少 CVE 數量；
④ 不要因為掃出 200 個 LOW 等級漏洞就停止部署——那會讓團隊直接關掉掃描。

四、Binary Authorization：只准通過驗證的映像上線

這是企業級的最後一道防線：強制所有部署的映像都必須有「證明」——證明它通過了掃描、通過了測試、來自可信的建置系統。

bash
# 建立政策：要求所有映像都必須有證明
gcloud container binauthz policy import policy.yaml

# policy.yaml
cat > policy.yaml <<'YAML'
defaultAdmissionRule:
  evaluationMode: REQUIRE_ATTESTATION
  enforcementMode: ENFORCED_BLOCK_AND_AUDIT_LOG
  requireAttestationsBy:
    - projects/PROJECT/attestors/prod-attestor
clusterAdmissionRules:
  asia-east1.dev-cluster:
    evaluationMode: ALWAYS_ALLOW      # 開發叢集不強制
    enforcementMode: DRYRUN_AUDIT_LOG_ONLY
YAML

# 建立證明者（attestor）
gcloud container binauthz attestors create prod-attestor \
  --attestation-authority-note=prod-note \
  --attestation-authority-note-project=PROJECT

完整流程：CI 建置 → 漏洞掃描通過 → 測試通過 → CI 用私鑰簽署證明 → 部署時 Binary Authorization 驗證簽章 → 通過才允許執行。沒有簽章的映像連 GKE 都拒絕啟動。

五、清理政策：控制儲存成本

bash
# 自動刪除舊映像（保留最近 10 個版本，刪除 30 天前的未標記映像）
cat > cleanup-policy.json <<'EOF'
[
  {
    "name": "keep-recent-versions",
    "action": {"type": "Keep"},
    "mostRecentVersions": {"keepCount": 10}
  },
  {
    "name": "delete-untagged-old",
    "action": {"type": "Delete"},
    "condition": {
      "tagState": "UNTAGGED",
      "olderThan": "30d"
    }
  },
  {
    "name": "keep-release-tags",
    "action": {"type": "Keep"},
    "condition": {
      "tagState": "TAGGED",
      "tagPrefixes": ["v", "release-"]
    }
  }
]
EOF

gcloud artifacts repositories set-cleanup-policies my-apps \
  --location=asia-east1 --policy=cleanup-policy.json
實務提醒
映像儲存費用約 $0.10/GB/月。聽起來便宜，但一個 CI 每天建 20 個映像、每個 500MB，一年就是 3.6TB = 每月 $360 且持續成長。
清理政策要在專案一開始就設好，不要等到帳單出來才處理。

六、本課檢核

  • 能建立 Artifact Registry 倉庫並推送映像
  • 知道不該用 latest，且知道 immutable tags 的價值
  • 會用 commit SHA 做可追溯的標籤
  • 理解漏洞掃描的務實處理原則
  • 知道要設定清理政策控制成本

自我檢測

正式環境部署失敗，你想回滾。你用的標籤是 latest。會發生什麼？
你回不去。latest 現在指向的就是有問題的新版本，舊版本可能已經被覆蓋且沒有其他標籤指向它。

如果幸運的話，舊映像還在（只是沒有標籤），你可以用摘要（digest）找回來：
bash
gcloud artifacts docker images list $REPO/app --include-tags --format=json | \
  jq '.[] | {digest: .version, tags: .tags, created: .createTime}'
# 找到前一個版本的 sha256，用摘要部署
gcloud run deploy app --image=$REPO/app@sha256:xxxxx
但如果清理政策已經刪掉未標記的映像，就真的沒了，只能重新建置。
教訓：可回滾性是部署流程的必要屬性，不是附加功能。每次部署都要能明確回答「上一個好的版本是哪個映像摘要」。
資安部門要求「所有正式環境的容器都必須經過掃描且無 CRITICAL 漏洞」。怎麼強制？
分三層，缺一不可：

① CI 層（快速回饋）——建置後立即掃描，有 CRITICAL 就讓 pipeline 失敗。優點是開發者馬上知道，缺點是可以被繞過（有人直接手動 push）。

② Registry 層（持續監控）——啟用 Artifact Analysis 持續掃描。重點是「持續」——今天沒漏洞的映像，下週可能因為新公布的 CVE 而變成有漏洞。設定 Pub/Sub 通知，發現新的 CRITICAL 就告警。

③ 部署層（強制阻擋）——Binary Authorization。這是唯一無法繞過的一層：GKE / Cloud Run 在啟動容器前驗證證明，沒有通過就拒絕執行。

只做①是不夠的——它是「請求配合」而非「強制執行」。真正的控制必須在執行點（enforcement point）。
團隊抱怨「漏洞掃描每次都報幾百個問題，我們根本處理不完，可以關掉嗎？」
不要關掉，但要改變處理方式。「處理不完」通常表示過濾策略錯了，而不是掃描沒價值。

務實的分級處理：
• 阻擋部署：只有 CRITICAL + 有可用修補 + 在你實際使用的套件中。這通常只有個位數。
• 每週處理：HIGH 等級且有修補的。
• 自動化解決：設定每週自動重建映像。基底映像的更新會自動帶入大部分修補，這一招能消掉 70～80% 的漏洞而不需要人工介入。
• 結構性改善：改用 distroless 或更小的基底。python:3.12 有約 200 個套件，distroless 只有 20 個——攻擊面和 CVE 數量都少一個數量級。
• 記錄例外：無法修補的（例如上游還沒發布修補）要有明確的例外記錄與到期日，而不是默默忽略。

核心觀念：安全流程如果讓人痛苦，人就會繞過它。設計時要讓「做對的事」比「繞過」更容易。
