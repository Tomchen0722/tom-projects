LESSON 36

成本管理：從看得懂帳單到主動控制

雲端成本失控幾乎是每間公司的必經之路。這一課給你一套完整的成本治理方法，以及能直接省下 30～50% 的具體手段。

閱讀 25 分企業級

一、先能歸因，才能優化

成本管理的第一步不是省錢，是知道錢花在哪、是誰花的。做不到這件事，任何優化都是瞎猜。

  1. 標籤（Labels）強制化——每個資源必須有 env、owner、cost-center、system。用 Organization Policy 或 Terraform 模組強制。
  2. 專案結構對應組織結構——讓 Folder 層級就能拆出部門帳單。
  3. 計費資料匯出到 BigQuery——這是所有進階分析的基礎。
計費分析 SQL
# 啟用計費資料匯出（Console → 帳單 → 帳單匯出 → BigQuery）
# 之後可以這樣分析：

-- 按專案與服務的月費用
SELECT
  project.id AS project,
  service.description AS service,
  ROUND(SUM(cost), 2) AS cost_usd,
  ROUND(SUM(IFNULL((SELECT SUM(c.amount) FROM UNNEST(credits) c), 0)), 2) AS credits
FROM `PROJECT.billing.gcp_billing_export_v1_XXXXX`
WHERE DATE(usage_start_time) >= DATE_SUB(CURRENT_DATE(), INTERVAL 30 DAY)
GROUP BY 1, 2
ORDER BY cost_usd DESC
LIMIT 25;

-- 找出沒有 owner 標籤的資源（管理黑洞）
SELECT
  service.description,
  sku.description,
  ROUND(SUM(cost), 2) AS cost_usd
FROM `PROJECT.billing.gcp_billing_export_v1_XXXXX`
WHERE DATE(usage_start_time) >= DATE_SUB(CURRENT_DATE(), INTERVAL 30 DAY)
  AND NOT EXISTS (SELECT 1 FROM UNNEST(labels) l WHERE l.key = "owner")
GROUP BY 1, 2
ORDER BY cost_usd DESC;

-- 月對月變化，找出異常成長
SELECT
  service.description AS service,
  ROUND(SUM(IF(DATE_TRUNC(DATE(usage_start_time), MONTH) = DATE_TRUNC(CURRENT_DATE(), MONTH), cost, 0)), 2) AS this_month,
  ROUND(SUM(IF(DATE_TRUNC(DATE(usage_start_time), MONTH) = DATE_SUB(DATE_TRUNC(CURRENT_DATE(), MONTH), INTERVAL 1 MONTH), cost, 0)), 2) AS last_month
FROM `PROJECT.billing.gcp_billing_export_v1_XXXXX`
WHERE DATE(usage_start_time) >= DATE_SUB(DATE_TRUNC(CURRENT_DATE(), MONTH), INTERVAL 1 MONTH)
GROUP BY 1
HAVING this_month > last_month * 1.3 AND this_month > 100
ORDER BY this_month DESC;

二、成本優化的六個層次（依投報率排序）

層次手段典型節省風險
1. 刪除浪費關掉沒人用的資源、閒置 IP、孤兒磁碟、舊快照10~20%極低
2. 調整規格Rightsizing，依實際用量縮小機器15~30%低
3. 排程非正式環境下班關機、週末停機非prod 省 60%低
4. 定價機制承諾折扣、Spot VM25~60%中（承諾有綁約）
5. 架構優化加快取/CDN、改用無伺服器、資料分層20~50%中高（要改程式）
6. 服務替換換用更便宜的服務視情況高
小心踩雷
順序不能顛倒。最常見的錯誤是先簽了三年承諾折扣，之後才發現有 40% 的機器根本不需要——結果你對著浪費簽了長約，而且解不掉。
永遠先做 1～3 層（清理與調整），穩定兩個月後再談承諾折扣。

三、找出浪費：可直接執行的檢查

浪費檢查清單
# ① 閒置的靜態 IP（每個約 $7/月）
gcloud compute addresses list --filter="status=RESERVED" \
  --format="table(name, region, address)"

# ② 未掛載的磁碟（持續收費）
gcloud compute disks list --filter="-users:*" \
  --format="table(name, zone, sizeGb, type)"

# ③ 停止但未刪除的 VM（磁碟仍收費）
gcloud compute instances list --filter="status=TERMINATED"

# ④ 舊的快照
gcloud compute snapshots list \
  --filter="creationTimestamp<'-P90D'" \
  --format="table(name, diskSizeGb, creationTimestamp)"

# ⑤ 沒有流量的負載平衡器
gcloud compute forwarding-rules list --global

# ⑥ Rightsizing 建議（GCP 自動分析過去用量）
gcloud recommender recommendations list \
  --project=$PROJECT --location=asia-east1-b \
  --recommender=google.compute.instance.MachineTypeRecommender \
  --format="table(description, primaryImpact.costProjection.cost.units)"

# ⑦ 閒置 VM 建議
gcloud recommender recommendations list \
  --project=$PROJECT --location=asia-east1-b \
  --recommender=google.compute.instance.IdleResourceRecommender

四、承諾使用折扣（CUD）的正確用法

類型綁定對象彈性折扣
資源型 CUD特定 Region 的特定機器家族低——換機型就不適用1年 37% / 3年 55%
支出型 CUD
(Flexible)		每小時的美元支出金額高——跨機型、跨 Region 都算1年 28% / 3年 46%
實務提醒
建議策略：階梯式承諾。
① 分析過去 12 個月每小時的資源用量，找出最低水位（永遠不會低於的那條線）。
② 對這條線的 60～70% 簽 1 年約。不要簽到 100%——業務萎縮、架構改變、遷移到無伺服器都會讓用量下降。
③ 若一年後用量確實穩定，再對更低的部分加簽 3 年約。
④ 折扣不足的部分用隨用隨付，享受彈性。

寧可少省 5%，也不要被綁三年付不需要的錢。

五、自動化的成本護欄

自動成本剎車
# 預算警報 → Pub/Sub → Cloud Function → 自動處置
# (第 3 課提過「預算只會寄信」，這裡把它變成真正的剎車)

# ① 建立 Pub/Sub 主題
gcloud pubsub topics create budget-alerts

# ② 在預算設定中連結這個主題（Console 操作）

# ③ Cloud Function 處理
cat > main.py <<'EOF'
import base64, json, os
from googleapiclient import discovery

def handle_budget_alert(event, context):
    data = json.loads(base64.b64decode(event["data"]).decode("utf-8"))
    cost = data.get("costAmount", 0)
    budget = data.get("budgetAmount", 1)
    ratio = cost / budget

    if ratio >= 1.0:
        # 超過 100%：停用非正式環境的 VM
        stop_nonprod_instances()
        notify_slack(f"⚠️ 預算超支 {ratio:.0%}，已停止非正式環境資源")
    elif ratio >= 0.9:
        notify_slack(f"⚠️ 預算已用 {ratio:.0%}，請檢查")

def stop_nonprod_instances():
    compute = discovery.build("compute", "v1")
    project = os.environ["PROJECT_ID"]
    result = compute.instances().aggregatedList(
        project=project, filter='labels.env!=prod').execute()
    for zone, data in result.get("items", {}).items():
        for inst in data.get("instances", []):
            compute.instances().stop(
                project=project,
                zone=zone.split("/")[-1],
                instance=inst["name"]).execute()
EOF
小心踩雷
「停用計費帳戶」是核彈級選項，慎用。它會讓專案內所有服務立即停止，包括正式環境。
只有在「絕對不能超支」的實驗專案（例如教學帳號、研究專案）才適合。正式環境請用「停止非 prod 資源」這類有選擇性的處置。

六、FinOps：把成本變成工程文化

  1. 成本可見性下放到團隊——每個團隊有自己的儀表板，看得到自己花了多少。看不到的東西沒有人會優化。
  2. 把成本納入設計審查——新架構提案要附上成本估算（用 Pricing Calculator）。
  3. 單位經濟指標——不要只看總成本，要看「每筆訂單的雲端成本」「每個活躍使用者的成本」。總成本上升但單位成本下降，其實是好事。
  4. 定期檢討會——每月一次，30 分鐘，看趨勢、看異常、追蹤優化項目。
  5. 慶祝節省——把省下的錢明確歸功給團隊，形成正向循環。

自我檢測

這個月帳單突然多了 $5000，怎麼在 30 分鐘內找出原因？
三步驟，用 BigQuery 計費資料由粗到細：

① 哪個服務？——按 service.description 分組，比較本月與上月。通常會直接看到某一項暴增。
② 哪個專案 / 哪個 SKU？——鎖定服務後，往下切到 project.id 和 sku.description。SKU 會告訴你是「運算」「儲存」還是「網路流出」。
③ 哪一天開始的？——按日期畫出趨勢，找到起始日，再對照那天的變更記錄（部署、Terraform apply、設定變更）。

最常見的五個真兇：
• 忘記刪除的 GPU 執行個體或大型 VM
• BigQuery 的失控查詢（某個排程或 BI 工具）
• 網路流出費——通常是跨區流量、或是資料被大量下載
• 日誌量暴增（有人開了 DEBUG 層級）
• 測試環境的自動擴充失控

治本：設定成本異常偵測（Cost Anomaly Detection），它會自動學習你的用量模式並在偏離時告警，不用等月底。
CFO 要求「明年雲端成本降 30%」，但業務量預計成長 50%。可能嗎？
總成本降 30% 同時業務成長 50%，等於單位成本要降 53%。這很困難但不是不可能——取決於目前有多浪費。

誠實的做法是先做基線評估，再承諾數字：

① 量化目前的浪費（1～2 週）——跑一次完整的資源盤點與 Rightsizing 分析。如果目前平均 CPU 使用率只有 15%，那有很大空間；如果已經 70%，那空間有限。

② 分階段目標：
  • Q1：清理浪費 + Rightsizing + 非prod排程 → 降 20～25%，零風險
  • Q2：承諾折扣（對清理後的穩定基線）→ 再降 15～20%
  • Q3-Q4：架構優化（CDN、快取、資料分層、無伺服器化）→ 再降 10～20%

③ 改用單位成本當指標——向 CFO 說明「每筆交易的雲端成本從 $0.05 降到 $0.023」比「總成本降 30%」更能反映效率。如果業務成長 50% 而總成本只成長 5%，那已經是巨大的成功。

④ 誠實說明取捨——某些優化（例如降低冗餘度、縮短日誌保留）會增加風險，需要業務方一起決定。

不要一開始就承諾 30%。先給「無風險可達成的數字」，再談需要投入資源的部分。
團隊反對設定成本上限，說「會影響服務穩定」。怎麼平衡？
他們的擔心是合理的——粗糙的成本上限確實可能造成服務中斷。解法是分層設計，不是二選一。

正確的做法：

① 正式環境：只警報，不自動處置——設定多段警報（80%/100%/120%），通知到 on-call，由人判斷。正式環境的可用性優先於成本。

② 非正式環境：積極自動化——dev/staging 可以設定自動停機、自動縮容。這裡的成本節省最大且風險最低。

③ 用「配額」而非「開關」做正式環境的護欄——例如：
  • Cloud Run 設 max-instances（限制爆發上限，但不影響正常運作）
  • BigQuery 設每日查詢量配額（防止單一失控查詢）
  • GKE 設 Cluster Autoscaler 節點上限
  這些是「防止異常」而非「限制正常」。

④ 把成本異常當成事故訊號——成本突然暴增，往往代表有東西壞了（無限迴圈、重試風暴、被攻擊）。從這個角度看，成本監控其實是可靠性監控的一部分。這個框架通常能說服工程團隊。

把對話從「省錢 vs 穩定」轉成「異常偵測」，雙方就站在同一邊了。
