LESSON 23

Docker 速成：把應用裝進箱子

容器是現代雲端的通用貨幣。這一課用最短的路徑讓你理解容器的原理，並寫出一個符合正式環境標準的 Dockerfile。

操作 45 分實作

一、容器解決什麼問題

「在我電腦上明明可以跑」——這句話造成的浪費，一年大概能繞地球好幾圈。原因是環境差異：Python 版本、系統套件、環境變數、檔案路徑。

生活比喻
虛擬機 vs 容器：搬家的兩種方式。

虛擬機 = 把整棟房子連地基一起搬走。包含作業系統、驅動程式、所有東西。完整但笨重（幾 GB，開機要分鐘）。

容器 = 只搬走你的家具和個人物品，房子（作業系統核心）借用當地的。輕巧（幾十 MB，啟動只要毫秒）。

關鍵：容器共用主機的 Linux 核心，但擁有自己獨立的檔案系統、程序空間、網路空間。所以它輕得像程序，隔離得像機器。
虛擬機容器
包含完整作業系統 + 應用只有應用與其依賴
大小幾 GB幾十 MB ~ 幾百 MB
啟動時間30 秒 ~ 幾分鐘毫秒 ~ 幾秒
隔離強度強（硬體層虛擬化）中（核心層命名空間）
單機可跑數量數個 ~ 數十個數百個

二、三個核心概念

Dockerfile → Image → Container
Dockerfile（食譜）
   「怎麼做出這道菜」— 一行行的建置指令
        ↓ docker build
Image 映像（半成品，唯讀）
   「做好的冷凍調理包」— 可以複製、可以分享、不可修改
        ↓ docker run
Container 容器（執行中的實例）
   「加熱後端上桌的菜」— 可以有很多份，各自獨立

三、寫一個合格的 Dockerfile

動手實作

實作：從差的寫法改進到好的寫法

  1. 先看一個典型的糟糕範例（很多教學都這樣寫）：
    bash
    # ❌ 問題很多的寫法
FROM python:3.12          # 完整版，約 1GB
COPY . .                  # 一次複製全部，任何檔案改動都讓快取失效
RUN pip install -r requirements.txt
CMD python app.py         # 用 root 執行、用開發伺服器
  2. 改進版本，每一行都有理由：
    bash
    # ✅ 正式環境水準的寫法

# --- 第一階段：建置 ---
FROM python:3.12-slim AS builder

WORKDIR /app

# 只先複製依賴清單，讓 Docker 快取這一層
# 之後只改程式碼時，這一層不用重跑（省下大量建置時間）
COPY requirements.txt .
RUN pip install --no-cache-dir --user -r requirements.txt

# --- 第二階段：執行 ---
FROM python:3.12-slim

# 建立非 root 使用者（資安基本要求）
RUN useradd --create-home --shell /bin/bash appuser

WORKDIR /app

# 只從建置階段複製「安裝好的套件」，不帶編譯工具進來
COPY --from=builder /root/.local /home/appuser/.local
COPY --chown=appuser:appuser . .

ENV PATH=/home/appuser/.local/bin:$PATH \
    PYTHONUNBUFFERED=1 \
    PYTHONDONTWRITEBYTECODE=1

USER appuser

EXPOSE 8080

HEALTHCHECK --interval=30s --timeout=3s --start-period=5s \
  CMD python -c "import urllib.request; urllib.request.urlopen('http://localhost:8080/healthz')"

CMD ["gunicorn", "--bind", "0.0.0.0:8080", "--workers", "2", "--threads", "4", "main:app"]
  3. 建立 .dockerignore（忘記寫這個會把 .git 和 node_modules 打包進去）：
    bash
    cat > .dockerignore <<'EOF'
.git/
.gitignore
__pycache__/
*.pyc
*.pyo
.env
.venv/
venv/
node_modules/
*.md
tests/
.pytest_cache/
Dockerfile
.dockerignore
EOF
  4. 在 Cloud Shell 建置與測試：
    bash
    docker build -t task-api:v1 .
docker images | grep task-api          # 看映像大小

docker run -d -p 8080:8080 --name test task-api:v1
curl localhost:8080
docker logs test
docker exec -it test /bin/bash          # 進去看看
docker stop test && docker rm test

四、映像瘦身：為什麼重要

映像大小直接影響三件事：部署速度、冷啟動時間、儲存與傳輸成本。

基底映像大小說明
python:3.12約 1.0 GB完整 Debian + 編譯工具，不要用在正式環境
python:3.12-slim約 130 MB大多數情況的好選擇
python:3.12-alpine約 50 MB最小，但 C 擴充套件常編譯失敗（musl libc 相容性問題）
gcr.io/distroless/python3約 50 MB最安全：沒有 shell、沒有套件管理器，攻擊面極小
實務提醒
Alpine 不一定是好選擇。它用 musl libc 而非 glibc，導致很多 Python 套件（numpy、pandas、psycopg2）要從原始碼編譯，建置時間從 30 秒變成 10 分鐘，而且效能可能更差。
建議順序：先用 -slim，如果安全稽核要求極小攻擊面，再評估 distroless。Alpine 留給 Go 這類靜態編譯的語言。

五、多階段建置的威力（Go 範例）

Go 的多階段建置
# 第一階段：編譯（需要完整的 Go 工具鏈，約 800MB）
FROM golang:1.22 AS builder
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 GOOS=linux go build -ldflags="-s -w" -o /app/server .

# 第二階段：只放編譯結果（最終映像只有幾 MB！）
FROM gcr.io/distroless/static-debian12
COPY --from=builder /app/server /server
USER nonroot:nonroot
ENTRYPOINT ["/server"]

# 結果：最終映像約 8 MB，冷啟動 < 100ms

六、容器的十條實務準則

  1. 一個容器只跑一個主程序。不要在裡面塞 nginx + app + cron。
  2. 不要用 root 執行。加 USER 指令。
  3. 不要把密鑰寫進映像。映像的每一層都可以被解出來，docker history 就看得到。用環境變數或 Secret Manager。
  4. 用具體的版本標籤，不要用 latest。latest 讓你無法知道正在跑什麼版本，也無法可靠回滾。
  5. 日誌輸出到 stdout/stderr。不要寫進容器內的檔案——容器一消失就沒了。
  6. 設計成可以隨時被殺掉。處理 SIGTERM，優雅關閉連線。
  7. 不要在容器內存資料。容器的檔案系統是暫時的。
  8. 加 HEALTHCHECK。讓編排系統知道你的服務是否真的健康。
  9. 把常變的東西放在 Dockerfile 後面。最大化快取利用。
  10. 定期重建映像。基底映像的安全修補需要重建才會套用。

  • 能解釋容器與虛擬機的差異

自我檢測

同事說「我把資料庫密碼寫在 Dockerfile 的 ENV 裡，反正映像是私有的」。你的回應？
這是嚴重的安全問題，私有倉庫不是保護。三個理由：
① 映像層是可解析的——任何拿到映像的人執行 docker history --no-trunc 就能看到所有 ENV 值和 RUN 指令，不需要執行容器。
② 權限範圍太大——能拉映像的人不等於該知道正式密碼的人。CI 系統、外包、備份系統都可能拿到映像。
③ 無法輪換——密碼改了要重建映像、重新部署所有環境。

正確做法：密鑰存 Secret Manager，執行時注入：
bash
gcloud run services update my-app --set-secrets=DB_PASSWORD=db-password:latest
或在 GKE 用 Secret + Workload Identity。原則：映像應該是「無環境差異」的——同一個映像可以部署到 dev 和 prod，只有注入的設定不同。
你的 Docker 建置每次都要 8 分鐘，其中 7 分鐘在 pip install。怎麼優化？
問題出在層的順序，讓快取失效了。

如果 Dockerfile 寫成：
bash
COPY . .                              # 任何檔案改動都讓這一層失效
RUN pip install -r requirements.txt   # 所以這一層也永遠要重跑
改成：
bash
COPY requirements.txt .               # 只有這個檔案改動才失效
RUN pip install -r requirements.txt   # 依賴沒變就用快取
COPY . .                              # 程式碼改動只影響這一層
效果：改程式碼時建置時間從 8 分鐘降到 10 秒。

Docker 快取的規則很簡單：某一層失效，之後所有層都失效。所以把「最少變動的東西」放最前面。這個原則適用於所有語言（npm、go mod、maven 都一樣）。

額外優化：在 Cloud Build 啟用 --cache-from 使用前一次的映像當快取。
容器跑起來後立刻退出，docker logs 什麼都沒有。怎麼查？
「立刻退出且無日誌」通常是四種情況之一：
① 主程序在前景結束了——容器的生命跟 PID 1 綁定。如果 CMD 是 service nginx start（會背景執行後返回），容器就會立刻結束。要用 nginx -g 'daemon off;' 讓它在前景跑。
② 程式啟動就崩潰——但日誌被緩衝住沒輸出。Python 加 PYTHONUNBUFFERED=1，Node 通常沒問題。
③ ENTRYPOINT / CMD 語法錯誤——用 shell 形式 CMD python app.py 和 exec 形式 CMD ["python","app.py"] 對訊號處理不同。
④ 架構不符——在 M1 Mac 建的 arm64 映像，跑在 amd64 的 Cloud Run 上會失敗。用 docker build --platform=linux/amd64。

除錯技巧：覆寫進入點進去看看
bash
docker run -it --entrypoint /bin/sh my-image
