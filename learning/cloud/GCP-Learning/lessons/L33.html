LESSON 33

Cloud Logging 與 Monitoring：看得見才管得動

系統出事時，你有多快能知道「哪裡壞了」？這一課建立完整的可觀測性——日誌、指標、追蹤、告警。沒有這一層，前面所有架構都是黑箱。

操作 45 分實作

一、可觀測性的三根支柱

日誌 Logs指標 Metrics追蹤 Traces
回答什麼「發生了什麼事」「現在狀況如何」「時間花在哪裡」
資料形態離散的事件記錄時間序列的數字一個請求跨服務的完整路徑
GCP 服務Cloud LoggingCloud MonitoringCloud Trace
典型用途除錯、稽核、事後調查儀表板、告警、容量規劃找出微服務中的效能瓶頸
成本特性量大時很貴相對便宜抽樣後便宜

二、Cloud Logging：日誌的收集與查詢

GCP 的服務預設就會產生日誌，不用你做任何事。你的應用程式只要把日誌寫到 stdout／stderr，Cloud Run、GKE、Compute Engine 上的代理會自動收集。

結構化日誌：最重要的一個習慣

結構化日誌
# ❌ 純文字日誌：無法篩選、無法分析
print("User 12345 failed to login from 1.2.3.4")

# ✅ 結構化日誌：每個欄位都可以查詢與聚合
import json, sys

def log(severity, message, **fields):
    print(json.dumps({
        "severity": severity,          # Cloud Logging 會自動識別這個欄位
        "message": message,
        **fields
    }), file=sys.stdout)

log("ERROR", "登入失敗",
    user_id="12345",
    source_ip="1.2.3.4",
    reason="invalid_password",
    attempt_count=3,
    trace=f"projects/{PROJECT}/traces/{trace_id}")   # 關聯到 Cloud Trace
實務提醒
加上 trace 欄位後，Cloud Logging 會自動把同一個請求的所有日誌串在一起，而且能從 Cloud Trace 的時間軸直接跳到對應日誌。
這在除錯微服務時價值極高——你能看到一個請求經過 5 個服務時，每一站發生了什麼。

查詢語法

Logging 查詢語法
# 基本篩選
resource.type="cloud_run_revision"
resource.labels.service_name="task-api"
severity>=ERROR
timestamp>="2026-07-31T00:00:00Z"

# 查結構化欄位
jsonPayload.user_id="12345"
jsonPayload.attempt_count>3

# 文字搜尋與正則
textPayload:"connection refused"
jsonPayload.message=~"timeout.*database"

# 排除雜訊（很實用）
resource.type="k8s_container"
severity>=WARNING
NOT jsonPayload.message:"health check"

# 找出 HTTP 5xx
httpRequest.status>=500
bash
# CLI 查詢
gcloud logging read \
  'resource.type="cloud_run_revision" AND severity>=ERROR' \
  --limit=50 --format=json --freshness=1h

# 即時追蹤（像 tail -f）
gcloud beta logging tail 'resource.type="cloud_run_revision"'

三、日誌路由：控制成本的關鍵

小心踩雷
日誌是最容易失控的成本項目。Cloud Logging 每月前 50GB 免費，之後每 GB 約 $0.50。
一個中型 GKE 叢集開啟所有日誌，一個月產生 2TB 是很正常的——那就是 $1000/月，而其中 95% 你永遠不會看。
bash
# ① 建立排除規則：直接丟棄不需要的日誌（不收費）
gcloud logging sinks update _Default \
  --add-exclusion=name=exclude-health-checks,\
filter='httpRequest.requestUrl=~"/healthz|/readyz"'

gcloud logging sinks update _Default \
  --add-exclusion=name=exclude-debug,\
filter='severity<INFO'

# ② 建立 sink 把日誌路由到便宜的儲存
#    稽核日誌要留 7 年 → 存 GCS Archive（比 Logging 便宜 100 倍）
gcloud logging sinks create audit-archive \
  storage.googleapis.com/projects/PROJ/buckets/audit-logs \
  --log-filter='logName:"cloudaudit.googleapis.com"'

#    需要分析的日誌 → 送 BigQuery
gcloud logging sinks create app-logs-bq \
  bigquery.googleapis.com/projects/PROJ/datasets/logs \
  --log-filter='resource.type="cloud_run_revision" AND severity>=WARNING'

# ③ 調整保留期（預設 30 天）
gcloud logging buckets update _Default \
  --location=global --retention-days=14
實務提醒
日誌成本管理的黃金組合：
① 排除健康檢查、除錯層級的日誌（省 60～80%）
② 路由需要長期保存的到 GCS Archive
③ 路由需要分析的到 BigQuery（分析能力更強且更便宜）
④ Logging 本身只保留最近 14～30 天供即時排查

這套做完通常能把日誌費用降到原本的 10～20%，而且能力更強。

四、Cloud Monitoring：指標與儀表板

動手實作

實作：建立告警政策

  1. 從 Console 或 CLI 建立一個「錯誤率過高」的告警：
    bash
    cat > alert-policy.json <<'EOF'
{
  "displayName": "Cloud Run 5xx 錯誤率過高",
  "combiner": "OR",
  "conditions": [{
    "displayName": "5xx > 5%",
    "conditionThreshold": {
      "filter": "resource.type=\"cloud_run_revision\" AND metric.type=\"run.googleapis.com/request_count\" AND metric.label.response_code_class=\"5xx\"",
      "aggregations": [{
        "alignmentPeriod": "300s",
        "perSeriesAligner": "ALIGN_RATE",
        "crossSeriesReducer": "REDUCE_SUM"
      }],
      "comparison": "COMPARISON_GT",
      "thresholdValue": 0.05,
      "duration": "300s"
    }
  }],
  "alertStrategy": {
    "autoClose": "1800s"
  },
  "notificationChannels": []
}
EOF

gcloud alpha monitoring policies create --policy-from-file=alert-policy.json
  2. 建立通知管道：
    bash
    # Email
gcloud beta monitoring channels create \
  --display-name="工程團隊" --type=email \
  --channel-labels=email_address=eng@corp.com

# Slack / PagerDuty 也支援
gcloud beta monitoring channels list
  3. 建立自訂指標（應用程式層級的業務指標）：
    bash
    from google.cloud import monitoring_v3
import time

client = monitoring_v3.MetricServiceClient()
project_name = f"projects/{PROJECT_ID}"

series = monitoring_v3.TimeSeries()
series.metric.type = "custom.googleapis.com/orders/completed"
series.resource.type = "global"
series.metric.labels["store_id"] = "ST001"

point = monitoring_v3.Point()
point.value.int64_value = 1
point.interval.end_time.seconds = int(time.time())
series.points = [point]

client.create_time_series(name=project_name, time_series=[series])

五、告警設計：避免告警疲勞

小心踩雷
最危險的監控狀態不是「沒有告警」，是「告警太多所以大家都忽略」。
如果一個團隊每天收到 50 則告警，那第 51 則（真正的事故）也會被忽略。

好的告警必須滿足三個條件：

  1. 可行動（actionable）——收到告警的人知道該做什麼。「CPU 80%」不可行動，「使用者無法完成結帳」可行動。
  2. 影響使用者——不影響使用者的異常應該記錄下來週會檢討，不該半夜叫醒人。
  3. 不重複——一個根因不應該觸發 20 則告警。
❌ 不好的告警✅ 好的告警
CPU 使用率 > 80%結帳 API 的 P95 延遲 > 2 秒，持續 5 分鐘
磁碟使用率 > 70%磁碟預計 4 小時後寫滿
有一台機器重啟了服務可用實例數 < 2
記憶體用量上升錯誤預算（error budget）本月已消耗 80%

六、Cloud Trace 與 Profiler

Cloud Trace 顯示一個請求在各服務間的時間分配。當使用者說「很慢」，Trace 直接告訴你慢在哪一段。

bash
# OpenTelemetry 自動檢測（Python）
pip install opentelemetry-distro opentelemetry-exporter-gcp-trace
opentelemetry-bootstrap -a install

# 執行時自動追蹤所有 HTTP 請求、資料庫查詢
OTEL_TRACES_EXPORTER=gcp_trace \
OTEL_SERVICE_NAME=task-api \
opentelemetry-instrument python main.py

Cloud Profiler 則是持續性的效能剖析——它會告訴你「哪一個函式吃掉最多 CPU」，且開銷極低（可以在正式環境常駐）。

七、本課檢核

  • 知道日誌、指標、追蹤各自回答什麼問題
  • 會寫結構化日誌並關聯 trace ID
  • 會用排除規則與 sink 控制日誌成本
  • 能設計「可行動、影響使用者、不重複」的告警
  • 知道 Cloud Trace 用來定位跨服務的效能瓶頸

自我檢測

使用者回報「網站很慢」，但你的儀表板顯示所有指標正常。怎麼查？
「平均值正常」不代表「使用者體驗正常」。這是監控最經典的盲點。

① 看百分位數而非平均——平均 200ms 可能是「95% 的請求 100ms，5% 的請求 10 秒」。要看 P50 / P95 / P99。P99 才代表最慢的那群使用者。
② 按維度切分——是所有使用者都慢，還是特定地區、特定裝置、特定 API 路徑？用 Cloud Monitoring 的 group by 拆開看。
③ 看 Cloud Trace 的慢請求樣本——直接篩選延遲 > 3 秒的追蹤，看時間花在哪一段。
④ 檢查前端——後端 100ms，但前端載入 5MB 的 JS，使用者體感就是慢。後端指標看不到這個，需要 RUM（真實使用者監控）。
⑤ 問清楚「慢」的定義——是首次載入慢？某個操作慢？特定時段慢？

教訓：要監控使用者體驗，不是監控伺服器。SLI 應該定義在使用者感知得到的層面。
Cloud Logging 每月 $2400，怎麼降到 $300 以下且不損失排查能力？
分四步，累積效果通常能降 85～90%：

① 找出誰在產生日誌：
bash
gcloud logging read 'timestamp>="2026-07-01"' --format=json \
  | jq -r '.resource.type' | sort | uniq -c | sort -rn
通常會發現 70% 來自一兩個來源（GKE 的 kubelet 日誌、健康檢查、某個 debug 沒關掉的服務）。

② 建立排除規則——健康檢查、DEBUG/INFO 層級的雜訊、Kubernetes 系統元件日誌。這一步通常就砍掉 60～70%。

③ 把長期保存需求路由到 GCS——稽核日誌存 Archive 等級，成本從 $0.50/GB 降到 $0.0012/GB（便宜 400 倍）。

④ 把分析需求路由到 BigQuery——需要做日誌分析的話，BigQuery 的儲存與查詢都比 Logging 便宜，而且能寫 SQL。

⑤ 縮短 Logging 保留期到 14 天（即時排查用），更久的去 GCS/BQ 查。

排查能力不但沒下降，反而更強——因為雜訊少了，且有 SQL 可以分析。
團隊說「我們的告警太多，大家都關掉通知了」。你怎麼處理？
這是嚴重的可靠性風險，要當成事故處理。但解法不是叫大家「認真看告警」，而是修好告警系統。

步驟：
① 盤點——統計過去 30 天每則告警的觸發次數與「實際採取行動的次數」。行動率低於 20% 的告警都是雜訊。
② 大膽刪除——把所有雜訊告警直接關掉（不是調高門檻，是關掉）。心理上很難，但保留半殘的告警比沒有更糟。
③ 重建，從 SLO 出發——定義 2～4 個真正重要的使用者體驗指標（例如「結帳成功率 > 99.5%」「首頁 P95 < 1 秒」），只對這些設告警。從 50 則降到 5 則。
④ 分級——
  • P1 立即處理：呼叫 on-call，半夜也叫。一週不該超過 1～2 次。
  • P2 上班時間處理：進工單系統。
  • P3 趨勢觀察：進週報，不發通知。
⑤ 建立回饋循環——每則 P1 告警事後都要問「這則告警幫到我們了嗎？」沒幫到就調整或刪除。

SRE 的準則：如果一則告警不需要人立即做什麼，它就不該是告警。
