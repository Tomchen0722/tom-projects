LESSON 02

GCP 的三層地圖：組織、資料夾、專案

這是整套 GCP 最重要的心智模型。權限、計費、配額、稽核全部掛在這棵樹上。搞懂它，後面所有「為什麼我沒權限」的問題都會自己解開。

閱讀 22 分核心觀念

一、資源階層：一棵由上往下長的樹

GCP 把所有東西掛在一棵樹上，由上到下四層：

資源階層
組織 Organization（例：mycompany.com）
  └── 資料夾 Folder（例：正式環境）
        └── 資料夾 Folder（例：電商事業部）
              └── 專案 Project（例：shop-prod-001）
                    ├── 虛擬機 VM instance
                    ├── 儲存桶 Cloud Storage bucket
                    └── 資料庫 Cloud SQL instance

四層的角色分工是這樣的：

層級是什麼什麼時候會有關鍵性質
Organization整間公司的根節點，綁定一個網域你有 Google Workspace 或 Cloud Identity 才會有；個人帳號沒有政策從這裡往下強制繼承
Folder部門／環境的分組只有 Organization 底下才能建可以巢狀，最多 10 層
Project資源的容器，也是最重要的隔離單位一定會有，這是最小可用單位計費、配額、API 啟用、權限的邊界
Resource實際的服務實體你開出來的東西一定屬於某個專案
生活比喻
把它想成一間公司的組織圖：

Organization = 公司本身。董事會在這裡訂「全公司不准把資料存到海外」這種規矩。
Folder = 事業處。事業處長可以再加自己的規矩，但不能推翻董事會的。
Project = 一個專案小組。有自己的預算（計費）、自己的門禁（IAM）、自己的辦公室（資源）。
Resource = 小組裡的桌椅電腦。

重點：權限跟政策只會往下流，不會往上流。你在某個 Project 是管理員，不代表你能碰隔壁 Project。

二、專案（Project）為什麼是核心

每個專案有三個識別資訊，很容易搞混：

欄位範例可否修改用途
Project Name電商正式環境✅ 可改給人看的顯示名稱
Project IDshop-prod-4a7b2❌ 建立後永不可改全球唯一，指令與 API 都用這個
Project Number739284016523❌ 系統自動產生部分內部 API 與服務帳號會用到
小心踩雷
Project ID 全球唯一且永遠不能改。意思是全世界只要有人用過 test 這個 ID，你就再也拿不到。而且刪掉專案後 ID 也不會釋放。
請一開始就用有規則的命名：{公司}-{系統}-{環境}-{序號}，例如 acme-shop-prod-01。

一個專案該裝多少東西？

這是新手最常問、也最沒有標準答案的問題。實務上的判斷準則：

  • 不同環境一定要分專案：dev / staging / prod 各一個。理由不是「比較整齊」，而是權限與爆炸半徑——實習生在 dev 誤刪東西，不會碰到 prod。
  • 不同計費對象要分專案：如果財務要拆帳到部門，就照部門分。
  • 配額會互相排擠的要分專案：配額是專案級的。一個吃 CPU 的批次系統和一個線上服務放同一個專案，批次跑起來可能把配額吃光，導致線上服務擴不出去。
  • 不要為了每個微服務開一個專案：管理成本會爆炸。同一個系統的多個服務放同一個專案，用命名和標籤區分就好。

三、政策繼承：Organization Policy

這是企業級 GCP 最重要的護欄機制。你在上層設一條政策，底下所有專案強制遵守，而且下層無法解除。

組織政策範例
# 常見的企業護欄政策（Organization Policy Constraints）

constraints/gcp.resourceLocations
  → 限制資源只能開在指定的 Region（例如只准 asia-east1）
     用途：法遵、資料落地要求

constraints/compute.requireShieldedVm
  → 所有虛擬機必須啟用 Shielded VM（安全開機、完整性監控）

constraints/storage.publicAccessPrevention
  → 禁止任何 Cloud Storage 桶設為公開
     用途：防止最經典的資料外洩事故

constraints/iam.disableServiceAccountKeyCreation
  → 禁止產生服務帳號金鑰檔（.json）
     用途：金鑰外洩是雲端最大宗的入侵途徑

constraints/compute.vmExternalIpAccess
  → 白名單制，只有列出的 VM 能有外部 IP
實務提醒
政策是「拒絕優先」的：上層說不行，下層再怎麼設也不行。這跟 IAM 權限（往下繼承、可累加）的邏輯不同，兩者要分開理解。
面試或考證照時，這是高頻考點：「如何確保全公司沒有人能建立公開的儲存桶？」答案永遠是 Organization Policy，不是 IAM。

四、計費帳戶（Billing Account）

計費帳戶跟資源階層是兩棵不同的樹，只在專案這一層交會。這點常被誤解。

兩棵樹的關係
[資源樹]                    [計費樹]
Organization                Billing Account（綁信用卡）
    │                              │
  Folder                           │
    │                              │
  Project  ←───── 連結 ─────→      │
                             （一個計費帳戶可付很多專案的錢）
  • 一個專案只能連到一個計費帳戶。
  • 一個計費帳戶可以付很多專案的錢。
  • 解除連結 = 專案裡的服務會停掉（資料通常保留一段時間，但別依賴這個）。
  • 計費權限跟資源權限是分開的：財務可以只有計費檢視權，完全看不到裡面有什麼機器。

五、標籤（Labels）與標記（Tags）

階層只能做到「哪個專案」，但實務上你常需要跨專案分類。這時用 Labels：

bash
# 為資源加上標籤（key-value，最多 64 組）
gcloud compute instances add-labels my-vm \
    --labels=env=prod,team=payment,cost-center=cc1024,owner=tom

# 之後就能在帳單裡按 label 拆帳
# 也能用 label 篩選資源
gcloud compute instances list --filter="labels.env=prod"
實務提醒
從第一天就強制打標籤。建議至少四個必填：env（環境）、owner（負責人）、cost-center（成本中心）、system（所屬系統）。
三個月後當帳單長到你看不懂時，沒有標籤的資源你會完全查不出是誰開的、能不能刪。這是幾乎每間公司都踩過的坑。

六、本課小結

  • 畫得出 Organization → Folder → Project → Resource 的樹
  • 知道 Project ID 不可修改、全球唯一
  • 能說明為什麼 dev / prod 要分不同專案
  • 知道 Organization Policy 是強制護欄、IAM 是權限授予，兩者不同
  • 知道計費帳戶和資源階層是兩棵樹

自我檢測

你是某專案的 Owner，想在 us-east1 開一台機器，卻一直失敗。可能原因是什麼？
很可能是上層設了 constraints/gcp.resourceLocations，限制只能用特定 Region。Owner 權限也無法覆寫組織政策——這正是政策的設計目的。你要找組織管理員調整政策，而不是想辦法提權。
公司要求「行銷部門的雲端花費要獨立結算，但共用同一張公司信用卡」。怎麼做？
把行銷部門的專案放進一個 Folder，所有專案連到同一個計費帳戶（同一張卡），然後在計費報表中按 Folder 或 Label 篩選來拆帳。
不需要開第二個計費帳戶——那反而會讓財務多對一張帳單。
開發團隊說「我在 dev 專案測試沒問題，上 prod 就 403 權限錯誤」。你怎麼排查？
三個方向依序查：
① IAM 角色沒同步——服務帳號在 prod 專案沒被授予對應角色（最常見）。
② API 沒啟用——每個專案要各自啟用 API。
③ 組織政策差異——prod 所在的 Folder 可能有 dev 沒有的限制。
先看 Cloud Logging 的錯誤訊息，GCP 的 403 通常會明確寫出缺哪個權限。
