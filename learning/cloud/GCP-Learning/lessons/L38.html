LESSON 38

上雲遷移：策略、評估與實際步驟

企業上雲不是技術問題，是專案管理問題。這一課給你一套完整的遷移方法論，以及每個階段最容易踩的坑。

閱讀 28 分企業級

一、遷移的 6R 策略

每一個系統都要個別決定用哪種策略。不要對所有系統套用同一種。

策略做什麼工作量雲端效益適合
Rehost
直接搬		VM 對 VM 搬過去最低最低地端機房到期、要快速撤離
Replatform
小改後搬		改用託管服務（自架 MySQL → Cloud SQL）低~中中最常見的甜蜜點
Refactor
重構		改造成雲原生（單體 → 微服務 + 容器）高最高核心系統、有長期投資價值
Repurchase
換買 SaaS		自建 CRM → 改用 Salesforce中高非核心的通用功能
Retire
退役		直接關掉零—盤點後發現沒人在用
通常佔 10~20%，這是最划算的一項
Retain
保留		暫時不動零—法規限制、剛投資完硬體、即將汰換
實務提醒
盤點階段最大的驚喜通常是「Retire」。幾乎每間公司都會發現 10～20% 的伺服器沒有人知道它在做什麼，關掉也沒人抱怨。
先做這一項——它零成本、零風險，而且立刻減少後續的遷移工作量。

二、遷移的五個階段

遷移五階段
① 評估 Assess（2~8 週）
    盤點資產、相依關係、成本、風險
        ↓
② 規劃 Plan（2~4 週）
    分批、排序、landing zone 設計、團隊準備
        ↓
③ 準備 Prepare（4~8 週）
    建立 landing zone、網路連通、身分整合、CI/CD
        ↓
④ 遷移 Migrate（數月~數年）
    分批執行，每批：搬 → 驗證 → 切換 → 觀察
        ↓
⑤ 優化 Optimize（持續）
    成本優化、雲原生化、自動化

① 評估：你必須知道的四件事

  1. 有什麼——所有伺服器、資料庫、儲存、網路設備的清單與規格。用 Migration Center（GCP 提供的免費評估工具）自動掃描地端環境。
  2. 誰在用——每個系統的擁有者、使用者、業務重要性。找不到擁有者的系統，就是 Retire 的候選。
  3. 相依什麼——這是最困難也最重要的一項。系統之間的呼叫關係、共用的資料庫、批次排程的先後順序。
  4. 成本基線——目前地端的總持有成本（硬體攤提、機房、電力、人力、授權）。沒有這個數字，之後無法證明上雲的價值。
小心踩雷
相依關係是遷移失敗的第一大原因。典型情境：搬了 A 系統，結果 B 系統半夜的批次跑不動了——因為 B 會連 A 的資料庫，而沒人知道這件事。

找出相依關係的方法：
• Migration Center 的網路流量分析（自動偵測誰連誰）
• 防火牆規則與連線日誌
• 訪談——但要有心理準備，人的記憶通常不完整
• 最可靠的方法：在地端裝流量收集器，觀察一到兩個月（要涵蓋月結、季結等週期性作業）

三、Landing Zone：先蓋好地基

Landing Zone 是指在搬任何東西上去之前，先建好的基礎架構與治理框架。這一步做不好，之後每個系統都會歪。

Landing Zone 組成
Landing Zone 的必要組成

① 資源階層
     Organization → Folders（環境/部門）→ Projects 命名規範

② 身分與存取
     Cloud Identity / Workspace 整合
     群組結構、角色定義、特權存取流程

③ 網路
     Shared VPC 架構、IP 位址規劃（★ 最難改的一項）
     混合雲連線（VPN / Interconnect）
     防火牆基準規則、DNS 架構

④ 資安基準
     Organization Policies（護欄）
     稽核日誌集中收集
     Security Command Center

⑤ 成本治理
     計費帳戶結構、標籤規範、預算與警報

⑥ 自動化
     Terraform 模組庫、專案建立流程（vending machine）
     CI/CD 骨架
實務提醒
用 Terraform 建 landing zone，不要用手點。Google 提供了 Cloud Foundation Toolkit，是經過驗證的企業級藍圖。
從它開始改，比從零寫快好幾個月，而且少踩很多坑。

五、分批策略：先搬什麼

遷移順序決定了專案的成敗。建議的排序原則：

  1. 第一批：低風險 + 有代表性——選一個「不會出大事，但足夠真實」的系統。目的是驗證流程、建立團隊信心、發現 landing zone 的問題。不要選最簡單的（學不到東西），也不要選最重要的（風險太高）。
  2. 第二批：相依關係單純的系統——累積速度與經驗。
  3. 第三批：資料密集型系統——此時團隊已經熟練，能處理資料遷移的複雜度。
  4. 最後：核心系統——風險最高，需要最多演練與最完整的回滾計畫。
小心踩雷
「先搬最簡單的」是常見但錯誤的直覺。如果第一批全是靜態網站，你學不到任何關於資料庫、網路、身分整合的教訓，而這些才是真正的難點。
第一批的目標是「學習」，不是「完成數量」。

六、每個系統的切換流程

切換檢查清單
【切換前】
□ 目標環境已建好並通過測試
□ 資料已同步且延遲 < 可接受範圍
□ 效能測試通過（★ 常被跳過，然後上線才發現慢 3 倍）
□ 回滾計畫已寫好且演練過
□ 切換視窗已公告，相關人員待命
□ 監控與告警已在新環境設定完成

【切換中】
1. 停止舊環境的寫入（進入唯讀模式）
2. 等待最後一批資料同步完成
3. 驗證資料一致性（筆數、關鍵欄位比對）
4. 切換流量（DNS / LB / 設定檔）
5. 冒煙測試（關鍵功能逐一驗證）
6. 開放寫入

【切換後】
□ 監控 24~72 小時
□ 舊環境保持可用（但唯讀）至少 1~2 週
□ 確認無誤後才拆除舊環境
□ 記錄實際耗時與遇到的問題（給下一批參考）

七、常見的遷移陷阱

陷阱後果預防
沒做效能測試上線後發現比地端慢，使用者暴怒遷移前在雲上做壓力測試，且用真實資料量
忽略網路延遲應用在雲、資料庫在地端，回應時間暴增一起搬，或先加快取層
授權沒處理Oracle/SQL Server/Windows 授權在雲上不合規提前 3 個月釐清授權條款（BYOL 規則很複雜）
只搬不改（lift & shift 全部）成本比地端更高，還沒有雲的好處至少對資料庫與中介軟體做 Replatform
沒有訓練團隊上雲後沒人會維運遷移前就開始訓練，並讓團隊參與遷移過程
低估資料遷移時間100TB 走 1Gbps 專線要 9 天提前算好：時間 = 資料量 / 頻寬 × 1.5
沒有明確的完成定義專案拖三年還在「遷移中」每一批都有明確的驗收標準與退場條件

八、本課檢核

  • 能說出 6R 策略並判斷系統該用哪一種
  • 知道評估階段要盤點的四件事，特別是相依關係
  • 理解 Landing Zone 的組成與「先蓋地基」的重要性
  • 知道第一批遷移該選什麼樣的系統
  • 能列出切換前中後的檢查項目

自我檢測

公司要在 12 個月內把 200 台伺服器搬上雲。怎麼規劃？
200 台在 12 個月是可行但緊湊的，關鍵是前三個月不要急著搬。

時程建議：
• M1-M2 評估——用 Migration Center 自動盤點，找出相依關係。預期能 Retire 20～40 台（通常是最大的意外收穫），實際要搬的降到 160 台左右。
• M2-M3 Landing Zone——這是最重要的投資。用 Cloud Foundation Toolkit 建，同時建立 Terraform 模組庫與專案自動化。這三個月看起來沒有進度，但它決定後面九個月的速度。
• M4 第一批（5～10 台）——選有代表性的系統，慢慢做，把流程與工具磨順。
• M5-M11 批次推進——每兩週一批，每批 10～20 台。速度會隨著自動化成熟而加快。
• M12 收尾——核心系統與緩衝。

成功的關鍵：
① 成立專責團隊——遷移不是「大家有空時做」的事。
② 大量自動化——200 台不可能手工搬。第一批就要把流程腳本化。
③ 留 20% 緩衝——一定會有系統比預期難搬。
④ 並行訓練——維運團隊要在遷移過程中就上手，不是搬完才學。

最大的風險不是技術，是沒有人有空——原團隊還要維持地端營運。這件事要在一開始就跟管理層講清楚。
一個跑了 15 年的 Java 單體系統，沒有原始文件，原作者都離職了。怎麼搬？
這種系統要用 Rehost，不要嘗試 Refactor。理由是風險不對稱——重構的收益有限，但搞砸的代價極高。

務實的步驟：
① 先建立「行為基線」——在不改程式碼的前提下，記錄系統目前的行為：對外的 API 回應、資料庫的讀寫模式、批次作業的時程與輸出。這是之後驗證的唯一依據。

② 用 Migrate to Virtual Machines 整台搬——連作業系統、設定、相依套件一起複製。不要嘗試「重新安裝一遍」，因為你不知道 15 年來有人手動改過什麼。

③ 網路先接通——確保它在雲上還能連到它依賴的一切（資料庫、檔案伺服器、外部 API）。

④ 用行為基線驗證——同樣的輸入，比對雲上與地端的輸出是否一致。

⑤ 穩定後再逐步改善：
  • 先把資料庫 Replatform 到 Cloud SQL
  • 加上完整的日誌與監控（這是最重要的一步，讓黑箱變透明）
  • 有了可觀測性之後，才有能力判斷哪些部分可以安全地重構
  • 用絞殺者模式（Strangler Fig）逐步替換：新功能寫成獨立服務，舊功能一塊一塊搬出來

核心判斷：你無法安全地重構一個你不理解的系統。先搬上去、先加監控、先建立理解，再談改造。這個過程可能要一到兩年，這是正常的。
上雲一年後，成本比地端高 40%。管理層質疑決策。怎麼回應？
這是非常常見的狀況，而且通常是「lift & shift 沒有後續優化」造成的。要分成三部分回應：

① 先確認比較基準是否公平——地端成本常被低估，因為很多成本沒被算進去：機房租金與電力、硬體攤提、備援設備、網路設備、維護合約、機房人力、災難復原的機房、以及「無法快速擴充」的機會成本。把這些加回去後，差距通常會縮小很多。

② 承認問題，提出具體計畫——如果扣除上述因素後成本仍然較高，那確實是優化不足。這是可以修正的：
  • Rightsizing（地端習慣超額配置，因為擴充很痛。雲上不需要）→ 通常 20～30%
  • 非正式環境排程關機 → 非prod 省 60%
  • 承諾使用折扣 → 25～55%
  • 自架服務改用託管服務（省人力，雖然帳單可能持平）
  • 給出6 個月降 30～40% 的具體時程表與負責人

③ 把討論從「成本」拉到「價值」——上雲的效益不只帳單：新服務上線時間從 3 個月變 3 天、災難復原能力從無到有、彈性應對尖峰、團隊不用值班換硬碟。這些要量化呈現。

但也要誠實：如果你的負載極度穩定、完全不需要彈性、且有充足的機房與人力，那地端確實可能更便宜。上雲不是對每個組織都划算——重點是把決策依據攤開來，用數字討論，而不是用信仰。
