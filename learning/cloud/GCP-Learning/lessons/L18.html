LESSON 18

Cloud SQL：託管的關聯式資料庫

Cloud SQL 是 MySQL、PostgreSQL、SQL Server 的託管版本。它幫你處理備份、修補、高可用與副本——但你仍要懂它的限制在哪。

操作 45 分約 0.5 美元實作

一、託管資料庫幫你做了什麼

工作自架 MySQLCloud SQL
安裝與設定你做Google
版本升級與安全修補你做（且常常拖著不敢做）自動（可設定維護時段）
自動備份你寫 cron + 驗證還原內建，含時間點還原（PITR）
高可用切換你建 replication + 自己寫 failover內建，自動故障轉移
監控你架 Prometheus內建 Cloud Monitoring
作業系統存取有沒有（不能 SSH 進去、不能裝任意外掛）
超級使用者權限有受限

取捨很明確：你放棄底層控制權，換來不用值班處理資料庫。對絕大多數團隊，這筆交易划算。

二、實作：建立一個正式規格的 Cloud SQL

動手實作

實作：PostgreSQL 執行個體

  1. 建立執行個體（注意這些參數都是正式環境該有的設定）：
    bash
    gcloud sql instances create lab-pg \
  --database-version=POSTGRES_15 \
  --tier=db-custom-2-8192 \
  --region=asia-east1 \
  --storage-type=SSD \
  --storage-size=20GB \
  --storage-auto-increase \
  --availability-type=ZONAL \
  --backup-start-time=18:00 \
  --enable-point-in-time-recovery \
  --retained-backups-count=7 \
  --maintenance-window-day=SUN \
  --maintenance-window-hour=3 \
  --database-flags=max_connections=200,log_min_duration_statement=1000
  2. 設定密碼並建立資料庫：
    bash
    gcloud sql users set-password postgres \
  --instance=lab-pg --password="請用強密碼"

gcloud sql databases create appdb --instance=lab-pg
  3. 用 Cloud SQL Auth Proxy 安全連線（不需要開放任何 IP）：
    bash
    # Cloud Shell 已內建 proxy
gcloud sql connect lab-pg --user=postgres --database=appdb

# 或手動啟動 proxy（應用程式的標準做法）
cloud-sql-proxy PROJECT:asia-east1:lab-pg --port 5432 &
psql -h 127.0.0.1 -p 5432 -U postgres -d appdb
  4. 建個表試試：
    bash
    CREATE TABLE orders (
  id SERIAL PRIMARY KEY,
  customer TEXT NOT NULL,
  amount NUMERIC(10,2),
  created_at TIMESTAMPTZ DEFAULT now()
);
INSERT INTO orders (customer, amount) VALUES ('王小明', 1200.50);
SELECT * FROM orders;
  5. 驗證備份與還原（這一步大多數人從來沒做過，直到出事）：
    bash
    # 手動建立備份
gcloud sql backups create --instance=lab-pg

# 列出備份
gcloud sql backups list --instance=lab-pg

# 時間點還原到 10 分鐘前（會建立新的執行個體）
gcloud sql instances clone lab-pg lab-pg-restored \
  --point-in-time="2026-07-31T10:00:00.000Z"
小心踩雷
「有備份」不等於「能還原」。我看過太多團隊在災難發生時才發現備份是壞的、或者沒人知道還原流程。
把「季度還原演練」寫進行事曆：實際還原一次到新執行個體，確認資料完整、確認團隊知道步驟、確認需要多久。沒演練過的備份等於沒有備份。

三、連線方式：三種，安全性差很多

方式設定安全性建議
公開 IP + 授權網路--authorized-networks=1.2.3.4/32差——資料庫暴露在網際網路上不要用
私有 IP--network=vpc --no-assign-ip好——只有 VPC 內能連正式環境首選
Cloud SQL Auth Proxy以 IAM 認證建立加密通道最好——不需要 IP 白名單，走 IAM應用程式的標準做法
bash
# 正式環境：只給私有 IP
gcloud sql instances create prod-pg \
  --database-version=POSTGRES_15 --tier=db-custom-4-16384 \
  --region=asia-east1 \
  --network=projects/PROJECT/global/networks/prod-vpc \
  --no-assign-ip \
  --availability-type=REGIONAL \
  --enable-google-private-path

# 用 IAM 資料庫認證（不再需要管理資料庫密碼）
gcloud sql instances patch prod-pg \
  --database-flags=cloudsql.iam_authentication=on

gcloud sql users create app@PROJECT.iam \
  --instance=prod-pg --type=cloud_iam_service_account

四、高可用（HA）與唯讀副本

高可用 REGIONAL唯讀副本 Read Replica
目的故障自動接手分攤讀取負載
架構同步複製到另一個 Zone 的備援機非同步複製
能否讀取不能，備援機平時完全不服務可以
切換自動，約 60～120 秒手動提升（promote）
費用×2每個副本 ×1
資料遺失無（同步）可能有（非同步延遲）
bash
# 開啟高可用（會重啟，約 5 分鐘）
gcloud sql instances patch prod-pg --availability-type=REGIONAL

# 建立唯讀副本（可跨 Region，做災難備援兼就近讀取）
gcloud sql instances create prod-pg-replica-us \
  --master-instance-name=prod-pg \
  --region=us-central1 \
  --tier=db-custom-4-16384

# 檢查複製延遲（重要監控指標）
gcloud sql instances describe prod-pg-replica-us \
  --format="value(replicaConfiguration)"
實務提醒
常見誤解：以為開了 HA 就有讀取擴充能力。沒有。HA 的備援機是完全閒置的，你付兩倍的錢買的是「自動故障轉移」，不是效能。
要分攤讀取負載必須另外建唯讀副本。典型的正式架構是：HA 主庫（寫入）+ 2 個唯讀副本（讀取）+ 跨區副本（災難備援）。

五、效能與成本調校

  1. 先看慢查詢，不要急著加規格。設定 log_min_duration_statement=1000 記錄超過 1 秒的查詢，通常會發現是缺索引而非機器不夠力。
  2. 用連線池。PostgreSQL 每個連線都是一個作業系統程序，1000 個連線會吃掉幾 GB 記憶體。用 PgBouncer 或應用層的連線池，把實際連線數控制在 CPU 核心數的 2～4 倍。
  3. 磁碟自動擴充要設上限。--storage-auto-increase 很方便，但磁碟只能擴大不能縮小。一個失控的日誌表可能讓磁碟從 100GB 長到 2TB，然後你永遠要付 2TB 的錢。務必加 --storage-auto-increase-limit。
  4. 開發環境用排程停機。Cloud SQL 可以停止，停止時只收磁碟費。dev 環境晚上和週末停掉，能省約 65%。
bash
# 用 Cloud Scheduler 排程停啟 dev 資料庫
gcloud scheduler jobs create http stop-dev-db \
  --schedule="0 20 * * 1-5" --time-zone="Asia/Taipei" \
  --uri="https://sqladmin.googleapis.com/v1/projects/PROJ/instances/dev-pg" \
  --http-method=PATCH \
  --oauth-service-account-email=scheduler@PROJ.iam.gserviceaccount.com \
  --message-body='{"settings":{"activationPolicy":"NEVER"}}'

六、清理

bash
# 刪除保護預設開啟，要先關掉
gcloud sql instances patch lab-pg --no-deletion-protection
gcloud sql instances delete lab-pg --quiet

七、本課檢核

  • 能建立一個含備份、PITR、維護時段的執行個體
  • 知道正式環境要用私有 IP + Cloud SQL Auth Proxy
  • 能區分 HA 與唯讀副本的用途
  • 知道磁碟自動擴充要設上限
  • 已實際做過一次還原演練

自我檢測

Cloud SQL 的 CPU 一直在 90%，你的第一個動作是升級規格嗎？
不是。升級規格是最貴、也最可能治標不治本的做法。正確順序：
① 找出慢查詢——用 Query Insights 或 pg_stat_statements，看是哪幾個查詢吃掉 CPU。通常 80% 的負載來自 2～3 個查詢。
② 檢查索引——EXPLAIN ANALYZE 看有沒有全表掃描。加一個索引可能讓 CPU 從 90% 掉到 10%。
③ 檢查連線數——連線過多本身就會吃 CPU。
④ 加唯讀副本——如果是讀取為主。
⑤ 最後才升級規格。
我見過把資料庫從 4 核升到 32 核（成本 8 倍）結果只快 20% 的案例——因為瓶頸是缺索引導致的磁碟 I/O，加 CPU 完全沒用。
公司要求 RPO（可容忍資料遺失）< 5 分鐘、RTO（可容忍停機）< 30 分鐘。Cloud SQL 怎麼配置？
RPO < 5 分鐘：
• 開啟 Point-in-Time Recovery（PITR），可還原到任意秒。
• 開啟 REGIONAL 高可用——同步複製，Zone 故障時 RPO = 0。

RTO < 30 分鐘：
• HA 自動故障轉移約 60～120 秒 ✅ 遠優於需求。
• 但如果是整個 Region 故障，要靠跨區唯讀副本手動提升，通常 5～15 分鐘。

完整配置：REGIONAL HA + PITR + 跨 Region 唯讀副本 + 事先寫好且演練過的提升腳本。
最後那一項最重要——RTO 的瓶頸從來不是技術，是「半夜三點誰知道該做什麼」。
開發者想用 PostgreSQL 的 pg_cron 外掛做排程任務，但 Cloud SQL 不支援。有什麼替代方案？
這正是託管服務的取捨——你不能裝任意外掛。三個替代方案：
① Cloud Scheduler + Cloud Run Job（推薦）——把排程邏輯搬到資料庫外面。優點是可觀測、可版控、失敗會告警，而且不佔資料庫資源。
② Cloud Scheduler + Cloud Functions——輕量任務適用。
③ 改用 AlloyDB 或自架——如果真的非某個外掛不可。

更深一層的思考：把排程放在資料庫裡（pg_cron）本來就不是好設計——它讓排程邏輯藏在資料庫裡難以版控、難以監控、且會跟著資料庫一起故障。被迫搬出來反而是好事。
先查 Cloud SQL 支援的外掛清單，很多常用外掛（PostGIS、pgvector、pg_stat_statements）其實都有支援。
