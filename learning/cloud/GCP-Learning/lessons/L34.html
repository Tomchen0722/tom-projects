LESSON 34

SRE 實務：SLI、SLO 與事故處理

這一課講的不是 GCP 功能，而是 Google 發明的一套可靠性工程方法。它回答一個關鍵問題：「我們的服務應該多可靠？」——答案不是「越可靠越好」。

閱讀 25 分方法論

一、為什麼「100% 可用」是錯誤的目標

追求 100% 可用性的成本是指數級上升的，而使用者感知的價值是邊際遞減的。

可用性每年停機時間每月停機時間典型成本
99%3.65 天7.2 小時單機即可
99.9%8.76 小時43.8 分鐘跨 Zone 冗餘
99.95%4.38 小時21.9 分鐘+ 自動故障轉移
99.99%52.6 分鐘4.38 分鐘跨 Region + 完整自動化
99.999%5.26 分鐘26 秒成本可能是 99.9% 的 10~100 倍
補充
關鍵洞察：如果使用者的手機網路本身只有 99% 的可用性，你把服務從 99.9% 提升到 99.99% 對使用者完全沒有感覺——但你可能花了 10 倍的成本。
可靠性的目標應該設在「使用者開始不滿意」的那條線，不是越高越好。

二、SLI / SLO / SLA：三個容易混淆的詞

三者關係
SLI（Service Level Indicator）服務水準「指標」
   「我們實際量測到的數字」
   例：過去 28 天，成功的 HTTP 請求佔比 = 99.94%

SLO（Service Level Objective）服務水準「目標」
   「我們自己訂的內部目標」
   例：成功率必須 ≥ 99.9%

SLA（Service Level Agreement）服務水準「協議」
   「跟客戶簽的合約，違反要賠錢」
   例：若成功率 < 99.5%，退還 10% 月費

關係：SLA 門檻 < SLO 門檻 < 實際 SLI
      （留緩衝，不要讓 SLO 剛好等於 SLA）

怎麼定義好的 SLI

好的 SLI 要從使用者角度定義，而且是一個比例：

bash
SLI = 好事件數 / 總事件數

可用性 SLI = 回應碼非 5xx 的請求數 / 總請求數
延遲 SLI   = 回應時間 < 500ms 的請求數 / 總請求數
品質 SLI   = 完整回應（未降級）的請求數 / 總請求數
新鮮度 SLI = 資料延遲 < 5 分鐘的查詢數 / 總查詢數
小心踩雷
不要用「CPU 使用率」或「機器數量」當 SLI。那些是原因指標不是結果指標。
使用者不在乎你的 CPU 幾趴，只在乎「我的請求成功了嗎、快不快」。

三、錯誤預算（Error Budget）：SRE 最重要的發明

錯誤預算計算
錯誤預算 = 100% − SLO

SLO = 99.9%  →  錯誤預算 = 0.1%
                每月允許失敗的請求 = 總請求 × 0.1%

假設每月 1000 萬次請求：
   錯誤預算 = 10,000 次失敗
   等於 每月約 43.8 分鐘的完全停機

錯誤預算把「可靠性」變成一個可以花用的資源，這解決了工程團隊永恆的衝突：

情況代表什麼該做什麼
預算還很多（用了 < 50%）服務比目標更可靠可以承擔風險：加快發布節奏、做混沌工程、嘗試新架構
預算快用完（用了 > 80%）接近不可接受的水準放慢：加強測試、增加金絲雀比例、延後高風險變更
預算用完已經違反 SLO凍結功能發布，全力投入可靠性改善，直到預算恢復
實務提醒
這個機制的美妙之處是它把「要不要上新功能」從主觀爭論變成客觀數據。
產品經理想快點上線、SRE 想要穩定——以前這是永無止境的角力。有了錯誤預算，答案是：「預算還有 60%，可以上；預算剩 5%，這週先修穩定性。」
雙方事先同意規則，事發時就不用吵架。

四、監控 SLO 與燃燒率告警

直接對 SLO 設告警會太遲鈍（等到月底才發現超標）。SRE 的做法是監控燃燒率（burn rate）——錯誤預算被消耗的速度。

燃燒率告警
燃燒率 = 目前的錯誤率 / 錯誤預算的錯誤率

SLO 99.9% → 允許錯誤率 0.1%
若目前錯誤率是 1%  →  燃燒率 = 10 倍
                      表示 30 天的預算會在 3 天內用完

【多視窗多燃燒率告警】（Google SRE 手冊的建議）
┌────────────┬──────────┬─────────────┬──────────┐
│ 燃燒率      │ 長視窗    │ 預算耗盡時間  │ 告警等級  │
├────────────┼──────────┼─────────────┼──────────┤
│ 14.4 倍     │ 1 小時    │ ~2 天        │ P1 立即呼叫│
│ 6 倍        │ 6 小時    │ ~5 天        │ P1 立即呼叫│
│ 3 倍        │ 1 天      │ ~10 天       │ P2 工單    │
│ 1 倍        │ 3 天      │ 30 天        │ P3 觀察    │
└────────────┴──────────┴─────────────┴──────────┘
bash
# 在 GCP 建立 SLO
gcloud alpha monitoring slos create \
  --service=SERVICE_ID \
  --slo-id=availability-slo \
  --display-name="可用性 99.9%" \
  --goal=0.999 \
  --rolling-period=28d \
  --request-based-good-total-ratio \
  --good-service-filter='metric.label.response_code_class!="5xx"'

五、事故處理流程

事故處理五階段
① 偵測 Detect
    告警觸發，或使用者回報
        ↓
② 分流 Triage
    嚴重程度？影響範圍？需要多少人？
    ★ 指派「事故指揮官」(Incident Commander)
        ↓
③ 止血 Mitigate     ← ★ 這一步優先於「找出根因」
    回滾？切流量？降級？擴容？
    目標：讓使用者先恢復，原因之後再說
        ↓
④ 修復 Resolve
    根因分析與修正
        ↓
⑤ 事後檢討 Postmortem
    ★ 無指責文化（blameless）
    產出可執行的改善項目與負責人
小心踩雷
事故處理最常見的錯誤：花 40 分鐘找根因，而不是花 2 分鐘回滾。
當服務掛掉時，你的第一目標是恢復服務，不是理解問題。回滾、切流量、關掉有問題的功能開關——這些都比「弄清楚為什麼」更優先。
根因分析可以在服務恢復後從容進行，但使用者不會等你。

無指責事後檢討（Blameless Postmortem）

這是 SRE 文化的核心。如果檢討會變成追究責任，人們就會隱瞞資訊，而你會失去改善的機會。

❌ 指責式✅ 無指責式
「小王沒有測試就上線」「我們的流程允許未經測試的變更進入正式環境」
「應該要更小心」「我們需要一個自動化檢查來攔截這類變更」
「這是人為疏失」「這個介面設計容易導致誤操作」

核心信念：人在當下的資訊與壓力下，做的是他認為合理的決定。如果結果是錯的，問題在系統，不在人。

事後檢討報告的必要內容

  1. 影響：多少使用者、多久、什麼功能受影響、損失估算
  2. 時間軸：從第一個異常到完全恢復，每個關鍵動作的時間點
  3. 根因：技術根因，且要問到夠深（五個為什麼）
  4. 偵測：我們多久才發現？為什麼不是更快？（這一項最常被忽略但最重要）
  5. 做得好的地方：不要只寫問題
  6. 行動項目：每一項都要有負責人、期限、追蹤編號。沒有這三樣就是許願

六、本課檢核

  • 能區分 SLI / SLO / SLA
  • 知道 SLI 要從使用者角度定義且是比例
  • 理解錯誤預算如何調解「速度 vs 穩定」的衝突
  • 知道燃燒率告警優於直接對 SLO 告警
  • 理解事故處理中「止血優先於找根因」
  • 理解無指責文化的價值

自我檢測

老闆說「我們要 99.999% 的可用性」。你怎麼回應？
不要直接說「做不到」或直接答應，而是把成本與需求攤開來討論：

① 換算成具體數字——「99.999% 表示每年最多停機 5 分 15 秒，包含所有計畫內維護、雲廠商故障、部署失誤。Google Cloud 自己的多數服務 SLA 也只有 99.95%～99.99%。」

② 估算成本——需要多 Region 主動-主動架構、跨區資料同步（可能要用 Spanner）、完整的自動故障轉移、24/7 on-call 團隊。基礎設施成本可能是現在的 3～5 倍，人力成本增加一個團隊。

③ 反問業務價值——「從 99.9% 提升到 99.99%，每年減少 8 小時停機。這 8 小時對業務的損失是多少？如果是 100 萬，那值得投入；如果是 5 萬，投入 500 萬是不划算的。」

④ 提出替代方案——「與其追求全站 99.999%，不如分級：結帳流程做 99.99%，商品瀏覽做 99.9%，後台報表做 99%。這樣把資源花在真正重要的地方。」

關鍵是把「越可靠越好」的直覺，轉換成「可靠性是有成本的投資決策」。
這個月錯誤預算已經用掉 95%，但產品部門堅持要上新功能。怎麼辦？
這正是錯誤預算機制要解決的場景——而且答案應該在事前就談好了。

① 回到事先的協議——如果團隊事前同意「預算耗盡則凍結發布」，那就執行。錯誤預算的價值在於它是事前訂的規則，不是事後的談判籌碼。

② 但要有例外機制——如果這個功能有明確的、時效性的商業理由（法規要求、重大合約、競品壓力），可以由更高層級的人核准例外，但必須：
  • 明確記錄決策與理由
  • 承擔對應的風險（例如同步安排 on-call 加強）
  • 事後補上可靠性工作

③ 找中間路線——「可以上，但用功能開關先關閉，只對 1% 使用者開放；且必須有一鍵關閉的能力。」這樣把風險控制在極小範圍。

④ 檢討 SLO 是否合理——如果錯誤預算每個月都用完，可能是 SLO 訂得太嚴苛，不符合業務實際需要。SLO 應該每季檢討。

要避免的兩個極端：教條式地說「規則就是規則」，或每次都妥協讓機制形同虛設。
事故已經恢復，但你們花了 45 分鐘才發現問題。檢討時該問什麼？
「為什麼是 45 分鐘？」這個問題比「為什麼壞掉」更重要。因為壞掉是不可避免的，但發現得慢是可以系統性改善的。

要追問的層次：
① 誰先發現的？是監控告警，還是使用者投訴？如果是後者，那是監控的重大缺口。
② 有沒有相關的告警？
  • 沒有 → 需要新增什麼 SLI 與告警？
  • 有但沒觸發 → 門檻太寬鬆？視窗太長？
  • 有觸發但沒人看 → 告警疲勞問題，這比技術問題更嚴重。
③ 告警送到哪裡？是不是送到一個沒人看的頻道？on-call 輪值有沒有真的運作？
④ 從告警到有人開始處理花了多久？這是「回應時間」，跟「偵測時間」是兩件事，要分開量測。

可行動的改善方向：
• 對關鍵使用者旅程建立合成監控（synthetic monitoring）——每分鐘模擬一次完整的結帳流程，比等真實使用者觸發問題快得多。
• 建立燃燒率告警取代靜態門檻。
• 量測並追蹤 MTTD（平均偵測時間） 作為團隊指標。

SRE 的核心指標是 MTTR（平均修復時間），而 MTTR = 偵測時間 + 回應時間 + 修復時間。多數團隊只優化最後一項。
