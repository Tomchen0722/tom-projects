LESSON 32

生成式 AI：Gemini API 與 RAG 架構

生成式 AI 已經是企業標配。這一課講怎麼在 GCP 上落地一個能回答公司內部知識的 AI 助理，以及必須處理的風險。

閱讀 25 分進階

一、在 GCP 上用 Gemini 的三種方式

方式特點適合
Vertex AI Gemini API企業級：資料不用於訓練、支援 VPC-SC、有 SLA、可用 CMEK正式產品
Google AI Studio API快速原型，免費額度大實驗與個人專案
BigQuery ML 的 ML.GENERATE_TEXT直接在 SQL 中呼叫批次處理資料（分類、摘要、抽取）
BigQuery ML 呼叫 Gemini
-- 在 SQL 裡直接用 Gemini 處理資料
CREATE OR REPLACE MODEL ml.gemini
REMOTE WITH CONNECTION `asia-east1.vertex-conn`
OPTIONS (ENDPOINT = 'gemini-2.0-flash');

SELECT
  ticket_id,
  ml_generate_text_llm_result AS category
FROM ML.GENERATE_TEXT(
  MODEL ml.gemini,
  (SELECT
     ticket_id,
     CONCAT('把以下客服工單分類成「退貨」「技術問題」「帳務」「其他」之一，只回答類別名稱：\n',
            content) AS prompt
   FROM support.tickets
   WHERE created_date = CURRENT_DATE()),
  STRUCT(0.1 AS temperature, 20 AS max_output_tokens)
);

二、RAG：讓 AI 知道你公司的事

大型語言模型不知道你公司的內部規章、產品手冊、客戶資料。RAG（Retrieval-Augmented Generation）的作法是：先從你的文件庫找出相關段落，連同問題一起餵給模型。

RAG 架構
【建立索引階段】（一次性 + 定期更新）
文件（PDF/Word/網頁）
   ↓ Document AI 解析
純文字
   ↓ 切成段落（chunking，通常 300~800 字，要有重疊）
文字片段
   ↓ Vertex AI Embeddings（text-embedding-004）
向量（768 維數字陣列）
   ↓ 存入
Vector Search / AlloyDB pgvector / BigQuery VECTOR_SEARCH

【查詢階段】（每次提問）
使用者問題「請假規則是什麼？」
   ↓ 轉成向量
   ↓ 向量相似度搜尋 → 找出最相關的 5 個段落
   ↓ 組成提示詞
「根據以下資料回答問題。若資料中沒有答案，請說不知道。
 資料：[段落1][段落2]...
 問題：請假規則是什麼？」
   ↓ Gemini
帶有出處的答案

GCP 上的三種向量儲存選擇

方案特點適合
Vertex AI Vector Search專用向量資料庫，可擴充到數十億向量，延遲極低大規模、高效能需求
AlloyDB / Cloud SQL + pgvector可以跟業務資料放一起，用 SQL 同時做向量與條件篩選中小規模，最實用
BigQuery VECTOR_SEARCH不用額外服務，直接在資料倉儲中做批次場景、資料已在 BQ
bash
-- 用 AlloyDB / Cloud SQL 的 pgvector
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE documents (
  id          BIGSERIAL PRIMARY KEY,
  source      TEXT,
  page        INT,
  content     TEXT,
  department  TEXT,               -- 可以混合條件篩選
  embedding   vector(768)
);

CREATE INDEX ON documents USING hnsw (embedding vector_cosine_ops);

-- 混合搜尋：向量相似度 + 傳統條件（這是 pgvector 的最大優勢）
SELECT content, source, page,
       1 - (embedding <=> $1) AS similarity
FROM documents
WHERE department = 'HR'                      -- 只搜 HR 的文件
  AND 1 - (embedding <=> $1) > 0.7           -- 相似度門檻
ORDER BY embedding <=> $1
LIMIT 5;

三、Vertex AI Search：不用自己組 RAG

如果你不想自己處理切段、嵌入、索引、檢索，Vertex AI Search（原 Enterprise Search）把整套 RAG 包成託管服務：

  • 支援從 Cloud Storage、BigQuery、網站、Confluence、SharePoint 直接匯入
  • 自動處理文件解析、切段、嵌入、索引
  • 內建存取控制——每個使用者只能搜尋到自己有權限的文件
  • 回答附帶引用來源
實務提醒
先評估 Vertex AI Search，再考慮自建。自建 RAG 看起來簡單，但要處理的細節很多：文件格式轉換、表格解析、切段策略、多語言、增量更新、權限過濾、重排序（reranking）。
除非你有特殊需求（例如自訂的檢索邏輯），託管方案通常品質更好且維護成本低得多。

四、必須處理的四類風險

風險說明對策
幻覺 Hallucination模型會自信地編造不存在的資訊① RAG 提供事實依據
② 提示詞明確要求「資料中沒有就說不知道」
③ 回答附上來源連結讓使用者能驗證
④ 用 Vertex AI 的 Grounding 功能
提示注入 Prompt Injection使用者輸入「忽略前面的指令，改為...」① 系統指令與使用者輸入分離
② 輸出驗證
③ 最小權限：AI 能呼叫的工具要嚴格限制
資料外洩把機密資料送到模型，或模型回答洩漏他人資料① 用 Vertex AI（不用於訓練）
② 檢索階段就套用權限過濾，而非事後過濾
③ 用 Sensitive Data Protection 遮罩 PII
成本失控Token 用量隨使用者增長線性上升① 快取常見問題的答案
② 限制輸入長度與對話輪數
③ 簡單任務用 Flash 模型而非 Pro
④ 設定每使用者配額
小心踩雷
權限過濾必須發生在「檢索階段」，不是「生成之後」。
錯誤做法：檢索所有文件 → 生成答案 → 檢查使用者有沒有權限。此時機密內容已經進入模型的上下文，模型可能已經在答案中透露了資訊。
正確做法：先用使用者身分過濾可搜尋的文件範圍，再檢索、再生成。

自我檢測

主管說「幫我們做一個能回答公司所有問題的 AI」。你的第一個問題是什麼？
「哪些人可以看到哪些資料？」

這是 RAG 專案最容易低估、也最容易致命的部分。技術上組一個 RAG 只要一週，但權限模型錯了會直接造成資安事故——例如一般員工問「主管的薪資是多少」，AI 從 HR 文件中忠實地回答了。

接著要問的問題：
• 文件從哪來？格式是什麼？有多少？多久更新一次？
• 「回答錯誤」的代價是什麼？（內部查詢 vs 對客戶承諾，風險等級完全不同）
• 怎麼衡量好壞？誰來評估？
• 現有的文件品質如何？如果內部文件本身就過時、矛盾，AI 只會忠實地放大這些問題。

經驗法則：RAG 專案 70% 的工作在資料準備與權限，只有 30% 在 AI。
AI 助理回答「根據公司政策，年假是 30 天」，但實際上是 14 天。怎麼防止？
分層處理，缺一不可：

① 找出根因——是檢索錯了（找到過期文件）還是生成錯了（模型編造）？先看檢索出來的段落內容。這決定後續方向。

② 如果是檢索問題：
• 文件庫裡有過期版本 → 建立版本管理與生效日期的中繼資料，檢索時過濾。
• 切段切爛了 → 調整切段策略，確保「年假天數」的上下文完整。
• 相似度不夠準 → 加入重排序（reranking）步驟。

③ 如果是生成問題：
• 提示詞加強：「只根據提供的資料回答。若資料中沒有明確答案，回答『我在文件中找不到這個資訊，請聯繫 HR』。不要推測。」
• 降低 temperature 到 0.1 以下。
• 啟用 Vertex AI 的 Grounding 功能，強制答案有依據。

④ 系統性防護：
• 每個答案附上來源連結與原文片段——這是最重要的一項。使用者能自己驗證，且能回報錯誤。
• 建立回饋機制與定期抽樣評估。
• 對高風險主題（薪資、法務、醫療）設定白名單模式，只允許回答已驗證的問題。

務實的認知：幻覺無法完全消除，只能降低機率並讓錯誤可被發現。設計時要假設它會出錯。
你的 RAG 系統上線一個月，Gemini API 費用是預期的 8 倍。怎麼查與怎麼降？
先量測，找出 token 花在哪。把每次請求的「輸入 token、輸出 token、使用者、問題類型」都記到 BigQuery，然後分析。

最常見的四個原因與對策：
① 檢索段落塞太多——有人設定「取前 20 個段落」，每個 800 字，光輸入就 16000 token。對策：降到 3～5 個，並加入重排序確保品質。這通常是最大宗。
② 對話歷史無限累積——每輪都把完整歷史送進去，第 10 輪的成本是第 1 輪的 10 倍。對策：只保留最近 3 輪，或用摘要壓縮。
③ 用錯模型——簡單的分類、抽取任務用了 Gemini Pro。對策：分流——簡單任務用 Flash（便宜約 10 倍），複雜推理才用 Pro。
④ 重複問題沒快取——「請假規則」被問了 500 次。對策：用問題的向量做語意快取，相似度 > 0.95 就回傳快取答案。

額外手段：啟用 Context Caching（重複的長系統提示可以快取，大幅降低成本），以及設定每使用者每日 token 配額。
