LESSON 43

IAP 與 Apigee：內部系統存取與 API 治理

員工怎麼不用 VPN 就安全連進內部系統？API 開放給合作夥伴後怎麼不失控？這一課處理企業上雲後一定會遇到的這兩題。

操作 45 分實作

一、企業的兩個經典難題

這一課處理企業上雲後幾乎一定會遇到的兩件事：員工怎麼安全地存取內部系統，以及API 怎麼開放給外部又不失控。前者靠 IAP，後者靠 API 管理層。

生活比喻
傳統 VPN 像大樓的地下停車場入口：刷卡進去之後，整棟樓你都走得到。一旦有人偷到卡，整棟樓都失守。

IAP 像每個房間門口都有讀卡機：你進大樓不需要特別許可，但每扇門都會問「你是誰、你能不能進這一間」。

這個思路叫 BeyondCorp（零信任）——不再假設「進到內網就是自己人」。

二、Identity-Aware Proxy（IAP）

IAP 擋在你的應用程式前面，在流量抵達應用之前先做身分驗證與授權。使用者用公司的 Google 帳號登入，通過才放行。

IAP 的位置
外部使用者
   │
   ↓
Cloud Load Balancer
   │
   ├── ① Cloud Armor（擋 DDoS、WAF 規則）
   │
   ├── ② IAP  ←── 這一層：你是誰？你有權限嗎？
   │       │
   │       ├─ 未登入 → 導到 Google 登入頁
   │       ├─ 已登入但無權限 → 403
   │       └─ 已登入且有權限 → 放行,並附上身分資訊
   │
   ↓
你的應用（Cloud Run / GCE / GKE / App Engine）
   收到 header:X-Goog-Authenticated-User-Email
比較VPNIAP
使用者要裝東西嗎要裝 VPN 用戶端不用，瀏覽器就行
權限粒度進了就通每個應用分別授權
外包/廠商臨時存取要開 VPN 帳號，麻煩加一個 IAM 綁定就好
離職員工要記得停 VPN 帳號停用 Google 帳號即全斷
稽核紀錄看 VPN logCloud Audit Logs 有完整紀錄
動手實作

實作一：幫內部工具加上 IAP

情境：你有一個部署在 Cloud Run 的內部報表工具，只想讓財務部門的人看到。

  1. 部署一個測試服務（注意用 --no-allow-unauthenticated）：
    bash
    gcloud run deploy internal-report \
  --image=gcr.io/cloudrun/hello \
  --region=asia-east1 \
  --no-allow-unauthenticated
  2. 授權特定使用者或群組：
    bash
    # 授權整個群組（實務上一律用群組，不要綁個人）
gcloud run services add-iam-policy-binding internal-report \
  --region=asia-east1 \
  --member="group:finance@example.com" \
  --role="roles/run.invoker"
  3. 若要走 Load Balancer + IAP（適合 GCE / GKE 或需要自訂網域時）：
    bash
    # 在後端服務上開啟 IAP
gcloud compute backend-services update my-backend \
  --global \
  --iap=enabled

# 授權誰能通過 IAP
gcloud iap web add-iam-policy-binding \
  --resource-type=backend-services \
  --service=my-backend \
  --member="group:finance@example.com" \
  --role="roles/iap.httpsResourceAccessor"
  4. 在應用程式裡讀取 IAP 傳來的身分：
    python
    from flask import request

@app.route("/")
def index():
    # IAP 驗證通過後會加上這個 header
    email = request.headers.get("X-Goog-Authenticated-User-Email", "")
    email = email.replace("accounts.google.com:", "")
    return f"你好，{email}"
最重要的一個安全前提
應用程式本身必須擋住「不經過 IAP 的直接連線」。
如果你的 Cloud Run 是 --allow-unauthenticated，或 GCE 有對外 IP 且防火牆沒鎖，攻擊者可以繞過 Load Balancer 直接打你的應用，IAP 完全形同虛設。

作法：
• Cloud Run：用 --no-allow-unauthenticated，並限制 ingress 只接受內部與 LB 流量
• GCE / GKE：防火牆只允許 Google LB 的來源網段
• 應用層再驗一次 X-Goog-IAP-JWT-Assertion 這個 JWT 的簽章（縱深防禦）

三、API 管理：三個選項怎麼選

當你要把 API 開放出去——給前端、給合作夥伴、給客戶——就需要一層管理：誰能呼叫、呼叫幾次、出問題怎麼查。GCP 有三個層級的選項。

API GatewayCloud EndpointsApigee
定位輕量託管閘道與後端一起部署的代理企業級 API 管理平台
典型用途保護 Cloud Run / FunctionsApp Engine / GKE 上的 API對外商業化 API
金鑰與配額基本支援基本支援完整（分級方案、計費）
開發者入口網站無無有（合作夥伴自助申請）
流量政策有限有限豐富（改寫、快取、串接、加解密）
成本低低高，數量級的差距
Apigee 的成本要先講清楚
Apigee 是企業級產品，定價和前兩者不在同一個量級，通常以年約起算。

什麼時候才值得：API 本身是你的產品（要對外收費、要分級方案、要給合作夥伴自助申請金鑰、要有 SLA 保證）。
什麼時候不值得：只是想保護自家前端要呼叫的後端 API——那用 API Gateway 或直接在 Cloud Run 上做驗證就夠了。

實際報價請洽 Google Cloud 業務，這裡不列數字以免過期。
動手實作

實作二：用 API Gateway 保護 Cloud Run

  1. 寫一份 OpenAPI 設定 api-config.yaml：
    api-config.yaml
    swagger: "2.0"
info:
  title: orders-api
  description: 訂單查詢 API
  version: "1.0.0"
schemes: [https]
produces: [application/json]

securityDefinitions:
  api_key:
    type: apiKey
    name: key
    in: query

paths:
  /orders:
    get:
      summary: 查詢訂單
      operationId: listOrders
      security:
        - api_key: []
      x-google-backend:
        address: https://internal-report-xxxx.a.run.app
      responses:
        "200":
          description: 成功
  2. 建立閘道：
    bash
    gcloud services enable apigateway.googleapis.com \
  servicemanagement.googleapis.com servicecontrol.googleapis.com

gcloud api-gateway api-configs create orders-cfg \
  --api=orders-api --openapi-spec=api-config.yaml

gcloud api-gateway gateways create orders-gw \
  --api=orders-api --api-config=orders-cfg \
  --location=asia-east1
  3. 取得網址並測試（沒帶金鑰應該被擋）：
    bash
    gcloud api-gateway gateways describe orders-gw \
  --location=asia-east1 --format="value(defaultHostname)"

curl https://GATEWAY_HOST/orders            # 401,沒有金鑰
curl https://GATEWAY_HOST/orders?key=YOUR_KEY
API 金鑰不是身分驗證
API 金鑰只回答「哪個應用在呼叫我」，用來做配額與用量統計。
它不能回答「哪個使用者在呼叫」，而且金鑰放在查詢字串裡會進到各種日誌。

要驗證使用者身分，用 JWT（Firebase Auth、Google ID token、或自家 OIDC）。金鑰與 JWT 是兩件事，通常一起用。

四、企業 API 治理的四個要素

要素要解決什麼做法
驗證與授權誰能呼叫哪些端點JWT 驗證 + 範圍（scope）控制
配額與限流單一客戶把服務打掛每金鑰每分鐘上限，超過回 429
版本管理改 API 不能弄壞既有客戶路徑帶版本（/v1、/v2），舊版設落日期程
可觀測性「客戶說很慢」要查得出來每次呼叫記錄延遲、狀態碼、呼叫方
版本落日的實務作法
宣布 v1 要停用時，光發信沒有用——一定有人不讀信。

有效的三段式：
① 先觀測：從 API 日誌撈出「還在用 v1 的呼叫方清單」，直接點名通知。
② brownout（間歇性中斷）：在落日前幾週，每天挑一小時讓 v1 回 410，逼還沒遷移的人有感。
③ 正式停用：保留一段時間的 410 回應並附上遷移文件連結，而不是直接 404。

五、IAP 與 API 管理怎麼搭配

兩種流量,兩種守門方式
【內部員工存取內部系統】
  員工瀏覽器 → LB → Cloud Armor → IAP → 內部工具
                                    ↑
                            Google 帳號 + IAM 群組

【外部程式呼叫你的 API】
  合作夥伴系統 → LB → Cloud Armor → API Gateway/Apigee → 後端服務
                                          ↑
                                  API 金鑰（配額）+ JWT（身分）

共通層:Cloud Armor 擋 DDoS 與惡意流量
共通層:Cloud Logging 記錄所有存取,供稽核
不要用 IAP 保護給機器呼叫的 API
IAP 的登入流程是瀏覽器導向的（會跳轉到 Google 登入頁）。機器對機器的呼叫走不了這個流程。

機器要通過 IAP，得用服務帳戶簽發 OIDC token，設定比較繞。
如果對象是程式而不是人，直接用 API Gateway + JWT 會單純很多。

六、本課檢核

  • 講得出 IAP 與 VPN 在權限粒度上的差別
  • 知道 IAP 生效的前提是「應用不能被繞過直連」
  • 能讀取 X-Goog-Authenticated-User-Email 取得使用者身分
  • 講得出 API Gateway、Cloud Endpoints、Apigee 的選擇時機
  • 知道 API 金鑰用於配額、JWT 用於身分，兩者不同
  • 知道 IAP 適合人、API Gateway 適合機器

自我檢測

你幫內部管理後台開了 IAP，但資安稽核說「這樣還是有風險」。他可能指的是什麼？
最可能是「應用程式可以被繞過 IAP 直接存取」。

IAP 是擋在 Load Balancer 那一層的。如果後端本身還有其他進入點，攻擊者根本不用經過 IAP：
• GCE 執行個體有對外 IP，防火牆又開了 0.0.0.0/0
• Cloud Run 設成 --allow-unauthenticated
• GKE Service 是 LoadBalancer 型態，自己就有一個公開 IP

修正方式：
① 移除後端的對外 IP，或防火牆只允許 Google LB 的來源網段（35.191.0.0/16、130.211.0.0/22）
② Cloud Run 設 ingress 為「僅限內部與 Cloud Load Balancing」
③ 應用層再驗一次 X-Goog-IAP-JWT-Assertion 的簽章——這樣即使網路層被繞過，應用自己也會拒絕

第 ③ 點是縱深防禦的精神：不要把安全性完全押在單一層。
主管看到 Apigee 的簡報很心動，說「我們也要導入」。公司目前只有一個給自家 App 用的後端 API。你怎麼建議？
先問一句：這個 API 會對外賣嗎？

如果答案是「不會，只有自家 App 呼叫」，那 Apigee 的功能九成用不到——開發者入口網站、分級計費方案、合作夥伴自助申請、複雜流量政策，這些都是為了把 API 當成商品在賣而設計的。

目前的需求用便宜的方案就能滿足：
• 身分驗證 → Firebase Auth 或 Google ID token 的 JWT 驗證
• 防濫用 → API Gateway 的配額，或 Cloud Armor 的速率限制
• 監控 → Cloud Logging + Monitoring

什麼時候回頭看 Apigee：
• 開始有外部客戶要串接，而且數量會成長
• 需要依用量分級收費
• 需要合作夥伴自己申請金鑰、自己看用量（不然這些都是你的客服工作）

講法建議：「這些功能我們現在都用不到，但它解決的問題是真的。等我們開始對外賣 API，我會第一個提出來。」——不要否定工具，要說清楚時機。
合作夥伴的系統要定時呼叫你的 API 拉資料。你打算用 IAP 保護。這個設計有什麼問題？
對象搞錯了。IAP 是為「人用瀏覽器」設計的。

IAP 的驗證流程會把未登入的請求導向 Google 登入頁。合作夥伴的排程程式收到的會是一個 HTML 登入頁面，而不是 JSON 資料。

技術上有解，但很繞：合作夥伴要用服務帳戶產生 OIDC token 放進 Authorization header。這代表：
• 他們必須有 Google Cloud 帳號
• 你要教他們怎麼設定
• 金鑰輪替的流程要一起處理

比較好的設計：
用 API Gateway，發給合作夥伴一組 API 金鑰（做配額與用量統計）+ 要求 JWT（做身分驗證）。這是業界標準做法，對方的工程師一看就懂，不用學 GCP 特有的東西。

判斷原則很簡單：使用者是人就用 IAP，是程式就用 API Gateway。
