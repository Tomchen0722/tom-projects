LESSON 17

Cloud Storage：物件儲存的一切

Cloud Storage 是你在 GCP 用得最頻繁的服務——備份、日誌、圖片、資料湖、靜態網站全都靠它。這一課把儲存等級、生命週期與權限一次講完。

操作 40 分約 0 元實作

一、物件儲存不是檔案系統

Cloud Storage 存的是物件（object），不是檔案。這個差別會影響你的所有設計：

檔案系統（如 NFS）物件儲存（Cloud Storage）
結構真的有目錄樹扁平的。a/b/c.txt 只是一個名字，斜線沒有特殊意義
修改可以改檔案的某幾個位元組只能整個覆蓋，不能局部修改
存取掛載後像本機磁碟透過 HTTP API
延遲微秒級數十毫秒
容量有上限無限
適合作業系統、資料庫檔案備份、媒體檔、日誌、資料湖、靜態資源
小心踩雷
不要把 Cloud Storage 當成磁碟用。雖然有 Cloud Storage FUSE 可以掛載成目錄，但底層每次讀寫都是完整的 HTTP 請求。把資料庫檔案放上去會慢到無法使用。
需要共享檔案系統請用 Filestore（託管 NFS），需要磁碟請用 Persistent Disk。

二、四種儲存等級：用「多久讀一次」來選

等級儲存費
(每GB/月)		取用費
(每GB)		最短保存期適用
Standard$0.020$0無每天都會讀：網站資源、進行中的資料
Nearline$0.010$0.0130 天每月讀一次：月報表資料、近期備份
Coldline$0.004$0.0290 天每季讀一次：季度歸檔
Archive$0.0012$0.05365 天幾乎不讀：法規保存、災難備援
取用仍是毫秒級，不像磁帶要等幾小時
小心踩雷
最短保存期是最容易被忽略的成本陷阱。
把檔案放進 Archive 後隔天刪除，你仍要付整整 365 天的儲存費。
算一筆帳：1TB 資料放 Archive 一天就刪 → 仍要付 $1.2 × 12 = 約 $14.4；但如果你頻繁寫入刪除，這個數字會不斷累積。
準則：只有確定「放進去就不會動」的資料才用 Coldline / Archive。

三、實作：建立與使用儲存桶

動手實作

實作：完整的 bucket 操作

  1. 建立儲存桶（名稱全球唯一，請加上你的專案代號）：
    bash
    gcloud storage buckets create gs://tom-gcp-lab-data \
  --location=asia-east1 \
  --default-storage-class=STANDARD \
  --uniform-bucket-level-access \
  --public-access-prevention
  2. 上傳、下載、列出：
    bash
    echo "測試內容" > test.txt
gcloud storage cp test.txt gs://tom-gcp-lab-data/
gcloud storage cp -r ./mydir gs://tom-gcp-lab-data/backup/    # 遞迴上傳
gcloud storage ls -l gs://tom-gcp-lab-data/
gcloud storage cat gs://tom-gcp-lab-data/test.txt
gcloud storage cp gs://tom-gcp-lab-data/test.txt ./downloaded.txt
  3. 同步整個目錄（類似 rsync，只傳有變動的）：
    bash
    gcloud storage rsync -r ./local-dir gs://tom-gcp-lab-data/synced/ --delete-unmatched-destination-objects
  4. 啟用版本控制（防止誤刪，強烈建議正式環境開啟）：
    bash
    gcloud storage buckets update gs://tom-gcp-lab-data --versioning

# 覆蓋同一個檔案，舊版本仍保留
echo "新內容" > test.txt
gcloud storage cp test.txt gs://tom-gcp-lab-data/
gcloud storage ls -a gs://tom-gcp-lab-data/test.txt   # 看到多個世代
  5. 設定生命週期規則（自動降等級、自動刪除，這是控制成本的關鍵）：
    bash
    cat > lifecycle.json <<'EOF'
{
  "lifecycle": {
    "rule": [
      {
        "action": {"type": "SetStorageClass", "storageClass": "NEARLINE"},
        "condition": {"age": 30, "matchesStorageClass": ["STANDARD"]}
      },
      {
        "action": {"type": "SetStorageClass", "storageClass": "COLDLINE"},
        "condition": {"age": 90, "matchesStorageClass": ["NEARLINE"]}
      },
      {
        "action": {"type": "SetStorageClass", "storageClass": "ARCHIVE"},
        "condition": {"age": 365, "matchesStorageClass": ["COLDLINE"]}
      },
      {
        "action": {"type": "Delete"},
        "condition": {"age": 2555}
      },
      {
        "action": {"type": "Delete"},
        "condition": {"numNewerVersions": 5, "isLive": false}
      }
    ]
  }
}
EOF
gcloud storage buckets update gs://tom-gcp-lab-data --lifecycle-file=lifecycle.json
實務提醒
上面那份生命週期設定值得存起來當範本。它做了四件事：30 天後降 Nearline、90 天降 Coldline、365 天降 Archive、7 年後刪除，同時只保留最近 5 個舊版本。
對一個典型的日誌桶，這套規則通常能把儲存成本降低 70～85%，而且完全自動。

四、位置類型：單區域 vs 多區域

類型範例可用性價格適用
Region 單一區域asia-east199.9%最便宜與運算資源同區，大多數情況的正確選擇
Dual-region 雙區域asia1（東京+大阪）99.95%中需要區域級容錯，且要求低延遲
Multi-region 多區域asia、us99.95%貴約 15~25%全球使用者存取的靜態內容
實務提醒
選錯位置類型的成本影響比你想像的大。
把資料放 multi-region 但運算在 asia-east1，每次讀取都算跨區流量。
準則：資料放在最常存取它的運算資源旁邊。只有「全球使用者直接下載」的內容（如網站圖片，且搭配 CDN）才需要 multi-region。

五、權限：兩種模式與五種存取方式

統一 vs 細粒度

  • Uniform bucket-level access（統一，建議）：只用 IAM，權限設在桶層級。簡單、可稽核、不會有「某個檔案不小心變公開」的意外。
  • Fine-grained（細粒度）：除了 IAM 還可以對每個物件設 ACL。強烈建議不要用——這是絕大多數 GCS 資料外洩事件的根因。
bash
# 授予服務帳號讀取權限
gcloud storage buckets add-iam-policy-binding gs://tom-gcp-lab-data \
  --member="serviceAccount:app@PROJECT.iam.gserviceaccount.com" \
  --role="roles/storage.objectViewer"

# 產生有時效的簽署網址（分享單一檔案給外部人員）
gcloud storage sign-url gs://tom-gcp-lab-data/report.pdf \
  --private-key-file=key.json --duration=1h

# 檢查有沒有公開的桶（資安必查）
gcloud storage buckets get-iam-policy gs://tom-gcp-lab-data \
  --format="json" | grep -E "allUsers|allAuthenticatedUsers"
小心踩雷
資料外洩事件的第一名原因：不小心把桶設成公開。
防範方式有三層：
① 建桶時加 --public-access-prevention；
② 用 --uniform-bucket-level-access 關掉物件層級 ACL；
③ 在 Organization 層級設 constraints/storage.publicAccessPrevention，讓任何人都無法建立公開桶。
第③層是唯一可靠的，前兩層都可以被個別使用者關掉。

功能解決什麼問題指令

鎖定後連 Owner 都刪不掉

實務提醒
Autoclass 值得認真考慮。它會自動監控每個物件的存取頻率，自動在四個等級之間移動，而且沒有最短保存期的懲罰。
代價是每個物件每月約 $0.0025 的管理費。如果你的存取模式難以預測，Autoclass 通常比自己寫生命週期規則更省。

八、本課檢核

  • 理解物件儲存與檔案系統的本質差異
  • 能依存取頻率選對儲存等級，且知道最短保存期的陷阱
  • 會寫生命週期規則自動降等級與刪除
  • 知道要用 uniform bucket-level access + public access prevention
  • 知道資料位置要跟運算資源在同一區

自我檢測

公司要保存 7 年的交易紀錄，共 50TB，法規要求「不可竄改、不可提前刪除」。怎麼設計？
Archive 等級 + Bucket Lock 保留政策：
bash
gcloud storage buckets create gs://audit-archive \
  --location=asia-east1 --default-storage-class=ARCHIVE \
  --uniform-bucket-level-access --public-access-prevention

gcloud storage buckets update gs://audit-archive --retention-period=2555d
gcloud storage buckets update gs://audit-archive --lock-retention-period  # 不可逆！
成本估算：50TB × $0.0012 × 12 ≈ 每年 $720。

關鍵注意事項：--lock-retention-period 是不可逆的，鎖定後連 Organization Admin 也無法縮短或刪除資料，桶也無法刪除。這正是法規要的效果，但執行前務必再三確認。建議先在測試桶上用短期限（如 1 天）演練一次。
網站的圖片放在 asia-east1，但有大量歐美使用者抱怨載入慢。怎麼解？
不是把資料搬到 multi-region，而是加 CDN。

正確做法：
① 建立 Global External Application LB，把 Cloud Storage 桶掛成 backend bucket；
② 啟用 Cloud CDN；
③ 設定合適的 Cache-Control 標頭。

效果：歐美使用者從當地的 Google 邊緣節點取得圖片（延遲從 250ms 降到 20ms），來源桶只在快取失效時被讀取。

為什麼不用 multi-region？因為 multi-region 只是把資料複製到幾個大區域，仍然不是邊緣節點，改善有限但費用增加 25%。CDN 有上百個節點，效果好得多且更便宜（CDN 快取命中的流量費比直接從 GCS 出還低）。
開發者說「我把 Cloud Storage 掛載成目錄，直接讓 SQLite 資料庫檔案放上去，這樣就有備份了」。你的評估？
這會壞掉，而且是很難查的那種壞法。三個理由：
① 物件儲存不支援局部寫入——SQLite 會頻繁修改檔案中間的位元組，而每次修改在 GCS FUSE 上都變成「下載整個檔案 → 修改 → 上傳整個檔案」。1GB 的資料庫每次寫入都要傳 1GB。
② 沒有檔案鎖——多個程序同時寫入會導致資料庫損毀，而且損毀可能過幾天才顯現。
③ 沒有 fsync 保證——斷電或實例重啟時，SQLite 的交易完整性無法保證。

正確做法：
• 需要 SQL → Cloud SQL（自帶自動備份、時間點還原）。
• 真的要用 SQLite → 放在 Persistent Disk 上，用快照做備份，或用 Litestream 之類的工具持續複製 WAL 到 GCS。
核心觀念：備份的目標是「資料能還原」，不是「檔案在雲上有一份」。
