LESSON 35

資安縱深：IAM 進階、密鑰與加密

資安不是一個開關，是一層層的防護。這一課把前面散落各處的資安概念整合成一套可執行的縱深防禦架構。

閱讀 28 分企業級

一、縱深防禦的七層

縱深防禦
① 組織政策 Organization Policy
     「全公司的硬性護欄」— 上層說不行就是不行
          ↓
② 身分與存取 IAM
     「誰能做什麼」— 最小權限
          ↓
③ 網路邊界 VPC / 防火牆 / VPC-SC
     「從哪裡能連進來」「資料能不能出去」
          ↓
④ 工作負載安全 Shielded VM / Binary Authorization
     「執行的是不是我們信任的東西」
          ↓
⑤ 資料保護 加密 / CMEK / DLP
     「就算拿到資料也讀不懂」
          ↓
⑥ 密鑰管理 Secret Manager / KMS
     「憑證不落地、可輪換、可撤銷」
          ↓
⑦ 偵測與回應 Audit Logs / SCC
     「出事時我們知道，且能追溯」

核心假設：每一層都會被突破。所以設計時要問「如果這一層失守，下一層擋得住嗎？」

二、IAM 進階：三個必須知道的機制

① Deny Policy：明確拒絕

一般 IAM 只有「允許」的加法。Deny Policy 提供了「拒絕」，而且優先於所有 allow：

bash
cat > deny-policy.json <<'EOF'
{
  "displayName": "禁止刪除正式環境資料庫",
  "rules": [{
    "denyRule": {
      "deniedPrincipals": ["principalSet://goog/public:all"],
      "exceptionPrincipals": ["principalSet://goog/group/dba-oncall@corp.com"],
      "deniedPermissions": [
        "cloudsql.googleapis.com/instances.delete",
        "spanner.googleapis.com/databases.drop"
      ]
    }
  }]
}
EOF

gcloud iam policies create deny-prod-db-delete \
  --attachment-point=cloudresourcemanager.googleapis.com/folders/FOLDER_ID \
  --kind=denypolicies --policy-file=deny-policy.json

② Conditional Binding：帶條件的權限

bash
# 只在上班時間、且從公司網段才能存取
gcloud projects add-iam-policy-binding PROJECT \
  --member="group:support@corp.com" \
  --role="roles/logging.viewer" \
  --condition='expression=
    request.time.getHours("Asia/Taipei") >= 9 &&
    request.time.getHours("Asia/Taipei") < 18,
    title=僅上班時間'

# 只能存取特定前綴的資源
--condition='expression=resource.name.startsWith("projects/_/buckets/public-"),title=僅公開桶'

③ 特權存取管理（Just-in-Time）

正式環境不該有人「永久」持有管理員權限。Privileged Access Manager 讓人在需要時申請、核准後取得有時效的權限：

bash
# 建立權限授予資格（entitlement）
gcloud pam entitlements create prod-dba-access \
  --location=global --organization=ORG_ID \
  --entitlement-file=entitlement.yaml

# entitlement.yaml 定義：
#   誰可以申請、需要誰核准、最長多久、給什麼角色
# 使用者申請後，核准者同意，權限在 4 小時後自動撤銷

三、Secret Manager：憑證的正確存放處

動手實作

實作：密鑰管理

  1. 建立密鑰：
    bash
    echo -n "my-super-secret-password" | \
  gcloud secrets create db-password \
    --data-file=- \
    --replication-policy=user-managed \
    --locations=asia-east1
  2. 存取與版本管理：
    bash
    gcloud secrets versions access latest --secret=db-password

# 輪換：新增版本，舊版本仍可用（讓應用有時間切換）
echo -n "new-password" | gcloud secrets versions add db-password --data-file=-

# 確認新版本正常後，停用舊版本
gcloud secrets versions disable 1 --secret=db-password

# 徹底銷毀
gcloud secrets versions destroy 1 --secret=db-password
  3. 授權給服務帳號（權限給在單一密鑰上，不要給整個專案）：
    bash
    gcloud secrets add-iam-policy-binding db-password \
  --member="serviceAccount:app@PROJECT.iam.gserviceaccount.com" \
  --role="roles/secretmanager.secretAccessor"
  4. 在 Cloud Run 中使用：
    bash
    # 方式一：注入為環境變數（簡單）
gcloud run services update task-api \
  --set-secrets=DB_PASSWORD=db-password:latest

# 方式二：掛載為檔案（更安全，不會出現在程序環境中）
gcloud run services update task-api \
  --set-secrets=/secrets/db-password=db-password:latest
  5. 設定輪換提醒：
    bash
    gcloud secrets update db-password \
  --next-rotation-time="2026-10-31T00:00:00Z" \
  --rotation-period="90d" \
  --topic=projects/PROJECT/topics/secret-rotation
小心踩雷
用 :latest 還是固定版本號？
• :latest：輪換後自動生效，但如果新版本是壞的，所有服務同時掛掉。
• 固定版本（:3）：需要重新部署才生效，但可控、可漸進。

正式環境建議：釘住版本號，把密鑰輪換納入正常的部署流程。這樣輪換也能享受金絲雀部署的保護。

四、加密：三種層級

層級誰持有金鑰適用設定成本
Google 預設加密Google所有資料預設就有，靜態與傳輸中都加密零，自動
CMEK
客戶管理金鑰		你（存在 Cloud KMS）法遵要求「客戶控制金鑰」、需要能撤銷存取中
CSEK / EKM
客戶提供 / 外部金鑰		你（在 GCP 外）極高安全要求、金鑰絕不能進雲高
bash
# 建立金鑰環與金鑰
gcloud kms keyrings create prod-keyring --location=asia-east1

gcloud kms keys create data-key \
  --location=asia-east1 --keyring=prod-keyring \
  --purpose=encryption \
  --rotation-period=90d \
  --next-rotation-time=2026-10-31T00:00:00Z

# 授權服務使用金鑰
gcloud kms keys add-iam-policy-binding data-key \
  --location=asia-east1 --keyring=prod-keyring \
  --member="serviceAccount:service-PROJECT_NUMBER@gs-project-accounts.iam.gserviceaccount.com" \
  --role="roles/cloudkms.cryptoKeyEncrypterDecrypter"

# 用 CMEK 建立資源
gcloud storage buckets create gs://sensitive-data \
  --location=asia-east1 \
  --default-encryption-key=projects/PROJECT/locations/asia-east1/keyRings/prod-keyring/cryptoKeys/data-key
實務提醒
CMEK 的真正價值是「可撤銷」。如果你停用或銷毀金鑰，所有用它加密的資料立即變成無法讀取——即使是 Google 也讀不了。
這在「員工離職帶走資料」「法規要求證明資料已銷毀」的情境有實際意義。
但也是雙面刃：金鑰誤刪 = 資料永久遺失。所以金鑰的 IAM 權限要比資料本身更嚴格。

五、Security Command Center：資安的統一儀表板

SCC 自動掃描並回報：

  • 設定錯誤：公開的儲存桶、開放的防火牆、未加密的資料庫
  • 漏洞：容器映像與 VM 的 CVE
  • 威脅偵測：異常的 API 呼叫模式、加密貨幣挖礦、對外的異常連線
  • 法遵狀態：對照 CIS Benchmark、PCI-DSS、ISO 27001 的落差報告
bash
gcloud scc findings list ORGANIZATION_ID \
  --filter="state=\"ACTIVE\" AND severity=\"HIGH\"" \
  --format="table(category, resourceName, eventTime)"

# 把發現的問題送到 Pub/Sub 觸發自動修復
gcloud scc notifications create high-severity-alerts \
  --organization=ORG_ID \
  --pubsub-topic=projects/PROJECT/topics/scc-findings \
  --filter="severity=\"HIGH\" OR severity=\"CRITICAL\""

六、資安檢核清單（可直接拿去用）

  • Organization Policy 已設定：禁止公開桶、禁止服務帳號金鑰、限制資源位置
  • 沒有任何使用者持有 Owner 或 Editor 角色（除了必要的少數）
  • 所有服務帳號金鑰檔已清除，改用 Workload Identity
  • 正式環境資料庫僅有私有 IP
  • 所有密鑰存在 Secret Manager，且已設定輪換排程
  • VPC Flow Logs 與 Data Access Audit Logs 已啟用
  • Security Command Center 已啟用並有人負責處理發現的問題
  • 已有稽核日誌的長期保存（GCS Archive + Bucket Lock）
  • Binary Authorization 已在正式環境強制執行
  • 定期（每季）執行權限盤點與 IAM Recommender 清理

七、本課檢核

自我檢測

稽核發現有 15 個服務帳號金鑰檔散落在各處。怎麼處理？
分四步，順序很重要——先建替代方案，再撤銷：

① 盤點使用情形——用 gcloud iam service-accounts keys list 找出所有金鑰，並查 Audit Log 看每把金鑰最近的使用時間與來源 IP。沒用過的直接刪，這通常佔一半。

② 依使用場景導入替代方案：
  • GCP 內執行（VM/Cloud Run/GKE）→ 附加服務帳號 或 Workload Identity，完全不需要金鑰。
  • GitHub Actions / GitLab CI → Workload Identity Federation，用 OIDC token 換取短期憑證。
  • 地端系統 → Workload Identity Federation 或 短期金鑰 + 自動輪換。

③ 逐一遷移並驗證——每遷移一個就停用（disable，不是刪除）對應的金鑰，觀察一週確認沒問題再刪除。disable 可以復原，delete 不行。

④ 從源頭封死——設定 Organization Policy constraints/iam.disableServiceAccountKeyCreation，讓未來沒有人能再產生金鑰。

順序錯誤的後果：先設政策禁止建立，結果有人的金鑰過期後無法重新產生，服務中斷。
開發者說「我需要正式環境的資料庫權限來排查問題」。怎麼回應？
不要直接給，也不要直接拒絕——提供一條安全的路徑。

依需求的具體程度，由輕到重：

① 先確認真正需要什麼——多數「需要資料庫權限」其實是「需要看某個查詢的結果」或「需要知道某筆資料的狀態」。如果日誌與監控足夠好，通常不需要碰資料庫。這反過來是可觀測性的改善需求。

② 唯讀副本 + 遮罩——建立一個 PII 已遮罩的唯讀副本，開發者可以自由查詢。

③ Just-in-Time 存取——用 Privileged Access Manager：開發者申請 → 主管核准 → 取得 2 小時的權限 → 自動撤銷。全程有記錄。

④ Session 錄影——若必須直接操作正式環境，透過堡壘機並錄製操作過程。

都要搭配：Data Access Audit Logs 全開，事後可稽核；且對大量資料匯出設定告警。

核心原則：不要在「安全」與「能做事」之間二選一——那會逼人用不安全的方式偷做。要提供一條又安全又順暢的路。
公司要通過 ISO 27001 稽核。GCP 這邊要準備什麼？
先釐清一個常見誤解：GCP 本身有 ISO 27001 認證，但那只涵蓋「Google 的責任」，不涵蓋你的設定。這叫共同責任模型。

你要準備的四類證據：

① 存取控制
  • IAM 政策的匯出與定期審查記錄
  • 權限申請與核准流程的證據（PAM 的記錄很好用）
  • 離職員工權限撤銷的記錄

② 資料保護
  • 加密設定（靜態 + 傳輸中）的證明
  • CMEK 金鑰管理與輪換記錄
  • 資料分類與保留政策

③ 可稽核性
  • Cloud Audit Logs 全面啟用，並匯出到不可竄改的儲存（GCS + Bucket Lock）
  • 保留期符合要求（通常 1～7 年）

④ 持續監控與改善
  • Security Command Center Premium 的法遵儀表板可以直接產出對照 ISO 27001 控制項的報告
  • 弱點管理流程與修補記錄
  • 事故處理記錄與事後檢討報告

最實用的一招：用 Assured Workloads 或 Terraform + Policy as Code，讓法遵設定變成程式碼。稽核時直接展示 Git 記錄，證明控制項從未被繞過——這比事後整理文件有說服力得多。

另外記得下載 Google 的合規文件（Compliance Reports Manager），稽核員會要求看雲廠商的認證。
