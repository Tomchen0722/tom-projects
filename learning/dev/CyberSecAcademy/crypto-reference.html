1. 三大類型概覽

對稱加密 Symmetric 加密 = 解密用同一把金鑰
✅ 速度快（硬體加速）
❌ 金鑰分發問題（如何安全傳金鑰？）
用途：大量資料加密（磁碟、資料庫、通訊內容）
非對稱加密 Asymmetric 公鑰加密，私鑰解密（或反過來用於簽章）
✅ 安全金鑰交換（公鑰可公開）
❌ 速度慢（比對稱慢 1000x）
用途：金鑰交換、數位簽章、憑證
雜湊函數 Hash 單向函數，不可逆
✅ 固定長度輸出、任何輸入變更都會改變雜湊值
❌ 不是加密（無法解密）
用途：密碼儲存、資料完整性驗證、數位簽章
混合加密 Hybrid TLS 的實際做法：
① 非對稱交換會話金鑰
② 用對稱加密傳資料
同時獲得兩者優點（安全+速度）

2. 對稱加密演算法

演算法金鑰長度區塊大小狀態考試重點
AES
Advanced Encryption Standard		 128 / 192 / 256 bit 128 bit ✅ 現代標準 政府、金融的標準加密；AES-256 是最高安全等級
3DES
Triple DES		 112 或 168 bit（實效） 64 bit ⚠️ 逐漸淘汰 DES 應用三次，比 DES 安全但比 AES 慢；舊系統相容性
DES
Data Encryption Standard		 56 bit 64 bit ❌ 已被破解 金鑰太短，可暴力破解。不應使用
RC4 40-2048 bit（串流加密） N/A（串流） ❌ 已棄用 WEP、舊版 TLS 用過；已有已知攻擊，不安全
ChaCha20 256 bit（串流加密） N/A（串流） ✅ 現代標準 無硬體 AES 加速時（行動裝置）比 AES 更快；TLS 1.3 支援
Blowfish / Twofish 128-448 / 128-256 bit 64 / 128 bit ⚠️ 特殊用途 Blowfish 64-bit 區塊有生日攻擊風險（不用於大量資料）

AES 操作模式（Modes of Operation）

模式特性Security+ 考點
ECB（電子密碼本）最簡單，每個區塊獨立加密❌ 不安全！相同明文→相同密文（企鵝圖示攻擊）
CBC（密碼區塊鏈結）每個區塊依賴前一個密文，需 IVTLS 1.2 常用；Padding Oracle Attack 弱點
CTR（計數器）把 AES 轉換成串流加密，可平行處理快速，適合隨機存取
GCM（伽羅瓦計數器）同時加密+認證（AEAD），內建完整性驗證✅ TLS 1.3 推薦；同時防竄改
考試陷阱：題目說「需要同時加密和確保資料完整性」→ AES-GCM（AEAD = Authenticated Encryption with Associated Data）

3. 非對稱加密演算法

演算法安全金鑰長度用途考試重點
RSA 2048 bit 最低
4096 bit 高安全		 金鑰交換、數位簽章、憑證 1024 bit 已不安全；2048 bit 是現在的最低標準。基於大數因式分解難題
ECC
Elliptic Curve Cryptography		 256 bit ≈ RSA 3072 bit
更短金鑰、更強安全		 TLS（ECDHE）、行動裝置、IoT 比 RSA 更高效（同等安全但金鑰更短）；行動/資源受限設備首選
ECDSA
ECC + DSA		 256 / 384 / 521 bit 數位簽章 比 RSA 簽章更快、金鑰更短；比特幣、TLS 1.3 使用
Diffie-Hellman (DH) 2048 bit 最低 金鑰交換（不傳金鑰本身） 在不安全通道上協商共享金鑰，本身不做身分驗證
ECDH / ECDHE 256 bit 起 TLS 金鑰交換 ECDHE 的 E = Ephemeral（臨時金鑰）→ 提供 Forward Secrecy
DSA 2048 / 3072 bit 數位簽章 比 RSA 更快簽章，但無法加密；已被 ECDSA 取代
數位簽章流程（非對稱 + 雜湊）：
發送方：訊息 → Hash（摘要） → 用私鑰加密摘要 = 簽章
接收方：收到訊息+簽章 → 用公鑰解密簽章拿到摘要A → 自己算訊息的摘要B → A==B 則驗簽成功

記憶口訣：
加密傳給對方：用對方的公鑰加密（只有他的私鑰能解）
簽章證明是我：用自己的私鑰簽（任何人用我的公鑰可驗證）
最常考的陷阱：
「公鑰加密，公鑰解密」❌
「公鑰加密，私鑰解密」✅（加密用途）
「私鑰簽章，公鑰驗簽」✅（簽章用途）

4. 雜湊函數（Hash Functions）

演算法輸出長度狀態考試重點
MD5128 bit（32 hex）❌ 已破解（可找碰撞）不應用於密碼或完整性驗證；仍用於非安全場景（快速校驗和）
SHA-1160 bit（40 hex）❌ 碰撞已被證明瀏覽器已停止信任 SHA-1 憑證（2017 起）
SHA-256256 bit（64 hex）✅ 現代標準SHA-2 家族；TLS、憑證、比特幣
SHA-384 / SHA-512384 / 512 bit✅ 高安全SHA-2 家族；政府機密資料
SHA-3（Keccak）224-512 bit✅ 最新標準SHA-2 的替代方案（不同架構，若 SHA-2 被破解時備用）
bcrypt60 字元（固定）✅ 密碼儲存首選內建 Salt、可調整運算成本（work factor）、抵抗 GPU 暴力破解
Argon2可變✅ 最新密碼 Hash2015 Password Hashing Competition 冠軍；記憶體消耗型

HMAC（Hash-based Message Authentication Code）

HMAC = Hash(金鑰 + 訊息)

單純 Hash 只驗完整性（有沒有被改）
HMAC 同時驗完整性 + 來源（只有知道金鑰的人才能產生正確的 HMAC）

常見：HMAC-SHA256 用於 JWT 簽章、API 請求驗證

5. PKI 與數位憑證

PKI 角色

角色功能考試重點
Root CAPKI 信任根，自簽憑證。通常離線（Air-gapped）Root CA 的私鑰一旦外洩，整個 PKI 體系崩潰
Intermediate CA
（Subordinate CA）		Root CA 簽發的中間 CA，實際簽發 End-Entity 憑證Root CA 通常離線，Intermediate CA 在線上簽憑證
End-Entity 憑證伺服器/使用者的實際憑證包含：公鑰、擁有者資訊、有效期、簽發 CA 資訊、Subject Alternative Names（SAN）
RA（Registration Authority）驗證憑證申請者的身分（不直接簽發）RA 驗身分，CA 簽憑證，分工合作
CRL（Certificate Revocation List）已撤銷憑證的清單，定期發布CRL 是批次下載，可能有延遲；OCSP 是即時查詢
OCSP（Online Certificate Status Protocol）即時查詢憑證是否已撤銷OCSP Stapling：伺服器預先取得 OCSP 回應並附在 TLS 握手中，減少延遲

憑證類型

DV（Domain Validation）只驗域名所有權（自動化，幾分鐘）。HTTPS 加密，但不驗公司身分。Let's Encrypt 是 DV。
OV（Organization Validation）驗域名 + 公司合法性（需人工審查，數天）。憑證中包含公司名稱。
EV（Extended Validation）最嚴格，驗公司、地址、電話（數週）。舊時瀏覽器會顯示綠色公司名，現在大多數瀏覽器已取消此顯示。
Wildcard（萬用字元）*.example.com：涵蓋所有一層子域（a.example.com、b.example.com），但不涵蓋 a.b.example.com。
SAN（Subject Alternative Names）一張憑證涵蓋多個域名（example.com、example.tw、api.example.com）。現代 TLS 的標準做法。
Self-signed（自簽憑證）自己簽給自己，瀏覽器不信任。僅適合測試環境或內部系統（配合自有 CA）。

X.509：憑證裡面到底裝了什麼

所有的 TLS 憑證都遵循 X.509 這個格式標準。知道裡面有哪些欄位，排錯時才知道要看什麼。

欄位內容排錯時的用途
Subject這張憑證發給誰（CN、O、C）確認憑證是不是發給正確的網域
Issuer誰簽發的（哪個 CA）信任鏈斷掉時從這裡往上追
ValidityNot Before / Not After憑證過期是最常見的故障
Public Key公鑰與演算法（RSA 2048、ECDSA P-256）確認金鑰強度是否符合政策
SAN涵蓋的所有網域名稱現代瀏覽器只看 SAN，不看 CN
Key Usage / EKU這張憑證能拿來做什麼（伺服器驗證、用戶端驗證、簽章）用途不符會被拒絕
SignatureCA 用自己的私鑰對以上內容的簽章驗證憑證未被竄改
實際查看一張憑證：
openssl s_client -connect example.com:443 -servername example.com < /dev/null \
  | openssl x509 -noout -text

只看關鍵欄位：
openssl x509 -noout -subject -issuer -dates -ext subjectAltName
常見陷阱：CN 已經不夠用了。從 2017 年起主流瀏覽器只檢查 SAN 欄位。如果憑證只寫了 CN 沒寫 SAN，Chrome 會直接判定不安全——這是自簽憑證最常見的失敗原因。

mTLS：雙向驗證

一般的 TLS 只有用戶端驗證伺服器（你確認銀行網站是真的）。mTLS（Mutual TLS）則是雙方互相驗證。

一般 TLSmTLS
誰驗誰用戶端驗伺服器雙方互驗
用戶端要有憑證嗎不用要，每個用戶端各有一張
典型場景一般網站 HTTPSAPI 對 API、微服務之間、IoT 裝置、零信任架構
身分依據帳號密碼／Token憑證本身就是身分
為什麼機器對機器要用 mTLS：API 金鑰會外洩、會被寫進程式碼、輪替麻煩。憑證有明確的有效期、可以被撤銷、而且私鑰不會離開持有者。這是服務網格（Istio、Linkerd）預設啟用 mTLS 的原因。

代價：要自建 CA 並管理憑證生命週期——幾百個微服務就是幾百張憑證要簽發、輪替、撤銷。這也是為什麼要用自動化的憑證管理。
憑證信任鏈驗證：
瀏覽器收到伺服器憑證
→ 檢查簽發者（Intermediate CA）→ 驗 Intermediate CA 的簽章
→ 往上找 Root CA → 檢查 Root CA 是否在瀏覽器的信任存儲中
→ 全部通過 = 信任；任一環節失敗 = 憑證錯誤警告

6. 常見協議的加密組合

協議使用的加密Security+ 考點
TLS 1.3ECDHE（金鑰交換）+ AES-GCM / ChaCha20（加密）+ SHA-384（HMAC）廢除 RSA 金鑰交換（無 Forward Secrecy）；強制 Forward Secrecy
TLS 1.2RSA 或 ECDHE + AES-CBC 或 AES-GCM + SHA-256仍廣泛使用，但不如 TLS 1.3 安全；仍支援較弱的 Cipher Suite
SSHDiffie-Hellman / ECDH（金鑰交換）+ AES / ChaCha20（加密）+ HMAC-SHA2比密碼更安全的是 Public Key Authentication（SSH Key）
IPsecAES（加密）+ SHA-256/384/512（完整性）+ DH/ECDH（金鑰交換）VPN 常用；AH 只提供完整性、ESP 提供加密+完整性
PGP / GPGRSA 或 ECC（金鑰加密）+ AES（訊息加密）+ SHA-256（雜湊）Email 加密與簽章；Web of Trust（去中心化信任）
WPA3SAE（Simultaneous Authentication of Equals）取代 WPA2-PSK防止離線字典攻擊；Forward Secrecy；DRAGONBLOOD 是 WPA3 的已知弱點
Forward Secrecy（前向保密）：即使伺服器的長期私鑰被竊，過去的通訊記錄也無法被解密。實現方式：每次會話都用臨時（Ephemeral）金鑰對（ECDHE 中的 E 就是 Ephemeral）。TLS 1.3 強制所有連線都有 Forward Secrecy。

7. 考試陷阱彙整

題目情境答案關鍵字
最快的加密方式？AES-256（對稱加密，有硬體加速）
行動/IoT 設備需要非對稱加密？ECC（金鑰短、計算量少）
同時加密 + 驗完整性？AES-GCM（AEAD）
密碼存在資料庫的最佳方式？bcrypt 或 Argon2（不是 SHA-256！Hash 需要加 Salt 且要慢）
需要 Forward Secrecy 的 TLS？ECDHE（E = Ephemeral = 臨時金鑰）
即時查詢憑證是否撤銷？OCSP（CRL 是批次下載，有延遲）
安全等級最高的加密標準（美國政府）？AES-256（NSA Suite B，最機密資料）
金鑰長度等效安全性？ECC 256 ≈ RSA 3072（ECC 更短但等效安全）
已被破解、不應使用？DES（56 bit）、MD5（可找碰撞）、SHA-1（已有碰撞）、RC4
Quantum Computing 威脅？AES-256 和 SHA-384 有一定抵抗力；RSA/ECC 可能被量子電腦破解 → 後量子密碼學（PQC）
