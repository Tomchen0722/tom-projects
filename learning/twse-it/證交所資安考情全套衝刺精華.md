### 【滿分標竿答題範本（五段式架構示範）】

#### 一、破題立論：金融關鍵基礎設施與縱深治理方針
臺灣證券交易所（TWSE）肩負資本市場交易撮合與金融穩定重任，屬《資通安全管理法》明定之 A 級關鍵基礎設施核心機關。面對混合雲遷移與委外軟體開發，必須在政策面深化風險治理，全面遵循 ISO/IEC 27001:2022 控制措施與金管會「金融資安行動方案 2.0」，建構兼具供應鏈韌性、零信任動態防禦與快速復原（Resilience）之金融防護體系。

#### 二、第三方供應鏈 SBOM 查核與 ISO 27001:2022 控制落實
針對委外軟體廠商與雲端服務業者，應自「採購選商、開發交付、營運查核」全生命週期實施三項關鍵控制：
1. **軟體物料清單（SBOM）與交付查核**：
   * **標準化交付**：強制委外廠商隨版本交付遵循國際標準格式（SPDX 或 CycloneDX）之機器可讀 SBOM 清單，詳列所有開源與第三方元件、版本號及數位雜湊。
   * **安全檢測標準**：實施靜態原始碼安全檢測（SAST，重大弱點零容忍）、軟體相依性分析（SCA，比對 CVE 漏洞庫），並透過數位簽章（Cosign/Sigstore）防範編譯管線供應鏈投毒。
2. **ISO/IEC 27001:2022 新版三大關鍵控制措施之落地**：
   * **A.5.7 威脅情資（Threat Intelligence）**：建立外部情資介接流程，主動將金融資安資訊分享與分析中心（F-ISAC）與國家資通安全會報所發布之最新 IoC/IoA，整合至 SOC 與 SIEM 關聯規則中預防性封鎖。
   * **A.5.23 雲端服務資安（Cloud Services Security）**：依據「共擔責任模型（Shared Responsibility Model）」，明確界定證交所（資料主權、組態與存取控制）與雲端業者（實體設施與虛擬化底層）之職責，落實租戶隔離與定期第三方合規稽核報告（SOC 2 Type II）。
   * **A.8.11 資料屏蔽（Data Masking）**：於非正式環境（測試、開發）與日誌記錄中，針對投資人身分證號、銀行帳號及敏感交易軌跡，全面落實動態遮罩（Dynamic Masking）、假名化（Pseudonymization）與不可逆雜湊，防止機敏資料橫向洩漏。

#### 三、六大階段資安事件應變流程與「30 分鐘重大通報機制」
當系統遭遇進階持續性威脅或勒索軟體攻擊時，應即刻啟動電腦緊急應變小組（CSIRT），遵循 NIST SP 800-61 六大階段處置：
1. **準備階段（Preparation）**：平時完備金融重大事件 Playbook、部署 EDR 與不可篡改儲存（WORM）。
2. **偵測與分析（Detection & Analysis）**：透過 SOC/SIEM 彙整終端日誌與異常流量，辨識攻擊手法（MITRE ATT&CK）並界定受駭範圍。
3. **圍堵階段（Containment）**：
   * **短程圍堵**：以網路微隔離（Cilium eBPF）立即阻斷受害雲端執行個體對內部核心撮合網路之連線。
   * **長程圍堵**：保留主機記憶體映像檔（Memory Forensics）與日誌證據鏈，供司法與監管機關鑑定。
4. **清除階段（Eradication）**：全面撤銷遭滲透之 API 金鑰與管理員憑證，清除惡意後門並完成系統弱點修補。
5. **復原階段（Recovery）**：以經簽章驗證之乾淨黃金映像檔（Golden Image）重建服務，驗證資料庫交易一致性，並實施強化監控後分階段上線。
6. **事後檢討（Lessons Learned / RCA）**：於事件平息後 3 個工作天內完成根本原因分析（RCA）報告，優化防禦規則。
* **臺灣金融專屬「30 分鐘重大資安通報」法定程序**：
  依據《證券期貨業資通安全聯合防禦應變作業程序》，當發生「核心系統中斷 10 分鐘以上」或「機敏個資大量外洩」等重大資安事件時，自**「知悉（Awareness）」起 30 分鐘內**，必須循通報管道向主管機關（金管會證期局）與 F-ISAC 完成初報；後續每 2 小時滾動回報處置進度，以啟動跨機構金融聯防。

#### 四、營運持續管理（BCP/BIA）與法定日誌保存實務
1. **業務影響分析（BIA）與 RTO / RPO 達成方案**：
   * **關鍵系統優先順序**：透過 BIA 評估各服務中斷之財務損失與監管懲處，將交易撮合、結算交割列為最優先復原等級。
   * **極致復原指標**：建置「同城雙活（Active-Active）資料庫」搭配同步複製（Synchronous Replication），確保交易數據 **RPO = 0**；配合自動容錯移轉（Failover）與備援線路，使撮合中斷之 **RTO ≤ 10 分鐘**。
   * **不可篡改備份**：落實「3-2-1-1-0」原則，至少一份離線隔離（Air-Gapped）或啟用 WORM 唯讀鎖定之不可變備份，嚴防勒索軟體加密。
2. **系統日誌（Log）法定保存規範**：
   * **留存年限**：依據金融監管查核要求，邊界防火牆、入侵偵測（IDS/IPS）及網路設備日誌至少保存 **3 年**；核心主機作業日誌、資料庫存取紀錄及稽核軌跡（Audit Trail）至少保存 **5 年**。
   * **完整性防護**：日誌須以唯讀協定即時傳輸至獨立之集中式 Log Server / SIEM，並施加 NTP/PTP 高精度時間戳記與 HMAC 數位雜湊，確保法庭證據之真實性與不可否認性。

#### 五、結論：邁向主動防禦與金融營運韌性
面對多變的國際網路威脅，證交所不應僅滿足於被動合規，而應結合供應鏈嚴格審查、零信任動態存取及 F-ISAC 全國金融聯防，將資安防護內化為業務持續運作的基石，打造安全、穩定、深具國際信賴之資本市場交易環境。

| :--- | :--- | :--- | :--- |
| **A01:2021<br>權限控制失效<br>(Broken Access Control)** | 存取控制策略未在伺服器端強制執行，導致未授權存取、越權操作。包含水平越權（BOLA/IDOR，用戶A查用戶B個資）與垂直越權（一般下單帳戶躍升管理員）。 | 網銀/證券 API 直接透過 URL 參數（如 `accountId=1002`）查詢交易紀錄，未檢核該帳戶是否屬於當前登入者。 | 1. **預設拒絕（Deny by default）**。<br>2. 實施基於屬性/角色存取控制（ABAC/RBAC）。<br>3. 伺服器端強制校驗 Session/Token 與資源所屬權，嚴禁前端傳遞客戶主鍵。<br>4. 關閉目錄瀏覽，API 實施嚴格 CORS 白名單。 |

# 模組三：金融零信任架構（ZTA）在證券體系中的「三大驗證核心」

依據 **NIST SP 800-207** 零信任標準與金管會「金融資安行動方案 2.0」要求，證券期貨業必須揚棄傳統「邊界內即信任」之城堡護城河模型，轉向「**永不信任，始終驗證（Never Trust, Always Verify）**」之現代縱深防禦架構。其落地核心建立於以下三大支柱：

```
                    ┌─────────────────────────────────────────┐
                    │        政策決策點 PDP (Policy Engine)    │
                    │  身分信任評級 + 設備基準 + 情境推斷 UEBA  │
                    └────────────────────┬────────────────────┘
                                         │ 動態核發短期 mTLS 權杖
                                         ▼
[使用者/委外工程師] ────────▶ [ 政策強制點 PEP 閘道器 ] ────────▶ [核心撮合/敏感資產]
  - FIDO2 無密碼驗證           - Cilium eBPF 微隔離            - 最小特權原則
  - 設備健康度 (TPM 2.0)        - 阻斷未授權橫向移動            - 持續動態評估
```

### 1. 第一核心：身分鑑別（Identity Pillar）—— 從靜態密碼邁向強韌抗釣魚
* **傳統缺陷**：傳統帳號密碼極易遭暴力破解、撞庫攻擊或社交工程釣魚；即使配置簡訊 OTP，亦容易遭 SIM 換卡或反向代理釣魚網站（AiTM）中間人攔截。
* **證券體系零信任落地方案**：
  * **FIDO2 / WebAuthn 來源網域綁定**：身分驗證強制採用公私鑰非對稱密碼機制。私鑰安全封存於硬體金鑰（如 YubiKey、終端 TPM 晶片），驗證過程將當前瀏覽器 URL 網域名稱寫入驗證特徵（Origin Binding），即使進入偽冒釣魚網站亦無法簽發有效驗證，從物理根源徹底杜絕釣魚攻擊。
  * **特權存取管理（PAM）與 JIT 動態授權**：針對內部系統工程師與委外維運廠商，廢除長效靜態帳密，全面改採**及時授權（Just-In-Time, JIT）**與**足額特權（Just-Enough-Access）**；連線全程透過堡壘機錄影並啟用「雙人授權（Dual Control）」，連線結束憑證立即自動撤銷廢棄。

### 2. 第二核心：設備健康度基線（Device Pillar）—— 硬體根基信任與端點安全態勢
* **傳統缺陷**：傳統 VPN 只要使用者帳密正確，即允許任何受感染或缺乏防護的私人筆電接入內網，成為勒索軟體橫向擴散溫床。
* **證券體系零信任落地方案**：
  * **TPM 2.0 硬體認證（Device Health Attestation）**：連線設備必須具備 TPM 2.0 安全晶片，於開機載入引導時透過「安全開機（Secure Boot）」計算核心雜湊，向驗證伺服器證明作業系統與開機程式未遭篡改（無 Rootkit/Bootkit）。
  * **端點態勢感知（EDR Posture Check）**：政策強制點（PEP）於建立連線前，動態檢查設備是否符合基準線：
    * EDR / XDR 常駐且防毒特徵碼為最新。
    * 作業系統重大安全性更新（Hotfix）已修補。
    * 全磁碟加密（BitLocker）啟用中。
    * 嚴格停用外部 USB 儲存裝置。
  * **委外人員實體隔離檢測**：委外廠商筆電進入證交所機房前，必須於「安全隔離清洗站（Security Kiosk）」進行惡意程式靜態深層掃描，並透過單向光閘（Data Diode）傳輸維護檔案，嚴禁未檢測設備直接接觸生產網路。

### 3. 第三核心：情境與動態信任推斷（Contextual Trust Inference Pillar）—— PDP / PEP 動態風險授權
* **核心概念**：零信任的核心大腦由 **政策決策點（Policy Decision Point, PDP）** 與 **政策強制點（Policy Enforcement Point, PEP）** 組成。信任不是一次性授予，而是「持續性、動態性」評估。
* **證券體系零信任落地方案**：
  * **動態風險評分矩陣（Continuous Risk Engine）**：
    PDP 即時綜合分析四大維度情境數據：
    1. **身分維度**：登入時間、歷史常規操作排程、是否跨越時空不可能位移（Impossible Travel，如 10 分鐘內自臺北與倫敦登入）。
    2. **設備維度**：設備信任分數、端點是否出現未簽名 PowerShell / WMI 執行行程。
    3. **網路情境**：連線 IP 是否列於 F-ISAC 最新惡意情資黑名單、是否來自 Tor 節點或未授權商業 VPN。
    4. **行為異常（UEBA）**：是否突然於非開盤時段大量查詢非名下客戶之交易紀錄。
  * **微隔離與動態降權（eBPF Microsegmentation & Step-up Auth）**：
    PEP 部署於微服務邊界與 API 閘道端。若 PDP 偵測連線風險評級升高，PEP 立即實施**階梯式升級驗證（Step-up Auth）**，要求額外生物特徵驗證；若風險超標，立即透過 Cilium eBPF 封包過濾切斷其網路存取權，將威脅死死限制於單一端點，無法於內網展開橫向移動。
